Governance control acceptance matrix and operational evidence guide

Overview

Purpose
This document defines a single, operational governance matrix that maps control families (RBAC & authentication, audit logging, data residency & retention, secure SDLC, incident response and evidence workflows) to: responsible owners, minimum artifacts required for an external audit, automated collection paths, SLOs/thresholds, and the exception/escalation process. The goal is to make control acceptance decisions repeatable and machine-friendly so that evidence packaging for audits and incident investigations is predictable.

Scope
- Applies to all Redwood-managed services and customer-facing control surfaces (hosted API, console, Dedicated control plane, Private control plane).
- Does NOT replace service-level runbooks; instead it references them as evidence sources.

Audience
- Security operations, compliance, platform engineering, product owners, SREs, and auditors.

Principles
- Single source of truth: every compliance assertion maps to a documented artifact and an automated collection path where possible.
- Least privilege by default: RBAC changes are treated as risky and require evidence.
- Time-bounded evidence: retention and timelines must be explicit and enforced.
- Incident-first packaging: evidence workflows are optimized for post-incident triage and external audit readiness.

Control-level acceptance criteria and evidence examples
1) RBAC & authentication
- Acceptance criteria: role model documented; least-privilege baseline exists; role membership is certified at least quarterly; JIT activation is recorded with session context.
- Required artifacts: canonical role manifest (YAML), quarterly certification snapshots (CSV), IdP audit logs (SAML/OIDC login events), JIT activation events (timestamp, actor, duration, justification).
- Example artifact paths and extraction commands:
  - IdP export (Okta example):
    - curl -H "Authorization: Bearer $OKTA_API" "https://redwood.okta.com/api/v1/groups?limit=200" > /tmp/okta-groups.json
  - Access certification report: /tools/certifications/export --quarter=2025Q4 --format=csv

2) Audit logging
- Acceptance criteria: structured audit stream enabled for all control planes; event schema version pinned; ingestion latency within SLAs; read-only immutable archive created daily.
- Required artifacts: event schema doc, ingestion lag metrics, daily archive manifests (with checksums), export of queryable IDs for critical events.
- Common queries for evidence extraction (example):
  - List all privileged-account token uses for a time window:
    - elasticsearch: POST /_search ? {query: {bool: {must: [{term: {event.type: "token_use"}},{range: { @timestamp: {gte: "2026-01-01", lte: "2026-01-10"}}}]}}}
  - Export pipeline manifest: /ops/logging/pipeline-manifests --date=2026-01-12 --output=manifest.json

3) Data residency and retention
- Acceptance criteria: data mapped to regions, retention policies implemented in lifecycle rules, legal hold process documented and triggered from ticketing.
- Evidence artifacts: data flow diagram (draw.io export), bucket lifecycle rules (JSON), customer-residency contracts, KMS CMK rotation logs.
- Example verification snippet (GCS lifecycle):
  - gsutil lifecycle get gs://redwood-artifacts | jq .rule

4) Secure SDLC
- Acceptance criteria: PRs for production services include threat-model signoff or IAC changes blocked; SCA results must not exceed critical vulnerability thresholds or must have documented risk acceptance.
- Required artifacts: PR sign-off history (with security approver), SCA scan CSV, release manifest with image digests and provenance.
- Gate checklist (required for release):
  1. Security approver signoff present in PR.
  2. SCA vulnerability scan passed gating rules or documented exception.
  3. Signed release artifact with digest and build metadata.

5) Incident response (security)
- Acceptance criteria: evidence bundle created for Sev1/2 incidents within 4 hours, chain-of-custody recorded for any forensic artifacts, remediation validated and closed with post-incident security review.
- Artifact list: incident ticket export (CSV), preserved raw logs, EBS snapshot IDs (if applicable), forensic hash manifest (SHA256).
- Incident evidence collection play (short):
  1. Triage: create incident ticket and tag as "forensic-preserve".
  2. Snapshot: run orchestration job to snapshot log partitions for the window.
  3. Hash: calculate SHA256 for each artifact and record in evidence manifest.
  4. Archive: copy evidence to restricted bucket with KMS key and ACLs.

Operational evidence orchestration patterns
- Evidence manifest standard (JSON lines) fields: artifact_id, control_family, source_path, collector_job_id, sha256, collected_at, owner_team, ticket_id.
- Provenance store must be append-only and store the manifest hash chain; the evidence orchestration service will emit a signed manifest for every audit-pack generation.
- Automated packaging: a request to /internal/evidence/pack?audit_id=XXX will trigger collection jobs and return a pre-signed S3 bundle and manifest.

Exception and risk acceptance process
1. Submit exception request via ticketing classification "control-exception". Include: affected control, rationale, compensating controls, proposed TTL, and owner.
2. Security reviewers perform technical assessment and assign a risk rating (Low/Med/High/Critical).
3. For Med+ risk, route to Security Compliance Council for approval; for High/Critical require CRO sign-off.
4. If approved, exception becomes timeboxed with mandatory mitigation milestones tracked in the ticket. Evidence artifacts required for acceptance are appended to the ticket.

RBAC change & certification cadence (procedural steps)
- Quarterly access certification: automated report generated and emailed to owners. Owners must validate within 14 days. Non-response triggers escalation to manager and then to Security.
- Emergency RBAC change: must be requested via "Emergency Access" workflow, with automatic JIT activation and a required post-hoc review within 7 days.

Audit readiness runbook (quick steps)
1. Intake: Security receives audit request; create audit ticket and assign auditor liaison.
2. Map requested control IDs to matrix rows and required artifacts.
3. Trigger /internal/evidence/pack generation for each required artifact.
4. Validate manifest hashes and generate auditor bundle; produce a summary mapping doc.
5. Deliver bundle via pre-signed URL and record delivery in audit ticket.

SLOs, alerting and monitoring policy
- Audit ingestion latency: 95th percentile < 120s. Alert if > 300s for 5m.
- Evidence orchestration success rate: 99% per audit request. Alert on failure rate > 1% per week.
- RBAC certification completion: 95% on-time; escalate when weekly backlog > 2 cycles.

Example change-control checklist for evidence-related changes
- Update control matrix entry (this doc) and record change in ADR log.
- Add or modify collectors with unit tests and integration tests.
- Deploy collectors behind a feature flag for 48 hours; verify collector success rate > 99.5%.
- Update documentation links and notify Security Council.

FAQ and common audit questions
Q: What if an artifact cannot be recovered?
A: The incident evidence process includes an immediate legal-hold request. If the artifact was ephemeral and unrecoverable, the owner must provide compensating evidence (e.g., pipeline logs, monitoring metrics) and a documented remediation plan.

Q: Who signs off an exception for data residency?
A: Data residency exceptions require Security, Privacy, and the Data Custodian; for customer-impacting exceptions the VP of Product signs off after Legal review.
