Ephemeral GPU Sandbox Lifecycle and Cost Reclamation Playbook

Overview

Purpose: This playbook defines the lifecycle, automation, and billing reconciliation process for ephemeral GPU sandboxes used by engineers and evaluators. It focuses on minimizing wasted spend, ensuring predictable SLAs for sandbox provisioning, and automating reclamation of orphaned/idle GPU resources.

Scope
- Applies to self-service sandbox pools used for CI/eval, experimentation, and short-lived developer workloads.
- Excludes Dedicated production clusters and long-running Private customer deployments.
- Covers provisioning flow (IaC), tagging/ownership, monitoring/alerts, automated reclamation, and billing reconciliation.

Owners and Contacts
- Primary owner: eng-infra GPU Platform (oncall: gpu-platform)
- Secondary owner: CI/Eval Team
- Slack channel: #gpu-sandboxes
- Pager: /incidents/gpu-platform (for high-severity reclamation failures)

SLOs and Financial Targets
- Provision success within 3 minutes (p95) for pre-warmed images.
- Sandbox idle reclamation within 30 minutes of idle detection (automated reclaim action).
- Monthly orphaned GPU spend <= 2% of sandbox budget.
- Accuracy of tag-to-cost attribution >= 98% per billing report.

Lifecycle and Tagging Rules (must be enforced at provisioning)
1) Creation: all sandboxes provisioned via self-serve portal or ci pipelines must include these tags: owner, project, purpose, cost_center, created_by, expiration_ts.
2) Default TTL: 12 hours for ad-hoc dev sandboxes, 4 hours for CI/eval jobs unless extended by explicit workflow.
3) Auto-extension: allowed only via a long-running job token (max 48 hours) and requires approval from owner (email callback).
4) Immutable tag policy: owner and cost_center must not be changed by users; only infra automation can update ttl or expiration_ts.

Lifecycle Timing Reference (table)
| Phase | Default timeout | Action owner | Observability signal |
|---|---:|---|---|
| Provisioning | 3m (p95) | provisioning service | provision-success metric, logs |
| Warm-up | 1m | image service | node-ready metric |
| Active | variable (TTL) | end user | request/throughput metrics |
| Idle detection | 15m | monitoring rule | idle-cpu/gpu metric |
| Reclamation window | 30m after idle | reclamation controller | reclamation-attempt metric |
| Termination grace | 5m | reclamation controller | termination-success log |

Automated Reclamation Flow (step-by-step)
1. Detection: Prometheus rule evaluates GPU utilization (GPU % < 5% and CPU < 10% and no active kube pods attaching) for the tagged sandbox for 15 minutes.
2. Marking: reclamation-controller writes a "pending-reclaim" annotation and sends a Slack DM and email to owner with action buttons.
3. Grace period: owner has 30 minutes to respond. If owner clicks "Request extension", a webhook triggers the extension flow; automation can extend once up to TTL cap.
4. Forced reclaim: on timeout, reclamation-controller runs Terraform destroy (or cloud-API delete) with a reclaim-job-run-id, snapshots logs to S3, and attaches deletion reason metadata to billing records.
5. Post-reclaim report: controller emits an audit event and updates the reconciliation table used by finance.

Terraform / IaC Patterns
- All sandbox modules must expose these variables: owner, cost_center, purpose, ttl_hours, created_by.
- Use a lifecycle policy in terraform to prevent accidental destruction of active user sandboxes: utilize a pre-destroy hook that queries the monitoring API for an "active" tag.
- Example snippet (pseudo-terraform):

resource "aws_instance" "sandbox_gpu" {
  ami           = var.ami
  instance_type = var.instance_type
  tags = merge(var.tags, {
    "created_by" = var.created_by,
    "expiration_ts" = timestampadd("hour", var.ttl_hours, utcnow())
  })

  provisioner "local-exec" {
    when    = "destroy"
    command = "scripts/sandbox_pre_destroy_check.sh ${self.id} || exit 1"
  }
}

- Recommended pattern: keep a lightweight provisioning lambda (or controller) that writes a sandbox manifest to DynamoDB/ETCD with a checksum; reclamation reads manifests rather than cloud tags for authoritative state.

Monitoring, Metrics, and Alerts
- Key metrics to emit: sandbox.provision_success, sandbox.reclamation_attempts, sandbox.reclamation_failures, sandbox.orphaned_cost_daily, sandbox.active_count, sandbox.idle_duration_seconds.
- Alerts:
  - P0: reclamation-controller failure >= 5 failures in 10m -> page gpu-platform (pager-duty).
  - P1: orphaned_cost_daily > $X threshold -> notify #cost-ops and create weekly ticket.
  - P2: provisioning latency > 3m (p95) -> notify eng-infra slack.

Billing Reconciliation and Tag Hygiene
1) Daily job aggregates sandbox manifests, cloud billing exports, and tag audit logs.
2) Matching rules (in order): manifest id -> cloud resource id -> owner tag. If mismatch occurs, mark as "unattributed" and surface to cost-ops.
3) Reconciliation outputs a CSV with columns: date, resource_id, manifest_id, owner, cost_center, charge_usd, reclaim_reason.
4) Weekly correction cycle: cost-ops contacts owners for unattributed costs > $100.

Incident Playbook for Reclamation Failures
1) Detection: alert fires (reclamation-controller failure).
2) Triage steps:
   a) Check controller logs (/var/log/reclaim-controller.log) for stack traces.
   b) Verify IAM credentials for the controller (STS expiration, rotated keys).
   c) Run the reclaim controller in dry-run mode: "reclaim-controller --dry-run --resource <id>".
3) If controller cannot delete due to API quota, escalate to cloud accounts and enable emergency quota bump (use approved emergency change runbook).
4) If controller deleted wrong resources, use snapshots to restore and issue SLA remediation; notify stakeholders and open postmortem if >$1000 lost.

Testing and Chaos Exercises
- Monthly chaos test: randomly select 5% of sandboxes and run a simulated idle-detection to verify reclaim+restore flow.
- CI integration tests: terraform module unit tests must include mocked reclaim-controller hooks.

Operational Play Examples (commands)
- Query pending reclamation: curl -s https://api.internal/sandboxes?state=pending-reclaim | jq '.'
- Force reclaim for resource: reclaim-controller --force --resource <manifest_id> --reason "manual_cleanup"

Rollback and Safety Nets
- Reclamation controller runs in two phases: snapshot -> delete. Snapshots must succeed before deletion. If snapshot fails, controller retries with exponential backoff and alerts after 3 failed attempts.
- Soft delete: maintain a 24-hour "deleted-but-restoreable" window in the manifest store to allow accidental restores.

Operational Run Checklist (for oncall or SRE handling a reclamation incident)
1) Confirm alert and scope.
2) Verify monitoring rules (Prometheus) and recent metric samples.
3) Attempt dry-run reclaim for one resource.
4) If dry-run succeeds, run bulk reclaim in 10% batches with 5-minute pauses.
5) Post-run: generate reconciliation CSV and notify cost-ops.

Appendix: Implementation Notes and Gotchas
- Do not rely solely on cloud tags for ownership: tags can be modified by cross-account processes. Use a manifest store as source-of-truth.
- Be cautious with image warm pools: nodes appearing idle may be reserved for fast provisioning; reclamation rules must respect warm-pool labels.
- Audit logs: ensure every reclamation action includes a pre-signed snapshot link and the reclaim-controller run-id for traceability.
