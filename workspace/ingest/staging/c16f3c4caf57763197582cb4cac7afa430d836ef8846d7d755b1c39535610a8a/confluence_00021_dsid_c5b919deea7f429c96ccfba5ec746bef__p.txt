PRD: Cost What‑If Simulator and Consumption Visibility (Console + SDK)

Summary

This document describes the product requirements, UX flows, backend contracts, rollout plan, and success metrics for the "Cost What‑If Simulator and Consumption Visibility" feature. The goal is to give developers and platform engineers a unified, low‑friction way to understand the cost and performance impact of configuration choices (model variant, batch size, quantization, KV cache, routing policy, SLO targets) before they hit production. The feature includes: a Console wizard, a headless SDK for automation, and a simulation API that mirrors Redwood's runtime economics models.

Audience

- Product and engineering teams evaluating migration from hosted to dedicated/private.
- Customer SREs and platform engineers tuning SLOs and cost budgets.
- Solutions/SEs running onboarding cost projections for enterprise deals.

Goals (What success looks like)

1. Developers can generate an end‑to‑end cost/latency estimate for a defined traffic profile within 30 seconds (interactive mode) or via batch simulation (background jobs).
2. Simulator predictions are within +/- 15% of observed cost for representative workloads across 30 customer pilots after 3 months.
3. 40% reduction in onboarding time for Dedicated customers who use the simulator during migration (measured by time from sales handoff to first production traffic).
4. Expose per‑route and per‑model cost drivers in Console with actionable optimization recommendations (top 3).

Out of scope

- Billing system changes to invoices or contractual language (this is an insights and estimation tool; final billing remains authoritative).
- Real‑time prediction for live production requests (simulator is offline or best‑effort background).

User personas and primary flows

- Developer (self‑serve): Uses Console QuickStart, uploads a small representative trace (or selects a template), toggles model variant and quantization, gets immediate cost/latency delta and a short list of recommended configs.
- Platform Engineer (bulk): Uses SDK to run nightlies that simulate 7 day/30 day traffic windows across multiple affinity policies and produces CSV reports for finance/infra planning.
- Solutions Engineer (sales assist): Runs an onboarding scenario with realistic QPS and gets a packaged recommendation for Dedicated capacity and expected monthly spend range.

Functional requirements

1. Console Wizard
   - Input: traffic profile (QPS, percentiles of sequence length, mix of embeddings vs generation vs chat), optional sample requests (JSON), time window, region.
   - Controls: model variant selector, quantization toggle, batch target, KV cache enabled/disabled, routing policy (latency|cost|affinity), preferred capacity tier (hosted|dedicated|private).
   - Output: interactive dashboard with: estimated tokens/month, estimated monthly cost range (min/median/max), latency P50/P95/P99 estimates, expected GPU hours, confidence band, and top 3 cost drivers with suggestions.
   - Export options: PDF executive summary, CSV scenario results, SDK JSON payload for re‑run.

2. Simulation API / SDK
   - POST /api/v1/simulate with body (see API contract below) that returns a simulation id and async results endpoint.
   - Support synchronous mode for small traces (<= 1000 requests) and asynchronous for larger runs.
   - SDK bindings in Python and TypeScript mirroring Console options.

3. Fidelity to Billing Model
   - Simulator uses the same unit economics as billing metadata service v2 to ensure consistent cost factors (token types, per‑model multipliers, embedding unit conversion).
   - Simulator must include a configurable safety margin (0–20%) to account for variability; default 10%.

4. Recommendation Engine
   - Returns ranked suggestions (e.g., lower precision quantization, smaller model variant, enable prefix caching) with estimated delta to cost and latency and an approximate impact score.

5. Audit & reproducibility
   - Every simulation run is stored with a hashable scenario id, inputs, simulator version, and a reproducible command (SDK CLI example). Runs are retained for 90 days in the Console.

Non‑functional requirements

- Latency: interactive synchronous simulations should return within 30 seconds for small traces; async jobs should complete within 4 hours for 7‑day traffic windows of up to 10M tokens.
- Accuracy: mean absolute percentage error (MAPE) <= 15% against observed charges in pilot customers within first 90 days.
- Cost: simulator compute should be subject to internal quota; typical runs should not exceed 1 vCPU and 512MB memory for small scenarios.
- Security & privacy: sample traces must be optional and scrubbed by default. Customer can opt into retention for reproducibility with explicit consent.

Console UX specification

- Entry points: per‑tenant Overview page (quick card), per‑route settings (simulate this route), and a top‑level "Cost Studio" in product nav.
- Primary visualization panels:
  1) Summary card: tokens/month | est. cost | est. latency P95 | recommendation badge.
  2) Waterfall: cost breakdown by model, request type, batching, caching, and region.
  3) Sensitivity slider: allow interactive adjustment of QPS or batch target and see live cost delta.
  4) Scenario comparison: pin up to 3 scenarios side‑by‑side.
- Accessibility: keyboard navigable controls, color palette meets AA contrast.

Data model and example table (described)

Every scenario persists a flat record with columns: scenario_id, name, owner_user_id, created_at, simulator_version, model_list (comma separated), qps, time_window_days, estimated_tokens, est_monthly_cost_usd_min, est_monthly_cost_usd_median, est_monthly_cost_usd_max, latency_p95_ms, top_cost_drivers (comma separated), exported_files (urls, comma separated).

Recommendation ranking algorithm (high level)

- Score each suggestion by a combined metric: impact_score = normalized_cost_delta * 0.7 + normalized_latency_delta * 0.3 - confidence_bonus.
- Only show recommendations with confidence > 0.5 and expected cost saving > 2%.

Telemetry and observability

- Events emitted: simulation.submitted, simulation.completed, simulation.failed, recommendation.clicked, scenario.exported.
- Required telemetry fields: simulation_id, user_id, tenant_id, simulator_version, runtime_ms, tokens_processed_estimate, models_considered_count.
- Alerts: more than 3 failed simulations in 10m across a tenant triggers pager for infra oncall.

Rollout plan and milestones

1. Alpha (internal): 2026-07-01 to 2026-08-01
   - Console prototype with single model type and static unit economics. Internal testing only.
   - Owners: Asha Patel (product), Daniel Weber (backend), Priya Singh (UX).

2. Private Beta (select customers): 2026-08-15 to 2026-10-15
   - Add SDK, async jobs, recommendations, support for multiple model variants and safety_margin. Pilot with 6 customers (mix of start‑ups and 2 Dedicated customers).

3. General Availability: 2026-11-10
   - Full Console surface, export capabilities, telemetry, stored runs. Public docs and SDK packages.

Operational playbook (day‑to‑day)

- Troubleshooting checklist:
  1) simulation failed -> check simulator logs (service: cost-sim-engine), validate input schema, check billing-meta service connectivity.
  2) large latency -> check async worker queue depth and resize worker pool if > 80% utilized.
  3) accuracy drift -> run monthly calibration job that re‑trains multipliers against observed billing for pilot clients.

- Ownership and escalation:
  - Product owner: Asha Patel (product).
  - Backend owner: Daniel Weber (eng-infra).
  - Observability: SRE oncall; alert channel #prod-cost-sim-alerts.

Security and compliance notes

- Sample traces: scrub PII by default using redaction rules (regex patterns for emails, keys, tokens).
- Simulator does not persist raw request bodies unless customer opts in; opt‑in must be explicit and accompanied by retention TTL.
- All exported artifacts are subject to tenant RBAC and the same SSO policies as Console.

Open questions and risks

1) How to map simulator outputs to invoiceable line items for customers that have custom discounts? (Risk: expectation mismatch). Proposed mitigation: UI callout and additional "apply discount" input for SE workflows.
2) Simulator accuracy on multimodal pipelines is untested. Priority: run focused pilots with multimodal customers in Beta.
3) Potential for customers to rely on simulator for exact billing — clearly label this as "estimate" and add confidence bands.

Appendices

A. CLI/SDK example (Python)

from redwood_sdk import CostSimulator

sim = CostSimulator(api_key="$REDWOOD_KEY")
scenario = {
  "scenario_name": "migration-test",
  "region": "eu-central-1",
  "time_window_days": 30,
  "traffic_profile": {"qps": 8, "mix": {"chat": 0.8, "embeddings": 0.2}, "seq_len_p95": 512},
  "models": ["redwood-7b-compat-4bit", "redwood-7b-fp16"],
  "kv_cache_enabled": true
}
run = sim.create_simulation(scenario)
print(run["simulation_id"])

B. Acceptance criteria

- SDK functions available and pass integration tests against staging billing metadata.
- Pilot accuracy MAPE <= 15% across at least 5 pilot customers.
