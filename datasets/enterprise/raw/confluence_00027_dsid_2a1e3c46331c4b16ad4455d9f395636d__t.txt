Tenant-heavy Ingest Surge Mitigation: Connector Patterns and Operational Playbook

Overview

This playbook documents proven connector integration patterns and operator runbooks for handling tenant-heavy ingest surges against Redwood inference endpoints (hosted, dedicated, and private). It is intended for solutions engineers, customer success, SREs, and partner integrators who build connectors or bridges that forward high-volume telemetry, batched requests, or streaming job workloads into Redwood.

Goals
- Prevent noisy-tenant surges from degrading other tenants or customer SLAs.
- Provide single-source connector configuration templates for backpressure, graceful degradation, and safe failover.
- Define operational checks, monitoring signals, and an on-call escalation ladder.

Scope
- Applies to connectors that: ingest text payloads for generation, embeddings, or reranking; proxy tenant traffic; or batch large historical backfills.
- Covers both synchronous (API) and asynchronous (job/batch) ingestion patterns.
- Does NOT cover hardware-level GPU autoscaling (see eng-infra docs).

High-level Patterns (when to use each)
1) Client-side rate shaping (ideal for SaaS partners)
   - Best when you control the client SDK or agent.
   - Enforce tenant-level QPS/TPU caps and token limits proactively.
2) Connector-side adaptive throttling (recommended default)
   - Connector maintains per-tenant token counters and request queues; adjusts ingress windows based on downstream latency and error rates.
3) Burst cache + queueing with prioritized dispatch
   - For bursty workloads: short-term KV/prefix cache for repeated prompts + prioritized consumer queue to dispatch high-value requests first.
4) Degraded-mode fallback to lower-cost model variants
   - Fall back to quantized or smaller model variants when latency SLOs break. Useful in Dedicated and Private where model variants are available.
5) Backfill and bulk job isolation
   - Run large backfills on isolated routing paths and quota pools; never share production routing with real-time traffic.

Connector Architecture (text diagram)
- Ingress -> Per-tenant ingress limiter -> Priority queue (hot/warm/cold) -> Dispatch worker pool -> Redwood proxy (smart routing) -> Redwood inference endpoints
- Optional: Local caching layer and metrics exporter between queue and dispatch.

Required Preconditions
- Tenant quotas configured in Redwood console or via API (min and max token caps).
- Observability hooks configured: request tracing, per-tenant latency histograms, error counters, and token-metering.
- Circuit-breaker library available in connector runtime (examples use circuitbreaker v1.2).

Connector Configuration Examples
1) Per-tenant sliding window token limiter (pseudo-YAML)
---
# tenant rate limiter
window_seconds: 60
max_tokens_per_window: 10000
burst_allowance: 1.5
priority_buckets:
  - hot: 0.6    # 60% capacity reserved for high-priority routes
  - warm: 0.3
  - cold: 0.1
---

2) Adaptive dispatch strategy (pseudo-config)
---
autoscale:
  enabled: true
  target_latency_ms: 200
  min_workers: 2
  max_workers: 100
  cooldown_seconds: 30
backoff:
  initial_ms: 100
  max_ms: 5000
  factor: 2.0
---

Implementation recipes
A) Synchronous connector (recommended) - Validate incoming request size and tokens; reject with 429 when tenant quota exceeded.
- Maintain a token bucket per tenant persisted in Redis for cross-instance coordination.
- If downstream latency > target_latency_ms for 3 consecutive windows, reduce per-tenant throughput by multiplier 0.5 and emit event to telemetry.

B) Asynchronous large-batch worker - Accept job payloads, store in durable queue (SQS/Kafka), run preflight estimator that calculates token estimate, and schedule against a backfill queue with dedicated capacity pools.
- Mark job "low-priority" when it would exceed daily tenant quota; schedule to off-peak windows.

C) Prioritization example
- Tags: critical (SLAs), interactive (real-time), background (backfills).
- Dispatcher policy: always reserve 30% of capacity for critical and interactive. Background only consumes spare capacity or dedicated backfill pool.

Monitoring & Telemetry (what to track)
- Per-tenant token consumption (tokens/min, tokens/day)
- 95th/99th latency per tenant and per route
- 429 rate and quota rejections per tenant
- Queue depth by priority bucket
- Dispatch worker saturation (gpu_utilization, inflight_requests)
- Model fallback events and quality-regression alerts
- Cost metrics: estimated tokens billed vs allowed

Suggested SLOs and thresholds (connector owner to adopt)
- Target P95 end-to-end latency: 300ms for interactive routes, 1.5s for batch submission acceptance.
- Queue depth alert: queue_depth > 500 for 5m -> page oncall.
- Token spike alert: tenant token rate > 3x baseline for 5m -> create incident priority P2.
- Error ratio alert: 5xx_rate > 2% over 3m -> page P1.

Runbook: Surge detected (step-by-step)
1) Detection: Alert triggered (token spike OR queue_depth OR p99 latency).
2) Triage: Oncall examines per-tenant metrics, request traces, and Redwood console SLO page.
3) Immediate mitigation (5–15 minutes):
   - Throttle the offending tenant to safe cap (e.g., 50% of capacity) using Redis token bucket override.
   - If available, shift tenant to a dedicated low-priority pool or pause background jobs.
   - If customer has a go-live playbook, contact CS lead to coordinate intentional throttling.
4) Short-term containment (15–60 minutes):
   - Enable degraded-mode: route tenant to smaller model variant or quantized profile.
   - Add temporary rule in gateway to drop non-critical requests (e.g., trace-only or sampling).
5) Recovery & Postmortem (>60 minutes):
   - Maintain reduced cap until token rate returns to baseline for 30m.
   - Open RCA with customer and document actions in ticket; include traces and telemetry snapshots.

Escalation & Communication matrix
- If mitigation fails in 30 minutes escalate to Tier 2 SRE and CS Director.
- Customer communication template (first 30 minutes): acknowledge the surge, confirm an active mitigation, and provide ETA 60–90 minutes.
- Post-incident follow-up: share RCA and recommended client-side changes (e.g., batching, retry backoff).

Quality safeguards for degraded-mode fallbacks
- If switching to smaller model variant, run a validation prompt set (20 representative prompts) and measure fidelity threshold (>= 90% acceptable). If below threshold: avoid fallback and instead tighten throttling.

Testing & QA checklist before enabling connector in production
- Load test with per-tenant mix: 80% interactive, 15% background, 5% critical.
- Verify token metering persists across restart and multiple instances.
- Chaos test: simulate network partition to Redis; ensure connector fails open-to-safe-mode (reject new requests with 503 rather than silently accept).
- Confirm alerts and dashboards surface tenant attribution in < 60s.

Operational notes and best practices
- Always prefer rejection (429) with clear error body for quota vs silent delay.
- Maintain a customer-specific throttle override table for known forged bursts (e.g., scheduled batch imports).
- Store per-tenant historical baseline metrics for anomaly detection rather than relying on global thresholds.
- Keep model fallback as a last-resort; measure downstream quality drift and notify customer when used.

Customer Success Playbook (how CS teams should engage)
- Pre-onboarding: document expected daily token volume and peak profile; agree on backfill windows.
- Go-live: run a pre-go-live surge simulation with the customer (30–60 minutes) and validate connector behavior.
- Post-incident: recommend engineering changes (batching, client SDK backoff), and schedule a follow-up health QBR focusing on inference economics.
