Field Handoff, Tenant Surgery, and Safe Cutover Playbook

Summary
This playbook describes the operational pattern we call 'tenant surgery' — a safe, auditable process for making targeted changes to a single tenant or a small tenant cohort in a Redwood Private deployment (VPC or on‑prem). It focuses on three phases: field handoff to customer operators, pre-cutover compatibility validation (packaging + network + KMS), and staged cutover with guaranteed rollback. Use this for major model swaps, KV cache migrations, network boundary changes, or tenant-level capacity rebalancing.

Audience
- Field engineers and customer operators performing tenant cutovers
- Platform SREs owning rollback automation and observability contracts
- Solutions engineers validating customer compatibility and acceptance criteria

Assumptions and scope
- Applies to Redwood Private (VPC and air‑gapped on‑prem) deployments managed under our operator handoff contract.
- Assumes existing telemetry ingestion and per-tenant tracing are active.
- Not for full fleet upgrades (see incremental-stateful-upgrade strategy doc).

High-level goals
1) Minimize tenant downtime: target < 2m P99 for ephemeral cutover operations, non‑disruptive where possible.
2) Provide deterministic rollback with preserved evidence for compliance.
3) Ensure customer-run acceptance tests are reproducible and auditable.
4) Limit blast radius: one tenant or tenant cohort at a time unless explicit approval.

Ownership and roles
- Field Lead (owner): executes cutover with customer operator present.
- SRE Oncall: watches platform SLOs and has escalation rights to abort cutover.
- Release Engineer: prepares artifacts, signs images, and validates compatibility gates.
- Customer Operator: performs network/KMS handshakes and runs acceptance tests.
- Compliance/Support: receives evidence bundle on completion for audit.

Prerequisites (checklist)
- Release artifacts: image SHA, signature, bill of materials (BOM), and quantization profile.
- Compatibility matrix: CPU/GPU arch support, CUDA/cuDNN versions, container runtime.
- Network proofs: BGP peering or VPC peering established, IP allowlists updated.
- KMS/HSM keys: test wrap/unwrap confirmed in staging.
- Telemetry: per-tenant metrics (latency, token rate, error rate) streaming to observability.
- Acceptance tests: deterministic prompt set, expected output hash range, latency budget.

Pre‑field handoff tasks (release engineer)
1. Generate evidence bundle: artifacts list, checksums, container image signature, upgrade checklist.
2. Run deterministic offline simulation against cached KV snapshots (if model change touches KV layout). Store results and diffs.
3. Publish canary/compatibility policy (YAML) to operator API and attach to evidence bundle. Example policy:

---
canary: 
  cohort_size: 1
  success_criteria:
    p50_latency_ms: 120
    error_rate_pct: 0.5
    semantic_regression_score: 0.95
  max_duration_minutes: 30
---

4. Verify signed images on target runtime: run sha256sum and container-sig verify.

Field handoff checklist (operator + field lead)
- Confirm maintenance window and customer notifications sent.
- Confirm access: operator SSH jumpbox, RBAC token, KMS policies.
- Validate telemetry forwarders are healthy (last 5m data present).
- Confirm snapshot of tenant state and KV cache created and archived.

Staged cutover procedure (step by step)
Stage 0 — Preflight validation (non-disruptive)\1. Run acceptance smoke tests against a mirrored staging path:
   - run: ./rci acceptance-run --tenant <tenant-id> --suite smoke
   - verify output hashes within tolerance.\2. Confirm routing policy: requests destined for tenant traffic must be tag‑routed to a canary host pool.

Stage 1 — Canary (single tenant instance)\1. Deploy artifact to canary host pool with prefix canary-<tenant>-<ts>.
   - kubectl apply -f canary-deployment.yaml --namespace=tenant-<id>
2. Observe telemetry for max_duration_minutes from canary policy. Key metrics:
   - inference_latency_p50/p90/p99
   - inference_error_rate
   - kv-cache-hit-rate
   - cost_per_token_estimate
3. Run customer acceptance suite: run canonical prompts and match semantic_regression_score >= threshold. Use eval harness sample command:
   - python -m redwood.eval.run --tenant <tenant-id> --suite canary_prompts --baseline /evidence/baseline.json
4. If criteria pass, promote to cohort. If not, trigger immediate rollback (see rollback cookbook).

Stage 2 — Cohort expansion (progressive ramp)
1. Expand from 1 -> 5 -> 20% -> 50% of tenant traffic using traffic-steering policy with 30m stabilization windows. Example traffic policy fragment:

trafficRouting:
  - step: 1
    weight: 1
    durationMinutes: 30
  - step: 2
    weight: 5
    durationMinutes: 30
  - step: 3
    weight: 20
    durationMinutes: 60
  - final
    weight: 100

2. At each step verify acceptance tests and SLOs; preserve evidence bundle of metric snapshots.
3. Pause and investigate if p99 latency exceeds target or error rate spikes > 2x baseline.

Rollback cookbook (deterministic, auditable)
Principles:
- Rollback must be automatic for safety-critical thresholds or manual with documented approval otherwise.
- Preserve post-failure evidence: traces, per-token logs (redacted), and the artifact that caused the failure.

Automatic rollback triggers\- inference_error_rate > 5% sustained for 5 minutes\- p99 latency > 5x baseline for 3 consecutive windows\- semantic_regression_score < 0.85 on canary prompts

Rollback steps\1. Set traffic weight back to last stable target (or 0 for immediate cutover abort).
   - CLI: redwoodctl traffic set --tenant <id> --policy previous-stable\2. Drain canary hosts: kubectl cordon/evict with grace period 30s.
3. Revert routing tables and BGP announcements if changed.
4. Run integrity validation: KV snapshot replay and state hash comparison.
5. Archive evidence and open a postmortem ticket with initial severity and impact.

Postcutover validation and evidence package
- Deliverable artifacts to customer and compliance: signed image SHA, canary run results, metric snapshots, logs (redacted), and rollback timeline.
- Postcutover acceptance: customer to run full acceptance suite within 24 hours.
- SRE to monitor SLOs for 72 hours and sign off.

On‑prem packaging compatibility notes
- Minimal runtime footprint: ensure staging images are built with BUILD_TAG=runtime-minimal to avoid optional tools requiring internet.
- FIPS/KMS: ensure our kmod/driver versions match vendor HSM firmware versions documented in the BOM.
- Airgap Caching: provide a tarball of container layers and a checksum manifest. Import steps for customer operator:
  1. scp layers.tar.gz to jumpbox
  2. ctr -n moby images import layers.tar.gz
  3. container-sig verify --artifact <image>.sha256

Telemetry and alert thresholds (operator defaults)
- p50 latency: baseline + 30ms alert (warning)
- p99 latency: baseline + 200ms alert (critical)
- error_rate_pct: > 1% warning, > 3% critical
- kv_cache_hit_rate: < 70% warning
- token_consume_5m_rate: sudden drop > 50% -> investigate routing 

Testing matrix and customer acceptance criteria (table)
| Test | Purpose | Pass criteria | Owner |
| --- | --- | --- | --- |
| Smoke prompts | Verify liveness and basic correctness | 100% run success | Field Lead |
| Regression eval | Semantic parity against baseline | cosine >= 0.95 | Customer + SE |
| Latency profiling | Validate tail latency | p99 <= 250ms | SRE |
| KV replay | Ensure stateful requests return consistent results | state_hash match | Release Eng |

Communication templates
- Precutover notification: include maintenance window, risk, rollback plan, contact list.
- Abort notification: time of abort, reason, immediate impact, next steps.
- Completion note: duration, artifacts delivered, request for customer sign-off.

Recordkeeping and compliance
- All cutovers must have a ticket in the deployment tracker with linked evidence bundle.
- Evidence retention: 12 months for regulated customers, 90 days default.
- For restricted data workloads, export telemetry at reduced fidelity and include data handling justification.

Common failure modes and mitigations
- Failure: semantic regression on edge prompts. Mitigation: roll back and schedule a targeted fine-tuning or prompt-filter patch.
- Failure: KMS unwrap errors post-cutover. Mitigation: revert key policy change, re-run test unwrap flow, escalate to KMS vendor.
- Failure: slow p99 due to KV cache cold start. Mitigation: pre-warm cache with synthetic traffic to reach target hit rate.

        - name: TENANT_ID

- Scope of impact (tenants, requests/minute, time window)
- Root cause hypothesis and next steps
