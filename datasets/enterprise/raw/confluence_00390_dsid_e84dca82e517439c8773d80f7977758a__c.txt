Console UI Design Spec: Batching Recommendations (SLO Tiers) + “Why this profile”

## Summary
This document specifies how **Redwood Console** surfaces tiered batching defaults (Fast / Standard / Cost-efficient) for operators, including:
- Where tier selection appears in Console
- How Console provides **recommended tier hints** per route/model policy
- How Console explains **“Why this profile”** with clear reason codes and workload signals
- How Console reflects effective configuration when overrides exist (customer override > route policy > tier default)

The goal is to make batching configuration **safer and more automatic**, while keeping enterprise operators in control and enabling fast diagnosis when latency/cost shifts.

## Background
Runtime 1.22 introduces **workload-aware batching defaults** mapped to three customer-facing SLO tiers. While runtime chooses the effective batching profile at request time, Console must:
1) Make it easy to pick a tier intentionally (or understand the default).
2) Show what is currently effective (including overrides).
3) Provide actionable explanations that help customers trust the system and troubleshoot regressions.

## Goals
1. **Tier selection is discoverable and consistent** across Hosted API routes and Dedicated deployments.
2. Operators can see:
   - Their current configured tier (or “Use default”) for each route/model policy
   - The **effective tier** being applied (after overrides)
   - A **recommendation** based on observed workload (when available)
3. Operators can answer “why is this tier/profile being used?” via:
   - Human-readable explanations
   - Structured reason codes
   - Direct links to relevant dashboards and recent changes
4. Provide guardrails and clear warnings to reduce foot-guns (e.g., selecting Cost-efficient for strict streaming p99).

## Non-goals
- Real-time per-tenant auto-tuning controls in the UI (Console will display recommendations and allow tier selection/overrides, not expose internal knobs like max_wait_ms directly for most users).
- Cross-region routing policy configuration redesign (Console will integrate with existing routing/policy screens).
- Full debugging of request-level scheduling decisions (Console will provide aggregated explanations and reason-code breakdowns, not per-request trace exploration as a primary workflow).

## Primary personas & jobs-to-be-done
### Persona A: Hosted API operator (startup / mid-market)
- Wants a safe default and a simple choice: “I need lowest latency” vs “I want lower cost.”
- Needs a clear recommendation and confidence in expected outcomes.

### Persona B: Enterprise platform operator (Dedicated)
- Manages multiple routes and teams.
- Needs precedence clarity: “Why didn’t my override apply?”
- Needs auditability: “Who changed tier selection and when?”

### Persona C: SRE / on-call
- Needs quick correlation between tier selection and latency regressions.
- Needs dashboards and reason-code breakdowns to reduce time-to-mitigation.

## IA: Where tier selection appears in Console
Tier selection appears in three places (in priority order):

1) **Route Settings → Performance** (primary entry point)
   - For route owners configuring behavior per endpoint.

2) **Model Policy → Inference Defaults** (for org-level defaults)
   - For platform teams standardizing across many routes.

3) **Dedicated Cluster → Overrides** (Dedicated-only)
   - For dedicated operators applying tenant/cluster-level overrides with explicit precedence.

Console should keep the labels and controls identical across these views.

## Core UI components
### 1) Tier Selector control (shared component)
**Label:** Batching tier

**Options:**
- Use default (recommended)
- Fast
- Standard
- Cost-efficient

**Help text (collapsed):**
“Controls batching behavior to trade latency vs cost. Defaults are workload-aware and may adjust within the selected tier.”

**Help link:** “Learn about batching tiers” (links to public docs once launched; internal link pre-launch).

**Validation & warnings:**
- If Streaming is enabled and user selects Cost-efficient, show warning:
  “Cost-efficient may increase time-to-first-token and tail latency for streaming routes.”
- If route has a published SLA target in Fast tier and user selects Standard/Cost-efficient, show confirmation with SLA reminder.

**Read-only mode:** If user lacks permissions, show selected value + “Request access to edit.”

### 2) Recommendation Card (“Recommended tier for this route”)
Displayed on Route Settings → Performance and Model Policy → Inference Defaults.

**Card fields:**
- Recommended tier (e.g., “Standard”)
- Confidence (High / Medium / Low)
- Primary drivers (2–3 bullets)
- “Why this recommendation?” link (opens detail drawer)

**When shown:**
- Shown when we have sufficient observed traffic to compute workload signals.
- Hidden (or replaced with empty state) when insufficient traffic.

**Empty state copy:**
“Not enough recent traffic to recommend a tier yet. Once this route sees sustained usage, we’ll suggest a tier based on prompt length, streaming, and concurrency.”

### 3) “Why this profile?” drawer (explanations)
A right-side drawer that explains either:
- Why a tier is **recommended**, or
- Why a tier/profile is **effective** (including overrides and constraints)

The same drawer is used from:
- Recommendation Card → “Why this recommendation?”
- Effective tier badge (see below) → “Why is this effective?”
- Dedicated Overrides page → “Why is this route using X?”

**Drawer sections:**
1) Effective configuration summary
2) Signals observed
3) Reason codes (with counts and definitions)
4) Expected impact
5) Links: dashboards, recent changes, docs

### 4) Effective Tier Badge + Precedence indicator
Every route row and route detail header shows:
- **Configured:** (Use default / Fast / Standard / Cost-efficient)
- **Effective:** (Fast / Standard / Cost-efficient)

If Effective != Configured, show a small “Override applied” chip. Clicking opens “Why this profile?” drawer.

**Precedence line (always shown in drawer):**
“Precedence: Customer override > Route policy > Org model policy > Tier default > Runtime safe fallback”

## Screen-level specs
### A) Routes list (table)
Add columns:
- Configured tier
- Effective tier
- Recommendation (optional badge: “Recommended: Standard”)

**Row actions:** “Edit tier” opens route settings modal (or navigates to Route Settings → Performance).

### B) Route Settings → Performance
Layout:
1) Batching Tier selector (configured)
2) Effective tier & explanation link
3) Recommendation card
4) Observability quick links

**Observability quick links:**
- Latency (p50/p95/p99) by tier
- Batch size distribution
- Queue depth / admission control events
- Cost per 1K tokens (where available)

**Copy for Effective tier line:**
“Effective tier (currently applied): **Standard** · Last 24h · Why?”

### C) Model Policy → Inference Defaults
For org-level admins.

Controls:
- Default tier for routes that select “Use default”
- Per-model-family constraints banner (read-only)

**Constraints banner example:**
“Some model variants do not support all profiles (e.g., quantization compatibility). Console will fall back to the closest supported profile and record a reason code.”

### D) Dedicated Cluster → Overrides (Dedicated only)
Purpose: make override precedence explicit.

UI sections:
1) Tenant override table (tenant → tier override)
2) Route override table (route → tier override)
3) “Effective configuration explorer” (search route/tenant, show the chain)

**Key requirement:** The UI must prevent ambiguity by displaying:
- Where the override was set
- Who set it
- When it was last changed
- Whether it is currently in effect

## “Why this profile?” drawer: data model + copy
### 1) Effective configuration summary
**Fields:**
- Effective tier: Standard
- Effective profile name (optional, internal): e.g., “std.v3.h100.chat_mixed”
- Source: “Route policy” / “Tenant override” / “Tier default” / “Runtime fallback”
- Time window: last 24h (dropdown: 1h / 24h / 7d)

**Source definitions:**
- Tenant override: Dedicated only
- Route policy: route-level selection in Console or API
- Org model policy: org-level default tier
- Tier default: runtime-chosen within tier based on signals
- Runtime fallback: safety fallback due to constraints/overload

### 2) Signals observed (aggregates)
Display as small metric tiles with tooltips:
- Streaming % (e.g., 82%)
- Prompt length distribution (p50/p95 input tokens)
- Output length distribution (p50/p95 output tokens)
- Concurrency (p50/p95 in-flight)
- Overload events (admission control, shed) count

**Tooltips should be explicit about sampling:**
“Computed from sampled request metadata. Does not include request content.”

### 3) Reason codes (structured explanations)
Show a ranked list of reason codes with % of requests in time window.

**Example display:**
- 61% — TIER_DEFAULT_SELECTED
- 18% — STREAMING_FAST_PREFERENCE
- 11% — OVERLOAD_MODE_ACTIVE
- 10% — MODEL_CONSTRAINT_FALLBACK

**Reason code definitions (UI copy):**
- TIER_DEFAULT_SELECTED: “No override was set; runtime selected the default profile for the chosen tier.”
- ROUTE_TIER_OVERRIDE: “A route-level tier was configured and applied.”
- TENANT_TIER_OVERRIDE: “A tenant/cluster-level override was applied (Dedicated).”
- MODEL_CONSTRAINT_FALLBACK: “Requested tier/profile was not supported for the active model variant; runtime chose the closest compatible profile.”
- OVERLOAD_MODE_ACTIVE: “Cluster was under load; runtime applied overload safeguards (e.g., backpressure or modified batching) to protect stability.”
- STREAMING_FAST_PREFERENCE: “High streaming usage led to a latency-protective selection within the tier.”
- LONG_PROMPT_MIX_DETECTED: “A heavy long-prompt mix reduced safe batch growth to protect p99 latency.”

**Important:** Console should not expose internal scheduler knobs, but may show a short note: “This selection may adjust batching wait budget and maximum batch tokens.”

### 4) Expected impact (tier explainer)
When a user is viewing a recommendation or considering a change, show:
- “What you should expect” bullets for that tier
- “Best for” and “Not ideal for”

**Fast:**
- Expect: best p99 latency; lower throughput under concurrency.
- Best for: streaming chat, interactive UX.
- Not ideal for: batch jobs, non-interactive summarization at high volume.

**Standard:**
- Expect: balanced latency and cost.
- Best for: mixed workloads, typical SaaS routes.

**Cost-efficient:**
- Expect: lower $/1K tokens; higher tail latency risk.
- Best for: asynchronous or non-streaming workloads.
- Not ideal for: strict p99 SLAs, highly spiky concurrency.

### 5) Links
Always include:
- “View tier dashboards” (deep link to Observability dashboard filtered by route/model/region)
- “View recent changes” (audit log filtered to this route/model policy)
- “Docs: batching tiers”

## Interaction flows
### Flow 1: New route defaults
1) User creates route.
2) Default selection is “Use default”.
3) Effective tier shows “Standard” (unless org default is different).
4) Recommendation card is hidden until traffic is sufficient.

### Flow 2: User changes tier
1) User selects a tier from dropdown.
2) Console shows inline warning if risky combination (e.g., streaming + cost-efficient).
3) User saves.
4) Confirmation includes:
   - “Change will roll out within ~N minutes.”
   - “Monitor p99 latency and queue depth for the next 30 minutes.”
5) Audit log entry is created.

### Flow 3: Effective != Configured (override/constraint)
1) User sees “Configured: Fast” but “Effective: Standard (Override applied)”.
2) Click “Why?” opens drawer.
3) Drawer shows:
   - Source: “Model constraint fallback” or “Tenant override”
   - Reason code breakdown
   - Link to the exact override setting page (Dedicated) or model policy constraints.

### Flow 4: Regression troubleshooting
1) SRE sees latency regression.
2) In Console route header, they open “Why this profile?”
3) They see OVERLOAD_MODE_ACTIVE increase and admission control events.
4) They click dashboards (queue depth, batch size distribution).
5) If needed, they set tier to Fast temporarily (or disable tiered defaults via existing feature flag tooling outside Console; Console provides link to internal runbook).

## Permissions & auditability
### Permissions
- Route tier editing: route owner + org admin
- Org model policy tier editing: org admin only
- Dedicated tenant overrides: Dedicated admin only

### Audit log entries
For any change to tier config/override:
- Actor
- Timestamp
- Object (route / model policy / tenant override)
- Old value → new value
- Optional note (“Temporary mitigation for incident INC-xxxx”)

## Telemetry requirements (Console instrumentation)
Console should emit client-side events for:
- Viewed Recommendation Card
- Opened “Why this profile?” drawer
- Copied reason code list
- Changed tier (attempted/succeeded/failed)

Additionally, Console must be able to query (server-side):
- Effective tier distribution for selected time window
- Reason code breakdown
- Workload signal aggregates
- Last-known effective profile name (optional; internal)

## Content design / terminology
### Tier naming
Customer-facing tier names are fixed:
- Fast
- Standard
- Cost-efficient

Do not use “realtime” or “throughput” as tier labels in Console UI.

### Avoid over-promising
Console copy must avoid guaranteeing specific latency numbers. It should reference the SLO tier definitions page for targets and explicitly note variability by model, region, and workload.

### Recommended copy snippets
- “Recommended tier” badge tooltip:
  “Based on your recent traffic patterns (streaming, prompt length, concurrency). Review ‘Why’ for details.”

- “Use default” helper:
  “Default selects a tier profile that aims to meet the tier’s latency SLO while improving throughput.”

## Edge cases & failure modes
1) **Insufficient traffic** → no recommendation; show empty state.
2) **Telemetry gaps** (metrics delayed) → show “Data unavailable” with last successful timestamp.
3) **High-cardinality protection** → if reason code breakdown is truncated, show:
   “Some low-volume reason codes are grouped as ‘Other’ to reduce telemetry overhead.”
4) **Incompatible model variant** → show clear fallback explanation + link to model compatibility.
5) **Overload mode** → show banner:
   “Cluster is in overload protection mode; effective behavior may differ temporarily.”

## Accessibility & UX requirements
- Tier selector must be fully keyboard navigable.
- Drawer must trap focus and be screen-reader friendly.
- Color is not the only indicator for warnings; include icon + text and ARIA labels.

## Open questions
1) Should Recommendation Card show a single recommended tier, or a ranked list (“Top choice” + “Alternative”)? Current proposal: single recommended tier with explanation.
2) Should we expose “effective profile name” to customers? Current proposal: show only to internal users; for external users show “Effective tier” + reason codes.
3) How do we handle routes with multiple models behind routing? Proposal: recommendation computed per route, but “Why” drawer allows switching model/region filters.

## Rollout plan (Console)
1) Internal-only behind feature flag: `console.tiered_batching_ui`
2) Enable for Hosted API beta customers (subset)
3) Enable for Dedicated opt-in orgs
4) General availability once:
   - Reason code pipeline is stable
   - Dashboard deep links are live
   - Support playbook and docs are published
