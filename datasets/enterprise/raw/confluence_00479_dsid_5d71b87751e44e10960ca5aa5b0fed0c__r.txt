Runtime Trace Correlator and Event Reconciliation Playbook

Summary
-------
This runbook describes the recommended operational process and commands to correlate end-to-end request traces with low-level kernel dispatch events and GPU timeline samples, detect event mismatches ("reconciliation failures"), and perform remediation and post-incident analysis. It is intended for SREs and runtime engineers responding to tail-latency, unexplained cost spikes, or transient model-swap oscillations where higher-level traces (API/ingress) do not match kernel-level telemetry.

When to use
-----------
- Persistent or recurring tail latency (>99.9th percentile) with no clear API-level throttling.
- Cost anomalies where per-token compute does not match expected kernel time.
- Model swap or variant fallback events observed in control plane logs but no downstream kernel activity.
- Kernel timeouts, stalled GPUs, or delayed KV cache warmups that manifest as opaque request slowdowns.

Owner & escalation
------------------
- Primary on-call: eng-sre/runtime-sli on-call.
- Secondary: runtime-kernel team (pager) if kernel or GPU hang suspected.
- Escalate to infra on-call for suspected hardware/driver issues.
- Post-incident owner: person who closes the incident must schedule a postmortem in 72 hours.

Prerequisites and telemetry
--------------------------
Ensure the following telemetry streams are available and not in degraded mode before starting:
- request-traces (sampled via trace-collector; trace-id present in headers x-rw-trace-id)
- kernel-events stream (kernel-dispatcher -> event bus) with event_id and parent_request_id
- gpu-timeline samples (per-device microsecond timestamps)
- kvcache-metrics and session-affinity logs
- runtime-proxy and model-router logs at info level

Minimum retention and sampling recommendations:
- request-traces: 1% deterministic sampling for production; increase to 10% during investigation
- kernel-events: full capture for at least 6 hours around incident window
- gpu-timeline: rolling 1-hour window, sampled at 100Hz aggregation for latency spikes

Step-by-step procedure
----------------------
1) Capture incident window and identify a representative trace
   - Timebox: pick 5 minutes around alert onset and 30 minutes before for baseline.
   - Query traces:

   ```bash
   # increase sampling if possible for live investigations
   curl -s "https://obs-api.internal/v1/traces?start=2025-09-10T12:10:00Z&end=2025-09-10T12:15:00Z&min_duration_ms=200" \
     -H "Authorization: Bearer $OBS_API_KEY" | jq . | less
   ```

   - Identify a trace with full path: ingress -> runtime-proxy -> model-router -> kernel-dispatcher. Note the x-rw-trace-id and request_id (request-id header).

2) Map high-level trace spans to kernel events
   - Kernel events contain fields: {event_id, parent_request_id, kernel_name, start_us, end_us, device_id, reason}. Use parent_request_id to map to request_id.
   - Example kernel-events query (Elasticsearch/ESQL):

   ```sql
   SELECT event_id, parent_request_id, kernel_name, start_us, end_us, device_id, reason
   FROM kernel-events
   WHERE parent_request_id = 'req-1234' AND timestamp BETWEEN '2025-09-10T12:09:30Z' AND '2025-09-10T12:15:30Z';
   ```

   - If parent_request_id is missing: search by trace timestamp +/- 50ms on same host/slot and correlate by kernel start_us approximate to span.start_timestamp_us.

3) Reconciliation rules and heuristics (event matching algorithm)
   - Exact-match: trace.request_id == kernel.parent_request_id -> mark reconciled.
   - Heuristic match: if exact-match absent, match by host, GPU device_id, and kernel start timestamp within +/- 2500us of span boundary.
   - Unmatched span classification:
     - Missing-kernel: high-level span present, kernel event absent => suspect routing/fallback or kernel dispatch failure.
     - Orphan-kernel: kernel event with no active high-level trace => likely system-level background task or delayed trace sampling.
     - Delayed-commit: kernel start occurs but no end_us recorded -> suspect watchdog or driver hang.

4) Run automated reconciliation query and produce summary report\
   - Use the provided connector script (trace-correlator) on the runbox:

   ```bash
   ./tools/trace-correlator --trace-id req-1234 --window 30s --output /tmp/recon-req-1234.json
   cat /tmp/recon-req-1234.json | jq .summary
   ```

   - Expected output: counts for reconciled, missing-kernel, orphan-kernel, delayed-commit.

5) Remediation actions by category\
   - Missing-kernel:
     1. Check model-router logs for "no-capacity" or "variant-mismatch" for the affected trace-id.
     2. If routing indicates fallback to another region/tier, verify that cross-region routing is completing and that kernel-dispatcher is reachable.
     3. If model was swapped mid-request, run the model-swap audit:

   ```bash
   curl -s "https://control-plane.internal/v1/rollouts?request_id=req-1234" -H "Authorization: Bearer $CP_API" | jq .
   ```

     4. If routing and control-plane look healthy, raise a kernel-dispatcher debug request to capture next 100 dispatch attempts and escalate to kernel team.

   - Orphan-kernel:
     1. Check whether the kernel was part of a background eviction, prefetch, or garbage collection by inspecting kernel_name and reason.
     2. If orphaned kernel time is significant (>100ms), investigate whether tracing sampling missed the parent due to rate limits. Consider increasing request-traces sampling temporarily.

   - Delayed-commit / GPU hang:
     1. Immediately check GPU watchdog metrics and driver logs on node.
     2. If kernel end_us missing, perform a soft-reset on the dispatcher lane (non-destructive) by toggling lane draining: `curl -X POST https://admin.internal/dispatcher/lane/drain?lane=lane-7`
     3. If soft-reset fails, escalate to infra; capture a full GPU dump and attach to incident.

6) Short-term mitigations to restore SLOs\
   - Activate canary fallback: route to pre-warmed smaller variant (model-small-quant) for new inbound requests for the affected customers.
   - Increase continuous-batching windows for short period to absorb variance if kernel queue depth is high.
   - Temporarily raise trace sampling to 10% to improve reconciliation signal.

7) Post-incident diagnostics and artifacts\
   - Required artifacts to attach to postmortem:
     - Representative trace(s) x-rw-trace-id(s) and request-id(s).
     - /tmp/recon-<id>.json output.
     - Kernel-event dump for the incident window.
     - GPU timeline sample slice (.timeline.gz).
     - Control-plane rollout events for model-variants.
   - Run a delta analysis comparing expected kernel time vs observed kernel time across the 1-hour window around incident. Include token counts and model variant in analysis.

Operational tools and snippets
----------------------------
- trace-correlator usage: `./tools/trace-correlator --window 30s --sample-rate 10% --trace-id <id>`
- quick ES aggregate to get reconciliation rates by host:

  ```sql
  SELECT host, COUNT(*) as total_traces, SUM(case when reconciled then 1 else 0 end) as reconciled_count
  FROM trace-recon-results
  WHERE timestamp BETWEEN '2025-09-10T12:00:00Z' AND '2025-09-10T13:00:00Z'
  GROUP BY host
  ORDER BY reconciled_count ASC
  ```

- Kernel dispatch debug mode (non-prod first):

  ```yaml
  debug_mode: true
  capture_count: 100
  include_backtrace: true
  filter: "device_id=nvA100-07 and kernel_name contains 'attn'"
  ```

Telemetry tuning & sampling guidance
-----------------------------------
- Increase kernel-events retention to 24 hours for clusters with 1000+ qps.
- For noisy customers, add request-id sticky sampling so heavy users get 100% trace sampling for a rolling 15-minute window when an anomaly starts.
- Add a reconciliation metric: `recon.mismatch_rate` (percent of spans that did not reconcile) with 1-minute resolution to use in alerting.

Common investigation scenarios (examples)
---------------------------------------
- Scenario A: p99 spike with many Missing-kernel classified traces.
  - Likely cause: transient model-router GC cleared routing table. Look for model-router logs: "slot reaped". Mitigation: increase routing-table TTL or add warm probes.

- Scenario B: Orphan-kernel dominated by background prefetch kernels during peak.
  - Likely cause: aggressive prefetch; add prefetch-rate-limit per tenant and move prefetch work to separate non-urgent queue.

- Scenario C: Delayed-commit on a single device.
  - Likely cause: intermittent driver hang/firmware bug. Escalation: infra kernel/GPU vendor support with timeline and logs.

Postmortem template and action items
-----------------------------------
Include the following fields in every postmortem derived from this playbook:
- Incident summary (what happened, impact)
- Timeline with reconciled/unreconciled counts per 5-minute bucket
- Root cause hypothesis and evidence (link to recon JSON and kernel dumps)
- Remediation actions (what fixed it) and long-term fixes (owner + ETA)
- Telemetry improvements (sampling, metrics to add)
- Runbook updates (this doc should be updated if new heuristics are discovered)

Notes and caveats
-----------------
- This playbook focuses on telemetry correlation, not on kernel kernel-level patching. If a kernel bug is suspected, coordinate with the kernel team for safe reproduction in staging.
- Reconciliation will never be perfect due to sampling; use heuristics and representative samples for investigative confidence.
