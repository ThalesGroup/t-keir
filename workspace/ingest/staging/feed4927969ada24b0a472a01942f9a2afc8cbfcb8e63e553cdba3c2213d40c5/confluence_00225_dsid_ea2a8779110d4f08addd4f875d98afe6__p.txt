Probe-Led Quant Migration Safety Contract

Overview
This page defines the safety contract and operational playbook for rolling quantized model artifacts into production using a probe-first approach. The contract is intended for model onboarding, release engineers, and the eval-harness team. It applies to: per-layer and end-to-end quant conversions; mixed-precision fallbacks; and token/kv-cache-sensitive variants.

Goals
- Ensure user-visible quality regressions are constrained within an agreed fidelity budget.
- Provide deterministic, observable gating for canary and progressive rollouts.
- Minimize blast radius by coupling probes, telemetry, and automated fallback logic.

Scope and Risk Model
- Scope: Inference artifacts served via Redwood runtime (hosted, dedicated, private) where a quantized binary replaces a floating-point baseline. Includes customer-facing endpoints, internal eval shadows, and long-context workloads.
- Not in scope: offline batch scoring jobs (separate migration policy), model architecture changes.
- Principal risks: semantic drift, hallucination rate increase, latency regressions on small-batch/interactive tails, KV cache incompatibilities.

Definitions
- Baseline: the currently promoted (non-quant or prior-quant) model artifact used for comparison.
- Probe: a curated test case (automated or human-labeled) representing slices of production traffic used to measure quality metrics.
- Fidelity budget: numeric thresholds of acceptable deltas (see Acceptance Criteria).

Ownership
- Model owner: product/ML engineer who requests quant rollout. Responsible for probe set curation and initial evaluation artifacts.
- Eval-harness team: implements probes, schedules shadow runs, and computes metrics.
- Runtime/SRE: configures rollout routing, caching policies, and automated fallback triggers.
- Release engineer: executes promotion steps and signs off on exceptions.

Acceptance Criteria (Safety Contract)
All conditions must be satisfied for promotion from validation -> canary -> staged -> GA.
1) Functional correctness: intent-preserving metrics must remain within the fidelity budget compared to Baseline on the production-proxy probe suite:
   - Semantic Similarity (SBERT cosine) >= baseline - 0.02 OR absolute >= 0.90
   - Task Accuracy (where labeled) >= baseline - 1.5 percentage points
   - Safety/suppression tests: no new high-severity safety failures introduced (severity 1)
2) Latency & resource:
   - Median token latency <= baseline * 1.15
   - P99 token latency <= baseline * 1.5 AND absolute P99 <= 2.0s for interactive endpoints
   - GPU memory footprint reduction or within +5% of expected profile for mixed deployments
3) Stability & determinism:
   - KV-cache compatibility check: no divergence in continuation probability mass > 0.05 across 10k long-context probes
   - Determinism seeds: identical prompts under deterministic setting must match baseline behavior with <= 0.5% token edit-distance
4) Operational safety:
   - Rollout must have automated fallback route configured (quant -> baseline) with health-check cooldown of 30s
   - Telemetry events emitted for quant_migration_probe.result, quant_fallback.triggered, quant_rollout.progress

Probe Design Guidelines
- Maintain a prioritized probe portfolio:
  - Hot slices: 50K daily samples for latency-sensitive prompts (short, API-driven paths).
  - Long-context: 20K probes with >2k token histories to stress KV cache and attention speedups.
  - Function-call and structured-output probes: 5K examples covering common schema shapes.
  - Safety and red-team seeds: 10K fuzz/adversarial probes maintained by Security & Applied ML.

- Labeling and thresholds:
  - Each probe includes: prompt, expected intent, baseline response fingerprint (hash), and reference metric values.
  - Use aggregated metrics with confidence intervals (95% CI). Accept if CI upper bound meets acceptance criteria.

Rollout Plan (Procedure)
1) Local quant validation (model-owner)
   - Run local quant conversion and unit tests. Generate local evaluator report (artifact: quant_local_report.json).
   - Quick checks: shape/ops parity, seed determinism smoke tests, sample inference on 100 probes.
2) Shadow validation (eval-harness)
   - Schedule 48h shadow against production-proxy probe suite. Compare metrics to baseline.
   - Generate runbook comments and open PR to promote to canary if pass.
3) Canary (1% traffic or 0.5% depending on tenant sensitivity)
   - Duration: 4 hours minimum. Monitor metrics over 5-minute windows.
   - Automatic abort conditions:
     - Runtime error rate increase > 0.5pp absolute OR >= 2x baseline
     - Semantic Similarity delta > 0.03
     - Latency P99 increase > 2x baseline or > 3s absolute
   - If abort triggers, traffic routed to baseline immediately and release engineer notified.
4) Staged ramp (1% -> 5% -> 20% -> 50% -> 100%)
   - Each step minimum 6 hours, or longer for high-risk slices.
   - At each step, run full probe-suite and the lightweight smoke probes; require automated checks to pass.
5) GA promotion
   - Final artifact signed, release notes posted, and quant artifact retained in artifact registry with tags: quantized, promotor, baseline_hash.

Automated Fallback & Runbook
- Fallback logic (runtime): a rule set in the Router that evaluates telemetry windows and flips traffic to the configured fallback artifact.
- Emergency rollback steps (manual):
  1. Open incident on #prod-model-rollouts and tag Model Owner + Runtime oncall.
  2. Trigger immediate route reassign: curl -X POST https://runtime.internal/api/route/switch -d '{"route":"/v1/generate","to":"baseline-artifact-id"}'
  3. Validate baseline responses on 100 smoke probes.
  4. Create postmortem and hold a triage meeting within 48 hours.

Telemetry, Dashboards and Alerts
- Required telemetry exports:
  - quant_migration_probe.result: {probe_id, slice, metric_vector, delta_from_baseline, pass_fail}
  - quant_rollout.progress: {artifact_id, percent_traffic, step, timestamp}
  - quant_fallback.triggered: {artifact_id, reason, metric_snapshot}
- Dashboards (names):
  - Quant Migration Overview (team: eval-harness)
  - Quant Canary Health (team: runtime/SRE)
  - KV-Cache Divergence Monitor (team: serving)
- Alert thresholds (examples):
  - ALERT: quant_canary_semantic_regression if semantic_similarity_delta < -0.03 over 10m window -> Pager to runtime oncall
  - ALERT: quant_canary_error_spike if error_rate > 1.0% for 5m -> Slack + Pager

Metrics Table (exemplar)
| Metric | Baseline target | Acceptable delta | Alert level | Owner |
|---|---:|---:|---|---|
| Semantic Similarity (sBERT) | 0.94 | -0.02 | critical if <-0.03 | applied-ml |
| Task Accuracy (labeled) | 92% | -1.5pp | high if <-2pp | applied-ml |
| Latency P50 (token) | 12ms | +15% | medium if >+50% | serving |
| Latency P99 (token) | 180ms | +50% | critical if >2x or >2000ms | serving |
| Error rate (inference) | 0.2% | +0.5pp | critical if >1% | runtime/SRE |
| KV divergence (KL proxy) | 0.01 | +0.05 | high if >0.08 | serving |

Checklist before promotion
- [ ] Probe suite completeness verified (hot, long-context, functioncall, safety).
- [ ] Shadow-run metrics uploaded and reviewed by at least one reviewer.
- [ ] Rollout route and fallback configured in Router with cooldowns.
- [ ] Dashboards created and alerts configured for the artifact.
- [ ] Artifact stored in registry with reproducibility metadata (seed, conversion script hash, quant params).

Post-promotion monitoring and audits
- Maintain probe sampling for 14 days post-GA with daily digest to model owner.
- Schedule a 7-day audit to check for slow drift in fidelity metrics; if drift > half the fidelity budget, place artifact on periodic review cadence.
- Record all incidents and anomaly detections in the migration registry and link to model promotion PRs.

Exceptions and fast-paths
- For low-risk, internal-only artifacts (non-customer-facing), expedited rollouts (shadow -> 20% -> GA in 24h) are allowed with explicit approval from Model Owner + Runtime lead. Document reason and probe subset used.

Appendix: Typical failure modes and mitigations
- Increased continuation hallucinations on long-context: reduce quant aggressiveness, re-run with higher-precision attention layers, expand long-context probe set and rebaseline.
- Tokenization boundary drift: re-run tokenization alignment tests and validate prompt-segmentation heuristics.
- Instance OOMs after quant: tighten memory profiling in conversion and add margin to batch size scheduling.
