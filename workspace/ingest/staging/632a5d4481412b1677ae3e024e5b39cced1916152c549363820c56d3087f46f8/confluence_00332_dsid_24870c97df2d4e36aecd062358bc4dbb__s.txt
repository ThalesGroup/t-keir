SLO Resilience Scenario Workbook and Execution Guide

Summary:

This workbook collects high-value SRE scenarios that exercise SLOs, error budget governance, capacity planning, reliability initiatives, incident review standards, and operational tooling. It is intended for on-call responders, SRE leads running war rooms, and engineering teams planning capacity experiments and runbook validation. Use it to rehearse, run tabletop exercises, and to guide post-incident changes.

Scope:
- Services: model-serving, request-router, prefix-cache, embedding-pipeline, billing-proxy, capacity-orchestrator.
- Environments: prod (all regions), staging (pre-production), shadow clusters (canary).
- Audience: on-call, reliability engineers, product stewards, platform capacity owners.

When to use this workbook:
1) Prior to high-risk releases (model rollouts, autoscaler changes, quantization changes).
2) During quarterly resilience drills.
3) As part of incident retrospectives: validate mitigations in lab before closing action items.

How to read this guide:
- Each scenario includes: triggering conditions, impacted SLOs, error-budget thresholds, runbook steps (rapid mitigation and recovery), telemetry to collect, post-incident verification, and experiment-lab instructions.
- Use the Decision Matrix at the end to choose escalation and capacity actions.

Roles and responsibilities:
- Primary responder (on-call): execute immediate mitigations, own the incident timeline.
- Capacity owner: evaluate capacity maneuvers, run quota/eviction operations.
- SRE lead: coordinate cross-team escalations, declare incident severity.
- Product steward: approve quality-vs-cost tradeoffs and rollback decisions.
- Postmortem author: collect evidence and complete incident review within 5 business days.

Scenario catalog (executables):

1) Multi-region GPU fabric outage (cold failure)
- Trigger: > 30% GPU nodes in region X transition to UNREACHABLE in 5m window; model-serving p95 latency doubles; overall successful request rate drops > 10%.
- Impacted SLOs: request success rate (99.9% monthly), p95 latency (200ms target).
- Error budget action thresholds:
  - Warning: 5% of monthly error budget burned in 30m -> trigger emergency monitoring channel and throttle low-priority tenants.
  - Critical: 20%+ in 1h -> initiate cross-region failover and capacity rebalancing.
- Rapid mitigation steps (ordered):
  1. Verify Hermes alert and confirm node state via capacity-orchestrator: `capctl list nodes --region X --status unreachable`.
  2. Immediately enable burst-absorber: `capctl absorb --policy surge-redirect --target region-Y`.
  3. Shift model routing policy to failover pools: update slo-router policy to `regional-fallback: true` with canary fraction 10%.
  4. Scale dedicated warm pools in region Y by +25% using `autoscale apply --pool warm-pool-model-a --delta 25`.
  5. If external traffic surge persists, throttle non-critical routes (embedding-bulk, async-batch) by 50% via traffic-shepherd rule.
- Telemetry to collect during incident:
  - Per-region GPU health, node counts, queue lengths, and preemption events.
  - Token-level success and error rates by tenant and route.
  - Autoscaler decisions and recent allocation traces.
- Recovery verification:
  - p95 latency returns within 1.2x baseline and success rate returns to >= 99.5% for 30m window.
  - Re-enable throttled routes one at a time and confirm no relapse.
- Post-incident lab reproduction:
  - Use the capacity-sandbox harness: `cap-sim --fail-region X --duration 15m --load-profile spike-50pct`.
  - Validate that `burst-absorber` and `warm-pool` scale up as expected and alert as expected.

2) Latency tail regression after quantized runtime rollout
- Trigger: p99 latency increases 2x after quantization kernel flip; customer complaints for interactive chat increase.
- Impacted SLOs: tail-latency (p99), interactive response SLA (200ms p95).
- Error budget actions:
  - Immediate rollback if p99 breach sustained for 10 minutes and error budget burn > 8%/day.
- Runbook steps:
  1. Confirm deployment tag and kernel selection: `runtimectl show --deployment model-a --field kernel`.
  2. Switch traffic to pre-quantized variant (model-a.fp16) via gradual rollback (canary 5% -> 20% -> 100%).
  3. Pin suspect kernel in model catalog and mark as blocked: `modelctl block-kernel quant-kernel-v3`.
  4. Open a regression ticket to Applied ML + Runtime with reproducible trace, token sampling, and profiler dumps.
- Data to collect: tail latency histograms, kernel-level traceback logs, NVTX timings, memory copy durations.
- Lab reproduction: run `quant-lab --input sample-promptset.json --sequence-length 1024 --repeat 1000 --measure p99` and attach profiler output.

3) Embedding workload microburst causing queue starvation
- Trigger: embedding cluster queue depth > 10k sustained for > 2m with consumer lag rising; embeddings SLO degrades.
- Impacted SLOs: embedding throughput (99% of requests processed within 30s), embedding freshness.
- Mitigations:
  1. Enable backpressure admission control for bulk embedding jobs: `embedctl admit --mode conservative`.
  2. Temporarily promote high-priority tenants to reserved lanes with guaranteed slots (update fairshare config).
  3. If queue cannot be drained in 15m, activate emergency preemption of long-running batch jobs.
- Observability artifacts: sample request traces, queue latency percentiles, tenant-level queue contributions.
- Prevention experiments: implement and A/B the suggested intelligent-batching policy in Optimize for 7 days with shadow traffic.

4) Model quality regression that triggers silent error budget burn
- Trigger: automated evals show a drop in prompt-set accuracy by > 5% vs baseline while service metrics remain green (no latency errors).
- Impacted SLOs: qualitative SLOs tracked in QualityGuard (accuracy / hallucination rate).
- Immediate actions:
  1. Shift traffic to last known-good model variant and enable traffic shadowing for observability.
  2. Quarantine suspect model from catalog and disable auto-rollout policies.
  3. Run quick rollback validation with canary prompts and human-in-the-loop checks for critical tenants.
- Post-incident steps: add new synthetic prompt sets to regression harness, extend eval cadence for that family of prompts to 4 runs/day for one week.

5) Billing-proxy induced throttling that appears as SLO degradation
- Trigger: billing-proxy rate limiter misconfiguration causes 429s on background routes, error budget unaccounted.
- Impacted SLOs: background request success; customer-facing SLAs if cascade occurs.
- Rapid mitigation:
  1. Revert recent billing rule changes: `billingctl rollback --commit HEAD~1`.
  2. Open short-lived exception to allow traffic through for affected tenants, track cost impact.
  3. Add metric guard: rate limiter headroom must be >= 20% of peak observed 30d traffic.
- Long-term: create a pre-deploy validation harness that emulates quota exhaustion.

Standard incident-review checklist (mandatory for every SRE incident):
1. Evidence collection: timeline, traces, top-10 related alerts, and debug snapshots.
2. SLO impact reconciliation: compute exact error-budget burn windows and map to service commits/deploys.
3. Root-cause hypothesis and validated steps reproducing the behavior in lab.
4. Action items: owner, target date, verification steps.
5. Severity and customer-impact annotation for postmortem.

Decision matrix (quick reference):
- If error budget burn rate > 10%/hour: escalate to SRE lead and consider tenant throttles.
- If key SLO degraded and recovery not achieved within 30m: invoke cross-region failover.
- If degradation is quality-only (no infra signal): prioritize rollback of model changes and run quiet rollback validation.

Operational tooling and commands (examples):
- capacity-orchestrator: `capctl list pools`, `capctl scale --pool-name X --ratio 1.25`.
- slo-monitor: query recent SLO burns: `sloquery --service model-serving --window 1h`.
- telemetry-replay: `teleplay --from 2025-08-01T12:00Z --to 2025-08-01T13:00Z --service embedding-pipeline`.
- sandbox reproduction harness: `cap-sim --scenario multi-region-gpu-fail --scale 0.5`.

Post-incident verification rubric (for action item closure):
- Make: change merged, tests added (unit + integration for the failure mode).
- Test: a deterministic replay reproduces the failing behavior in the sandbox and demonstrates the fix.
- Observe: metrics show improvement with no regression to other SLOs for 72 hours in staging shadow and 1 week in prod for critical fixes.

Experiment lab playbook (safe rehearsals):
1. Plan: define hypothesis, duration, and blast radius.
2. Preflight checks: run `telemetry-replay` for baseline windows and save snapshots.
3. Execute in shadow cluster with mirrored traffic: `trafficctl mirror --target shadow-1 --fraction 0.25`.
4. Monitor: slo-monitor + real-time dashboard; hold go/no-go windows every 5 minutes.
5. Rollback plan: pre-prepare rollback runbooks and an automated switch to previous routing with `slo-router switch --to previous`.

Continuous improvement and reliability initiatives:
- Quarterly scenario additions: each team contributes 1 new scenario per quarter focused on their highest risk surface.
- Runbook rehearsal cadence: run one large multi-team drill and two focused single-team drills per quarter.
- Tooling improvements: invest in telemetry-replay fidelity and expand `burst-absorber` policies to include token-aware throttles.
