Cross-domain access assurance and evidence guidelines

Overview:

This guideline describes the cross-domain controls, evidence requirements, and operational procedures for assembling, retaining, and transferring access and authorization evidence across Redwood Inference domains (hosted, dedicated, and private) and across geographies. It harmonizes RBAC and attribute-based controls with audit logging, data residency constraints, secure SDLC touchpoints, and incident response handoffs. The goal is to ensure forensic integrity, regulatory compliance, and efficient response to legal or security requests.

Scope and audience:

- Scope: All services and components that influence authorization decisions, authentication flows, sessioning, and audit telemetry for customer-facing inference endpoints and control plane services. This includes API gateways, authn/authz services, identity brokers, service mesh sidecars, audit collectors, and storage locations for evidence artifacts.
- Audience: Security engineers, SREs, backend engineers owning auth or logging, compliance officers, and legal for evidence handoff.

Key definitions:

- Evidence artifact: Any recorded object that can be used to prove or reconstruct an authorization decision or access path (logs, session recordings, entitlement snapshots, attestation manifests, packet captures where permitted, KMS access logs).
- Provenance header: Immutable metadata attached to evidence artifacts capturing source service, ingestion timestamp, region, and canonical id.
- Entitlement snapshot: Time-indexed dump of RBAC/attribute bindings and policy versions relevant to a request window.

Principles:

1. Minimal collection for purpose: Collect only the telemetry needed for audits, incidents, or audits to limit exposure.
2. Immutable packaging: Evidence is packaged immutably with checksums and signed provenance metadata before long-term storage.
3. Residency-aware retention: Retention periods and storage locations respect data residency and legal hold constraints.
4. Chain-of-custody: Every transfer of evidence to legal/compliance/third-parties must be logged and verifiable.
5. Reproducibility: It must be possible to reconstruct authorization decisions for a specific time window given the assembled artifacts.

Owner and escalation:

- Primary owner: Security (Access & Identity team).
- Secondary owner: Eng-sre (for pipeline and storage availability).
- Escalation path: Incident -> oncall security -> compliance liaison -> legal.

High-level mapping (RBAC and audit logging to evidence):

- AuthN layer (identity provider, federation): record authn events (successful/failed), token issue/refresh with nonce, identity attributes included in provenance header.
- AuthZ layer (policy engine, ABAC/RBAC store): capture policy decision logs with policy version id, matched rules, input attributes, and decision delta.
- Session/KV caches: record cache population/eviction events to aid replay.
- API gateway / ingress: capture request metadata, client certificate/MTLS context, source IP, and per-request entitlement headers.
- Audit pipeline: ingest events with integrity checks, enrich with geo and residency tags, and forward to short-term vault for triage and long-term immutable store for evidence retention.

Evidence categories and retention matrix (summary):

- The following table is a concise mapping. For full regulatory matrices consult the Compliance team.

Artifact | Purpose | Short-term retention | Long-term retention | Residency constraint
--------|---------|----------------------|---------------------|--------------------
AuthN events (token issue/refresh) | Reconstruct identity assertion | 90 days | 3 years (or as-required) | Store in region of originating tenant unless legal hold
AuthZ decisions (decision logs + policy id) | Reconstruct allow/deny decisions | 180 days | 7 years for regulated customers | Mirror to customer region for Private deployments
Entitlement snapshots (daily) | State of bindings & groups | 30 days (online) | 5 years (cold) | Segregated based on tenant residency
API request headers + minimal payload metadata | Incident triage | 30 days | 3 years (index only) | PII redaction before cross-border archive
Session captures / KV cache traces | Deep investigation | 14 days | 1 year (with approvals) | Avoid exporting full captures outside region without DPA
Checksums & provenance manifests | Evidence integrity | Indefinite (index) | Indefinite | Global index acceptable (no user data)

Note: retention windows are defaults and can be shortened by privacy requests; extensions require legal approval.

Secure SDLC touchpoints for evidence integrity:

- CI artifacts: Build IDs, pipeline approvals, and artifact signatures are recorded and treated as evidence for deployment-time policy changes.
- Feature flags and rollout metadata: Every rollout that changes authz behavior must attach a deployment manifest signed by the release engineer.
- Model onboarding: When a model is added with altered inference-level controls (e.g., content filters), include a policy revision id in the model manifest.
- KMS use: All operations that decrypt keys for authz decisions must log key usage context to KMS audit logs and include output in the evidence manifest.

Operational playbook: evidence assembly for an incident (summary)

1) Initial triage (0–2 hours)
   - Triage lead collects the incident window and primary indicators.
   - Query short-term audit store for request ids, authz decision ids, and entitlements; mark snapshot for preservation.
   - Create evidence workspace in secure staging with a unique case id and provenance header.

2) Preservation (2–12 hours)
   - Pull entitlement snapshots, policy versions, and authn/authz logs for the window.
   - Generate checksums (SHA-256) and sign manifest with case signing key.
   - Place artifacts into immutable bucket with time-based lock.

3) Deep analysis (12–72 hours)
   - Correlate entitlements, inbound requests, and downstream actions.
   - If cross-border data is required, consult compliance and log the justification in the provenance header.

4) Handoff (72+ hours)
   - Prepare evidence package: manifest, index, artifact list, and redaction notes.
   - Execute chain-of-custody transfer: log recipient, timestamp, and transfer checksum.

Commands and example forensic queries (examples for triage team):

- Query authz decision by request id (Clickhouse-like pseudocode):
  SELECT * FROM authz_decisions WHERE request_id = 'REQ-xxxx' AND ts BETWEEN '2026-07-01' AND '2026-07-01 00:10';

- Export entitlement snapshot at date:
  curl -H "Authorization: Bearer $ADMIN_TOKEN" https://internal-api.redwood/v1/entitlements/snapshot?at=2026-07-01T00:00:00Z -o snapshot-2026-07-01.json

- Generate manifest and sign (example):
  sha256sum artifacts/* > checksums.txt
  gpg --detach-sign --armor --output checksums.txt.asc checksums.txt

Chain-of-custody and packaging checklist:

- Case id created and logged.
- Provenance header attached to each artifact.
- Checksums generated and detached signature created.
- Storage location immutable/append-only.
- Transfer logs created for any external handoff.
- Redaction notes with rationale recorded.

Risk calibration for delegated and just-in-time access:

- For high-risk entitlements (admin, key management, model-pull in Private), require:
  - Multi-person attestation recorded in the evidence manifest.
  - Short-lived credentials (<= 6 hours) with automatic revocation logging.
  - Session recording enabled (where permitted) with immediate checksuming.

- Sampling policy for privileged activity:
  - 100% logging of all privileged actions.
  - Weekly evidence packaging for a rolling 30-day window for spot audits.

Data residency and cross-border constraints (practical steps):

1. Tag every event at ingestion with tenant_region and regulatory_profile.
2. When a request for evidence requires cross-border transfer, create a jurisdictional justification entry and the minimal export set.
3. Use on-prem/private deployment evidence stores for regulated tenants when possible; otherwise use encrypted, customer-region buckets with access policies.

Evidence request workflows (legal/compliance/audit):

- Routine audit: Compliance requests 30-day window artifacts. Security assembles package and delivers encrypted archive with access expiry.
- Legal request (subpoena): Engage Legal, produce only required artifacts, and log chain-of-custody.
- Customer data subject request: Follow privacy process; redact or remove PII per policy and log redaction operations as part of evidence.

Templates and example artifacts to include in package:

- Manifest.json (required): includes case_id, artifacts[], checksums[], signer, region, justification.
- EntitlementSnapshot.json (required): include policy_version and bindings.
- DecisionLog.ndjson (required): per-line decision object with rule_match and input attributes.
- RedactionNotes.md (optional): list of redacted fields and justification.

Governance and attestations:

- Quarterly review: Security and Compliance validate retention settings and alignment with law changes.
- Change management: Any change to authz decision schema or retention defaults requires an ADR and signed deployment manifest.
