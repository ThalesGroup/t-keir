Runtime Initializer and Sample Adapter Catalog — Onramp Launchpad

Overview

This document is a compact, production-oriented quickstart and pattern catalog to bootstrap a local developer integration against the Redwood Serving Runtime. It is intended for SDK authors, integrators, and platform engineers who need a repeatable, observable, and CI-friendly path to ship an adapter (client-side or runtime shim) that interoperates with Redwood’s API and local runtime stubs.

Goals
- Reduce time-to-first-success for new adapter authors to under 60 minutes.
- Provide canonical templates for adapter manifests, telemetry specs, and CI checks.
- Capture most-common support issues and canonical fixes so DX and Support can triage quickly.

When to use this page
- You are building a new client-side adapter (language SDK or runtime shim).
- You are onboarding a partner runtime or third-party accelerator.
- You need a reproducible local test harness and CI gates for compatibility.

Quickstart: Runtime Initializer (local)
Prerequisites
1) Docker 24.x or higher installed.
2) Node 18+/Python 3.10+/Go 1.20+ depending on adapter language.
3) Clone the runtime-initializer repo (internal): git@github.redwood:dx/runtime-initializer.git

Steps
1. Start the local runtime stub (provides model routing and telemetry hooks):
   - CLI: docker compose -f docker/local-stub.yaml up --build --detach
   - The stub listens on http://localhost:8080 and exposes a health endpoint /_health and metrics at /metrics.

2. Choose a template adapter from the catalog (examples below). Copy the template and set the adapter id:
   - Template folder: templates/<language>-adapter-stub
   - Example: cp -r templates/python-adapter-stub my-first-adapter

3. Edit the adapter manifest (adapter.yaml) and set required fields (see manifest table).

4. Run local smoke test: ./scripts/run_local_tests.sh --adapter ./my-first-adapter --runtime http://localhost:8080
   - Expected result: 3 tests passed, local telemetry emitted to stdout.

Adapter manifest (adapter.yaml) — required fields\| Field \| Type \| Description \|
\| adapter_id \| string \| Unique adapter identifier (kebab-case)
\| language \| string \| Implementation language: python | node | go
\| runtime_compatibility \| list[string] \| Supported runtime versions (semver-like): [">=1.3.0", "<2.0.0"]
\| api_surface \| list[string] \| Features implemented: ["generation", "streaming", "kv-cache"]
\| testing_targets \| list[string] \| Smoke tests to run: ["health","generation-basic","streaming-chunking"]

Sample adapter.yaml
```yaml
adapter_id: local-demo-adapter
language: python
runtime_compatibility: [ ">=1.3.0", "<2.0.0" ]
api_surface: [ "generation", "streaming" ]
testing_targets: [ "health", "generation-basic" ]
```

Health, telemetry, and observability: recommended configuration
- Health: adapter must expose /_health returning 200 and JSON {"status":"ok","version":"<adapter-version>"}.
- Metrics: expose Prometheus metrics at /metrics with labels: adapter_id, runtime_version, host
- Traces: if OpenTelemetry enabled, send spans to collector at OTEL_COLLECTOR_URL. Include span attribute adapter.adapter_id.

Example Prometheus metrics (text exposition)
# HELP adapter_requests_total Total adapter requests
# TYPE adapter_requests_total counter
adapter_requests_total{adapter_id="local-demo-adapter",runtime_version="1.3.2"} 42

Local test harness (what it validates)
- API contract: generation response shape for non-streaming and streaming chunk boundaries.
- Failure handling: retry/backoff observable behavior when stub returns 5xx.
- Telemetry: metrics and trace attributes present.

Sample API example: multi-model fallback snippet (Node.js)
```js
import fetch from 'node-fetch';

async function callGenerate(prompt) {
  const resp = await fetch('http://localhost:8080/v1/generate', {
    method: 'POST',
    headers: { 'Content-Type': 'application/json', 'x-adapter-id': 'local-demo-adapter' },
    body: JSON.stringify({ model: 'redwood/small-1', prompt })
  });
  if (resp.status === 503) {
    // fallback to lower-cost model variant
    return fetch('http://localhost:8080/v1/generate', {
      method: 'POST',
      headers: { 'Content-Type': 'application/json', 'x-adapter-id': 'local-demo-adapter' },
      body: JSON.stringify({ model: 'redwood/small-1-quant', prompt })
    });
  }
  return resp;
}
```

CI gate: required checks for adapter PRs
1) Unit tests: pytest / jest / go test with >= 90% coverage for core adapter code paths.
2) Contract tests: run contract-suite against runtime-stub; fail on any schema mismatch.
3) Telemetry coverage: verify metrics emitted for health and request counters.
4) Linting: language standard linters (ruff/black/eslint/gofmt).

Top support issues and canonical fixes
1) Failure: "adapter:handshake:incompatible-runtime-version"
   - Symptom: Adapter rejects connection with error listing unsupported runtime version.
   - Cause: adapter.runtime_compatibility does not cover the runtime version returned by /_health.
   - Fix: Update adapter.yaml runtime_compatibility to include the runtime version or implement a graceful fallback mapping.
   - Example fix: change runtime_compatibility to [">=1.2.0", "<2.0.0"] and publish patch.

2) Failure: "generation:truncated-stream" seen in production traces
   - Symptom: Streaming clients stop early; last chunk missing newline delimiter.
   - Cause: adapter chunk boundaries not respecting streaming framing protocol (missing \"data: [chunk]\" prefixes).
   - Fix: Use canonical framing helper in templates/streaming-framer.{js,py} and add end-of-stream sentinel in tests.

3) Failure: missing metrics for adapter_requests_total
   - Symptom: dashboard shows empty or zero metrics for some adapter deployments.
   - Cause: /metrics endpoint not exposed, or path blocked by internal ingress rules.
   - Fix: Expose /metrics in adapter app, ensure container port published in Kubernetes Service. Add unit test asserting /metrics returns 200.

Operational playbook: local-to-prod rollout steps
1) Validate adapter against runtime-stub and internal canary runtime (staging).
2) Create canary rollout with 1% traffic and monitor key metrics for 30 minutes:
   - adapter_requests_total (increase)
   - adapter_error_rate (should be < 0.5%)
   - p95 latency (baseline +/- 10%)
3) If metrics stable, increase to 10% for 2 hours, then to 50% for 6 hours.
4) Full rollout with feature flag and rollback window of 24 hours.

Support escalation notes
- If a customer reports production errors that reproduce locally against the stub, open an escalation with Support ID prefix DX-ADAPTER and include: adapter.yaml, failing trace id, /metrics snapshot, and runtime /_health output.

Appendix: Debug checklist (fast triage)
1) Check /_health on runtime and adapter. Confirm versions.
2) Curl a known-good generation path with small prompt to validate shape: curl -X POST http://localhost:8080/v1/generate -d '{"model":"redwood/small-1","prompt":"hi"}'
3) Confirm /metrics exposed and contains adapter_requests_total.
4) Reproduce streaming locally and verify chunk framing.
5) If intermittent 5xx, run load profile with ab or wrk to validate backpressure handling and to capture traces.
