Conversation Context Compression Proxy — design brief and rollout plan

Overview
========

This document describes the Conversation Context Compression Proxy (CCCP) — a network-side service and runtime shim that transparently compresses long conversational context into a compact, fidelity-aware representation before it reaches the inference runtime. The goal is to reduce per-request token cost and improve tail latency for long-session workloads while preserving application-level quality targets.

Intended audience: product managers, runtime engineers, infra SREs, and customer success for enterprise clients with long-session conversational workloads.

Problem statement
------------------

- Customers increasingly run multi-turn conversations with long context windows (document assistants, multi-step agents, chat history).
- Passing full raw context to the model causes high token cost and variable latency; caches and KV-only approaches address parts of the problem but either increase memory footprint or hurt model quality.
- We need a progressive, reversible compression strategy that preserves critical context (instructions, recent facts, unanswered questions) and degrades gracefully.

Goals and success metrics (OKRs)
--------------------------------

1. Reduce median per-session token consumption by 35% for target workloads (customer internal benchmark).
2. Reduce 95th-percentile inference latency for sessions >4k tokens by 20% without increasing model error rate beyond 2% absolute on evaluation prompts.
3. Provide a rollback-safe, configurable deployment path for Hosted, Dedicated, and Private customers.

Product requirements (shippable PRD items)
-----------------------------------------

1. Compression proxy service must accept an HTTP request containing: session_id, recent_history (array of messages), metadata (tenant_id, route, fidelity_budget).
2. The proxy returns a compressed payload plus a traceable compression-metadata header with: compression_version, heuristics_used, retained_message_ids, quality_score_estimate.
3. Compression must be parameterizable per-route and per-tenant (compression_level: none|light|balanced|aggressive).
4. The system must provide an opt-out header for customers who require full context (X-Redwood-No-Compress).
5. The proxy must support a sidecar mode (local developer sandbox), edge mode (regional proxy), and central-hosted mode.
6. Observability: per-request compression ratio, estimated semantic recall, fallbacks triggered, CPU/GPU cost delta.
7. Compatibility: must integrate with existing routing policy (latency vs cost) and fallback model variants.

Design overview
---------------

High-level components:

- Compression Proxy (stateless service): accepts original request, produces compressed payload and metadata. Owner: eng-platform.
- Compression Catalog: unmarshalling rules, tokenizer-preserving heuristics, and model-of-model that scores quality (small transformer 50M). Owner: applied-ml-and-evals.
- Recovery & Expansion Adapter: on the serving runtime, expands compressed payload into a compact context structure the runtime understands (KV entries, summary tokens). Owner: eng-serving-runtime.
- Monitoring & Rollout Orchestrator: feature flag gating, route-level config, canary scheduler. Owner: eng-sre and product.

Data flow (textual diagram):

1) Client -> Redwood API Gateway -> Compression Proxy (if enabled)
2) Compression Proxy -> stores compression metadata to telemetry (sampling) -> forwards compressed payload to Serving Runtime
3) Serving Runtime -> Expansion Adapter -> Model invocation (with augmented prompts if needed)
4) Model output -> optionally post-process against compressed metadata (consistency checks) -> response to client

Compression techniques and heuristics
------------------------------------

- Heuristics layer (deterministic): trim low-utility messages (e.g., system keep-alives), collapse near-duplicates, remove benign boilerplate.
- Semantic summarization (ML): lightweight encoder-decoder that generates a short summary preserving entities, instructions, and unresolved user asks.
- Embedding fingerprinting: compute embeddings for message spans and de-duplicate semantically equivalent content.
- Hybrid packing: produce a mixed representation of retained raw tokens (recent N turns) + summary tokens for older context.

Quality-control model and thresholds
-----------------------------------

- Small QC model returns an estimated recall_score in [0,1]. We require recall_score >= 0.88 for balanced compression in canary.
- If recall_score < threshold, proxy will: (a) increase compression_level (less aggressive) and re-score (b) emit a compression-fallback event and optionally forward full context.

Configuration table (example)
----------------------------

| field | description | example |
|---|---|---|
| compression_level | controls aggressiveness | balanced |
| max_summary_tokens | maximum tokens used for summary | 128 |
| preserve_last_tokens | number of tokens from most recent turns preserved verbatim | 512 |
| qc_threshold | minimum recall_score | 0.88 |
| mode | sidecar|edge|hosted | hosted |

APIs and contract (example)
--------------------------

Request (JSON payload) example:

{
  "session_id": "s-1234",
  "tenant_id": "acct-987",
  "route": "chat.completion",
  "recent_history": [
    {"role": "user", "text": "Upload the Q2 revenue file"},
    {"role": "assistant", "text": "Sure — give me a second."}
  ],
  "fidelity_budget": {"max_tokens": 4096, "latency_ms_target": 200}
}

Proxy response headers (critically consumed by runtime):

- X-Compression-Version: 0.3
- X-Compression-Ratio: 4.3
- X-Compression-QC: 0.91
- X-Compression-Retained-IDs: msg-333,msg-334

Design tradeoffs and rationale
-----------------------------

- Why not only cache at runtime? Caching reduces repeated token cost but does not help cold-starts and increases memory pressure at scale. CCCP compresses upstream to save bandwidth and tokenization cost early.
- Why a proxy vs in-runtime compression? A proxy enables per-tenant policy enforcement, experiment-driven canaries, and reuse across serving runtimes and cloud/private deployments.
- Risks: semantic loss (mitigated by QC scoring and per-route conservative defaults), increased CPU at the edge (mitigated via adaptive fallbacks and offloading to specialized capacity).

Observability and SLOs
---------------------

- Metrics to track: compression_ratio (p50/p95), recall_score distribution, compression_cpu_ms, compression_fallback_rate, end_to_end_latency_delta.
- SLO: 99.9% of proxied requests must see proxy-induced latency < 30ms in hosted mode (median target <10ms).
- Alerting: alert if compression_fallback_rate > 1% per-tenant for 10m.

Compatibility matrix
--------------------

- Hosted API: full feature set (canary, telemetry capture).
- Dedicated: depends on customer capacity; offer bundled lightweight QC model or integrate with customer's private QC endpoint.
- Private/on-prem: sidecar mode only (no central telemetry by default); require explicit ops consent for model components.

Roadmap and rollout plan (milestones)
------------------------------------

1. Pilot (Q2 2026, June): Sidecar mode + local QC model, opt-in beta with 3 customers. Deliverables: SDK sidecar, metrics dashboard, simple route-level toggle.
2. Edge canary (Q3 2026, Aug): Regional edge proxy, per-route config, canary scheduler. Deliverables: host-level rollout, telemetry hooks.
3. Hosted GA (Q4 2026, Nov): Global hosted proxy, integration with Optimize suggestions, pricing pilot.
4. Dedicated & Private packaging (Q1 2027): packaging for Dedicated pools and on-prem sidecar installer.

Pricing and packaging notes (product considerations)
--------------------------------------------------

- Pricing levers: per-request compression processing fee (small, e.g., $0.0001), reduced token bill credited back to customer based on measured compression_ratio, and tiered subscription for premium QC (enterprise).
- Packaging concepts: include CCCP basic in Managed Hosted at no extra charge for dev tiers; charge an Optimize add-on for QC-backed aggressive compression for enterprise.

Pricing example table:

Release notes (initial beta)
---------------------------

- Initial beta (Pilot): Sidecar mode only.
- Enabled features: light and balanced compression, QC scoring (v0.1), telemetry metrics, opt-out header.
- Known issues: very long binary attachments are not compressed; some third-party tokenizers may produce higher-than-expected token counts in balanced mode — tracked under eng-serving-runtime/known-issues ticket #CCCP-12.

Migration and customer communication plan
----------------------------------------

1. Developer-facing: release SDK sidecar + sample app showing billing delta and latency change.
2. Enterprise: proactive outreach with a measured analysis of potential token savings using a 24-hour session replay sample.
3. Migration steps: a) enable sidecar in sandbox, b) run with telemetry capture (no autop-apply), c) run canary with limited traffic, d) enable route-level default.
