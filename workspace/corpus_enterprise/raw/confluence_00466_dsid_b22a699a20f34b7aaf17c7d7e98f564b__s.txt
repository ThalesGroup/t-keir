SLO Lease and Temporary Capacity Grant Procedure

Summary

This runbook defines the SLO Lease model: a controlled, auditable procedure that temporarily grants additional capacity or relaxed SLO enforcement to a product/team for a bounded window. The intent is to provide predictable, low-friction operational support for planned experiments, burst traffic events, and carefully-scoped migrations while protecting platform-wide stability and multi-tenant fairness.

Why we need an SLO Lease

- Many production changes are time-bound (launch windows, migrations, marketing spikes) and require transient exceptions to normal SLO enforcement or capacity allocations.
- Existing mechanisms for emergency capacity (ad-hoc admin quotas, manual throttle lifts) are ad hoc, lack audit trail, and risk race conditions across tenants.
- SLO Lease provides a structured path with approval, telemetry guardrails, automated enforcement, and post-lease review.

Scope

- Applies to hosted and dedicated inference tenants managed by Redwood Inference.
- Covers temporary increases to concurrency, burst capacity, priority token bands, and controlled SLO relaxation (latency tail allowances, elevated error budget allocation).
- Excludes permanent capacity changes and SLA re-negotiations (handled by capacity reservations or sales/enterprise workflows).

Definitions

- SLO Lease: Time-boxed permission allowing a consumer to exceed normal resource allocations or error budget limits under specified conditions.
- Lessee: The team or product requestor receiving the lease.
- Lease Governor: The owning SRE oncall or capacity owner who approves/oversees the lease.
- Lease Window: Start and end time for the grant.

High-level policy

- Maximum lease duration: 72 hours for burst experiments without exec approval. Longer leases require justification and product/SRE leadership sign-off.
- Maximum additional capacity: capped at 2x baseline concurrency for public tenants, and 3x for dedicated customers with reserved headroom agreed in contract.
- Every lease must include: purpose, owner, concrete rollback criteria, observability plan, and a post-lease audit.

SLO Lease Request Procedure (one-click + manual steps)

1) Request initiation (lessee):
   - Fill the SLO Lease request form (internal UI or CLI). Required fields: service, tenant id, lease window (UTC start/end), requested delta (concurrency/priority/tokens), objective (launch/migration/load test), expected traffic profile, owner (oncall contact), and automated rollback criteria.

2) Automated pre-checks (system):
   - Verify current platform load: local cluster CPU/GPU utilization < 85% and platform-wide spare headroom >= requested delta.
   - Simulate projected pick-up using recent traffic histograms. If simulation predicts >15% SLO degradation to impacted services, the request is auto-deferred to manual review.

3) Lease Governor review (SRE):
   - Verify that observability hooks exist (synthetic canaries, trace sampling, cost estimate).
   - Confirm ownership and rollback playbook.
   - Approve, approve-with-conditions, or deny. Decision must be recorded with reasons and TTL.

4) Execution (automation):
   - Upon approval, orchestration creates a scoped policy: new quota, dynamic routing weights, and a telemetry-scraping job.
   - Enforcement pieces: admission-controller patch, priority-queue token update, and real-time dashboard link posted to the lease request thread.

5) Active monitoring (lessee + SRE):
   - SRE oncall monitors lease health dashboard for the first 30 minutes at 1-minute resolution.
   - Alert thresholds: 5xx rate delta > 0.5% AND p99 latency increase > 25% triggers auto-revoke.

6) Lease termination and audit:
   - At lease end (or on auto-revoke) automation reverts policies and captures a lease runbook artifact: metrics snapshot, decision log, and owner confirmation of rollback.
   - Lessee files short post-lease note within 48 hours summarizing outcomes and learnings.

Approval Criteria (decision table)

| Criterion | Acceptable Range | Action if outside range |
|---|---:|---|
| Platform spare headroom | >= requested delta + 10% | Defer to capacity team; deny automated approval |
| Projected impact to top-10 tenants | <= 2% SLO degradation | Manual review required if >2% |
| Observability coverage | Synthetic canary + traces for affected routes | Block if missing |
| Rollback automation | Must exist and be tested | Block if untested |
| Security / data path changes | None or reviewed by security | Security review required |

Note: The table above must be used by the Lease Governor during manual reviews.

Oncall Runbook: Steps for SRE when a lease is active

1) Acknowledge lease request in the oncall page and subscribe to the lease thread.
2) Verify automation applied the intended quota delta (CLI check):

   rwictl lease status --lease-id=<ID> --format=json

   Expected fields: applied:true, start_ts, end_ts, delta_concurrency, rollback_query_link

3) Open the live lease dashboard (link auto-posted). Focus metrics: p95/p99 latency, 5xx rate, headroom ratio, cluster GPU utilization, and tenant throttling counters.

4) First-30-minute checks (manual):
   - Confirm synthetic canary steady within 10% of baseline.
   - Confirm total platform headroom drift < 5%.

5) Escalation criteria (immediate action):
   - If 5xx rate delta > 0.5% AND p99 > 25%: trigger auto-revoke and page product owner + SRE manager.
   - If cluster GPU utilization > 95% for 3 consecutive minutes: initiate emergency backpressure (see emergency backpressure CLI below).

6) If auto-revoke triggered: follow rollback verification steps (below). Open incident channel if root cause uncertain.

Rollback verification steps (automation + manual validation)

- Automation reverts quotas/policies. Confirm via CLI and telemetry:

  rwictl lease revert --lease-id=<ID>
  rwictl quota list --tenant=<TENANT_ID> | grep <TENANT_ID>

- Validate telemetry returns to baseline in 15 minutes. If not, escalate to SRE lead and open incident.

Telemetry queries and dashboards (examples)

- Canary success rate (PromQL):
  sum(rate(canary_success_total[1m])) / sum(rate(canary_run_total[1m]))

- Tenant 5xx delta (PromQL):
  (sum(rate(http_requests_total{tenant=\"<TENANT_ID>\",status=~\"5..\"}[1m])) - sum(rate(http_requests_total{status=~\"5..\"}[1m])) * tenant_traffic_fraction)

- Headroom ratio (internal metric):
  1 - (cluster_allocated_capacity / cluster_capacity)

Automation and sample manifests

- Lease Request JSON (example):

  {
    \"tenant_id\": \"tenant-42\",
    \"service\": \"text-generation-prod\",
    \"start_utc\": \"2026-06-10T08:00:00Z\",
    \"end_utc\": \"2026-06-10T14:00:00Z\",
    \"delta_concurrency\": 100,
    \"owner\": \"eng:search-team\",
    \"rollback_criteria\": {
      \"p99_latency_increase_pct\": 25,
      \"five_xx_delta_pct\": 0.5
    },
    \"observability_hooks\": [\"canary-heuristic-01\", \"trace-sampling-1000/10min\"]
  }

- Admission controller patch (YAML snippet):

  apiVersion: rwi.platform/v1
  kind: LeaseOverride
  metadata:
    name: lease-tenant-42-20260610
  spec:
    tenant: tenant-42
    deltaConcurrency: 100
    targetServices:
      - text-generation-prod
    revertAfter: 6h

Audit, post-lease review and KPIs

- Within 48 hours the lessee must publish a short post-lease audit note capturing: whether rollback criteria fired, actual cost delta, lessons learned, and whether a follow-up permanent capacity request is required.
- SRE team will sample 10% of leases for quarterly audits focusing on cross-tenant impact and governance adherence.
- KPIs to track: lease success rate (no auto-revoke), avg time-to-revoke, percent of leases with complete observability, and cost delta per lease.

Security and compliance notes

- No lease may alter data residency configurations or bypass encryption. Any request that affects data paths must include a security reviewer and be marked \"restricted\".

Edge cases and guidance

- Overlapping leases: If two leases would in aggregate exceed accepted headroom, automation serializes approvals and notifies both lessees.
- Unresponsive lessee: If lessee owner does not respond during active alerts, the Lease Governor has authority to revoke.

Appendix: FAQ and examples

Q: Can we extend a lease mid-window?
A: Yes, with a new request and shortened automated pre-checks; Lease Governor must approve extension. Maximum cumulative extension limited to 72 hours without exec approval.

Q: What happens when a lease is revoked automatically?
A: Automation immediately reverts policies and posts metrics snapshot. Oncall must validate the revert and open an incident if metrics do not recover within 15 minutes.
