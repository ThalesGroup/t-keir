Service Traffic Topology and Adaptive Shaping Guide

Overview

This guide documents the platform-level approach for mapping service traffic topology and applying an adaptive request-shaping layer to guarantee latency SLOs, control cost exposure, and preserve fairness across tenants and feature priorities. It covers topology discovery, shaping algorithm design, configuration examples, dashboards and alerting, an operational runbook for degraded conditions, retrospective observations from the Q4 2025 trial, and a short roadmap for next steps.

Motivation and goals

- Problem: Multi-tenant inference traffic causes unpredictable tail latency and sudden cost spikes when bursty workloads align with cold caches or concentrated GPU affinity.
- Goals:
  - Keep 99th percentile inference latency below configured SLOs per tenant (default 500ms for interactive endpoints).
  - Limit per-tenant burst cost to committed budget (burst credit model).
  - Prevent head-of-line (HOL) blocking between latency-sensitive and batch/background workloads.
  - Provide operators clear observability and safe rollbacks.

Scope and assumptions

- Applies to all platform ingress proxies and the request router layer that makes placement decisions.
- Assumes existing tokenized SLI metrics (p95/p99 latency, token cost, KV cache hit rate) are available per-tenant and per-model.
- Does not replace model-level QoS (quantization/cost tuning) but complements it by shaping at the network/runtime boundary.

Design summary

1) Topology mapping: Build a dynamic graph that tracks traffic flows between logical request sources (tenants/routes) and serving clusters (model-version pools, GPU pools, regional endpoints).

2) Shaping primitives:
  - Rate limit (requests/sec) with elastic burst credits.
  - Concurrency cap (active requests) per tenant+route.
  - Priority queueing with preemption hints for emergency-fallback routes.
  - Cost-gated admission based on token budget windows.

3) Adaptive controller: Uses short-term telemetry (30s, 1m windows) to adjust shaping parameters: lower concurrency when p99 rises or cache hit-rate drops; replenish burst credits gradually; move low-priority traffic to cooler pools.

Topology mapping details

We maintain three primary maps:
- Source map: tenant -> active routes -> origin region
- Pool map: GPU pool -> region -> served model-variants -> current utilization and evictable slots
- Link map: measured latency and KV-hit statistics for source->pool pairs (updated continuously)

These maps are stored in the platform catalog service and replicated to the request-router sidecars (read-only primary) every 15s. Topology reconciliation frequency is configurable (default 15s) and should balance staleness risk vs. control-plane load.

Adaptive shaping algorithm (high level)

Inputs (per-request window): p99_latency_source, pool_utilization, kv_hit_rate, token_cost_rate, tenant_priority, burst_credit_balance.

Algorithm steps (per control interval, default 10s):
1) Compute violation_score = w1 * (p99_latency_source / p99_slo) + w2 * (1 - kv_hit_rate) + w3 * pool_utilization
2) If violation_score > threshold_high: tighten shaping for that source by reducing concurrency_cap by 20% and draining 1/3 of available burst credits to the shaping bucket.
3) If threshold_low < violation_score <= threshold_high: reduce concurrency_cap by 10% and mark lower-priority routes for cold-pool migration.
4) If violation_score <= threshold_low for 3 consecutive intervals: relax shaping (increase concurrency_cap up to configured max) and slowly replenish burst credits at configured refill rate.

Default weights and thresholds (can be tuned per tenant):
- w1=0.6 (latency importance), w2=0.2 (cache health), w3=0.2 (utilization)
- threshold_high = 1.2, threshold_low = 0.8

Configuration examples

Below is an example tenant policy YAML applied at the router: 

policy: "interactive-standard"
settings:
  p99_slo_ms: 500
  concurrency_max: 50
  concurrency_min: 2
  burst_credit_initial: 1000
  burst_refill_per_min: 50
  cold_pool_migration_enabled: true
  weights: [0.6, 0.2, 0.2]
  thresholds: [0.8, 1.2]
  control_interval_secs: 10

CLI (example):
- Apply policy: 
  rctl policy apply --tenant=acme --policy-file=interactive-standard.yaml --env=prod
- Query topology: 
  rctl topology describe --tenant=acme --format=table

Dashboard and alerting guidance

Recommended dashboard panels (per-tenant / per-model):
- Real-time topology heatmap: source -> pool latency (color-coded)
- SLI trend: p50/p95/p99 latency (1m, 5m), with SLO lines
- Burst credit balance and refill rate histogram
- Concurrency cap and current active requests
- KV cache hit rate and model load trend

Suggested alert rules (Prometheus-style expressions):
1) High p99 breach:
  expr: max_over_time(p99_latency_ms[5m]) > tenant_p99_slo_ms * 1.2
  for: 3m
  severity: P1
2) Rapid burst depletion:
  expr: rate(burst_credit_balance[1m]) < - (burst_refill_per_min / 60) * 2
  for: 2m
  severity: P2
3) Cold-pool overload:
  expr: avg_over_time(pool_utilization[2m]) > 0.85 and avg_over_time(kv_hit_rate[2m]) < 0.6
  severity: P2

Alert routing: P1 -> oncall SRE + platform pager; P2 -> platform channel + ticketing. Include tenant owner in notifications for P1 and require explicit acknowledgement in the incident runbook.

Operational runbook (degraded latency event)

1) Triage (owner: platform oncall)
  1. Check dashboards: identify affected tenants and serving pools.
  2. Inspect topology map: are many sources draining to the same pool?
  3. Check KV cache hit rate and recent rollouts for model variants.

2) Immediate mitigation (if p99 > slo * 1.5):
  a. Apply emergency shaping for impacted tenants: reduce concurrency_cap by 50% and set burst_refill_per_min to 0.
     Command: rctl policy override --tenant=<T> --concurrency-cap=<value> --reason="emergency-latency"
  b. If eviction is required, move non-priority traffic to cold pools: rctl migration start --from=<hot-pool> --to=<cold-pool> --selector='priority<50'
  c. If persistent, enable temporary fallback to model-variant with lower memory footprint: rctl model fallback --tenant=<T> --variant=quantized-v2

3) Root cause analysis (owner: platform reliability team)
  - Collect traces and tail logs for sample requests.
  - Compare recent deployments, kernel changes, and topology reconciliation events.
  - If hardware saturation suspected, coordinate with GPU-ops to inspect node health.

4) Post-incident follow-up:
  - Publish incident notes with timeline, actions, and suggested policy tweaks.
  - Adjust default weights or thresholds if event tied to algorithm mis-calibration.

Retrospective: Q4 2025 trial summary

What we did: Deployed adaptive-shaping to 20% of production traffic for non-enterprise tenants in 3 regions. We collected 6 weeks of telemetry and ran 4 injected workload bursts to exercise cold-pool transitions.

Key findings:
- Adaptive shaping reduced p99 tail by median 38% for affected tenants.
- Inaccurate topology mappings (stale link map entries) caused two unnecessary migrations; lowered reconciliation interval from 30s to 15s resolved this.
- The default burst refill rate was too aggressive, producing oscillations; we replaced instantaneous refill with token-bucket smoothing.

Action items from retrospective:
- Add canary tests for topology reconciliation when control-plane changes are released.
- Introduce synthetic KV-hit probes per pool to better predict cold transitions.
- Provide a per-tenant tuning page in the Redwood Console showing how weights affect behavior.

Roadmap (next 12 months)

- Q2 2026: Apply tenant-level machine-learning model to adapt weights (w1/w2/w3) instead of static values.
- Q3 2026: Integrate shaping decisions with cost-optimization engine (link tags for billable credits).
- Q4 2026: Expose self-serve shaping policy editor in console with simulation mode.
