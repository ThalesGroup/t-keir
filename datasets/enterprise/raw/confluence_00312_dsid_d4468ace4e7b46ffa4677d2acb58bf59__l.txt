Local Cost Emulator and Developer SDK - Design Spec

Overview:

This design specification describes the Local Cost Emulator (LCE) and accompanying Developer SDK. The LCE is a lightweight, reproducible emulator that lets developers and solutions engineers simulate Redwood Inference consumption scenarios (token counts, streaming vs batched paths, quantization variants, caching hit rates, warmup/coldstart behaviour) on a developer laptop or CI runner without requiring access to a live account. The goal is to give fast, local feedback for cost and latency trade-offs during prompt engineering, model selection, and product integration.

Why we need this:
- Reduce iteration time for developers who need to evaluate cost/latency implications before running against hosted or dedicated capacity.
- Prevent costly developer mistakes that produce wide-scale unintended consumption (e.g., runaway loops, incorrect sampling settings).
- Provide a consistent baseline for pre-sales and onboarding conversations (estimate impact of fidelity choices).

Goals (MUST):
1. Provide deterministic cost and latency estimates that match production telemetry within a bounded error (target +/- 15% for token cost; +/- 20% for 95th percentile latency for representative workloads).
2. Offer programmatic SDK primitives (Python/Node) that mirror Redwood API surface area for generation, streaming, and embeddings calls used in cost calculations.
3. Support configurable workload profiles: session length distribution, prefix caching rate, batching windows, and quantization variant.
4. Run offline (no cloud calls) with lightweight sample models and precomputed per-variant cost kernels.

Non-Goals (explicitly out of scope):
- Producing exact latency numbers for specialized hardware (e.g., large multi-GPU setups). LCE provides representative signals, not hardware-level benchmarking.
- Replacing lab-grade performance harnesses and stress testing used by SRE/Runtime teams.

High-level architecture:
- Emulator Core (Rust): deterministic tokenization, cost model evaluator, event-driven session simulator. Exposes a thin FFI to language SDKs.
- Workload Profiles (YAML): composable presets (low-latency chat, high-throughput batch, interactive embeddings) that define request distributions, sequence length histograms, and cache-hit probabilities.
- Cost Kernel Store (JSON): per-model token cost coefficients, per-variant overheads (quantization multipliers, KV cache savings), and precomputed batching efficiency curves.
- Developer SDKs: Python and Node wrappers that expose Redwood-like client APIs (generate(), stream(), embed()) but route calls to the local emulator.
- CLI and CI Integrations: run scenarios, produce CSV/JSON reports, and fail CI gates if cost or latency thresholds are exceeded.

API examples (Python):
# client = LocalCostClient(profile='interactive-chat')
# resp = client.generate(prompt, model_variant='redwood-compat-7b-q4_0', max_tokens=200)
# resp.summary -> { 'estimated_cost_usd': 0.0032, 'median_latency_ms': 45, 'batching_efficiency': 0.72 }

Configuration table (examples):
| field | type | description | sample |
| Profile.name | string | profile identifier | interactive-chat |
| seq_length_p50 | int | median sequence length (tokens) | 128 |
| cache_hit_rate | float | estimated prefix/KV cache hit ratio (0-1) | 0.38 |
| batching_window_ms | int | emulated batching window to approximate runtime batching | 25 |
| model_variant | string | model + quantization label used to select cost kernel | redwood-compat-7b-q4_0 |

Cost model details:
- Token cost = base_token_coeff * generated_tokens * variant_multiplier + per-request_overhead
- Variant multiplier captures quantization and kernel efficiency; derived from lab measurement matrix maintained by Runtime team.
- Batching efficiency curve is a sigmoid approximation: efficiency(batch_size) = 1 - exp(-alpha * batch_size) scaled by sequence composition. The LCE ships with calibrated alpha values for common families.

Developer SDK surface (public functions):
- LocalClient(profile: str, budget_usd: float = None)
- generate(prompt: str, max_tokens: int, model_variant: str, stream: bool = False) -> dict
- embed(texts: List[str], model_variant: str) -> dict
- run_scenario(scenario_name: str, iterations: int) -> report (JSON)
- audit_report() -> attaches per-call simulated telemetry (tokens_in, tokens_out, estimated_cost, simulated_latency_ms)

CI integration patterns:
1. Scenario smoke test: run 'lce run_scenario smoke' as part of PR; fail if estimated cost per 1k requests > budget or median latency > threshold.
2. Regression guard: add a telemetry snapshot to repo; CI verifies that code changes do not increase estimated cost by more than 10% for canonical prompts.

Testing & calibration plan:
1. Initial calibration against 10 canonical workloads using runtime lab traces. Compute multipliers and batching alpha constants.
2. Backtest weekly for first 8 weeks of rollout: compare LCE estimates to production telemetry (token cost and latency buckets) and adjust kernels.
3. Provide a calibration CLI: 'lce calibrate --upload-trace <trace.json>' to propose new kernel coefficients (requires opt-in telemetry upload).

Security and privacy considerations:
- LCE runs offline by default and stores no customer secrets. If a customer chooses to calibrate with real traces, the CLI must validate and scrub PII and require an explicit flag.
- Telemetry artifacts collected for calibration are encrypted at rest and retained according to the data retention playbook.

Metrics and success criteria (30/60/90 day):
- 30d: SDK distributed internally; 10 teams have used LCE for at least one integration; calibration pipeline established.
- 60d: Mean absolute error for token cost <= 12% vs production for canonical workloads.
- 90d: LCE integrated into onboarding demo and included in at least 3 sales evaluations; documented CI patterns adopted by SDK teams.

Rollout plan:
1. Alpha (internal only): engineering and solutions enablement teams. Collect calibration traces.
2. Beta (wider internal + pilot customers): opt-in for early customers via SDK package; gating requires security review.
3. GA: public release in package manager and included in developer onboarding.

Backwards compatibility and upgrade notes:
- Cost kernels are versioned; reports include kernel_version to ensure reproducible results.
- CI gates should pin kernel_version to avoid noisy diffs; provide an automated 'bump' workflow that re-runs canonical scenarios and annotates PRs.

Operational runbook (summary):
1. If calibration delta > 25% across canonical workloads, open an incident tagged 'lce-calibration' and assign to Runtime tools.
2. For reports of large discrepancies from customers, request trace artifacts and run 'lce calibrate' in a secured environment.

Documentation and example artifacts to ship with GA:
- Quickstart: local install, run 'interactive-chat' scenario, read report.
- Cookbook: tuning batching_window, simulating coldstart-heavy workloads, interpreting audit_report fields.
- Example CI pipeline snippet (GitHub Actions) and prebuilt canonical scenario JSONs.
