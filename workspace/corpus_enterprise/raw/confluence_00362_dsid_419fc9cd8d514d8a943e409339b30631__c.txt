contract-gateway-and-edge-validation-adr-2026

Summary
-------
This ADR records the decision to introduce a Contract Gateway at the edge (the Contract Gateway) that performs: (1) lightweight schema validation and capability negotiation for incoming requests, (2) fast-path routing for compatible requests, and (3) structured downgrade and audit mechanisms for incompatible or degraded requests. The gateway is a small, highly-available service deployed in the edge/ingress plane that standardizes request/response envelopes and enforces deployable validation policy.

Context and motivation
----------------------
- We operate multiple model variants (quantized/FP16/multi-precision) and deployment modes (hosted/dedicated/private). Clients currently need to anticipate variant differences leading to brittle client logic.
- Several incidents have been traced to mismatched request envelopes and late-stage validation failures that amplify cost and latency.
- We want an operationally simple mechanism to route compatible requests through a low-latency fast-path to runtime variants while rejecting or transforming incompatible requests at the edge with actionable telemetry.

Goals
-----
1. Provide a single entrypoint that validates canonical request envelopes and capability hints before requests hit serving runtime.
2. Enable deterministic fast-path routing for requests with verified compatibility (sub-10ms extra edge processing).
3. Emit precise validation telemetry and structured error reasons for downstream tracing/evals.
4. Support progressive rollout: feature-flagged validation policies and a clear rollback plan.

Non-goals
---------
- Full payload schema transformation (heavy payload rewriting belongs to gateway adapters downstream).
- Replacing the model-serving contract or long-term client adaptation; this gateway is a compatibility enforcement and observability layer.

Decision
--------
We will implement a Contract Gateway service with the following characteristics:
- Lightweight JSON schema checks and key capability negotiation (e.g., streaming, function-calls, structured-output) performed synchronously before routing.
- A stable metadata envelope that contains: client-capabilities, request-class, route-hints, request-id, and optional client-schema-hash.
- Fast-path allowlist: verified request signatures/hashes or capability proofs that bypass in-depth validation.
- Degradation policy: if validation fails, gateway returns clearly typed errors (4xx with structured reason) or routes to a transform/backfill path depending on policy.
- Telemetry: every decision emits an event to Kafka/telemetry pipeline with fields mapped to existing telemetry schema.

Design details
--------------
Request envelope (example):
{
  "envelope_version": "1.0",
  "request_id": "req_abc123",
  "client_capabilities": ["streaming", "function_call_v2"],
  "request_class": "interactive",
  "schema_hash": "sha256:...",
  "payload": { /* model-specific body */ }
}

Validation rules (summary table):
| Rule ID | Target field | Check | Failure action | Owner |
|---------|--------------|-------|----------------|-------|
| VG-001  | envelope_version | must be 1.0 or 1.x | reject (400) | api-platform |
| VG-002  | schema_hash | optional but if present must match canonical schema store | route-to-transform or reject | model-onboarding |
| VG-003  | client_capabilities | subset of known capabilities | downgrade to non-streaming fast-path | eng-serving-runtime |
| VG-004  | request_class | must be one of {background, batch, interactive} | reject (400) | api-platform |

Capability negotiation
- Clients include declared capabilities; the gateway validates them against the capability catalog. If a declared capability is unknown but non-critical, gateway removes it and records a capability-mismatch metric. Critical unknown capability -> reject.
- For streaming requests, the gateway verifies transport and allowed size/time budgets before handing off to the runtime.

Fast-path routing
- A fast-path requires: envelope_version match, schema_hash match to canonical store, and client_capabilities subset verified.
- Fast-path routing target: cluster label fastpath=true on runtime side. Fallback to default route when any check fails.
- Metric: fastpath_accept_rate (target >= 80% for stable workloads) and fastpath_added_latency (target < 10ms p50).

Observability and SLOs
---------------------
- SLOs (Contract Gateway):
  - Availability: 99.99% (global edge for control plane calls excluded).
  - Validation throughput: handle peak p95 request rates with <5% additional tail latency.
  - Fast-path latency budget: additional p50 < 10ms, p95 < 35ms.
- Telemetry emitted per request: request_id, envelope_version, validation_result, failure_reason (if any), routed_variant, schema_hash, client_capabilities, latency_ms.
- Traces: start trace in gateway and propagate trace context to runtime; add an event for validation decision.
- Error budgeting: validation-rejects per client are counted against client-specific onboarding metrics and trigger alerts when >1% of requests rejected for 5m.

Runtime integrations and infra implications
----------------------------------------
- The gateway is stateless and horizontally scalable. It lives in the edge layer (kube cluster(s) colocated with ingress).
- It needs read-only access to: canonical schema registry (with caching), capability catalog, and route metadata. These are read-through caches with TTLs.
- For Private deployments, the gateway will be packaged as a lightweight sidecar option or an edge-service template with configuration flags (to respect customer network controls).

Security and privacy
--------------------
- Gateway must not persist payloads beyond ephemeral processing except for structured audit events. Payloads that contain PII are redacted before any audit emission (use default redaction rules consistent with data-management policy).
- All config endpoints and the schema registry access must be TLS mutual-auth.

Rollout plan
------------
1. Prototype (2 weeks): implement a mock gateway that validates envelope_version and request_class; capture metrics.
2. Pilot (4 weeks): enable in non-production region; instrument telemetry and run canary traffic for a subset of clients (feature-flagged).
3. Gradual rollout (8 weeks): incrementally enable validation rules; monitor fastpath_accept_rate, validation_reject_rate, and latency budgets.
4. Enforcement (after 12 weeks): begin rejecting with 4xx for high-confidence rules; communicate deprecation windows to SDK teams.

Rollback and mitigation
- Feature flags for each validation rule.
- If gateway causes >0.5% increase in p95 latency across a region for 15m -> disable new validation rules immediately and rollback to previous gateway image.
- Emergency bypass: an authenticated tenant-level header (signed by infra) can route requests directly to runtime; usage of this bypass must be tracked and limited.

Ownership and next steps
------------------------
- Owner: api-platform (primary), eng-serving-runtime (integration), eng-infra (deployment & infra), security (privacy review).
- First implementation ticket: AP-1234 (Contract Gateway basic validation and telemetry).
- Documentation: add a new page under eng-developer-experience/api-examples that includes SDK examples for building compatible envelopes.

Open questions
--------------
- Canonical schema store consistency model for private deployments (pull vs. push sync).
- How to handle encrypted payloads where schema_hash cannot be computed at the gateway. Proposed temporary solution: route to runtime with a flag and rely on runtime-side validation.

Appendix: example HTTP interaction
----------------------------------
Request:
POST /v1/generate HTTP/1.1
Host: api.redwood.ai
Content-Type: application/json
X-Client-Id: sdk-js-2.3.0

{ "envelope_version":"1.0", "request_id":"req-123", "client_capabilities":["streaming"], "request_class":"interactive", "payload": {"prompt":"Hello"} }

Possible gateway responses:
- 200 -> routed to runtime (fast-path header: X-Routed-FastPath: true)
- 400 -> { "error": "validation_error", "reason": "unknown_capability:function_call_v3" }
- 202 -> accepted for async transform/backfill (policy dependent)

This ADR is effective immediately for new ingress deployments created after the date above.
