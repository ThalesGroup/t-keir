VPC Terraform modules (alpha) – suite overview (AWS / Redwood Private)

## Summary
This page provides a high-level overview of the **VPC Terraform modules (alpha)** shipped in the `redwood-terraform` repository for **Redwood Private (AWS VPC + optional on-prem connectivity)** deployments.

The intent is to reduce networking variability during customer discovery/pilots by providing **Redwood-validated defaults** for:
- VPC + subnet layout
- routing + NAT strategy
- VPC endpoints (PrivateLink) + DNS behavior
- baseline security group patterns
- flow logs + log destinations
- IAM scaffolding (permission-boundary-friendly) for installer execution
- integration hooks for VPN / Direct Connect (placeholders)

This is **foundational infrastructure only**. Cluster install and application components are handled by **redwood-private-installer / Helm**.

---

## Goals (alpha)
1. Provide opinionated, composable modules with safe defaults that work for most Private deployments.
2. Expose a controlled set of inputs/overrides with clearly documented constraints.
3. Standardize outputs that the **Redwood Private installer** can consume (or preflight-validate).
4. Ship a repeatable validation pipeline (fmt/validate/tflint/checkov + integration tests).
5. Make Solutions Engineering/Pro Services successful in POCs with reference examples.

### Non-goals (alpha)
- Multi-cloud parity (GCP/Azure) beyond stubs/roadmap notes.
- Turnkey “one click” end-to-end environment + cluster install.
- Supporting every enterprise topology; instead we document **supported extension points** and anti-patterns.

---

## Where these modules fit in Redwood Private
**Typical flow (AWS):**
1) Customer (or SE/PS) runs Terraform modules to create the networking + foundational IAM/logging.
2) Terraform outputs are used to configure and run `redwood-private-installer`.
3) Installer performs preflight checks (endpoints, DNS, egress) and then installs cluster add-ons / Redwood services.

**Key integration points with the installer:**
- Subnet IDs for worker/node groups (private subnets) and (optional) ingress subnets
- VPC endpoints presence + Private DNS behavior (ECR is the most common failure mode)
- Egress strategy and allowed destinations (NAT vs proxy patterns)
- Log destinations for auditability (Flow Logs -> CloudWatch or S3)
- IAM execution role for installer with permission boundaries

**Design principle:** Modules must produce a predictable, supportable footprint that aligns with the reference architecture and installer assumptions.

## Module suite (alpha)
Modules are designed to be composable. You can use the full suite, or bring your own VPC and only use endpoints/logging/IAM patterns.

> Naming note: module source paths below reflect the `modules/` layout in `redwood-terraform`. Actual module names in docs/examples should match the repository README for the released tag.

### Module list and responsibilities
| Module | Primary responsibility | Key resources created | Typical inputs (high-level) | Key outputs (for consumers/installer) | Primary owner |
|---|---|---|---|---|---|
| `modules/vpc` | Opinionated VPC + subnet topology + routing defaults for Private deployments | VPC, subnets (public/private), route tables, IGW (optional), NAT gateways (default per-AZ), NACL defaults | `vpc_cidr`, `az_count`, `private_subnet_cidrs`, `public_subnet_cidrs` (optional), `nat_mode` (default: per_az) | `vpc_id`, `private_subnet_ids`, `public_subnet_ids`, route table IDs | Infra Eng (Networking): Victor Alvarez |
| `modules/vpc-endpoints` | Required/recommended VPC endpoints + Private DNS controls | Interface + gateway endpoints (S3 gateway; ECR API/DKR; STS; CloudWatch Logs; EC2; EKS; SSM/SSMMessages; KMS as needed) | `vpc_id`, `subnet_ids`, `endpoint_policy_mode`, `private_dns_enabled` per-service | `endpoint_ids`, `endpoint_sg_id`, resolved endpoint service set | Infra Eng (Networking): Victor Alvarez |
| `modules/logging-flow-logs` | Flow Logs defaults and destinations for auditability | VPC Flow Logs, IAM role/policy (CW option), CW Log Group or S3 target wiring | `destination_type` (cloudwatch|s3), `retention_days` (CW), `s3_bucket_arn` (customer-owned recommended), `traffic_type` | `flow_log_id`, destination identifiers, IAM role ARN (CW) | Security Eng + Infra: Kevin Osei / Irene Choi |
| `modules/security-groups` | Opinionated SG patterns for Private EKS footprints | SGs for nodes, control plane access patterns (where applicable), endpoint SG, egress SG patterns | `vpc_id`, `cluster_cidr`, `allowed_admin_cidrs` (optional), `egress_mode` | SG IDs for nodes/endpoints/ingress, egress rule summaries | Infra Eng + Private Deployments: Nina Petrova / Victor Alvarez |
| `modules/iam-installer` | IAM scaffolding for installer execution with permission boundaries | IAM role, policies, optional permission boundary attachment points | `role_name`, `permission_boundary_arn`, `tags`, `policy_mode` | `installer_role_arn`, policy ARNs, external ID placeholders (if used) | Security Eng: Marcus Lin / Hanae Suzuki |
| `modules/connectivity-hooks` | Placeholders/outputs for VPN/DX integration without encoding enterprise-specific assumptions | Minimal route propagation hooks, output structure for VGW/TGW attachment IDs (if supplied) | `tgw_id` (optional), `customer_cidrs`, `route_table_ids` | route table IDs, attachment placeholders, documented extension points | Solutions Eng + Infra: Markus Klein / Irene Choi |

### Recommended consumption patterns
**Pattern A (most common): Full suite**
- Use `vpc` + `vpc-endpoints` + `logging-flow-logs` + `security-groups` + `iam-installer`

**Pattern B: Customer-managed VPC**
- Customer provides `vpc_id`, subnets, route tables
- Use `vpc-endpoints` + `logging-flow-logs` + `iam-installer` (and optionally `security-groups`)

**Pattern C: Strict enterprise connectivity (TGW/VPN/DX)**
- Use Pattern A or B
- Add `connectivity-hooks` and follow documented extension points (customer network team implements attachments and routing)

## Supported topologies (alpha)
Supported topologies are intentionally narrow for supportability.

### Baseline topology
- **2 or 3 Availability Zones** (3 recommended)
- **Private subnets** for cluster nodes and internal services
- Optional **public subnets** for managed ingress where customer policy permits (otherwise use private ingress + customer-provided LBs)
- **NAT gateways**:
  - Default: **per-AZ NAT** (resilience)
  - Supported override: **single NAT** (cost optimization; lower availability)

### DNS assumptions
- VPC DNS support and hostnames **enabled**.
- Interface endpoints often rely on **Private DNS** for “just works” behavior.
- If Private DNS must be disabled (rare), the deployment guide requires explicit endpoint-specific DNS handling and installer preflight will warn.

### Endpoint expectations
- At minimum, endpoints required to avoid image pull / control-plane dependencies in private subnets:
  - **ECR (api + dkr)**
  - **S3 (gateway)**
  - **STS**
  - **CloudWatch Logs** (if using CW logging destinations)
- Additional endpoints may be required depending on cluster setup and customer controls (SSM, KMS, EKS, EC2).

## Interfaces: inputs/outputs (design intent)
The module interfaces are designed around:
- **Minimal required inputs** for the happy path
- **Explicitly documented extension points** for enterprise needs
- **Stable outputs** that other modules and the installer depend on

Output stability is critical during alpha because customers will pin module versions and wire outputs into their own pipelines.

See: ADR-027 for module boundaries and the public interface philosophy.

---

## CI, validation, and integration tests
CI is designed to catch the most common failure modes before they reach pilots.

**Per-PR checks (gated):**
- `terraform fmt` and `terraform validate`
- tflint (AWS ruleset)
- checkov (baseline IaC security scanning)
- docs lint (where applicable)

**Integration tests:**
- Ephemeral environment tests (create/destroy) validate:
  - subnet + route table wiring
  - NAT assumptions across AZ counts
  - endpoint creation + Private DNS toggles
  - expected outputs exist and are non-empty

Heavier integration tests may be scheduled nightly to manage cost/time; PR gating remains focused on fast feedback.

See: ADR-028 for full acceptance criteria.

## Versioning and releases (alpha expectations)
- Semantic versioning is used (MAJOR.MINOR.PATCH).
- During alpha, we will avoid breaking changes, but **breaking changes may occur** if required for security/supportability.
- Design partners should pin exact tags and coordinate upgrades with Redwood.

Release process details are documented in the Terraform module versioning and release standard (see related pages).

---

## Known limitations (alpha)
- Not validated for GovCloud or air-gapped on-prem-only environments.
- DNS edge cases (custom resolvers, split-horizon) require careful design; we provide guidance but do not encode enterprise DNS appliances in modules.
- Connectivity (VPN/DX/TGW) is supported via hooks/outputs and patterns, not as a full turnkey module.
- Flow Logs cover VPC-level traffic; workload/cluster logs are handled by installer/cluster tooling.

## Appendix: What “opinionated defaults” means here
These modules default to:
- private-by-default subnet usage
- endpoint-first access to AWS services to reduce public egress reliance
- logging enabled with explicit destinations
- least-privilege scaffolding with customer-managed permission boundaries

If a customer’s baseline violates one of these assumptions, treat it as an architecture review item and involve Infra + Security early.
