Onboarding observability contracts for dedicated tenants

Summary

This playbook defines the observability contract that Redwood and a customer agree on when provisioning a Dedicated tenant (reserved capacity or private deployment). The contract covers the telemetry signals, their schema, minimum retention and sampling guarantees, alerting baseline, SLO mappings, and a validation checklist used during onboarding. The goal is to ensure parity between Redwood operational expectations and the customer’s telemetry exports so that both parties can reliably triage incidents, verify SLAs, and run QBRs.

Who this is for

- Customer Success (CS) owners running onboarding
- Solutions Engineers and Integration Engineers
- Dedicated tenant SRE/Platform owners at Redwood
- Customer platform/observability engineers

Goals and non-goals

- Goals:
  - Agree and validate a minimum telemetry contract prior to production onboarding.
  - Prevent blind spots that block incident diagnosis (e.g., missing request trace ids, tenant_id labels).
  - Provide deterministic SLI extraction and alert thresholds for initial week-0 to week-12 SLOs.
- Non-goals:
  - Do not mandate customer-specific internal metrics beyond agreed labels and formats.
  - This is not an exhaustive observability design for the customer; it is a compatibility contract for Redwood’s support and SRE workflows.

Contract: required telemetry signals (table)

| Signal type | Canonical name (example) | Required fields/labels | Minimum frequency / retention | Notes |
|-------------|--------------------------|------------------------|------------------------------|-------|
| Request metric (histogram) | request.duration | service, route, model, tenant_id, status_code, request_id | 1s buckets; retention 90d for aggregates | Redwood expects histogram or Prometheus SUMMARY so p50/p90/p99 can be computed. |
| Request counter | request.count | service, route, model, tenant_id, status_code | delta COUNTER; retention 365d | Increment on request start/finish. Include status_code for error classification. |
| Token metric | tokens.generated | model, tenant_id, request_id | per-request sample; retention 90d | Optional for cost attribution but strongly recommended. |
| Traces / spans | span (OTel) | trace_id, span_id, parent_id, service, operation, route, model, tenant_id, request_id, sampling.priority | full traces for 1% of requests, tail-sampling for errors (100%) | Spans should attach request_id and tenant_id. Use semantic conventions below. |
| Logs | structured logs (JSON) | timestamp, level, service, tenant_id, request_id, message, err_code (optional) | 100% of errors; INFO sampling 1-10% | JSON structured logs preferred. Use consistent field names. |
| Synthetic checks | synthetic.transaction | check_id, tenant_id, route, latency_ms, success | run every 60s during cutover; retention 90d | Used for validation step and baseline alerts. |

Required labels and conventions

- tenant_id: string, immutable per tenant (required for all signals).
- request_id: UUID assigned by router / ingress for the request lifecycle (required).
- model: model id or family (e.g., gpt4o-small) when relevant.
- route: logical API route name (e.g., generation.v1, embeddings.v1).
- service: component name (e.g., ingress-proxy, inference-worker).
- status_code: canonical codes (200, 4xx, 5xx) or internal error categories.

Sampling guarantees and error tail collection

- Baseline sampling: 1% uniform sampling of traces across traffic for 30d after go-live to collect representative traces.
- Error-tail sampling: 100% of traces that result in an error status (5xx or internal error) must be sent. This enables root-cause analysis regardless of base sampling.
- Synthetic journey traces: 100% of synthetic checks must export full spans.

Alerting and incident thresholds (default initial set)

- Pager/critical (Redwood SRE + CS on-call):
  - sustained p99 request latency > 4s for > 5m across > 5% of tenants
  - error rate (5xx) > 3% for > 5m across total requests
- High-priority (CS/SE + engineering on first response):
  - tenant-specific p99 > configured tenant SLO by 2x for > 10m
  - synthetic.check failures > 3 consecutive failures for a tenant
- Informational (Slack/ops):
  - tokens.generated 24h change > 50% vs baseline (cost-monitoring trigger)

SLO mapping and initial targets

- Recommended starter SLOs for Dedicated tenants (can be adjusted by contract):
  - Availability SLO: successful request rate >= 99.9% over rolling 30d (success = status_code < 500)
  - Latency SLO: p95(request.duration) <= 1.2s for generation routes (initial baseline)
  - Cost-awareness SLO: median tokens per request stable within 20% of baseline across 7d (informational)

Onboarding validation checklist (ordered steps)

1. Pre-cutover alignment call (SE + Customer observability lead + Redwood SRE): review contract and choose export method (Prometheus scrape vs OTLP push).
2. Export configuration: customer provides test endpoint or config; Redwood provides example scraping job / OTEL collector config (see snippets).
3. Smoke export test: send 1,000 synthetic transactions and validate metrics/labels arrive in Redwood tenant ingestion pipeline.
4. Trace validation: ensure at least 1% of traces appear, and 100% of error traces for test error injection.
5. Alert simulation: trigger synthetic failures and latency injection to verify alerts fire to CS channel.
6. QBR baseline capture: run 72h of production-equivalent traffic to capture baseline metrics for QBR and SLO tuning.
7. Production cutover sign-off: CS, SRE and Customer observability lead sign the checklist.

Troubleshooting common mismatches

- Missing tenant_id on metrics: verify collector includes resource attributes or the scraping job populates tenant_id via relabel_configs.
- request.duration is a gauge instead of histogram: the ingestion pipeline expects histogram buckets; either change to histogram or send summary with sufficient quantiles.
- Spans missing request_id: ensure the ingress assigns request_id and propagates it to downstream services via headers (x-request-id).
- No error traces: check tail-sampling config and error classification rules in the collector.

Rollout notes and risk mitigations

- Canary for telemetry: enable telemetry export for a low-volume tenant first for 48h to validate label cardinality and cost.
- Cardinality caps: Redwood reserves the right to request label normalization if cardinality exceeds 5k distinct values/day for tenant-scoped labels.
- Cost controls: if metrics/log egress costs exceed agreed thresholds, throttle sampling and re-run validation.

Appendix: example SLO extraction PromQL

- p95 latency (generation route):
  histogram_quantile(0.95, sum(rate(request_duration_seconds_bucket{route=\"generation.v1\"}[5m])) by (le))
- success rate over 30d:
  1 - sum(increase(request.count{status_code=~\"5..\"}[30d])) / sum(increase(request.count[30d]))
