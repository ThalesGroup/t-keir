Runbook: Runtime keycache index corruption causing GPU OOMs (runtime-2.4.x hotfix)

## Purpose
This runbook covers detection, mitigation, and rollout steps for a class of incidents where long-running sessions experience sustained GPU memory growth, degraded tail latency, and eventual GPU OOMs due to keycache index inconsistency after journal compaction.

This page supersedes the emergency notes in ENG-424242 by consolidating the confirmed root cause, the runtime-2.4.x hotfix behavior, and operational procedures for Hosted, Dedicated, and Private deployments.

## Summary (what happened)
Over multiple escalations (Hosted + Dedicated), customers reported sudden GPU OOMs coinciding with:
- Sustained GPU memory growth on long-running sessions
- Increased p95/p99 latency
- Spikes in keycache journal compaction time
- Repeated key index resync events

In affected cases, stale index entries prevented proper eviction. Under fragmentation, the GPU allocator entered a stall pattern (increased reserve/retry loops), leading to runaway reservation for a subset of sessions and eventual OOM.

## Confirmed root cause (updated)
The initial hypothesis (dangling pointers in the merge path) was partially correct but incomplete.

**Confirmed cause (runtime-2.4.0 through runtime-2.4.1):**
A race condition in the keycache journal compaction + snapshot merge path where concurrent eviction and a compaction commit could publish a partially-updated index view. The index version could advance while a subset of segments still referenced pre-compaction offsets, producing a mixed-generation index.

**Why it showed up “cross-environment”:**
Hosted, Dedicated, and Private deployments manifested at different thresholds because:
- Workload mixes differed (long-tail autoregressive vs. short requests)
- Memory pressure differed (fragmentation tolerance varies by GPU SKU and co-tenant load)
- Some environments had higher compaction frequency due to key churn

**Secondary amplifiers:**
- Long-tail autoregressive requests with large KV footprints avoid typical short-circuit evictions.
- Fragmentation increases allocator compaction overhead; once stalls begin, handle cleanup lags, increasing pressure further.

## Blast radius / customer impact
- High severity when it triggers: request failures due to OOM, degraded throughput, and sometimes traffic migration.
- Hosted: multi-tenant transient throttles and elevated retries.
- Dedicated/Private: prolonged degradation possible if nodes are not restarted or upgraded.

## When to use this runbook
Use this runbook when you observe any combination of:
1) Rapidly increasing GPU memory (allocated or reserved) without matching throughput
2) Keycache index resync loops and/or elevated compaction latency
3) GPU allocator stall metrics increasing (reserve failures, retry loops)
4) OOMs on long-running sessions that do not reproduce on fresh pods

## Triage checklist (15 minutes)
1. Confirm scope
   - Is it a single model deployment, a region, or multi-region?
   - Identify whether issues correlate with long-running sessions.

2. Confirm symptoms
   - Check OOM logs and allocator stall metrics.
   - Check for index resync spikes and compaction spikes.

3. Identify runtime version
   - Versions at highest risk: runtime-2.4.0, runtime-2.4.1.
   - Hotfix versions: runtime-2.4.2-hotfix (preferred) and runtime-2.4.1-hotfix (intermediate, if already deployed).

4. Decide immediate mitigation
   - If active OOMs: apply emergency mitigations first (below), then proceed to rollout/upgrade.

## Immediate mitigations (no code change)
### Mitigation A: Reduce long-lived session pressure
- Temporarily lower max session TTL (if supported by the serving config) and/or reduce max context length for affected endpoints.
- Preferably target only the affected model deployment(s) to minimize customer impact.

### Mitigation B: Force safe eviction mode (runtime flag)
If the deployment supports runtime flags, enable safe eviction mode to reduce the probability of publishing mixed-generation index views during pressure.

Set one of the following flags (depending on environment tooling):
- KEYCACHE_SAFE_EVICT=1
- RUNTIME_KEYCACHE_SAFE_EVICT=true

Operational notes:
- Safe eviction can reduce throughput by ~2–6% on KV-heavy workloads; treat as temporary.
- If OOMs persist after enabling, proceed to Mitigation C and upgrade.

### Mitigation C: Controlled restart / pod recycling
If allocator stalls are already severe, a rolling restart can restore service while you prepare the hotfix rollout.

Guidance:
- Hosted: follow standard regional rolling restart policy; keep capacity headroom.
- Dedicated/Private: coordinate with Customer Success; do not restart all nodes simultaneously.

## Hotfix / permanent remediation
### Recommended fix version
**runtime-2.4.2-hotfix** (preferred)
- Adds index generation fencing and atomic publish semantics for compaction merges.
- Introduces stricter validation around index segment boundaries.
- Adds a bounded emergency reclaim path to break allocator stall loops.

Notes on earlier hotfix:
- runtime-2.4.1-hotfix reduces incidence via linearized merge fencing, but does not fully eliminate mixed-generation edge cases under extreme churn. Upgrade to runtime-2.4.2-hotfix as soon as feasible.

### What the hotfix changes (operator-facing)
- New metric: runtime.keycache.index_generation_conflict_count (should remain near zero)
- Additional log lines when safe eviction is triggered under fragmentation
- Emergency reclaim triggers only when stall thresholds are exceeded; it is rate-limited

## Rollout procedure
### Hosted rollout (canary → regional → global)
1. Stage
   - Deploy runtime-2.4.2-hotfix to staging.
   - Run replay workload for at least 6 hours (24 hours preferred if incident pressure is low).

2. Canary
   - Start at 5–10% traffic in a low-risk region (historically eu-west-1 was used).
   - Monitor for at least 12 hours; extend to 48 hours if the incident is ongoing or signals are noisy.

3. Regional expansion
   - Increase to 25% then 50% in the canary region.
   - Expand to one additional region.

4. Global
   - Proceed to full rollout once key signals stabilize (see Success Criteria below).

Rollback plan:
- If index_generation_conflict_count increases or OOM rate worsens, roll back to prior stable runtime and enable KEYCACHE_SAFE_EVICT=1 until a corrected build is deployed.

### Dedicated/Private rollout
1. Confirm maintenance window with Customer Success.
2. Upgrade one node first (or one pool) and run a 2–4 hour soak test.
3. Upgrade remaining nodes in rolling fashion.
4. Leave safe eviction enabled for 24 hours post-upgrade if the customer runs KV-heavy workloads, then disable if stable.

## Success criteria (what “fixed” looks like)
- No OOM regressions on historical replay traces or during soak.
- allocator stall metrics decrease materially (target: ≥25% reduction from incident baseline).
- Memory fragmentation improves (arena free-percentiles improve by ~20% within 24 hours on representative load).
- Index resync count returns to baseline; generation conflicts remain ~0.
- Impacted customers confirm restored baseline throughput.

## Failure modes and what to do
1) OOMs persist after hotfix rollout
- Verify the running version actually updated.
- Check if workload exceeds expected KV limits; consider tightening context/TTL.
- Enable safe eviction mode temporarily.
- Escalate to Serving Runtime on-call with:
  - Region(s), model deployment(s)
  - Runtime version(s)
  - 2–4 hour window of dashboards
  - Representative request traces (redacted)

2) Throughput regression after enabling safe eviction
- Disable safe eviction after hotfix deployment and 24 hours of stability.
- If throughput remains degraded, check for unrelated GPU fragmentation drivers (driver version changes, co-tenancy shifts, model swaps).

## Communications guidance
- For active incidents: publish a brief customer-facing status update noting mitigations in progress and an ETA for a runtime hotfix.
- For Dedicated/Private: provide a maintenance window and a rollback plan.
- After full rollout: share a short incident summary and confirm monitoring improvements.
