Adaptive Embeddings Fidelity Packaging and Onramp Brief

h1. Adaptive Embeddings Fidelity Packaging and Onramp Brief

Summary

This brief describes a product packaging and onboarding proposal for "Adaptive Embeddings": a set of SKU and fidelity controls that let customers trade storage cost, retrieval latency, and vector fidelity for embeddings-powered features (search, rerank, semantic matching). The document covers target users, concrete packaging options, pricing heuristics, SLO/telemetry requirements, an onboarding checklist, and rollout recommendations for hosted, dedicated, and private deployments.

Problem statement

As more customers integrate high-cardinality embeddings stores into production applications, we observe three common pain points:

- Unpredictable storage costs driven by retention and dimensionality.
- Latency and throughput regressions at scale when embeddings are hot or when retrieval patterns spike.
- Difficulty mapping model fidelity (float/quantized, dimensionality, index recall) to commercial tiering and SLOs.

Goals

1. Create a small set of packaging tiers that are simple to understand and map to unit economics.
2. Expose fidelity knobs (dimensionality, quantization, retention tiers, index type) to customers through API and Console UX.
3. Provide an onramp that means small customers can self-serve while enterprise customers can request assisted migration paths.
4. Instrument SLOs and telemetry so we can correlate fidelity choices to real cost and quality outcomes.

Target users

- Product teams adding semantic search or recommendation features to customer-facing apps.
- Data platform teams that need predictable billing and multi-tenant isolation.
- ML engineers experimenting with quantization, dimensionality reduction, and hybrid indexes.

Packaging proposals (summary table)

| Tier name | Typical use-case | Dimensionality & storage | Index defaults | Throughput SLA | Monthly price anchor |
|---|---:|---|---|---:|---:|
| Starter | Prototype / dev | 128-d, float16 (no compression) | IVF/PQ small shards | Best-effort | $0.03 per 1k vectors stored |
| Balanced | Production search & rerank | 256-d, int8 quantization option | HNSW default | 99.9% query P95 < 200ms | $0.09 per 1k vectors stored + query units |
| High-Fidelity | High recall, embeddings experiments | 1024-d, float32, no quant | IVF+HNSW hybrid | 99.95% P95 < 120ms | $0.35 per 1k vectors stored + higher query unit rate |
| Archive | Long-term, infrequent recall | 64-d projection, lossy compression | Flat files / cold index | Best-effort (async) | $0.005 per 1k vectors stored (cold retrieval fees apply) |

Notes on the table:

- Prices are anchors for packaging discussion and must be validated in billing experiments.
- Query units: a separate metered quantity that charges per thousand vector-scoring operations with tier-based discounts.
- Index defaults are suggestions customers can override but may incur higher cost or relaxed SLAs.

Pricing model mechanics

- Two primary meters: storage-per-1k-vectors-month and query-units-per-1k-ops. Storage accounts for dimensionality and quantization factor (e.g., int8 reduces storage by ~4x relative to float32).
- Add-on meters: warm-capacity (reserved shards), fast-prefix-cache (per-seat), and snapshot retention beyond N days.
- Overages: soft-threshold alerts and auto-repack windows (customers can opt-in to auto-compact quantized vectors during off-peak windows).
- Bundles: Developer Bundle (Starter + 5k free queries), Production Bundle (Balanced + reserved warm capacity), Enterprise Fidelity (High-Fidelity + SLA + migration assistance).

SLOs, SLIs and telemetry

Recommended SLOs (hosted and dedicated):

- Query latency SLO: 99th percentile end-to-end query time (including network) <= tier P99 target (Starter: 800ms, Balanced: 250ms, High-Fidelity: 150ms).
- Availability SLO: > 99.9% per calendar month for Balanced and >99.95% for High-Fidelity.
- Recall guardrail: for High-Fidelity tier, maintain recall@10 >= baseline model's recall@10 +/- 2% over rolling 7 days.

Telemetry requirements (must be surfaced in Console):

- Per-tenant: average vector dimensionality distribution, quantization ratio, index type, and the storage bytes per vector.
- Cost signals: tokens-equivalent estimate for query units (to help product teams reason about cost per search request).
- Quality signals: shadow-eval sampling rate that computes recall and MRR against a small promptset for regression detection.

Onboarding and self-serve flow (numbered steps)

1. Developer signs up and chooses Starter or Balanced trial from Console.
2. Quickstart: upload up to 10k vectors via REST SDK or S3 connector; default index created automatically.
3. Run the "quality preflight" (console button)  returns recall@10 against the customer's golden set or our sandbox set.
4. Console recommends fidelity adjustments (e.g., reduce dimension to 256, enable int8) and shows estimated monthly cost delta.
5. If customer chooses a higher tier (Reserved Warm Capacity), show contract UI and provisioning ETA.
6. After acceptance, the system will (a) reserve capacity, (b) run an index optimize job, and (c) enable SLA monitoring.

Migration and rollout plan

- Phase 1 (Q3 2029): Launch Starter and Balanced tiers to hosted customers with Console guidance only. Track conversion from Starter -> Balanced.
- Phase 2 (Q4 2029): Add High-Fidelity as an opt-in for selected customers and pilot enterprise pricing; introduce dedicated warm-capacity reservations.
- Phase 3 (Q1 2030): Expand to Private (VPC/on-prem) with an assisted migration service and formal runbook for data transfer and index rebuild.

Rollout safeguards and guardrails

- Automatic rollback: If the shadow-eval shows recall degradation > 3% after an index change, auto-revert index configuration and notify the customer.
- Cost caps: Default per-account monthly soft cap that halts new ingestion and sends an escalation email when crossed.
- Gradual shard rolling: rebalance index jobs to limit CPU/GPU impact (max 10% fleet disruption at a time).

Implementation notes for engineering

- Index metadata contract: store per-vector metadata (schema) with keys: tenant_id, vector_id, dimension, quantization, index_version, created_at, last_compacted_at. (Console and billing systems read these fields.)
- Storage calc equation: storage_bytes = N_vectors * dimension * bytes_per_dimension * compression_factor + index_overhead.
- Suggested default bytes_per_dimension: float32=4, float16=2, int8=1.
- Compact/repack scheduling: Background worker that runs compaction windows during tenant low-traffic windows (configurable via API).

Release notes summary (initial launch)

- Feature: Adaptive Embeddings packaging with Starter and Balanced tiers.
- UX: Console Quickstart wizard for 10k vectors and quality preflight.
- API: New endpoints: POST /v1/embeddings/import, POST /v1/embeddings/preflight, GET /v1/embeddings/cost-estimate.
- Telemetry: per-tenant vector telemetry and shadow-eval hook.

Monitoring & ops runbook highlights

- Pager thresholds: P95 query latency spike > 3x baseline for 5 minutes -> page oncall platform engineer.
- Cost anomaly detector: daily job that flags >30% day-over-day increase in query units for a tenant.
- Incident triage: steps to identify index compaction jobs, recent schema changes, and warm-cache eviction events.

Open questions (decision needed)

- Pricing experimentation: Should we prefer storage-heavy anchors or query-unit heavy anchors for initial commercial trials?
- Multi-index tradeoffs: Should Balanced default to HNSW or IVF hybrid for multi-tenant efficiency?
- Cold retrieval model: what SLA and UX guarantees do we give for Archive tier asynchronous requests?
