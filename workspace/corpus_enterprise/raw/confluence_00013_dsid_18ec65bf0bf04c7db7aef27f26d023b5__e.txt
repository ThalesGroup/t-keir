Edge Quantization Fitness: Onboarding Guide and Report Template

Overview

Purpose: This guide defines a repeatable, measurable onboarding path for promoting models that target edge or constrained-device inference. It combines quantization fitness checks, latency/throughput gating, and a telemetry contract so teams can safely deploy quantized artifacts to Redwood Dedicated and Private edge pools. Use this document as both a runbook and a reporting template for model owners.

Scope

- Applies to model binaries and artifacts intended for low-memory, low-power, or latency-sensitive edge deployments (examples: mobile, embedded gateways, small VMs with <8GB GPU RAM).
- Covers deterministic quantization profiles, functional and behavioral validation, perf stability, and promotion gates.
- Not intended for large-batch cloud endpoints or multi-GPU high-throughput deployments (use the standard model promotion checklist for those).

Summary of Core Requirements (Quick reference)

- Functional fidelity: BLEU/ROUGE/embedding-stability deltas must be within defined deltas for the primary prompt set (default: <= 2.0% relative change for classification and <= 3% for generation on slice-weighted average).
- Latency SLO (single-request): median <= 40ms, p95 <= 120ms on target edge device emulator; for extremely constrained targets (<=4GB), median <= 60ms, p95 <= 200ms.
- Memory footprint: resident set < device-memory-threshold (example: 6.5GB for 8GB targets).
- Token-coherence stress: top-k/token-entropy drift < 5% measured across calibration probes.
- Regression budget: no more than 1% of critical prompt set failures increasing severity grade (A->B or B->C) after quantization.

Detailed Onboarding Steps

1) Prepare artifacts

- Deliverables from model owner: float FP16 model and candidate quantized artifacts (INT8, mixed-precision, or custom profile as appropriate). Provide a manifest file named songbird-manifest.yaml that includes model id, hash, tokenizer version, quant profile id, and expected max-seq-length. Example snippet: 

```yaml
model_id: my-model-v2
sha256: 3a7b...
tokenizer: tkn-v1.4
quant_profiles:
  - id: edge-int8-lowmem
    backend: qint8
    notes: symmetric per-channel
max_seq_len: 2048
```

2) Functional and behavioral validation (Eval harness integration)

- Run the eval-harness in shadow mode against two probe families: 
  - Production probe set (representative live prompts, ~5k samples, weighted by traffic slices)
  - Edge stress set (long-tail, adversarial, and tokenization-edge probes, ~2k samples)
- Required metrics: exact-match, semantic-similarity (embedding cosine), response-length distribution, and top-TokenEntropy. Capture per-slice deltas versus FP16 baseline.
- Pass criteria: see "Core Requirements" above. Any slice failing the thresholds must be annotated and triaged before moving forward.

3) Performance and resource validation (emulator + real hardware)

- Execute the performance harness on: 
  - Edge emulator (containerized emulator matching target CPU/GPU/driver) with continuous-batching disabled.
  - Reference device (if available) or smallest supported VM flavor.
- Measure: median latency, p95 latency, memory RSS, peak GPU memory, context warmup delta, and cold-start time.
- Load profile: single-request latency and 10qps ramp test for burst behavior. Document results in the report table below.

4) Telemetry contract and observability

- The artifact must implement the telemetry contract: emit structured traces with the following fields on every request: model_id, quant_profile_id, seq_len, tokens_generated, latency_ms, kv_cache_hit (true/false), and quant_fallback_reason (nullable).
- Telemetry format: JSON-lines to the Redwood ingestion endpoint (or local forwarder). Example event: 

```json
{ "model_id": "my-model-v2", "quant_profile_id": "edge-int8-lowmem", "seq_len": 128, "tokens_generated": 42, "latency_ms": 36, "kv_cache_hit": true, "quant_fallback_reason": null }
```

- Observability checks: must have a perf-counter for quantized model temperature (numeric stability gauge) and an event for quant-fallback.

5) Safety and regression triage

- Run targeted safety checks from the safety-sandbox probe catalog (must be the latest release). Any high-severity safety regression (change in safety sentinel from pass->fail) blocks promotion.
- If behavioral regressions exceed regression budget, follow the triage flow: 
  1. Create a regression ticket with annotated probes and diffs.
  2. Run a targeted bisect with seeds using the quantized replay orchestrator.
  3. If bisect points to quant algorithm, revert to fallback profile and re-evaluate.

Report Template (to submit for promotion)

- Title: [Model-id] Edge Quant Fitness Report
- Executive summary: 2–4 sentences summarizing outcome and recommended profile
- Manifest: (attach songbird-manifest.yaml)
- Key metrics table (example):

| Metric | FP16 baseline | Quantized (edge-int8-lowmem) | Pass? | Notes |
|---|---:|---:|---:|---|
| Median latency (ms) | 34 | 38 | Yes | emulator results, 95% CI ±2ms |
| p95 latency (ms) | 110 | 118 | Yes | under p95 SLO 120ms |
| RSS memory (GB) | 7.8 | 6.2 | Yes | fits 8GB constraint |
| Embedding cosine (slice-weighted) | 0.982 | 0.977 | Yes | delta 0.5% |
| Semantic failure increase | 0.6% | 1.2% | No | cause: prompt family A drift — see triage notes |

- Probe-level appendix: include two CSV attachments: production_probe_deltas.csv and edge_stress_annotated.csv
- Telemetry contract verification: attach sample events and ingestion validation screenshots or link to the trace explorer 

Promotion gates and allowed actions

- Green: all pass -> OK to promote to shadow-edge pool and schedule a rolling canary (10% of edge traffic) for 48 hours.
- Yellow: minor slice regressions or p95 borderline -> require canary + additional probe sampling + annotate risks before canary.
- Red: safety regressions, semantic failure increase >1% absolute, or memory/latency violation -> block promotion.

Rollback and emergency runbook (if promoted artifact causes incidents)

1) Immediately flip traffic routing to fallback model (platform runbook: route policy "edge-fallback-v1").
2) Open an incident with severity mapping: if customer-visible errors >0.5% traffic -> Sev2.
3) Collect repro probe, telemetry, and core dump (if available). Notify model owner and SRE.
4) If fallback fails, escalate to Platform Lead and enable centralized traffic throttling.

Operational checklist before first canary

- [ ] Manifest uploaded and checksum verified
- [ ] Eval-harness reports attached and signed by QA lead
- [ ] Telemetry contract validated against ingestion (sample verified)
- [ ] Safety checks green
- [ ] Performance targets met on emulator and at least one hardware reference
- [ ] Rollback policy and fallback model staged

Appendices

A. Example eval-harness command

```bash
python -m eval_harness.run 
  --manifest songbird-manifest.yaml 
  --probes production_probe_set.json --probes edge_stress_set.json 
  --output report_edge_quant.json 
  --mode shadow --disable-batching
```

B. Recommended quant profiles for common families

| Family | Profile id | Notes |
|---|---|---|
| Small encoder-decoder | edge-int8-lowmem | symmetric, per-channel, int8 weights, fp16 activations |
| Decoder-only medium | edge-mixint8 | mixed-precision 6-bit attention + int8 matmul |

C. Known limitations

- Some prompt families with heavy numerical conditioning may require mixed-precision to avoid coherence drift.
- Emulators approximate but may not capture thermal/cooling variability in true edge hardware. Always validate on at least one physical reference when available.
