Delegated Access Honeypots and Audit Fallback Guideline

Summary
-------
This guide defines a standardized pattern for deploying and operating delegated-access (role/permission delegation) detection honeypots and an audit-fallback workflow to ensure forensic-quality evidence capture in cases where primary audit streams are degraded. It covers architecture, configuration, SLOs, operational runbook steps, evidence packaging, and the rollout & testing plan. The goal is to reduce detection gap windows, preserve admissible evidence, and maintain clear ownership for triage during delegation-based incidents.

Scope
-----
Applies to:
- Service and user-level delegation flows (e.g., "service-to-service" token exchange, impersonation, temporary role activation).
- Systems: authz-service, token-broker, identity-provider (IdP), audit-collector pipeline, and model-serving endpoints that support delegated calls.
- Regions: All production regions.

Out of scope: App-level business-logic delegation (application-specific workflows) unless they rely on the central authz-service.

Key principles
--------------
- Fail open for availability but fail-safe for evidence: delegation decisions should not cause mass outage; however when audit telemetry is degraded we prefer conservative capture that preserves evidence even if it incurs cost.
- Minimal blast radius: honeypots must not expose credentials or escalate privileges; they are read-only or isolated tokens.
- Deterministic evidence: every capture includes a timestamp, canonical request, raw token metadata, and correlated audit stream fragments.
- Legal admissibility: chain-of-custody metadata is attached to artifacts and retention follows compliance catalog.

Architecture overview
---------------------
Textual diagram (components and data flows):
- authz-service (primary policy decision point) --> audit-client (synchronous log forward) --> kafka-ingest --> audit-collector --> long-term storage (s3-evidence-bucket, encrypted)
- token-broker/IdP --> delegated-access-hooks --> honeypot-proxy (isolated) --> honeypot-logger --> audit-collector (parallel)
- fallback controller watches audit-collector health and flips capture-mode to "forensic" when primary path fails.

Component responsibilities:
- authz-service: emit structured decision events (JSON schema v2).
- honeypot-proxy: accept bait delegation attempts and capture token headers and environment information. Must never use captured tokens to access real resources.
- audit-collector: persist events to staged bucket, sign manifests with KMS, and push notifications to security-oncall.
- fallback controller (eng-sre-owned): monitor metrics and trigger forensic capture flag.

SLOs and alerting thresholds
----------------------------
- Authz event delivery: 99.95% of authz events must reach audit-collector within 10s.
- Honeypot availability: 99.9% uptime.
- Fallback activation threshold: if >0.5% of authz events fail forward to audit-collector for 5 consecutive minutes, fallback->forensic mode.
- Alerting: PagerDuty to security-oncall if fallback activates for >2 minutes.

Configuration table (recommended defaults)
----------------------------------------
| Setting | Default value | Rationale | Owner |
|---------|---------------|-----------|-------|
| honeypot-token-ttl | 30s | Minimal lifetime; prevents reuse | eng-platform |
| forensic-capture-ttl | 14 days (staging) / 7 years (archive) | Compliance evidence retention | security |
| fallback-debounce | 5m | Avoid flapping | eng-sre |
| max-honeypot-rate | 5 reqs/min per region | Limits cost and noise | eng-sre |

Operational runbook: detection and triage
-----------------------------------------
1) Detection: Fallback controller alarm fires (metric: authz_forward_errors > 0.5% for 5m).
2) Immediate actions (0–2min):
   - Eng-sre announces incident in #incident-authz and on the status page.
   - Controller sets forensic-capture=true (read-only switch).
   - audit-collector switches to write-through stage bucket s3-evidence-staging (encrypted: kms://evidence-key-prod).
3) Stabilize (2–15min):
   - Security triage team validates that captured events include token metadata, raw headers and correlating request_id. Run this query:
     - Example: curl -H 'Authorization: Bearer $TOKEN' -X GET 'https://audit-collector.internal/_search?q=request_id:abcd1234'
   - If the primary audit stream is restored, disable forensic-capture and notify channels.
4) Escalate to legal (if indicators of compromise): collect manifest and open case in Legal Tracker.

Forensic evidence manifest (schema fields)
-----------------------------------------
- manifest_id
- incident_id
- created_at (ISO8601)
- collector_version
- evidence_paths (list of object keys)
- signed_by (kms-key-id)
- hash_sha256
- chain_of_custody_notes

Sample CLI: generate and sign manifest
------------------------------------
# Collect staged objects into a manifest (example)
aws s3 ls s3://redwood-audit-staging/region=us-west-2/date=2026-03-01/
aws s3 cp s3://redwood-audit-staging/region=us-west-2/date=2026-03-01/ artifacts/ --recursive
python tools/sign_manifest.py --input artifacts/ --kms-key arn:aws:kms:us-west-2:123456:key/evidence-key-prod --out manifest.json

YAML example: honeypot config
---------------------------
honeypot:
  enabled: true
  max_rate_per_region: 5
  token_ttl_seconds: 30
  capture_fields:
    - raw_token_header
    - user_agent
    - source_ip
    - request_id
  safe_mode: true  # ensures no outbound calls are made with captured credentials

Evidence packaging and retention
--------------------------------
- Staging: evidence written to s3-evidence-staging with 90-day lifecycle.
- Signing: all manifests must be signed with KMS key id evidence-key-prod.
- Archival: for confirmed incidents, copy artifacts to s3-evidence-archive with 7-year retention and legal hold support.
- Metadata: attach ticket id, incident tags, and chain_of_custody_notes in S3 object metadata.

Testing and rollout plan
------------------------
- Unit tests: ensure honeypot-proxy returns sanitized responses and logs capture fields.
- Integration tests: simulate IdP delegated token flow and assert audit-collector receives both primary and honeypot events.
- Canary rollout: feature-flag via LaunchDarkly: 5% -> 25% -> 100% across regions. Observe: authz_forward_errors, honeypot_rate, forensic-capture toggles.
- Game day: run a quarterly tabletop where the primary audit path is intentionally broken and teams validate evidence capture and manifest creation.

Appendix A: Example forensic query patterns
------------------------------------------
- Correlate by request_id: SELECT * FROM audit_events WHERE request_id = 'abcd1234' ORDER BY timestamp DESC;
- Find suspicious delegation spikes: SELECT window_start, count(*) FROM audit_events WHERE event_type = 'delegation' GROUP BY window_start ORDER BY count DESC LIMIT 20;

Appendix B: Risk and mitigation table
------------------------------------
| Risk | Impact | Mitigation |
|------|--------|------------|
| Honeypot token leakage | High | Short TTL (30s), read-only proxies, disabled outbound access |
| Evidence tampering during transport | High | KMS-sign manifests, immutable storage, write-once policies |
| Cost of forced forensic capture | Medium | Debounce and rate limits, RBAC guardrails to limit who can enable forensic mode |
