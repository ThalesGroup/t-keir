GPU plugin release gatekeeper and experimentation runbook

Overview

This runbook describes the release gatekeeper and experimentation workflow for GPU runtime plugins and related IaC/CI artifacts. It consolidates the safe rollout patterns we use when introducing new kernel changes, operator plugins, and Terraform module updates that affect GPU allocation, scheduling, or runtime behavior. The goal is to enable frequent, measurable experiments while minimizing blast radius and providing an operator-focused rollback path.

Scope

- Applies to changes that touch: runtime plugins (CUDA/cuDNN wrappers, mixed-precision kernels), scheduler hooks, kube-device-plugin updates, device-plugin CRDs, and Terraform modules that change GPU pool topology or autoscaling policies.
- Not for model weights or purely application-level changes (those follow application release processes).

Motivation

GPU plugin changes can produce subtle performance regressions or availability problems (OOMs, kernel timeouts, NVLink saturation). We need a single, well-documented path for CI gating, canary experiments, and rapid rollback so SRE and infra engineers can act quickly during incidents.

Key concepts and definitions

- Gatekeeper: the CI pipeline stage (and human review step) that prevents unsafe changes from reaching production GPU pools.
- Canary cohort: a reserved subset of tenants and runtime instances used for early verification.
- Fractional routing: traffic split controlled by traffic router to send X% of inference requests to new plugin variant.
- Safe-mode: a runtime fallback that disables the plugin and uses a verified baseline kernel path.

Design overview

1) Preflight validations (automated): unit tests, kernel-level microbenchmarks (latency and memory), IaC plan diffs, and model smoke evals ran against canary images.
2) CI gate: artifact promotion blocked unless benchmarks meet thresholds and all checks pass. Human reviewers can override with documented justification.
3) Canary rollout: staged policy that attaches new plugin to a reserved canary GPU pool, backs up KV caches, and enables fractional routing.
4) Observation window & experiment metrics: performance, error rates, OOMs, and cost delta tracked for a minimum observation window (see thresholds).
5) Decision and rollout: promote to broader pools only when success criteria met. If not, automated rollback to baseline.

Preflight checklist (automated + manual)

- CI must run kernel microbenchmarks (P50, P95 latency for 128/512/2048 token sequences) comparing new plugin vs baseline.
- Terraform plan must be approved; diff must not modify production GPU pool sizes without explicit capacity sign-off.
- Smoke eval: run 3 representative prompts per model family for deterministic regressions.
- Security scan of plugin binary for SLSA provenance and signatures.
- Disk and NVMe throughput tests on sample nodes.

Thresholds (gates)

- Latency regression: P95 increase <= 10% for 512-sequence workloads.
- Error rate: increase <= 0.5 percentage points over traffic baseline.
- OOMs: zero OOMs during a 30-minute stress run on canary nodes.
- Resource delta: GPU utilization increase <= 15% at equivalent throughput.

CI/CD pipeline steps (numbered)

1. Developer opens PR that includes: code, changelog, and an integration test manifest (test cluster config reference).
2. CI runs unit tests and builds plugin artifact (container + signed checksum).
3. CI executes microbenchmarks in an ephemeral GPU sandbox and posts results to PR.
4. IaC job runs terraform plan against a dry-run workspace. Changes to production pools trigger a blocked state requiring "infra-approver" review.
5. If automated gates pass, PR enters "gatekeeper_pending" and sends reviewers. Reviewer must: check logs, confirm canary plan, and approve within 48 hours or request more tests.
6. On approval, CI publishes canary artifact tag (e.g., plugin:v2025-01-18-canary) and kicks off canary rollout pipeline.

Canary rollout procedure

1. Provision canary GPU pool using a stable IaC module and tag nodes with `canary=true`. Keep pool size small (3-6 GPUs).
2. Deploy plugin container to canary pool using the runtime operator with feature flags: enable plugin behind runtime flag `runtime.pluginX.enabled=true`.
3. Seed canary cohort: attach 3 internal tenants + 1 synthetic load generator to canary pool. No production customer traffic unless explicit opt-in and written consent.
4. Set fractional routing to 10% initially for 2 hours, 25% for next 2 hours, then 50% for 4 hours if metrics stable.
5. Observation window: minimum 8 hours total with at least one daily peak.

Metric dashboards and SLOs to monitor

- Throughput (tokens/sec) and per-request latency P50/P95/P99.
- GPU metrics: SM utilization, memory alloc failures, GPU temperature, NVLink error counters.
- Node metrics: CPU steal, network egress, disk IOPS.
- Application error budget: 5-minute rolling error-rate and 1-hour rolling error-rate tracked.
- Alert thresholds (examples):
  - P95 latency increase > 15% over baseline for 10 minutes -> SEV-2.
  - Any new OOM on canary pool -> SEV-1.
  - GPU ECC errors or NVLink CRC errors -> SEV-1.

Automated rollback and safe-mode activation

- If any SEV-1 condition fires: immediately flip feature flag to disable plugin and re-schedule nodes to baseline runtime. CI pipeline will mark the canary tag as failed.
- For SEV-2 conditions: hold rollout, pause fractional routing at current level, run targeted diagnostics scripted below.

Rollback steps (ordered)

1. Disable fractional routing: set traffic-split to 0% for plugin variant.
2. Flip runtime flag to baseline: `kubectl patch deployment runtime-operator -n redwood --type=json -p '[{"op":"replace","path":"/spec/template/spec/containers/0/env/0/value","value":"false"}]'` (example).
3. Drain canary pool and cordon nodes for postmortem.
4. Re-deploy baseline plugin from signed artifact.
5. Run immediate smoke evals and validate metric baseline is restored.

Incident diagnostic checklist (for SRE oncall)

- Collect plugin container logs from all canary pods: `stern plugin -n runtime --selector=canary=true`
- Pull kernel messages on host: `sudo journalctl -k --since "-30m" | grep -i nv`
- Query GPU counters via nvidia-smi and nvprof where available.
- Check recent Terraform apply runs and IaC diffs for accidental topology changes.
- Capture top models causing spikes and isolate via routing.

Experimentation guidance (AB tests and QoE measurements)

- Use multi-arm experiments: compare baseline vs pluginX vs pluginY with traffic-split and hypothesis-driven metrics (latency and quality proxies).
- Randomization: route based on request id hash to avoid correlated traffic.
- Minimum sample sizes: ensure at least 50k requests per arm for high-traffic endpoints; scale down for low-volume endpoints but extend observation window.
- Quality proxies: use eval prompts tied to model outputs and automated regression detectors (token-level divergence, repetition metrics).

Example GitHub Actions snippet (canary publish job)

```yaml
name: Publish Canary
on: [workflow_dispatch]
jobs:
  build-and-publish:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - name: Build plugin container
        run: |
          docker build -t ghcr.io/redwood/pluginX:${{ github.run_id }} -f docker/Dockerfile .
      - name: Sign artifact
        run: |
          cosign sign --key ${{ secrets.COSIGN_KEY }} ghcr.io/redwood/pluginX:${{ github.run_id }}
      - name: Publish canary tag
        run: |
          docker tag ghcr.io/redwood/pluginX:${{ github.run_id }} ghcr.io/redwood/pluginX:canary-${{ github.run_id }}
          docker push ghcr.io/redwood/pluginX:canary-${{ github.run_id }}
```

Terraform module example (version pin and safety flags)

```hcl
module "gpu_pool_canary" {
  source = "git::ssh://git@github.com/redwood-iac/gpu-pool.git//module?ref=v1.14.2"
  name   = "canary"
  size   = 3
  labels = { canary = "true" }
  lifecycle = {
    prevent_destroy = true
  }
}
```

Rollout governance and approvals

- Any plugin that modifies kernel launch parameters or memory pooling must have a TL or SRE approver in the PR.
- Changes that increase GPU pool max size or modify subnet routing require cloud-networking approval and billing sign-off.

Ownership, contacts and escalation

- Primary owner: infra-runtime team (oncall channel #infra-runtime).
- Secondary owner: gpu-fleet team.
- Oncall escalation: PagerDuty rotation `infra-runtime-pager`. If SEV-1, page the primary and the platform-engineering manager.

Postmortem and learnings

- Failed canaries require a postmortem within 5 business days with root cause analysis, impact timeline, and preventive actions. Share postmortem link on the PR and tag `release-failure`.

Appendix: common debugging commands

- `nvidia-smi --query-gpu=utilization.gpu,utilization.memory,memory.used --format=csv -l 5`
- `kubectl describe pod <pod> -n runtime`
- `stern runtime -n runtime-logs --selector=canary=true`
