Congestion Control and Degradation Orchestration Playbook

Summary
-------
This playbook defines a standardized approach for detecting, orchestrating, and remediating congestion and capacity-driven degradations across Redwood's inference runtime. It is intended for SREs, on-call engineers, and platform owners to ensure predictable behavior during high-load scenarios while protecting SLOs and minimizing user impact.

Goals
-----
- Detect emergent congestion early and attribute root cause (hardware, network, scheduling, noisy tenant).
- Apply deterministic degradation strategies (traffic shaping, graceful tail-latency throttles, model-quality fallbacks) tied to error-budget policy.
- Preserve latency and availability targets for high-priority tenants while enabling fair-share for multi-tenant pools.
- Provide reproducible post-incident analysis artifacts for incident reviews and capacity remediation.

1) Detection & telemetry thresholds
-------------------------------
Primary signals (evaluated at 1m and 5m windows):
- p99 latency for token-generation API > 750ms for 5m (critical)
- p95 latency increase &gt; 2x baseline for 10m (warning)
- GPU utilization &gt; 90% sustained on &gt; 30% of pool hosts (warning)
- Queue depth (request backlog) &gt; 50 requests per shard for 3m (critical)
- Error rate (500/502/504) &gt; 0.5% absolute increase over baseline for 5m

Telemetry-derived context to collect automatically:
- Affected model and variant, sequence length percentiles, average KV cache hit-rate
- Tenant(s) with high qps, per-tenant token/memory usage, and recent rollout events
- Recent autoscale events and model-compilation cache misses

2) Immediate mitigations and routing choreography (automated first)
---------------------------------------------------------------
Automated actions (run by the traffic controller) in order: 
1. Apply token-level soft rate-limit for noisy tenant(s) at 95th percentile of recent traffic.
2. Engage fast-path routing to lower-latency model variant (if within quality budget).
3. Enable prefix/KV cache bypass mode to reduce cache pressure for long-context requests.
4. Trigger autoscale policy: spin up pre-warmed nodes if pool free capacity &lt; 20%.
5. If GPU saturation persists, activate multi-tenant fair-share: cap per-tenant concurrency to configured share.

Human-visible escalation steps (if automation insufficient):
1. Pager escalates to on-call SRE with subject line: [CONGESTION] service:<service> p99 outlier.
2. On-call executes "triage-checklist" to confirm signals (see Runbook Commands).
3. If mitigation impacts critical tenants, follow the Priority Tenant Safeguard procedure in Section 4.

3) Degradation strategies and ordering
-----------------------------------
Degradation is a controlled, reversible sequence. Follow this strict ordering to reduce blast radius: 
A. Soft shaping and throttles (non-disruptive)
B. Traffic steering to compatible model variants (quality vs cost trade-off)
C. Per-tenant concurrency caps and queued-accept/reject policies
D. Token budget enforcement for bursty tenants (token-rate smoothing)
E. Graceful model fallback (lower-parameter or quantized variant)
F. Bulk eviction to degraded pool or read-only mode (last resort)

Decision matrix (abbreviated):
| Trigger | Action | Contention risk | Notes |
|---|---:|---:|---|
| p95 &gt; 2x baseline + GPU util &gt; 90% | A (soft shaping) | low | Always attempt first |
| Queue depth &gt; 50 per shard | B then C | medium | Prefer steering first to keep latency |
| Error rate &gt; 1% | E (fallback) | medium-high | Validate fallback quality metrics |

4) Escalation and human-in-the-loop procedures
---------------------------------------------
When automation cannot restore SLOs within 10 minutes, follow this escalation ladder: 
1. On-call SRE (Tier 1) — execute immediate mitigations and notify owners.
2. Platform lead (Tier 2) — authorize capacity increase or cross-pool routing.
3. Runtime team (Tier 3) — investigate kernel/compilation regressions and rollback if needed.
4. Incident Commander — declare Sev if customer impact crosses thresholds (see incident criteria table).

Incident criteria table:
| Severity | Criteria | Error-budget impact | Immediate owner |
| Sev-1 | p99 latency > 1.5s for 15m OR availability &lt; 99.5% for 15m | Major | Platform oncall |
| Sev-2 | sustained p99 &gt; 1s for 30m OR error rate spike > 2% | Significant | Service owner |
| Sev-3 | intermittent latency increases or transient queue spikes | Minor | Local oncall |

Priority Tenant Safeguard
- If a named priority tenant is affected, execute controlled divergence: allocate reserved burst pool, notify customer success and account team, and avoid disruptive fallbacks without explicit approval.

5) Post-incident actions and capacity retrofit checklist
-----------------------------------------------------
Required artifacts for every declared incident:
- Triage timeline (annotated with automated actions and manual steps)
- Compact reproducible load profile (JMeter/loader script) and request traces for 95/99 percentile traces
- Capacity fallout matrix: number of hosts, pods, GPUs impacted and composition
- Error-budget accounting entry and remediation plan

Retrofit checklist (assign owners and ETA):
1. Review autoscale thresholds and increase pre-warm window by 30s if warmup failures observed.
2. Tune batcher concurrency and batching window for affected model family.
3. Add synthetic canary that exercises tail-latency at production p99 throughput.
4. Create per-tenant slow-path alerts and a noisy-tenant mitigation rule.
5. Run a capacity rehearsal (games-day) with the new thresholds within 2 sprints.

6) Runbook CLI snippets and play examples
---------------------------------------
Triage checklist (commands):
1) Check pool utilization and queue depth:
   $ rictl pool metrics get --pool=vision-infer --window=5m --fields=gpu_util,queue_depth,p99_latency
2) Identify top tenants by qps and token usage:
   $ rictl tenants top --pool=vision-infer --metric=qps --window=5m --limit=10
3) Engage soft shaping for tenant (example):
   $ rictl tenant throttle set --tenant-id=tenant-123 --qps=120 --mode=soft --duration=15m
4) Move traffic to fallback model variant:
   $ rictl route update --service=inference-vision --from=model-v2 --to=model-v2-quant --pct=30 --step=10

Play example: fast surge at 09:12 UTC
1. Alert fires: p99 1.2s, queue depth 60/shard. Automation applied soft shaping and started autoscale.
2. On-call runs triage-checklist; top tenant consumes 45% of pool. Set tenant throttle to 120 qps.
3. After 4m p99 improved to 720ms; after 12m autoscale added nodes and restored baseline.
4. Post-incident: add a per-tenant alert rule and schedule capacity rehearsal.

Quality & Validation Criteria for Fallbacks
-----------------------------------------
- Fallback model must pass a reduced prompt-set regression check with max BLEU/ROUGE drop of X (team to define X per model family).
- A/B samples must be recorded for quality comparison for 1 hour post-fallback.
