SLO Consumption Patterns and Tenant Provisioning Playbook

Overview

Purpose:
This playbook defines how Redwood SREs detect, classify, and act on SLO error-budget consumption patterns across multi-tenant inference services. It codifies preemptive tenant provisioning and throttling decisions to preserve service-level quality while minimizing customer impact and cost.

Scope:
- Applies to core inference endpoints (text-generation, chat, embeddings) and the routing/proxy layer (service names: rwd-proxy, rwd-batcher, rwd-router).
- Intended for on-call SREs, capacity planners, and platform owners.
- Does NOT replace product-level billing or contractual entitlements; see Finance and Customer Success for overrides.

Key definitions:
- SLO: objective for request success/latency/availability for a given route and tenant. Example: /v1/generate P50 latency < 80ms, availability 99.9%.
- Error budget: allowed SLO loss over a rolling window (typically 28 days).
- Consumption pattern: time-series shape of error-budget depletion (steady, bursty, creeping, episodic).
- Preemptive provisioning: adding capacity, warming model variants, or routing traffic to protect SLOs before hitting critical thresholds.

High-level detection and classification

Telemetry signals (priority order):
1) Error budget burn-rate (per-tenant, per-route) computed in telemetry pipeline (metric: slo:error_budget_burn_rate{tenant,route}).
2) Latency percentile shifts (p50,p95,p99) with sudden slope > threshold (metric: http_request_duration_seconds_bucket).
3) Queue/backlog growth on batcher nodes (metric: rwd_batcher_queue_size).
4) Pod/container CPU & GPU saturation (node exporter + nvidia-smi derived metrics).
5) Request/retry amplification (rate of 5xx responses and retries).

Pattern taxonomy and associated risks

1) Bursty consumption
- Characteristics: short, high-amplitude spikes in tokens or RPS (minutes).
- Risks: transient tail-latency breaches, autoscaler lag, throttling blast.
- Typical cause: customer load test, new feature rollout, upstream client bug.

2) Sustained surge
- Characteristics: elevated consumption over hours/days with consistent burn.
- Risks: prolonged SLO degradation leading to sustained availability loss and downstream throttles.
- Typical cause: marketing campaign, change in model configuration (higher temperature or longer max_tokens).

3) Creeping degradation (slow burn)
- Characteristics: gradual increase in latency and error budget depletion over weeks.
- Risks: unnoticed SLO erosion, hard to correlate to single event.
- Typical cause: model drift, unobserved config changes, billing/usage policy changes.

4) Episodic/recurring pattern
- Characteristics: predictable regular spikes (daily/weekly).
- Risks: repeated breach windows if unmitigated.
- Typical cause: scheduled batch jobs, geo/timezone-driven customer behavior.

Detection thresholds (example values)
- Burn-rate alert (warning): slo:error_budget_burn_rate > 0.2 for 30m
- Burn-rate alert (critical): slo:error_budget_burn_rate > 0.8 for 15m
- Latency slope: p95 increase > 2x baseline in 10m
- Queue growth: rwd_batcher_queue_size growth rate > 50% in 5m

Preemptive actions matrix

This matrix maps pattern -> automated/preemptive operator actions. Use the matrix to choose the lowest-impact effective action.

ASCII table (Provisioning Matrix):

Pattern | Immediate automated action | Short-term operator action (15-60m) | Medium-term action (1-24h)
---|---|---|---
Bursty | Temporary per-tenant throttling (shape to 80% of baseline) + burst-absorber routing | Warm additional batcher workers in same region; increase dispatch parallelism | Review client pattern; propose rate-limit quota change or guidance
Sustained surge | Route new requests to pre-warmed variant with quantized weights (model: gptx-quant-fast) | Trigger reserved-capacity allocation from capacity pool; enable burst credits | Open capacity ticket with GPU-fleet and negotiate commit/short-term reserve
Creeping | Emit escalation signal to capacity team and owner; flag tenant for manual review | Progressive scaling based on predicted 72h demand; adjust batching window | Evaluate model quantization or batching policy; engage Product on usage change and pricing signal
Episodic | Schedule autoscaler warm windows aligned to expected spikes | Coordinate with tenant (CS) for scheduled increases; apply per-window quota | Consider SLO tiering and time-windowed SLAs for that tenant

Concrete runbook: step-by-step for on-call

If you see slo:error_budget_burn_rate{tenant="$TENANT"} > 0.8 for 15m or matching high-severity alerts:
1) Triage in PagerDuty: acknowledge and assign (owner role: on-call SRE).
2) Query telemetry: Grafana dashboard "SLO Consumption - Tenant View" and run these queries:
   - slo:error_budget_remaining{tenant="$TENANT"}
   - http_request_duration_seconds{route="/v1/generate",tenant="$TENANT"}
   - rwd_batcher_queue_size{node=~"batcher.*"}
3) Classify pattern (use taxonomy above).
4) Perform lowest-impact automated mitigation first (runbook CLI):
   - rwdctl tenant throttle --tenant $TENANT --route /v1/generate --rate 0.8x --duration 20m
   - rwdctl routing divert --from-zone us-west-2 --to-zone us-east-1 --selectors tenant=$TENANT --duration 30m
5) If automated mitigation insufficient after 10 minutes, escalate to Capacity Pager (channel #sre-capacity) and open Capacity Incident in JIRA with tags [slo-burn, tenant:$TENANT].
6) Coordinate with Customer Success for tenant notification if any customer-visible throttling or degradation is planned.
7) Post-resolution: run Incident Review (see section below) and update tenant provisioning scorecard.

Prometheus alert rule examples (paste into alerts repo):

- alert: TenantErrorBudgetCritical
  expr: slo_error_budget_burn_rate{tenant!~"internal.*"} > 0.8
  for: 15m
  labels:
    severity: critical
    team: eng-sre
  annotations:
    summary: "High error budget burn for tenant {{ $labels.tenant }}"

- alert: BatcherQueueGrowth
  expr: increase(rwd_batcher_queue_size[5m]) / avg_over_time(rwd_batcher_queue_size[30m]) > 0.5
  for: 5m
  labels:
    severity: warning
    team: eng-sre
  annotations:
    summary: "Rapid batcher queue growth detected"

Ownership and decision authorities
- On-call SRE: initial triage, automated mitigations, 60-minute owner for action.
- Capacity Team: medium-term provisioning, reserved capacity commits.
- Platform Owner (rwd-router/rwd-batcher): approves routing/divert changes.
- Customer Success: customer communication and SLA exceptions.

Provisioning scorecard (use to decide when to convert preemptive actions into committed capacity)
- Key inputs: 28d burn rate trend, 7d sustained surplus RPS, predicted 72h demand, customer tier (Free/Standard/Premier), revenue impact estimate.
- Score thresholds:
  - < 30 points: use transient mitigations only
  - 30-70 points: consider short-term reserved capacity (1-7 days)
  - > 70 points: open reserved capacity/contract discussion with Sales

Runbook for planned pre-warm/provisioning (change process)
1) Owner opens a Capacity Plan PR in infra repo with: expected delta, duration, nodes required, cost estimate, rollback plan.
2) Run deployment in canary region for 30m and validate metrics (latency, burn-rate).
3) Notify #sre-capacity and #platform-runway 10m before scale-up.
4) After scale: monitor for 1h, then mark plan as effective. If instability: rollback immediately following rollback plan.

Post-incident review and KB updates
- Every time a preemptive action (throttle/provisioning) is executed, on-call must create a short Incident Log entry with: tenant, pattern classification, mitigation used, duration, and outcome.
- If mitigation used more than 3 times in 30 days for a tenant, schedule a stakeholder review with Product and CS.
- Update the tenant provisioning scorecard and archive runbook decisions in "SLO Consumption Decisions" Confluence child page.

Operational tooling and automation suggestions
- Implement a burn-rate predictor (baseline: simple exponential smoothing) that produces a 72h forecast and a provisioning recommendation.
- Provide a one-click mitigation button in Grafana dashboards that runs validated rwdctl commands (confirmation modal required).
- Maintain a staging pool of pre-warmed model variants (gptx-small-quant, gptx-medium-quant) to reduce cold-start impact.
