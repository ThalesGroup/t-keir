Attribute-access rollout and evidence retention roadmap

Overview

This document provides a practical, phased roadmap for adopting Attribute-Based Access Control (ABAC) across Redwood Inference resources and services. It ties RBAC compatibility, audit logging requirements, evidence retention timelines, secure-SDLC gating, and incident-response triggers into a single operational playbook. Intended audience: security engineers, IAM owners, product platform teams, SRE, and compliance reviewers.

Goals
- Reduce over-provisioning by expressing access as attributes and policies instead of large role collections.
- Ensure auditability and compliance: every attribute evaluation must be traceable and retained per the evidence matrix below.
- Provide deterministic migration steps from existing RBAC constructs to ABAC, with explicit exception handling.
- Integrate ABAC checks into SDLC and incident response so policy drift and attribute abuse are detectable and recoverable.

Scope
- In-scope: all internal control plane services, model-serving endpoints, customer tenancy metadata, and privileged admin functions.
- Out-of-scope: ephemeral internal dev-only feature flags (will be addressed in a follow-up).

Definitions
- Attribute: a key-value pair about a subject (user/service), resource, action, or environment (e.g., department:engineering, resource.sensitivity:high, request.origin:private_vpc).
- ABAC policy: world-readable policy that combines attributes into allow/deny logic.
- Evidence artifact: packaged set of logs, policy snapshots, and attribute-change records required for audits or investigations.

Ownership and roles
- IAM Security Team (owner): policy design, central attribute catalog, evidence retention policy enforcement.
- Platform Engineering: runtime enforcement hooks, policy evaluation libraries, SDKs.
- Service Owners: map service-specific attributes to the central catalog and own migration of local roles.
- Compliance: validates evidence packaging and retention during audits.

High-level migration phases
1) Discovery (0-2 months)
   - Inventory: export current role assignments, service accounts, role-to-permission mappings.
   - Attribute catalog kickoff: seed attributes (department, tier, environment, resource.sensitivity, customer_org_id).
   - Deliverable: discovery report and attribute catalog v0.

2) Pilot (2-5 months)
   - Select 2 services (one infra service, one product-facing) for ABAC pilot.
   - Implement policy-evaluation middleware and audit hooks.
   - Run RBAC side-by-side: enforce ABAC in allow-mode while RBAC remains authoritative.
   - Deliverable: pilot runbook, sample policy set, lessons learned.

3) Gradual rollout (6-12 months)
   - Phased cutover by business unit.
   - Enforce ABAC for read-only ops first, then move to write/privileged ops after 2 weeks of stable metrics.
   - Automate attribute syncs from HR and customer directories.

4) Harden & Optimize (ongoing)
   - Enforce periodic policy review, anomaly detection, and evidence packaging for audits.

Mapping to RBAC (compatibility pattern)
- Pattern: Role -> Policy shim
  1. For each RBAC role, define an ABAC policy that reproduces permissions using subject attributes (e.g., department, job_level) and resource tags.
  2. Create a compatibility layer that evaluates both RBAC and ABAC for a transition window.
  3. Decommission roles when no bindings remain and policy test coverage shows parity.

Example ABAC policy (JSON policy snippet)
{
  "id": "policy.allow.data-read.engineering",
  "target": { "resource.sensitivity": "low", "action": "read" },
  "condition": "subject.department == \"engineering\" && subject.job_level >= 2",
  "effect": "allow"
}

Audit logging and evidence retention matrix
- All ABAC evaluations must produce an evaluation event with the following minimal fields: timestamp, request_id, subject.id, subject.attributes(snapshot_id), resource.id, resource.attributes(snapshot_id), policy_id, decision(allow|deny), decision_reason, evaluator_version.

Retention matrix (summary)
- Evaluation events: 3 years (primary evidence)
- Policy snapshots: 7 years (archival, per compliance)
- Attribute source sync logs (HR/SCIM/KMS): 1 year (sensitive PII redaction applied)
- Attribute-change records (who changed attribute, why, approval id): 7 years
- Role to policy deprecation logs: 5 years

Evidence packaging format (required fields)
- Evidence artifact must be a zipped manifest containing:
  - manifest.json (list of files, policy_ids, snapshot timestamps)
  - evaluation_events.ndjson (queryable event stream)
  - policies/ (policy snapshots in JSON)
  - attribute_snapshots/ (CSV of attribute key-values with snapshot_id)
  - acl_mappings/ (legacy RBAC role exports for the time window)
  - signer.txt (PKI-signed hash of the manifest)

Sample manifest.json (mini example)
{
  "artifact_id": "evidence-2029-01-10-0001",
  "time_range": "2028-12-01/2029-01-10",
  "included_files": ["evaluation_events.ndjson", "policies/policy.allow.*.json"]
}

Retention and storage considerations
- Primary evidence store: write-once, encrypted S3 bucket (KMS CMK: evidence-primary).
- Archival: cold store with immutability flags (7y).
- Access to evidence artifacts: RBAC+ABAC gated; access requests require documented business justification and TTR < 48 hours for compliance requests.

Secure SDLC gates
- Policy changes must follow this pipeline: dev -> peer review -> staging (test harness with replayed evaluation events) -> canary -> production.
- PR templates must include a policy-testing checklist and required unit tests for decision coverage.
- All policy PR merges trigger a policy-snapshot commit (immutable) and generate a signed manifest entry.

Incident response integration
- Attribute change anomaly detection: trigger when >5% of attributes for a domain change within 1 hour or any attribute change to resource.sensitivity:high.
- Incident playbook steps when triggered:
  1. Auto-create incident and tag with "abac-attribute-anomaly".
  2. Freeze attribute propagation pipelines (HR sync, SCIM connectors, internal APIs).
  3. Collect evidence artifact covering the 72 hours prior to anomaly and lock it for forensic analysis.
  4. Rotate any affected service credentials if policy evaluations affected privileged flows.
  5. Post-incident: run attribution analysis, policy/role rollback if required, and create a remediation timeline.

Risk exceptions and approvals
- Short-lived exceptions (<=14 days): product manager + service owner approval in ticketing system; must include compensating controls and evidence snapshot.
- Medium exceptions (15-90 days): security approver + business SLA review; artifact retention must be extended to cover exception period.
- Long exceptions (>90 days): require CISO review and recorded board-level approval.

Operational runbook (quick checklist)
- Daily:
  - Monitor ABAC evaluation error rate (<0.05% target).
  - Verify attribute sync success (last sync age < 5 minutes).
- Weekly:
  - Run policy coverage test suite for active services.
  - Review top-10 denied-but-requested cases for potential false positives.
- Quarterly:
  - Evidence retention audit (verify manifests and cold-store integrity).
  - Policy review with service owners.

Queries and dashboards to build
- Live: ABAC evaluation rate, deny-rate by service, average decision latency, evaluator version distribution.
- Forensics: event-explorer filtering by policy_id, subject.id, attribute snapshot_id, and time range.

Appendix A: SDK enforcement snippets
- Example Golang evaluator call (pseudo):
  resp, err := evaluator.Evaluate(ctx, &EvaluateRequest{
    Subject: subjectSnapshot,

    Action: "write",

Appendix B: Policy test harness checklist
- Unit tests for deny/allow boundary cases
- Fuzz tests for unexpected attribute values
- Replay of historical evaluation events to validate decision parity with RBAC baseline
