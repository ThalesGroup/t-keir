On-call exercise curriculum and status template bundle

Summary

This document defines a repeatable on-call exercise curriculum (game-days + tabletop), the responder rota templates, runbook validation checklist, and a small bundle of customer- and status-page templates intended for fast, consistent external communication. It is designed for teams operating Redwood’s model-serving infrastructure and is explicitly scoped to operational readiness (not hiring or policy).

Scope and intended audience

- Scope: full lifecycle of on-call readiness exercises and the artifacts produced (rotas, runbooks, evidence, customer notices).
- Audience: SREs, service owners, support leads, and engineering team leads who run or participate in exercises.

Goals

1. Ensure responders can stabilize common failure modes within SLO objectives.
2. Validate runbook correctness and handover clarity.
3. Practice customer-facing status communication and cadence.
4. Create reproducible artifacts (evidence packages) for compliance and postmortem analysis.

Exercise curriculum overview

- Types of exercises
  - Simulation (live traffic replay to staging): validates autoscaling, throttling, and cache behavior.
  - Tabletop (lead facilitation, no live infra): policy and decision-path validation.
  - Injected-failure game day (chaos experiments in a sandboxed cluster): tests fallback routing and KV cache recovery.
  - Customer-comm drill (status page + incident notification cadence): exercises external messaging.

- Cadence recommendations
  - Quarterly: one injected-failure game day per critical service.
  - Monthly: tabletop for cross-team coordination and runbook review.
  - After each major release: focused simulation for features touching routing, caching, or quantization.

Exercise planning checklist (pre-game)

1. Define objective (e.g., validate canary fallback within 90s).
2. Identify scope (services, environments, traffic subset).
3. Assign roles: facilitator, incident commander (IC), bridge operator, service steward, reporter.
4. Produce an evidence plan (logs, traces, KV cache snapshots, request samples).
5. Publish safety guardrails (blast radius, kill-switch, rollback plan).
6. Notify stakeholders and schedule a 30-minute pre-brief.

Role definitions and rota templates

- Key roles
  - Incident Commander (IC): overall decision authority for the exercise or live incident.
  - Bridge Operator: runs the incident conference bridge / status page posts.
  - Service Steward: subject-matter owner for the failing service or model.
  - Recovery Engineer: implements fixes, rollbacks or mitigations.
  - Customer Liaison: crafts and approves public notifications for customers.

Incident lifecycle & runbook validation pattern

1. Detection: alert fires -> initial triage within first 2 minutes.
2. Triage: IC assigns severity and service steward within 5 minutes.
3. Containment: short-term mitigations (rate-limit, fallback region) within SLO window.
4. Remediation: code/infra changes or rollback.
5. Recovery: verify metrics and synthetic tests pass.
6. Handover: formal postmortem evidence package created and the incident is closed.

Runbook validation checklist (for each runbook)

- Header metadata present: owner, last updated date, slack channel, escalation contacts.
- SLOs and customer impact thresholds defined.
- Clear decision ladder: when to escalate, when to rollback.
- Repro steps for common faults (eg. cache thrash, GPU OOM, model quality regression).
- Minimal commands and examples: kubectl, curl, analysis queries.
- Post-exercise smoke test and verification steps.

Example runbook excerpt: KV cache eviction spike

### Incident signal
- Sudden drop in token throughput with increased 5xx errors and large KV_cache_miss ratio (>40%).

### Immediate actions (IC / Service Steward)
1. Set primary route to fallback-model-1 and reduce batch sizes.
2. Run: kubectl -n serving get pods -l app=cache | grep Evicted
3. Check Redis/remote-KV latency: curl -s http://kv-proxy:9090/metrics | grep kv_latency_ms
4. If whether the KV store is saturated, toggle read-only mode: curl -X POST http://kv-admin/ro-mode
5. Notify bridge and begin customer comm script (see templates below).

Postmortem evidence package (minimum)

- Timeline (UTC) with automated metric spikes and human actions.
- Relevant traces (trace IDs list).
- Logs: filtered by request IDs and pod names.
- Snapshots: KV cache size and configuration, model versions deployed.
- Configuration diffs if a recent deploy exists.

Customer-facing status templates (copy-and-paste ready)

1) Status page initial notice (short)
- Title: Degraded response times for hosted API
- Body: We are investigating increased latency affecting text generation for a subset of requests. Users may see slower responses or occasional 5xx errors. Our team has identified a service-dependency impacting KV cache performance and is actively working on containment. We will provide an update within 30 minutes.
- Severity: partial_degradation

2) Status page update (investigation)
- Title: Active mitigation in progress
- Body: We have applied a traffic routing change to fall back to model-variant B for affected requests and reduced batching to lower pressure. Error rates are down ~60%; latency is improving but not yet back to baseline. Estimated next update: 60 minutes.

3) Customer notification (email) — brief
Subject: Service update: latency affecting model responses
Body:
Hi —
We experienced elevated latency impacting a subset of text generation requests between 14:12–14:45 UTC. We applied a routing mitigation and validated recovery at 14:53 UTC. No data was lost.
If you rely on strict latency, consider pinning to a dedicated capacity plan or enabling our reduced-batch routing config (see KB: /internal/ops/reduced-batch-config).
Thanks,
Redwood Inference Support

  - Next update: +30m or on state change

Post-exercise & post-incident learning loop

1. Capture a 1–2 page incident summary with root cause hypothesis and what worked/who was impeded.
2. Upload evidence package to the incident folder and tag the postmortem ticket.
3. Runbook edits: assign owner to implement fixes within 7 business days or raise a backlog ticket.
4. Training update: schedule a targeted 60-minute lab for any recurring tooling gaps.
5. Metrics review: check for false-positive alerts and adjust thresholds.

Table: SLO examples and action thresholds

| SLO name | Target | Alert threshold | Action |
| API p95 latency | < 200ms | p95 > 350ms for 5m | Trigger incident, notify IC |
| Model-serving error rate | < 0.5% | 5xx > 2% for 3m | Route to fallback-model, engage steward |
| Embedding throughput | >= 500 qps | sustained drop > 50% | Check autoscaling and GPU health |

Game day safety principles

- Always run destructive experiments in a sandbox or staging cluster unless pre-authorized.
- Provide a live kill-switch and a tested rollback plan before injecting faults.
- Limit blast radius to a single customer tenant where possible during partial tests.
- Keep customer liaison in the loop for any public-impacting simulations.

Evidence retention and postmortem governance

- Evidence packages must be retained for 12 months for auditability.
- High-severity incidents (SEV2/SEV1): postmortem published within 7 business days; follow-up action owner assigned.
- Quarterly executive digest to summarize recurring failure modes and remediation progress.
