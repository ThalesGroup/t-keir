sandbox-to-production-capture-and-credits-playbook

Summary

This playbook describes a cross-functional product and commercialization initiative to make the developer sandbox experience a first-class funnel into paid consumption. It covers the product overview, prioritized PRD requirements, high-level design decisions, a pragmatic roadmap broken into four phases, pricing/packaging guidance for crediting and smoothing, and release notes and launch checklist items. The objective is to reduce friction from experimentation to production while protecting unit economics.

Problem statement

- Many teams try features in the Redwood developer sandbox, but a sizeable fraction drop off before hitting committed usage because of unclear conversion paths, misaligned credits, or surprising post-trial billing.
- Current credit allocation is opaque to customers and does not reflect real production consumption shapes (streams, sessions, embeddings).

Goals

1. Create a clear, measurable path from sandbox usage to paid tiers with minimal manual sales intervention.
2. Introduce a credit-smoothing system that maps sandbox activity to production entitlements in ways that preserve demonstrable value and predictable billing.
3. Instrument conversion telemetry to support experiments and run A/B tests for credit policies.
4. Maintain gross margin targets for hosted API while improving conversion rate by at least 15% in target cohorts.

Non-goals

- This playbook does not propose changes to enterprise Reserved Capacity contracts or deeply affect Dedicated capacity procurement.
- It is not a substitute for negotiated large-customer onboarding; it targets self-serve and small-to-mid-market funnels.

Target users and journeys

- Developer trying the sandbox: low-volume streaming, short chat sessions, embedding lookups.
- Product/PM evaluating fit: will test repeated session flows with conversation history and function-calls.
- Engineering evaluating latency/cost: will stress longer sequences and multimodal payloads.

User journeys (happy path)

1. Signup and sandbox credit grant: developer receives 10,000 token-equivalent credits for 30 days.
2. Guided experiment: developer uses Quickstart templates (chat, embeddings) and receives in-console insights that estimate equivalent production spend.
3. Conversion prompt: after reaching a configurable usage threshold or time window, in-console CTA offers discounted first-month credits and shows an estimate of committed entitlements.
4. Smooth transition: once developer upgrades, sandbox sessions map to a 30-day trial entitlement that credits up to 80% of matched sandbox consumption for the first billing period.

Prioritized requirements (PRD-style)

- MUST: Track token-equivalent consumption per sandbox session and persist anonymized consumption patterns for conversion attribution.
- MUST: Provide an in-console estimator that translates sandbox actions to projected monthly cost under common plans (Hosted pay-as-you-go, Starter bundles, and Dedicated anchors).
- MUST: Define a credit-smoothing algorithm that maps sandbox tokens -> production credits using configurable multipliers per route (e.g., streaming, chat-with-kv, embeddings).
- SHOULD: Allow devs to opt into an "accelerated credit" experiment that increases conversion credits in exchange for identity and usage telemetry sharing.
- SHOULD: Expose a developer-visible conversion ledger showing how sandbox activity was mapped to production credits.
- MAY: Beta an automated discount for customers who consistently exceed a monthly threshold during the sandbox window.
- MUST: Telemetry hooks for cohort experiments and A/B testing tied to conversion funnel.

Design and UX considerations

- In-console transparency: all credit conversions must be explainable in a single view with dropdown details for multipliers and rationale.
- Progressive disclosure: show high-level conversion estimates early, detailed ledger available after conversion event.
- Defaults tuned for unit economics: streaming and long-context uses receive lower multipliers by default to avoid gaming.
- Privacy & telemetry opt-in: accelerated credit experiments must collect telemetry with a clear developer consent modal and minimal PII.
- Fail-open behavior: if conversion mapping fails, default to conservative (lower) credit and log telemetry for troubleshooting.

Technical design overview

- Components:
  - Sandbox meter (client + server SDK hooks) — collects per-request token-equivalent and route metadata.
  - Conversion engine (service) — consumes anonymized events, applies smoothing multipliers and cohort rules, writes to conversion ledger.
  - Conversion ledger (immutable append-only store) — stores sandbox->credit mappings with reason codes and timestamps.
  - In-console UI and estimator — reads ledger and projects production equivalence.
  - Experimentation & telemetry pipeline — routes metrics to the experimentation platform and A/B service.

- API surface (example):
  - POST /sandbox/events {session_id, route, tokens, kv_size, embeddings_count, timestamp}  => 202 Accepted
  - GET /sandbox/ledger?user_id=... => returns ledger entries (paginated)
  - POST /sandbox/convert?cohort=... => triggers conversion job (admins)

Operational and reliability requirements

- SLOs: conversion engine: 99.9% success for queued conversions within 30s, conversion API 99% for read operations within 200ms.
- Monitoring: error rates, conversion delta (expected vs granted), cohort uplift metrics, and revenue leakage indicators.
- Rollback: conversion rules are versioned; emergency rollback is a single configuration toggle with an immediate stop of new conversion jobs while leaving ledger read-only.

Roadmap and phases (high level)

1) Phase 0 — Discovery and pilots (Q1–Q2 2026)
   - Run qualitative interviews with 25 sandbox users; instrument representative workloads.
   - Pilot two smoothing policies (conservative, aggressive) with 3 customer cohorts.

2) Phase 1 — Core launch (Q3 2026)
   - Implement sandbox meter + conversion engine + ledger.
   - Launch in-console estimator and conversion ledger UI.
   - Pricing pilot: offer 50% matched credits for first-month conversion for beta cohorts.

3) Phase 2 — Optimization and experiments (Q4 2026–Q1 2027)
   - Run A/B experiments on multipliers and conversion CTAs.
   - Integrate with billing and attribution pipelines for seamless entitlements.

4) Phase 3 — Commercialization (Q2 2027)
   - Full rollout of credit-smoothing across self-serve and direct-sell funnels.
   - Launch developer-focused marketing materials and onboarding guides.

Pricing and packaging guidance

- Principles:
  - Credits should demonstrate value but not replace first-month ARPU expectations.
  - Use progressive multipliers to match value-to-cost ratio per route.
  - Keep commercial exceptions for negotiated customers (sales override).

- Suggested commercial treatments:
  - Self-serve Starter: sandbox-to-prod match = 60% for first 30 days, then standard Starter bundle pricing.
  - Pay-as-you-go: estimate calculator shown, sandbox credits consumed first before billed usage.
  - Trial Accelerator (opt-in telemetry): up to 80% match in exchange for participation in anonymized telemetry program; limited to 3 months.
  - Anti-fraud: automated heuristics detect synthetic traffic and drop match multiplier to 0 for flagged sessions.

Measurement and success metrics

- Conversion rate (sandbox -> paid) for target cohorts (baseline -> +15% target).
- Average revenue per converted developer in first 90 days.
- Cost delta per converted customer vs control group.
- Experiment lift and confidence intervals for multiplier experiments.
- Fraud rate and false-positive rate on heuristics.

Launch checklist and runbook highlights

1. Product readiness
   - UI elements live for estimator, ledger, and CTA.
   - Default multipliers and cohort definitions configured.
2. Engineering readiness
   - Conversion engine deployed to prod and tested in shadow mode.
   - Billing integration smoke tests and idempotency guaranteed.
3. Legal & Compliance
   - Telemetry opt-in language approved by legal.
   - Data retention policy set for ledger entries (90 days for full detail; aggregated retention 24 months).
4. GTM readiness
   - Messaging and onboarding emails drafted.
   - Customer-facing docs and Quickstarts updated.

Planned release notes (for initial launch)

- Feature: Sandbox Credit Smoothing — converts sandbox activity into production credits with explainable multipliers.
- Feature: In-console Estimator — projects production cost equivalents for common workflows.
- Beta: Trial Accelerator — telemetry opt-in program that increases conversion credits.
- Breaking changes: None. Billing integration requires a one-time entitlements sync; customers converting during rollout may see a reconciliation event in billing within 48 hours.

Open questions and risks

- How aggressively should multipliers be tuned before we have 1,000 converted customers of telemetry-backed evidence?
- Risk: customers may attempt to game the sandbox to capture credits; anti-fraud measures must be robust.
- Reconciliation complexity: mapping permanent entitlements to temporary conversion credits requires careful billing engineering.
