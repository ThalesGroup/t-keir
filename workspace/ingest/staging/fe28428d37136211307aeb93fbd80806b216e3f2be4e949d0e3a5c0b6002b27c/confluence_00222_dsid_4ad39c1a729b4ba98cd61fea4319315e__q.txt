Quota Protector Webhook Integration and Reconciliation Guide

Overview
--------
This integration guide describes the Quota Protector webhook used by Redwood Inference to reliably surface customer quota events and automate protective credits and throttling adjustments during anomalous billing or rate-limit events. The document explains the webhook contract, delivery guarantees, recommended reconciliation workflow for enterprise customers, on-call runbooks for mismatches, and examples for implementing a receiver and reconciliation worker in third-party billing systems.

Goals
- Reduce false-positive quota rejections for enterprise customers during bursty or partial-failure conditions.
- Provide deterministic reconciliation steps to reconcile token usage vs. billing records within a 72-hour window.
- Support automated protective credits (temporary credits) and safe rollback actions with auditability.

When to use this integration
- Enterprise customers with reserved or committed capacity (Dedicated or Private) that need automated protective measures when perceived usage spikes or system anomalies occur.
- Partners who want proactive notifications and a standard reconciliation API for invoicing systems.

Prerequisites
- Customer must have a configured webhook receiver endpoint reachable from Redwood (HTTPS/TLS).
- Shared secret (HMAC-SHA256) provisioning via the console or SRE onboarding link.
- Access to your billing system’s ingestion pipeline (batch or streaming) for reconciliation.

Webhook contract (delivery semantics)
1) Event types (payload field event_type):
   - quota.alert: short-lived alert when usage approaches a quota threshold (INFO).
   - quota.protective_action: Redwood applied a temporary protective credit or soft-throttle (ACTION).
   - quota.reconcile_request: Redwood requests reconciliation for an identified discrepancy (RECONCILE).
   - quota.reconcile_result: Customer posts back reconciliation outcome (RESULT).
2) Delivery guarantees:
   - Redwood will attempt delivery with exponential backoff for up to 24 hours.
   - Events are delivered at-least-once; receivers must be idempotent (see Idempotency section).
   - Quota.reconcile_request is guaranteed to be emitted once per discrepancy case.
3) Security:
   - Each HTTP request includes X-Redwood-Timestamp and X-Redwood-Signature (HMAC-SHA256 of body + timestamp with shared secret).
   - Request body is application/json and UTF-8 encoded.

Idempotency and receiver best practices
- Use event_id as the primary idempotency key. Store event_id and processing result for 90 days.
- Design reconciliation handlers to accept repeated reconcile_request events and only create a single case per unique correlation_id.
- Return standard HTTP codes: 200 for success, 202 for accepted (async processing), 4xx for client errors, 5xx for transient failures. Redwood will retry on 5xx and network errors.

Sample receiver flow (recommended)
1) Verify signature and timestamp within +/- 5 minutes. Reject otherwise with 401.
2) Check local dedupe store by event_id; if found, return 200 with existing outcome.
3) For quota.protective_action: apply temporary internal protective credit and create an internal ticket with priority=high if action==temporary_credit.
4) For quota.reconcile_request: enqueue a reconciliation job that performs matching between reported_usage_tokens and your billing records for the provided window. Post a quota.reconcile_result when complete.

Reconciliation worker design
- Match level: ingestion-level (per request ID) if available; fallback to route-level aggregation by minute.
- Tolerance band: accept discrepancies <= 2.5% as noise; >2.5% and <=10% trigger automated protective credit up to suggested_action. >10% escalates to human review.
- Audit trail: include the Redwood event_id, your reconciliation_job_id, and links to raw records.

Automated protective credits and accounting flow
1) On reconcile_request that falls into the automated band, your system should:
   - Create a refundable credit entry tied to the tenant and reconciliation_job_id.
   - Post quota.reconcile_result with fields (event_id, job_id, outcome: auto_credit_applied, credit_amount_tokens, note).
2) Finance integration: reconcile refundable credit entries weekly against Redwood billing exports.
3) Auto-expiry: credits applied as protective must be stamped with expiry (default 30 days) and a reconciliation flag to convert to permanent credit only after human approval.

SLOs and monitoring
- Delivery SLOs: Redwood aims for 99.5% successful initial delivery (non-5xx) across webhook endpoints.
- Customer receiver SLOs: process reconcile_request within 8 hours or reply with 202+job_id to indicate longer processing windows.
- Alerting: customers should alert if more than 5 reconcile_request events are queued for >24 hours for a single tenant.

On-call runbook: unresolved reconciliation mismatch
1) Redwood emits quota.reconcile_request with suggested_action. Customer system posts back quota.reconcile_result. If no result after 24 hours, do:
   a) Check delivery logs (Redwood Console -> Integrations -> Webhooks -> Delivery).
   b) Confirm webhook receiver health (CPU, request queue depth, TLS cert validity).
   c) If receiver healthy but processing stuck, escalate to internal billing ops: create ticket with tags [recon-stuck, tenant:<tenant_id>] and assign to billing-ops on-call.
2) If the reconcile_result indicates disagreement (customer refutes observed usage), run a manual audit:
   a) Export raw request logs from Redwood for the window (Console -> Tenants -> Export Usage).
   b) Crosswalk timestamps and request IDs. If discrepancies persist, open a joint investigation with Redwood SRE via the enterprise support channel.
3) If finance disputes remain after 7 days, follow the contractual dispute process (see related_pages billing-credit-policy).

Troubleshooting common errors
- 401 Unauthorized: bad HMAC signature or clock skew. Verify shared secret and sync NTP.
- 422 Unprocessable Entity: missing required fields (event_id, event_type, tenant_id, timestamp). Confirm JSON schema.
- Repeated duplicates: confirm dedupe store retention and idempotency key correctness.
- Large backlog: increase worker parallelism and consider accepting 202 with job_id for long-running reconciliation.

Implementation examples and helper scripts
- Minimal Node.js receiver skeleton (pseudocode)
```js
const express = require('express');
app.post('/webhooks/rdw', verifySignatureMiddleware, async (req, res) => {
  const event = req.body;
  if (await alreadyProcessed(event.event_id)) return res.status(200).send({status:'duplicate'});
  enqueueReconcile(event).then(jobId => res.status(202).send({job_id: jobId}));
});
```

Operational recommendations for enterprise customers
- Keep a rolling 7-day window of raw request logs for quick manual audits.
- Configure alert thresholds on per-tenant queue depth and reconcile_request age.
- Regularly rotate webhook secrets and use mutual TLS for sensitive integrations.

Privacy and audit considerations
- Webhook payloads may contain tenant identifiers and usage aggregates. Do not log PII.
- All reconciliation actions must be recorded with who/what/when for billing audit trails.

Appendix: field reference
- event_id: UUID v4, unique per event.
- correlation_id: opaque string that groups related protective actions / reconcile flows.
- reported_usage_tokens: integer, tokens Redwood observed.
- observed_usage_tokens: integer, any computed alternate observation.
- suggested_action: free-text suggestion (credit_x_tokens | manual_review).
