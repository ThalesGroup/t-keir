SLO Deprecation and Legacy Service Retirement Runbook

Purpose
-------
This runbook defines the standard process and gating criteria for deprecating an SLO and retiring a legacy service. It is intended for SREs, service owners, product managers, and platform engineers. The goal is to retire services safely while preserving customer-facing SLOs, minimizing capacity disruption, and ensuring clean incident evidence for postmortems.

Scope
-----
Applies to: internal and customer-facing services listed in the Redwood service catalog.
Does NOT apply to: short-lived feature flags, AB-test backends under 30 days of lifetime (use feature-flag playbooks).

Definitions
-----------
- SLO: Service Level Objective (e.g., 99.9% success rate for generate-text).
- SBI: Service Burn Indicator — combined metrics that indicate whether a service is on-track for retirement (error budget, active callers, routing weight).
- Legacy service: a service that is being retired because of replacement, consolidation, or end-of-life.

Owners and Stakeholders
-----------------------
- Primary owner: service team product lead (PL) and service oncall.
- SRE lead: responsible for runbook enforcement and capacity verification.
- Platform/Networking: routing and traffic-shift operations.
- Security/Compliance: data-retention checks for customer-sensitive data.

Prerequisites & Signals to Start Retirement
------------------------------------------
1) Product decision recorded (JIRA: RWI-####) with sign-off from PL and PM.
2) Replacement service available or confirmed migration path.
3) Metrics baseline available for 30 days: traffic, p95 latency, error budget burn rate.
4) No Sev1/2 incident in the last 7 days for the service.

Common triggers:
- Sustained <10% traffic over 60 days.
- Low active callers and deprecation announcement window passed.
- Cost/maintenance rationale accepted by product and SRE.

Gating Criteria (quick reference)
--------------------------------
| Gate | Requirement | Owner | Pass/Fail |
|------|-------------|-------|----------|
| Product sign-off | JIRA documented + roadmap removal | PL | pass |
| Migration path | Validated end-to-end tests + dry run | Eng | pass |
| SLO impact | No SLO regression > 0.1% absolute or compensatory plan | SRE | pass |
| Capacity | Capacity headroom >= projected variance + 20% | SRE | pass |
| Compliance | Data retention & audit obligations reviewed | Security | pass |

Step-by-step Runbook
--------------------
1) Pre-deprecation analysis (2-4 weeks before announce)
   - Run "service-usage" query for 90/60/30 day windows and document active callers.
     CLI example: rwi-admin metrics query --service inference-router --window 90d --metrics callers,p95,error_rate > analysis.csv
   - Calculate projected residual load if migration fails (worst-case 10% rollback).
   - SLO analysis: compute baseline and simulate removal. Use the SLO-sim tool: rwi-slo simulate --service inference-router --remove=true --horizon 30d

2) Announce deprecation (T-14 days)
   - Publish deprecation notice to product-consumers Slack channel and to the internal deprecation registry (Confluence page + tag).
   - Open a JIRA runbook ticket with checklist sub-tasks and assign owners.
   - Set the service routing flag: deprecation_notice=true (objectives: monitoring and routing behavior).

3) Canary removal and capacity verification (T-7 to T-3 days)
   - Create a 1% traffic canary to the replacement service for 48 hours. Monitor: error budget burn, p95 latency, and user-visible errors.
   - Verify autoscaling profiles on replacement to handle burst +10% traffic.
   - SRE action: if burn rate > 3x baseline or p95 regresses > 20% -> abort and investigate.

4) Phased traffic shift (T-2 to T)
   - Shift routing weights: 10% -> 25% -> 50% -> 75% -> 100%, observing 2x collection window for each step.
   - Use the platform tooling command: rwi-router shift --from inference-router --to inference-v2 --steps 10,25,50,75,100 --monitoring-profile slo-critical
   - At each step validate SLO telemetry, error budget and capacity headroom. Document result in JIRA.

5) Final retirement (T+0)
   - Remove service from production routing (set weight 0).
   - Trigger infrastructure teardown plan (if applicable) after 72 hours of zero traffic.
   - Create a retirement snapshot: config export, metrics export, and logs for 90 days.

6) Post-retirement verification (T+3 to T+30)
   - Monitor for hidden callers: run daily dead-letter and 404 routing analysis.
   - Run SLO reconciliation job to ensure no downstream SLO degradation.
   - Close JIRA runbook when all artifacts and audits completed.

Rollback and Emergency Procedures
--------------------------------
- Immediate rollback condition: >5% absolute SLO regression or evidence of customer impact (SEV1).
- Rollback command: rwi-router rollback --service inference-v2 --to inference-router --until stable --reason "SLO regression"
- Post-rollback steps: create an incident, assign SRE incident commander, and follow the incident review template (see related pages).

Integration with Incident Review and SLO governance
--------------------------------------------------
- Any retirement-triggered incident must reference the runbook JIRA id and include gates that were passed.
- Incident review must include: timeline of traffic shifts, SLO telemetry graphs (p50/p95/p99, error rates), routing config, and change events.
- If an incident caused >25% of the remaining error budget to be spent in a burn window, the retirement is paused for a minimal 30-day cooldown and re-evaluated.

Operational Tooling and Automation
----------------------------------
- Automated checks: the runbook registers to-run validations with the runbook-orchestrator service (rwi-runbookd).
- Dashboard templates: create a retirement-dashboard from template 'retirement-basic' which includes: callers, traffic weight, error budget burn, p95 latency, and infra capacity headroom.
- Examples:
  - rwi-runbookd create --template retirement-basic --service inference-router --owner priya@redwood.ai
  - YAML for traffic-shift policy (example):
    policy_name: phased-shift
    steps: [10,25,50,75,100]
    validation_metrics: [error_rate,p95_latency,error_budget_burn]

Checklists and Templates
------------------------
1) Pre-deprecation checklist (must be completed before public notice):
   - [ ] JIRA decision logged and approved.
   - [ ] Replacement service end-to-end tests passing.
   - [ ] 30-day metrics baseline exported.
   - [ ] Audit & data-retention review completed.
2) Retirement execution checklist:
   - [ ] Canary run executed and monitored.
   - [ ] Phased traffic shift completed with no SLO regression.
   - [ ] Config snapshot taken and stored in artifact store.
3) Post-retirement checklist:
   - [ ] No callers detected for 30 days.
   - [ ] Teardown ticket executed.
   - [ ] Postmortem or closeout doc created and linked.

Monitoring and Metrics to Watch
------------------------------
- Active callers (primary leading indicator)
- Error budget burn rate (1h, 6h, 24h windows)
- p95 and p99 latency
- Request arrival distribution and sudden spike detection
- Routing 404/unknown-host spikes after weight shift

Post-retirement Incident Review Considerations
--------------------------------------------
- Include service retirement gates and timestamps in the evidence packet.
- For each incident post-retirement, verify whether callers are from deprecated clients; attach client versions.
- If retirement caused a production incident that consumed a downstream product SLO, escalate to the product SLO committee.

FAQ and Edge Cases
------------------
Q: What if we find a hidden caller 60 days after teardown?
A: Open a high-priority migration support ticket, temporarily re-enable a lightweight proxy for that caller if feasible, and run the standard canary + shift sequence targeted at that caller.

Q: Who signs off on final teardown?
A: Product lead + SRE lead + Security reviewer must sign-off in the JIRA runbook.
