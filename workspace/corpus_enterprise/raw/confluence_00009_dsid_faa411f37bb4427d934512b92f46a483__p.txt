Playground patterns and support sherpa

Overview:

This page collects pragmatic developer-experience patterns (the "playground") and a compact support 'Sherpa' that engineers can use to onboard, iterate, and troubleshoot SDK integrations with Redwood’s inference API. The goal is to reduce time-to-first-success for integrators, and provide a single reference for reproducible canonical fixes for the most common edge cases.

When to use this doc:
- Teams building or embedding Redwood SDKs to iterate quickly in a local or CI sandbox.
- Customer success and support engineers troubleshooting reproducible failures.
- Docs site authors writing quickstarts and snippet bundles.

Quick start patterns (recipes):
1) Minimal local playground (good for debugging auth and streaming):
   - Create a sandbox project directory and add the sample .env (API_KEY, REDWOOD_ENV).
   - Run the local proxy (see sample below) to capture requests & replay.
   - Use the minimal client snippet to assert connectivity and token usage.

2) Batch vs streaming toggle test (validate latency-cost behavior):
   - Use the sample harness to send 50 short requests and 10 long requests with both streaming and blocking endpoints.
   - Verify throughput and token breakdown in the Console.

Canonical fixes (top issues):
- 401 / ApiKey errors:
  1) Verify API key location (ENV vs config file). Use `redwood-cli auth:validate` to confirm key scope.
  2) Check clock skew on VM (token expiry errors show in logs).
  3) If using private deployment, confirm network route to control plane and KMS auth.

- Streaming interruptions (partial responses):
  1) If client closes early, check timeout/retry policy: increase socket-level read timeout by 30s.
  2) Inspect proxy logs for chunked transfer-encoding and ensure no intermediate reverse proxy is buffering.
  3) Use `SDK.debug.streamTrace=true` to surface per-chunk latencies.

- Embedding mismatch and vector drift:
  1) Confirm model version used to generate embedding via the Console (embedding_model field).
  2) Recompute a small validation set and compare cosine similarity distribution; threshold < 0.8 indicates drift.
  3) If drift detected, pin model version in requests and schedule a rolling reindex.

Support Sherpa: a short triage checklist (5 mins to decide next action):
1) Is the request authenticed? (check X-Request-ID and API key header)
2) Does the Console show the request hitting our gateway? If not, ask for a HAR or proxy capture.
3) If the request hit the gateway, pull the gateway logs (query by trace_id) and inspect the runtime selection and fallback logs.
4) Reproduce locally using the captured request with `tools/replayer --redwood-endpoint=<endpoint>` and attach the transcript.
5) If reproduction fails, escalate to Runtime-Oncall with: reproducible steps, minimal capture, recent model_id and batch size.

Appendix: useful commands and diagnostics (copyable)
- Validate environment and key:
  `redwood-cli auth:validate --key $REDWOOD_API_KEY`
- Fetch last 500 gateway logs for a trace: 
  `redwood-cli logs tail --trace-id <trace> --limit 500`
- Replayer invocation example: 
  `node tools/replay.js --capture captures/session.json --endpoint https://api.redwood.example.com`
