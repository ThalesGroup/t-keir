Incident Ecosystem Catalog and Rotation Succession Plan

Summary:

This document defines the Incident Ecosystem Catalog (the canonical inventory of services, dependencies, and runbook ownership), the runbook lifecycle (creation, validation, maintenance, retirement), and a rotation succession plan tied to training/game-day cadence. It also contains templated status-page and customer communication artifacts and a repeatable post-incident follow-through process.

Scope:

- Applies to all production-facing services under Redwood Inference (hosted API, dedicated fleet, private control plane).
- Primary consumers: SRE, Serving Runtime, Platform, Customer Success.
- Excluded: non-production experimental feature branches and personal projects.

1) Incident Ecosystem Catalog (IEC)

Purpose: keep a small, queryable index of services, critical thresholds, primary/secondary owners, and an accession link to the authoritative runbook. Update cadence: weekly sync from service owners; audited quarterly by SRE.

Minimum IEC entry fields (single-line CSV allowed):
- service_name, tier (critical/high/medium), primary_owner, secondary_owner, sla_target, p99_latency_threshold_ms, error_rate_threshold_pct, runbook_path, alert_channel, data_sensitivity

Example entries (CSV):
"runtime-router,critical,serving-runtime@redwood.com,platform-oncall@redwood.com,99.95,800,0.5,sources/confluence/eng-serving-runtime/runbooks/runtime-router-ops.json,#svc-runtime-router,internal"
"kv-cache,high,serving-runtime@redwood.com,eng-sre@redwood.com,99.9,120,1.0,sources/confluence/eng-serving-runtime/runbooks/kv-cache-eviction.json,#svc-kv-cache,internal"

Where to find the catalog: Confluence index + canonical YAML at git://infra/configs/incident-catalog.yaml (read-only for non-SRE teams).

2) Runbook lifecycle and governance

Principles:
- Runbooks are living, tested playbooks for common faults. They must be concise (<= 6 steps for first-responder play), include mitigation commands, known-safe rollbacks, and postmortem hooks.
- Every runbook must have an owner and a quarterly reviewer.

Stages and required artifacts:
1. Draft: create markdown in the runbooks repo under /runbooks/{service}/prod.md. Add IEC reference.
2. Review: assign two reviewers (1 owner-team, 1 SRE). Use the PR template checklist: alerts, mitigation, rollback, comms template, test plan.
3. Validation: perform a tabletop or runbook test during a game day within 30 days of merging. Attach test notes to the PR.
4. Published: add confluence link and tag version (vYYYYMMDD).
5. Maintenance: owner signs off quarterly; automated stale runbook reminder after 90 days without edits.
6. Retirement: deprecate with 90-day notice window; redirect IEC entry to replacement or archive.

Runbook content template (top-of-file):
- title: short service identifier
- impact_summary: one-sentence impact profile
- when_to_run: bullet list of alert signatures
- immediate_actions: numbered steps for first 10 minutes
- mitigation_commands: shell/cli commands (tested)
- rollback_instructions: how to undo risky steps
- owner: person/email/team
- last_tested: YYYY-MM-DD
- metrics_to_capture: list of Grafana dashboards/alerts

Sample mitigation_commands snippet:
```
# fetch last 30m errors for runtime-router
rbx logs query --service runtime-router --since 30m --severity error --limit 200
# temporarily disable model-fanout path
kubectl -n serving patch svc model-fanout --type=json -p='[{"op":"replace","path":"/spec/type","value":"ClusterIP"}]'
```

3) Alerting thresholds and immediate SLO triggers

Standard thresholds (service owners may set stricter values in IEC):
- Availability SLO breach: 5m of sustained failing health checks across >= 3 regions. Escalation: auto-page SRE and owner.
- Latency SLO degradation: p95 > 500ms for more than 5 minutes or p99 > 800ms for more than 1 minute -> consult oncall, consider fallbacks.
- Error rate: 0.5% error rate sustained for 10 minutes -> page.
- KV cache eviction storm: eviction_rate > 1000/s for > 2 minutes -> page.

Example alert rule (YAML):
```
alert: RuntimeHighP99
expr: histogram_quantile(0.99, sum(rate(request_duration_seconds_bucket{job="runtime-router"}[2m])) by (le)) > 0.8
for: 1m
labels:
  severity: page
annotations:
  summary: "runtime-router p99 > 800ms"
```

4) On-call roles & Succession ladder

Roles (primary responsibilities):
- Incident Commander (IC): owns prioritization, customer comms, and decision to rollback.
- Bridge Operator (BO): manages the incident bridge, records timeline, runs shared commands, and updates status page.
- Service Owner (SO): subject-matter expert for the affected service; leads mitigation steps.
- Customer Liaison (CL): coordinates CS/Sales/Legal comms, templates, and escalations.
- Artifact Scribe: collects artifacts and ensures evidence is attached for postmortem.

Succession & escalation ladder (automated paging):
1. Primary oncall page (IC) -> 5 minutes -> secondary oncall (IC2) -> 10 minutes -> oncall lead -> 15 minutes escalate to Eng Director.
2. If BO does not join within 3 minutes, the first responder must declare a bridge and assume BO duties.

Succession plan for rotations:
- Each rotation is 2 weeks for SRE ICs, with an overlap (shadow) week.
- Every third rotation the secondary is required to shadow the primary for at least one incident.
- Rotation handoff checklist (short): latest flagged runbooks, active alerts, outstanding action items, customer-impacting incidents in last 7 days. Store as /handovers/{oncall}-handover-YYYYMMDD.md.

5) Training and game-day schedule

Cadence:
- Quarterly global game day (all responder roles): full 6-hour scenario simulating a multi-region model-serving degradation including KV-cache thrash and failover to dedicated.
- Monthly focused drills (2 hours) for a single failure class: latency spike, memory pressure, or model quality regression.
- New-oncall ramp: 1-week shadow + 1 simulated incident inside first 30 days.

Game-day deliverables:
- A play-by-play timeline (shared in the bridge)
- Evidence capture (logs, heap dumps, tracer snapshots) and upload location (s3://incidents/game-days/{date}/)
- Post-exercise retro with action owners and deadlines (must be closed within 30 days).

6) Status page and customer communications

Status page taxonomy (internal canonical):
- Operational, Degraded Performance, Partial Outage, Major Outage, Under Maintenance.

Customer comms templates (short form) - use Customer Liaison to fill contextual fields.

Immediate acknowledgement (within 30m):
Subject: Redwood Inference — Service Disruption Acknowledged
Body:
We’ve detected elevated errors impacting the Redwood Hosted API. Our SRE team is investigating. Affected customers may experience increased latency or errors. We will post updates every 30 minutes or when there is material progress.

Status update (every 30–60m):
Subject: Redwood Inference — Update on Ongoing Disruption
Body:
Summary of impact (services/regions affected), actions taken to date, next steps and ETA if available, mitigation in place (e.g., routing to fallback region), any customer workarounds.

Resolution notice (post-resolution):
Subject: Redwood Inference — Incident Resolved
Body:
Root cause summary (high level), impact window, customer mitigation steps if action required, link to postmortem, and SLA/credit guidance if applicable.

Template examples (copyable):
```
Subject: [Incident #{INCIDENT_ID}] Redwood Inference — Partial Outage (runtime-router)
Body:
Hello,

We are currently investigating elevated 5xx errors from runtime-router affecting requests routed to us-east-1. Our mitigation steps include throttling large-batch requests and routing traffic to a healthy model-fanout pool. We will send updates every 30 minutes.

Regards,
Redwood SRE
```

7) Postmortem and action tracking

Minimum postmortem content:
- incident_id, time_window, impact_summary, timeline (minute granularity for first 60 minutes), root_cause_analysis, contributing_factors, corrective_actions (owner + due date), detection_time, mean_time_to_recovery (MTTR), customer_impact_summary, SLA impact.

Postmortem process:
1. Draft within 72 hours by Artifact Scribe.
2. RCA workshop within 7 calendar days with SO and IC.
3. Publish postmortem (Confluence) within 14 days.
4. Track corrective actions in a shared board (JIRA project: INF-INC). Actions must be tagged with severity and closed within agreed timelines (critical: 14 days, high: 30 days, medium: 90 days).

8) Runbook retirement checklist (appendix)

When to retire: service removed, replaced, or runbook obsolete for >180 days.
Checklist (mark each):
- [ ] Confirm IEC entry marked deprecated
- [ ] Notify stakeholders and open retirement PR (90-day notice)
- [ ] Migrate any linked alerts to replacement runbook
- [ ] Archive runbook to /runbooks/archive with explanation and final test logs
- [ ] Update redirect in Confluence to replacement or archive note

9) Evidence and compliance notes

- For any incident involving customer data, attach audit logs + KMS access records to postmortem. Security must be CC’d for restricted incidents.
- For enterprise customers impacted, attach the customer notification log and timestamps for regulatory review if requested.

10) Appendix — Quick commands and dashboards

- Logs: rbx logs query --service {svc} --since 60m --severity error --json > /tmp/{svc}-errors.json
