Postmortem Automation and Action Tracker Playbook

Overview:

This playbook defines a repeatable, partially automated postmortem and action-tracking workflow for LLM-serving incidents. It is intended for SREs, service owners, responders, and incident reviewers. The goal is to reduce manual overhead during incident writeups, ensure forensic evidence is captured consistently, and close post-incident actions within defined SLAs.

Goals:
- Reduce postmortem turnaround time (trigger -> draft) to under 48 hours for Sev2+ incidents.
- Ensure automated capture of the evidence pack with >95% fidelity for tokenized requests, KV cache state, autoscaler events, and model rollbacks.
- Track and close actions with measurable SLAs (see Action SLAs).
- Provide standard templates for internal review and customer-facing summaries.

Scope and applicability:
- Applies to all incidents that meet the severity threshold: Sev2 (partial customer impact) and Sev1 (major outage).
- Does not replace runbook-specific operational remediation steps; it complements incident runloop documentation and the existing runbook library.

Key concepts and definitions:
- Evidence Pack: A timeboxed collection of logs, traces, config snapshots, model version manifests, and autoscaler metrics gathered automatically at incident detection + user-specified time window.
- PM Draft: A skeleton postmortem automatically generated with timeline, evidence pointers, and initial action items.
- Action Tracker: A canonical table (tracked in JIRA/Confluence) with closure SLAs and owner assignments.

Automated evidence collection (recommended implementation):
1) Trigger points
   - On active incident creation in PagerDuty (PD), an automation webhook triggers the Evidence Pack collector.
   - Manual trigger from the bridge operator is supported (slash command: /collect-evidence).
2) Collector outputs (zip)
   - service-logs.jsonl (NGINX/ingress, api-gateway)
   - inference-requests-sample.ndjson (sampled requests with redaction)
   - kv-cache-snapshot.json (state for hot clients within timeframe)
   - model-manifest.txt (model versions and quantization profile in use)
   - autoscaler-events.csv (scale-up/scale-down events)
   - trace-span-ids.txt (top 100 slow traces)
   - metrics-export.prom (time-windowed Prometheus slice)
3) Storage and access
   - Collected evidence is pushed to S3://redwood-incident-evidence/<incident-id>/<timestamp>/ with a lifecycle tag 'incident:hold' for 90 days.
   - A signed read-only URL is attached to the PM Draft and to the incident ticket.

Collector example (CLI):
- To run manually from ops laptop:
  ./tools/collect-evidence 
    --incident-id PD12345 
    --start "2026-07-03T02:00:00Z" 
    --end "2026-07-03T03:30:00Z" 
    --samples 200 
    --redact-keys authorization,credit_card

Automated postmortem draft generation (workflow):
1) Incident declared (PagerDuty severity >= 2) -> webhook triggers PM generator.
2) PM generator creates a Confluence page under /oncall-and-incident-response/incidents/<incident-id> with the following seeded sections: 
   - Summary (1-2 sentences auto-composed from incident title and tags)
   - Timeline (auto-extracted events from traces and autoscaler events)
   - Evidence Pack link(s)
   - Initial action suggestions (automatically inferred using keywords: rollback, configuration, capacity, model-quality)
   - Suggested owners (based on oncall roster and recent commit metadata)
3) Bridge operator fills gaps and marks PM as "draft ready".

Timeline extraction heuristics (implementation notes):
- Use trace sampling + ingress timestamps. Prefer the earliest request timestamp with error response rate >5% as the start marker for partial degradations.
- Autoscaler spikes that correlate with latency > p95 are annotated as contributing events.

Action Tracker schema (single canonical table stored in Confluence and mirrored to JIRA project RID-ACT):
| action_id | summary | owner | severity | due_date | status | evidence_link | closure_notes | created_by | created_at |
|----------:|---------|-------|---------:|---------:|-------:|---------------|---------------|-----------|-----------|
| ACT-0001  | Rotate model to v2 | @mxavier | 2 | 2026-07-10 | open | s3://... | | ada.team | 2026-07-03 |

Notes on fields (must be applied to every action row):
- action_id: Prefer JIRA issue key when mirrored; if not present, canonical ACT-000n id is assigned.
- severity: 1 (urgent), 2 (important), 3 (nice-to-have).
- due_date: ISO format. Actions without a due_date default to 30 days for severity 3, 14 days for severity 2, and 7 days for severity 1.
- evidence_link: link back to Evidence Pack or a specific file within it.

Action SLAs and escalation:
- Severity 1: owner must acknowledge within 4 hours, provide a mitigation plan within 24 hours, and close or transition within 7 days.
- Severity 2: owner acknowledges within 48 hours, mitigation plan within 7 days, close within 14 days.
- Unresolved actions beyond SLA are auto-escalated to the incident steward and copied to the owner’s manager on day+1 overdue.

Runbook: Automated PM generation — step-by-step (operator-facing):
1) Confirm incident classification and PD ticket.
2) Run or verify Evidence Pack collection (CLI or /collect-evidence). Verify S3 link is present.
3) Execute PM generation job (internal script):
   - /scripts/generate_pm --incident PD12345 --evidence s3://... --template standard
4) Review auto-populated sections, correct factual errors, add human-readable context, and list any immediate action items.
5) Assign actions in the Action Tracker and create linked JIRA issues for severity 1 items (use project RID-ACT).
6) Mark the postmortem state: draft -> in_review -> published. Assign 2 reviewers (one SRE, one Service Owner).

Reviewer expectations and checklist:
- Verify timeline accuracy: confirm timestamps and event causality.
- Validate evidence pack completeness: logs, traces, model metadata.
- Assess action quality: clear owner, measurable acceptance criteria, and due date.
- Confirm customer-facing summary is concise and avoids technical noise.

Customer communication templates (brief & editable):
- Short status update (to use on status.redwood.ai or customer e-mail):
  Subject: Incident PD12345 — Degraded API latency (Resolved)
  Body: 
  Hello —
  We experienced increased latency for text generation requests between 02:15 and 03:25 UTC on 2026-07-03 affecting ~12% of requests. Root cause: an autoscaler configuration regression that delayed warmup for burst traffic.
  What we did: Rolled back the most recent autoscaler config and restarted the gateway group.
  Next steps: We have created an action to add pre-warm scaling in our autoscaler policy (ACT-0001); estimated remediation complete by 2026-07-10.
  If you experienced client errors, please reach out to support@redwood.ai with your request IDs.

Internal status page copy (concise):
- Title: PD12345 — Inference latency spike (Resolved)
- Short: Latency spike caused by autoscaler regression; rollback applied.
- Impact window: 2026-07-03T02:15:00Z -> 2026-07-03T03:25:00Z

Game day and continuous improvement loop:
- Quarterly game day should include at least one scenario where the Evidence Pack collector is the primary verification tool (failure to collect is a failure mode).
- Post-game-day artifacts: ensure PM generator templates are updated and action tracker is pruned.

Operational ownership and tooling map (examples):
- PagerDuty: service-oncall@redwood (PD schedule: SRE rotation)
- Bridge: #incident-bridge channel in Slack; use react :triage: to indicate bridge operator presence.
- Evidence collector: tools/collect-evidence (owned by eng-infra)
- PM generator: jobs/generate_pm (owned by eng-sre)
- Action mirror: JIRA project RID-ACT (owned by eng-platform)

Retention and compliance notes:
- Evidence packs are retained 90 days by default, flagged for longer retention on customer-sensitive incidents (escalate to security/legal for 2-year retention).
- Redaction is required for PII and secrets. The collector supports a redact-keys list; default redact list: authorization, cookie, credit_card, ssn.

Metrics and KPIs (dashboard suggestions):
- PM generation latency (incident -> draft) median and 95th percentile.
- Percentage of incidents with Evidence Pack present at draft creation.
- Action closure rate by severity at 7/14/30 day marks.

Appendix A — Implementation tips and sample queries:
- Prometheus slice example: 
  curl -s 'https://prometheus.redwood/api/v1/query_range?query=histogram_quantile(0.95, sum(rate(http_request_duration_seconds_bucket{service="inference-api"}[5m])) by (le))&start=...&end=...&step=30s' 
- Trace extraction (example): query traces with error count > 5 in timeframe and export top 100 trace ids: 
  ./tools/trace-cli export --service inference-api --start ... --end ... --errors-only --top 100 > trace-span-ids.txt

Appendix B — Sample PM skeleton (auto-produced):
- Title: PD12345 — Inference latency spike (Resolved)
- Summary: Short auto-summary here
- Timeline: auto-extracted events (timestamps and short descriptions)
- Evidence: S3 links to evidence pack
- Actions: seeded actions with suggested owners
- Reviewers: auto-suggested reviewers (SRE oncall, Service Owner)

Appendix C — Troubleshooting collector failures:
1) Common failure: missing logs for a region. Action: verify log ingestion agents (fluentd) and re-run collector with --force-historical-fetch.
2) Common failure: redact keys removed important request headers. Action: re-run collector with redact-keys override and keep derivative token IDs only.
