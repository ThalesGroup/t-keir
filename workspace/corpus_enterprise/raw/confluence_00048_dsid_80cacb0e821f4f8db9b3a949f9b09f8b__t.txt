tabletop-rehearsal-scenario-library-and-evidence-templates-2027

Summary:
This page is a compact, reusable library of SRE tabletop scenarios and standardized evidence templates for Redwood Inference. It is intended for cross-functional rehearsal (SRE, runtime, model teams, product, and support) to validate SLO response, capacity handoffs, and post-incident evidence packaging. Use these scenarios to exercise decision-making, validate tools, and produce incident-ready artifacts that meet our incident review standards.

Goals:
- Validate end-to-end escalation and mitigation paths for SLO breaches and capacity events.
- Ensure evidence collected during an event is complete, standardized, and replayable for postmortem analysis.
- Surface operational gaps between serving runtime, autoscaling, and routing policies.
- Reduce time-to-decision during real incidents by exercising runbooks and automation.

Audience:
- SRE oncall and incident commanders
- Runtime and infra engineers (GPU fleet, autoscaler owners)
- Model and ML infra teams
- Product reliability owners and on-call support

How to use this library:
1) Select a scenario card that matches the service / model profile (embedding-heavy, chat, long-sequence generation).
2) Identify the primary SLO(s) and error-budget threshold to trigger the rehearsal (see table below).
3) Run the scenario as a tabletop (discussion-driven) or a live drill (simulated traffic, synthetic canaries).
4) Collect the required evidence using the templates below.
5) Run the post-exercise review using the incident review checklist and produce artifacts for the RCA.

Scenario cards (canonical examples):
1) Cold KV-cache Storm (embedding-heavy traffic)
- Summary: Sudden spike in embedding requests with long prefixes that bypass prefix cache, saturating KV cache lookups and increasing p99 latency for embedding route.
- Trigger: p99 latency > 2.5s for embedding.generate for > 10m or error-budget burn rate > 5x baseline.
- Primary SLOs: embedding.p99_latency (SLO: 99th percentile < 1.2s), overall availability (99.9%).
- Capacity vectors: mem-bound NVMe/CPU contention, saturation of cache clients, per-tenant throttles.
- Mitigations to exercise: temporary tenant throttling, activate burst pool, switch to cached embeddings variant, apply adaptive batching policy.
- Evidence checklist: embedding traces, cache hit/miss rates, per-token CPU/GPU utilization, autoscaler events, token-level request logs.

2) Quantized Model Tail Latency Regression
- Summary: A new quantized variant of a generation model was rolled to prod; traffic shows elevated tail latency (p99.9) due to suboptimal kernel path for long sequences.
- Trigger: p99.9 > 6s for generation route for > 5m or >10% user-facing error increase.
- Primary SLOs: generation.p99.9_latency, generation.success_rate.
- Capacity vectors: kernel fallback, OOM retry cascades, KV cache coherence.
- Mitigations to exercise: immediate rollback to previous model, enable fallback model variant routing, emergency hotpatch to kernel selection.
- Evidence checklist: model rollout timeline, kernel selection traces, GPU memory growth charts, node OOM logs, canary vs prod diff traces.

3) Regional Networking Partition (multi-region fallback)
- Summary: A partial networking partition isolates a single region's control plane causing slow metadata updates and increased routing to backup regions.
- Trigger: cross-region request errors or sustained increase in cross-region latency > 500ms for > 10m.
- Primary SLOs: cross-region latency SLOs, regional availability.
- Capacity vectors: cross-region burst capacity, cold caches in failover regions.
- Mitigations to exercise: traffic re-routing policy, warm-up downstream KV caches, fast failover plan, customer notification cadence.
- Evidence checklist: routing policy logs, region failover actions, cache warmup metrics, customer impact table.

4) Tenant Burst with Headroom Exhaustion
- Summary: A single tenant hit a synthetic spike and consumed headroom, forcing preemption of burst pools and causing proportional throttling for other tenants.
- Trigger: sustained tenant token consumption > 4x forecast for > 15m or immediate headroom allocation failure.
- Primary SLOs: tenant-fairness, global availability, burst-absorber SLOs.
- Capacity vectors: burst pool exhaustion, eviction behavior, quota enforcement.
- Mitigations to exercise: priority re-weighting, soft-eviction, escalation to sales for contracted guarantees.
- Evidence checklist: token-rate timeseries per tenant, eviction events, burst pool utilization logs, quota-policy decisions.

5) Credential Compromise — Limited Control Plane Access
- Summary: A read-only credentials leak led to noisy API calls against the model catalog and a storm of validation requests. Not an outright data breach, but causes throttling and elevated control plane latency.
- Trigger: abnormal API key usage patterns (new IPs, high-rate), control plane API latency > 2x baseline.
- Primary SLOs: control-plane latency and availability, audit-log completeness.
- Capacity vectors: auth service load, rate-limiter exhaustion, audit logging backpressure.
- Mitigations to exercise: key rotation, short-term key blacklisting, rate-limit strictness increase, customer communication protocol.
- Evidence checklist: auth logs, IP geolocation, API key usage samples, audit-log retention checks.

Evidence templates (required artifacts for any rehearsal or real incident):
- Timeline.csv (comma-separated): timestamp, actor, alert, action, rationale, evidence_ref
- Trace-bundle.tar.gz: top 1k traces for affected routes (span IDs, sampled traces)
- Metric-slice.json: time series for key metrics with annotation windows (embedding.p50/p95/p99, GPU utilization, cache hit rates)
- Rollout-manifest.txt: model version, kernel config, build SHA, rollout start/stop times, operator name
- Node-state-snapshot.txt: docker/k8s pod list, GPU allocation, kernel driver versions, memory maps
- Error-sample.log: representative request/response samples (sanitized), include request id and token counts

Evidence naming and retention convention:
- Use the canonical prefix: incident-YYYYMMDD-<service>-<scenario>-<artifact> (e.g., incident-20270209-embed-service-cache-traces.tar.gz).
- Store evidence in the incident bucket and index in the incident evidence ledger within 24 hours.
- Retain rehearsal evidence for 90 days, production incident evidence per security policy.

Operational tooling integration (how to exercise with our stack):
- Playbook-runner (CLI) usage examples:
  - Start tabletop: playbook-runner start --scenario cold-kv-cache --participants sre,model,prod
  - Collect evidence: playbook-runner collect --incident-id INC-20270209 --outputs traces,metrics,logs
  - Package for RCA: playbook-runner package --incident-id INC-20270209 --out /tmp/INC-20270209-package.tar.gz
- Synthetic canary harness: use the slo-synth tool to generate realistic traffic patterns. Example: slo-synth --profile embedding-high --duration 20m --rps 250 --prefix-length 512
- Telemetry queries (examples):
  - Cache hit rate: prometheus: sum(rate(redis_cache_hits_total[5m])) / sum(rate(redis_cache_requests_total[5m]))
  - p99 generation latency: tracing:quantile('generation.latency', 0.99, window='5m')

SRE runbook tie-ins and responsibilities:
- Runbook owners must declare primary SLOs and error-budget thresholds; include scenario mappings in the runbook header.
- Oncall play: SRE incident commander runs tabletop using the local playbook-runner and follows the scenario playbook.
- Post-incident: owner completes the evidence index and files RCA using the Incident Review Template (link in related pages).

Incident review standard for rehearsals and production events:
1) Evidence completeness check within 24 hours (Timeline, Traces, Metrics, Rollout manifest, Node snapshot, Error samples).
2) Blameless timeline creation (who did what and why) within 72 hours.
3) Root cause hypotheses & verification plan documented in the RCA draft.
4) Remediation actions with owners, target deadlines, and SLO-specific verification tests.
5) If the event burned >25% of the monthly error budget for the SLO, an executive summary must be prepared for leadership and customer success.

After-action and reliability initiatives linkage:
- Use rehearsal outputs to seed reliability initiatives: capacity deck creation, autoscaler improvements, kernel selection tuning, and cache warming strategies.
- Track initiatives in the SRE reliability backlog and measure impact against the SLOs used in the scenario library.

Run cadence recommendations:
- High-risk routes (generation with long-context models, high-embedding throughput): monthly live drills.
- Mid-risk (control plane, model rollouts): after each rollout and quarterly tabletop.
- Low-risk: biannual tabletop.
