Private deploy scaling scenarios and cost test catalog

Overview:
This document defines a canonical set of scaling scenarios and an executable test catalog for Redwood Private deployments (VPC and on-prem). Its intent is to provide operators, SREs, and field engineers with repeatable tests that validate performance, autoscaling behavior, billing/cost accounting signals, and safe rollback criteria during day‑2 operations and controlled load experiments.

Scope and audience:
- Scope: Private deployments (single-tenant and multi-tenant topologies), control plane routing to private runtime, autoscale policies, KV/prefix cache behavior, and telemetry required for cost attribution.
- Audience: Field engineers, SREs, platform operators, customer success engineers, and solution architects running pre-cutover or periodic validation tests.

Definitions:
- Baseline SLO: 99th percentile tail latency for token-generate API <= 350ms under nominal load.
- Burst window: short interval (1–5 minutes) of 3–10x nominal QPS.
- Steady window: sustained load for 30–120 minutes used for cost testing.
- Cost unit: $/1k token-equivalents (use your customer-specific rate card).

Owner and escalation:

- Secondary owner: eng-sre (Diego Morales)

Test policy and safety rules (must be read before running tests):
1) Obtain explicit customer approval and schedule maintenance window unless running a lab environment.
2) Notify oncall and customer success with test plan and expected outage risk.
3) Tests that modify routing or scale down capacity must include an immediate abort knob (kill switch) in the orchestration script.
4) All test runs are tagged in telemetry with test_id and operator to allow post-test filtering.

Scaling scenarios (high level):
- Scenario A — Steady-state capacity validation
  - Purpose: Validate throughput, latency, and per-token cost under expected production profile.
  - Duration: 60–120 minutes.
  - Expected behavior: CPU/GPU utilization within configured steady thresholds; autoscaler stable; no model swaps; SLOs met.

- Scenario B — Short-duration burst and graceful degradation
  - Purpose: Validate fast burst handling, queueing/backpressure, and automatic fallback to lower-cost model variants when enabled.
  - Burst profile: 3–8x nominal QPS for 1–5 minutes.
  - Expected behavior: Minimal error-rate increase (<0.5%), observed fallbacks proxied to compatible quantized model, documented cost spike.

- Scenario C — Sustained overload and eviction safety
  - Purpose: Exercise tenant eviction/fairness policies and capacity reclamation procedures.
  - Profile: 2x nominal QPS for 4+ hours.
  - Expected behavior: Controlled evictions according to tenant priority; degraded tenants receive clear 429/503 with retry-after; no silent data loss.

- Scenario D — Model hot-swap under load
  - Purpose: Verify model replacement (hot-swap) maintains session continuity for active chat sessions and KV-cache compatibility.
  - Steps: Initiate rolling swap from model vA->vB while generating steady traffic; validate continuity and token-level output comparison.

- Scenario E — Network partition / cross-region control-plane failover
  - Purpose: Validate control plane fallback to regional bridge and impact on telemetry/cost reporting.
  - Expected behavior: Regional routing to fallback control-plane with telemetry tags marking degraded path; no silent metric gaps longer than 60s.

Note: playbook paths above are logical names — implement as orchestration job templates in FieldOps CI.

Test-case execution template (numbered procedure):
1) Populate the orchestration job: set test_id, duration, target endpoints, and tags.
2) Verify preconditions: topology, autoscaler enabled, baseline snapshot of metrics.
3) Start traffic generator (k6, locust, or internal harness). Example k6 snippet:

# k6 example (pseudo)
export default function() {
  http.post(`${__ENV.TARGET}/v1/generate`, payload, { headers: { 'Authorization': `Bearer ${__ENV.TOKEN}` } });
}

4) Monitor telemetry (see Telemetry & metrics section) in real time.
5) If any hard abort criteria hit (error-rate > 1% for 2m, or GPU OOM), trigger kill switch and mark test as aborted.
6) After test completion, collect snapshots and run automated analysis script to produce a test summary.

Telemetry & metrics (required signals):
- Request plane: request_id, test_id tag, route, model_version, latency_ms, status_code, token_count, cost_estimate_usd.
- Runtime plane: GPU_util_percent, GPU_mem_used_mb, CPU_percent, KV_cache_hit_rate, queue_depth, evictions_count.
- Control plane: routing_decision, autoscale_event_id, model_swap_event, fallback_event_count.

Minimum retention for test artifacts: 90 days to support postmortem cost reconciliation.

Cost estimation method (quick reference):
- Estimate cost for a run = sum_over_requests(tokens * per_token_rate) + infra_allocated_hourly_cost * duration_hours.
- Example: 1M tokens at $0.005/1k tokens = (1,000 * 0.005) = $5; plus infra $0.50/hr * 2h = $1 => total $6.
- Tag each request with cost_estimate_usd to help downstream billing reconciliation.

Configuration snippets and thresholds (table):
| config_key | recommended default | rationale |
|------------|---------------------|-----------|
| autoscaler.min_replicas | 2 | avoid single-node loss-of-service |
| autoscaler.max_replicas | 20 | bound cost during runaway tests |
| autoscaler.scale_up_window | 30s | faster ramp for bursts |
| autoscaler.scale_down_window | 5m | avoid flapping after short bursts |
| eviction.priority_thresholds | {high: 1, medium: 5, low: 10} | tenant eviction scorecard (see eviction playbook) |

Pre-test checklist (must pass before test start):
- [ ] Customer consent recorded in ticket and Slack channel
- [ ] Baseline telemetry snapshot captured
- [ ] Canary endpoints for kill-switch validated
- [ ] Backup/rollback plan documented and accessible
- [ ] Billing contact notified for cost spike awareness

Abort, rollback, and post-failure procedure (short):
1) If abort criteria met, call orchestration kill-switch which should:
   a) immediately stop traffic generators,
   b) pin runtime model to last-known-good version,
   c) revert routing policy if modified,
   d) capture state dump and core logs.
2) If test caused customer-impacting service degradation, escalate to oncall and open a postmortem.
3) Run automated reconciliation: compare test cost_estimate_usd tags against invoice-level aggregation and annotate deviations > 10%.

Reporting and artifact requirements:
- Test summary must include: test_id, operator, start/end timestamp, topology snapshot (node counts, GPU types), per-minute p95/p99 latencies, total tokens served, total estimated cost, and runbook used.
- Attach artifacts: telemetry window export (Prometheus/Influx), raw request logs (redacted), orchestration job definition, and comparison diff for model outputs (for hot-swap tests).

Troubleshooting checklist (common failure modes):
- Symptom: p99 latency spike but no GPU saturation -> check network egress/ingress queues, NFS/remote store I/O.
- Symptom: elevated fallback count -> verify model variant compatibility and quantization profiles; check kernel mismatches.
- Symptom: telemetry gaps during control-plane test -> confirm metric exporter connectivity and local batching retention.

Postmortem guidance (quick template):
- Title: PD-<test_id> Postmortem
- Summary: high-level description and impact
- Timeline: minute-by-minute events
- Root cause analysis: one-paragraph RCA + evidence
- Corrective actions: owner, due date, and verification test plan
