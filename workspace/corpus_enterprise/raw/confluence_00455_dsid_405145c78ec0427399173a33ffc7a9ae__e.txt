Economic Priority Governor and Degradation Scenarios: design & runbook

Overview

Purpose: This document describes the Economic Priority Governor (EPG) — a scheduling policy component that combines token-cost signals, per-tenant budgets, SLOs, and priority tiers to make admission, throttling, and graceful-degradation decisions in Redwood's serving runtime. It includes design rationale, policy examples, a rollout/test plan, observable contract, and a practical incident/runbook for when degradation modes trigger.

Audience: runtime engineers, SREs, product owners for Dedicated/Private tiers, and on-call responders.

Summary of behavior

- The EPG takes as input: request priority, tenant token-budget metadata, model variant cost estimate, current per-GPU/KV cache pressure, and SLO health signals.
- It evaluates a scoring function that yields one of: allow, delay (micro-burst queue), degrade (route to cheaper model variant or quantized path), or reject.
- Degradation modes are tiered and reversible; the governor records decisions and exposes a decision trace for postmortem.

Design goals and constraints

1) SLO preservation: keep p95 latency and error-rate SLOs for high-priority users where feasible.
2) Cost predictability: prevent runaway cost from low-priority or uncontrolled workloads.
3) Graceful degradation: prefer fidelity stair-step (model->quantize->cached-response) rather than blackholing traffic.
4) Observability: each decision must emit a DecisionTrace event with inputs and reason codes.

Decision inputs and data model

- request.priority: enum (urgent, interactive, background)
- tenant.budget_window_usd_per_hour: numeric (configured per-tenant)
- model.variant.cost_per_ktoken_usd: numeric (runtime catalog metadata)
- gpu_utilization_pct: rolling 30s average
- kvcache_hit_rate: rolling 1m average
- slo_health: derived boolean from SLO engine (true=healthy)

Scoring function (high-level)

score = w_p * priority_score + w_c * cost_risk - w_s * slo_headroom + w_r * resource_pressure

Interpretation: lower score -> more aggressive degradation. We tune weights (w_*) via A/B simulation experiments documented below.

Policy configuration (example table, expressed in prose)

- admission_thresholds: numeric thresholds for allow/delay/degrade/reject decisions. Example: allow if score >= 0.7, delay if 0.5<=score<0.7, degrade if 0.2<=score<0.5, reject if score<0.2.
- degradation_order: [model_variant, quantize_profile, cached_prefix, approximate_rerank] (applies in sequence)
- preemption_policy: immediate for urgent over background; background requests can be preempted after 120ms of queuing.
- budget_burn_rate_limit: per-tenant burn-rate cap (e.g., 3x hourly average). Exceeding triggers soft-degrade, repeated exceed triggers strict reject.
- safety_gates: absolute p95 latency floor (e.g., 800ms) — if exceeded for 3 consecutive 1m windows, governor shifts to stricter degrade mapping for all non-urgent traffic.

Configuration example (YAML snippet)

policy:
  admission_thresholds:
    allow: 0.7
    delay: 0.5
    degrade: 0.2
    reject: 0.0
  degradation_order:
    - model_variant
    - quantize_profile
    - cached_prefix
    - approximate_rerank
  preemption:
    urgent_over_background_ms: 120
  budget_controls:
    max_burn_multiple: 3.0
    warning_window_minutes: 10
  safety_gates:
    p95_latency_floor_ms: 800
    sustained_window_minutes: 3

Operational observables (metrics, logs, traces)

Emit and dashboard these metrics at tenant and cluster level:
- epg.decisions.allow_total, delay_total, degrade_total, reject_total (counters)
- epg.degrade_by_type{model_variant,quantize,cached} (counters)
- epg.budget_overage_count (gauge, tenants currently over budget)
- epg.decision_latency_ms (histogram)
- request.p95_latency_ms, request.p50_latency_ms (runtime request metrics)
- cost.estimated_usd_per_minute (cluster estimate)
- slo_health (boolean per-service)

Each decision should also produce a DecisionTrace JSON attached to the request trace with fields (flattened key/value in logs): decision, score, inputs:[priority,cost_estimate,budget_headroom,gpu_util,kv_hit], applied_degradations, reason_code.

Runbook: incident flow when safety_gates trigger

Purpose: step-by-step actions for on-call to restore SLOs, assess cost impact, and roll back unintended degradation.

1) Alert symptoms and triage
  - Pager triggers when cluster-level p95 > 850ms for 3 consecutive minutes AND epg.degrade_total increased by >200% vs baseline.
  - On-call examines: cluster GPU utilization, epg metrics, per-tenant budget_overage_count, and DecisionTrace samples.

2) Initial mitigation (fast)
  - Temporarily widen admission_thresholds (allow->0.6) for 5 minutes to favor throughput over cost while diagnosing: CLI: redwoodctl epg set --path /policy/admission_thresholds.allow --value 0.6 --team runtime --ttl 300
  - If widening reduces p95 under floor, keep open and continue root-cause. Otherwise revert.

3) If broad widening is unsafe, quick-targeted mitigations:
  - Pin high-value tenants to reserved capacity (switch routing policy to dedicated pool) via routing API. Example: curl -XPOST $ROUTER/api/v1/route/pin -d '{"tenant":"acme","pool":"dedicated-us-west-1"}'
  - For top offending tenants (by DecisionTrace), apply temporary per-tenant throttle: redwoodctl tenant throttle --tenant-id <id> --qps 10 --duration 15m

4) Deeper diagnosis
  - Replay DecisionTrace logs via the EPG simulator (see Testing and simulation) to reproduce policy decisions.
  - Check for model catalog mis-priced variants (cost_per_ktoken drift) and measurement anomalies in cost model.
  - Confirm KV cache hit-rate; low hit-rate may force model re-exec and drive up cost.

5) Restore & follow-up
  - Roll back any ephemeral policy changes using redwoodctl epg rollback --reason "post-incident".
  - Open postmortem referencing DecisionTrace correlation ids for affected requests.
  - If mis-pricing found, publish corrected model cost metadata and run full canary.

Testing and simulation plan (before rollout)

1) Unit tests: deterministic scoring inputs -> expected action (allow/delay/degrade/reject). Store cases in the scoring test matrix repo.
2) E2E EPG simulator: a lightweight harness that replays real request traces and asserts that SLOs, cost, and per-tenant budgets behave as expected for policy parameter sweeps.
3) A/B rollout in sandbox (recommended matrix):
  - 5% traffic with canary weights for 24h across three traffic shapes: interactive-heavy, background-batch, and bursty-chat.
  - Measure p50/p95 latency, epg.degrade_by_type, and cost.delta_usd/hr.
4) Chaos tests: inject KV cache TTL expiration spikes, and GPU slow-path latency increase to validate degradation order and safety gates.

Simulation commands (examples)

- Start simulator with historic trace: ./epg-sim --trace traces/2026-02-22/interactive.json --policy policy/epg-canary.yaml --report reports/canary-interactive.json
- Run parameter sweep: ./epg-sim --sweep policy/param_grid.yaml --out reports/sweep-summary.csv

Rollout plan and gating

- Stage 0 (dev): unit tests + simulator run (green)
- Stage 1 (canary): 5% production traffic, 24–48h. Must show no >2% regression on p95 for urgent tier and cost delta within expected band.
- Stage 2 (regional expansion): 25% traffic for 48h with alternate hardware templates.
- Stage 3 (full): 100% with gradual scale over 6h and a 1h fallback window.

Acceptance criteria (example)

- Urgent-tier p95 change <= +2% versus baseline.
- Background-tier cost reduction >= 10% in high-burn traces without increasing urgent-tier p95.
- DecisionTrace sampling success >= 99%.

Known risks and mitigations

- Mis-priced model variants: mitigate by batching a catalog refresh job and adding canary tags on cost changes.
- DecisionTrace overload: sample at 1% by default; increase when debugging but watch storage cost.
- Tenant UX regressions: add visible headers in API responses when degraded: X-Redwood-Degraded: quantized-profile-3 so customers can failover.

Appendix B: quick CLI reference

- Inspect current policy: redwoodctl epg get --path /policy --format yaml
- Set a temporary threshold: redwoodctl epg set --path /policy/admission_thresholds/degrade --value 0.25 --ttl 600 --author "oncall"
- Revert latest change: redwoodctl epg rollback --last 1 --author "oncall" --reason "mitigation"

Appendix C: simulation test cases (human-readable table)

1) Interactive low-cost: high urgent fraction, low average sequence length -> expect allow rate >95% for urgent tier.
2) Bursty batch: many background jobs arriving in bursts -> expect degrade for background and stable urgent p95.
3) Cache-thrash + expensive model: low kv_hit + high model cost -> expect degrade to cached_prefix or quantize earlier.
