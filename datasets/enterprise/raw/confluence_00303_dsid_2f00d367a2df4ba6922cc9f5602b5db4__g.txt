GPU tenant credit buckets and granular throttling policy

Overview

This document describes the design, operational controls, and IaC contract for GPU tenant credit buckets and a granular throttling policy used by Redwood's GPU fleet. The mechanism is intended to enable predictable multi-tenant sharing of constrained GPU capacity while preserving latency SLOs for high-priority customers. It covers: design rationale, definitions, Terraform module inputs/outputs, Prometheus metrics and alerting, runbook for exhaustion events, and rollout checklist.

Goals

- Provide per-tenant soft and hard credit budgets to shape consumption.
- Allow priority-based borrowing and preemption with clear accounting.
- Minimize tail latency impact for latency-SLOed routes.
- Expose clear telemetry, billing signals, and IaC primitives for automation.

Scope and non-goals

- Scope: hosted and dedicated GPU pools managed by the GPU scheduler service (gpu-scheduler), quota enforcement in quota-service, and telemetry via redwood-telemetry -> Prometheus.
- Non-goal: billing invoice generation; accounting for billing will use the credits as input but is handled by finance pipelines separately.

Definitions

- Credit bucket: a time-windowed allocation of GPU-usage units (GPU-minutes) assigned to a tenant.
- Soft limit: tenant is throttled when credits are below soft threshold, but allowed to spike using borrowing rules.
- Hard limit: tenant is blocked from launching new GPU sessions when credits are exhausted.
- Borrow pool: a small globally-shared emergency bucket used for short bursts; drained first before preemption.
- Priority score: numeric score computed from customer tier + route SLO that drives scheduling priority.

Design overview

1) Accounting unit: GPU-minutes (1 GPU at 100% utilization for 1 minute). We convert observed usage into GPU-minutes using node-level utilization and allocation windows. Metric exported: gpu.tenant.credit.consumed_total

2) Two-tier bucket model:
- Base daily bucket (configured per tenant) e.g. 1,440 GPU-minutes = 24 GPU-hours/day.
- Reserve bucket (borrowable) sized as a percent of base (configurable per contract).

3) Enforcement points:
- Admission: gpu-scheduler consults quota-service before scheduling a new session. If credits >= hard threshold -> allow. If credits between soft and hard threshold -> allow with rate-limiter token assigned. If credits below soft threshold -> admission allowed only for high-priority routes.
- Runtime: continuous enforcement via agent on nodes reporting consumed GPU-minutes; quota-service decrements bucket in near realtime (<= 15s).

4) Preemption and graceful degradation:
- When global pressure > 85% utilization and borrow pool exhausted, scheduler will preempt ephemeral / low-priority sessions using existing preemption policy (preempt score + grace period 30s). Preemption emits event: gpu.preempt.event.

IaC module contract (terraform)

Use the module: redwood/gpu/tenant-credits v1.0. Example inputs and outputs (table):

| variable (input)               | type   | example        | description |
|-------------------------------|--------|----------------|-------------|
| tenant_id                     | string | "acct-1234"   | Tenant identifier |
| base_daily_gpu_minutes        | number | 1440           | Base daily bucket |
| reserve_percent               | number | 10             | Percent of base as borrowable reserve |
| soft_threshold_percent        | number | 20             | Percent of remaining to mark soft limit |
| hard_threshold_percent        | number | 0              | Percent at which new admissions are blocked |
| owner_oncall                  | string | "eng-sre"     | Pager duty team |

Outputs:
- quota_resource_id (string)
- initial_alert_rule_id (string)

Terraform usage snippet:

```
module "tenant_credits" {
  source                 = "git::ssh://git@repo.redwood.internal/infra/terraform//modules/gpu/tenant-credits?ref=v1.0"
  tenant_id              = var.tenant_id
  base_daily_gpu_minutes = var.base_daily_gpu_minutes
  reserve_percent        = var.reserve_percent
  soft_threshold_percent = var.soft_threshold_percent
  hard_threshold_percent = var.hard_threshold_percent
  owner_oncall           = var.owner_oncall
}
```

Prometheus metrics and alerts

Primary metrics (exported by quota-service / gpu-exporter):
- gpu_tenant_credit_remaining{tenant_id="..."}  (gauge, GPU-minutes remaining in bucket)
- gpu_tenant_credit_consumed_rate{tenant_id="..."} (gauge, GPU-minutes/min)
- gpu_borrow_pool_remaining (gauge)
- gpu_scheduler_queue_latency_p50/p90 (histogram summaries)
- gpu_preempt_count_total{tenant_id="..."} (counter)

Example PromQL alerts (alert manager):

- Low credits warning (soft):
  - expr: gpu_tenant_credit_remaining / on(tenant_id) (base_daily_gpu_minutes) < 0.2
  - for: 10m
  - labels: severity=warning, team={{ $labels.owner_oncall }}

- Critical credits exhausted (hard):
  - expr: gpu_tenant_credit_remaining == 0
  - for: 2m
  - labels: severity=critical, runbook="/confluence/eng-infra/runbooks/gpu-tenant-credit-exhaustion"

- Global pressure -> preemption risk:
  - expr: (sum(node_gpu_utilization) by (region) / sum(node_gpu_capacity) by (region)) > 0.85 and gpu_borrow_pool_remaining < 0.05 * sum(base_daily_gpu_minutes)
  - for: 1m
  - labels: severity=critical

Operational runbook: credit exhaustion (short)

1) Alert fires: critical credits exhausted. Pager routes to eng-sre primary.
2) Triage (5 min):
   - Check alert details in Grafana dashboard: GPU Credits -> Tenant view.
   - Query recent consumption: `sum by (tenant_id) (rate(gpu_tenant_credit_consumed_total[10m]))`
   - Check if tenant is on Dedicated cluster or Shared pool.
3) Mitigation options (ordered):
   a) Temporarily increase tenant reserve_percent via terraform variable override and apply (fast path for enterprise customers).
   b) If reserve exhausted and global pool healthy, transfer from shared borrow_pool: `POST /quota-service/admin/borrow?tenant=acct-1234&minutes=120` (requires admin token).
   c) If global pool under pressure, coordinate with scheduler to evict best-effort sessions: use `gpu-schedulerctl preempt --selector priority<=0.2 --max=10`
4) Post-incident: create incident note, update tenant consumption pattern, recommend rate limit or schedule adjustments.

Security and data residency notes

- Credit state is sensitive (can reveal usage patterns). Stored in DynamoDB/primary-db with encryption at rest and access controlled by IAM. Access limited to quota-service and telemetry-read-only roles.

FAQ

Q: How do credits interact with Dedicated pools?
A: Dedicated tenants get an equivalent credit bucket used for burst accounting but preemption rules differ: scheduler will not preempt non-ephemeral sessions on dedicated pools unless explicitly configured in the tenant contract.

Q: Can we auto-top-up credits?
A: Top-ups are supported via the billing pipeline which can call the quota-service admin endpoints. Auto-top-up requires an approved billing rule and is disabled by default.
