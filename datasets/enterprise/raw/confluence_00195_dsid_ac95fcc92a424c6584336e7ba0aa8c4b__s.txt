Secure Offline Update & Operator Toolkit for On‑Prem Deployments

Purpose and scope

This page describes the Secure Offline Update & Operator Toolkit: a prescriptive playbook for preparing, delivering, validating, and rolling back offline (air-gapped) updates to Redwood Private runtime bundles. It combines packaging requirements, operator CLI recipes, safety windows, tests, telemetry guardrails, and a concise operator checklist for day‑2 field operations.

Audience

- Field operators performing on‑prem upgrades
- SREs who build offline update bundles
- Security/compliance reviewers validating update artifacts
- Solutions engineers responsible for customer runbooks

Goals

1. Ensure updates for private/on‑prem deployments are delivered with cryptographic provenance and verifiable rollback capability.
2. Provide operator-friendly commands and automation templates for safe staged rollouts in air‑gapped environments.
3. Define minimal telemetry and evidence artifacts required for post‑upgrade audits.

When to use this guide

- Customer environment is air‑gapped or uses restricted egress
- The update touches runtime or model artifacts (kernel, quantization tables, model binaries)
- Regulatory requirement mandates offline delivery and preserved evidence

Prerequisites

- Operator workstation with GPG/cosign and sha256sum installed
- Customer acceptance of maintenance window and SLA impact
- Signed operator access key (short‑lived) provisioned per customer operator account
- Secure physical or logically isolated bundle transfer channel (USB, controlled SCP jump-host, or couriered media)

Artifact & bundle format (required fields)

All offline bundles MUST be tarball archives with a deterministic layout and the following files (example manifest below):

- bundle.manifest.json — canonical manifest listing artifact names, semantic version, build id, and checksums (sha256)
- bundle.signatures.sig — cosign or GPG detached signatures for the manifest and each artifact
- runtime.tar.zst — runtime binaries & kernels
- models/ — folder containing model artifacts (quantization variant metadata included)
- migrations/ — optional state migration scripts with idempotency guarantees
- upgrade-plan.yaml — operator steps (precheck, apply, verify, rollback)
- verify-scripts/ — signed scripts used for post‑apply assertions (read‑only by default)

Example bundle.manifest.json (excerpt, replace placeholders):

{
  "bundle_version": "2026.02.1",
  "build_id": "runtimes-prod-20260210-94ab",
  "artifacts": [
    { "path": "runtime.tar.zst", "sha256": "<sha256hex>" },
    { "path": "models/llama-16b.q4.bin", "sha256": "<sha256hex>" }
  ],
  "upgrade_plan": "upgrade-plan.yaml"
}

Verification & signature model

- All bundles MUST be signed with the Redwood release key using cosign v2 or GPG (customer can provide their own attestation key in managed engagements).
- Operators must verify both the manifest signature and individual artifact checksums before ingest.

Commands (operator workstation examples)

# Verify manifest signature (cosign):
cosign verify-blob --key /keys/redwood-release.pub bundle.manifest.json bundle.signatures.sig

# Validate artifact checksums:
sha256sum -c bundle-checksums.txt  # bundle-checksums.txt generated from manifest

# Optional GPG verification: 
gpg --verify bundle.signatures.sig bundle.manifest.json

Safety window and planning

1. Schedule a maintenance window with customer and ensure at least one rollback slot reserved (30 minutes per tenant for rollback decision).
2. Run the preflight suite on a representative staging cluster offline snapshot (see preflight checklist).
3. Establish an operator hot path: primary operator, secondary operator, and on‑call SRE.

Preflight checklist (run before transfer to customer site)

- Build artifact deterministic re‑creation verified
- Smoke VM with runtime.tar.zst deployed and run smoke generator for 2,000 synthetic tokens
- Migration scripts validated in an isolated replica of the target KV cache
- Telemetry masks applied: PII redaction rules validated

Operator apply sequence (canonical steps)

1. Ingest stage — verify signatures and checksums, unpack to staging volume (read‑only by default).
2. Snapshot — take a full runtime snapshot (KV caches and ephemeral state) and export pointer to evidence bundle.
3. Dry‑run apply — run upgrade-plan.yaml in dry‑run mode (no state changes) and capture logs.
4. Apply — execute upgrade-plan.yaml with controlled concurrency (tenant groups of 10% first wave).
5. Verify — run verify-scripts/ and sampling queries (liveness, tail latency, model continuity).
6. Promote — remove read‑only flags and switch traffic to the new runtime variant.
7. Evidence archive — collect signed logs, verification artifacts, and store in customer evidence bucket.

Upgrade-plan.yaml pattern (illustrative fragment)

steps:
  - id: prechecks
    action: run
    script: verify-scripts/prechecks.sh
  - id: snapshot
    action: snapshot
    ttl: 72h
  - id: apply-runtime
    action: replace-files
    path: /opt/redwood/runtime
    concurrency: 10%
  - id: post-verify
    action: run
    script: verify-scripts/post-verify.sh
  - id: finalize
    action: promote

Canary & staged rollout policy

- Wave 0 (canary): 1 host or 0.5% traffic for 30 minutes. Must pass health checks and model-quality smoke set.
- Wave 1: 10% tenant groups for 60 minutes. Monitor tail p95/p99 latency and error budget.
- Wave 2: 50% for 2 hours.
- Wave 3: full capacity.

Abort conditions (automatic/manual)

- Any host with >1.5x historical p99 latency for 30s
- Error rate >0.5% for control routes or >1% for non‑control routes
- Model quality regression flagged by eval harness (precision drop exceeding 3% for critical prompts)

Rollback strategy

- Rollback MUST be possible within the defined maintenance window. Keep two full generations of runtime snapshots: pre‑upgrade and last‑known‑good.
- Rollback steps:
  1. Trigger rollback via operator CLI: rdu-rollback --snapshot <snapshot-id> --reason "auto|manual"
  2. Wait for raft/leader stabilization (monitor leader election logs)
  3. Run post‑rollback validations (see verification checklist)
  4. Archive rollback evidence and trigger incident creation if rollback was due to service regression

Operator CLI examples

# Ingest and verify bundle locally
rdu-ingest --bundle /media/bundle-2026.02.1.tar.zst --verify --key /keys/redwood-release.pub

# Dry run apply (no traffic switch)
rdu-apply --plan upgrade-plan.yaml --dry-run --output logs/dryrun-2026-02-15.log

# Apply to canary tenants
rdu-apply --plan upgrade-plan.yaml --wave canary --concurrency 1

# Rollback to snapshot
rdu-rollback --snapshot pre-upgrade-20260215 --reason "p99-regression-detected"

Verification checklist (post‑apply)

- Service health: all processes up, pod restarts = 0, disk pressure = none
- Latency: p50/p95/p99 within expected thresholds (p99 increase <10% allowed for bursty workloads)
- Model outputs: run 50 golden prompts and compare embedding similarity thresholds
- KV consistency: checksum of hot KV namespace unchanged (unless migration expected)
- Telemetry: evidence archive created and signed

Telemetry & privacy guidance

- Minimum telemetry for update evidence: signed syslogs for apply, verify script outputs, checksums, and bundle.manifest.json.
- Do NOT include raw customer prompts or embeddings in evidence; instead include hashed prompt identifiers and aggregated quality metrics.
- Sampling policy: 1% random sampling for human readable traces, 100% for error events.

Evidence package contents (required)

| Artifact | Purpose | Retention 
|---------|---------|---------
| bundle.manifest.json | Provenance | 2 years
| bundle.signatures.sig | Attestation | 2 years
| pre/post apply logs (signed) | Forensics | 1 year (hipaa/reg sites: 2 years)
| verify-scripts outputs | Validation | 1 year
| snapshot pointer ID | Rollback anchor | 90 days

Customer requirements (minimum acceptance contract)

1. Customer must provide an operator contact and maintenance window approval.
2. Customer provides an ingress channel (USB device or approved transfer host) and a defined acceptance test harness (list of golden prompts).
3. Customer agrees to evidence retention policy and provides KMS public key for attestation if required.

Field operator checklists (condensed)

Pre‑transfer (service owner):
- [ ] Confirm maintenance window and customer contact
- [ ] Generate evidence package template and preflight smoke results

At customer site (operator):
- [ ] Verify signatures and checksums
- [ ] Snapshot runtime state
- [ ] Dry‑run apply and collect logs
- [ ] Apply to canary, monitor for 30 minutes
- [ ] Escalate on abort conditions
- [ ] If safe, continue staged rollout
- [ ] Produce and sign evidence archive

Post‑operation (postmortem & archive):
- [ ] Upload evidence to customer evidence bucket
- [ ] Create short postmortem if rollback occurred
- [ ] Update bundle compatibility matrix if any manual patches were made

Operational roles and escalation

- Primary operator: executes the bundle ingestion and apply steps.
- Secondary operator: validates evidence and readiness.
- SRE on‑call: available for leader/raft issues and cross‑tenant regressions.

Common failure modes & mitigations

- Checksum mismatch: abort ingest, request re‑transfer, validate transport integrity
- Migration script error: run migration in isolated replica and apply hotfix; if urgent, rollback to snapshot
- Latency spike during canary: abort and roll back, escalate to SRE

Appendix: useful scripts and snippets

- generate-checksums.sh (example):
for f in runtime.tar.zst models/*; do sha256sum "$f" >> bundle-checksums.txt; done

- quick-verify.sh (example):
#!/bin/bash
set -e
cosign verify-blob --key /keys/redwood-release.pub bundle.manifest.json bundle.signatures.sig
sha256sum -c bundle-checksums.txt
