Gatekeeper: Deployment Safety, Config Fencing, and Runtime Contract Playbook

Overview

Purpose:
This playbook defines a layered ‘Gatekeeper’ approach to make deployments and config changes across Redwood Inference predictable and safe. It combines pre-deploy validation, runtime contract enforcement, and automated rollback/mitigation rules so that services (especially model-serving and inference pipelines) can evolve without causing widespread customer impact.

Audience:
Engineering teams that own API surface, runtime components, fleet configuration, and release tooling; SRE/PD teams who run canaries, and product owners who need clear rollback SLAs.

Scope:
- Applies to all API-facing services and inference runtime components: hosted API, Dedicated schedulers, and Private runtime sidecars.
- Does NOT replace per-service release notes or change approval; it standardizes checks and rollback triggers.

Key principles:
- Fail-fast before traffic: stop bad config artifacts at the gate.
- Least-surprise runtime: enforce backward-compatible contracts and optional capability negotiation.
- Observable safety: every gate emits telemetry and a single canonical incident signal.
- Automated but auditable: automated remediation triggers must be reversible and logged.

Terminology:
- Gatekeeper (the pattern): a collection of validations and runtime enforcements applied during deploy and live traffic.
- Fence: a rule that prevents a config, schema or artifact from progressing to the next stage.
- Contract: API/schema/behavioral expectations declared by the service.

Safety layers (summary):
1) Preflight/Lint Gate (CI)
   - Config schema validation (YAML/JSON schema).
   - Static contract tests (OpenAPI/protobuf compatibility).
   - Resource and quota checks against current capacity (see Capacity rubric).
2) Canary Gate (staged rollout)
   - Canary ratio: default 1% traffic for 30 minutes with synthetic tests.
   - Automated health checks and model-quality smoke tests (if inference change).
3) Runtime Fence (adaptive enforcement)
   - Capability negotiation: failing clients are served with a stable fallback.
   - Circuit conditions: enforce early-exit and backpressure thresholds.
4) Automated Rollback/Degrade Gate
   - Triggers for rollback/degrade include SLO breach, error spike, quality regression, or contract violations.

Concrete checks and thresholds (table):
| Gate | Check | Default Threshold | Owner | Action on failure |
|------|-------|-------------------:|-------|------------------|
| Preflight | Schema validation | 0 errors | Authoring service | Block merge |
| Preflight | Compatibility tests | 0 incompatible ops | API platform | Block deploy |
| Canary | 5xx rate | > 0.5% absolute increase | SRE | Pause rollout, investigat e |
| Canary | P95 latency | > 2x baseline | SRE/Service | Abort canary, rollback |
| Runtime | Model-quality delta (eval) | absolute drop > 3 points | Applied-ML | Revert to previous model |
| Runtime | Error budget burn | > 60%/30m | SRE/Owner | Traffic cutback + rollback |

NOTE: Teams may tighten thresholds for high-risk services (see service risk matrix).

Preflight checklist (detailed):
- Lint and schema: run ./tools/config-lint --schema=infra-config-v2.yaml
- Contract tests: make contract-test; includes OpenAPI diff and Protobuf compatibility check.
- Security gating: secrets not embedded; KMS key reference validated.
- Cost guard: estimated GPU-hours and memory footprint reported; alert if exceeds reserved budget.
- Smoke harness: run synthetic request set (prompt-suite-ci) against new artifact in test cluster.

Example CLI snippet (preflight):
$ ./ci/preflight-run --service inference-api --artifact sha:abcd1234 
# returns JSON summary with fields: passed_checks, failed_checks, estimated_gpu_hours

Canary rollout recipe (recommended default):
1. Deploy artifact to canary fleet (tag: canary-<build>) in region-local cluster.
2. Route 1% of production traffic using traffic-router v2 with header-based stickiness.
3. Run automated synthetic prompts every 30s (10 concurrent).
4. Monitor pre-configured dashboards for 30 min.
5. If no triggered fences, increase to 10% for 1 hour, then 50% for 2 hours, then full.

Numbered rollback decision flow (automated + human-in-the-loop):
1) Monitoring detects a fence trigger (e.g., error spike, latency exceedance, model-quality regression).
2) Automation evaluates severity and service tier. If severity >= automated_rollback_threshold, proceed to step 4.
3) Notify on-call, create an incident with runbook link, and pause rollout.
4) Automated rollback: traffic-router shifts all traffic to previous stable variant, sidecars mark artifact as deprecated, and the deploy is rolled back in orchestration system.
5) Post-action: postmortem owner assigned within 24 hours.

Automated rollback safeguards (must be implemented):
- TTL window: automated rollback operations must be rate-limited (no more than 2 auto-rollback events per service per 24h).
- Human override: on-call can veto an automated rollback within 2 minutes of trigger if a mitigation path exists. The override must be recorded with justification.
- Read-only staging flag: rollbacks in private deployments (air-gapped) require manual approval unless the customer opts-in for automated recovery.

Runtime contract enforcement patterns:
- Schema negotiation: responses include x-contract-version header; clients that cannot parse newer fields receive a compatibility view (stable schema renderer).
- Feature toggles: server-side feature gates are fenced by a config hash; older clients are mapped to conservative toggles.
- Graceful degradation: when dependent subsystems are unhealthy, the runtime returns structured partial responses with metadata about missing fields and reason codes.

YAML example: Gatekeeper admission (k8s webhook) config
---
apiVersion: admissionregistration.k8s.io/v1
kind: ValidatingWebhookConfiguration
metadata:
  name: gatekeeper-deploy-fence.redwood.svc
webhooks:
  - name: validate-infra-config.redwood.svc
    rules:
      - apiGroups: ["apps"]
        apiVersions: ["v1"]
        operations: ["CREATE","UPDATE"]
        resources: ["deployments"]
    failurePolicy: Fail
    admissionReviewVersions: ["v1"]
    clientConfig:
      service:
        name: gatekeeper-admission
        namespace: infra-system
        path: /validate-deploy

Observability and SLO instrumentation (must-haves):
- Metrics: deploy.latency_ms, deploy.canary_error_rate, deploy.rollback.invocations, model.eval_delta, contract.compatibility_failures.
- Traces: every deploy should include a distributed-trace span: deploy.flow.<service> linking CI -> canary -> promotion.
- Logs: structured event at each fence with fields {service, artifact, gate, result, actor, timestamp}.
- Dashboards: per-service deploy summary and a team-wide Gatekeeper health board.

Alerting rules (examples):
- P0: deploy.rollback.invocations > 1 for a single service in 15m -> Pager to SRE and service on-call.
- P1: contract.compatibility_failures > 0.1% of traffic in 10m -> Slack @channel and ticket created.

Testing and CI integration:
- Contract fuzz tests: run nightly with a corpus covering major client types. Failure must block production promotion.
- Synthetic prompt-suite: every model variant must include a 200-query smoke set; regression > 2% triggers a fence.
- Chaos tests: periodic simulated canary failures to ensure rollback automation works end-to-end.

Ownership and roles:
- Service Owner: ensures preflight tests and synthetic harness exist.
- SRE: owns canary platform, alerting, and rollback automation.
- Applied-ML: owns quality metrics and model-eval gating.
- Release Engineering: integrates the Gatekeeper checks into CI and provides the promotion API.

Escalation matrix:
- 0–15 min: on-call engineer triages and either approves immediate rollback or pauses rollout.
- 15–60 min: SRE + Service Owner coordinate mitigations and decide on targeted rollback windows.
- 60+ min: Engineering manager and product representative determine broader customer communication and executive notification.

Governance and exceptions:
- High-priority customer hotfixes may request bypass of automated gates via the emergency release process; request must include a rollback plan and acceptance of potential increased monitoring.
- For Private/On-Prem deployments, Gatekeeper automation is advisory by default; customers can opt into automated rollback via contract.

Operational runbook excerpts (quick actions):
- Pause rollout: curl -X POST https://traffic-router.internal/api/v1/pause -d '{"service":"inference-api"}'
- Force rollback: ./releases/promote --service=inference-api --to=stable --force
- Query last fence events: ./infra/events query --filter 'service:inference-api AND gate:fence' --last 1h

Appendix A: Capacity rubric (short)
- Low risk: services with < 500 RPS and no GPU dependency: default gates.
- Medium risk: services with 500–5k RPS or single-GPU models: tightened thresholds (P95 latency x1.5).
- High risk: multi-region ingress, >5k RPS, or customer-facing SLA: require full canary sequence plus staged DB migrations.
