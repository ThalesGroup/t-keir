Quota enforcement shim Terraform module and SLO contracts

Overview

This document describes the design, implementation, and rollout plan for a small, reusable Terraform module (quota-enforcement-shim) that enforces tenant egress and GPU capacity quotas at infrastructure provisioning time and exposes SLO contract metadata for downstream billing and alerting. The shim is intentionally lightweight: it does not replace the allocator, but it provides deterministic enforcement points for cross-account / cross-region quota policies, a test harness for canary promotion, and integration hooks for billing reconciliation.

Goals

- Provide a single, testable Terraform primitive teams can attach to tenant onboarding and burst orchestration.
- Enforce hard and soft quotas consistently across cloud accounts (GCP/AWS).
- Emit structured SLO metadata and provenance tags to be consumed by billing and telemetry pipelines.
- Enable safe canary promotion of quota changes via CI/CD (Buildkite/GitHub Actions).
- Minimize blast radius: the shim is opt-in per-tenant and can be rolled back via automated TF rollback.

Non-goals

- Not a replacement for runtime capacity allocators or the GPU scheduler.
- Not responsible for chargeback computation (it provides attributes used by billing pipelines).

Architecture and components

1) Terraform module (quota-enforcement-shim)
   - Purpose: attach quota checks and enforcement resources (IAM, service-accounts, deny policies, quota alarms) to tenant landing zone.
   - Outputs: enforcement_ids, slo_metadata_tag, canary_flag_resource_id.

2) Policy adapter (lambda/cloudfunction)
   - Purpose: reconcile desired quota in TF state with cloud provider quota APIs and set soft/hard limits where supported.
   - Runs: on TF apply (invoked via remote-exec or provider webhook) and on a scheduled reconciliation every 30 minutes.

3) Canary harness (CI/CD job template)
   - Purpose: promote changes in small increments (per-region / per-tenant subset) using a staircase canary pattern.
   - Integrations: Buildkite pipeline that runs TF plan/apply in canary mode with smoke tests.

4) Telemetry and billing hooks
   - The module writes an slo_metadata_tag (JSON string) into resource tags and emits a CloudWatch/Stackdriver metric "tenant.quota.enforced" with dimensions {tenant_id, region, policy_id}.

Module interface and example

Table: module variables and short descriptions

- variables: (expressed here as a human table)
  - tenant_id: string - unique tenant identifier (required)
  - quota_group: string - egress|gpu_compute|concurrent_sessions (required)
  - hard_limit: number - absolute limit that must not be exceeded (optional - provider dependent)
  - soft_limit: number - threshold to trigger alerts and throttling (optional)
  - enforcement_mode: string - block|throttle|monitor (default: monitor)
  - canary_percent: number - percent of tenant traffic/capacity to apply change to during canary (default: 0)
  - regions: list(string) - regions to apply enforcement in (default: [primary region])
  - billing_tag_override: string - optional freeform string for billing pipelines

Example snippet (Terraform usage):

provider "aws" { region = "us-west-2" }

module "tenant_quota_shim" {
  source = "git::ssh://git@github.com/redwood-infra/tf-modules.git//quota-enforcement-shim?ref=v1.2.0"
  tenant_id = "tenant-42"
  quota_group = "egress"
  soft_limit = 1000 // Mbps
  hard_limit = 2000 // Mbps
  enforcement_mode = "throttle"
  canary_percent = 10
  regions = ["us-west-2", "us-east-1"]
  billing_tag_override = "team-redwood-enterprise"
}

Behavioral policy matrix

- enforcement_mode = monitor -> write slo_metadata_tag, create metric, do not modify cloud provider quotas.
- enforcement_mode = throttle -> attach rate-limiting sidecar or quota policy when supported (e.g., Cloud NAT throttle rules / GCP egress gateway config).
- enforcement_mode = block -> attach deny policies where provider supports explicit denies (used only for extreme enforcement and requires legal & security approval).

Canary promotion workflow (step-by-step)

1) Developer opens PR bumping module usage and changes soft_limit/hard_limit/canary_percent.
2) CI runs unit tests on module (terrafmt, tflint, terraform validate) and an automated static policy check (OPA).
3) Buildkite pipeline: run TF plan in canary mode for a small tenant cohort and create a plan preview artifact accessible to SRE.
4) Smoke tests: run a 10-minute traffic replay against the canary region and verify: telemetry emitting, no unexpected 403/500 errors, slowdowns within SLO.
5) If smoke tests pass and telemetry indicates < 0.5% error delta, promote to additional cohorts using a staircase (10% -> 25% -> 50% -> 100%) with manual approval gates at each step.
6) Rollback: if any step fails, pipeline runs an automated TF apply reversing the change and creates an incident with pre-populated diagnostics.

Testing and CI requirements

- Mandatory checks for every PR using the module:
  - terraform validate & plan (diff must be explainable)
  - tflint & terratest suite (unit tests for provider interactions mocked)
  - OPA policies: ensure no module can create global-blocking deny without security tag
  - Integration test: ephemeral tenant created in a sandbox account, module applied, policy adapter run, telemetry validated

Operational runbook (oncall steps)

1) Alert: "tenant.quota.enforced.failed" -> primary oncall (infra) paged.
2) Triage: review last TF plan artifact, enforcement resource IDs, and provider API error codes.
3) Quick remediation: if enforcement caused unexpected blocking, set module enforcement_mode=monitor in the TF workspace and apply rollback.
4) Reconcile billing: trigger the billing export job to reindex slo_metadata_tag values and run the reconciliation script with the affected tenant_id.

SLOs and alert thresholds (consumable by monitoring)

- Enforcement success rate: 99.9% of TF applies that include quota-enforcement-shim should complete without provider error. Alert on < 99.0% over 1 hour.
- Canary stability: canary cohort must show < 1% increase in 5xx errors and < 5% tail latency increase during promotion window. Alert and auto-rollback otherwise.
- Telemetry emission: every enforcement apply must emit at least one metric point within 5 minutes. Alert if missing for > 10 minutes.

Billing reconciliation contract

- slo_metadata_tag contents (JSON string): {tenant_id, quota_group, enforcement_mode, applied_at_iso, module_version, policy_id}
- Billing pipeline job consumes slo_metadata_tag and creates billing rows. If enforcement fails mid-apply, module must write a "pending":true flag. Billing job ignores pending entries and notifies billing-ops channel.

Migration notes for legacy tenant-onboarding

- Legacy onboarding scripts must be updated to include the module in their TF root. For tenants where legacy automation cannot be updated immediately, use the policy adapter in read-only mode to generate reconciliation reports and gradually adopt enforcement.

Backout and disaster recovery

- TF rollback is the primary backout mechanism. The module provides an automated revert plan that targets only the enforcement resources added by the module.
- If provider APIs are unresponsive, run the offline reconciliation script to generate a safe-state plan that sets enforcement_mode=monitor for all affected tenants and applies it once the API recovers.

Telemetry and dashboards

- Dashboard widgets: enforcement success rate, canary error delta, enforcement latency (time between TF apply finish and metric emission), billing import lag.
- Saved queries: last 24h failed applies by region, list of tenant_ids with pending flag > 10m.

Risks and mitigations

- Risk: provider quota APIs are inconsistent across regions. Mitigation: module contains provider adapters and defaults to monitor mode for unsupported regions.
- Risk: mis-tagging could cause billing misattribution. Mitigation: strict tf tests verify slo_metadata_tag schema before apply.

Open design items

- Standardizing canonical metric names across clouds (work in progress with telemetry team).
- Formal SLA with billing team for reconciliation time window (proposal: 2 hours).
- Auto-approval logic for low-risk promotions (future work).

Appendix: CLI snippets and troubleshooting

- Create a canary plan locally:
  TF_WORKSPACE=staging 
  terraform init 
  terraform plan -var='tenant_id=tenant-42' -var='canary_percent=10' -out=canary.tfplan
\- Apply the plan:
  terraform apply canary.tfplan

- Re-run reconciliation lambda manually (AWS):
  aws lambda invoke --function-name quota-policy-adapter --payload '{"tenant_id":"tenant-42"}' /tmp/output.json

- Quick check: verify slo tag is present on enforcement resource:
  aws resourcegroupstaggingapi get-resources --tag-filters Key=slo_metadata_tag,Values="tenant-42"
