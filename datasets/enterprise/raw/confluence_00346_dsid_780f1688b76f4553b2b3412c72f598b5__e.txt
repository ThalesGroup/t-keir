elastic-tenant-quarantine-and-throttle-procedure

Summary

This playbook defines detection, containment, and remediation steps for noisy or misbehaving tenants that threaten cluster stability or SLOs. The procedure covers automatic and manual quarantine flows, throttling profiles, verification steps, and postmortem expectations. It is intended for Eng-SRE on-call and platform engineers who operate the runtime-router, edge-proxy, and autoscaling controllers.

Why this exists

As Redwood scales, a single tenant (customer, internal team, or integration test harness) can cause disproportionate resource consumption (GPU saturation, massive KV cache pressure, or telemetry storms). The goal is to contain impact quickly, restore service-level SLOs for other tenants, and provide reproducible remediation and follow-up.

Scope and applicability

- Applies to Hosted API and Dedicated pools where multi-tenant eviction/soft-quota is enabled.
- Not intended for air-gapped Private deployments — see eng-private-deployments runbooks for localized controls.
- Covers both burst and steady-state noisy neighbors.

Detection signals (primary)

1. p95 inference latency for runtime-router > configured latency budget AND error rate spike for a tenant (>= 5x baseline in 5m).
2. GPU util (per-pool) > 85% sustained for 10m with a single tenant accounting for >50% of requests.
3. KV cache churn > 1.5x normal eviction rate OR prefix miss ratio > 30% for a tenant's keys.
4. Edge-proxy 5xx rate >= 0.5% absolute or 5x baseline for 3m.
5. Telemetry ingestion backlog increases > 2x for tenant metrics or trace volume (indicates noisy sampling).

Detection signals (secondary)

- Rate limiter tripping frequently for a client token.
- Excessive streaming open connections per tenant (> 200).

Thresholds and containment decision matrix

| Signal | Alert threshold | Initial action | Escalation threshold |
|---|---:|---|---:|
| p95 latency (runtime-router) | > 400ms for 5m | soft-throttle 50% | > 800ms or sustained 15m -> quarantine |
| GPU pool util (per-GPU) | > 85% sustained 10m | shed low-priority queues | > 95% sustained 5m -> quarantine |
| KV cache eviction rate | > 1.5x baseline | increase cache-ttl weighting for high-hits | > 3x -> quarantine |
| 5xx rate (edge-proxy) | >= 0.5% for 3m | apply 429-based backpressure | >= 2% or >10m -> quarantine |

Definitions

- Soft-throttle: a per-tenant token-based rate limit and early drop that reduces throughput but allows best-effort traffic through. Implemented via edge-proxy token-bucket adjustments.
- Quarantine: a higher-confidence containment that moves tenant to a restricted policy (aggressive rate limits, disallow long-running streams, route to lower-fidelity model variants). Quarantine can be automatic or manual.

Automated flow (recommended)

1. Alert fires on the detection rule in PagerDuty (SRE-runbook alert). The alert page includes tenant-id, top endpoints, example requests, and recent telemetry link.
2. Automated controller evaluates runbook rules (runtime-guardian) and computes containment action: either apply soft-throttle profile or quarantine profile.
3. If soft-throttle selected: runtime-guardian issues config to edge-proxy with a JSON patch to tenant-rate-limits. Sample CLI: 

rctl tenant throttle --tenant-id tenant_1234 --mode soft --ingress-rps 120 --burst 200

4. If quarantine selected: runtime-guardian triggers a higher-priority policy and notifies on-call with pre-populated remediation checklist. Quarantine command (manual approval required for non-critical tenants):

rctl tenant quarantine --tenant-id tenant_1234 --apply-policy quarantine-2026-01 --reason "gpu-saturation"

Manual flow (when automation is disabled or ambiguous)

1. Triage the alert: confirm tenant, inspect traces, check recent deploys, load tests, and internal jobs. Primary dashboards: runtime-router/top-tenants, gpu-fleet/pool-util, kv-cache/tenant-breakdown.
2. If tenant is internal or test harness, contact owning team and apply temporary shutdown via service token rotation or disable client key.
3. For production tenants, engage account exec only after containment — do not delay containment for notification.

Containment profiles (examples)

- soft-throttle-profile-v1: ingress-rps = tenant_baseline * 1.2, burst = 200, priority = normal, stream-max-duration = 60s.
- restricted-quarantine-v1: ingress-rps = 50, burst = 20, priority = low, stream-max-duration = 10s, route-model = small-fallback-v1, disallow tools/function-calls.
- critical-cold-cut: immediate connection drain + 0 rps (use only for proven hostile or runaway billing risk).

Configuration table

| Config key | Location | Default | Notes |
|---|---|---|---|
| tenant-rate-limit.rps | edge-proxy config | 100 | Per-tenant default; adjusted by runtime-guardian |
| tenant-burst | edge-proxy config | 300 | Applied as token-bucket capacity |
| quarantine-policy | runtime-config-store (/configs/quarantine) | n/a | JSON policy documents referenced by runtime-guardian |
| telemetry-snapshot-window | telemetry-pipeline | 5m | Window used for moving averages in alerts |

Step-by-step containment procedure (on-call)

1. Acknowledge PagerDuty alert and open the SRE incident channel.
2. Verify the tenant-id and the signal(s). Capture the last 10 requests (request-ids) and attach to the incident.
3. Try soft-throttle first unless GPU util > 95% or 5xx >2% (see matrix). Apply: 

rctl tenant throttle --tenant-id <id> --mode soft --ingress-rps <calc> --burst <calc> 

4. Monitor for 5 minutes. Verify p95 latency improvement and drop in cross-tenant impact. If no improvement or tenant is bypassing throttles, escalate to quarantine. 

5. Quarantine steps (manual approval required unless automated rule matched):
  a. Apply quarantine policy: rctl tenant quarantine --tenant-id <id> --apply-policy restricted-quarantine-v1 --ticket <pd-incident-id>
  b. Rotate tenant token if abuse suspected: rctl tenant rotate-token --tenant-id <id> --force 
  c. If streams persist, forcibly close long connections via edge-proxy: kubectl exec -n edge-proxy edge-proxy-0 -- /bin/close-conns --tenant <id>

6. Notify account and product teams after containment. Provide observed metrics and applied policy.

Rollback and recovery

- Recovery criteria: p95 latency < baseline + 20% for 15m AND GPU pool util < 70% for 15m AND 5xx < 0.2% for 15m.
- To rollback: incrementally restore rate limits over a 30 minute window: 

rctl tenant throttle --tenant-id <id> --mode blended --ingress-rps <50% of previous> --burst <half>
(wait 10m) then increase to 75%, etc.

- Document applied changes in the incident ticket and schedule a post-incident review if quarantine lasted > 10m or if billing exposure occurred.

Testing and validation

- Canary tests: apply quarantine policy to a synthetic tenant in staging and validate that the policy limits remove load from pool without affecting other tenants.
- Chaos test: run a scheduled SRE game-day that simulates a tenant with high streaming connections and verify monitoring/automations.

Metrics and SLOs to observe

- Cross-tenant p95 latency (runtime-router): target < 250ms; alert if > 400ms.
- GPU pool saturation: alert if per-GPU util > 85% for 10m.
- Telemetry backlog: no more than 2x baseline for more than 10m.
- Quarantine false-positive rate: target < 1% of quarantines per quarter (measured by post-incident rollbacks where tenant had no abnormal behavior).

Ownership and escalation

- Primary owner: Eng-SRE (sre-team@redwood.com).
- Secondary owner: Platform (platform-ops@redwood.com).
- On-call escalation: PagerDuty -> Platform lead -> VP Eng (if customer-impacting and > 60m unresolved).

Communication templates

- Customer notification (template): 

"Redwood Inference has detected abnormal traffic from your integration (tenant-id: <id>) and has applied temporary rate limits to protect service stability. We are investigating and will restore normal traffic when safe. Contact: support@redwood.com."

Post-incident review requirements

- Owners must create a short incident summary within 48 hours with: timeline of actions, telemetry snapshots, root cause (if identified), remediation plan, and any billing adjustments.
- If removal of a customer key or token rotation occurred, include audit log references.

Security and compliance notes

- Quarantine/rotation actions are audited in audit-logging/tenants with correlated request IDs and actor.
- For regulated customers, coordinate with Security prior to any token rotation that may cause data deletion or loss of audit continuity.
