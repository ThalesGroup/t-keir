streaming-fidelity-negotiation-prd-2029-07-12

Overview
========

This PRD defines Streaming Fidelity Negotiation: a product capability for dynamically negotiating output fidelity versus latency/cost when serving streaming generation requests to client applications. The feature enables clients and the Redwood serving plane to agree on per-request fidelity levels (e.g., full-fidelity, low-fidelity draft, token-skim) at request time and to gracefully degrade or improve fidelity mid-stream based on real-time capacity, burst policies, and tenant SLOs.

Background and motivation
-------------------------

Customers increasingly use streaming generations in low-latency experiences (chat, code assistance, IDE autocompletion). However, fixed-fidelity models either cause high per-token cost or miss latency targets. Current options (model switching, pre-quantized variants) are coarse and happen at request boundaries. Streaming Fidelity Negotiation reduces user-facing latency and cost by:

- Allowing client and server to express acceptable fidelity ranges per request.
- Enabling mid-stream fidelity transitions when resource signals or QoS policies require it.
- Preserving a clear API contract so client SDKs can render partial outputs appropriately.

Objectives (must-have)
----------------------

1. Provide a stable, documented API for clients to request a fidelity profile when calling the streaming generation endpoint.
2. Enable the server to signal fidelity transitions mid-stream with minimal protocol changes.
3. Ensure fidelity transitions are observable in Console (per-request fidelity timeline, token-level cost estimate).
4. Maintain SLOs: median tail latency (p95) for low-fidelity requests must remain <= 150ms per token for typical short-turn workloads.

Non-goals
---------

- Automatic rewriting of prompts to match fidelity (clients must opt-in or provide fallback renderers).
- Changing model semantics beyond predicted quality trade-offs (no unsupervised content transformations).

Primary user personas and user stories
------------------------------------

- Product engineers (web/mobile)
  - "As a frontend engineer, I want to request a draft (low-fidelity) stream for quick previews and then request refinement only when the user commits, so initial latency is minimal."

- Platform/ML infra
  - "As an infra engineer, I want the serving runtime to downshift fidelity under heavy load to preserve global latency SLOs and to record the events for billing reconciliation."

- Customer success / enterprise admins
  - "As an enterprise admin, I want an SLO-driven policy that prevents fidelity degradation below a contractual floor for high-tier customers."

Functional requirements
-----------------------

Req-F1: Fidelity profile in API
- Description: Streaming generation API must accept a fidelity_profile object with the following attributes: {min_fidelity, target_fidelity, max_latency_budget_ms, allow_midstream_transition: bool}.
- Priority: P0
- Owner: API and SDK teams

Req-F2: Server-initiated fidelity change events
- Description: Server shall emit a standardized mid-stream event (EVENT:FIDELITY_CHANGE) with fields {previous_fidelity, new_fidelity, reason_code, effective_token_index}.
- Priority: P0
- Owner: Serving runtime team

Req-F3: Client SDK support and rendering guidance
- Description: Official JavaScript and Python SDKs must expose hooks for fidelity events and provide UI guidance for mid-stream render transitions.
- Priority: P1
- Owner: Developer Experience

Req-F4: Policy engine integration
- Description: Policy engine must be able to evaluate per-request signals (tenant tier, lane, current cluster CPU/GPU utilization, queued tokens) and decide to request/signal fidelity transitions.
- Priority: P0
- Owner: Routing & Policy

Req-F5: Billing and observability flags
- Description: All streams must include token-level fidelity metadata so Console and billing can attribute cost. Metadata: fidelity_label, effective_variant_id, transition_history.
- Priority: P0
- Owner: Console & Billing

Non-functional requirements
---------------------------

- NF1: Latency impact: p95 token latency for low-fidelity requests should not exceed 1.5x baseline p95 for equivalent short turns.
- NF2: Transition overhead: Emitting a fidelity change event must add <= 5ms median overhead to the streaming pipeline.
- NF3: Backwards compatibility: If a client does not include fidelity_profile, behavior defaults to target_fidelity = full-fidelity (current behavior).

API contract (summary)
---------------------

Endpoint: POST /v1/streams/generate
Request body (JSON):
```json
{
  "model": "redwood-3b-stream",
  "prompt": "Summarize the quarterly goals...",
  "stream": true,
  "fidelity_profile": {
    "min_fidelity": "draft",
    "target_fidelity": "balanced",
    "max_latency_budget_ms": 300,
    "allow_midstream_transition": true
  }
}
```

Server event sequence (example wire events):
- DATA: token chunk (fidelity_label: draft)
- EVENT:FIDELITY_CHANGE {"previous_fidelity":"draft","new_fidelity":"balanced","reason_code":"CAPACITY_PRESSURE","effective_token_index":12}
- DATA: token chunk (fidelity_label: balanced)

Fidelity taxonomy (example labels)
- draft — lowest compute path, lighter sampling, more aggressive top-k/top-p truncation.
- balanced — default production tradeoff for cost/quality.
- full — highest fidelity (longer context, temperature adjustments, ensemble/decoder variants).

SLOs, metrics and dashboards
----------------------------

Minimum metrics to implement prior to rollout:
- Median token latency by fidelity (per model): gauge
- p95 token latency by fidelity: alert on > 1.5x baseline
- Fraction of streams that experienced mid-stream fidelity transition: gauge
- Fidelity transition reasons breakdown (capacity, policy, tenant request): timeseries
- Cost delta per request attributed to fidelity (estimated per-token cost): histogram

Suggested SLOs:
- p95 token latency for balanced streams <= 200ms
- p95 token latency for draft streams <= 150ms
- Fidelity-transition event delivery success >= 99.9%

Rollout plan and feature gates
------------------------------

1. Canary (internal) — feature enabled for Redwood internal tenants and 2 pilot customers. Duration: 2 weeks.
2. Pilot customers — onboard 5-10 customers (customer success and solutions engineering manage). Duration: 4 weeks.
3. Gradual GA — traffic ramp in five steps (5%, 20%, 50%, 80%, 100%) with automated rollback on SLO/regression triggers.

Gate checks before each ramp:
- No fidelity-transition-related errors > 0.1% of streams.
- Observability metrics within expected ranges for p95 latency.
- Billing attribution present for all pilot streams.

Compatibility and migration notes
--------------------------------

- Backwards compatibility: clients not specifying fidelity_profile will see unchanged behavior.
- SDK upgrade: new SDK versions will expose fidelity hooks; server will accept legacy clients.

Operational playbook (how to investigate a migration-induced fidelity drop)
--------------------------------------------------------------------------

1. Identify affected tenant(s) via Console: filter by fidelity_label and increased error/latency.
2. Check event logs for EVENT:FIDELITY_CHANGE reason_code. Common codes: CAPACITY_PRESSURE, POLICY_ENFORCED, TENANT_FLOOR_OVERRIDE.
3. If CAPACITY_PRESSURE is frequent: check cluster utilization dashboards, scale capacity or adjust batching parameters.
4. If POLICY_ENFORCED: review policy engine logs and recent rule changes.
5. Reproduce in staging: send synthetic streams with fidelity_profile and observe transitions.

Open questions and tradeoffs
---------------------------

- Q1: Should fidelity profiles be expressed as continuous budgets (e.g., scaled float) rather than categorical labels? Tradeoff: finer-grained control vs. complexity for SDKs and observability.
- Q2: How do fidelity transitions interact with function/tool calling and structured outputs? Need to ensure consistency when switching mid-stream.
- Q3: Are there model classes where mid-stream transition is not safe (long-running internal state)? We need to catalog model compatibility.
