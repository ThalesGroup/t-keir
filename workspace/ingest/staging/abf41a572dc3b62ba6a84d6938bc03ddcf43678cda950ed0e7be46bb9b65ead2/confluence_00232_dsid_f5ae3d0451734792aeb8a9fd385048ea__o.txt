Overview

This runbook defines the operational handshake and validator catalog used during private (VPC / on‑prem) deployments. It is intended for Operator/Field teams, Solutions Engineering, and SREs who perform acceptance, day‑2 validation, and controlled cutovers to production traffic. The goal is to provide a single, repeatable validation checklist that: (1) verifies networking, security and runtime invariants; (2) exercises the runtime and model swap paths with canary traffic; and (3) provides clear rollback triggers and remediation guidance.

Scope

- Applies to Redwood Private deployments: VPC-hosted control plane with customer-managed data plane, and air‑gapped on‑prem appliances.
- Covers pre-install validation, post-install smoke tests, canary traffic plan, performance regression checks, and rollback criteria.
- Does NOT replace security compliance evidence artifacts (see customer-requirements library) but references the minimum evidence required for acceptance.

Preflight / Prerequisites

Before running validators, confirm: 

- Customer network ACLs and BGP/VPC routes are applied per the commissioned design.
- KMS/HSM endpoints reachable from operator VLANs and test service account has encrypt/decrypt privileges.
- Minimum hardware + firmware baseline validated against the compatibility matrix (GPU driver, CUDA/ROCm version, BIOS/firmware).
- Time sync (NTP/PTP) drift < 500ms across control and data nodes.
- Inventory snapshot (serials, NIC MACs, disk UUIDs) uploaded to ticketing system for forensic traceability.

Validator Catalog (operator-friendly table)

| Check | Command / Tool | Expected Result | Remediation |
|---|---|---|---|
| Network path to control-plane API | curl -k https://{{control_plane_ip}}/healthz | 200 + JSON {"status":"ok"} | Validate route tables, firewall policy, and proxy ACLs; run traceroute and tcpdump |
| KMS envelope encrypt/decrypt | redwood-kms-tool verify --endpoint {{kms}} --key-id kv-1 | encrypt/decrypt roundtrip < 500ms and success code | Check KMS IAM, VPC endpoints, DNS, and customer firewall; fallback: use ledger-encrypted keystore for acceptance |
| GPU driver / CUDA compatibility | dpkg -l | nvidia-driver >= 525 and CUDA 12.x OR rocm >= 6.x | Reinstall certified driver image; isolate node from pool and re-run burnin |
| Image signature verification | cosign verify --key public.pem image.tar.gz | signature valid, provenance matches release tag | Re-download signed image, verify root of trust; if persistent, escalate to supply-chain security |
| Model artifact checksum / provenance | sha256sum model.tar.gz && cat provenance.json | checksums match release manifest; provenance contains signed build id | Failure -> quarantine artifact and fetch canonical artifact from model registry |
| KV cache warmup smoke | curl -X POST {{runtime}}/v1/cache/warm -d '{"prompt":"hello"}' | cache hit rate increase of >10% in 5m window | If miss-rate persists, verify model-to-cache mapping and network between workers |
| Cold start latency test | pb-runner --seq 2048 --qps 1 | p50 < 150ms, p95 < 400ms (baseline) | If regressions, collect runtime profile and compare to baseline; may require rollback of runtime build |
| TLS certificate chain validation | openssl s_client -connect {{endpoint}}:443 -servername host | full chain validated, no SHA1 intermediates | Replace cert, validate intermediates; check OCSP/CRL reachability |
| Audit log forwarding | tail -n 100 /var/log/redwood/audit.log | recent entries for install actions, no permission failures | Fix agent config and restart collector; ensure log retention policy met |

Acceptance Criteria (binary pass/fail per section)

- Critical validators (network, KMS, image signature) must pass 100%.
- Performance validators (latency/throughput) must be within defined guardrails relative to the customer profile:
  - Latency guardrails: p50 <= 120ms, p95 <= 350ms under canary load (see Performance Baseline).
  - Throughput: sustained QPS within 10% of committed throughput for dedicated pools under synthetic profile.
- Canaries: at least 30 minutes of canary traffic with < 0.5% error rate and no steady increase in 99th percentile latency.
- Security: KMS envelope rotation validated end-to-end and audit events present.

Performance Baseline (example values, tune per-customer)

- Canary profile: 10 concurrent sessions; 1.5 RPS per session; sequence length distribution 512/2048/4096 token buckets.
- Expected results for medium model (16GB KV per replica):
  - Steady-state throughput: 45 req/s per replica
  - Token generation latency: p50 90ms, p95 260ms (generator only)

Runbook: Field Validation Procedure (numbered)

1. Preflight: Review installation ticket and confirm prerequisites checklist (network, KMS reachable, inventory uploaded).
2. Smoke install: Deploy runtime image to a single validation node in the tenant pool. Run image-signature + driver + cert validators.
3. Control-plane handshake: Execute control-plane API health, and create a temporary test-tenant with restricted quota.
4. Artifact validation: Pull the model artifact and verify checksum/provenance.
5. Warmup: Trigger KV-cache warmup and confirm cache hit-rate and memory usage remain within expected bounds.
6. Canary start: Route 1% of production traffic (or synthetic canary profile defined above) to the validation tenant. Monitor for 30m.
7. Performance sweep: Run the cold-start latency and throughput synthetic tests; collect perf profiles and compare to golden baselines.
8. Security checks: Validate KMS key usage logs, certificate chain verification, and audit log forwarding.
9. Acceptance decision: If all critical validators and canary performance pass, schedule incremental traffic ramp per the traffic migration matrix.
10. Post-cutover: After reaching 100% traffic, run a second sweep of performance validators for 2 hours to detect latent regressions.

Rollback Triggers (automated + operator-observed)

- Error rate > 2% sustained for 10 minutes on production routes originating from the new deployment.
- 99th percentile latency regression > 30% compared to baseline for > 5 minutes.
- KV-cache corruption or state divergence detected (inconsistent model responses across replicas).
- Failures in KMS envelope operations or certificate chain validity errors.

Rollback Procedure (fast, auditable)

1. Initiate Safemode: operator sets tenant to safemode which pauses new model swaps: `redwood-ctl tenant update --id {{tenant}} --safemode=true`.
2. Traffic re-route: shift traffic back to previous revision via control-plane: `redwood-ctl traffic-shift --from={{new}} --to={{prev}} --weight=100` (automated orchestration preferred).
3. Verify: confirm error rate returns to baseline and latency stabilizes within 10 minutes. Collect diagnostic bundles `redwood-ctl collect-diagnostics --tenant {{tenant}} --since "-15m"`.
4. Snapshot & Quarantine: snapshot runtime state and quarantine artifact versions for forensic analysis.
5. Postmortem initiate: create incident with labels `private-deploy-regression` and assign to runtime lead.

Remediation Playbook Examples

- Networking regression: If packet loss or MTU mismatch is detected, isolate node, confirm jumbo frame settings and BGP adjacencies, then reintroduce to pool after validation.
- KMS intermittent: fallback to cached symmetric wrap with strict TTL; escalate to cryptography team if KMS SLA cannot be met for 30 minutes.
- Performance regression tied to driver mismatch: pause scheduling on heterogeneous GPU node type and trigger immutable rollback to previous image.

Telemetry & Alerts (minimum metrics to emit)

- metrics.runtime.request_count (per model, per route)
- metrics.runtime.error_count (per error class) – Alert: error_rate > 1% sustained 5m (warning), > 2% 10m (critical)
- metrics.runtime.latency_ms (p50/p90/p95/p99) – Alert: p99 > baseline * 1.3 (critical)
- metrics.kvcache.hit_rate – Alert: hit_rate drop > 20% relative to baseline during warmup window
- audit.kms.operation – Alert: KMS failures > 5 in 10m

Evidence & Reporting (for Customer Acceptance)

- Upload the following artifacts to the deployment ticket before handoff:
  - inventory.csv (hardware identifiers)
  - topology.json (VPC/BGP routes snapshot)
  - diagnostic bundle tarball from the validation node
  - signed model provenance and checksums
  - canary perf report (pdf) with latency histograms and QPS timeline

CLI & Example Commands

- Health check: `curl -sS https://{{control_plane_ip}}/healthz | jq`
- Canaries: `redwood-ctl canary start --tenant {{tenant}} --profile canary-small --duration 30m`
- Collect diagnostics: `redwood-ctl collect-diagnostics --tenant {{tenant}} --out /tmp/diag.tar.gz`
