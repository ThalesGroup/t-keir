Preemption-aware Batch Slicing: Spec and Operational Playbook

This document defines the design and operational guidance for "preemption-aware batch slicing" — a kernel-scheduler-adjacent feature that slices large inference batches into smaller execution windows aligned to expected preemption boundaries and GPU occupancy windows. The goal is to reduce tail-latency spikes caused by mid-kernel preemption, long-running kernels blocking higher-priority work, and KV-cache warmup penalties while preserving throughput and unit-cost efficiency.
Large requests and long-sequence generation can produce kernel executions that exceed preemption windows on shared GPU pools. When preemption occurs mid-kernel, it can cause: lost progress for KV cache priming, long tail latencies for higher-priority requests, and noisy GPU utilization signals that complicate autoscaling. Preemption-aware batch slicing inserts low-overhead slice boundaries and scheduling hints so the kernel mapper and dispatcher can make better trade-offs between latency and efficiency.
- Applies to: runtime dispatcher + kernel mapper + per-shard executor on heterogeneous GPU fleets (hosted and Dedicated modes).
- Not in scope: model-architecture-level sequence truncation, offline compilation changes, or business-layer client batching policies.
- Reduce 95th/99th percentile latency regressions caused by preemption during long kernels.
- Minimize KV-cache thrash from repeated long preemptions.
- Preserve (or gracefully trade) throughput for improved latency predictability.
- Provide knobs for operations to tune behavior per service / customer tier.
- Non-invasive: default behavior should be conservative (opt-in per route or model bundle).
- Scheduler hints: expose slice boundary hints to kernel mapper and GPU dispatcher rather than forcing a single global policy.
- Cheap slicing: slices add minimal overhead (<2–4% per-token CPU overhead in microbenchmarks) and leverage existing continuous-batching state (KV cache re-use across slices).
- Observability-first: emit slice metrics (counts, preemptions, latency per slice, warmup penalty) for actionable alerts.
1. Request classification: the dispatcher categorizes incoming requests by expected kernel duration (microbenchmark model estimate + runtime sampler). If estimated kernel > slice_threshold_ms, candidate for slicing.
2. Slice generation: generate a sequence of slice descriptors. Each slice descriptor contains: slice_token_budget, expected_execution_ms, priority_hint, and cache_warmup (boolean).
3. Execution model: slices are enqueued to shard executors. The kernel mapper may coalesce slices from different requests if compatibility and priority allow, subject to slice size upper bounds.
4. Preemption and recovery: if a slice is preempted mid-execution, runtime records a "preempted_slice" event and restarts the slice respecting cache_warmup. Recovery strategy prefers resuming from last KV checkpoint if supported; otherwise slice is retried and warmup penalty is recorded.
5. Completion semantics: final response is reassembled from slice outputs. The runtime ensures deterministic ordering and idempotency of slice execution.
- KV cache: slices should be sized to preserve meaningful KV reuse. The runtime tags warmup slices to avoid evicting critical entries.
- Adaptive kernel mapper: uses slice.expected_execution_ms to choose different kernel implementations (fast-preemptible kernels vs high-throughput kernels).
- Priority and credit accounting: slice_priority is charged against the original request budget and interacts with kernel-credit-accounting and fairness systems.
- Autoscaler: emits slice-level throughput and preemption rates to autoscaler to help scaling decisions (see metrics section).
Parameter | Default | Description
slice.enabled | false | Master kill-switch. Must be enabled per route or model via config blob.
slice.threshold_ms | "120" | Estimate threshold above which requests become slicing candidates (ms).
slice.max_tokens | "2048" | Maximum token budget for a single slice; influences kernel execution time.
slice.min_tokens | "16" | Minimum slice token size to avoid excessive overhead on tiny requests.
slice.timeout_ms | "200" | Wall-clock timeout to cut a running slice for fairness and preemption sensitivity.
slice.priority_policy | "inherit" | inherit | explicit-priority | preemptible-first — how a slice chooses priority.
slice.warmup_policy | "sticky" | sticky | fresh — whether slices assume prior KV warmup is valid.
slice.coalesce_window_ms | "10" | Micro-window where compatible slices can be coalesced by the dispatcher.
slice.metrics_sampling | "1.0" | Fraction of slices for detailed telemetry (0.0–1.0).

1) High preempted slice rate
- Trigger: increase in runtime_slice_preempted_total over 5m such that rate > 0.5% of runtime_slice_total AND p95 latency for route increases > 30% relative to baseline.
- Severity: P2
- Action: follow "slice preemption triage" runbook (below).

2) Warmup penalty regression
- Trigger: runtime_slice_warmup_penalty_ms_avg > 30ms for 10m for a paid-customer route.
- Severity: P3
- Action: Consider increasing slice.min_tokens, enabling sticky warmup, or moving customer to dedicated pool if persistent.
1. Identify affected routes
- Query: top 5 routes by runtime_slice_preempted_total in last 30m and correlated p95 latency.
2. Verify cluster-level preemption activity
- Inspect kube/gpu-proxy preemption events and cloud provider preemption logs.
3. Inspect slice metrics
- Check slice_estimation_error_ms; if high, the estimator is underpredicting kernel duration.
4. Interim mitigations (in order):
  a) Reduce slice.max_tokens for the route to favor smaller slices.
  b) Increase slice.coalesce_window_ms to allow the dispatcher to recombine smaller slices into more efficient kernels when preemption risk drops.
  c) Switch priority_policy to "explicit-priority" for the route to pin critical slices as non-preemptible during peak.
  d) If persistent and customer-critical: migrate the route to Dedicated or a higher QoS node pool.
5. Postmortem actions
- Add representative traces to the runtime profiling harness and schedule a microbenchmark to reproduce estimator error.
- If estimator logic is faulty, file a kernel-mapper improvement ADR with evidence.

- Latency-first, interactive routes: slice.threshold_ms=80, slice.max_tokens=256, slice.coalesce_window_ms=5, slice.priority_policy=explicit-priority.
- Throughput-first batch routes: slice.enabled=false (unless preemption observed), or slice.max_tokens=4096, coalesce_window_ms=20, warmup_policy=fresh.
- Mixed: enable slicing but set slice.metrics_sampling=0.2 and experiment with slice.min_tokens=64.
- Small-to-medium generation (avg 512 tokens): enabling preemption-aware slicing with conservative defaults reduced p99 from 1.8s to 1.2s on shared pools with occasional preemption, at a CPU overhead of ~2.9% and GPU utilization delta of −1.2%.
- Extreme long sequences (avg 4096 tokens): slicing reduced mean recovery cost after preemption by 46% due to smaller warmup windows and more KV checkpoint opportunities.
- Supported models: All transformer-based models that expose token-budgetable execution pathways (most catalog models). Models that rely on monolithic fused kernels with no checkpointing are "best-effort".
- Hardware: Works on Ampere/Blackwell class GPUs. On very old drivers where preemption is coarse, increase slice.timeout_ms to avoid thrash.
- Determinism: slice boundaries must not change model output deterministic ordering. The reassembly step uses sequence indices and deterministic padding.
- Side channels: slicing may produce more frequent kernel scheduling signals. Ensure no customer data is leaked via slice-level telemetry; redact identifiers and only emit per-route aggregates.
1. Feature toggle (master off): enable slice.enabled at 0.0 globally.
2. Canary: enable per-route for internal "sandbox/latency" routes (5% of fleet) for 2 weeks, sample metrics.
3. Pilot: open opt-in for 3 enterprise customers with known preemption exposure; collect feedback and perf traces.
4. Gradual ramp: enable for low-latency tier routes across Hosted pools with automated rollback on SLO regression.
5. GA: document in public runbook and enable for Dedicated with default enabled for high-density pools.
- p99 latency regression > 15% sustained for 30m on a route after enabling.
- runtime_slice_preempted_total increases by >2x without corresponding reduction in p95 latency.
- Estimator quality: inaccurate kernel-duration estimator can cause harmful slicing. Follow-up action: invest in sequence-length-aware microbenchmarks and model profiling hooks.
- KV checkpoint overhead: repeated checkpoint/resume may uncover model-internal invariants. Follow-up: test with representation-pruned models.
- Hardware cornercases: preemption semantics differ across GPUs; need driver-specific adaptors.
