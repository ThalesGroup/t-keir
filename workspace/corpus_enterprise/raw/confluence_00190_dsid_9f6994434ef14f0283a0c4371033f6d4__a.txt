Adaptive cohort probing and handoff runbook

Summary

This runbook describes the adaptive cohort probing and handoff process used by the Redwood serving runtime to detect per-cohort fidelity degradation, orchestrate kernel handoffs, and safely probe changes under production traffic. It defines telemetry signals, thresholds, automated decision steps, and operator procedures for investigation and rollback. The goal is to allow dynamic handoffs (e.g., between quantized kernel A and fallback kernel B) while preserving SLOs and minimizing cost impact.

Scope

- Applies to multi-tenant inference pools running heterogeneous kernels (FP16, 8-bit quantized, sparse-aware kernels) on GPU clusters.
- Covers automated probing, graceful handoff, telemetry required, manual intervention steps, and validation/benchmarking checklist.
- Excludes model packaging and build processes (see model-onboarding docs).

Audience

- Oncall SREs and runtime engineers responsible for scheduler and kernel rollouts.
- Benchmarking and profiling engineers validating kernel variants.

Background and motivation

Redwood supports multiple kernel implementations with different performance/cost/quality characteristics. When the scheduler considers swapping a cohort to a new kernel variant (for cost saving or fallback), naive switchovers can introduce regressions (tail latency spikes, token errors) that impact customer SLAs. Adaptive probing lets us sample production traffic for a small and controlled cohort, gather fidelity and latency signals, and make a conservative decision to expand, hold, or rollback.

Key terminology

- Cohort: A logical group of requests defined by model, route, or customer label.
- Probe window: The time-bounded sampling period used to evaluate a kernel change for a cohort (default 5 minutes).
- Handoff: The act of routing cohort traffic from one kernel variant to another.
- Fidelity regression: Any measurable reduction in output quality against a defined prompt-suite (e.g., Rouge/BLEU/embedding-similarity drop or increased hallucination rate).

Architecture overview (textual diagram)

Serving runtime components involved:

- Dispatcher: request classifier and cohort router (policy engine)
- Scheduler: allocates kernel slots and performs handoff orchestration
- Kernel Registry: metadata and compatibility matrix for kernel variants
- Probe Engine: lightweight mirroring and sampling sub-system for probe windows
- Telemetry Pipeline: streaming traces, percentile latencies, fidelity probes, error rates

(Imagine a horizontally stacked diagram: Dispatcher -> Scheduler -> Kernel instances; Probe Engine forks short-lived shadow requests to probe kernels and emits enriched traces into Telemetry Pipeline.)

Signals to collect

Collect these signals at 1s/10s/60s granularities depending on signal type:

- Latency: p50/p95/p99 for token generation and end-to-end request time
- Error rates: gRPC/HTTP 5xx, codec errors, kernel panics
- Fidelity metrics: embedding cosine similarity to baseline, token-level divergence, special token counts (UNK/UNK-like), model-specific eval score on a small prompt set
- Resource signals: GPU SM utilization, memory pressure, kernel queue depth
- Queueing indicators: queuing_time_ms, active_slots, preempt_count

Decision thresholds (defaults)

- Latency: p99 increase > 15% for probe cohort compared to baseline => fail probe
- Error rate: absolute increase > 0.5 percentage points or relative > 2x => fail probe
- Fidelity: embedding similarity drop > 0.015 absolute or relative quality delta > 5% on validation prompts => fail probe
- Resource: sustained (30s) GPU mem pressure > 90% or SM utilization pegged at 98% => fail probe

Config table (example values)

- probe_window_minutes: 5
- probing_fraction_initial: 0.01 (1% of cohort)
- probing_fraction_step: 0.05 (increase to 5% on success)
- max_probe_fraction: 0.20
- telemetry_aggregation_interval_seconds: 10
- required_consecutive_success_windows: 2

Automated probe lifecycle (high-level steps)

1) Candidate selection: Release pipeline marks kernel variant K2 as candidate for kernel K1 on cohort C.
2) Canary allocation: Scheduler selects a probe subset P (probing_fraction_initial) of cohort C and routes those requests to K2 for probe_window_minutes.
3) Shadow probing (optional): For fidelity-sensitive cohorts, the dispatcher sends a non-blocking shadow request to K2 in parallel; results are compared against the primary path.
4) Aggregation: Probe Engine aggregates telemetry for P and computes delta vs baseline.
5) Decision: If all thresholds are satisfied and required_consecutive_success_windows are met, increase probing_fraction by probing_fraction_step and continue. If probe reaches max_probe_fraction and passes final checks, promote K2 for cohort C. Otherwise, abort and revert to K1.

Manual escalation playbook (when automated probe fails but metrics are borderline)

1) Pager triggers: If failure threshold crossed for production cohort above severity threshold (see SLO incident taxonomy), page runtime-oncall.
2) Initial triage (5 min):
  - Confirm the cohort identity and affected customers.
  - Check recent kernel release events, model version swaps, infra incidents.
  - Run ktrace for an exemplar request (see commands below).
3) Containment (10 min):
  - Quarantine cohort: change cohort routing policy to pin to stable kernel K1 for all non-probe traffic.
  - Increase telemetry sampling to 100% for affected cohort for 15 minutes.
4) Root cause and remediation (30–90 min):
  - If kernel bug suspected, open kernel rollback and mark variant as unsafe in Kernel Registry.
  - If resource pressure, expand capacity or move cohort to different node pool.
  - For fidelity regressions, trigger a focused validation replay (see benchmarking steps) and notify model quality team.

Investigation commands and examples

- Capture a short trace for a failed sample:
  curl -s -H \"Authorization: Bearer $TOKEN\" \
    -d '{\"model\":\"X-small\",\"input\":\"<repro prompt>\",\"trace_id\":\"probe-debug-$(date +%s)\"}' \
    https://dispatcher.internal/v1/execute

- Query probe aggregates (PromQL example):
  sum(rate(kernel_request_duration_seconds_bucket{cohort="$COHORT",kernel_variant="K2"}[5m])) by (le)

- Compare embeddings (quick python snippet):
  from numpy import dot
  from numpy.linalg import norm
  def cos(a,b):
    return dot(a,b)/(norm(a)*norm(b))

Profiling and synthetic replay checklist

- Before large cohort promotions, run the following:
  - Microbench: run 1k synthetic requests with mixed sequence lengths (16/64/256) using the benchmark harness. Record p50/p95/p99 and compare to baseline.
  - Shadow replay: replay a 10k-sample window from production tracing storage through candidate kernel in sandbox.
  - Fidelity run: execute cohort-specific prompt set (50–200 prompts) and compute embedding similarity + model-specific metrics.

Benchmark commands (example harness invocation)

- ./bench_harness --kernel K2 --model X-small --sequences 1000 --mix \"16:0.5,64:0.3,256:0.2\" --concurrency 8 --report out/K2-microbench.json

Kernel scheduling policy examples

Use this sample policy to prefer memory-efficient kernels for cohorts with high concurrency:

- policy name: cohort_memory_preference
- selectors: cohort.labels.fidelity_tolerance <= 0.02 and avg_seq_length > 128
- preferred_kernel_order: [quantized_lowmem, fp16_sparse, fp16_full]
- admission: max_slots_per_node 32

Validation and rollout checklist (pre-promotion)

- Automated probe passed for required_consecutive_success_windows.
- Microbench p99 no more than 10% increased vs baseline.
- Fidelity metrics within thresholds on the validation prompt set.
- No related infra incidents in last 60 minutes.
- Release notes entry added to runtime release notes and Kernel Registry annotated with risk level.

Rollback policy

- Immediate auto-rollback on: p99 latency > 2x baseline or absolute error-rate jump > 2 percentage points.
- Automated partial rollback: if probe window fails but not catastrophic, revert probing_fraction to 0 and annotate Kernel Registry with failure reason.

Operational run scenarios (short examples)

- Scenario A: New quantized kernel shows 3% p99 improvement but 0.02 drop in embedding similarity.
  1) Probe small cohort (1%). 2) Fidelity delta borderline — hold probe and escalate to model-quality team. 3) After validating prompt set, either accept with a soft-fidelity gate or rollback.

- Scenario B: Kernel passes fidelity but causes GPU mem pressure.
  1) Probe fails on resource signal. 2) Quarantine cohort, move to larger nodes, re-run microbench.

Safety notes and guardrails

- Never promote a kernel that showed any instance of deterministic correctness error (e.g., tokenization mismatch) in probe windows.
- For regulated cohorts (confidentiality=restricted), shadow probing is disabled unless explicitly approved by security/compliance.

Audit and postmortem requirements

- Any automated rollback must generate an incident record with: timeline, probe aggregates, decision rationale, and remediation plan.
- For rollouts that change >10% of cohort volume, perform a 72-hour post-rollout review and record in related_pages.

Appendix: troubleshooting quick hits

- If probe_latency spikes but resource signals are normal: collect detailed kernel traces and map to kernel queue depth; suspect scheduling contention.
- If fidelity drops only for long sequences: check kvcache eviction settings and kernel-specific KV handling toggles.
