private-deploy-capacity-modeling-and-preemptible-safety-playbook

Guidance and operational procedures for modeling capacity in private deployments that rely on preemptible/spot GPU instances or transient nodes. This playbook explains safety patterns, autoscale boundaries, fallback topologies, testing recipes, and the operator runbook for eviction and preemption events.
Overview

This playbook documents how to model capacity for private (VPC or on-prem with transient nodes) deployments that intentionally use preemptible (spot-like) GPU/CPU instances to reduce unit cost, while preserving application SLOs and operator safety. It provides concrete steps for estimating headroom, configuring autoscalers and queuing, implementing graceful eviction handling, and validating fallbacks with test recipes.

Audience
- Field operators and SREs responsible for private deployments
- Platform and runtime engineers building autoscale/eviction handlers
- Solutions engineers doing customer capacity sizing and risk analysis

Scope
- Applies to Redwood Private deployments with mixed-instance fleets: reserved nodes + preemptible nodes + optional burst-to-hosted fallback routes.
- Covers GPU and CPU-backed worker fleets, model KV cache considerations, and network/proxy constraints.
- Does NOT replace customer contract SLAs — use this playbook to design operational safeguards and evidence for customer readiness.

Assumptions and definitions
- Preemptible node: a node that can be evicted without prior notice (cloud spot GPU, cloud preemptible VM, or on-prem transient slot).
- Reserved node: non-evictable instance purchased or pinned for predictable throughput.
- Safety headroom: reserved capacity benchmarked to absorb X% of load while preemptible nodes are reclaimed.
- Warm-standby: smaller number of pre-initialized models/KV on reserved nodes to reduce cold-starts.

Responsibilities
1) Field engineering: perform initial capacity model for customer workload and document assumptions.
2) Platform/SRE: implement autoscale policies, eviction handlers, and routing fallbacks.
3) Solutions/Customer Success: validate the model with customer workload traces and signoff on operational risk.

Capacity modeling workflow (step-by-step)
1) Collect workload traces (7/30/90-day): requests per second (RPS), tokens per request distribution (p50/p95/p99), session/chat concurrency, and peak burst patterns.
2) Measure per-model throughput on target instance types under realistic batch/sequence lengths (stable test harness). Report tokens/sec, latency percentiles, and GPU memory headroom.
3) Define target SLOs: e.g., p95 tail latency <= 250ms for short prompt class, p99 <= 800ms for long sequences, availability SLO 99.9% for production route.
4) Compute baseline reserved capacity: provision enough reserved nodes to serve sustained baseline load (p50 sustained + safety margin).
5) Add preemptible layer: size preemptible fleet to cover bursts and reduce average cost. Use historical burst ratio (burst RPS / sustained RPS) to compute needed preemptible capacity.
6) Define safety headroom: minimum reserved capacity must cover at least 30–60% of peak depending on customer risk tolerance and SLOs. Capture this as a parameter in the customer onboarding workbook.
7) Validate with synthetic replay and failover chaos tests (see Testing and validation).

Preemptible safety patterns
- Conservative headroom: reserved nodes are the primary safety boundary. We recommend reserved capacity >= 40% of peak for customers with strict latency SLOs, and >= 20% for best-effort workloads. Document customer's accepted degradation profile.
- Graceful eviction handler: run a lightweight eviction agent that quickly reassigns in-flight requests, snaps KV caches to stable storage, and marks the node as draining to the load-balancer.
- Queueing with backpressure: introduce a short-memory request queue (per-tenant) with dynamic admission controls. Configure circuit breakers to convert excess load into 503s rather than unbounded latency.
- Warm-standby cache policy: keep the most frequently accessed model KV entries on reserved nodes. Use a bloom-filter or LFU approximate set to populate warm-standby candidates.
- Fallback routing: for severe preemption spikes, steer requests to: 1) other private-region reserved capacity, 2) cross-region reserved pool (if contract allows), or 3) Redwood hosted API as last-resort (with customer consent).

Eviction handling sequence (operator-facing)
1) Detection: cloud provider eviction webhook / node heartbeat loss triggers immediate alert.
2) Mark node draining: set LB weight to 0 and stop new assignments.
3) Snapshot KV cache and flush hot prefixes to object store (if configured).
4) Migrate in-progress sessions: where possible, replay short sessions on an alternate node; otherwise return controlled failure to client with retry-after header.
5) Trigger autoscale policy to replace capacity. If replacement fails, escalate to fallback routing.

Autoscale and safety limits (recommended defaults)
- Min reserved nodes: sized per customer baseline; do not autoscale below this.
- Max preemptible nodes: customer-specific but limit to prevent eviction storm amplification (default 4x reserved nodes).
- Scale-up cooldown: 30s for ramping preemptible layer; 120s to scale reserved nodes.
- Eviction surge dampener: after >10% sudden preemptions in 60s, temporarily cap new preemptible allocations for 5 minutes.

Testing and validation
- Synthetic replay: replay a 24-hour trace that includes 99th percentile bursts to validate autoscale behavior and eviction handling.
- Chaos test: simulate a 25% preemption wave and observe fallback routing, eviction handler correctness, and SLO impact. Record metrics and compare against acceptance criteria.
- Cold-start experiment: force cache eviction and measure p95/p99 latency with warm-standby disabled to quantify customer-visible impact.

Acceptance criteria for production signoff
- p95 latency degradation during a 25% preemptible eviction simulation is <= 2x baseline and p99 does not exceed customer-defined hard limit.
- No data loss observed for model KV (snapshots or warm-standby).
- Fallback routing succeeds and error budget for hosted fallback is exercised in a controlled manner.

Metrics, SLOs and alerts
- Essential SLIs: request success rate, p50/p95/p99 latency, tokens/sec, eviction-rate, warm-cache-hit-rate.
- SLO example: availability 99.9% measured as request success rate over 30d window.
- Alerts (examples):
  - eviction-rate > 5% sustained for 5m -> page SRE and owner.
  - reserved-utilization > 85% and preemptible-utilization > 75% -> warn, prepare fallback.
  - KV snapshot failures -> page oncall immediately.

Operational runbook (short playbook)
1) Alert: eviction-rate > 5% -> acknowledge and run checks: provider status, node heartbeat, LB health.
2) If multiple nodes evicted simultaneously (>10% fleet): enact fallback routing to alternate pool or hosted endpoint and notify customer contact.
3) If autoscaler cannot replace capacity within 10 minutes: escalate to platform lead and begin incident conference.
4) Post-incident: collect traces, KV snapshot logs, and reproduce in staging. Update capacity model and adjust headroom parameter.

Rollout checklist for customers
- Collect 30d production-like traces and run sizing harness.
- Agree on reserved-min headroom and fallback routes in onboarding kickoff.
- Deploy eviction handler and run a supervised chaos test in staging.
- Run preemption simulation and obtain customer signoff on acceptable degradation profile.

Appendix: common pitfalls and mitigations
- Pitfall: over-aggressive preemptible sizing -> causes cascading evictions and noisy autoscaling. Mitigation: cap preemptible_max_ratio and use surge dampener.
- Pitfall: KV cold-starts on fallback -> pre-populate warm-standby caches and snapshot frequently.
- Pitfall: network egress or proxy limits reached during bulk fallback -> account for NAT/egress concurrency when sizing fallback capacity.
