Request sampler and golden-trace validation playbook

Overview

This playbook describes the Request Sampler and Golden-Trace Validation workflow used by Developer Experience (DX) to: 1) capture representative SDK/API requests with low overhead, 2) produce golden traces for deterministic integration tests and quality checks, and 3) validate telemetry stability across SDK and runtime releases. The goals are reproducible samples for regression detection, minimal perf impact (<0.5% p50 latency change), and a well-defined triage path for telemetry drift.

When to use this playbook

- Onboarding: collect starter traces for new SDK integrations.
- Release gating: validate that SDK vX and runtime vY produce matching golden traces for canonical prompts.
- Incident analysis: replay sampled traces when investigating errors or regressions.

High-level architecture

- Request Sampler (client-side): lightweight component embedded in SDKs that probabilistically captures request metadata and optionally full payloads when consented.
- Sample Collector (ingest): a Redwood internal service (service name: dx-sampler-ingest) that receives sampled envelopes over HTTPS and writes to a partitioned S3 bucket and an internal RocksDB index for quick lookup.
- Golden-Trace Builder: offline job (dx-golden-builder) that normalizes payloads, redacts PII, and computes canonical outputs against target models for golden traces.
- Validator: CI job and on-demand service (dx-trace-validate) which compares new traces against goldens and emits metrics/alerts.

Sampling policy and config

Default policy (applies to SDKs unless overridden by tenant config):

1) Low-volume tenants (<1000 requests/day): deterministic capture of first 50 requests/day, then 1% random sampling.
2) Mid-volume tenants (1k-100k/day): Poisson sampling at 0.5% with deterministic capture for error responses (HTTP >= 500) and slow responses (>99th latency pct).
3) High-volume tenants (>100k/day): reservoir sampling capped to 10k samples/day with priority for error/slow traces and explicit developer flags.

Config table (example values to include in SDK config):

- sampler.enabled: true|false
- sampler.rate_pct: "0.5"
- sampler.max_daily: "10000"
- sampler.capture_response: true|false
- sampler.capture_headers: ["x-request-id","x-redwood-route"]
- sampler.redact_fields: ["user.email","user.phone"]

Example SDK snippet (JavaScript)

const redwood = new RedwoodClient({
  apiKey: process.env.REDWOOD_KEY,
  sampler: { enabled: true, rate_pct: 0.5, capture_response: false }
});

// Attach an explicit sample request when you need a guaranteed capture
redwood.sampler.markForCapture({ reason: 'onboarding:sample-1' });

Collector contract and envelope schema (example JSON)

{
  "envelope_id": "uuid-v4",
  "sdk_name": "js-client",
  "sdk_version": "1.12.0",
  "timestamp": "2026-02-08T10:12:34Z",
  "route": "/v1/generate",
  "metadata": { "tenant_id": "acct-123", "region": "us-west-2" },
  "payload_redacted": true,
  "response_hash": "sha256:abcd...",
  "latency_ms": 128
}

(Collector stores redacted payloads by default; full payloads require customer consent and a signed ACL)

Golden-trace generation and normalization rules

1) Redact: PII fields defined by sampler.redact_fields must be removed or replaced with stable placeholders (user.email -> <REDACTED_EMAIL>).
2) Determinize: random seeds, timestamps, and ephemeral IDs must be normalized. Examples: unify date formats to YYYY-MM-DD, inject stable pseudo-random seed from envelope_id.
3) Tokenization consistency: use dx-golden-builder's tokenization v2 (tokenizer version baked into golden metadata).
4) Output canonicalization: strip whitespace-only differences and apply language-specific normalization (Unicode NFKC).

Validator checks (ordered)

1) Hash match: compare response_hash to golden. If identical -> PASS.
2) Fuzzy-match: if hash differs, compute token-level diff and score. Thresholds: fuzzy_score >= 0.98 -> WARNING, 0.9-0.98 -> INVESTIGATE, <0.9 -> FAIL.
3) Latency delta: if median latency for this trace class increases >20% in canary -> PERFORMANCE ALERT.

CI gating and rollout integration

- Pre-merge: run dx-trace-validate on a curated set of 100 golden traces. Failures block merges for runtime or SDK changes that touch tokenization, serialization, or sampling logic.
- Post-deploy canary: run validation against a live golden cohort for first 1% of traffic. If FAIL or >20% WARNINGs, automatic rollback to previous runtime version.

Dashboards and metrics to monitor

- trace.validation.pass_rate (per sdk_name, per model)
- trace.validation.fuzzy_score_p50/p90
- sampler.ingest.latency_ms (SLO: p95 < 200 ms)
- sampler.ingest.error_count (SLO: <0.1% errors/day)
- validation.ci_blocked_count

Operational playbook: triage path

1) Alert triggers: validation FAIL or validation.pass_rate < 99% for 10 minutes.
2) On-call (eng-sre) creates incident and assigns to dx-telemetry rotation.
3) Initial checks (10 minutes): verify dx-sampler-ingest health, storage quotas, and collector error logs (/var/log/dx-sampler/*.log).
4) Reproduce locally: use dx-replay tool to replay the offending envelope against current runtime and golden runtime. Command example:

# replay by envelope id
dx-replay --env-id uuid-v4 --target runtime://staging-us-west-2

5) If mismatch is reproducible: collect a golden-diff artifact and escalate to eng-developer-experience and eng-serving-runtime for root cause. Attach artifacts: envelope.json, golden.json, diff.patch.
6) If mismatch is non-reproducible or intermittent: increase sampling rate for the tenant to 5% and enable full payload capture for 24 hours (requires customer notification if not internal).

Compliance and privacy notes

- Default behavior is to redact PII. Full payload capture requires explicit customer consent and a signed Data Collection Addendum (DCA).
- Stored samples are retained 90 days in S3 partitioned by tenant and then moved to cold archive for 1 year. Retention overrides for security incidents must be approved by Security.

Examples and troubleshooting

Q: I’m seeing validation WARNINGS on benign formatting changes.
A: Use dx-golden-builder normalization rules to re-run the golden build with updated normalization for this language. Document the normalization change and add the new golden to the curated cohort.

Q: Sampling rate seems to reduce SDK performance.
A: Validate with feature flag: disable capture_response or reduce rate_pct. Expected p50 latency delta with sampler.enabled:true is <5ms for typical requests.

Appendix: rollout checklist for enabling sampler in a new SDK

1) Add sampler config defaults to SDK config schema and unit tests for rate boundary conditions.
2) Integrate SDK telemetry with dx-sampler-ingest using the envelope contract.
3) Add golden traces for 10 representative prompts to the curated cohort (include at least 3 edge-case prompts).
4) Run dx-trace-validate locally and in CI.
5) Deploy to canary population (1% traffic) and monitor trace.validation.pass_rate for 24 hours.
6) Ramp to 10% then 100% by manual approval once pass_rate >= 99.5% for 24 hours.
