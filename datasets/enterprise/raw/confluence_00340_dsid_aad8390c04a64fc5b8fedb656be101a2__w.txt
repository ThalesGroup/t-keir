Workload placement decision matrix and examples

Summary

This document provides a pragmatic decision matrix and worked examples to help platform engineers and service owners decide where to place inference workloads across Redwood deployment modes (hosted API, Dedicated pools, Private/VPC). It summarizes the key workload signals, placement rules, and a repeatable evaluation procedure. The goal is to reduce subjective calls, speed provisioning, and make placement decisions auditable.

When to consult this document

- New model onboarding requests (PRD -> runbook)
- Product teams considering SLA/latency guarantees or cost tradeoffs
- Capacity planning and budgeting cycles
- Incident triage when capacity constraints require devolution/fallbacks

Decision matrix (short form)

Use the following primary signals to decide placement. Each bullet is weighted (high/medium/low) for the typical tradeoff decision:

- Latency sensitivity: high = p50 < 50ms endpoint response; medium = 50-200ms; low = >200ms
- Peak concurrency: high = >500 qps sustained; medium = 50-500 qps; low = <50 qps
- Data sensitivity: regulated/PII = high; internal-only = low
- Cost-sensitivity: budget caps or startup cost constraints = high; cost-secondary = low
- Model churn: frequent/new-variants = high; stable pinned model = low

Rule of thumb mapping (summary):

- Hosted API: best for low-to-medium concurrency, low data-sensitivity, fast time-to-value, and experimental models.
- Dedicated (reserved GPU pools): best for high concurrency, predictable throughput, and moderate data-sensitivity where SLA-backed latency is required.
- Private (VPC / on-prem): required for regulated workloads, full data isolation requests, or when network egress controls require it.

Decision matrix (detailed)

| Signal | Hosted | Dedicated | Private (VPC/on-prem) | Notes |
|---|---:|---:|---:|---|
| Latency SLO p50/p95 | medium | high | high | Dedicated and Private support pinned capacity and colocated networking to meet tail SLOs |
| Sustained QPS | <500 | >=500 | >=500 (but depends on infra) | Dedicated has autoscaling/burst policies for queues |
| Data sensitivity | low | medium | high | Private required for regulated data or explicit KMS/HSM needs |
| Model churn / releases | high (fast) | medium | low (slower ops) | Hosted supports quick rollouts, Private deployments prefer controlled rollouts |
| Cost predictability | low | high | high | Dedicated contracts provide committed cost predictability |
| Operational ownership | Redwood managed | shared | customer-managed | Private shifts day-2 ops to customer or integration team |

How to use the matrix (step-by-step)

1. Collect signals: service owner fills the Workload Intake form (see Appendix). Required fields: expected p50/p95, peak qps, data classification, expected token volume, model size, SHAs of model artifacts.
2. Compute placement score: apply weights (latency 30%, concurrency 30%, data-sensitivity 20%, cost 10%, churn 10%).
3. If score > 0.7 -> recommend Dedicated; 0.4-0.7 -> recommend Hosted (with optional Dedicated for burst); <0.4 -> Hosted. If data-sensitivity = high => override -> Private.
4. Present recommendation in an RFC and include a runbook snippet for rollout and rollback.

Evaluation procedure (detailed checklist)

- Owner: service product/ML engineer; Reviewer: platform oncall
- Required artifacts:
  1. Latency SLOs (p50/p95/p99) and error budget (e.g., 99.9% p95).
 2. Traffic profile: QPS distribution, daily/hourly peaks, 30/90-day projections.
 3. Model profile: model name, architecture, size (FP16/INT8), KV-cache expected reuse ratio.
 4. Cost expectations: per-token cost target or monthly committed spend limit.
  5. Security requirements: data residency, KMS/HSM, audit retention.

- Runbook sanity checks (pre-provision):
  - Verify test harness that reproduces 95th percentile latency locally or on canary capacity.
  - Verify model behaves with recommended quantization profile (if any).
  - Confirm fallback path (smaller model / hosted fallback) is implemented.

Example decision scenarios

Scenario A — Chat completion for internal analytics (low sensitivity, medium concurrency)
- Signals: p50=80ms, p95=220ms, peak=120 qps, model = 13B quantized INT8, data = internal
- Matrix => Hosted recommended with a caching layer and request-level batching.
- Implementation notes:
  - Use hosted with recommended batching: batch_size=64, batch_timeout_ms=12.
  - KV cache TTL = 4 hours for common prefixes.
  - Monitor token-cost per 1k requests and set alert if > baseline + 20%.

Scenario B — Customer-facing real-time assistant (PII, high concurrency)
- Signals: p50=30ms requirement, p95<80ms, peak=800 qps, model=30B FP16, data=PII
- Matrix => Private or Dedicated (if customer consents to shared Dedicated with strict tenancy).
- Implementation notes:
  - Prefer Private when legal requires VPC and customer-managed KMS.
  - If Dedicated: reserve 2x baseline capacity (autoscale headroom) and enable burst credits.
  - Set circuit-breaker thresholds: queue_length > 5000 -> degrade to distilled model and route to fallback endpoint.

Scenario C — Experimentation: new open-source model (high churn, low concurrency)
- Signals: p50=120ms, peak=15 qps, model changes weekly
- Matrix => Hosted (experimental) with rapid canaries.
- Implementation notes:
  - Use hosted ephemeral model variants with traffic split 90/10 canary.
  - Integrate automated evals against golden prompt-set and fail on >5% quality regression.

Operational knobs by placement mode

Hosted API:
- Batching: configure per-route suggested batch_size and timeout. Default: 32/10ms.
- Caching: prefix and KV cache enabled by default with suggested TTLs.
- Rollouts: canary splits via Redwood Console.

Dedicated:
- Pool sizing: reserve GPUs based on sustained qps and model per-GPU throughput (measured in tokens/sec).
- Autoscaling: target CPU/GPU utilization 60–75% to preserve headroom for spikes.
- Fallbacks: pre-provision smaller/quantized model variants in the same pool for graceful degradation.

Private / VPC:
- Network: colocate model-serving nodes in same subnet as customer ingress to keep tail latency low.
- Security: enforce KMS/HSM integration, audit logging shipped to customer SIEM endpoint.

Example configuration snippets

- Model placement request (YAML)

service_name: customer-assistant
placement_preference: dedicated
latency_slos:
  p50_ms: 30
  p95_ms: 80
peak_qps: 800
model:
  name: customer-assistant-v2
  size: 30B
  quant_profile: fp16
data_classification: pii
commitment: annual 24/7

- Example CLI to request Dedicated pool sizing (platform-infra CLI)

# estimate GPUs based on measured tokens/sec per GPU
platform-infra pool estimate --model customer-assistant-v2 --target-qps 800 --safety-factor 1.5

Alerts and dashboards to create

For any placement decision we require these standard dashboards and alerts before full production rollout: 

- Dashboards:
  - Per-route latency (p50/p95/p99) with breakdown by model variant and region
  - Token-cost per-minute and 24h rolling average
  - GPU pool utilization with per-instance metrics (util, mem, temp)

- Alerts (examples):
  1. Latency p95 > target + 20% for 3 consecutive mins -> Sev2 -> page oncall
  2. GPU utilization > 85% for 5 mins -> run autoscale or trigger pool expansion
  3. Token-cost anomaly > 30% day-over-day -> notify cost-owners

Ownership and escalation

- Service owner: product/ML team that requested placement (primary owner).
- Platform: responsible for provisioning Dedicated pools, templates, and runbook approvals.
- SRE/Oncall: enforce SLO alerting and initial triage during rollout.

Escalation flow (short):
1) Service owner -> Platform oncall (15 min)
2) Platform oncall -> Eng-SRE (30 min) if capacity, network, or GPU health indicated
3) Exec escalation -> Head of Platform (60+ min) for cross-region failovers or contract-level incidents
