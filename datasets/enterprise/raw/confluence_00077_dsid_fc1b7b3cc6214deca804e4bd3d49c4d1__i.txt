Incremental probe-driven onboarding for function-call-capable models

Overview
-------
This playbook describes an incremental, probe-driven onboarding procedure for models that expose function-call behavior and interact with runtime tooling (webhooks, databases, external APIs). It focuses on minimizing user-visible regressions while validating runtime contracts: function schema stability, tool-call ordering, tokenization/serialization invariants, and quantization / KV-cache interactions. The goal is a repeatable checklist teams can follow to promote a candidate model from shadow to mixed canary to full production with defined metrics and rollback criteria.

Why this is needed
------------------
Function-call models introduce new failure classes that typical text-only onboarding misses: mismatched JSON schemas, missing/extra fields, latency-sensitive external tool calls, and subtle behavior shifts after quantization or KV cache migration. These failures can manifest as incorrect downstream actions or data corruption. An incremental probe-driven approach lets us exercise these surface areas under controlled load and detect regressions early.

Scope
-----
- Applies to models used for programmatic outputs (JSON/tool calls) and models that rely on runtime toolchains (e.g., DB lookups, external API calls).
- Intended for Hosted, Dedicated, and Private deployment modes.
- Does NOT replace safety/safety-sandbox fuzzing; it's complementary and focused on integrability and runtime contract stability.

High-level timeline (recommended)
--------------------------------
1. Readiness check & probe design (1–3 days)
2. Shadow probe run + offline analysis (2–5 days)
3. Incremental canaries (mixed traffic) with targeted probes (3–7 days)
4. Full rollout with continuous probe monitoring and autoscale validation (1–3 days)

Readiness checklist (pre-shadow)
--------------------------------
- [ ] Model artifact passes unit schema checks (declared function signatures)
- [ ] Tokenization-snapshot: captured tokenization mapping for top 1000 prompt templates
- [ ] Quantization baseline: run fast quant regression on 50 representative probes (latency + determinism)
- [ ] KV-cache compatibility: smoke checks for prefix reuse on sampling probes
- [ ] Tooling harness: test harness that can simulate external tools and record call traces

Designing probes for function-call surfaces
----------------------------------------
Probes should exercise:
- Positive path: well-formed function calls, correct ordering, sequential tool interactions
- Negative path: malformed payloads, missing optional fields, extra unexpected keys
- Latency-sensitive path: function calls that depend on sub-100ms downstream responses
- Stateful path: multi-turn sequences that rely on KV cache warmup and key reuse

Probe attributes (minimum)
- probe_id (string)
- intent (short description)
- input_prompt (template + slot schema)
- expected_function_schema (json schema string)
- allowed_semantic_variance (description / thresholds)
- drift_guard (metric to track)
- run_frequency (shadow/canary/prod)

Example probe (text block)
-------------------------
Probe: account-balance-fetch-1
- intent: fetch a customer account balance and format as: {"account_id":string,"balance":number,"currency":string}
- input_prompt: "Get balance for CUSTOMER_ID={{customer_id}}; return as JSON using function 'get_balance'"
- expected_function_schema: {"type":"object","properties":{"account_id":{"type":"string"},"balance":{"type":"number"},"currency":{"type":"string"}},"required":["account_id","balance"]}
- allowed_semantic_variance: numeric rounding +/- 0.01; currency code must be ISO-4217
- drift_guard: function_schema_mismatch_rate < 0.5% over rolling 1k probes

Shadow phase (offline + limited live)
----------------------------------
Goals: verify deterministic schema adherence, identify tokenization regressions, measure quant sensitivity, and validate KV cache warmup behavior.
Steps:
1. Run probes through the evaluation harness in shadow mode (no downstream side-effects). Capture: function call traces, tokenization deltas, logits top-k for key tokens.
2. Run the same probes with the current production model to establish baselines.
3. Compare metrics and generate report with the following sections:
   - Schema mismatch counts and representative examples
   - Tokenization delta summary (fraction of probes where tokenization changed)
   - KV-prefix reuse distribution and hit-rate diff (shadow vs prod)
   - Quantization sensitivity summary (latency delta, deterministic mismatch rate)
4. Required pass criteria to proceed to canary:
   - schema_mismatch_rate <= 0.5%
   - tokenization_delta_rate <= 1.0% for critical templates
   - kv_warmup_hit_drop <= 15% relative to baseline
   - quant_determinism_mismatch <= 0.3%

Incremental canary plan
-----------------------
Objective: expose limited production traffic and live downstream integrations while protecting customers and enabling rapid rollback.
Phases:
A. Dry canary (no downstream side-effects) — 5% of probe traffic mapped to live endpoints with tool calls stubbed and recorded. Duration: 24–48 hours.
B. Mixed canary (select tenants, idempotent tool calls only) — 10–20% of traffic, live tool calls with strict rate limits and circuit breakers. Duration: 48–96 hours.
C. Targeted canary (full behavior for a small tenant cohort) — 1–3 production tenants or 2% of overall traffic. Duration: 3–7 days.

Canary gating metrics (examples)
- function_schema_mismatch_rate (SLO gate): must remain <= 0.5% over each 1-hour window
- semantic_fidelity_index (SFI): composite signal (BLEU/embedding-similarity + manual review) must not degrade by >2.5 percentile points vs baseline
- downstream_error_rate: increase <= +0.1 percentage points absolute
- latency_p50/p95: p95 must not exceed baseline p95 + 35% or +200ms (whichever smaller)
- kv_miss_rate: not increase by >10% absolute for top-500 keys
- tokenization_symbol_shifts: zero tolerant changes for canonical templates; any shift triggers immediate investigatory pause

Telemetry and logging requirements
--------------------------------
- Function call trace fields to capture: probe_id, model_version, request_timestamp, function_name, encoded_payload_hash, downstream_status, downstream_latency_ms
- Log all function payloads to the eval sandbox for at least 7 days (redact PII automatically)
- Capture model logits for the token positions around function call markers for 1% sample to support determinism triage
- Store tokenization snapshots for each probe run (hashes) and diff against baseline

Automated anomaly detection rules (suggested)
- rule: schema_mismatch_spike — trigger if rate jumps by >5x over a 5m window or absolute >1%
- rule: semantic_routing_shift — if top-1 function selection changes for a probe family >3%
- rule: kv_warmup_failure — sustained kv miss rate increase >10% for 30m
- rule: quant_non_determinism — run a nightly batch to detect increased seed-level mismatch above 0.5%

Runbook: triage steps when a canary alarm fires
---------------------------------------------
1. Acknowledge the alert in PagerDuty, create an incident in Incident Review (link to template).
2. Collect reproducible probe IDs from the canary window and fetch: tokenization snapshots, function trace logs, and logits sample.
3. Compare with baseline probe runs (prod model): run a deterministic replay via eval harness.
4. If schema mismatch or tokenization shift is present: rollback the canary (automated route if gate violations are configured).
5. If latency or downstream error increase: throttle canary traffic to 0% and engage SRE for infra traces and client-side rate-limiting checks.
6. Perform a root-cause hypothesis matrix (model change, quantization artifact, kernel selection change, runtime flag).
7. Tag the incident with root cause and remediation owner; follow postmortem cadence if customer impact occurred.

Rollback and recovery strategy
----------------------------
- Automated rollback: if any SLO gate is violated for two consecutive evaluation windows, the system should automatically roll traffic back to previous stable model version.
- Manual rollback: Follow the rollback checklist; ensure the eval harness is set to re-run probes against the rolled-back model to confirm reversion of metrics.
- Post-rollback: increase probe sampling for 48 hours and schedule a focused shadow run for the candidate model pending fixes.

Special considerations: quantization and kernel heterogeneity
----------------------------------------------------------
- For quantized builds, run quant-shadow profiling across heterogeneous hardware (A100, H100, top-tier edge accelerators). Document kernel choices and fallback paths.
- Maintain an artifacts manifest that records: model_version, quant_profile_id, kernel_set_hash, and host_fingerprint. Include this artifact id in each probe trace for postmortem correlation.
- If a quantized candidate shows non-deterministic function-call behavior, treat this as a critical failure until determinism is restored.

Checklist before full rollout
----------------------------
- [ ] All canary gates passed for at least 72 hours with stable traffic mix
- [ ] No schema_mismatch incidents remaining in the last 7 days
- [ ] KV-cache hit-rate within target thresholds for top keys
- [ ] SRE confirms no infra-induced latency regressions
- [ ] Evaluators sign-off on semantic fidelity (2 independent reviewers)

Appendix A: example CLI to run a probe via eval harness
-----------------------------------------------------
curl -X POST https://eval-harness.internal/api/v1/run-probe \
  -H 'Authorization: Bearer $EVAL_TOKEN' \
  -H 'Content-Type: application/json' \
  -d '{"probe_id":"account-balance-fetch-1","model_version":"candidate-2026-02-01","mode":"shadow"}'

Appendix B: sample YAML probe manifest (abbreviated)
--------------------------------------------------
- probe_id: account-balance-fetch-1
  intent: "fetch account balance and return structured JSON"
  inputs:
    - name: customer_id
      type: string
  expected_function: get_balance
  expected_schema: |
    {"type":"object","properties":{"account_id":{"type":"string"},"balance":{"type":"number"}},"required":["account_id","balance"]}
  run_frequency: [shadow, dry-canary, mixed-canary]
