Offline artifact delivery and model refresh operator runbook

Summary

This runbook describes the operator-level steps, verification checks, and rollback procedures for delivering model artifacts to air-gapped or VPC-private Redwood Private deployments and performing a safe model refresh (hot-swap or staged rollout). It covers secure artifact packaging, transport validation, HSM/KMS verification, on-host ingestion, staged rollout patterns, automated health checks, and troubleshooting. Intended audience: field operators, platform engineers, and customer SREs running private deployments.

Goals and SLOs

- Goal: Replace a model bundle in an offline/private environment with minimal downtime and provable integrity.
- SLO: Model refresh completion within the operator maintenance window (default 30 minutes for small changes, 90 minutes for full model swap) 95% of the time.
- Safety constraints: No automatic switch to a new artifact unless all verification gates pass.

Ownership

- Primary executor: Field Operator / Platform Engineer (on-call operator).
- Reviewer/approver: Deployment Custodian (customer or Redwood field lead).
- Backup: Remote Escalation to Redwood Private Deployments team (pager).

Prerequisites and environment checklist

1) Pre-flight (remote before artifact export):
   - Confirm approved change request: CR-ID (vendor or customer) and signed acceptance.
   - Verify package manifest and signed digest are present in the artifacts registry (S3, GCS, or internal registry).
   - Ensure operator has the following: dev laptop with USB-A/USB-C transfer tools, signed access token (expiration >= 6 hours), and the vendor-supplied manifest.

2) Target environment (on-prem or VPC):
   - KV-store (redis) and serving runtime versions must match compatibility matrix (see Compatibility table below).
   - Node-level disk free >= 50GB (recommended) and memory headroom for model load (see resource table).
   - HSM/KMS accessible: either network HSM (for VPC) or local hardware token (for airgapped sites) with operator key escrow details.

Compatibility table (example)

| Component | Minimum supported | Verified for this run | Notes |
|---|---:|---|---|
| Serving runtime | 1.8.2 | 1.9.0 | Runtime picks specific kernels for quantized models |
| KV cache format | v2 | v2 | v2->v3 migrations require pre-warm step |
| Model bundle format | rbf-2025-10 | rbf-2026-01 | rbf-2026-01 supports delta patches |
| On-host agent | 3.4.x | 3.4.1 | Feature flag for atomic-swap required |

Artifact packaging requirements

Each model bundle must include the following files at top level of the artifact tarball (.tar.gz or .zip):
- model.bin (binary weights or shard list)
- model.metadata.json (see example below)
- model.manifest.sig (detached signature; signed by Redwood release key or customer-signed key)
- checksums.sha256 (SHA-256 sums of artifact contents)
- compatibility.txt (runtime and kv-cache constraints)

Example model.metadata.json (operator should validate locally):

```
{
  "model_name": "rw-opt-13b-q4_0",
  "variant": "quantized-q4_0",
  "version": "2026-05-01",
  "shards": 4,
  "size_bytes": 14000000000,
  "created_by": "redwood-release-bot@redwood.ai",
  "notes": "delta-patch-ready"
}
```

Transport and delivery patterns

There are three recommended delivery methods depending on customer connectivity:

A) Encrypted network transfer (VPC with egress to secured artifact gateway):
   - Use the internal artifact gateway with TLS mutual auth. Transfer command (example):

   curl --key operator.key.pem --cert operator.crt.pem --cacert gateway-ca.pem \
     -F "artifact=@/tmp/rw-opt-13b-q4_0-2026-05-01.tar.gz" \
     https://artifact-gateway.internal.redwood/api/v1/upload

   - Verify gateway returned upload_id and that server-side checksum matches checksums.sha256.

B) Physical transfer (airgapped sites):
   1. Export artifact from build farm to an encrypted thumbdrive using vendor tooling. Use LUKS or BitLocker with a randomly generated passphrase exchanged via an out-of-band channel (phone or secure chat with OTP).
   2. Maintain chain-of-custody log: operator name, time, thumbdrive ID, CRC of transfer.

C) Shuttle appliance (for large datasets > 100GB):
   - Use Redwood-certified shuttle appliance. Follow appliance manifest signing flow and use the provided transfer client (shuttle-client v2+).

Signature and integrity verification (mandatory)

All artifact arrivals must pass cryptographic checks before ingestion. Steps: 
1) Verify checksums: `sha256sum -c checksums.sha256` should report `OK` for every file.
2) Verify detached signature: `openssl cms -verify -in model.manifest.sig -content model.metadata.json -CAfile release-certs.pem` (or use `gpg --verify` for GPG-signed manifests).
3) Verify manifest fields against a local allowlist (expected model_name, version range, shard count).
4) HSM/KMS verification: if the artifact is encrypted with customer key, run `kms-client decrypt --key-id alias/customer-model-key --input model.bin.enc --output model.bin` and validate HMAC in `checksums.sha256`.

On-host ingestion sequence (safe mode)

1) Quiesce new traffic: set runtime flag `--accept-new-models=false` and drain short-lived requests. This preserves in-flight responses and keeps cold starts predictable.
2) Create a staging directory with unique timestamp: `/var/lib/redwood/staging/model-2026-05-01-timestamp/`
3) Copy artifact to staging and run verification steps from previous section on-host.
4) Unpack into staging and run container-level smoke load: `./bin/model-verify --warm --max-requests 20 --kv-preload` (the agent provides this helper). Expected exit code 0.
5) Validate runtime telemetry: check `model_load_time < 60s` and `initial_memory_rss < 90% of node free memory` in agent logs.

Staged rollout patterns (choose one)

A) Canary (recommended for critical customers):
   1. Add new model to the runtime but keep traffic weight = 0.
   2. Configure synthetic traffic generator to send 1% of production-equivalent traffic (10 qps or min(1% of avg qps, 20 qps)).
   3. Observe SLOs for 30 minutes: latency p95 < 2x baseline, error rate < 0.5%.
   4. If stable, increase weight in exponential steps (1%, 5%, 25%, 50%, 100%) with 15–30 minute observation windows.

B) Atomic swap (fast path for non-breaking quantization fallback):
   - Perform a single atomic endpoint switch after pre-warm. Requires `--atomic-swap` enabled. Backup snapshot is kept for 15 minutes before garbage collection.

Automated health checks and telemetry gating (must pass before advancing)

- Health checks: `model_ready` metric, `kv_cache_hit_ratio > 0.6`, `latency_p95 < baseline * 1.5`, `error_rate < baseline + 0.25%`.
- Telemetry sources: per-node agent, control-plane trace, and synthetic client.
- Gate: all checks must be green for two consecutive windows to proceed.

Rollback and emergency backout

Immediate rollback (fast):
1) If canary/atomic swap fails, immediately set traffic weight back to previous model (control-plane API call). Example API call: 

POST https://control-plane.internal.redwood/api/v1/models/{endpoint}/traffic-shift
Content-Type: application/json
{
  "from": "rw-opt-13b-q4_0:2026-05-01",
  "to": "rw-opt-13b-q4_0:2026-04-15",
  "weight": 100
}

2) If node-level memory pressure or OOM observed, execute emergency kill (on operator judgement) and restart runtime with previous snapshot: `systemctl restart redwood-runtime && /usr/local/bin/redwood-restore --snapshot /var/backups/model-snapshot-2026-04-15.tar.gz`

Forensic evidence collection (post-failure)

- Save staging directory, `/var/log/redwood/agent.log` (last 5000 lines), and `journalctl -u redwood-runtime --since "-2h" > /tmp/runtime-journal.log`.
- Preserve checksums and manifest, and forward to Redwood forensic bucket (via secured transfer) within the customer-approved retention policy.

Operator checklist (short)

1) Confirm CR and maintenance window.
2) Validate artifact signature and checksums.
3) Quiesce new connections and stage artifact.
4) Run container smoke tests and telemetry validations.
5) Execute canary or atomic swap as per policy.
6) Observe telemetry gates, then ramp to 100% if green.
7) If failure, perform rollback steps and collect forensic data.

Troubleshooting and common failure modes

- Failed signature verification: ensure operator has the correct release-certs.pem. If missing, escalate to Release Engineering.
- HSM decryption timeout: Check network path to KMS, verify operator token validity, and re-run with `--kms-retry 3`.
- High cold-start latency: ensure KV preload completed and increase pre-warm threads `--prewarm-threads` by +2.
- Serving runtime rejects shards: verify `shards` count in model.metadata.json and confirm shard placement in `/etc/redwood/shard-map.json`

Audit and evidence log format (minimum fields)

- operator, timestamp (UTC), artifact_id, transfer_method, signature_key_id, preflight_checks_passed (true/false), canary_result (pass/fail), rollback_invoked (true/false)

Sample audit line (CSV)

operator,timestamp,artifact_id,transfer_method,signature_key_id,preflight_checks_passed,canary_result,rollback_invoked
mtthompson,2026-05-12T11:05:12Z,rw-opt-13b-q4_0-2026-05-01,physical,B2F3-RELEASE-2026,true,pass,false

Appendix: quick commands

Verify checksum:
sha256sum -c checksums.sha256

Verify signature (CMS):
openssl cms -verify -in model.manifest.sig -content model.metadata.json -CAfile /etc/redwood/release-certs.pem -out /dev/null && echo "signature OK"

Unpack into staging and run verify helper:
mkdir -p /var/lib/redwood/staging/model-2026-05-01-timestamp && tar -xzvf /tmp/artifact.tar.gz -C /var/lib/redwood/staging/model-2026-05-01-timestamp && /usr/local/bin/model-verify --path /var/lib/redwood/staging/model-2026-05-01-timestamp
