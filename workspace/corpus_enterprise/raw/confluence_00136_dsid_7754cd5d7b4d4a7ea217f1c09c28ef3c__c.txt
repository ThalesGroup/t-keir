Contributor Toolflow and Privileges Playbook

Overview

Purpose: This playbook documents the standard tool access lifecycle for contributors at Redwood — from first-day provisioning through promotions, cross-team rotations, and final deprovisioning. The emphasis is on fast enablement, least-privilege by default, auditable changes, and clear manager/engineer responsibilities.

Audience: people-ops, hiring managers, engineering managers, IT, security reviewers, and new contributors.

Summary of goals:
- Ensure 95% of new hires have usable accounts and core tool access within 8 business hours of start.
- Enforce least-privilege role assignments for 90% of contributors by role templates.
- Complete deprovisioning within 24 hours for offboarded contributors (per security SLA).

Key principles
- Least privilege: grant only the roles required for the contributor’s current responsibilities.
- Role templates: use standardized permission packages (see Role → Tool mapping).
- Manager-driven exceptions: any deviation requires manager justification and a 90-day review.
- Auditability: every access change must be recorded in Okta and the access-request ticket.

Role → Tool mapping (canonical templates)
| Role | GitHub | GCP (project) | Datadog | Jira | Slack | Console/Secrets | Notes |
|------|--------|----------------|---------|------|-------|----------------|-------|
| IC-Engineer-Level-1 | repo:read | viewer | dash:read | dev-project | full | vault:read | Standard new-hire dev access (no prod) |
| IC-Engineer-Level-2 | repo:write | dev-editor | dash:read | dev-squad | full | vault:read | Can merge to non-protected branches; needs sprint leads approval for protected branches |
| IC-Engineer-Level-3 | repo:admin* | staging-editor | dash:write | squad-admin | full | vault:deploy | Elevated staging access; production access by exception and 90-day review |
| Platform-Engineer | repo:admin | multi-project | dash:write | infra | full | vault:admin | Broad access required for ops teams; requires security onboarding checklist |

*repo:admin for Level-3 is scoped to staging and infra-adjacent repos only.

Provisioning process (first-day onboarding)
1) Hiring manager creates a People Ops onboarding request in Workday/HRIS and links the candidate start date.
2) Manager files an Access Request ticket in Jira using template: "Access Request: New Hire - <NAME> - <TEAM> - <ROLE TEMPLATE>". Include start date and required projects.
3) people-ops triages: validates manager, picks correct role template, and initiates Okta provisioning flows.
4) Core accounts to create: Okta account, GitHub account (SAML link), Slack, GCP IAM invite, Datadog, Confluence.
5) Owner (people-ops) confirms repo and project invites; manager completes the New Hire Checklist and schedules Security Onboarding session.

Expected times:
- Okta and Slack: within 2 hours of ticket acknowledgement.
- GitHub & GCP invites: within 4 hours.
- All core tooling active and verified: target within 8 business hours.

Manager checklist for first 3 days
- Verify that the contributor can clone the repo and run the local dev script (tools/dev-setup.sh).
- Confirm access to Jira board and Datadog dashboards used by the team.
- Run through the security checklist: 2FA enforced, passwordless keys setup, vault read only.
- Submit permission escalation requests for protected branches if needed (see Escalation flow).

Permission escalation flow (protected or prod access)
1) Engineer or manager opens a "Privilege Escalation" Jira ticket with justification, duration, and list of specific resources.
2) Security reviews and responds within 2 business days. If approved, a scoped temporary role is created (max 90 days).
3) Audit log entry created; approver is added as owner.
4) 7 days before expiry, system sends reminders to the owner and manager to extend or revert access.

Cross-team rotations and role transitions
- When a contributor changes teams, the new manager must:
  - Open a change request ticket to add new role template and remove prior team templates.
  - Schedule a knowledge transfer and update on-call and pager duty rosters if applicable.
  - Verify completed de-escalation of previous team secrets and remove access to prior projects.
- people-ops will run an automated script (rotation-reconcile) that compares current Okta groups to team rosters and flags mismatches weekly.

Promotion-specific tool changes
- Promotion to IC-3 or above triggers a permissions review: expected changes include elevated staging permissions and write access to internal infra repos.
- Manager must document the promotion in the "Promotion Access" ticket and indicate any necessary temporary exceptions.

Deprovisioning (offboarding)
1) Offboard event triggers: manager submits Offboard ticket in Jira or HRIS marks termination/leave.
2) Immediate actions (within 2 hours): suspend Okta session, remove Slack privileges, revoke long-lived GitHub tokens.
3) Secondary actions (within 24 hours): remove GCP and Datadog access, rotate any secrets where the contributor was a maintainer.
4) Final reconciliation (within 72 hours): people-ops confirms all access removed and produces an audit report attached to the Offboard ticket.

Escalation playbook for stuck provisioning
- If new hire lacks access after 8 business hours: manager escalates to people-ops-ops channel and pings the people-ops oncall.
- If an access change is refused by security for unclear reasons: open a security-appeal with evidence and invite the security reviewer to a 30-minute working session.

Audit and quarterly clean-up
- Quarterly automated audit runs across Okta, GitHub org, GCP IAM, and Datadog.
- Flags generated: stale groups (>90 days), inactive users with elevated roles, long-lived tokens.
- people-ops and security jointly triage and close flags within 30 days.

Tooling snippets and examples
- Access request JSON example (paste into Jira ticket):
  {"candidate": "First Last", "team": "Platform", "role_template": "IC-Engineer-Level-2", "projects": ["project-dev-a", "project-infra-test"], "start_date": "2026-11-01", "justification": "Standard onboarding for backend engineer"}

- CLI to verify GitHub team membership (example):
  gh api repos/org/repo/teams --jq '.[] | select(.name=="platform") | .members_count'

Ownership and SLAs
- people-ops: primary owner for provisioning and deprovisioning SLAs.
- Security: owner for privilege escalations and audits.
- Team manager: owner for role correctness and business justifications.
- SLA targets: provisioning complete within 8 business hours (95%), deprovisioning within 24 hours (100% for suspension).

Templates & attachments
- New Hire Access Request (Jira template): create issue type ONBOARD-ACCESS with fields: name, start_date, role_template, projects, repo_list, manager_approver.
- Offboard checklist (attached to offboard ticket): suspend Okta session, revoke tokens, rotate secrets, remove from oncall, archive workspace.

Common FAQs
- Q: What if the new hire needs production access on day 1?
  A: Production access requires an explicit Privilege Escalation ticket plus security approval. Expect 48–72 hour lead time.
- Q: Who can request temporary elevated roles?
  A: Only the hire’s manager or a Director-level approver; all requests create audit trail entries.
