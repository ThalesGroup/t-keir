Multi-Vector Authorization Incident: Evidence, Containment, and Restoration Playbook

Summary

This playbook defines the triage, containment, evidence collection, and restoration workflow for multi-vector authorization (authz) incidents affecting Redwood Inference services (hosted, dedicated, private). A multi-vector authz incident is any event where authorization failures or entitlements (RBAC/attributes/roles) are implicated across more than one boundary: user-facing API, internal service-to-service, and/or administrative control plane. The goal is to preserve provable evidence, contain blast radius, restore least-privilege state, and produce a compliance-grade evidence bundle within SLA.

Scope and non-goals

- Scope: incidents where authorization decisions, entitlement changes, or privileged token misuse lead to unauthorized data access, model invocation, or administrative actions. This includes combined failures with audit logging gaps or cross-region residency concerns.
- Non-goals: application-layer privilege bugs not involving RBAC policy (these belong to product bug triage).

Ownership and roles

1) Incident Commander (IC): Security on-call. Responsible for overall coordination and final evidence sign-off.
2) Authz Forensics Lead: Security engineer specializing in RBAC and identity stores (owner of evidence bundle).
3) Audit/Telemetry Lead: Observability engineer for log retrieval and retention snapshots.
4) Network & Residency Lead: Infra engineer responsible for geo/residency containment and data egress checks.
5) SRE/Platform Lead: Executes runtime containment (feature flags, policy rollbacks).
6) Legal & Compliance: Notified for incidents with cross-border data movement or customer scope.

Alerting and initial triage (first 60 minutes)

1) Triage checklist (IC or primary on-call):
   - Confirm alert source(s): SIEM, WAF, anomaly detector, or customer report. Note time and detection signals.
   - Capture scope: affected customer tenants, namespaces, models, and services.
   - Determine blast radius: user requests, service tokens, admin console actions.
   - Immediately preserve clocks and offsets: note UTC epoch, host times, and time sync status.

2) First-hour objectives (SLOs):
   - Contain obvious ongoing exploitation: 1 hour
   - Initial evidence snapshot captured and immutable: 1 hour
   - Legal notified if PII or cross-border data potentially exposed: 2 hours

Containment play (technical steps)

- Short-term containment (fast, reversible):
  - Revoke active session tokens for affected service/tenant. Example (internal token service):
    curl -X POST https://auth.redwood.internal/v1/sessions/revoke -d '{"scope":"tenant:abcd"}' -H 'Authorization: Bearer $IC_TOKEN'
  - Apply deny-listing policy to the implicated role(s) in the attribute broker (example):
    # One-line: set-role-state --role devops/cluster-admin --state suspended --reason "incident"
  - Deploy emergency feature flag to disable high-risk endpoints (console write actions, model rollouts).

- Medium-term containment (safe, audited):
  - Create scoped ACL overrides that restrict privileged operations to IC and Authz Forensics Lead for the investigation window.
  - Enable immutable logging for queues/runtimes where KV cache or model artifacts could be exfiltrated.
  - Preserve database snapshots (read-only) for affected tenants in a write-blocked storage bucket.

Evidence collection and preservation

Principles: collect chronological, provable, and tamper-evident artifacts. Prefer immutable exports, signed manifests, and checksums. Do not modify original artifacts; only create read-only copies.

Required evidence components (minimum):
- Entitlement change log (authorization graph deltas) for 90 days prior to incident start.
- Authentication/session tokens timeline (session create/revoke) and token binding info.
- Audit event stream for the affected services (application, control plane, admin console).
- Network flow metadata for cross-region endpoints and egress hosts.
- Model invocation logs (model id, prompt hash, output hash), if model-serving involved.
- Storage object access logs (S3/GCS access entries) and object checksums.
- KMS/HSM signing events and key-access logs if keys were used by any privileged ops.

Evidence snapshot procedure (step-by-step)

1) Create a forensic staging bucket (immutable) in the same region as data residency requires. Naming convention: redwood-forensics-<incident-id>-<region>.
2) Run audit export queries and stream to staging bucket with object-level metadata and sha256 checksums. Example query for clickhouse-style audit index:
   SELECT timestamp, tenant_id, actor, action, resource, decision, reason FROM authz_audit WHERE tenant_id IN ('t1','t2') AND timestamp >= '2026-02-20T10:00:00Z' ORDER BY timestamp ASC;
   Pipe output to: gzip | tee >(sha256sum > /tmp/audit.sha256) | aws s3 cp - s3://redwood-forensics-INC123/audit/audit-20260220.gz
3) Collect host-level forensic snapshots (memory/disk) only after Legal approval if required; otherwise collect process-level logs and syscalls.
4) Pull index of entitlements from attribute store: export attributes in CSV with schema header and sign the file with key-capture utility.
5) Export and sign any CI/CD release artifacts that coincide with suspicious admin actions (commit SHA, release id).

Audit log discovery queries (examples)

- Service audit events (Elasticsearch/Kibana DSL):
  {
    "query": {
      "bool": {
        "must": [ { "term": { "tenant_id": "t-123" } }, { "range": { "@timestamp": { "gte": "now-14d" } } } ]
      }
    }
  }
- Postgres for entitlement deltas: SELECT * FROM role_changes WHERE role_name = 'admin' AND created_at >= '2026-02-20' ORDER BY created_at;

Evidence packaging and chain-of-custody

- Forensic bundle manifest fields (text file): incident_id, collector, collection_time_utc, region, object_paths, sha256s, signature_key_id, legal_hold_flag, hashing_algorithm.
- Every artifact must be accompanied by a signed manifest entry. Use the internal signing tool:
  sign-artifact --key-id=forensics-2026 --file=/tmp/audit-20260220.gz --out=/tmp/audit-20260220.gz.sig
- Maintain chain-of-custody log in our case management system (security-incidents/INC-123) recording who accessed each staging object and when.

Data residency and cross-border considerations

- If evidence contains residency-restricted customer data, keep copies only in regionally compliant forensics buckets and set confidentiality=restricted.
- If a copy must be moved for law enforcement or cross-region analysis, the Network & Residency Lead must record the legal basis and update the manifest with destination region and legal approval ID.

Restoration, remediation, and authorization hardening (post-containment)

1) Determine rollback vs. patch: if entitlement change was human error (e.g., bad rollout), prefer rollback to last-good policy snapshot. If root cause is a policy enforcement bug, deploy an annotated patch with tests.
2) Enforce short-term role rotation: rotate secrets for any service account that had elevated access (SLO: rotation within 4 hours for direct compromise suspects).
3) Reapply least-privilege baseline and run the entitlement conformance test-suite (see SDLC section below).

Post-incident evidence workflow and compliance deliverables

- Deliver an evidence bundle within 72 hours containing: manifest, signed audit exports, signed entitlement snapshot, network metadata, and a remediation timeline.
- For incidents impacting customers, produce a customer-facing summary template and a redacted evidence bundle scoped to the customer and approved by Legal.

SDLC integration and forward controls

- All authorization policy changes must pass the pre-deploy policy static analysis and test-suite (policy-lint, policy-simulate, policy-e2e). The incident should seed new unit/integration tests that replicate the failure vector.
- CI gate: policy changes touching high-privilege roles require two approvers from the security rota and a signed justification comment in the PR.
- Release-time evidence hook: any admin console change triggers an automatic audit snapshot that is stored for 180 days.

Automation snippets and useful commands

- Create immutable S3 object with retention (example):
  aws s3api put-object --bucket redwood-forensics-INC123 --key audit/audit-20260220.gz --body ./audit-20260220.gz --metadata file-signer=EvelynPark --object-lock-mode GOVERNANCE --object-lock-retain-until-date 2030-12-31T00:00:00Z
- Query session store for active tokens (redis example):
  redis-cli -h session-cache.redwood keys 'session:*tenant:t-123*' | xargs -L1 redis-cli -h session-cache.redwood ttl > /tmp/session-ttls.txt

Retention, legal hold and evidence lifecycle

- Default evidence retention: 7 years for high-severity incidents; 3 years for moderate incidents unless Legal extends.
- Legal hold takes precedence over normal retention; manifests must include legal_hold_flag=true.

Reporting and postmortem requirements

- Trigger post-incident review (PIR) for Sev 1/2 incidents within 7 calendar days. PIR deliverables: timeline, root cause, remediation verification, regression tests added to CI, and evidence bundle index.
- Update risk register entry for the affected entitlement patterns and track mitigation completion in the quarterly roadmap.

Appendix: quick-reference checklist

1) Triage & notify: IC, Authz Lead, Audit Lead, Legal (if PII) — within 1 hour.
2) Contain: revoke tokens, suspend implicated roles, feature-flag endpoints — within 1 hour.
3) Snapshot evidence to immutable staging bucket with sha256 and signatures — within 1 hour.
4) Package manifest, sign artifacts, log chain-of-custody — within 24 hours.
5) Deliver compliance-grade evidence bundle and customer communications (if applicable) — within 72 hours.
