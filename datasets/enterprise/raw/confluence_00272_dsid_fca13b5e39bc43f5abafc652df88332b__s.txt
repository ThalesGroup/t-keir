Service Traffic Shepherding and Devolution Playbook

Overview

Purpose: This playbook documents the design, operational guidance, dashboards, and runbooks for service traffic shepherding — the platform layer that routes customer requests across model variants, regions, and capacity tiers — and the controlled devolution behaviors used when primary paths become degraded. The approach balances latency SLOs, cost targets, and reliability.

Audience: Platform engineers, oncall, SREs, and product engineers implementing routing policies for inference endpoints.

Scope

- Systems covered: platform_router, request-mux, model-variant-proxy, cached-kv-service, per-customer-shaper.
- Environments: hosted API, dedicated GPU pools, private deployments (where the same primitives exist).
- Excludes: client-side retry strategies (refer to SDK guides).

Goals

- Maintain 99.95% request success for production endpoints with p95 latency < 120ms for short-prompt paths.
- Keep median cost-per-token within configured budget tiers by active routing decisions and quantization fallbacks.
- Provide deterministic, observable devolution (graceful downgrade) when downstream capacity or quality degrades.

Terminology

- Primary path: preferred region/model/variant for a request by policy.
- Devolution: controlled downgrade to a lower-cost or lower-latency variant or cached response when primary fails or breaches SLOs.
- Shepherding policy: a configured set of rules (latency target, cost cap, region affinity) that the router uses to pick routes.

Ownership & SLAs

| Component | Owner | SLO | Alert Owner |
|---|---|---:|---|
| platform_router (service) | eng-platform-routing | 99.95% success, p95 < 120ms | platform oncall |
| model-variant-proxy | eng-serving-runtime | 99.9% per-model availability | runtime oncall |
| cached-kv-service | eng-platform-batching | 99.99% hit availability | infra oncall |

Routing Policies (high level)

- Priority ordering: region-local low-latency variants -> region-low-cost (quantized) -> global fallback -> cached prefix -> error.
- Cost-aware decisioning: for routes tagged with budget:strict the router computes expected token-cost baseline and avoids variants with >15% expected cost overhead unless latency SLO would otherwise be missed.
- Quality guardrails: model-variant must pass recent quality checks (rolling eval failure rate < 0.5%) to be eligible.
- Affinity and stickiness: traffic is sticky by route_key (customer_id + model_id + session_id) for KV-cache warmness.

Routing Policies: Example YAML

```
policy_name: interactive-low-latency
latency_slo_ms: 120
cost_cap_pct: 15 # relative to baseline variant
variant_preference:
  - name: model-1.7b-lowlat
    region_pref: us-west-2
    quality_threshold: 0.5
  - name: model-1.7b-quantized
    region_pref: us-west-2
    quality_threshold: 1.0
  - name: model-legacy-3b
    region_pref: global
    quality_threshold: 0.8
devolution:
  cache_prefix: true
  fallback_message: "service_unavailable_try_again"
```

Implementation primitives

- feature-flag:router-devolution-enabled (per-tenant)
- sidecar:local-proxy (Envoy) that performs initial health checks and local devolution to cache.
- circuit-breakers: per-variant open when error_rate > 3% for 60s.
- tokenized-cost-estimator: microservice that estimates expected token cost and latency using request metadata and recent perf curves.

Dashboards & Alerts

Primary dashboards to maintain and review weekly:

1) Traffic Shepherding Overview (team dashboard)
   - Widgets: total routed QPS, p50/p95/p99 latency by route_key, cost per 1k tokens by variant, active devolution rate.
   - Prometheus/Tempo queries:
     - avg_over_time(request_latency_ms[5m]) grouped by variant
     - increase(routed_requests_total[5m]) by (route_key, variant)
     - sum_over_time(token_cost_cents_total[5m]) / sum_over_time(routed_requests_total[5m])

2) Devolution Heatmap
   - Widget shows % of requests devolved by hour and by customer. Use to detect noisy tenants.

Alerting thresholds (examples)

- router_devolution_rate_high: if devolution_rate > 5% for 5m for any prod tenant -> Sev2 -> paging to platform oncall.
- variant_error_spike: if variant_error_rate > 3% for 1m and p95 latency > 300ms -> Sev1 (runtime + platform)
- cost_overrun_alarm: if rolling 6h cost per token for policy > cost_cap_pct threshold -> notify cost-ops slack and product

Runbook: Active Devolution Recovery (Sev2 -> Escalate to Sev1 if unresolved)

1) Triage (0-5m)
   - Identify impacted route_keys via Shepherding Overview dashboard.
   - Check recent deploys: `git log --since=\"1 hour\" deploys/router`.
   - Verify router health: `kubectl -n platform get pods -l app=platform-router` and `kubectl logs` of failing pod.

2) Short-term mitigation (5-15m)
   - If global variant is failing, enable feature-flag `router-force-fallback-to-cache` for affected tenants: `ffcli set router-force-fallback-to-cache on --tenants tenant-id-1,tenant-id-2`.
   - Reduce routing churn: set `policy.max_retries=1` to prevent cascading retries.

3) Variant circuit-breaker action (15-45m)
   - Open the variant in the router: `POST /admin/variants/{variant}/open` (internal admin API) or use the admin console.
   - Monitor for stabilization for 10 minutes.

4) Restore & verification (45-90m)
   - Once variant metrics return to baseline, move variant to half-open and monitor for 30 minutes.
   - Roll back any temporary feature flags and verify cache warmness for sticky flows.

5) Post-incident (within 48h)
   - Populate incident timeline, attach dashboard snapshots, and run the retrospective checklist below.

Automated Remediations (playbook primitives)

- Auto-devolution rule: when variant_error_rate > 2.5% AND p95_latency > 250ms for 90s, router will automatically route 50% traffic to next eligible variant and escalate.
- Auto-warm cache: when traffic shifts to cache fallback, trigger background prefetch for top-10 prefixes per tenant.

Canary and Rollout Guidance

- Always enable flag `router-new-routing-algo` in staged mode with a 1% traffic shard for 24h, measure devolution_rate and cost impact; increase to 10% for 12h before 50%.
- Runload tests with synthetic traffic matching customer distributions (tool: load-shepherd). Use realistic token-length distributions.

Retrospective Checklist (post-incident)

- Confirm the timeline is complete and slos.
- Quantify cost impact of devolution and estimate 30-day delta.
- Identify a single corrective action owner and due date.
- Decide whether to add a new alert or adjust thresholds.

Roadmap: Next 6–12 months (prioritized)

1) Cost-informed routing 2.0: integrate per-tenant cost budgets and automatic spend throttling (Q2 2025).
2) Per-customer quality profiles: allow customers to set quality-first vs cost-first routing preferences in console (Q3 2025).
3) ML-driven prediction: use short-window ML models to predict variant degradation and proactively shift traffic (experiment Q4 2025).

Team Wiki Notes & Operational FAQs

- Q: When should we prefer cache devolution vs quantized variant?
  A: Cache devolution if prefix coverage > 30% and latency requirement <= 50ms. Prefer quantized variant when output quality must be preserved and latency SLO can be relaxed to <= 200ms.

- Q: Who can flip router-level feature flags?
  A: Platform leads + oncall SREs. For emergency toggles, product and security must be notified in the incident channel.

```

```
