Hardware tuning profiles: known issues and mitigations (living)

## Purpose
This page is a living list of issues we have observed (or can reliably reproduce) when enabling the **hardware tuning profiles pack** for the serving runtime (H100, B200, L40S). Each issue includes:
- Symptoms you can validate quickly (what customers/oncall will see)
- How to detect (metrics/log signatures)
- Immediate mitigation steps (safe toggles/flags)
- Longer-term fix status (when known)

This is *not* an incident log. It is intended to reduce time-to-triage during rollouts and prevent repeated regressions.

**Primary audience:** Runtime oncall, SRE, Infra rollout owners, Support/Solutions.

**Owner:** Serving Runtime (Scheduling + Kernels). Operational upkeep coordinated by SRE.

---

## How to use this page during an incident
1) Identify the deployment + pool + GPU SKU (H100/B200/L40S) and confirm whether a profile is selected.
2) Check if the symptom matches one of the patterns below.
3) Apply the mitigation in the order listed (prefer “revert to baseline/default profile” over ad-hoc knob edits).
4) If mitigation requires disabling profiles for a pool/region, follow the rollout runbook and record the toggle + time window.

**Fast checks (recommended order):**
- Runtime startup logs: profile version + compatibility matrix (runtime version vs profile pack)
- Metrics: `runtime_profile_selected{sku,profile}` and `runtime_profile_override_source{source}`
- Tail latency: p95/p99 by route/model, segmented by profile
- OOM/restart rate and GPU memory headroom

---

## Common mitigations (safe-by-default toggles)
These are the mitigations referenced throughout the issue list.

### A) Disable profile selection (force baseline)
- **Use when:** unknown regression, ambiguous GPU detection, widespread tail-latency increase.
- **Effect:** runtime falls back to built-in baseline defaults.
- **Notes:** Use per-pool override first; avoid global unless impact is broad.

### B) Force a specific profile mode (e.g., H100 balanced)
- **Use when:** throughput-first mode causes tail latency or streaming instability.
- **Effect:** keeps profile benefits while restoring fairness/backpressure.

### C) Reduce batching / tighten queue limits
- **Use when:** tail latency spikes, request queue growth, streaming stutter.
- **Effect:** reduces queueing delay at the cost of throughput.

### D) Constrain KV cache budget
- **Use when:** OOMs, frequent restarts, memory fragmentation, long-context workloads.
- **Effect:** caps memory reserved for KV cache; may reduce max concurrency for long contexts.

### E) Disable experimental B200 profile
- **Use when:** any regression in B200 pools; if driver/CUDA mismatch suspected.
- **Effect:** revert to H100-like baseline or “generic” safe config.

(Exact flag/env/Helm key names vary by deployment mode; see the rollout runbook and the profile schema doc for current canonical names.)

## Known issues (by category)

### 1) Pathological prompt distributions / workload mismatch

#### KI-PP-001: Long-prefill-heavy workloads regress tail latency under throughput-first scheduler presets
**Applies to:** H100 (primarily), sometimes B200 when experimental mode is enabled.

**Symptom(s):**
- p95/p99 latency increases (often 20–60%) while average tokens/sec improves.
- Queue depth increases; “time-to-first-token” (TTFT) regresses most.
- Customers report “slow start” on long prompts, especially during load spikes.

**Likely trigger:**
- Workload skewed to long prefill (e.g., large context ingestion, retrieval-heavy prompts, tool-call scaffolding) combined with high concurrency.

**How to detect:**
- Segment by request type: prefill vs decode (if available).
- Look for disproportionate increase in TTFT and “prefill queue wait time.”
- `scheduler_fairness_adjustments_total` trending up (if instrumented) alongside tail latency.

**Mitigation:**
1) Switch pool to **balanced** mode profile (B).
2) Tighten max queue depth / reduce batching (C).
3) If still regressing: disable profiles for the pool (A) and proceed with rollback criteria.

**Status / notes:**
- A similar tail-latency regression was previously fixed in the prefill/decode fairness logic; if this appears after a profile pack update, treat as a candidate regression and compare to prior profile pack version.

---

#### KI-PP-002: “Too-clean” benchmark prompt mix hides streaming instability
**Applies to:** H100, L40S.

**Symptom(s):**
- Benchmarks pass; real traffic shows intermittent streaming stalls (“chunky” streaming) and elevated partial-response retries.
- p50 steady; p95 spikes correlate with peak concurrency.

**Likely trigger:**
- Real prompts include tool-calling patterns, high variance in output length, or client-side disconnects; these stress backpressure/streaming buffers.

**How to detect:**
- Increase in `stream_send_blocked_seconds` (or equivalent), and `client_disconnects_total` correlated with latency spikes.
- Elevated `request_retries_total{reason="upstream_timeout"}` on streaming routes.

**Mitigation:**
1) Reduce max in-flight streams per worker / tighten backpressure settings (C).
2) Prefer balanced mode (B) for streaming-heavy pools.
3) If stability issues persist, rollback profiles for the pool (A) and file an issue to expand workload matrix coverage.

**Status / notes:**
- Treat as a “workload matrix gap” if it passes canary but fails in prod; update the workload matrix with a representative streaming mix.

### 2) KV cache, memory fragmentation, and OOM patterns

#### KI-MEM-001: L40S OOMs under long-context + high concurrency due to KV cache over-reservation
**Applies to:** L40S.

**Symptom(s):**
- Sudden OOMs during prefill on long contexts; pods restart.
- GPU memory headroom oscillates; fragmentation increases over time.
- p95 latency spikes preceding OOMs (retries and warm-up effects).

**Likely trigger:**
- L40S has tighter memory constraints; aggressive KV cache budgeting that is safe on H100 can be unsafe on L40S.

**How to detect:**
- `gpu_oom_events_total` increases.
- `gpu_memory_free_bytes` trends downward across hours even at similar QPS (fragmentation pattern).
- Runtime logs mention KV cache allocation failure or emergency eviction.

**Mitigation:**
1) Enforce L40S profile with explicit KV cache budget constraints (D).
2) Reduce max batch size and/or max queued requests (C).
3) If OOMs continue: disable profiles (A) and set conservative runtime memory defaults until re-validated.

**Status / notes:**
- If you see “creeping” fragmentation, capture an hourly memory snapshot and attach to the tracking ticket; this typically indicates a reuse/allocator behavior mismatch for this workload.

---

#### KI-MEM-002: Memory fragmentation leading to degraded throughput after several hours (allocator behavior)
**Applies to:** L40S (most common), occasionally H100 in high churn traffic.

**Symptom(s):**
- Tokens/sec gradually declines over time; p50 stable but p95 creeps.
- No explicit OOMs; instead, more frequent small allocations and cache thrash.

**Likely trigger:**
- High variance in sequence lengths and frequent cancellations time-slice allocations differently than the benchmark harness.

**How to detect:**
- `kv_cache_evictions_total` increases without QPS growth.
- `gpu_memory_fragmentation_ratio` (if available) increases.
- Elevated `cuda_malloc_retry_total` / allocator warning logs.

**Mitigation:**
1) Reduce KV cache target utilization (D).
2) Prefer settings that reduce churn: cap max concurrent long-context requests (C + D).
3) If impact is severe: roll pool and disable profiles (A) pending deeper allocator analysis.

**Status / notes:**
- Often shows up only on specific traffic mixes; request a traffic replay / prompt distribution sample (sanitized) to reproduce.

### 3) Kernel selection mismatches and micro-architecture assumptions

#### KI-KRN-001: Kernel auto-selection chooses a suboptimal path for short sequences, causing TTFT regression
**Applies to:** H100; can affect B200 if heuristics borrowed.

**Symptom(s):**
- TTFT regresses for short prompts (e.g., <256 tokens input) while long prompts improve.
- Overall throughput may appear neutral, but UX impact is high for chat-like workloads.

**Likely trigger:**
- Heuristic bucket boundaries (sequence length bins) don’t match the real distribution; “short” bucket gets a kernel optimized for different occupancy characteristics.

**How to detect:**
- Segment TTFT by prompt length buckets.
- Compare `kernel_selected{bucket=...}` distribution pre/post profile.

**Mitigation:**
1) Switch to balanced mode or the “general” kernel selection preset for that SKU (B).
2) If available, enable adaptive kernel selection rather than pinned selection for short buckets.
3) If no safe option: disable profiles (A) for the affected pool.

**Status / notes:**
- When filing a follow-up, include bucket histograms (input/output length) and the kernel selection stats.

---

#### KI-KRN-002: Kernel mismatch when GPU SKU string detection is ambiguous (provider-specific strings)
**Applies to:** All SKUs; most common in mixed fleet environments and during provider expansion.

**Symptom(s):**
- Runtime selects “generic” profile unexpectedly, or selects the wrong SKU profile.
- Performance deviates from expectations; in worst cases, stability issues if an incompatible toggle is applied.

**Likely trigger:**
- GPU model strings differ across drivers/providers/instance types (e.g., formatting or suffix variations).

**How to detect:**
- Startup log shows `gpu_sku_raw` and `gpu_sku_normalized` mismatch; profile selection metric shows fallback.
- Increased rate of `profile_selection_ambiguous_total`.

**Mitigation:**
1) Force explicit SKU/profile via pool override (B) until detection is fixed.
2) If forced override is not possible: disable profiles (A) and run with baseline.
3) File an Infra ticket with the raw strings and node types involved; add to normalization allowlist.

**Status / notes:**
- This should be treated as a correctness issue, not “just performance.” Incorrect profile selection can invalidate canary results.

### 4) Scheduler/backpressure edge cases

#### KI-SCH-001: Queue growth + timeouts during burst traffic due to queue limit mismatch with upstream timeouts
**Applies to:** H100, L40S.

**Symptom(s):**
- Requests time out upstream; runtime appears healthy but queue depth spikes.
- p99 latency spikes; retries increase; effective throughput drops.

**Likely trigger:**
- Profile queue limits allow too much buffering relative to gateway/client timeouts; burst traffic fills queue faster than it drains.

**How to detect:**
- `request_queue_depth` increases; `gateway_timeouts_total` increases.
- `queue_wait_ms` becomes dominant contributor to latency.

**Mitigation:**
1) Reduce queue limits and tighten backpressure (C).
2) Align per-route timeout budgets with expected max queue wait.
3) If customer impact persists, rollback profile for pool (A) and re-validate burst behavior.

**Status / notes:**
- Prefer smaller queues and more explicit load shedding for customer-visible endpoints; large queues hide overload until timeouts cascade.

---

#### KI-SCH-002: Multi-tenant interference in Dedicated pools when throughput-first batching is enabled
**Applies to:** Dedicated H100 pools with mixed tenant traffic.

**Symptom(s):**
- One tenant’s long-context or high-output requests dominate batching windows.
- Other tenants see tail-latency regressions and inconsistent TTFT.

**Likely trigger:**
- Batching parameters optimized for aggregate throughput without sufficient per-tenant fairness constraints.

**How to detect:**
- Latency segmented by tenant spikes for “small” tenants during another tenant’s traffic burst.
- Batch composition metrics show high skew.

**Mitigation:**
1) Switch pool to balanced profile mode (B).
2) Apply stricter per-tenant concurrency limits (if configured via routing/gateway).
3) If needed, split tenants to separate pools (operational action) and re-run perf validation.

**Status / notes:**
- Treat as a product/SLA concern; do not “optimize away” fairness unless the pool is explicitly single-tenant.

### 5) B200 experimental profile (maturity and compatibility)

#### KI-B2K-001: Driver/CUDA mismatch causes silent fallback or instability
**Applies to:** B200 only (experimental gated).

**Symptom(s):**
- Profile not applied even when enabled; runtime logs show version guardrails tripping.
- In some cases: increased error rate, sporadic kernel launch failures.

**Likely trigger:**
- B200 profile requires minimum driver/CUDA stack; partial fleet upgrades lead to mixed compatibility.

**How to detect:**
- Startup logs show “incompatible stack” warning and selected fallback.
- `profile_compatibility_violation_total{sku="B200"}` increases.

**Mitigation:**
1) Disable experimental B200 profile for the pool (E).
2) Verify driver/CUDA versions match the B200 bring-up checklist; upgrade fleet before re-enabling.
3) Re-enable only with canary gating and a rollback plan.

**Status / notes:**
- Default posture for B200 remains “gated + explicit enablement.” Treat any enabling as a staged change with extra SRE oversight.

---

#### KI-B2K-002: Cross-region regression requiring pool-level disable (known precedent)
**Applies to:** B200 (experimental) in specific pools/regions.

**Symptom(s):**
- Immediate p95 regression post-enable; canary gate triggers or customer reports.

**How to detect:**
- Perf canary gate breach for B200 pools; increased tail latency segmented by region.

**Mitigation:**
1) Disable experimental B200 profile for the impacted pool/region (E).
2) Leave other regions unchanged until root cause is understood.
3) Capture: node type, NCCL/topology characteristics (if multi-GPU), and driver stack details.

**Status / notes:**
- Regional differences (network topology, firmware, provider) can invalidate assumptions. Ensure each region has baseline curves.

## Observability: what to capture when filing a follow-up
When escalating to Runtime (Scheduling/Kernels) or Infra, include:
- Deployment mode (Hosted/Dedicated/Private), region, pool name, GPU SKU, MIG status (if any)
- Runtime version + profile pack version
- Selected profile and override source (fleet default vs per-pool vs per-deployment vs manual)
- Before/after comparison window and traffic level (QPS, concurrency)
- Workload characteristics: prompt length distribution, output length distribution, streaming vs non-streaming share
- Key metrics: p50/p95/p99 latency, TTFT, tokens/sec, queue wait, OOM/restart rate
- Relevant logs: startup compatibility matrix, kernel selection summary, allocator warnings

## Update process (for maintainers)
- Add a new entry when: (a) reproducible in perf suite, (b) observed in prod and confirmed profile-related, or (c) known hazard with a clear mitigation.
- Retire an entry only when the mitigation is no longer needed *and* the fix is present in the supported runtime/profile versions.
- Keep entries terse and operational. Link deeper analysis to the relevant PR/ADR/ticket.
