GPU Capacity Scenario Simulator & Release-Gating Runbook

Summary:
This runbook describes the GPU Capacity Scenario Simulator (GCSS), the CI/CD gating rules that use it, and the operational playbook for validating capacity, egress and latency SLOs before fleet or IaC changes are promoted to production. The simulator is used by infra, SRE and platform teams to exercise heterogeneous tenant mixes, preemptible/spot behavior, burst credits, and multi-region egress scenarios.

Purpose and scope:
- Purpose: prevent capacity-induced latency regressions and unexpected tenant failures by running automated scenario simulations as part of merge/merge-to-main and release pipelines.
- Scope: covers GPU fleet sizing changes, node-image/kernel/cuda driver rollouts, Terraform changes that modify topology or pool sizing, and routing/egress configuration updates. It does not replace full canary or live-traffic tests; it complements them.

Owners and escalation:
- Primary owner: infra-capacity@redwood (team: engineering)
- Secondary owner: platform-sre@redwood
- Pager: infra-oncall (rotation) for simulator infra failures

SLOs and acceptance criteria (must be checked by the simulator):
1) 95th percentile tail latency for interactive workloads must not regress > 10ms vs baseline for target load.
2) Per-tenant error-rate must remain < 0.2% under expected burst conditions.
3) Egress budget usage must not exceed 125% of expected for any tenant in worst-case simulation.
4) KV-cache warmup time for seeded workloads must be <= configured warmup window (default 60s).

Signals and telemetry used by GCSS:
- request.latency.p95, request.latency.p99, request.error_rate, tenant.egress.bytes, gpu.utilization, node.preemptions.count, kvcache.hit_rate
- Dashboards: infra -> Capacity -> GCSS-simulations (panel names listed at the end).

Components and where they live:
- Simulator binary: infra/gcss (Go) — repo: git.internal/redwood/infra/gcss
- Scenario catalog: infra/gcss/scenarios (YAML driven)
- Test harness: ci/gcss-runner (Buildkite) + local runner script (scripts/run_simulation.sh)
- IaC validator: Terraform module scanner (tf-iac-validator) invoked as part of pipeline
- Outputs: artifacts (JSON reports) stored in s3://redwood-gcss-results/<run-id>/report.json and snapshot traces in ClickHouse.

How to run locally (quickstart):
1) git clone git.internal/redwood/infra/gcss && cd gcss
2) ./scripts/setup-local.sh  # provisions local docker-compose lightweight simulator (dev env)
3) ./bin/gcss simulate --scenario scenarios/multi-tenant-burst.yaml --output ./out/report.json
4) jq .summary ./out/report.json   # high-level pass/fail

Common scenario YAML (extracted):
---
name: multi-tenant-burst
duration_s: 600
traffic_profiles:
  - tenant: sandbox-1
    qps: 30
    burst_pattern: { type: spike, peak_qps: 300, start: 120, length: 30 }
  - tenant: analytics
    qps: 10
    background_distribution: poisson
node_pool_config:
  - type: p4d.xlarge
    count: 12
    spot_mixed: true
kv_cache_seed: true
egress_shapers: true
rollback_thresholds:
  latency_p95_ms: 10
  tenant_error_rate_pct: 0.2
---

Terraform/IaC considerations (checklist):
- All topology-changing TF plans must include a preflight simulation step: run gcss simulate with the target plan (see pipeline step below).
- Use tfvars snapshot that mirrors production tenancy and token distribution. A small mismatch here invalidates results.
- Add tf-iac-validator annotation in module outputs: "gcss-expected-profile = \"stable\"" for modules that are capacity-sensitive.
- Modules that alter NAT/Gateway/egress rules must include egress budget estimates in outputs (see table below).

Required Terraform outputs (standardized table):
| output_name | type | description | example |
| pool_size | number | number of GPUs in pool | 48 |
| pool_type | string | instance family | p4d |
| expected_egress_bytes_per_hour | number | conservatively estimated egress | 5_000_000_000 |

CI/CD pipeline integration (Buildkite example):
1) On PR to infra modules: run tf plan -> if plan touches pool_size/pool_type/egress -> enqueue GCSS preflight job.
2) GCSS preflight job downloads a plan-derived scenario (scripts/plan_to_scenario.py) and executes ./bin/gcss simulate --scenario <generated.yaml>.
3) Upload results: artifacts and report.json. Run simple validator script that enforces rollback_thresholds.
4) If validator fails: block merge and create issue in repo with run-id and links to artifacts.
5) If validator passes: promote plan to canary lane (small-scale live rollout) per canary runbook.

Validation thresholds in pipeline (example):
- If latency_p95 increases by >10ms: fail
- If any tenant error_rate > 0.5%: fail
- If total egress > 140% expected: warn + manual review

Scenario catalog (recommended minimum set):
- baseline-steady: 24h low-variance traffic (validation of long-term steady state)
- burst-weekend: multiple tenants spike pattern (simulates marketing/PLG events)
- preempt-storm: simulate 20% spot preemption across pools in wave pattern
- cross-region-egress: simulate tenant traffic funneling through single egress region (egress hotspot)
- canary-scaleup: validate scale-up/scale-down stabilization patterns

Operational runbook (what to do when a preflight fails):
1) Triage the GCSS run: open the report.json, inspect failures and golden traces. Look at run-id and link to ClickHouse traces from artifacts.
2) If failure is latency-related: examine node pool CPU/GPU utilization and kvcache hit_rate. Common mitigations: increase pool_size by N% (typical N=10), enable extra warmup seeds, tune batching window.
3) If failure is egress-related: verify egress_shapers and NAT mapping; consider moving tenant to regional egress or increase egress allocation.
4) If failure is preemption-related: toggle spot_mixed flag to false and re-run, or increase warm pool.
5) Re-run simulation with adjusted tfvars and document results.
6) Once passing, create a follow-up canary rollout ticket and schedule a live canary per canary-runbook.

Escalation matrix (short):
- Infra engineer (owner) -> Platform SRE -> Head of Infra. For production degradations after rollout, follow the Incident Response playbook and engage PG and CS as needed.

Maintenance and cadence:
- Scenario catalog review: quarterly (owners: infra-capacity).
- Simulator binary: minor releases aligned with infra-tooling cadence (monthly). Major upgrades must be accompanied by an interlock with SRE and an ML-backed workload rebaseline.

Observability and dashboards (panels to check):
- GCSS / Latest run summary (pass/fail, failure categories)
- p95 latency delta vs baseline (panel: infra.capacity.gcss.latency_delta)
- tenant.egress.percent_of_expected (panel: infra.egress.gcss.percentage)
- node.preemptions.count time-series for run window

Artifacts and retention:
- Report JSONs stored in s3 for 90 days, traces stored in ClickHouse for 180 days. Golden baseline snapshots are stored under s3://redwood-gcss-baselines/<baseline-id>/

Post-run checklist (required to mark a preflight as reviewed):
1) Confirm report summary and attach to PR (author).
2) Reviewer inspects p95 delta and selects pass/fail with comment (reviewer).
3) If pass: merge with comment linking run-id. If fail: author must iterate.

Appendix A — Example validator snippet (pseudo-shell):
#!/bin/bash
REPORT=$1
LAT_DELTA=$(jq .summary.latency_p95_delta_ms $REPORT)
ERR_RATE=$(jq .summary.max_tenant_error_rate $REPORT)
EGRESS_PCT=$(jq .summary.max_egress_pct_expected $REPORT)
if (( $(echo "$LAT_DELTA > 10" | bc -l) )); then
  echo "FAIL: latency p95 regression > 10ms"; exit 1
fi
if (( $(echo "$ERR_RATE > 0.005" | bc -l) )); then
  echo "FAIL: tenant error rate > 0.5%"; exit 1
fi
if (( $(echo "$EGRESS_PCT > 1.4" | bc -l) )); then
  echo "WARN: egress > 140% expected"; exit 2
fi
exit 0
