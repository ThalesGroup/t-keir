Runtime workload signatures and SLO derivation playbook

Summary
-------
This playbook describes a repeatable process for converting observed runtime workload signatures into defensible Service Level Objectives (SLOs) and cost-sensitivity profiles for Redwood inference services. It ties together sampling, profiling, experiment design, and SLO derivation so teams can make consistent, evidence-based SLOs for new routes, model variants, and capacity plans.

Scope
-----
Applies to: all inference-facing HTTP/streaming routes and internal RPCs that contribute to model-serving latency or cost. Excludes: purely offline batch jobs (see eng-infra runbooks) and human-in-the-loop lab experiments.

Definitions
-----------
- Workload signature: a compact description of request shape and distribution (sequence length percentiles, batching patterns, KV cache hit ratio, request concurrency, special flags like streaming or tool-calls).
- Cost-sensitivity: the change in per-request GPU/time cost when a workload attribute shifts (e.g., +10 tokens => +X ms / +Y token-cost).
- SLO bucket: a named target (e.g., P95 latency 120ms for interactive, P99 500ms for high-throughput) tailored for a workload class.

Key Principles
--------------
- Evidence-first: SLOs must be justified by sampled production telemetry and controlled experiments.
- Workload-driven segmentation: avoid one-size-fits-all SLOs; segment by signature clusters that materially change cost/latency.
- Cost-aware guardrails: every SLO must include an associated cost-sensitivity statement used for tradeoff decisions (e.g., whether to enable larger batch sizes or fallback to cheaper model variants).
- Operational observability: each derived SLO must have dashboards, automated alerts, and an attached experiment plan for periodic revalidation.

Procedure: Derive SLOs from workload signatures (step-by-step)
-----------------------------------------------------------
1. Collect signatures (1–2 weeks):
   - Instrument route to emit compact signature blobs at sampling rate 1–5% (configurable per traffic volume). Required fields: route_id, timestamp, seq_len, input_tokens, output_tokens, kv_cache_hit, streaming_flag, client_tier, model_variant_hint.
   - Example signature JSON (emit to telemetry):

   {
     "route_id": "generate-chat",
     "timestamp": "2025-10-28T14:12:33Z",
     "seq_len": 1024,
     "input_tokens": 128,
     "output_tokens": 256,
     "kv_cache_hit": 0.62,
     "streaming_flag": false,
     "client_tier": "standard"
   }

2. Cluster signatures (offline job):
   - Run k-means / hierarchical clustering on normalized features: seq_len, total_tokens, kv_cache_hit, streaming_flag (binary), concurrency_hint. Aim for 3–6 clusters per route unless variance indicates more.
   - Save cluster centroids and representative percentiles (p50/p90/p99) for each numeric field.

3. Profile representative clusters (controlled experiments):
   - For each cluster, replay 10k representative requests against target model variants and runtime configurations (batch sizes, quantization profiles, kernel paths). Collect: p50/p90/p99 latencies, tail latency (p999), token throughput, GPU utilization, memory pressure, failure rate.
   - Record cost-per-request estimate (energy + GPU time + amortized infra) using the internal cost-modeler.

4. Construct candidate SLO buckets:
   - Use profiling results to propose SLOs that are achievable with a 95% confidence margin given current infra. Example logic: set P95 latency target to profiling p90 + 15% buffer; set error-rate target to observed mean + 3σ but not exceeding 1%.

5. Attach cost-sensitivity and fallback policy:
   - For each SLO, include a table showing how latency and cost change when you: increase batch_by, enable quantization Q4/Q5, or downgrade to smaller model variant.
   - Define automatic fallback thresholds (e.g., if queue length > 200 and P95 approaching target, route 20% to cheaper variant).

6. Review and publish with runbook:
   - Include owners (service, infra, SRE), approval from product for user-facing impact, and security sign-off when signatures include user data.

7. Deploy SLO and monitor:
   - Create dashboards that show per-cluster SLI trends, cost-per-1000-requests, and deviation from target. Configure alerts: SLO_red (p95 > target for 10m), SLO_yellow (p95 > 90% of target for 15m), cost_alert (cost growth > 20% week-over-week for the cluster).

Cost-sensitivity matrix (example)
--------------------------------
- Changing batch_size from 1 -> 8 on `Normal` cluster: +20% p95, -30% cost/request.
- Enabling Q4 quantization on `Long-turn`: +12% p95, -45% cost/request, memory drop 18%.

Operational playbook snippets
---------------------------
- When an SLO_red fires (p95 > target for 10m):
  1. Pager to oncall (SRE) and service owner.
  2. Run the quick triage checklist: confirm signature cluster involved, verify ongoing experiment/rollout, check GPU node saturation and preemption events.
  3. If saturation: trigger temporary priority decay policy and increase fallthrough to cheaper variant per SLO fallback policy.
  4. Post-incident: schedule a 2-hour root-cause session and update SLO derivation if recurring.

Best practices and guidance
---------------------------
- Prefer cluster-specific SLIs rather than global route-level; combine for a user-facing composite only when necessary.
- Maintain an experiment repository: every profiling run must have a reproducible seed, input corpus, model hash, and runtime flags.
- Re-derive SLAs quarterly or when a model variant, kernel path, or major infra change is shipped.
- Use conservative buffers for user-facing production routes (15–25%) and tighter buffers for internal tooling (5–10%).

Appendix: template for SLO record (to be copied into the SLO catalog)
--------------------------------------------------------------------
- route_id: string
- cluster_id: string
- cluster_signature_examples: list of example signature ids
- derived_SLOs: list of {metric: p95 latency, target_ms: number, buffer_pct: number}
- cost_sensitivity: list of {action: quantize/batch/downgrade, delta_cost_pct: number, delta_latency_pct: number}
- profiling_run_ids: list of run ids
- owners: list of emails
- rollback_plan: short text
