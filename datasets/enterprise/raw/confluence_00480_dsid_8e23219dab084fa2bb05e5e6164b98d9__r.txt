Release Readiness: Integrated Technical Gate for Runtime, Kernels, and Benchmarks

Overview

Purpose
This page defines the integrated technical gate that merges runtime architecture checks, kernel-scheduler validation, profiling smoke tests, and benchmark acceptance criteria into a single, repeatable release-readiness workflow. The gate is intended for major runtime releases, kernel rollouts, scheduler policy changes, quantization/format migrations, and any change that may materially affect latency/cost SLOs.

Scope
- Applies to changes merged into the runtime/main branch that will be deployed to production pools or dedicated capacity.
- Covers: kernel binary changes, scheduler policy DSL changes, KV-cache adjustments, batching/autotune algorithm updates, and observability/telemetry agents added to runtime.
- Not in scope: pure UI/console changes and non-runtime-facing documentation updates.

When to use
- Major version bumps (>=1.0.0 -> 1.1.0)
- Kernel ABI changes or accelerator/driver updates
- Scheduler policy changes that alter admission/backpressure behavior
- New autoscaling or eviction heuristics shipped to production

Roles & Ownership
- Release Lead: coordinates execution and signoff (Release Engineer on-call).
- Runtime Lead: technical owner of runtime arch and kernel compatibility (assigned eng owner).
- SRE: validates production-mirroring canaries, monitors post-deploy SLOs.
- Benchmarks Owner: runs and interprets perf suite and approves threshold passing.
- Observability Owner: verifies trace/metric sampling and budget configuration.

Integrated Gate checklist (automated + manual steps)
1) Pre-merge automated checks (CI) — must be green
   - Unit tests and integration tests with full mock KV and scheduler stubs.
   - Linting and static analysis for scheduler DSL changes.
   - Kernel ABI compatibility check (binary signature + interface tests).
   - Smoke profiling: 90-second microprofile run against a canary image.
     * Failure if P50 deviates >10%% from baseline or memory growth >15%%.

2) Controlled perf-suite run (pre-release) — automated but gated
   - Jobs: throughput_sustained, tail_latency_99_9, concurrency_scaling, mixed_workload_mirror.
   - Minimums: throughput within -6%%/+10%% of baseline; tail-99.9 latency not worse than +12%%.
   - Run on the same hardware class and driver versions intended for rollout.
   - Use synthetic corpus representing 60%% short chat, 30%% long completion, 10%% embeddings.

3) Scheduling & kernel handoff validation
   - Execute scheduler simulation harness for 12 hours with synthetic customer cohorts. Look for:
     * Priority inversion signals (request wait-time spikes correlated to lower-priority pods).
     * Kernel contention hotspots and cross-tenant interference.
   - Validate preemption/handoff latency is within configured guard rails (default: 150ms median handoff, 95th < 400ms).

4) Profiling and determinism checks (developer + perf engineer)
   - End-to-end profile capture (trace + GPU kernel timeline) for representative requests.
   - Determinism smoke: replay 50 trace samples, compare execution graph hash and KV cache warmup patterns.
   - Investigate if kernel ordering reorders >5%% of calls relative to baseline.

5) Flakiness & regression mitigation (benchmarks owner)
   - If any benchmark fluctuates between runs beyond historical variance band, perform: 3 additional runs, median wins.
   - Label results with run metadata (driver, kernel-commit, scheduler-flag snapshot, seed corpus version).

6) Canary deployment (SRE) — staged rollout to production-like pool
   - Canary size: 2%% of global production traffic or fixed slot count for Dedicated (whichever partitions to similar mix).
   - Monitoring window: 45 minutes steady-state + 3 hours accelerated traffic probing.
   - Abort rules (automatic): error-rate increase > 0.5pp absolute or token-cost spike > 20%% sustained for 10 minutes.
   - Manual abort: any SRE/release lead can stop and rollback immediately.

7) Observability & trace budget verification
   - Confirm span sampling is set to "release_high" for canary for the 3-hour window.
   - Verify traces produced include: kernel_id, scheduler_decision, execution_slot_id, kvcache_hits, quantize_profile_version.
   - Confirm metric rollups appear in the release dashboard within 5 minutes of traffic.

Acceptance criteria (final signoff)
- All CI gates green and no outstanding blocking defects.
- Perf-suite median results within acceptable deltas (throughput, tail).
- Scheduler simulation shows no priority inversion or catastrophic handoff regression.
- Canary window meets SLOs for 3x monitoring intervals and no auto/manual aborts.
- Observability traces and metrics verified and annotated.
- Release Notes drafted and peer-reviewed (incl. compatibility caveats).

Runbook: quick rollback steps
1. Trigger controlled traffic divert to previous runtime image (routing flag: runtime.fallback.image=sha256:<previous>).
2. Scale down new pods using staging selector and scale up previous replica set.
3. Invalidate caches on nodes where kernel artifacts changed: run node-tool flush-kvcache --node <id>.
4. Re-run minimal benchmark smoke to confirm restored baseline.
5. Open incident and attach perf capture and top-line metrics.

Observability budgeting and cost controls
- For any canary or perf-suite run lasting >2 hours, request a temporary trace-budget uplift via Observability Owner. Default trace-budget for routine canary: 10%% sampling on production traces, release_high: 50%% sampling for canary window.
- Annotate runs with label: release:<version> so sampling retention and export rules can be applied post-hoc.

Known caveats & interoperability notes
- Kernel change that touches 'direct-copy' path may temporarily increase PCIe transfers; expect short-lived memory-pressure signals. Plan to run memory-fragmentation diagnostic after any direct-copy kernel change.
- Scheduler policy 'async-preempt' can change handoff ordering; verify that KV-cache prefetch hints are still honored.
- Quantization profile upgrades must be tested for token-level quality regressions with the eval harness before committing to the gate.

Post-release hygiene
- Merge performance artifacts and annotated traces to the release artifact bucket: s3://redwood-release-artifacts/<release>/perf/
- Schedule a 1-week post-release review meeting to capture any slow-burn regressions.
- Add retro notes to runtime/team-wiki and link to this gate for future improvements.
