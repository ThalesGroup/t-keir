Telemetry-Driven Action Catalog and Operator Heuristics

Overview
-------
This document is an actionable catalog mapping platform telemetry signals to operator heuristics, automated remediations, and runbook play IDs. It is intended for platform SREs and operators who run the Redwood inference control plane and serving clusters. The goal is to reduce decision latency during incidents and to provide clear guidance for safe automation.

Context and scope
-----------------
- Scope: multi-tenant serving runtime, KV/prefix cache, GPU pools, request router, and telemetry-driven operator tasks.
- Audience: on-call SREs, platform operators, reliability engineers, and automation engineers.
- Alignment: complements the Observability SLI Onboarding Playbook and the Emergency Model Swap runbook.

How to use this catalog
-----------------------
1) Monitor: use the listed alert expressions and thresholds as the canonical starting point.
2) Triage: follow the heuristic decision tree to classify severity and likely root cause.
3) Act: choose manual steps or trigger the safe automation script referenced by play ID.
4) Post-incident: add notes to the incident ticket and update the catalog if new conditions are observed.

Signal categories and canonical plays
------------------------------------
1) Cache health signals
   - Signals: kv_prefix_cache_hit_rate, kv_prefix_cache_evictions_per_min, kv_prefix_cache_fill_latency_ms
   - Typical symptoms: increased per-request latency for cold prefixes, token cost spike for repeated re-generation, degraded throughput.
   - SLO guardrails: target kv_prefix_cache_hit_rate >= 0.85; alert when < 0.7 for 5m.
   - Play ID: C-REHYDRATE-01 (Rehydrate / Repair KV prefix cache)
   - Recommended operator heuristic: if evictions_per_min > 500 and hit_rate < 0.7: prioritize high-tenancy prefixes by weight and trigger targeted prefetch + backfill (automated), while enabling aggressive cache-retention for top 10 tenants (manual override option).
   - Safe automation: automated prefetch job that accepts a tenant whitelist and a max-rps budget. Example automation flag: --budget-tokens=50M --tenant-filter=top10-by-rps.

2) Tail-latency and headroom signals
   - Signals: inference_95th_latency_ms, inference_tail_percentile_spike_ratio, inflight_requests_per_instance
   - SLOs: 95th latency <= 220ms (small models), 95th <= 800ms (large models).
   - Play ID: L-TAIL-02 (Tail-latency soft-degrade and model-fallback)
   - Heuristic: if 95th latency breaches SLO by >20% and inflight_requests_per_instance > 75% capacity, first attempt adaptive batching reduction and KV rehydration; if still >2min, initiate model fallback to a compatible lower-latency variant with preserved semantics.
   - Manual safety checks: confirm fallback model has passed golden prompt-set checks (link in Related Pages) and that token cost delta is acceptable to the customer tier.

3) GPU pool and thermal/interference signals
   - Signals: gpu_temp_celsius, gpu_utilization_pct, gpu_context_switch_rate, gpu_preemption_events
   - Play ID: G-ISOLATE-03 (GPU interference isolation and live-evacuation)
   - Heuristic: sustained gpu_temp > 85C on >50% of devices in a pod -> schedule live-evacuation of affected pods to warm standby nodes, mark host for maintenance, and reduce batch size for tenants on that host. If preemption events spike, immediately migrate low-priority workloads and enable tenant burst-protections.
   - Operator actions: maintain a 5-node warm standby pool per region; use drain-with-warmup to avoid cold-start penalties.

4) Request router and routing fairness signals
   - Signals: tenant_queue_delay_ms, request_reject_rate, overflow_burst_credit_balance
   - Play ID: R-PRIOR-04 (Tenant prioritization and soft-quota enforcement)
   - Heuristic: when tenant_queue_delay > 300ms and burst_credit_balance < 0 for >2 minutes, soft-throttle best-effort tenants by returning HTTP 429 with Retry-After header and redirect high-priority tenants to dedicated capacity.
   - Automation snippet (example):
     "if tenant.priority == 'best_effort' and credit_balance < 0: return 429, Retry-After=30s"

5) Cost and token leak signals
   - Signals: token_rate_by_route, unexpected_token_spike_ratio, token_utilization_growth_24h
   - Play ID: C-LEAK-05 (Token leak detection and mitigation)
   - Heuristic: unexpected_token_spike_ratio > 3x baseline for >10m AND there is a matching increase in error_retries -> throttle route and trigger request-level debug capture for 1% of requests. Notify product owner.

Alert definitions (prometheus-style examples)
-------------------------------------------
- kv_cache_hit_rate_low: avg_over_time(kv_prefix_cache_hit_rate[5m]) < 0.7
- tail_latency_breach: (histogram_quantile(0.95, sum(rate(inference_latency_bucket[5m])))) > 1.2 * target_95th
- gpu_temp_spike: max_over_time(gpu_temp_celsius[2m]) > 85

Decision flow (quick)
---------------------
1) Observe: which signal category is primary? Cache / Latency / GPU / Routing / Cost
2) Classify severity: P1 if SLOs are violated for >5m and >10% of tenants impacted; P2 otherwise.
3) Execute play: pick matching Play ID and follow runbook steps.
4) Escalate: if automation fails or progress < 30% within 10 minutes, page Platform Lead and Incident Commander.

Operator runbook template (what each play must include)
------------------------------------------------------
- Title and Play ID
- Observable signals and canonical Grafana dashboard links
- Step-by-step operator actions (safety-first)
- CLI commands and automation toggles with examples
- Rollback criteria and safe-stop points
- Post-incident tasks and metrics to capture
- Owner and responder contact list

Example runbook excerpt: C-REHYDRATE-01
1) Owner: kv-cache team (oncall: @kv-cache-oncall)
2) Observe: confirm kv_prefix_cache_hit_rate < 0.7 on dashboard "KV Cache Health" (region filter = EU-WEST).
3) Run: ./scripts/prefetch-prefixes --tenant-file=/tmp/top10.json --budget-tokens=20M --dry-run=false
4) Verify: monitor kv_prefix_cache_fill_latency_ms and hit_rate for 10 minutes.
5) Rollback: if hit_rate decreases or model errors increase >1% after prefetch, kill prefetch and revert retention policy.
6) Postmortem triggers: if incident lasted >30 minutes or cost delta > $1000, open a postmortem ticket.

Automation safety knobs and feature flags
----------------------------------------
- All automated remediation jobs must require one of the following: region opt-in, tenant whitelist, token budget.
- Feature flags: ff.auto_rehydrate_enabled (boolean), ff.auto_model_fallback_disabled (boolean per-customer), ff.adaptive_batching_min_ratio (float).
- Default: auto remediation disabled for Restricted tenants; enabled for public dev/test and best-effort tiers.

Retrospective notes (from regional gameday, 2025-12)
--------------------------------------------------
- What worked: targeted prefetch reduced tail-latency during simulated workload surges.
- What did not: automation assumed perfect tenant metadata; missing tenant-to-model mappings caused two false positive rehydrates. Fix: add metadata health check.
- Action items: add tenant-model mapping health check (owner: infra-metadata team), add a 60s cooldown to automated prefetches to avoid thrash.
