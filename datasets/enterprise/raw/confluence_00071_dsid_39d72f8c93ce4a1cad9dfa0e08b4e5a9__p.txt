Parameterized Endpoint Hinting and Fidelity Bridging Guidelines

Summary

This document defines a lightweight, consistent standard for parameterized endpoint hinting (client-supplied signals) and the server-side fidelity-bridging behavior that uses those hints to balance latency, cost, and output quality. The goal is to provide a predictable, testable contract that SDKs and platform components can implement to enable graceful degradation, cost-aware routing, and safe rollouts of new fidelity tiers.

Scope and motivation

- Applies to public and private Redwood inference endpoints that accept narrative/text generation, chat, or structured-response requests.
- Covers: request surface (headers/query/payload hints), server routing decisions, recording telemetry, contract tests, deprecation semantics, and rollout / rollback procedures.
- Motivation: customers and internal services need explicit controls to trade fidelity for latency/cost without opaque behavior or hard failures. This reduces emergent faults where mixed client expectations and runtime capacity produce surprising outputs.

Terminology

- Fidelity hint: optional client-provided signal that expresses a preference for latency/cost vs. quality (e.g., high, balanced, low).
- Bridge variant: a runtime-selected model or config that provides a fidelity tier (for example, quantized small-model, full-precision large-model, cached-prefix-boost).
- Degradation plan: the observable path the service takes when capacity or SLO pressure requires lowering fidelity.

Surface contract (required fields)

All endpoints must accept fidelity hints and a stability header. The server MUST treat the absence of a hint as "balanced" and continue to serve. The canonical names and allowed values are: 

| Field | Location | Allowed values | Default | Description |
|-------|----------|----------------|---------|-------------|
| X-Redwood-Fidelity | request header | low, balanced, high | balanced | Client preference for latency vs. output fidelity |
| fidelity_hint | JSON body / top-level | "low"/"balanced"/"high" | balanced | Mirrors header for clients that cannot set headers |
| X-Redwood-Stability | request header | experimental, stable, pinned | stable | Signals client expectation about API/format stability |
| X-Redwood-Return-Variant | request header | variant-id (string) | unset | If provided, server should attempt to route to exact variant or return 412 if incompatible |

(Represented here as a plain-text table; servers should include these names verbatim.)

Behavior rules (server-side)

1. Respect hints: The server SHOULD attempt to honor X-Redwood-Fidelity when selecting a bridge variant. Hints are advisory, not authoritative; servers may choose a higher fidelity than requested but must never silently drop from high to low without telemetry and a routed reason code.
2. Capability negotiation: If a requested fidelity or variant is impossible for the tenant (e.g., regulatory pinning, private deployment constraints), the server must return 412 Precondition Failed with a machine-parsable JSON explaining the allowed options and the owner link. Example: 

```json
HTTP/1.1 412 Precondition Failed
Content-Type: application/json
{
  "error": "fidelity_not_available",
  "allowed": ["balanced"],
  "message": "Tenant policy pins model to balanced. Contact infra@redwood.example.com for exceptions.",
  "owner": "/teams/eng-serving-runtime"
}
```

3. Deterministic bridging: When routing to a bridge variant because of capacity or cost policies, routing must use deterministic keys (tenant id, request hash, or session id) to avoid flapping across sequential requests in a session.
4. Circuit transparency: If the runtime degrades fidelity due to SLO pressure, the response MUST include the applied_variant and fidelity_reason fields in the response metadata. Example response snippet: 

```json
{
  "output": "...",
  "meta": {
    "applied_variant": "gptx-lite-q4_5",
    "fidelity_reason": "slo_pressure::cpu_90pct"
  }
}
```

Telemetry and SLI obligations

- Every request must emit telemetry with dimensions: tenant_id, fidelity_hint, applied_variant, latency_ms_p50/p95/p99, tokens_generated, and fidelity_reason (when applicable).
- SLOs tied to fidelity tiers: each fidelity tier must declare a latency SLO and a quality SLI (see Quality monitoring section). Example: balanced: p95 < 450ms, quality_score >= 0.92 on canonical tests.
- Sampling guidance: For 'low' hints, record 100% of telemetry for the first 72 hours after a new bridge variant is introduced, then reduce to 10% unless anomalies are detected.

Contract testing and SDK expectations

- SDKs must expose an enum for Fidelity {LOW, BALANCED, HIGH} mapped to the header/value strings. SDKs should provide a default of BALANCED.
- Contract tests (run in CI) must include:
  1) Round-trip test asserting that sending fidelity_hint results in either the same applied_variant or a deterministic and documented alternate.
  2) Compatibility test asserting 412 behavior when tenant policy forbids a fidelity.
  3) Telemetry hook test verifying presence of applied_variant and fidelity_reason in response metadata for degraded paths.

Quality monitoring and regression gating

- Each bridge variant must have an associated prompt-suite (subset of the canonical eval harness) and a quality baseline.
- Changes to bridge variants must pass: automated regression checks (no >2% drop in baseline metric) and a manual signoff from the model steward.
- Degradation alerts: if the quality metric for any fidelity tier drops below its baseline by threshold (configurable; default 3%) for a 1-hour window, trigger P1 alert and automatically mark the variant as quarantined for rollback.

Rollout and rollback playbook (high level)

1. Preflight (local + staging): run full contract tests and the variant-specific prompt-suite.
2. Canary release: route 1–5% of traffic using deterministic bucketing tied to tenant or API-key. Monitor fidelity-specific SLIs for 24 hours.
3. Incremental ramp: increase to 20% and then 50% only if no quality/latency regressions.
4. Full release: after 72 hours with stable telemetry, mark variant as default for the target fidelity hint.
5. Hot rollback: on P1 or automated quarantine, switch deterministic routing to previous stable variant and open an incident with the serving-runtime on-call.

Each rollout step must annotate the release with: owner, targeted tenants (if any), monitoring playbook link, and a revert tag. Use the release metadata schema: 

```yaml
release_id: r-2026-xxxx
owner: eng-serving-runtime
canary_fraction: 0.01
start_time: 2026-02-01T15:00:00Z
revert_to: gptx-lite-q4_4
notes: "introduce q4_5 for low fidelity to reduce cost for short conversations"
```

Runtime and infra safeguards

- Cost cap: bridge variants labeled "low" must have a budget tag and be subject to daily spend caps enforced by the quota controller.
- Preemption policy: instances running high-fidelity variants must register preemption handlers; during forced preemption the service should attempt to complete in-flight tokens up to a safety cutoff (e.g., 50 tokens) and emit fidelity_reason = "preempt_shutdown".
- Cache-awareness: when applying a cached-prefix-boost as a bridge variant, ensure the cache TTL respects data retention policies and is tagged with the tenant id and prompt-suite hash.

Security and privacy considerations

- Any bridge variant that uses external retrieval or tool-calling must verify tenant authorization for external calls and redact telemetry fields that may contain PII before export.
- For Private deployments, the runtime MUST honor tenant-configured accepted_fidelities and may reject hints that would route traffic outside approved artifact manifests.

Observability: dashboards and alerts (example)

- Dashboard: Fidelity Overview (filters: tenant, variant, hint) showing applied_variant distribution, p95 latency per variant, tokens per request, and quality_metric trendlines.
- Alert examples:
  - fidelity_quarantine_trigger (P1): quality_metric_deviation > 3% for 1h on any fidelity tier.
  - fidelity_unexpected_variant (P2): >0.5% of 'high' hint requests served by 'low' variants without explicit fidelity_reason tag.

Appendices

A. Example request/response (full)

Request:
```http
POST /v1/generate HTTP/1.1
Host: api.redwood.ai
Content-Type: application/json
X-Redwood-Fidelity: low
X-Redwood-Stability: stable

{
  "model": "text-creative-v2",
  "prompt": "Summarize the release notes in 3 bullet points.",
  "fidelity_hint": "low"
}
```

Response (degraded path):
```http
HTTP/1.1 200 OK
Content-Type: application/json

{
  "output": "- Released performance improvements.
- Fixed bug in telemetry.
- Improved deployment safety.",
  "meta": {
    "applied_variant": "text-creative-v2-q4_5",
    "fidelity_reason": "slo_pressure::gpu_85pct",
    "latency_ms": 312
  }
}
```

B. Quick CLI checks for on-call

Run a fidelity-bridge health check against a tenant: 

```bash
# requires REDWOOD_API_KEY set
curl -sS -H "Authorization: Bearer $REDWOOD_API_KEY" \ 
  -H "X-Redwood-Fidelity: low" \ 
  -X POST https://api.redwood.ai/v1/debug/bridge-health \ 
  -d '{"tenant_id":"t-1234"}' | jq
```

Interpret output: presence of "quarantined": true indicates the variant is currently blocked.

D. Migration notes for clients

- SDKs: add Fidelity enum and expose a client flag `auto_fidelity_fallback` (default true). If set to false, client must handle 412 responses.
- Backwards compatibility: servers must accept legacy header X-RW-F (values numeric 0/1/2) mapping to low/balanced/high for at least 18 months and emit a deprecation header: X-Deprecation-Notice: "X-RW-F is deprecated; use X-Redwood-Fidelity".
