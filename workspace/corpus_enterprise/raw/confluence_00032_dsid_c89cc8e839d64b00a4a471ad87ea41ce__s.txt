SDK breaking change mitigation matrix and hotpatch playbook

Overview
--------
This document defines a practical mitigation matrix and hands-on hotpatch playbook for SDK breaking changes that affect customer integrations. It is intended for DX engineers, SDK maintainers, and on-call support engineers who need reproducible steps to triage, mitigate, ship a hotpatch, and verify compatibility with minimal customer impact.

Scope and goals
----------------
- Scope: client-side SDKs maintained by eng-developer-experience (JS, Python, Go) and ancillary adapter libraries produced by partners.
- Goals:
  - Triage breaking changes within 60 minutes of detection (severity-critical)
  - Ship a validated hotpatch inside a 4-hour window for customer-impacting regressions
  - Provide clear communication to customers and internal teams within 90 minutes
  - Reduce recurring break incidents through postmortems and improved tests

When to use this playbook
-------------------------
Use this flow for any of the following detection signals:
1) Automated integration test failures that started occurring after a dependency bump in the SDK CI pipeline.
2) Production error spike with >=5% of customer requests failing due to SDK client exceptions.
3) Multiple customer support tickets reporting the same reproducible error tied to a released SDK version.

Severity classification matrix
------------------------------
The following table maps observable symptoms to severity, SLA, and immediate action. Apply the first matching row.

| Symptom | Severity | Target MTTA | Immediate action owner | Temporary mitigation pattern |
|---------|----------|-------------|------------------------|-----------------------------|
| SDK throws exception on auth handshake for 100% of requests | critical | 15m | On-call DX engineer | Revert client-facing release or publish patched minor with compatibility shim and rollback policy |
| Tokenization/requests get garbled causing model misrouting for many customers | high | 30m | SDK lead + SRE | Enable server-side fallback to previous model route; advise customers to pin model version |
| Non-fatal response shape change (missing optional field) | medium | 4h | SDK maintainer | Release patch with backward-compatibility layer and deprecation notes |
| Performance regression < 2x latency for a minority of customers | low | 24h | Performance owner | Deploy client-side option to disable new optimization, gather telemetry |

Owners and communication matrix
-------------------------------
- Primary: eng-developer-experience SDK on-call (pager duty: dx-sdk-oncall).
- Secondary: eng-platform SRE for rollout and traffic shaping.
- Stakeholder notifications: product (PM), support, developer-advocate, security (if auth implicated).
- Customer comms owner: Customer Success (for named accounts) + Support (public issue tracker).

Triage checklist (first 60 minutes)
----------------------------------
1. Confirm signal provenance:
   - Verify Sentry/Errbot alerts, reproduce against latest published SDK version, and run the failing test in local sandbox.
   - Use reproducible request body and logs from the customer or synthetic harness.
2. Scope impact:
   - Use telemetry dashboards: percent of requests failing, top 10 customer IDs, geographic spread.
   - Check CI: which PR or dependency change landed last 24–72 hours.
3. Temporary mitigation decision (yes/no):
   - If severity is critical or high and mitigation possible, escalate to hotpatch flow.
4. Communicate initial status (within 90 minutes):
   - Post to #dx-incident channel with short summary, severity, impacted versions, and next ETA.

Hotpatch flow (shipable within 4 hours)
-------------------------------------
Step 0 — Pre-conditions: confirm reproducible failing test and safe rollback path exists (git/release tags).

Step 1 — Create minimal patch branch
- Author: SDK maintainer. Branch naming: hotpatch/sdk/<package>-<version>-<YYYYMMDD>-<short>
- Keep change small: compatibility shim, defensive null checks, or revert of recent commit.
- Example minimal change (JavaScript):

```js
// compat-shim.js
if (!response.parsedContent) {
  // fallback to older field name
  response.parsedContent = response.content_v1 || '';
}
```

Step 2 — Local and CI validation
- Run unit tests and full integration suite against the reproducible scenario.
- Add one targeted acceptance test in the patch branch that reproduces the bug.
- If integration tests are flaky, record run artifacts and proceed with conservative rollout.

Step 3 — Code review and quick sign-off
- Use expedited reviewers list (owner + one reviewer). PR label: hotpatch/expedite.
- If release manager approves, merge to main with commit message referencing the incident ID.

Step 4 — Release and canary
- Build artifact and publish to canary channel (npm tag: canary-<incident-id>, pip: pre-release wheel).
- Canary rollout plan:
  - 0–5% of downloads for 15 minutes
  - 5–25% for 30 minutes if no regressions
  - 25–100% after 1 hour with monitoring green
- For public package registries where immediate download % control is limited, issue clear advisory and provide patched package URL and pin instructions.

Step 5 — Verification and rollback criteria
- Metrics to watch during canary:
  - error rate for the failing endpoint (target: <25% of prior spike)
  - latency P95 should not degrade more than 20% relative to baseline
  - customer-reported reproduction count should drop to zero for confirmed customers
- Rollback if any of the following triggered:
  - new critical exceptions introduced within canary window
  - customer complaint rate increases after patch
  - test-suite failure in post-release smoke checks

Step 6 — Publish stable release
- After canary success, promote artifact to stable channel and publish changelog entry with clear migration guidance and API contract notes.
- Add deprecation timeline if behavior intentionally changed.

Communication templates
-----------------------
Use these snippets for rapid updates. Replace placeholders in brackets.

Initial status (internal):
"Incident [INC-YYYYMMDD-###]: SDK exception observed in [package-name] v[semver]. Impact: [X%] of requests failing. Triage in progress. Owner: [name]. ETA for next update: 60 minutes."

Customer advisory (public):
"We are investigating an issue impacting the [package-name] SDK v[semver] that may cause client errors during requests to the Redwood API. A mitigated release is available at [URL]. For immediate relief, pin to [previous-version] or install the patch with `npm i @redwood/sdk@[patched-tag]`. We will follow up when fully resolved."

Post-incident follow-up (24–72 hours)
-------------------------------------
- Run a blameless postmortem documenting root cause, timeline, and decisions.
- Required action items (assign owners and due dates):
  1. Add an automated integration test that reproduces the regression (owner: SDK QA) — due in 7 days.
  2. Add canary telemetry dashboard and alert with runbook link (owner: SRE) — due in 14 days.
  3. Review dependency upgrade policy to include staged rollout for critical transitive deps (owner: platform) — due in 21 days.

Prevention and engineering improvements
--------------------------------------
- Recommended CI gates:
  - Block dependency updates if integration tests are red for any supported runtime.
  - Require a locally reproducible acceptance test before merging changes that touch serialization, auth, or network layers.
- SDK design guidance:
  - Favor additive changes: add new fields under clearly namespaced keys, avoid renaming top-level fields.
  - Implement feature flags in SDKs for opt-in behavior changes.

Runbook quick commands and examples
----------------------------------
- Reproduce failing call (Python example):

```py
from redwood_sdk import Client
c = Client(api_key='REDACTED')
resp = c.generate(prompt='hello', model='gpt-lite')
print(resp.raw)
```

- Publish canary npm tag:

```bash
npm publish --tag canary-INC-20260210
```

- Tag for stable release after verification:

```bash
git tag -a v1.4.7 -m "hotpatch for INC-20260210" && git push origin v1.4.7
```
