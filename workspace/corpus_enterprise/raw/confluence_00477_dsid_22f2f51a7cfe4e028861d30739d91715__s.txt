satellite-edge-vpc-branchwork-deploy-strategy-2028

Overview
--------
This playbook describes the recommended strategy for deploying Redwood Private nodes to satellite / branch office environments that operate inside a customer VPC or in a co-located site with intermittent connectivity to the central control plane. It covers target architectures, hardware and network requirements, secure key management (vaulted KMS), deployment steps, upgrade and rollback patterns, and day‑2 operational runbooks for latency fallbacks and KV-cache warmups.

Goals
-----
- Provide a repeatable deployment pattern for low-latency inference at branch locations while preserving central governance.
- Ensure predictable failure modes and safe rollback/upgrade procedures for constrained-edge hardware.
- Maintain customer data isolation and strong cryptographic controls (HSM/KMS integration).
- Keep 95th percentile inference tail latency below 150ms for short prompt profiles in well-connected branches; provide graceful fallbacks when connectivity or capacity degrades.

Scope and non-goals
-------------------
- In scope: VPC-attached branch nodes, co-located rack appliances, constrained GPU/CPU edge configs, local KV cache, local model variants for degraded mode.
- Out of scope: fully air-gapped installations with zero control plane connectivity (see airgap packaging docs).

High-level architecture (text diagram)
-------------------------------------
Central Control Plane (Redwood-private-control) -- TLS 1.3 --> Customer VPC Transit Gateway -- BGP/HA --> Branch Edge Node(s) [Runtime + KV Cache + Local Router]

Components
- Branch Edge Node: lightweight runtime service (redwood-edge-runtime) that hosts model shards or quantized variants, local KV cache service (kv-cached), and health/telemetry agent (edge-agent).
- Transit Proxy: optionally a regional egress/ingress proxy (envoy) running in customer VPC to provide mutual TLS to central control plane.
- Vaulted KMS: customer-managed KMS/HSM or cloud KMS with a per-branch key envelope for local disk encryption and runtime key material.

Hardware profiles (recommended)
-----------------------------
| Profile Name | CPU | GPU | RAM | Local Storage (nvme) | Use case |
|--------------|-----|-----|-----|---------------------|----------|
| branch-s-1   | 8c  | 0   | 32GB| 1TB (enc)           | lightweight embedding/fast-proxy
| branch-g-2   | 16c | 1xA10| 128GB| 2TB (enc)         | interactive chat & small LLMs (quantized)
| branch-g-4   | 32c | 2xA100 | 256GB| 4TB (enc)        | high-throughput on-prem inference

Network & Security requirements
-------------------------------
- Outbound TLS to control plane: TCP 443 (mutual TLS). Certificate pinning required for branch-agent.
- Optional inbound for operator access: SSH on port 2222 (jump-host only).
- BGP sessions for transit failover recommended for branches with direct WAN. BFD timers: 300ms.
- Egress firewall rules: allow control-plane subnet CIDRs + telemetry ingestion endpoints.
- KMS binding: branch node must have access to customer KMS key using a service principal. Where HSM is required, ensure FIPS 140-2 compliance and that key wrapping occurs in hardware.

Prerequisites checklist (before installation)
--------------------------------------------
1) Provision hardware that matches one of the supported profiles.
2) Customer to provide a service principal and KMS key ID with key usage policy for runtime encryption.
3) Transit connectivity validated (IP reachability and mTLS test) to Redwood control-plane endpoints.
4) Admins have MOP (Maintenance & Operations Permit) and operator-approved change window.
5) Telemetry and log endpoints configured and IAM roles granted.
6) Backup image and rollback snapshot available in storage (s3-compatible).

Pre-flight validation commands (examples)
---------------------------------------
- Check control plane connectivity and certs:
  curl --cert client.pem --key client.key https://control.redwood.example.internal/healthz

- Validate KMS envelope unwrap (example AWS KMS CLI):
  aws kms decrypt --ciphertext-blob fileb://wrapped-key.bin --key-id arn:aws:kms:region:acct:key/EXAMPLE

Installation steps (atomic, numbered)
------------------------------------
1) Boot base image and confirm secure boot & measured boot attestation: run 'attest-check --policy branch-standard'.
2) Mount encrypted nvme and validate LUKS header: 'cryptsetup status /dev/nvme0n1'.
3) Install redwood-edge-runtime and kv-cached via package repo: 'apt install redwood-edge-runtime=1.7.3 kv-cached=2.2.1'.
4) Place branch manifest at /etc/redwood/branch-manifest.yaml (example below).
5) Start services in order: kv-cached -> edge-runtime -> edge-agent. Verify with 'systemctl status'.
6) Run model warmup procedure (see Day‑2 ops) before enabling traffic.

Example branch-manifest.yaml (for reference)
-------------------------------------------
# single-document manifest
node_id: branch-nyc-01
model_variants:
  - name: rlm-quant-small
    path: /opt/models/rlm-quant-small/
    max_seq: 512
  - name: rlm-embed-lite
    path: /opt/models/rlm-embed-lite/
    embeddings_only: true
control_plane_endpoint: https://control.redwood.example.internal
telemetry_endpoint: https://telemetry.redwood.example.internal
kv_cache:
  local_capacity_mb: "512"
  eviction_policy: lru
  prefetch_prefixes: ["/user/", "/session/"]

Post-install verification checklist
----------------------------------
- edge-agent reports healthy to control plane (reporting interval < 30s).
- KV cache hit-rate >= 60% after warmup (see warmup script).
- Local inference 95p latency within target for test prompt set (run 'redwood-bench --profile branch-short').
- Telemetry ingestion samples observed in central dashboard for the new node.

Model warmup and KV-cache migration (day-2 ops)
-----------------------------------------------
Purpose: reduce first-user cold-start latency and reduce fetches to central model store.
Procedure:
- Step A: Seed cache with canonical prefixes via the warmup tool: '/opt/bin/kv-warmup --manifest /etc/redwood/branch-manifest.yaml --concurrency 4'.
- Step B: Run inference synthetic load for 10m at 20 rps using the local test harness to populate KV entries and model caches.
- Step C: Monitor kv-cached metrics (kv_cache_hits, kv_cache_misses) and target hit-rate >= 60% within 30 minutes.

Upgrade strategy (safe staged approach)
------------------------------------
Principles:
- Always run upgrades in canary -> staged -> full pattern with automated health gates.
- Preserve the last-known-good artifact and boot image for at least 7 days.
- Use model-compatibility gates to avoid runtime ABI mismatches.

Staged upgrade steps:
1) Canary: pick a single branch node during low-traffic window and upgrade runtime and agent. Monitor for 6 hours.
2) Regional: upgrade 10–20% of branches in the region, verify KPIs for 24 hours.
3) Bulk: roll the remainder with a rolling window and an operator in the loop.

Automated health gates (examples)
- Edge agent must report healthy for 3 consecutive pings.
- 95th percentile inference latency must not increase by >20% from baseline.
- KV cache miss rate must not increase by >15% absolute.

Rollback & failure isolation patterns
-------------------------------------
- Fast rollback: boot to the previous image via boot manager and restore previous manifest snapshot. Use 'reboot --rollback-to snapshot-<ts>'.
- Controlled rollback: Mark node as "evacuate" in control plane, drain requests (max 60s drain), then apply rollback.
- Failure isolation: if runtime fails with OOM/thermal, place node into maintenance and shift traffic to regional fallback (see latency fallback).

Latency fallback topology & policy
--------------------------------
When the branch cannot serve requests (capacity exhausted or model mismatch), the control plane will apply the following policy (configurable per-customer):
- Priority 1: route to regional dedicated pool within same region (low extra latency, compatible model variant).
- Priority 2: route to hosted inference with enforced throttling and adaptive token budget.
- Backoff policy: exponential backoff with jitter starting at 250ms, max 8s.

Service Level Objectives (SLOs) and metrics to track
---------------------------------------------------
- Local inference 95p latency: target <= 150ms (severity: P2 if > 250ms).
- Availability (branch node): 99.5% monthly.
- KV cache hit-rate: target >= 60% within 30m of warmup.
- Telemetry heartbeat: agent heartbeat interval <= 30s, missing 5 consecutive heartbeats triggers alert.

Observability & Alerts
----------------------
Essential signals:
- edge-agent.health, edge-runtime.latency.p95, kv-cache.hitrate, nvme.disk_temperature, gpu.thermal_throttle_count
Suggested alerts:
- edge-runtime.latency.p95 > 300ms for 10m -> WARN -> run latency-fallback:trigger
- nvme.disk_temperature > 75C -> CRITICAL -> schedule maintenance and trigger thermal-throttle mitigations
- kv-cache.hitrate < 35% for 30m -> INVESTIGATE

Operator runbook: cold start incident (summary)
---------------------------------------------
1) Validate node health: 'systemctl status edge-runtime kv-cached edge-agent'.
2) If edge-runtime OOMs, collect /var/log/redwood/runtime.* logs and run 'redwood-dump-state'.
3) If disk errors present, mark node as degraded and redirect traffic to regional fallback.
4) If due to cache evictions, run localized warmup and increase local_capacity_mb by 20% as temporary mitigation.
5) After stabilization, initiate a post-incident ticket with root-cause and change-requests for config fixes.

Compliance, key management and audit evidence
-------------------------------------------
- Maintain key rotation logs for branch keys in central audit store. Rotation cadence: default 90 days; emergency rotate supported.
- All branch storage must be encrypted at rest with an auditable KMS envelope.
- Collect attestations from boot (TPM quote) and store in control-plane evidence store.

Change management template (for customer-run windows)
---------------------------------------------------
- Change ID: CM-<region>-<date>
- Impact: estimated downtime per node and expected performance impact.
- Rollout plan: canary node list, regional batch list, full rollout timing.
- Backout plan: snapshot IDs and rollback command sequence.
- Approvers: customer infra lead, Redwood private-deploy lead.

C. FAQs
- Q: Can branches run full-size LLMs?
  A: Only if hardware profile and thermal envelope support it; prefer quantized variants and sharding when possible.

- Q: What happens during extended control-plane outage?
  A: Branch nodes continue to serve using cached models and local routing policy. If cache misses spike, request routing will prefer pre-configured regional fallbacks.
