Token-Aware Scheduler: Telemetry, Safety Checks, and Fallback Playbook

Summary

This playbook documents the Token-Aware Scheduler (TAS) telemetry contract, production safety checks, and step-by-step fallback and mitigation procedures used by the serving runtime. TAS is the scheduler layer that considers request token counts, sequence-length distributions, and per-request SLO budgets when assigning kernels and shaping batching windows. The goal of this document is to make the scheduler-to-runtime observable, auditable, and safe for rapid rollouts without surprising regressions in tail latency or model fidelity.

Goals and scope

- Define the telemetry signals required by the scheduler and runtime for token-aware decisions.
- Enumerate deterministic safety checks and thresholds for automatic fallback or throttling.
- Provide an operational runbook for incidents caused by token-shape variability, kernel mismatches, or batching anomalies.
- Give test-and-rollout recipes for canarying TAS versions and new kernel handoff behaviors.
- Scope: applies to hosted and dedicated clusters running v2 scheduler runtime API. Does not prescribe cloud-provider specific autoscaling settings.

Key concepts and definitions

- Request token shape: observed pair {prompt_tokens, completion_budget} used to pick batching window and kernel hints.
- Kernel hint: metadata tag passed to runtime indicating preferred execution variant (float16/quantized/sharded-attn variant).
- Batching window: the time horizon TAS holds requests to form a batch; adaptive to token shape and SLO.
- Fidelity clamp: policy that gracefully reduces model variant (e.g., smaller model or lower precision) to preserve SLOs.

Required telemetry (contract)

All signals must be emitted at request decision time and at kernel completion. These are structured as key/value tags in the trace and as metrics in Prometheus/OTel.

- request.id (string)
- request.arrival_ts (epoch-ms)
- request.token_estimate (int)
- request.completion_budget_tokens (int)
- request.priority_tier (string) — {critical, standard, best_effort}
- scheduler.decision_ts (epoch-ms)
- scheduler.batch_id (string|null)
- scheduler.chosen_batching_window_ms (int)
- scheduler.kernel_hint (string) — e.g., "kv-sharded-ep10-q4",
- scheduler.predicted_latency_ms (int)
- scheduler.predicted_cost_micros (int)
- runtime.kernel_start_ts (epoch-ms)
- runtime.kernel_end_ts (epoch-ms)
- runtime.kv_cache_hit_rate (float)
- runtime.actual_tokens_emitted (int)
- runtime.memory_pressure_level (low|medium|high)
- runtime.fidelity_action (none|quantize|model-fallback|rate-limit)

Metric families (Prometheus)

- tas.request_token_distribution{tenant,model} histogram (buckets by 1,8,32,128,512,2048)
- tas.batch_size{pool,model} gauge
- tas.predicted_vs_actual_latency_ratio histogram
- runtime.kernel_handshake_failures counter (labels: reason)
- runtime.fidelity_actions_total counter (labels: action,reason)
- tas.batch_window_ms gauge

Safety thresholds and deterministic rules

The scheduler enforces these safety constraints before committing a request to a batch and emitting the kernel_hint.

1) Kernel compatibility gate
- If runtime reports kernel_handshake_failures > 5 in last 1m for chosen kernel_hint, mark hint as degraded and pick next compatible variant. If no variant available, fallback to model-fallback.

2) Token-window SLO guard
- If scheduler.predicted_latency_ms > SLO_target * 0.9 for the request.priority_tier, reduce batching_window_ms by 50% for the next 30s for that tenant-model pair.

3) Memory-pressure guard
- If runtime.memory_pressure_level==high on the target node, route new requests to alternative pool or trigger fidelity_action: quantize for best_effort only.

4) KV cache instability guard
- If runtime.kv_cache_hit_rate drops >20% vs baseline over 2 minutes, disable long-prefix batching for affected model for 5 minutes.

Fallback and mitigation actions (ordered by severity)

- Soft fallback (no fidelity change): reduce batching_window_ms, increase preemption priority for critical requests, spin up additional execution slots.
- Quantization fallback: switch kernel_hint to a quantized execution path (q4/q8) if the model variant has been validated for the tenant. Label action in telemetry: fidelity_action=quantize.
- Model fallback: route to a smaller/compatible model variant. Must attach a quality-warning header to downstream callers for auditing.
- Rate-limit fallback: for best_effort tier only, apply 429 with retry-after and emit runtime.fidelity_action=rate-limit.

Runbook: Incident response for elevated tail latency attributed to token-shaped bursts

Initial detection
1) Alert threshold: tas.predicted_vs_actual_latency_ratio > 1.4 for p99 over 5m for a tenant.
2) Pager triggers to runtime-sre oncall.

Triage steps (oncall)
1) Pull recent traces for sample request.id showing predicted latency and actual kernel durations.
2) Check scheduler.batch_window_ms and tas.batch_size trends.
3) Query runtime.memory_pressure_level and kernel_handshake_failures for 10m window.
4) If kv_cache_hit_rate dropped: identify whether a model rollout or cache eviction happened.

Immediate mitigations
1) If kernel_handshake_failures > 5: temporarily blacklist faulty kernel_hint (CLI below) and restart canary kernel pool.
2) If memory_pressure_level==high: trigger eviction policy, and if unavoidable, set tenant policy to quantize for next 10m.
3) If batch_window_ms is large and predicted latency is underestimated: reduce batch_window_ms by 40% for affected tenant-model via dynamic policy API.

CLI commands and examples

- Blacklist kernel hint (safely):
  rdsctl scheduler blacklist-kernel --kernel "kv-sharded-ep10-q4" --reason "handshake-failures" --duration 10m

- Set tenant-model dynamic policy (reduce batching):
  rdsctl scheduler set-policy --tenant acme-corp --model t-rxl-3b --batch-window-ms 25 --reason "tail-latency-mitigation"

- Force quantized fallback for best_effort:
  rdsctl runtime set-fidelity --tenant acme-corp --model t-rxl-3b --action quantize --duration 15m

Validation checklist (post-mitigation)

- Confirm tas.predicted_vs_actual_latency_ratio returns <1.1 at p99 for 10m window.
- Confirm runtime.fidelity_actions_total increments are expected and labeled properly.
- Run 1000 synthetic requests matching the original token shape via loadsculptor and compare responses for quality regressions (automated evaluation harness).
- Confirm related customer-facing routes show no 5xx spikes.

Canary and rollout recipe for new TAS kernel handoff behavior

1) Unit + integration tests: scheduler decision simulator with synthesized token-shaped workloads.
2) Private canary: enable on 1% of traffic with strict shadow tracing enabled (emit scheduler.* telemetry but route to stable path).
3) Observability gates for promotion (all must pass):
   - p99 latency difference <+5% vs baseline
   - kernel_handshake_failures == 0 sustained for 60 minutes
   - fidelity_action model-fallback count == 0
4) Progressive rollout: 1% -> 5% -> 25% -> 100% with 30–60 minute observation windows and auto-rollback on gate failure.

Testing guidance and bench harness

- Use load profiles that mirror long-tail token shapes: create corpora with 1%, 5%, 20%, 50% tails at 512+ tokens.
- Run A/B fidelity checks using our eval harness repository: refer to related_pages below.
- Synthetic chaos: inject kernel handshake failures and KV cache eviction events while running the bench to validate deterministic fallbacks.

Operational notes and best practices

- Prefer proactive KV cache warming for models with long-prefix reuse; TAS will prefer longer batching windows only after hit rate >70%.
- Annotate model variants with compatibility matrix: kernel capabilities, max_sequence_length, quantization validated flags.
- Maintain an "execution-compatibility" manifest per model in the model-onboarding catalog so TAS can enumerate fallbacks deterministically.
