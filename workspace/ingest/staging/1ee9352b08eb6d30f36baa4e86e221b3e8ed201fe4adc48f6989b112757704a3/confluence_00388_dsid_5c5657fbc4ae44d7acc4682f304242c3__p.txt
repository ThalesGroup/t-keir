Postmortem Action Bank and Regression Signal Library

Overview

This page centralizes: 1) a curated, searchable Action Bank of repeatable remediation steps distilled from past postmortems and operator playbooks; and 2) a Regression Signal Library — concrete telemetry rules and detection queries that have historically predicted production-quality regressions for Redwood's LLM inference platform. The purpose is to shorten time-to-remediate and reduce recurrence by making investigator knowledge explicit and actionable.

Scope

- Applies to platform incidents, degradations, and recurring reliability/cost regressions impacting hosted, dedicated, and private deployments.
- Primary audience: platform operators, SREs, runtime engineers, and oncall rotation leads.
- This is an operational reference; do not copy incident narratives here — link to original postmortems instead.

How to use this page

1. When a new postmortem is opened, attach an Action Candidate (see procedure below).
2. If a telemetry alert or dashboard anomaly matches a Regression Signal, mark the incident as a possible regression and follow the triage checklist.
3. Use prioritization matrix to convert Action Candidates into tracked tickets (JIRA/GitHub) and schedule execution windows.

Action Bank (canonical entries)

Format: ID | Short Description | Typical Owner | Time-to-implement | Preconditions | Post-implementation checks

| ID | Description | Owner | ETA | Preconditions | Post-checks |
|-----|-------------|-------:|-----:|-------------|------------:|
| AB-101 | Reduce batch size for 8k seq workloads on tenant-facing pools | runtime-team | 2h | Canary pool available | 99th pct latency drop, token-cost delta measured |

| AB-127 | Roll back last quantized kernel for model-variant v3 | serving-runtime | 1h | Fallback binary staged | Regression tests pass, latency normalized |

| AB-150 | Reconfigure regional egress routing to avoid noisy peering | infra-net | 6h | Alternate route validated | P95 RTT improved, egress cost within budget |

Each Action Bank entry includes: owner (team alias + rotation contact), related runbook links, required access (K8s, infra, model config), rollback steps, and a small test-plan to validate.

Procedure: From Postmortem to Tracked Ticket

1. Author extracts concrete remediation and maps to an AB-ID (or creates a new AB entry).
2. Run a sanity check: estimate tax (ETA, risk, rollback).
3. Assign owner and add to the weekly SRE triage board.
4. Create ticket with label "action-bank" and link to source postmortem.
5. Owner schedules work and updates the Action Bank entry with status: proposed -> in_progress -> complete -> verified.

Prioritization matrix (short)

- High priority: Affects >=1% of tenants or SLO burn > 2% per hour OR security impact.
- Medium priority: Latency/cost regressions with measurable P95/P99 increases impacting internal customers.
- Low priority: Cosmetic alerts, low-frequency anomalies with no SLO impact.

Regression Signal Library (examples and detection recipes)

Goal: provide deterministic queries and thresholds operators can reuse or import into alerting tooling. Each signal maps to an SLI, a query, a baseline window, and suggested cadence.

Signal: Token-to-latency divergence
- SLI: per-tenant tokens / P95_latency_ms by model-family
- Detection query (example PromQL-like):
  avg_over_time(rate(tokens_total{model_family=~"(gpt.*|redwood.*)"}[5m]) / avg_over_time(histogram_quantile(0.95, latency_bucket{route!="internal"}[5m]))[15m:1m]) > 1.5 * baseline_last_7d
- Baseline: rolling 7-day median
- Typical action: AB-101 or scale dedicated pool for tenant cohort

Signal: KV miss-rate spike with prefix churn
- SLI: kv_cache_hit_ratio by shard
- Detection rule (SQL for analytics):
  SELECT shard, percentile_cont(0.95) WITHIN GROUP (ORDER BY miss_rate) AS p95_miss
  FROM prefixes_telemetry
  WHERE time >= now() - interval '10 minutes'
  GROUP BY shard
  HAVING p95_miss > 0.08;
- Typical action: AB-114, and run cache-consistency recheck

Signal: Model-variant quality regression (eval micro-regression)
- SLI: eval_accuracy_delta_by_promptset
- Detection recipe: scheduled nightly evaluation comparing latest candidate to baseline model using anchor prompts; if delta < -0.5% on critical promptset, create regression ticket automatically.
- Typical action: AB-127 + rollback cadence

Signal: Cost spike correlated with small increase in latency (indicator of inefficient batching)
- SLI: cost_per_token_daily AND p95_latency
- Detection: correlate daily_cost anomalies with 95th-percentile latencies by tenant; run an automated affinity clustering to surface probable model-config changes.
- Typical action: AB-139 + operator notification

Oncall triage checklist (short)

1. Confirm SLI breach and match to a Regression Signal.
2. Identify affected tenants/regions and customer-facing impact.
3. Select immediate mitigations (from Action Bank).
4. Raise Incident/SEV ticket and assign owner; reference AB-ID(s).
5. If mitigation uses a migration/rollback, run preflight checklist.
6. After mitigation, schedule deeper root-cause analysis and map upstream follow-ups to owners.

Automation and integration patterns

- Alerting: signals should be published as low-noise, actionable alerts with links to AB entries and runbooks (alert body MUST contain AB-ID suggestions).
- Ticket creation: novel regression rules can auto-open "regression-candidate" tickets with a triage checklist template.
- Dashboarding: maintain an "Action Bank adoption" dashboard that shows actions open/closed over time and recurrence rate for AB-IDs.

Operational metrics to track for this program

| Metric | Target | Measurement | Owner |
|-------|--------|------------|------|
| Mean time to remediation (MTTR) for AB actions | < 6 hours for high-priority | incident tracker + AB status | eng-platform |
| Fraction of incidents with AB mapping | > 80% | postmortem tagging | eng-platform |
| Regression repeat rate for mapped AB-IDs | < 10% within 90 days | incident deduping | runtime-team |
| Automated detection precision | > 60% precision for top-10 signals | signal-to-incident mapping | observability-team |

Governance and cadence

- Weekly: Triage board reviews proposed AB actions and assigns owners.
- Monthly: Signal hygiene sweep — remove stale rules, tune thresholds with current baselines.
- Quarterly: Action Bank cleanup — retire AB-IDs with no usage, and publish a one-page summary to the platform forum.

Ownership matrix

- eng-platform: program owner, triage chair, backlog governance
- serving-runtime: kernel/quantization action owners (AB-127 family)
- platform-operator: operational playbooks and AB execution (AB-114 family)
- infra-net: routing and peering fixes (AB-150 family)
- observability: detection rules and oncall alert integration
