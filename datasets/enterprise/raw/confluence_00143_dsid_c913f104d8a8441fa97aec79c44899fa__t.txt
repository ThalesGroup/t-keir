Terraform Module Publish Safety Harness & Contract Testing

Summary:
This document describes a prescriptive, repeatable safety harness for publishing Terraform modules used by Redwood’s GPU and network infrastructure. The harness combines automated contract tests, security and lint gating, an account-aware canary rollout, and a fast rollback path. Its goal is to reduce surprise changes to customer-facing infra, maintain statefile compatibility, and make module upgrades reversible at low operational cost.

Scope:
- Terraform modules that are published to our internal registry and consumed by tenant onboarding, GPU pool provisioning, VPC modules, and edge-burst orchestration.
- CI/CD pipelines and test harnesses executed in Buildkite (primary) and GitHub Actions (backup).
- Does NOT apply to ephemeral one-off scripts or local developer-only modules. Those must be promoted before being used in production.

Goals:
1. Prevent breaking API/behavior changes from reaching production accounts.
2. Ensure module publishes are accompanied by deterministic smoke tests.
3. Maintain semantic versioning and compatibility metadata.
4. Allow safe, automated rollouts with observability and fast rollback.

Terminology:
- Contract test: automated test asserting the module’s public inputs, outputs, and remote-state-side effects match a consumer contract.
- Canary account: a low-risk internal account with synthetic tenants used for early validation.
- Consumer matrix: list of critical consumer stacks (e.g., gpu-pool-bootstrap, tenant-onboard) that must be exercised by the test suite.

Safety harness components:
- Pre-publish gates (local CI): terraform fmt, tflint, tfsec, module unit tests (kitchen-terraform or terratest), contract tests against mocked providers.
- Integration smoke (integration CI): apply/destroy in a dedicated ephemeral workspace against the canary account. Validate outputs and run reconciliation checks.
- Semantic-versioning enforcement: major/minor/patch policy via git tags and semver verification job.
- Publishing pipeline: automated registry publish only after gates pass and a manual approval for major versions.
- Rollout orchestration: staged apply to consumer matrix with percent-based canary windows and automated monitoring checks.
- Rollback automation: previous module version promotion and automated terraform state drift check and revert playbook.

Pre-publish pipeline (local CI) — checklist:
1. Developer runs tflint and fmt locally: `tflint --error` and `terraform fmt -recursive`
2. Run static security scan: `tfsec .` and fail on critical findings.
3. Run unit contract tests (mocking IaaS APIs) using terratest: `go test ./test -run TestModuleContracts`
4. Bump semantic version candidate in CHANGELOG and add release tag in branch.

Buildkite pipeline: contract-and-publish (high-level)
- Steps:
  1. checkout -> cache modules
  2. static-lint: terraform fmt, tflint, tfsec (fail fast)
  3. unit-tests: terratest / kitchen integration against mocks
  4. integration-smoke: apply to canary account workspace (auto-destroy on failure)
  5. publish-stage: upload artifact + registry metadata (only when branch is tagged)
  6. canary-rollout: trigger staged applies to consumer matrix (see Rollout policy)
  7. notify: slack channel #infra-module-publishes with results and link to runbook

Example Buildkite step snippet (pipeline YAML):
```
steps:
  - label: "🧪 Static + Unit"
    command: "./ci/run-lint-and-unit.sh"
  - label: "🔬 Integration (canary)"
    command: "./ci/run-integration.sh --workspace=canary"
    agents:
      queue: gpu-ci
  - wait
  - label: "📦 Publish"
    command: "./ci/publish-module.sh --tag=${BUILDKITE_TAG}"
    if: "build.tag == true"
```

Publishing rules and metadata requirements:
- Every published module must include: semantic version, CHANGELOG entry, consumer-compatibility matrix, backward-compatibility notes, and a module-usage example showing default inputs used by GPU stacks.
- Modules must set a `compatibility` metadata field listing minimum required provider versions and known incompatibilities. Example JSON for registry metadata: `{"semver":"1.4.0","compatibility":"aws>=4.0","consumers":["gpu-pool","tenant-onboard"]}`

Contract testing strategy:
- Contract tests are authored by module owners and reviewed by consumer owners. Each contract test must:
  - Instantiate the module with representative inputs for at least 2 consumer patterns.
  - Assert outputs shape / naming (e.g., `subnet_ids`, `asg_name`) and resource tags used for billing.
  - Validate post-apply reconciliation: simulate a control-plane restart and re-run `terraform plan` to ensure idempotency.
- Contract tests run in two modes: mocked (fast, part of PR) and live (slower, integration smoke).

Integration smoke (canary) acceptance checks — automated:
- Health checks: expected number of resources (table below)
- Cost sanity: quick estimator to ensure changes don’t increase ephemeral GPU pre-warm size by >12% for canary stack
- Drift check: run `terraform plan` post-apply and assert no diffs
- Tagging and audit: ensure `owner`, `component`, and `publish_tag` tags present on all top-level resources

Acceptance table (example for gpu-pool-bootstrap canary):
| Check | Success criteria | Failure action |
|---|---|---|
| resource-count | >= 12 nodes provisioned in canary pool | abort publish and notify owners |
| drift | `terraform plan` == no changes | auto-destroy canary, open incident ticket |
| cost-delta | estimator delta <= 12% | abort and require cost review |
| tags | tags present on 100% of root resources | abort and block publish |

Rollout policy (consumer matrix + windows):
- Stage 0: Canary account (internal) — run 1 full integration smoke. (0% customer exposure)
- Stage 1: 5% accounts in staging fleet (non-critical tenants) over 4 hours; monitor error rate, provisioning latency, and cost delta.
- Stage 2: 25% accounts across 2 regions over 12 hours if metrics are green.
- Stage 3: Full release to all consumers.
- Each stage includes an automated hold step if any gating metric exceeds thresholds (see Monitoring section).

Gating metric thresholds (initial):
- Provisioning error rate > 2% (relative to baseline) -> hold and revert
- Median provisioning latency increase > 30% -> hold
- Cost delta > 18% on rolling average -> hold and require manual review

Rollback procedure (fast path):
1. Trigger rollback job in Buildkite (pipeline: module-rollback). This repromotes the last known good module semver and marks the problematic semver as deprecated in the registry.
2. For affected consumers, gated terraform runs will apply the previous module version by updating module source reference and running `terraform init -upgrade=false && terraform apply -lock=true`.
3. If state drift prevents a clean revert, escalate to oncall and run the manual rollback playbook (link below).

Rollback playbook (short):
1. Identify last good version: `registry get-module-versions --module mycompany/gpu-pool`
2. Update consumer repo: bump module source to `vX.Y.Z` (last good) and open a gated PR.
3. Approver: module owner + consumer owner are required for the PR.
4. CI will run smoke tests and apply to a small subset of accounts.
5. Monitor for 1 hour; if metrics stabilize, continue rollout. If not, open incident and run deeper remediation.

Statefile compatibility guidance:
- Never remove outputs used by active consumers without issuing a major version with explicit migration steps.
- Schema change steps: document a migration recipe and provide an automated script where feasible.
- For state move/rename operations, prefer `terraform state mv` helper scripts in the consumer repo with step-by-step instructions.

Monitoring and alerts:
- Dashboards: infra-module-publishes (publish success rate, integration failure rate, canary metrics: provisioning-latency, error-rate, cost-delta).
- Alerting: PagerDuty on oncall when a canary-stage fails gating checks or when rollback automation fails.
- Slack: verbose, colored notifications in #infra-module-publishes and @channel for stage holds/rollbacks.

Ownership and responsibilities:
- Module owner: publishes module, maintains contract tests, triages publish failures. (Primary: infra-module-team)
- Consumer owners: maintain consumer matrix entries and review contracts. (Examples: gpu-team, private-deploys)
- CI owners: maintain Buildkite steps and runner pools (Primary: eng-infra-cicd)
- Oncall: respond to rollout holds and escalate per incident runbook.

Operational checklists (pre-publish quick checklist):
- [ ] Linting green and no tfsec criticals
- [ ] Contract tests written for all consumers in consumer matrix
- [ ] CHANGELOG entry and migration notes present
- [ ] Publish metadata (compatibility, consumers) populated
- [ ] Owner and reviewer set in registry metadata

Appendix A — Example minimal GH Actions job for mocked contract tests:
```
name: Contract Test
on: [pull_request]
jobs:
  contract:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - name: Set up Go
        uses: actions/setup-go@v4
        with:
          go-version: '1.21'
      - name: Run terratest contracts
        run: go test ./test -run TestModuleContracts -v
```

Appendix B — Example terratest assertion (pseudo-code):
```
func TestModuleContracts(t *testing.T) {
  t.Parallel()
  options := &terraform.Options{...}
  defer terraform.Destroy(t, options)
  terraform.InitAndApply(t, options)
  subnetIds := terraform.OutputList(t, options, "subnet_ids")
  assert.GreaterOrEqual(t, len(subnetIds), 2)
}
```

Frequently asked questions (FAQ):
Q: Who approves major version publishes?
A: Module owner + two consumer owners + security reviewer. Major versions must include a migration guide.

Q: Can a module bypass canary steps?
A: Only in emergency with exec approval and a documented post-publish remediation plan; all bypasses are audited.
