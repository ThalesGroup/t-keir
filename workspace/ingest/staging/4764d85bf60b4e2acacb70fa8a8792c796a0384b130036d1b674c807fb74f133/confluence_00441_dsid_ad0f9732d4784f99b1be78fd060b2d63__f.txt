Forensic-Friendly Rollback Protocol and Telemetry Preservation — Operator Guide

Summary:

This runbook describes a forensic-friendly rollback protocol for Redwood Private deployments (VPC and on-prem). It prioritizes safe service recovery, preservation of diagnostic telemetry and evidence, and minimal customer impact while keeping a clear chain-of-custody for postmortem analysis. Use this guide when a production rollout or upgrade causes: total or partial service regressions, data-integrity concerns, or regulatory-impacting failures.

Scope and applicability:
- Applies to: Private (VPC) control-plane coordinated upgrades, on-prem appliance upgrades, model artifact swaps, KV cache schema or migration rollouts.
- Not intended for: transient infra flakiness that can be resolved by autoscaler/tuner. Use the incident triage playbooks in day-2-ops for those cases.

Goals and acceptance criteria:
- RTO target: 15 minutes for partial rollbacks, 60 minutes for complex stateful rollbacks across regions.
- Preserve at least 99% of request-level telemetry for the incident window (see Telemetry Preservation below).
- Maintain auditable evidence for all changed artifacts and operator actions.
- Avoid customer data loss; if unavoidable, follow the evidence and notification procedures in Customer Impact and Legal Notification.

Ownership and escalation:
- Primary on-call: Private Deployments SRE (team: eng-private-deployments).
- Escalation: Platform Reliability -> Security Incident Response (if evidence tampering or exfiltration suspected) -> Legal & Compliance.
- Communications: use #private-deploy-ops and the customer-facing incident template to coordinate external communications.

Prerequisites and pre-rollback checks:
1) Confirm problem scope: model-only (inference quality), runtime-only (latency/CPU/GPU), or data plane (egress/ingest).
2) Confirm reproducible signal: elevated 5xx rate, token-level latency regression >2x baseline, or model-output quality regressions on canary prompt set.
3) Snapshot metadata and top-level state: control-plane revision, model artifact versions, KV-cache epoch IDs, node inventory.

Telemetry preservation strategy:
- Sampling: switch to full-sampling for the incident window for these streams: request traces, model-input snapshots (redact PII), kernel-level GPU telemetry, and operator CLI actions.
- Buffering: for on-prem/airgapped sites, enable the local telemetry buffer retention (config: telemetry.buffer.enabled=true, telemetry.buffer.size=10GB) and do not rotate buffers until evidence preserved.
- Export: immediately trigger an export job to the secure evidence S3 bucket (or customer-specified bucket for VPC) with prefix: evidence/rollback/{customer}/{YYYYMMDD_HHMMSS}.
- Hashing: compute SHA256 of exported archives and record in the evidence ledger.

Decision matrix: rollback vs degrade vs fix-forward
- Rollback if any of:
  - Model artifact causes a quality regression >10% on production prompt set AND cannot be mitigated by config knobs in 10 minutes.
  - New runtime binary causes persistent 5xx >0.5% for 30 minutes.
  - Migration causes KV-cache inconsistency across >5% of tenants.
- Degrade (gradual feature toggle) if the failure is localized and rollback would cause broader disruption (use canary-unwind pattern).
- Fix-forward if the change is non-stateful and small patch can be validated within the SLO windows.

Pre-rollback checklist (operator must complete this before initiating rollback):
- [ ] Document incident id and reason in ticketing system.
- [ ] Record control-plane revision, model and artifact checksums.
- [ ] Trigger telemetry full-sample and evidence export.
- [ ] Validate backups for KV-store and model artifact repository exist (timestamped).
- [ ] Notify impacted customers per SLA template if customer-facing.

Rollback procedure (high-level, numbered steps):
1) Enter safe-mode for the affected tenants: restrict new model swaps and disable autoscale-driven node churn.
2) If a model artifact is the rollback target: mark model variant as deprecated and pin to previous stable artifact; run model-swap API with --force=false to ensure an orchestrated swap.
3) For runtime binary rollbacks: initiate orchestrated canary rollback through the control-plane with the stable image tag. Use the operator CLI: 
   - rwdctl rollout rollback --service serving-runtime --to-tag v2026.01.10-stable --max-in-flight 2
4) If stateful (KV) migration was applied, follow the stateful rollback cookbook: pause writes, run the reversible migration revert script, and coordinate epoch rollback across shards.
5) During rollback, keep telemetry full-sampling active and stream a copy of logs to the evidence bucket.
6) After each chunk of traffic is moved back, run verification tests (see Verification below).
7) When green, slowly re-enable autoscaling and unpin services; leave monitoring elevated for three full SLO windows.

Verification and acceptance tests (run after each step):
- Smoke tests: /health, per-tenant routing checks, and tokenized latency suite (p95 and p99 targets).
- Functional: run canary prompt set against model (if model swap) and compare quality metrics to baseline.
- Consistency: KV checksum and sample query validations for 1000 random keys.
- Telemetry: confirm export archive integrity and SHA256 matches evidence ledger.

Evidence collection and chain-of-custody:
1) Evidence artifacts to preserve: control-plane snapshots, model artifact checksums, operator CLI history, telemetry export, node-level system profiles (journalctl /var/log/syslog), and storage backend snapshots.
2) Evidence packaging: package artifacts into a single signed archive, compute SHA256 and sign with operator key (KMS/HSM).
3) Ledger entry: add an immutable ledger record with fields: incident_id, archive_path, sha256, signer, timestamp. Use the ledger CLI: ledger add --incident $ID --path s3://evidence/... --sha256 $HASH --signer priyam
4) Secure storage: move the archive to the restricted evidence S3 with bucket-policy: deny-delete-unless-role:legal_audit.

Special considerations by deployment type:
- VPC (customer-attached bucket):
  - Ensure export job uses the customer-approved encryption key.
  - Confirm network egress rule allows telemetry export to the bucket; if not, use the edge-proxy relay pattern.
  - Coordinate with customer security contact before moving evidence off-network where required by contract.
- On-prem / Airgapped:
  - Use local-attested USB transfer procedure only after signing and storing checksums in the control-plane ledger.
  - Maintain chain-of-custody paper or digitally-signed receipts for physical transfers.

KV cache and model artifact specifics:
- Rolling back a model that requires a changed KV cache schema requires a two-phase approach: first, restore service to stable model and keep both schema-compatibility adapters active; second, run adapter-based reconciliation across tenants for 48–72 hours before deprecating the old adapter.
- Avoid purging KV epochs until reconciliation is complete. If storage pressure requires pruning, take snapshots and store in the evidence bucket with explicit ledger references.

Interaction with customer requirements and SLAs:
- If rollback affects committed SLA windows, follow the customer compensation matrix and notify Customer Success.
- For regulated customers (finance/healthcare), follow the additional evidence preservation checklist in the Customer Requirements Library (see Related pages).

Runbook snippets and CLI examples:
- Trigger full telemetry sample: rwdctl telemetry sample --scope incident --enable true --duration 2h
- Export evidence: rwdctl evidence export --prefix evidence/rollback/${CUSTOMER}/${ID} --include logs,traces,artifacts --encrypt-kms arn:aws:kms:us-west-2:1234:key/abcd
- Roll back runtime image (canary-aware): rwdctl rollout rollback --service serving-runtime --to-tag v2026.01.10-stable --max-in-flight 2

Post-rollback steps and postmortem:
1) Keep monitoring elevated for 72 hours; collect SLO/quality metrics and compare to pre-incident baseline.
2) Populate postmortem with: timeline, root-cause hypothesis, decision justification for rollback, evidence ledger entries, and remediation action items.
3) If rollback should be automated for similar failures, open a design ticket for a safe-automation RFC and schedule a canary test.

Appendix A — Minimal evidence metadata table:
