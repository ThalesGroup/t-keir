Dependency latency attenuation playbook and operational pattern catalog

Overview

Purpose
This playbook codifies a set of operational patterns, configuration defaults, and rollout procedures for attenuating latency volatility introduced by downstream dependencies (datastores, feature services, model shards, third-party APIs, and hardware-accelerated kernels). It is intended for service owners, SREs, and runtime engineers who own end-to-end request latency SLOs.

Scope
- Applies to all Redwood production services that contribute to user-facing inference latency (edge proxies, request routers, model-serving frontends, and orchestration layers).
- Covers patterns for fault-tolerant latency control: time budgets, graceful degradation, hedging, caching, pipelining, rate-limiting, and backpressure.
- Does NOT replace per-service runbooks; it is a catalog and prescriptive default.

Why this matters
Downstream variability (GPU preemption, noisy neighbor I/O, upstream control plane spikes, external API throttling) is the most common root cause of bursty P50/P95 regressions. Consistent attenuation reduces incident volume, simplifies incident severity classification, and lowers token-unit cost by avoiding expensive emergency fallbacks.

Key concepts and definitions
- Attenuation: The deliberate insertion of control logic at call-sites to prevent downstream tail events from disproportionately affecting user-observed latency.
- Latency budget: Per-stage allocation of the end-to-end SLO (e.g., request_end_to_end_slo = 1200ms; model_infer_budget = 800ms).
- Elastic degradation: Graceful reduction of quality or feature set when budgets are exceeded (e.g., switch to cached answer, shorten context sent to model).
- Fast-fail vs Hedge: Fast-fail returns immediately with fallback when a call exceeds a short local timeout; hedging issues a parallel second request with higher cost to reduce tail latency.

Operational patterns (catalog)
1) Tiered time budgets and local timeouts - For every external call, require a documented latency budget and a local enforcement timeout that is a fraction of the allocated budget. Example: model shard call with allocated budget 400ms => local enforcement timeout = 320ms (80%). - Enforce time budget using language-level cancellable contexts or request-scoped cancellation tokens. - On timeout, emit an event with dimensions {service, route, caller_component, budget_class}.

2) Graceful degradation strategies (quality vs latency trade-offs)
- Prefer deterministic, low-compute fallbacks: prefix cache lookup, shorter prompt template, condensed user input, or canned response where correctness requirements allow.
- Degradation hierarchy (preferred order): in-memory cache -> local LRU prefix-match -> approximate reranking (cheap embedding) -> lower-capacity model variant -> canned/generic result.

3) Hedging policy (parallelism with guardrails)
- Use hedging only for requests where P95 tail materially affects UX and cost is justified by user impact.
- Default hedge policy: issue second request at 1.5x local budget when the first request hits 60% of its budget. Cancel slower request on first successful response.
- Hedge budget must be accounted for in cost forecasting and feature gating.

4) Client-side and gateway admission control
- Gate incoming traffic based on dynamic backpressure signals: outbound queue depth, active GPU utilization, and per-tenant cost throttles.
- Admission tiers: standard, degraded (reduced throughput), and blocked. Transitions must be recorded as events and tied to alerting.

5) Smart short-circuit and fast-path routing
- Short-circuit to cached outputs or lower-cost variants when request matches known patterns (exact prompt hash, frequent query). - Maintain a short-lived in-memory bloom filter for hot prompt-hashes to reduce cache-miss cost.

6) Circuit breakers and progressive retry policies
- Circuit breaker states: CLOSED, OPEN, HALF-OPEN. Open when error rate or latency breach exceeds threshold for 2 consecutive minutes. Use exponential backoff with jitter for retries and a guarded probe in HALF-OPEN. - Retries: only for idempotent idempotency-keyed requests. Maximum retries = 2; backoff base = 100ms.

7) Backpressure propagation and capacity-aware batching
- If downstream lag or GPU backlog exceeds threshold, upstream components should pause non-essential work and inform routers to reshape traffic (batch windows, fewer concurrent streams). - Implement a priority queue where control-plane and critical SLO traffic are preemptive.

8) Observability and signal taxonomy
- Required metrics at every call site: latency_histogram_ms, p50/p95/p99, error_rate, timeout_rate, active_inflight, retry_count.
- Required traces: end-to-end trace with spans for caller, network, dependency, and client-side cancellation. Include budget allocation tags: budget_total_ms and budget_consumed_ms.

Recommended defaults table (apply unless service-specific justification documented)
| Parameter | Default value | Rationale | Guardrail |
|---|---:|---|---|
| End-to-end SLO (interactive) | 1200ms | Target for chat/interactive inference | SLO must be declared in service profile |
| Per-stage budget (model inference) | 800ms | Typical model infer central budget | Budget must be validated under synthetic load |
| Local enforcement fraction | 80% | Protect downstream step for cancellation overhead | Must be >60% and <95% |
| Hedge trigger | 60% of local budget | Avoids unnecessary parallelism | Hedge only enabled via feature flag |
| Max retries | 2 | Limits amplification | Retries only for safe idempotent paths |
| Circuit open threshold | 5% error_rate or p95 > 2x budget for 120s | Fast protection from cascading failures | Requires ops review to adjust |

Instrumentation checklist (must be present in PRs that change call sites)
- Add local timeout and cancellation handling.
- Emit budget-start and budget-end events.
- Tag traces with budget metadata.
- Add metric for fallback_usage_count.
- Add alert if fallback_usage_count > 1% sustained for 10 minutes.

Runbook: detection -> mitigation -> post-incident steps
1) Detection (alerts)
- Alert: model_infer_p95 > 1.5x declared budget OR fallback_usage_count spike > 1%
- Pager: for sustained breach > 10 minutes or if customer-facing errors increase.

2) Mitigation (first 15 minutes)
- Triage owner (service-oncall) verifies recent deploys, config changes, and upstream incidents.
- Immediately enable fast-path degradation flag (pre-approved per-service) to switch to cached or smaller-variant model.
- Reduce admission rate to degraded tier by 25% if p95 remains high after 30s.
- If degradation ineffective, engage infra to scale GPU pool or shift traffic to a different region/replica.

3) Longer-term remediation
- Run synthetic replay with golden prompt set to reproduce tail.
- If root cause is a third-party API, apply aggressive caching and adjust circuit thresholds; consider on-ramps for SLA-bound customers.
- If root cause is model kernel stall (GPU), schedule kernel vendor escalation and perform kernel-version rollback per kernel upgrade playbook.

Rollout checklist for new attenuation features (minimum gate requirements)
1) Design doc with rationale and cost model that includes hedging overhead estimates.
2) Unit + integration tests that simulate timeouts and verify fallback path.
3) Controlled canary: start at 1% traffic with traffic shaping and synthetic golden prompts, monitor fallback_usage_count, p95, and cost delta.
4) Progressive ramp: 1% -> 5% -> 25% -> 100% with at least 30 minutes at each stage and automated rollback gates.
5) Post-rollout AAR (blameless) and update runbooks.

Ownership and responsibilities
- Service owner: declares per-route SLOs and budgets, implements local enforcement, owns runbook entries.
- Runtime/SRE: provides libraries for cancellable contexts, default middleware for timeouts/hedging, and dashboards.
- Observability team: enforces metric names, trace tags, and alert thresholds.

Open decisions (ADRs required)
- Whether hedging is allowed for non-interactive batch workloads (decision pending; default: disallowed).
- Standardized budget partitioning algorithm for multi-stage pipelines (proposal due Q2 2026).

Appendix: Example incident timeline (short)
- 12:03: Alert: Inference p95 increased to 2.5x budget.
- 12:05: Service oncall toggles enable_aggressive_degradation. p95 drops to 1.1x budget in 90s.
- 12:12: Traffic scaled down, infra adds a replica.
- 12:45: Root cause identified as an external feature service partial outage. Circuit thresholds adjusted and a cache warm-up job deployed.
