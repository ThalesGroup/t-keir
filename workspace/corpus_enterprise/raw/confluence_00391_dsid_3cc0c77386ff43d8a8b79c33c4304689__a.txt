Availability & Scaling Handbook: SLO-driven Capacity Playbook

Overview:

This handbook formalizes SLO-driven availability and scaling practices for Redwood Inference services. It codifies how we translate SLOs and error-budget signals into capacity decisions, autoscaling policies, reservation hedges, and runbook steps that keep production latency and availability within targets while minimizing cost. The intended audience is SREs, platform engineers, and service owners.

Key goals:
- Maintain availability SLOs with >=95% confidence under forecasted load and graceful degradation beyond design capacity.
- Automate capacity changes where safe; require manual approval for high-cost reserved capacity.
- Integrate error budget burn into autoscale and rollout decisions.

Relevant services and owners:
- inference-api (owner: eng-serving-runtime) — primary public REST endpoints, SLO: 99.95%% availability per 30d and p95 latency < 180ms.
- kv-cache (owner: eng-serving-runtime) — model KV cache service, SLO: 99.9%% availability per 30d.
- batch-ingest (owner: eng-platform) — background batching pipeline, SLO: 99.5%%.

SLO-to-Capacity mapping (short):
- Availability SLO 99.95%%: plan for 2.5x steady-state peak capacity with 10%% reserved hedge.
- Availability SLO 99.9%%: plan for 2x steady-state peak with 7%% reserved hedge.
- Non-critical batch SLOs: 1.4x peak with preemptible nodes allowed.

Operational thresholds and escalation:
- Normal: error-budget burn rate <= 1.0 — no escalations.
- Elevated: burn rate > 2.0 for 1 hour — page on-call, open incident channel, run corrective autoscale policy.
- Critical: burn rate > 4.0 for 15 mins or availability below SLO for > 10 mins — escalate to SRE pager and notify Eng-Leadership.

Autoscaling policy templates:
1) latency-sensitive endpoints (inference-api):
   - Metric: p95 latency and rps per instance.
   - Scale-out trigger: p95 > 150ms OR rps per instance > 200 for 3 minutes.
   - Scale-in trigger: p95 < 120ms AND rps per instance < 120 for 10 minutes.
   - Max burst: reserve 10%% headroom beyond target instances.

2) cache-backed services (kv-cache):
   - Metric: 99th percentile kv miss latency + eviction rate.
   - Policy: prefer vertical scale (larger instance) for low-latency tails, fallback to horizontal scaling when miss rate sustained > 5%%.

Capacity planning checklist (quarterly):
1. Forecast peak RPS by service using last 90-day 95th-percentile and business projections.
2. Calculate required instance-hours using performance curves from benchmarking suite: tokens/sec per GPU, warm/cold tail multipliers.
3. Add safety corridor: 10%% for guaranteed SLOs, 5%% for non-critical.
4. Map instance-hours to reserved capacity purchases and on-demand burst strategy.
5. Submit finance request for Dedicated reservations if forecasted monthly spend > $200k.

Runbook: sustained high burn (error budget)
1. Triage (first 10 minutes):
   - Verify SLO dashboards: availability, p95/p99 latency, error-rate by route and model.
   - Confirm whether burn is traffic-driven (external spike) or regression-driven (deploy/release).
2. Immediate mitigations (10-30 minutes):
   - If traffic spike: temporarily increase autoscaling limits and apply emergency instance pool (see CLI below).
   - If regression: rollback the release and scale up healthy model variant or fallback route.
   - Apply traffic shaping: enable per-tenant rate limits and prioritization (tiered routing).
3. Medium-term (30-120 minutes):
   - Provision reserved instances if forecast shows sustained increase > 12 hours (manual approval required).
   - Open incident review with owners, record decisions and evidence.

Emergency CLI snippets:
- Add emergency pool (Terraform-based):
  terraform apply -var='pool_name=emergency-pool' -var='min_gpus=8' -auto-approve

- Runtime scaling via internal CLI: (requires SRE role)
  rictl scale service inference-api --min 60 --max 120 --reason "emergency burn-rate"

Capacity hedging patterns (unique to Redwood):
- Safety corridor windows: maintain a rolling 48-hour reserved hedge equal to forecast 95th-pt * 10%%. This hedge is covered by Dedicated warm-pools (on call for Finance approval).
- Predictive spin-up: if the predictive model (see infra-predictor) estimates >20%% growth in next 6 hours with >85%% confidence, pre-warm 20%% of the predicted extra pool.
- Tenant slices: for multi-tenant services, maintain per-tenant soft-quota and a shared overflow pool to prevent noisy-neighbor collapse.

Integration with Incident Review and Reliability initiatives:
- Every critical availability incident must produce a linked post-incident report (PIR) and a capacity action item if root cause includes insufficient capacity. The PIR must include: timeline, SLO impact, error-budget delta, and recommended capacity changes.
- Quarterly reliability initiative: run a "reserve-surge" exercise simulating a 3x traffic spike for 6 hours across region pairs and validate automated hedges. Results feed into next-quarter purchase decisions.

Observability and tooling config snippets:
- Rules to compute burn rate:
  burn_rate = (error_budget_consumed / error_budget_total) / (time_window_minutes / 43200)
  Alert when burn_rate > 2 for 60 minutes (severity P2).

- Example Prometheus alert (pseudo):
  ALERT ErrorBudgetHighBurn
  IF burn_rate_service_inference_api > 2
  FOR 15m
  LABELS {severity=\"high\", team=\"eng-sre\"}
  ANNOTATIONS {summary=\"Sustained error budget burn for inference-api\"}

Governance and approvals:
- Any purchase of Dedicated reserved capacity requires: service owner signoff, SRE capacity plan, and Finance approval. Use the procurement template: procurement/reservation-request-2026.
- Automatic scaling parameter changes allowed by SREs; permanent increases to minimum reserved pools require a runbook entry and owner approval.

Post-incident capacity action template (to be included in PIR):
1. Incident ID and time window
2. Error budget impact (tokens or percent)
3. Was capacity the root cause? (Y/N)
4. Recommended immediate changes (scale, reserve, rate-limit)
5. Recommended long-term changes (benchmarking, code-level optimizations, additional hedging)
6. Owner and ETA for each action
