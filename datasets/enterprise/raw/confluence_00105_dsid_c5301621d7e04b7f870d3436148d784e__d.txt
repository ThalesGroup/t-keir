Dedicated-tenant-cutover-safety-net-playbook

Summary:

This playbook describes the safety-net and validation steps for cutover of a customer to a Redwood Dedicated tenant (reserved GPU pool). It focuses on minimizing user impact, preventing cost surprises, ensuring model-quality continuity, and providing clear rollback criteria. Use this playbook for final-week cutovers, high-risk migrations, or when a customer requests aggressive performance/cost targets.

Audience:
- Customer Success (CS) leads running the cutover
- SRE/Platform engineers executing capacity and routing changes
- Solutions/SE engineers responsible for integration validation
- Customer engineering contacts

Goals:
- Verify routing and auth for Dedicated endpoints with zero-production-traffic disruption
- Prevent token-cost spikes and quota blast through pre-cutover throttles and cost guards
- Validate model output quality parity with hosted-tier baseline on representative prompt sets
- Have an automated and manual rollback path with clear thresholds and owners

Prerequisites (hard blockers before cutover):
1. Dedicated capacity provisioned and green in the infra dashboard (Dedicated pool: <pool-id>)
2. Networking: VPC peering/firewall rules approved and tested in staging; VPN tunnels validated
3. IAM and customer API keys provisioned in a locked state for cutover window
4. Telemetry hooks in place: request traces, token-level cost, model version tags, and streaming logs to the customer-specific telemetry workspace
5. A canonical prompt set (10–50 prompts) selected for automatic quality checks (attach file to the ticket)
6. Escalation roster confirmed and reachable for the cutover window

Cutover safety-net configuration checklist (automated + manual):
| Area | Safety-net configured | How to verify |
|------|-----------------------|---------------|
| Routing | Canary traffic route + 5% initial traffic | Use gateway canary rule: tag requests with header X-Canary:dedicated | curl -H 'X-Canary:dedicated' -k https://api.redwood.example.com/health |
| Rate limiting | Per-tenant burst limiter: 50 rps; sustained throttle after 120s | Check rate-limit metrics in Grafana: metrics.ratelimit.tenant.<tenant-id>.rate |
| Cost protection | Token cost alert threshold: 2x baseline for 5min -> auto-throttle | Simulate large batch, watch cost delta in billing-live stream |
| Model fallback | Fallback route to hosted-similar-version with 1s latency penalty | Validate by forcing runtime unavailability: curl -X POST https://control-plane/.../simulate-fail |
| KV cache warmup | Prefetch top 100 prefixes from sample corpus | Confirm cache hit-rate > 70% within 10 minutes | Grafana: runtime.kvcache.hit_rate.tenant.<tenant-id> |
| Quality sentinel | Automatically run canonical prompts every 2 min and compute BLEU/ROUGE/semantic-sim score | Check daily quality dashboard; fail -> rollback flag in runbook |

Pre-cutover sanity checklist (run ~1 hour before):
- [ ] Run capacity smoke test: incremental 1, 5, 25, 100 concurrent requests at production token lengths
- [ ] Validate TLS cert chains for dedicated endpoints
- [ ] Confirm customer token scoping (read-only vs full) and IP allowlist applied
- [ ] Ensure canary header injection and sampling rate set to 5%
- [ ] Start continuous canonical prompt runner (see Validation below)

Cutover procedure (step-by-step):
1. Cutover kickoff meeting in #cs-cutovers and record the session. Confirm runbook owner and SLOs.
2. Set maintenance window in status page and notify customer stakeholders when 5 minutes out.
3. Route 5% of traffic with canary header to Dedicated pool. Monitor for 5 minutes for errors and quality drift.
   - Command to test canary routing (example):
     curl -v -H "Authorization: Bearer <cust-token>" -H "X-Canary:dedicated" -d '{"input":"Hello"}' https://dedicated.<tenant>.inference.redwood.example.com/v1/chat/completions
4. If step 3 stable, increase to 25% for 10 minutes. Continue sampling canonical prompts and live traffic metrics.
5. If no regressions and SLOs held, increase to 60% for 15 minutes and then to 100% if green.
6. Remove throttles only after 30 minutes of stable 100% traffic.

Validation and automated checks (what the platform will run):
- Latency: p50/p95/p99 must be within the committed SLOs (default Dedicated SLOs: p95 < 250ms for small models, p95 < 700ms for long-sequence workloads).
- Errors: 5xx errors must remain < 0.5% of requests in a rolling 5-minute window.
- Cost delta: per-token cost should not exceed the estimated forecast by more than 40% in the first hour.
- Quality sentinel: run canonical set and compute similarity to baseline hosted outputs. Failure = similarity drop > 8% (operator-defined).

Example telemetry queries (copy/paste):
- PromQL: 5m error rate per tenant
  sum(rate(http_requests_total{job=\"inference\",tenant_id=\"<tenant-id>\",status=~\"5..\"}[5m])) / sum(rate(http_requests_total{job=\"inference\",tenant_id=\"<tenant-id>\"}[5m]))

- Grafana filter: runtime.kvcache.hit_rate{tenant_id=\"<tenant-id>\"}  (set threshold alert: < 0.70 for 10m)

- Example SQL (billing):
  SELECT time_bucket('1 minute', ts) AS minute, SUM(tokens) AS tokens, SUM(cost) AS cost FROM billing.events WHERE tenant_id = '<tenant-id>' AND ts > now() - interval '60 minutes' GROUP BY minute ORDER BY minute DESC LIMIT 60;

Rollback criteria (automatic and manual):
Automatic rollback (platform will trigger):
- Sustained 5xx error rate > 2% for 10 minutes
- KV cache miss rate > 90% sustained for 15 minutes causing token amplification
- Cost delta > 3x forecast in 30 minutes

Manual rollback (CS/SRE decision if any of the following):
- Model quality sentinel fails 3 consecutive runs and customer reports degradation
- Latency p95 > committed SLO for 20 minutes
- Persistent auth or routing failures affecting > 10% of requests

Rollback procedure (manual):
1. Announce immediate rollback in #cs-cutovers and #infra-oncall.
2. Flip routing to hosted fallback via routing-control API: set route priority for tenant to hosted-fallback.
   - Example control-plane API payload (curl):
     curl -X POST https://control-plane.redwood.example.com/v1/routes/override \
       -H "Authorization: Bearer <admin-token>" \
       -H "Content-Type: application/json" \
       -d '{"tenant_id":"<tenant-id>", "override": {"route":"hosted-fallback", "priority": 100}}'
3. Scale down Dedicated pool ingress for tenant to reduce billing exposure (Platform does this via: infra scale down --tenant <tenant-id> --to 0).
4. Run post-rollback validation: ensure hosted-tier metrics return to baseline and customer traffic flows with acceptable latency.

Post-cutover checklist and artifacts to create (within 24 hours):
- Formal cutover report: include observed metrics, incidents, and time-series screenshots. Owner: CS lead.
- Cost reconciliation: compare forecast vs actual first-24h cost. Owner: Finance ops contact.
- Quality follow-up: evaluate sample of production prompts for semantic drift; if any issues, engage model-onboarding team.
- Update customer onboarding record in CRM with cutover outcome and any action items.

Common failure modes and mitigation notes:
- API key scope mismatch: cause = key previously scoped to hosted endpoints only. Mitigation: pre-validate token with dedicated endpoint using curl -I request.
- Excessive cold KV cache misses: mitigation: run cache-warm job pre-cutover and increase warmup to top-500 prefixes if needed.
- Rate limit misconfiguration: verify rate-limit policy applied to tenant namespace and not global shared bucket.

Appendix A — Canonical prompt runner (example script snippet):
#!/usr/bin/env bash
# Run canonical prompts against new dedicated endpoint and compute simple similarity (cosine of embeddings)
CANONICAL_FILE=canonical_prompts.jsonl
ENDPOINT=https://dedicated.<tenant>.inference.redwood.example.com/v1/embeddings
API_KEY=<cust-token>
while read -r line; do
  prompt=$(echo "$line" | jq -r '.prompt')
  curl -s -H "Authorization: Bearer $API_KEY" -H "Content-Type: application/json" -d "{\"model\":\"embed-v1\",\"input\":\"$prompt\"}" $ENDPOINT 
  sleep 1
done < $CANONICAL_FILE
