Privilege slimming and compliance synthesis

Summary:
This document defines Redwood Inference's "privilege slimming" program: an operational pattern that reduces and stabilizes entitlements across product, infra, and platform services while producing audit-grade artifacts and retention packages suitable for regulatory review. It ties RBAC changes to audit logging, data residency/retention policy, secure SDLC gates, incident response forensics, and a compliance evidence workflow. The goal is to lower blast radius from excess permissions and streamline evidence collection for audits with minimal developer friction.

Audience and scope:
- Audience: security engineers, platform engineers, SREs, engineering managers, compliance team, and auditors.
- Scope: applies to interactive user roles, service identities, CI/CD service accounts, and short-lived credentials across hosted, dedicated, and private deployments. Excludes ephemeral runtime model keys (handled by model-key-rotation doc).

Principles:
1) Least privilege by default: new roles start with read-only access; escalation must be authorized.
2) Evidence-first changes: every entitlement modification must emit an audit event and an evidence snapshot captured by our evidence-orchestrator service.
3) Timebound approvals: temporary entitlements should include automatic expiration and an approver audit trail.
4) Residency-aware access: entitlements that grant access to data in protected regions must carry residency tags for retention and legal hold processing.
5) SDLC integration: code and infra changes that affect RBAC require automated evidence packaging as part of the CI pipeline.

Key services and artifacts referenced:
- authz-service: central evaluation API for RBAC checks (service: authz.redwood.internal).
- audit-collector: Kafka-based ingestion for auth/audit events (topic: audit.events.authz).
- evidence-orchestrator: serverless pipeline that snapshots role manifests, approval emails, and logs into s3-evidence-bucket (encrypted with KMS key arn:aws:kms:region:acct:key/evidence-enc).
- audit-query: Kibana dashboards (dashboards: RBAC-Changes, Privilege-Slimming-Overview).
- cicd-pipeline / argo-cd: gates for RBAC-affecting PRs.

Privilege slimming lifecycle (high level):
1) Discovery: scheduled entitlement inventory runs (weekly) produce a 'role heatmap' with usage metrics from audit-collector.
2) Candidate selection: roles with <5 uses/month or unused privileges across >30 days are flagged.
3) Risk assessment: product/owner confirms business need or requests timebound exception.
4) Slimming change: role is reduced in scope, change is recorded in git (roles repo), PR includes mandatory evidence bundle.
5) Monitor & revert window: change is deployed behind a 72-hour canary with telemetry alerts.
6) Certification: after 90 days without negative impact, change is accepted and logged as permanent.

Procedure: automated entitlement reduction (detailed):
1. Run entitlement inventory job:
   - CLI: inventory-runner --scope=all --since=30d --out=role-heatmap-YYYYMMDD.json
2. Candidate triage by owner team: open ticket in Jira (project: SEC-ENT) and assign risk level (low/med/high).
3. If low risk, create a roles repo PR with the change. PR template must include: rationale, audit-query link, approval request (approvers: role_owner, sec-eng).
4. CI gate (cicd-pipeline): runs the evidence packager which records:
   - changed_role.yaml (manifest)
   - approval_email.eml (signed)
   - pre-change-audit-slice.json (last 30 days)
   Evidence packager uploads to s3-evidence-bucket with metadata tags {role:, owner:, residency:}.
5. Deploy behind canary (72h): monitoring alerts if failed auth rate changes >0.1% for affected service or latency regressions >20ms.
6. After canary, if no regressions, the change automatically seeds the certification job for 90-day acceptance.

Audit logging requirements (RBAC-specific):
- Required events: role.create, role.update, role.delete, permission.grant, permission.revoke, temporary-approval.grant, temporary-approval.revoke, impersonation.start/stop.
- Event schema (flat JSON example):
  {
    "event_type": "permission.revoke",
    "actor": "svc-account:ci-builder@redwood",
    "target_role": "model-serving-reader",
    "timestamp": "2026-02-15T10:12:00Z",
    "request_id": "req-abc123",
    "residency_tag": "eu-west-1",
    "evidence_ref": "s3://s3-evidence-bucket/2026/02/15/revoke-req-abc123.json"
  }
- Ingestion SLO: audit-collector must accept and persist >99.95% of authz events within 30 seconds of emission. Alert if 5m consecutive delay or backlog >1M events.
- Retention tiers: See retention matrix below.

Retention and residency matrix (summary table):
| Data class | Residency tag required? | Short retention | Long retention (archive) | Notes |
|-----------|------------------------|-----------------|-------------------------|-------|
| Entitlement audit events | yes | 365 days | 7 years | default for enterprise customers in regulated regions |
| Approval artifacts (emails, PRs) | conditional | 2 years | 7 years | if related to regulated data, archive in-region |
| Role manifests | no | 365 days | 3 years | manifests are git-backed; snapshot retained 1 year in evidence bucket |
| Forensic packages (incident) | yes | 5 years | 10 years | legal hold may extend indefinitely |
| Temporary credential audit traces | yes | 90 days | 2 years | keep to support retroactive queries

Implementation notes for residency enforcement:
- Every authz event MUST include a residency_tag field when the principal, resource, or dataset is regionally controlled. The authz-service will reject requests missing residency_tag for resources labeled as protected (403 + log).
- Evidence-orchestrator uploads retention-metadata.json alongside artifacts to enforce placement into region-specific S3 buckets (e.g., s3-evidence-eu. redwood).

Secure SDLC integration:
- PR-level gating: any PR that touches roles repo or authz-service code must include an evidence snapshot and pass a static analysis check for authz regressions (tool: authz-lint).
- Pre-merge checklist (automated):
  1) authz-lint: pass
  2) audit-slice: no anomalous deny spikes in last 7 days
  3) approval: signed by role_owner and sec_eng
  4) residency_tagging: validated for affected resources
- Post-merge: cicd-pipeline triggers packager and notifies owners in #sec-privilege-slimming, attaching the evidence bundle link.

Incident response tie-ins:
- When an incident involves privilege escalation or anomalous entitlements, incident lead runs the 'forensic evidence retrieval' playbook which pulls:
  - all authz events for the identity in question (time window +/- 48h)
  - the role manifests and approval history
  - temporary credential traces and session logs
- Forensic Retrieval CLI (example):
  forensic-retrieve --identity svc:user-123 --from=2026-02-10T00:00:00Z --to=2026-02-12T00:00:00Z --out=./incident-123-artifacts/
- Evidence integrity: every artifact pulled is signed by evidence-orchestrator with SHA256 and stored in a chain-of-custody file (chain_of_custody.json) before being delivered to legal or auditors.

Compliance evidence workflow (audit readiness):
1) Trigger: annual audit or customer-requested evidence package.
2) Scope agreement: compliance team and service owners agree the required artifact set and residency constraints.
3) Evidence assembly (automated): evidence-orchestrator composes the package from s3-evidence-bucket using the agreed filters and signs the bundle.
4) Human review: compliance reviewer validates package contents; a checklist is completed in AuditTracker (ticket).
5) Delivery: encrypted package delivered to auditor using designated external transfer (scp to auditor endpoint or wetransfer-sftp).
6) Retention and teardown: post-audit, temporary staging copies are deleted; canonical archive retained per retention matrix.

Risk and exceptions model (how to grant and record exceptions):
- Exception purpose: transient business needs or third-party integrations that cannot operate under strict least privilege.
- Exception lifetime: default 14 days; renewals require escalated sign-off (sec director).
- Exception artifact requirements:
  - scoped justification (ticket),
  - compensating controls (monitoring rule or revocation hook),
  - automatic expiry,
  - evidence snapshot uploaded to s3-evidence-bucket with label exception:true.
- Exception review cadence: weekly automated report of active exceptions to the Risk Board. Quarterly deep-dive for exceptions older than 90 days.

Metrics and dashboards to monitor program success:
- Active entitlements per service (trend): target 30% reduction in unneeded privileges in 12 months.
- Unused privileged permissions (30d window): target <0.5% of total perms.
- Audit ingestion latency P50/P95: target <2s / <10s; SLO 99.95% within 30s.
- Exception churn rate: number of new exceptions/week; target decreasing trend.
