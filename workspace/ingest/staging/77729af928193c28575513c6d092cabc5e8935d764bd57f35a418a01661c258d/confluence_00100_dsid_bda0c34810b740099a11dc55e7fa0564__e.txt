Experimental Metric Injection Campaign — Retrospective

Summary
=======

This document is a postmortem-style retrospective of the experimental metric injection campaign we ran from 2025-11-10 to 2025-12-05. The experiment intentionally injected synthetic telemetry into the platform metrics pipeline to validate: (1) alert sensitivity tuning for LLM prefix/KV cache degradation, (2) downstream dashboard behavior, and (3) costing and storage impact of higher cardinality metrics.

This retrospective records the experiment design, outcomes, operational impacts, lessons learned, and recommended next steps. It is intended for platform operators, SRE, observability engineers, and product owners evaluating telemetry tradeoffs.

Background and goals
--------------------

Context: The platform telemetry backlog showed repeated false-positive alerts during short-lived cache thrash events. To evaluate whether our alert rules, aggregation windows, and cardinality controls were balanced, the Observability team proposed a safe, time-limited metric injection campaign that simulates realistic degradation signals without impacting production services.

Goals:
- Validate alerting SLOs and silence durations for cache/serving regressions.
- Measure cost and cardinality impact when emitting per-tenant cache-hit partitions vs. aggregated metrics.
- Verify dashboard and runbook actions (including automated ticket creation) under noisy conditions.

Experiment design (high level)
----------------------------

1. Scope and windows:
   - Active window: 2025-11-10 08:00 UTC to 2025-12-05 20:00 UTC.
   - Test tenants: synthetic-tenant-001 .. synthetic-tenant-050 (no real customer traffic).
   - Injected services: kv-prefix-cache-service, serving-router, request-queue-proxy.

2. Injection mechanics:
   - A dedicated job (metric-injector v0.3.1) published synthetic Prometheus-compatible metrics into the metrics-ingest pipeline via the internal metrics-writer queue.
   - Mutation pattern: ramp-up (5m), steady-state (30m), burst (3m) — repeated every 2 hours.

3. Safety controls (must pass preconditions):
   - Injector uses a low-priority tag and sits behind a feature-flag (ff.metrics_injection).
   - AuthZ: only operator role obs-inject allowed to start/stop jobs.
   - Rate limit: 1500 metrics/sec throttle at the ingestion gateway.
   - Circuit breaker: ingestion spike > 10x baseline triggers automatic halt and alert to obs-ops.

Concrete sample metric (Prometheus exposition format):
# HELP kv_prefix_cache_hit Synthetic cache hit metric for experiment
# TYPE kv_prefix_cache_hit counter
kv_prefix_cache_hit{tenant="synthetic-tenant-001",prefix_shard="shard-12",pool="fast",experiment="metric-injection-2025"} 1

PromQL queries used during the campaign:
- 1m rate of synthetic hits (all tenants): sum(rate(kv_prefix_cache_hit[1m]))
- Per-tenant anomaly detection: increase(kv_prefix_cache_miss[5m]) / (increase(kv_prefix_cache_hit[5m]) + 1) > 0.25

Alerting rules exercised
-----------------------

We deliberately exercised three rule families to observe operator signal-to-noise and automated mitigations.

1) cache-degradation-severe
   - Expr: job:kv_cache_miss_ratio:5m > 0.25 AND sum(rate(kv_prefix_cache_miss[1m])) > 100
   - Severity: critical
   - Pager: obs-oncall -> eng-platform-sme (P1)
   - Runbook excerpt: see section "Runbook actions for severity-critical alerts" below.

2) cache-latency-elevated
   - Expr: histogram_quantile(0.95, sum(rate(kv_cache_request_duration_seconds_bucket[5m])) by (le)) > 0.2
   - Severity: warning
   - Pager: obs-oncall (P2)

3) high-cardinality-telemetry-cost
   - Expr: increase(metric_series_count_total[1d]) > 10000
   - Severity: info (but channels to cost-engineering slack)

Runbook actions for severity-critical alerts
-------------------------------------------

1. Triage (minutes 0–5)
   - Confirm alert origin using the alert details page and run the Playbook Debug CLI: 
     $ ./obsctl alert inspect cache-degradation-severe --start="-10m"
   - If source contains experiment tag experiment=metric-injection-2025, mark as "experimental" and follow experimental isolation path.

2. Isolation (minutes 5–20)
   - Use the operator UI to throttle metric-injector job: 
     $ ffcli set metrics_injection off --env=prod
   - If throttling fails, disable ingestion at the gateway: 
     $ kubectl scale deployment metrics-ingest-gateway --replicas=0 -n observability

3. Remediation (minutes 20–60)
   - If cache miss ratio reduces after halting injector, file a short incident note and run a post-incident checklist.
   - If not reduced, escalate to eng-serving-runtime and perform controlled model-swap fallback.

Observations and outcomes
-------------------------

Summary of collected artifacts (table):
| experiment_id | start | end | peak_cardinality | peak_series_rate | downstream_slo_burn | operator_actions | notes |
|---|---:|---:|---:|---:|---:|---|---|
| MI-2025-11-A | 2025-11-12T08:00Z | 2025-11-12T20:00Z | 24,600 | 1,350/s | serving-router 95th latency +0.9% | throttled injector, no service restart | small, transient dashboard churn |
| MI-2025-11-B | 2025-11-18T02:00Z | 2025-11-18T06:00Z | 42,100 | 2,200/s | cache-service SLO burn 0.4% | ingestion gateway scaled down | required manual backfill of metrics |
| MI-2025-11-C | 2025-11-28T14:00Z | 2025-11-28T18:00Z | 9,800 | 720/s | no measurable SLO burn | no operator action | safe, within forecasted costs |

Key findings:
- Alert fidelity: The critical cache-degradation-severe rule fired 18 times; 11 were attributable to the experiment. After tuning the rule's population threshold (sum(rate(...)) > 250), false positives from the injection decreased by 72%.
- Dashboard behavior: High-cardinality injection increased dashboard load times for 30–45s during peaks. We found one Grafana dashboard panel using unbounded label expansion (tenant label) causing heavy rendering cost; we updated panel to use topk(10, ...) aggregation.
- Cost impact: Metric series cardinality increased ingestion storage costs by ~9% in the experiment window. Extrapolating to sustained per-tenant telemetry (not recommended) would add ~1.2% to monthly telemetry bill per 10k tenants.
- Operator cognitive load: During the first two weeks, oncall time to diagnose experimental alerts averaged 28 minutes per incident. After adding an explicit experiment tag and a fast-path in the alert details UI, triage time dropped to 9 minutes.

Lessons learned
-------------

1. Experiment tagging is critical. Without experiment=... in the injected metrics and the alert payload, engineers could not quickly differentiate synthetic vs real incidents. Add tag by default for future tests.

2. Cardinality control must be enforced in the ingestion layer. The experiment highlighted that per-tenant per-prefix labels explode series count; we should enforce a policy of max 3 dynamic labels for production metrics and apply sampler/rollup for ephemeral tenants.

3. Dashboard templates must use bounded aggregations. Panels that iterate across unbounded label sets are fragile under injection. Use topk(), group_left, or explicit tenant lists in dashboards that power runbooks.

4. Alert rules need two-dimensional thresholds: both ratio and absolute volume guards prevented noisy firing in high-cardinality situations.

Decisions and follow-ups (action items)
-------------------------------------

1) Enforce ingestion label policy (owner: eng-platform telemetry) — due 2026-02-15
   - Implement ingestion-side label whitelist and hard caps in metrics-ingest-gateway.
   - Metric filters to reject metrics with >3 dynamic labels or value cardinality > 100k/day.

2) Alert rule change (owner: obs-slo-team) — due 2026-01-31
   - Update cache-degradation-severe to require sum(rate(...)) > 250 OR increase(metric_series_count_total[1h]) < 5000 to fire.

3) Dashboard hardening (owner: observability-frontend) — due 2026-01-20
   - Audit top-30 dashboards for unbounded label expansions; apply topk(10) or explicit tenant scoping.

4) Experiment framework improvements (owner: platform-experiments) — due 2026-03-01
   - Add an "experiment registry" page that automatically annotates alerts and dashboards when a live experiment is active.
   - Provide a one-click ff toggle for emergency stop and escalation metadata populated in PagerDuty incidents.
