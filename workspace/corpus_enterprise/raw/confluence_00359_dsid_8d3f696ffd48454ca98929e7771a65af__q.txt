Quantization rollout, observability & billing hooks — design spec

Overview

This design spec describes how Redwood will orchestrate a controlled rollout of model quantization variants while ensuring: (1) comprehensive observability to detect quality regressions early, (2) billing hooks that correctly surface changed unit economics to customers, and (3) customer-facing communication and migration tooling. The spec focuses on hosted and dedicated deployments; private deployments will be covered by a companion ops-runbook.

Goals

- Safely enable per-tenant or per-route quantized variants (8-bit/4-bit) with automatic fallbacks.
- Produce telemetry sufficient to detect quality drift within 30 minutes of rollout changes for any tenant.
- Expose billing events and cost delta estimates in the console and usage exports so customers can decide when to opt-in/out.
- Provide an automated preflight simulation to estimate latency, memory, and token-cost changes for a tenant before migration.

Non-goals

- This spec does not define new quantization kernels or low-level runtime execution optimizations (runtime team responsibility).
- It does not replace contractual changes for SLA/price adjustments; it provides signaling hooks and recommended contract text for commercial teams.

Background and motivation

Quantization reduces memory and compute cost but can change output distributions (fidelity) and latency characteristics. Customers with tight quality constraints need: (1) rigorous observability to detect regressions; (2) billing transparency when unit costs change; and (3) safe rollback and migration pathways. Existing model-variant rollouts handle code-level switches, but quantization introduces unique telemetry and billing semantics that must be integrated with Redwood Optimize and Console.

Key concepts

- Quantized variant (q-variant): A model binary compiled/quantized to a lower precision (e.g., int8, int4).
- Preflight simulation: Synthetic or replayed workload run that produces latency/memory/cost delta estimates and a shadow-quality score.
- Telemetry gate: A set of signals (metrics + regressions) used to automatically pause or rollback a rollout.
- Billing hook: Event emitted when a tenant's effective per-token cost or capacity credit changes due to quantization.

Design overview

1) Rollout model

- Variants are deployed per-route (API route) with tenant-specific policy override. Default policy is tenant-opt-in.
- Rollouts support staged canary: internal canary (eng-prod), external canary (select customers), gradual percentage-based ramp, and tenant-initiated migration.
- Each rollout includes an associated "quantization profile" meta-record: precision, expected throughput improvement, estimated cost multiplier, and known limitations.

2) Observability and telemetry gating

- Minimum telemetry produced for every q-variant invocation:
  - token_count (input + output)
  - latency_p99, latency_p95, latency_p50 (per route, per tenant)
  - kv_cache_hit_ratio (where applicable)
  - top_k_token_prob_shift (approx metric computed from shadow-eval; see QA below)
  - perplexity_delta (shadow vs baseline)
  - deterministic-safety-check-failures (count)

- Derived signals and thresholds (defaults):
  - quality_regression_alert if shadow-quality-drop > 3% on a route over a 30-minute window.
  - latency_regression_alert if latency_p95 increases by > 50ms and p95 baseline was < 300ms.
  - cost_delta_notice if effective per-token cost changes by > 10%.

- Telemetry collection details:
  - Streaming traces should tag invocations with variant_id, rollout_id, tenant_id, route_id, and inferred-fidelity-tier.
  - Shadow-eval: For external canaries and staged rollouts, a sample of requests (configurable, default 1%) are evaluated against baseline full-precision model to compute fidelity metrics off-path. These shadow-evals are sampled asynchronously and do not affect live latency.

- Automated gating:
  - Each active rollout has a gating policy (json). Gate checks run every 5 minutes and compute statistical significance (Welch t-test) between baseline and q-variant on the past 30 minutes. If any gate condition trips, the rollout is automatically paused and an incident-style notification is created with recommended rollback steps.

3) Billing hooks and semantics

- When a tenant receives traffic served by a q-variant, Redwood must:
  a) Calculate the rendered cost-per-token (C_token) used for billing and UI. Default: C_token(q-variant) = C_token(baseline) * cost_multiplier(profile).
  b) Emit a BillingEvent with the following attributes: tenant_id, rollout_id, variant_id, effective_cost_multiplier, timestamp, estimated_monthly_savings (based on last 7 days consumption).

- Billing integration points:
  - Real-time console: display effective per-route cost delta.
  - Ingestion pipeline: BillingEvents feed usage reconciliation and downstream billing batch (daily).
  - Alerts: If the billing delta is negative (unexpected cost increase) above threshold, create immediate PagerDuty alert.

- Customer-visible notices:
  - Console banner when a tenant is on a q-variant for more than 1 hour: "This route is using a quantized variant that reduces compute cost by ~X% and may change output fidelity. See migration details."
  - Billing exports include both baseline-equivalent tokens and effective tokens for reconciliation.

Config schema (example)

- rollout_policy.json (fields):
  - "rollout_id": string
  - "route_id": string
  - "variant_id": string
  - "target_percentage": integer (0-100)
  - "shadow_sample_rate": float (0-1)
  - "gating_policy_id": string
  - "billing_mode": ["pass-through", "adjusted"]  // pass-through uses baseline pricing; adjusted applies multiplier

YAML example:

  rollout_id: qroll-2027-04-21-42
  route_id: /v1/chat/completions
  variant_id: gptx-q8-2027-03
  target_percentage: 25
  shadow_sample_rate: 0.02
  gating_policy_id: gp-quant-std
  billing_mode: adjusted

Rollout steps (operational playbook)

1. Preparation (preflight)
  1.1. Create quantization profile and register variant_id.
  1.2. Run preflight simulation for the customer or tenant: replay last 24h sample calls or run synthetic prompt set to estimate latency/cost/fidelity deltas.
  1.3. Produce a preflight report: expected p95 latency change, estimated monthly savings, shadow-quality-score. Deliver to customer console.

2. Internal canary (multi-team)
  2.1. Deploy to internal canary pool (eng-prod).
  2.2. Observe telemetry for 48h.
  2.3. Approve or abort based on gating policy.

3. External canary (selected customers)
  3.1. Notify customers via console and email (template provided).
  3.2. Ramp target_percentage to 10% for 24-72h.
  3.3. Gate checks run every 5 minutes.

4. Gradual ramp
  4.1. Increase target_percentage in steps (10, 25, 50, 100) with minimum 2h at each step.
  4.2. If gating policy trips at any step, automatically pause and notify SRE/owner.

Observability & dashboards

- New dashboard tiles (Console + internal Grafana):
  - Per-route per-tenant fidelity heatmap (shadow-quality-score over time).
  - Cost delta timeline (estimated vs realized).
  - Rollout health timeline with gating decision markers.
  - Latency distribution overlay baseline vs q-variant.

- Alerts and PagerDuty:
  - quality_regression_alert => P2 (pager duty after 15m sustained).
  - latency_regression_alert => P3.
  - billing_delta_negative_alert => P1 (immediate).

SLOs and thresholds (suggested defaults)

- Shadow-quality-drop tolerance: <= 2% for internal canary, <= 3% for external canary, <= 5% for production ramp.
- Latency p95 increase tolerance: <= +20% or +50ms (whichever is smaller) during canary.
- Detection window: 30 minutes for automated gating; 7 days for billing reconciliation checks.

Testing, QA and metrics validation

- Unit tests: gating policy evaluation logic, billing event emission, edge-case missing telemetry.
- Integration: End-to-end test that simulates a 10k-req/hour tenant with shadow-evals enabled and asserts that: billing events are emitted, preflight report is produced, and that gate trips when intentional regression injected.
- Chaos testing: Inject synthetic noise in shadow-eval metrics to validate false-positive rate.

Customer communication and migration UX

- Preflight report displayed in Console with a single-click "Schedule migration" that triggers tenant-initiated ramp.
- Email + Console templates for external canary invitations.
- Billing FAQ text included in migration flow; template for Account Execs for larger customers.

Data retention and privacy considerations

- Shadow-eval artifacts that include customer prompt/response pairs must be subject to PII scrubbing and retained per Data Retention policies (default 30 days for preflight artifacts; longer only with explicit consent).

Ownership and rollout governance

- Feature owner: runtime-variant-team (primary).
- Observability/gating service owner: eng-platform (secondary).
- Billing pipeline integration: finance-legal (contract), billing-engine (implementation).
- Product comms: product-marketing (external).

Open questions and risks

- Calibration of shadow-quality-score: which metric best correlates to customer satisfaction across varied prompt sets? (Action: run multi-tenant correlation study Q2 2027).
- Should we offer an automated opt-out window that refunds a proportional credit if quality regressions are detected post-migration? (Commercial decision).
