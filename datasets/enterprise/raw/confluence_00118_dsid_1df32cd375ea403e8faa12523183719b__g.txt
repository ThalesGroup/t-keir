GPU runtime compatibility matrix and rollout playbook

Overview

This page documents the compatibility matrix for GPU runtimes we operate at Redwood and provides a step-by-step rollout playbook for introducing new runtime versions or kernel stacks to the fleet. It is intended for infra engineers, SREs, and platform release owners.

Goals
- Reduce model regressions introduced by runtime/kernel changes.
- Provide a repeatable, low-risk rollout path for runtime upgrades across regions and tenant classes.
- Capture compatibility constraints (CUDA/cuDNN/NCCL/kernel combos) so IaC and scheduler can make safe placement decisions.

Scope
- Applies to on-host GPU runtimes used by the serving runtime (service name: gpu-orchestrator) and the batch/eval fleet (service name: gpu-eval-worker).
- Covers Linux AMI bundles, CUDA/cuDNN/NCCL versions, GPU driver ABI compatibility, and kernel-level optimizations used by our inference kernels (kernel-hint v2).
- Does NOT cover hardware-level procurement or firmware upgrade procedures (see gpu-fleet-scaling-metrics-and-oncall-runbook).

Compatibility matrix (reference)

Note: This table is authoritative for the scheduler and Terraform placement modules. When adding a new runtime, update the Terraform module variable supported_runtimes and the placement constraints in module.gpu-node.

| Runtime name | Host driver (NVIDIA) | CUDA | cuDNN | NCCL | Models verified | Max seq len | Notes |
|--------------|---------------------:|-----:|------:|----:|----------------|-----------:|-------|
| runtime-2024-10 (stable) | 535.86 | 12.1 | 9.3 | 2.16 | Llama2-13B, Mistral-7B, Bloom | 4096 | Default for hosted-prod; supports tensor-core int8 kernels. |
| runtime-2025-01 (canary) | 545.23 | 13.0 | 9.5 | 2.18 | Llama2-13B (quantized), RedModel-Base | 8192 | New kernel-hint v3 enabled; improved KV-cache layout. Canary only. |
| runtime-arm64-2024-12 | 520.61 | 11.8 | 8.2 | 2.10 | Mistral-7B (arm build) | 2048 | For edge/arm pools; limited NCCL rings. |
| runtime-legacy-12x | 470.42 | 11.4 | 8.0 | 2.8 (legacy) | Legacy models for Dedicated customers | 1024 | Keep on a small pool for customers that pinned legacy stack. |

Compatibility guidance
- Scheduler should match model profile to runtime: e.g., models requiring kernel-hint v3 must be placed on runtime-2025-01 or higher.
- If driver bump > major (e.g., 535 -> 545), create a canary pool with isolated VPC/subnet and enrollment tag gpu:canary=true.
- Maintain at least one node pool with 'legacy' runtime for customer pinning; enforce capacity quotas to prevent accidental eviction.

Terraform / IaC changes required when adding a runtime
1) Module changes (recommended pattern):
   - Filename: modules/gpu-runtime/README.md and variables.tf
   - New variable: supported_runtimes = ["runtime-2024-10", "runtime-2025-01"]
   - Add data source to map AMI -> runtime tag: data.aws_ami.gpu_runtime_lookup
2) Example snippet to pin a pool to a runtime (HCL):

   module "gpu_pool_canary" {
     source = "git::ssh://git@repo.redwood.ai/infra-modules.git//modules/gpu-pool"
     name   = "gpu-pool-canary-us-west-2"
     node_count = 8
     runtime_tag = "runtime-2025-01"
     tenancy = "dedicated"
     labels = { "gpu:canary" = "true", "tier" = "canary" }
   }

3) Apply pattern: use -target for initial provisioning and avoid full plan apply when seeding canaries. Example CLI:
   terraform apply -target=module.gpu_pool_canary -var='region=us-west-2' -var='runtime=runtime-2025-01'

Rollout playbook (high-level)
Prerequisites
- CI/CD artifact: runtime AMI baked and signed, image tag uploaded to image registry (ami://redwood/gpu/runtime-2025-01).
- Benchmarks: perf run artifacts uploaded to S3 (s3://redwood-benchmarks/runtime-2025-01/).
- Owner assigned (release owner): infrastructure release lead (see Ownership).

Step 0 — Create canary pools (isolated)\1. Provision 2 canary pools: one for hosted-prod traffic (8 nodes), one for eval/batch (4 nodes).
2. Tag pools with gpu:canary=true and runtime_tag=runtime-2025-01.
3. Update scheduler placement rules to consider runtime_tag label for canary traffic only.

Step 1 — Validation smoke tests (automated, 4h window)\1. Run model seeding smoke: 1000 short inference requests across canary pools.
2. Verify functional correctness: token outputs must match golden references within tolerance thresholds for 95% of requests.
3. Run perf regression check: p50, p95, p99 token latency and token/s throughput compared to baseline.
   - Pass if p95 latency delta <= +10% and p50 delta <= +5% and token/s delta <= -10%.
4. Run memory and OOM soak: 72h soak with a mix of sequences up to declared max seq len; monitor gpu.memory.used.

Step 2 — Canary traffic ramp (gradual)\1. Open routing for <1% of production traffic to runtime canary. Hold 2 hours.
2. If no alerts and metric deltas within thresholds, increase to 5% for 4 hours.
3. Then 10% for 12 hours.
4. Evaluate logs for tail errors, e.g., NCCL errors, driver warnings.

Step 3 — Regional expansion\1. After successful canary in primary region (us-west-2), provision canary pools in eu-west-1 and ap-southeast-1.
2. Repeat Steps 1–2 in each region.

Step 4 — Fleet-wide roll\1. Convert canary pools into standard pools by scaling node counts and flipping labels, or provision new pools and repoint routing.
2. Rollout in waves by tenant class: non-SLA dev -> hosted standard -> dedicated reserved -> high-priority tenants.
3. Use cluster autoscaler safeguards: set max surge of +20% and drain strategy = safest.

Rollback / emergency procedure
- Trigger conditions: sustained p99 token latency > 2x baseline, spike in kernel OOMs > 0.5% of requests, or NCCL driver errors with severity >= WARN.
- Immediate actions:
  1) Remove runtime_tag from scheduler rotation to stop new placements onto runtime-2025-01 (CLI: curl -XPOST https://gpu-scheduler.internal/api/v1/placement/disable?tag=runtime-2025-01).
  2) Start a controlled drain of pods on runtime-2025-01 nodes: kubectl cordon/evict with drain-grace-period=120s and retry backoff.
  3) Repoint affected tenant routes to compatible runtime pools using fallback policy (fallback runtime: runtime-2024-10).
  4) Open incident in PagerDuty and page infra-oncall and runtime-release-owner.

Monitoring and SLOs (examples)
- Latency SLOs to watch during rollout: p95 token latency < 120ms (small models), p99 < 350ms for long-seq workloads.
- Availability SLO: < 0.1% error rate increase from baseline during rollout windows.
- PromQL examples:
  - p95 token latency (hosted): histogram_quantile(0.95, sum(rate(token_generation_latency_bucket[5m])) by (le))
  - GPU memory OOMs: sum(rate(gpu_memory_oom_total[5m])) by (region)
  - NCCL warnings: sum(rate(nccl_warning_total[5m])) by (driver_version)

Instrumenting the scheduler and placement module\- Add runtime_tag as a first-class constraint: placement must consider {runtime_tag, driver_version, arch}.
- Example placement JSON label used by scheduler:
  {"labels": {"runtime_tag": "runtime-2025-01", "gpu_driver": "545.23", "arch": "x86_64"}}
- Terraform variable to expose in module.gpu-pool: allowed_runtime_tags = ["runtime-2024-10", "runtime-2025-01"]

Testing checklist (pre-roll)
- Unit: module/gpu-runtime unit tests and AMI validation script pass.
- Integration: allocator + scheduler + ci-eval workflows green in staging.
- Perf: perf artifacts within thresholds and comparison report uploaded.
- Canary: automated rollback script validated in integration.

Post-roll validation (48–72h)
- Verify per-tenant cost delta (tokens/s) and GPU utilization trend.
- Run synthetic evaluation against golden prompt set and validate output-quality metrics (exact-match, BLEU-like metrics for structured outputs).
- Capture and file any regressions as regression tickets with tags: regression/runtime/<runtime-name>.

B. Minimum CI perf suite (high level)\- microbench: 1000 generations of short (<128 tokens) requests\- kv-cache test: open-loop 1M tokens across sequences\- memory-soak: allocate up to declared max seq len for 24h

C. Short glossary\- runtime_tag: logical label used to represent a specific runtime/driver/kernel stack.
- canary pool: an isolated node pool used for initial validation.
- kernel-hint: our inference runtime configuration that toggles optimized kernels.
