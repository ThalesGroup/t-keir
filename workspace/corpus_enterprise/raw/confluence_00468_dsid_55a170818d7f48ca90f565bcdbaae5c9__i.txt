Incident-bot Playbook Rehearsal CLI (Dry-Run Executor) — On-Call Runbook (2026)

h1. Overview
The *Playbook Rehearsal CLI* allows responders to validate incident-bot playbooks end-to-end in a controlled *dry-run* mode. Rehearsal executes the same step ordering, condition evaluation, and integration wiring as a live run, but prevents production mutations by enforcing strict side-effect policies.

Use rehearsal to:
* Confirm step ordering and guardrails before production changes.
* Validate that playbook queries/conditions work against realistic telemetry.
* Produce an auditable report of intended actions (including simulated API calls).

h1. What Rehearsal Does (and Does Not) Do
h2. Does
* Executes playbook steps using a *safe dry-run executor*.
* Replays sanitized telemetry (logs/metrics/traces) from a snapshot to validate queries used in conditions.
* Substitutes *mutating* requests with simulated responses and records the “intended” state transitions.
* Writes audit events for who rehearsed what and when (no secrets persisted).

h2. Does not
* Perform live production mutations.
* Persist secrets, raw customer payloads, or secret placeholders.
* Bypass network restrictions without explicit admin policy.

h1. Prerequisites
* You have incident-bot CLI access for your org.
* The org has the rehearsal feature enabled.
* You have (or can generate) a sanitized snapshot appropriate for the playbook.

h2. Feature Flag / Enablement
Rehearsal is gated per-org behind feature flag: *playbooks.rehearsal_cli*.

Notes:
* Org admins enable the flag in the org control-plane.
* Admins may optionally provide a policy file that allows specific non-mutating endpoints (see “Network Policy”).

h1. Quick Start
h2. Rehearse with a stored snapshot
Command:
*incident-bot rehearse <playbook-id> --context snapshot:<snapshot-id>*

Example:
incident-bot rehearse pbk_service_failover --context snapshot:svc-checkout-2026-03-12

h2. Rehearse with a short live sanitized capture (low risk)
Command:
*incident-bot rehearse <playbook-id> --live-snapshot --duration 120s*

Example:
incident-bot rehearse pbk_latency_mitigation --live-snapshot --duration 90s

h2. Output formats
* --output human (default)
* --output json
* --output compact-summary

Examples:
incident-bot rehearse pbk_service_failover --context snapshot:svc-checkout-2026-03-12 --output json > rehearsal-report.json
incident-bot rehearse pbk_service_failover --context snapshot:svc-checkout-2026-03-12 --output compact-summary

h1. Safety Model
h2. Side-effect prevention
The executor blocks production mutations by default.

Rules:
* HTTP methods POST/PUT/PATCH/DELETE are treated as mutating unless an integration explicitly marks the call as safe-to-simulate.
* Mutating calls are replaced with deterministic simulated responses.
* Read-only calls are permitted only if they match the active network policy (default is deny-by-default for external calls).

h2. Network policy (updated)
Rehearsal no longer uses an ad-hoc CLI allowlist. Instead it accepts an admin-managed policy file:
* --network-policy <path>

Policy file (YAML) supports:
* allowed_hosts
* allowed_paths (optional)
* allowed_methods (default GET/HEAD)
* deny_patterns (regex)

Example:
incident-bot rehearse pbk_service_failover --context snapshot:svc-checkout-2026-03-12 --network-policy ./rehearsal-network-policy.yaml

h2. Secrets handling
* Snapshots must be sanitized.
* The CLI fails fast if a snapshot contains secret placeholders (for example, tokens that match internal secret marker formats) or if a playbook references a secret directly.
* If you see a failure referencing “snapshot hygiene”, do not bypass it—regenerate the snapshot via the sanitizer.

h1. Snapshots and Telemetry Replay
h2. Snapshot sources
Rehearsal accepts:
* Stored snapshot IDs (recommended)
* Live-sanitized capture for short windows (use only when needed)

h2. Where snapshots live (updated)
Sanitized snapshots are stored in the org snapshot bucket and referenced by ID (the CLI does not require direct bucket access).

Operational notes:
* Snapshots are retained per org policy.
* Snapshot IDs are logged in audit events; snapshot contents are not.

h2. Telemetry replay behavior
The replay harness injects events into an isolated in-memory store for query evaluation. It uses accelerated timestamps (not real-time) to keep rehearsals fast.

h1. Expected Output / How to Interpret It
A rehearsal report includes:
* Playbook ID and revision
* Snapshot context
* Step-by-step results (pass/blocked/simulated)
* For each integration call:
  * whether it was executed (read-only), simulated (mutating), or blocked (policy)
  * request summary (sanitized)
  * simulated response summary (if applicable)
* Intended state transitions and guardrail triggers

Tip:
* A “blocked” step is usually a policy configuration issue or a playbook step that attempts a mutation without a simulation template.

h1. Common Failure Modes and Fixes
h2. Error: Feature flag disabled
Symptoms:
* CLI returns “rehearsal not enabled for org”.

Fix:
1) Ask the org admin to enable *playbooks.rehearsal_cli*.
2) Retry the command.

h2. Error: Snapshot hygiene check failed
Symptoms:
* CLI reports secret placeholder detected or “sanitizer assertion failed”.

Fix:
1) Regenerate the snapshot using the approved sanitizer.
2) Confirm the playbook does not reference secrets directly.
3) Re-run rehearsal.

h2. Error: Network call blocked by policy
Symptoms:
* Step fails with “blocked by network policy”.

Fix:
1) Confirm the playbook should be making the call in rehearsal.
2) If safe/required, ask an admin to update the *network policy file* (do not use one-off allowlists).
3) Re-run rehearsal with --network-policy.

h2. Error: Simulation template missing
Symptoms:
* Mutating call has no simulator response template and step fails.

Fix:
1) Add or update the integration simulation template for the endpoint.
2) Re-run rehearsal.

h1. Operational Guidance
h2. When to use rehearsal during an incident
* Before applying a new/updated playbook in production.
* When validating a high-risk step ordering change.
* When conditions depend on complex queries that are easy to misconfigure.

h2. Performance expectations (updated)
* Small snapshots: typically seconds.
* Large snapshots: may take 1–3 minutes depending on event count and query complexity.
* If a rehearsal exceeds 5 minutes, switch to compact-summary output and validate that the snapshot isn’t oversized for the scenario.

h1. Audit and Compliance
Rehearsals emit audit events including:
* actor (user)
* playbook ID and revision
* rehearsal context (snapshot ID or live capture metadata)
* policy mode (default/explicit network policy)
* high-level outcome summary

No secrets or raw snapshot payloads are stored in audit logs.

h1. Escalation / Ownership
* Primary owner: Incident Automation (incident-bot) — Eng SRE
* Security review questions: Security & Compliance (AppSec)

If rehearsal blocks incident response and you need urgent help:
1) Capture the rehearsal report (json output preferred).
2) Page the on-call for Incident Automation.
3) Include the playbook ID, snapshot ID, and the blocked endpoint summary.
