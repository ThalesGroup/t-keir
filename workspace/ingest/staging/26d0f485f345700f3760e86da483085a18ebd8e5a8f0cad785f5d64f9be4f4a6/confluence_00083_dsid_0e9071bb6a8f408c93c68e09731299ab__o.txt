Observability SLI/Tracing Guidelines and Cost Guardrails (ADR) - 2024

Overview

Purpose: Define a standardized, production-ready set of SLIs, tracing conventions, logging schema, and cost-aware sampling guardrails for Redwood inference services. This doc records the decision to adopt OpenTelemetry as the primary telemetry surface, the canonical SLI definitions for inference endpoints, and the rollout plan for migrating existing services.

Scope
- Services in scope: all API-facing inference routes (hosted API), Redwood Dedicated control-plane services, and the Private control-plane agent.
- Out of scope: offline batch model training jobs, developer local runtimes.

Goals
1) Provide unambiguous SLIs that map to SLOs used by SRE and product.
2) Ensure traces capture request lifecycle end-to-end across frontend, router, runtime, and GPU workers.
3) Keep telemetry cost predictable via sampling & adaptive policies.
4) Offer concrete dashboards and alert thresholds for oncall use.

Decision summary (ADR)
- Chosen telemetry stack: OpenTelemetry for instrumentation, Prometheus for long-lived metrics, Tempo/Jaeger-compatible backend for traces, Grafana for dashboards, and Loki for logs.
- Sampling model: Dynamic trace sampling with 100% sampling for error traces, 5% baseline for successful requests, and a capacity-aware progressive ramp (up to 25%) when experimentation mode is enabled.
- Metric naming convention: metric names must be prefixed with redwood_<service>_ and follow snake_case; labels must include service_version and model_id when applicable.

Rationale
- OpenTelemetry provides vendor neutrality and standardized context propagation (W3C traceparent).
- Prometheus is used for aggregated numeric SLI computation at scrape-time and integrates with existing alerting.
- Cost guardrails are necessary: inference generates large request volumes; uncontrolled tracing would increase egress and storage costs on hosted offerings. The dynamic sampling policy balances observability needs with cost.

SLI definitions (canonical)
- Request latency (P95, P99): histogram on end-to-end request duration measured at the API ingress. Label by route, model_id, deployment_tier. Unit: milliseconds.
- Request success rate: percentage of requests with http_status in the 2xx class and no downstream runtime errors (runtime_error=false).
- Token generation rate: tokens_per_second per model_id and per-instance. Useful for capacity planning.
- Cold-start rate: fraction of requests that experienced model load > 200ms.
- KV-cache hit rate: fraction of requests served from KV cache layer.
- Model-quality-regressions: periodic evaluation job-derived metric (regression_count_over_1000_prompts). See applied-ml-and-evals for eval harness.

Suggested SLO examples (for product teams to adopt)
| SLO name | SLI | Target | Window | Owner |
|---|---:|---:|---:|---|
| API latency (interactive) | P95 latency (text.generate) | <= 350 ms | 30d | api-platform-team |
| API availability | request success rate | >= 99.95% | 30d | api-platform-team |
| Dedicated throughput | 95th percentile throughput per-GPU | >= configured commit | 30d | infra-capacity-team |

Metric names and labels (required fields)
- Metric name pattern: redwood_<service>_<metric>
- Required labels: environment (prod/staging/dev), region, service_version, model_id (if applicable), route (e.g. /v1/generate-chat).
- Example Prometheus exposition (instrumentation guideline):
```
# HELP redwood_api_request_duration_ms End-to-end request latency in ms
# TYPE redwood_api_request_duration_ms histogram
redwood_api_request_duration_ms_bucket{le="50",environment="prod",region="us-west-2",service_version="v2.1",model_id="gpt-open-8k",route="/v1/generate-chat"} 12345
redwood_api_request_duration_ms_sum{environment="prod",region="us-west-2",service_version="v2.1",model_id="gpt-open-8k",route="/v1/generate-chat"} 9876543
redwood_api_request_duration_ms_count{environment="prod",region="us-west-2",service_version="v2.1",model_id="gpt-open-8k",route="/v1/generate-chat"} 45678
```

Tracing conventions
- Instrumentation libraries: Use OpenTelemetry auto-instrumentation for core languages (Go, Python, Node). Custom spans must be created for: request_ingress, router_dispatch, runtime_infer, kv_cache_lookup, gpu_batch_execute.
- Context propagation: Use W3C traceparent header. All internal service-to-service calls must forward traceparent.
- Span naming: <service>.<action> (e.g. router.dispatch, runtime.infer).
- Span attributes (required): trace.service, trace.route, model_id, request_id, runtime_gpu_id (when applicable), batch_size, token_count, sampling.priority.
- Error handling: Spans with errors must set status=ERROR and include exception.type and exception.message attributes.

Sampling policy (cost guardrails)
1) Baseline: 5% of successful requests sampled uniformly per service/region.
2) Error amplification: 100% of error traces sampled (http_status >= 500, runtime_error=true, model_timeout=true).
3) Adaptive ramp: For A/B experiments or detailed investigation, teams may opt-in to a higher sampling window for a given service or route. Opt-in is gated behind a quota and must include a cost owner approval.
4) Retention: Full traces retained for 14 days by default; aggregated trace-derived metrics retained in Prometheus for 90 days. Longer retention for traces requires explicit business justification.

Dashboards & Alerts (operational runbooks)
- Default dashboards (to be created in Grafana):
  - API Overview: P50/P95/P99 latency, request rate, error rate, token rate by model.
  - Runtime Health: queue depth, GPU utilization, KV cache hit rate, batch sizes.
  - Cost telemetry: sampled trace volume, metrics ingestion rate, estimated telemetry cost per region.

- Alert rules (examples):
  - High API latency (P95 > 500ms for 5m) -> SEV2 -> paging to api-platform oncall.
  - Error budget burn (error_rate > SLO threshold for 60m) -> SEV1 if sustained 4h.
  - Unusual telemetry spike (ingestion rate > 3x baseline) -> SEV2 -> paging to eng-telemetry.

Rolling out the standard (migration plan)
1) Inventory: run telemetry-discovery job to list services without OpenTelemetry keys. (owner: eng-telemetry).
2) Bootstrapping: instrument a pilot set of 3 services (api-router, runtime-proxy, dedicated-control-plane) using OTEL collector config. (timeline: 2 weeks).
3) Validate: confirm SLIs are reported, dashboards populate, and sampling reduces ingestion to target. (owner: eng-sre).
4) Gradual rollout: migrate remaining services in waves (by team), each wave limited to 6 services/week.
5) Post-migration audit: run a cost & quality audit 30 days after migration.

Ownership and runbooks
- Eng-telemetry owns collector configs, sampling policies, and cost guardrail enforcement.
- Eng-sre owns SLO monitoring, alerting rules, and oncall runbooks.
- Runtime-team owns span instrumentation inside the serving runtime and provides helper libs.

Runbook: High latency in production
1) Triage: check API Overview dashboard and latency histograms.
2) Drill down: identify the span with highest self-time (router.dispatch vs runtime.infer).
3) If runtime_infer is dominant: check GPU queue depth and batch_size heatmap. Scale or adjust batching policy as needed.
4) If router.dispatch is dominant: check recent deploys and routing table changes; rollback if necessary.
5) If KV-cache hit rate dropped: invalidate or warm cache; check cache service health.
6) Document incident in postmortem and tag related traces with postmortem id.

Appendix: Example OTEL collector snippet (yaml)
```
receivers:
  otlp:
    protocols:
      http: {}
      grpc: {}
processors:
  batch: {}
  probabilistic_sampler:
    sampling_percentage: 5
exporters:
  prometheus:
    endpoint: "0.0.0.0:9464"
  tempo:
    endpoint: "tempo-us-west-2.redwood.svc:14268"
service:
  pipelines:
    traces:
      receivers: [otlp]
      processors: [probabilistic_sampler, batch]
      exporters: [tempo]
    metrics:
      receivers: [otlp]
      processors: [batch]
      exporters: [prometheus]
```
