observability-driven-onboarding-runbook

Overview

Purpose:
This runbook defines an observability-first approach to enterprise onboarding for Redwood Inference customers. It standardizes the telemetry contract, synthetic acceptance checks, escalation paths, and QBR handoff artifacts used during a customer go-live and the first 90 days of production.

Scope:
- Applies to Dedicated and Private deployments and to Hosted customers with enterprise SLAs.
- Covers telemetry-onboarding, pre-cutover validation, day-0 to day-14 stabilization, and QBR handoff.

Acceptance gates (must pass before route to production)
1) Telemetry contract validation (required)
   - Metrics: request_count, request_latency_ms_p50/p95/p99, token_consumption_total, kvcache_hit_ratio, active_connections_by_tenant
   - Traces: 95% of generation requests produce a trace with span for model-select and runtime-exec
   - Logs: structured request_id on all runtime logs with severity mapping (INFO/WARN/ERROR)

2) Synthetic scenario pass (3 independent runs)
   - Latency synthetic: 95th percentile end-to-end generation under 2.5s for the workload profile
   - Accuracy synthetic: pre-agreed prompt set map-of-outputs >= customer baseline (see "synthetic-prompt-set" artifact)
   - Failover synthetic: simulate a model-variant fallback and verify successful completion within 3s of fallback trigger

3) Cost and quota sanity check
   - Token burn projection for first 30 days within agreed threshold +/- 30%
   - Adaptive-rate-limiter integrated and returning 429s with observability tags when saturating

Telemetry contract: implementation checklist
- Instrumentation owners must ensure metrics emit at the tenant/request granularity. Required labels: tenant_id, region, model_name, route
- Preferred exporters: Prometheus (metrics), OpenTelemetry (traces), JSONL to S3 for long-term logs.
- Retention: 90d metrics, 30d traces, 365d logs (customer may opt for shorter).

Prometheus example queries (copy into onboarding dashboard)
- Total requests by tenant (30m): rate(request_count{tenant_id=~"TENANT_ID.*"}[30m])
- 95th percentile latency (10m): histogram_quantile(0.95, sum(rate(request_latency_bucket[10m])) by (le))
- KV cache hit ratio: sum(rate(kvcache_hit_total[5m])) by (tenant_id) / sum(rate(kvcache_lookup_total[5m])) by (tenant_id)

Synthetic health checks and dashboard layout
- Dashboard sections: Overview, Latency & Throughput, Token Economics, Failure Modes, Instance Health, Rollout & Canary Status
- Widgets to include: p50/p95/p99 latency heatmap, request rate by tenant, token burn by route, cache hit ratio trend, recent errors table (parsed with error codes), live traces sample panel

Pre-cutover procedure (Day -3 to 0)
1) Day -3: Telemetry smoke test
   - Verify data arriving in Grafana and alerting pipeline.
   - Run the baseline synthetic suite; document results in the onboarding ticket.
2) Day -2: Load profile run
   - Ramp to expected steady-state TPS for 30 minutes, then peak to 2x for 15 minutes.
   - Confirm autoscaling/queueing behaves as expected, confirm no token anomalies.
3) Day -1: Canary rollout
   - 1% of traffic routed to the new tenant config. Monitor the canary for 60 minutes.
   - Check for errors, latency, and cost deltas. If any SLO breach detected, abort and roll back.
4) Day 0: Full cutover
   - Schedule 60 minute maintenance window. Notify stakeholders (email template provided below).
   - Enable full route, run post-cutover synthetic suite after 15 minutes, and validate telemetry contract.

Stability operations (Day 0–14)
- Daily cadence: 09:30 PST standup (CS + SRE + Runtime) for first 7 days, then every-other-day till day 14.
- Check list for standup:
  - Any SLO alerts fired in last 24h? (yes/no, link to alerts)
  - Token burn variance > 20%?
  - Customer reported LLM output quality regressions?
  - Any escalations initiated?

Escalation matrix and SLAs
- P1: Production-wide outage for customer's tenant (affects > 90% requests)
   - First response: SRE on-call (15m), followed by CS lead (30m)
   - Escalation: Paging to Engineering runtime leads at 60m, exec-brief within 2h
- P2: Severe degradation (p95 > target or error rate > 5%) for a single route
   - First response: CS + SRE (30m), resolution target 4h
- P3: Functional bug with workaround (non-blocking)
   - Response: Assigned support engineer within 8 business hours

Communication and customer comms templates
- Pre-cutover notification (email):
  Subject: [Redwood] Scheduled go-live window for <tenant_name> on <date>
  Body: Short summary, expected window, primary contacts, rollback criteria, monitoring link (dashboard URL).

- Incident update template (customer-facing):
  1) What happened (concise)
  2) Impacted customers/tenants
  3) Mitigation steps taken
  4) ETA for resolution or next update

Rollback and safe-fail procedures
- Automatic rollback trigger conditions (examples):
  - p95 latency increase > 2x baseline for > 10 minutes
  - error rate > 5% sustained for > 5 minutes
  - token burn projection exceeds agreed cap by > 50% within next 24 hours
- Rollback steps:
  1) Use routing control to switch traffic back to previous deployment (CLI example):
     redwood route set --tenant <TENANT_ID> --route <ROUTE> --target previous
  2) Re-enable canary at 5% and rerun synthetic
  3) Open a post-rollback ticket and schedule a root-cause analysis (RCA) meeting

Postmortem and RCA handoff criteria
- Trigger an RCA when any of the following occur:
  - P1 incident
  - P2 incident that required > 4 hours to resolve
  - Any customer quiet-go-live rollback within first 14 days
- RCA ownership: SRE + Runtime + CS representative. Deliverable: written RCA (timeline, root cause, corrective actions) within 5 business days.

QBR handoff and artifacts (first QBR after go-live)
- Dashboard snapshot exported with:
  - Latency/Throughput trends since go-live
  - Token economics and cost delta vs projection
  - Error and degradation timeline with RCA links
  - Synthetic suite pass/fail history and prompt-set differences
- Customer Success playbook for the QBR:
  1) Review contract SLOs and whether we met them
  2) Share operational highlights and any outstanding risks
  3) Agree on quality/regression plan (if any)

Troubleshooting checklist (quick steps during an incident)
1) Identify affected tenants and routes: run request_count PromQL filter by tenant_id.
2) Check instance health and oom/killed events on nodes serving tenant.
3) Inspect traces to find whether slowdown occurred in model selection or runtime execution.
4) If KV cache hit ratio dropped significantly, flush affected prefix cache and monitor.
5) If error codes 5xx dominate, scale burst pool or reroute to fallback variant.

FAQ
- Q: What if synthetic checks pass but customers report poor output quality?
  A: Open a quality triage ticket and escalate to Applied ML; attach failing prompts and model version. Consider A/B rolling back to prior model variant.
