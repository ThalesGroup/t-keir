Field-level Telemetry Classification and Privacy Enrichment Standard

Overview

This page defines the standard for field-level telemetry classification, runtime enrichment, and privacy-aware routing within Redwood Inference's observability pipelines. The goal is to provide a consistent, auditable approach for marking, transforming, and retaining telemetry fields so that engineering teams can meet SLOs and debugging needs without exposing regulated or sensitive information.

Goals

- Ensure every telemetry field ingested by observability pipelines is classified by sensitivity and utility.
- Standardize runtime enrichment (labels/contexts) that do not introduce new sensitive data.
- Provide deterministic, auditable transformations for fields classified as sensitive (PII/PHI/Secrets).
- Define sampling, retention, and retention-override rules driven by field classification and product context.

Scope

Applies to: all services producing logs, metrics, traces, and prompt/event telemetry that flow through Redwood’s ingestion platform (edge proxies, collectors, sidecars, and backends).
Excludes: high-cardinality customer application payloads that are explicitly routed to customer-managed Private deployments (see related private-deployments docs).

Field Classification Matrix

| Classification | Definition | Example fields | Default retention | Transformation required |
|---|---:|---|---:|---|
| public | Safe to include in debug output and dashboards | service_name, region, model_version | 90 days | none |
| low_risk | Operationally useful but may contain soft identifiers | request_size, latency_histogram, client_sdk | 90 days | redaction of rare identifiers by pattern |
| sensitive | Direct identifiers with re-identification risk | user_email, api_key, account_id | 30 days | deterministic hashing with salt (per-tenant) + tokenization |
| regulated | Legal/regulated PII/PHI or content under NDA | prompt_text, attachment_base64, health_data | 7 days (default) | drop-by-default OR explicit allowlist; if allowed then strong encryption and KMS-wrapped keys |
| secret | Credentials, private keys, tokens | hmac_secret, oauth_token | immediate purge (no retention) | drop from telemetry; generate stub event indicating removal |

Classification Rules and Examples

1. If a field contains free-text user content (prompts), classify as regulated unless an explicit policy allowlist exists.
2. Numeric identifiers (e.g., account_id) should be treated as sensitive by default; teams may request low_risk via a formal exception when downstream utility is proven.
3. IP addresses are treated as low_risk; if IPv6/geo inference is used, enforce coarse-graining before retention.

Field Tagging Schema (performed at producer side, enforced by collector)

Every telemetry record MUST include a header metadata map `__telemetry_meta` with the following fields:
- `producer_service` (string)
- `schema_version` (string)
- `fields` (list of field descriptors) — descriptor format illustrated below

Example descriptor (as plain text JSON in the header):
{
  "name": "user_email",
  "classification": "sensitive",
  "transform": "hash:sha256:salt-v1",
  "owner": "auth-service",
  "reason": "used for user-scoped debugging"
}

Enrichment and Runtime Transformations

- Deterministic Hashing: Use HMAC-SHA256 with a per-tenant salt stored in KMS. This allows group-by and correlating events without storing raw identifiers.
- Tokenization: Replace sensitive field with a stable token (format: TK-{service}-{shorthash}). Tokens are reversible only by a KMS-authorized tooling path.
- Coarse-graining: For location or numerical ranges, map to buckets (e.g., 0-100ms, 100-500ms) before emitting.
- Drop/Stub: For secrets, remove original value and emit a `field_removed` boolean with a reason code from the canonical list (secret, regulated_prohibition, retention_limit).

Operational Examples

Producer (pseudocode for sidecar transform):

# annotate fields
__telemetry_meta = {"producer_service":"payment-gateway","schema_version":"1.2","fields":[{"name":"account_id","classification":"sensitive","transform":"hash:sha256:salt-v1","owner":"payments"}]}

# original event (simplified)
event = {"account_id":"12345","latency_ms":245,"model_version":"redwood-v1"}

# after transform sent to collector
transformed = {"account_id":"HMAC:a1b2c3...","latency_ms":245,"__telemetry_meta":__telemetry_meta}

Collector-side checks

Collectors MUST reject records that:
- Contain fields marked `secret` in clear text.
- Omit `__telemetry_meta` unless the producer is on an allowlist (very rare).
- Use deprecated `schema_version` (reject and emit a schema_mismatch metric).

Sampling and Retention Policy (default)

- public/low_risk: 100% ingestion, retention 90d
- sensitive: 100% ingest, index minimal (no raw), retention 30d
- regulated: 10% default sampling for long tail, retention 7d unless allowlisted for full retention by security/legal
- secret: never retained; emit only removal_event for audit

Teams may request temporary retention extensions (for debugging incidents) via the Incident Retention Approval flow. All approvals must include the fields, justification, and an auto-expire timestamp.

SLOs and Telemetry Health Metrics

- Telemetry Schema Compliance: 99.9% of records in production must include valid `__telemetry_meta` (measured per producer).
- Transformation Latency: Producer-side transforms must add <= 20ms p50 and <= 150ms p99 to the request path for synchronous flows. For high-throughput collectors, asynchronous transformation is preferred.
- Sampling Accuracy: Deviation from configured sampling rates must be <1% (monitored by telemetry generator and ingestion counts).

Audit and Compliance

- Audit logs for transformation/reversal must be written to a restricted audit index with KMS protection. Reversal of tokens is logged and requires two-person approval (operator + security).
- Periodic audit: every 90 days security will sample pipelines and validate no raw regulated fields exist beyond their retention window.

Operational Runbook (Quick Steps)

1. On schema_mismatch alerts: route to producer team, spin a dry-run collector that accepts deprecated schema and emits diffs.
2. If a retention-breach suspected: pause ingestion for the producer, snapshot current index to a read-only bucket, contact Security.
3. For incident-driven retention extension: raise Incident Retention Approval (jira template), include time-bound justification. Include reviewer: Security Eng.

Implementation Checklist for Service Owners

- [ ] Add `__telemetry_meta` to emitted records and mark classification for all non-trivial fields.
- [ ] Implement producer-side deterministic transforms for sensitive fields.
- [ ] Add unit tests for transform logic and schema version bump tests.
- [ ] Register service with Telemetry Onboarding tool and pass schema linting.

Appendix: Canonical Transformation Codes

- hash:sha256:salt-v1 — deterministic HMAC-SHA256 with salt-v1
- token:tkn-v2 — stable tokenization using token service v2
- cg:latency-50-100 — coarse-grain bucket mapping
- drop:secret — field removed; emit removal_event
