Tenant Safety Scorecard and Auto-Mitigation Patterns

Overview
========
This document defines the Tenant Safety Scorecard (TSS) — a compact, production-focused scoring model and a library of automated mitigation patterns used to preserve platform SLOs while minimizing downstream customer impact. It describes: the metrics and weights for the scorecard, the ingestion and enrichment pipeline, operator thresholds, automated mitigation policies, observability and dashboards, runbook flows, and a safe rollout plan for enabling auto-mitigation in production.

Why we need a Tenant Safety Scorecard
------------------------------------
- Multi-tenant inference workloads can cause noisy neighbors: token spikes, KV cache pressure, GPU interference, or repeated misbehaving prompts.
- We must balance: preserving cluster SLOs (latency, availability) vs. customer-facing degradation and billing fairness.
- The TSS provides a single numeric signal per tenant that drives human alerts, automated actions, and retrospective analysis.

Goals
-----
1. Provide a deterministic, auditable score for tenant-induced platform risk.
2. Trigger graduated mitigations (informational -> soft limits -> hard limits) with human-in-the-loop gates.
3. Ensure mitigations are cost-aware and reversible with clear rollback primitives.
4. Provide dashboards and playbooks so oncall and SREs can quickly evaluate cause, customer impact, and remediation.

Scope and Non-Goals
-------------------
- Scope: realtime and 10m/1h aggregated signals affecting hosted and dedicated clusters. Applies to inference request routing, prefetched caches, and tenant-level autoscaling.
- Non-goal: tenant credit/billing dispute resolution (handled by billing workflows).

Definitions
-----------
- Tenant: account or API key group that owns requests and billing.
- TSS: Tenant Safety Scorecard, normalized 0.0 - 100.0 (higher = higher risk).
- Soft mitigation: non-blocking action (rate-limited responses, lower-priority queue).
- Hard mitigation: blocking action (temporary rate limit, model downgrade, or eviction).

Scorecard Components and Rationale
---------------------------------
We combine telemetry into compact sub-scores, each mapped to 0-100. The final TSS is a weighted sum, clipped to 100. Sub-scores:

1) Token Burst Score (weight 30)
- Measures percentile of short-window token rate vs. tenant baseline. Detects token storms.
- Signal sources: request_token_count, request_rate_1m, historical_7d_baseline.

2) GPU Interference Score (weight 20)
- Derived from GPU metrics: shared_p99_latency_increase, gpu_util_spikes, memory_swap_events. Correlates with tenant placement on noisy nodes.

3) KV Cache Pressure Score (weight 15)
- Tracks cache miss rate, prefix eviction rate, and hot-key skew. High score indicates evictions harming other tenants.

4) Quality-Stability Score (weight 15)
- Model-level errors: repeated malformed requests, function-calling misuses, and saturation of streaming channel errors.

5) SLO Burn Score (weight 20)
- Direct SLO impact: latency_p50/p95 increases attributable to tenant-weighted requests and error budget burn.

Scoring Table (example weights)
-------------------------------
| Component                | Weight | Nominal threshold | High-risk threshold | Notes |
|-------------------------|--------|-------------------|---------------------|-------|
| Token Burst             | 30     | +200% vs baseline | +800% vs baseline   | spikes in 1m window |
| GPU Interference        | 20     | p95+15ms increase | p95+50ms increase   | correlates with GPU metrics |
| KV Cache Pressure       | 15     | eviction_rate>5%  | eviction_rate>20%   | measured per-prefix |
| Quality-Stability       | 15     | repeated 5xx/400  | persistent 5xx/400  | per 1m and 1h windows |
| SLO Burn                | 20     | 5% SLO burn/1h    | 25% SLO burn/1h     | derived attribution engine |

How scores are computed (algorithmic outline)
---------------------------------------------
1. For each tenant, compute normalized sub-score S_i between 0 and 100 using piecewise-linear mapping with hysteresis.
2. Apply exponential smoothing alpha=0.2 to reduce jitter.
3. Final TSS = min(100, sum(weight_i * S_i / 100 * 100)). In practice: sum(weights * S_i) / sum(weights).
4. Persist 1m, 10m, 1h aggregates for retros and debugging.

Data pipeline and ownership
--------------------------
- Sources: ingress logs (request metadata), runtime telemetry (GPU metrics, cache metrics), router attribution, and anomaly-detector outputs.
- Pipeline: Kafka -> real-time scoring service (scoring-api) -> time-series store (VictoriaMetrics) and event sink (audit-events).
- Ownership: scoring-api owned by eng-platform/scoring team. Ingest schema managed in eng-platform/telemetry schema repo.

Operator thresholds and actions
------------------------------
The TSS triggers three classes of actions depending on score ranges and duration: informational (TSS 20-39), protective (TSS 40-69), and restrictive (TSS 70+). All actions are rate-limited and logged.

Informational (20-39)
- Alert: create a P1-Low pager (channel: #platform-tenant-safety) to inform tenant success and platform SRE.
- Action: add tenant to watchlist; increase sampling for detailed traces.

Protective (40-69)
- Automated action: apply adaptive backpressure for best-effort requests from tenant. Route tenant to lower-priority queue for non-critical routes.
- Operator action: open an incident review if TSS >50 for 15 consecutive minutes.

Restrictive (70+)
- Automated action (multi-step):
  1) Attempt soft mitigation: prefix-based throttling (reduce tokens/s by 30%), KV prefetch gating, and request batching enforcement. Wait 2 minutes to observe impact.
  2) If TSS persists >80 after 2 minutes, escalate to hard mitigation: temporary tenant rate limit (configurable, default 10% of baseline) and model downgrade to capped model variant.
  3) If TSS still >90 after additional 5 minutes, trigger eviction policy for the tenant from overloaded nodes and re-place to isolated capacity or dedicated pool if available.
- Human-in-loop: critical hard limits generate a page to the oncall SRE with a one-click rollback link in the incident UI.

Automated mitigation policy examples (YAML)
------------------------------------------
Example: soft-mitigation policy for token spikes\
```
policy_name: soft_token_backpressure_v1
match:
  tenant_id_regex: ".*"
  tss_range: [40, 80]
actions:
  - type: reduce_token_rate
    percent: 30
    duration: 120s
  - type: enable_high_sample_traces
    sample_rate: 0.05
audit: true
```

Example: hard-mitigation policy for repeated GPU interference\
```
policy_name: gpu_downgrade_and_eviction_v1
match:
  tss_range: [80, 100]
actions:
  - type: model_downgrade
    to_variant: quantized-small
  - type: tenant_rate_limit
    requests_per_minute: 100
  - type: node_eviction
    prefer_isolated_pool: true
escalate_to_oncall: true
audit: true
```
Observability and dashboards (owner: eng-platform/observability)
----------------------------------------------------------------
Required dashboard panels (reference names shown):
- TSS Overview (cluster heatmap): shows top 50 tenants by current TSS, sortable by sub-score composition.
- Tenant Detail: time-series for each sub-score + event timeline of policy actions.
- Mitigation Efficacy: percent reduction in SLO burn and token rate per mitigation policy.
- Incident Correlation: joins TSS events with GPU interference and placement changes.

Sample PromQL queries
---------------------
- Current tenant TSS (gauge): tenant_tss_current{tenant_id=~"$tenant"}
- Token burst component: tenant_token_burst_score{tenant_id=~"$tenant"}
- SLO burn attribution (1h window): increase_in_p95_attributable_to_tenant_1h{tenant_id=~"$tenant"}

Runbook: oncall first-responder flow (summary)
-------------------------------------------
1. Pager fires for TSS escalation (TSS >=70). Open the Tenant Detail dashboard and verify: 1m, 10m trends and recent policy actions.
2. Check the audit-events stream for policy decisions applied (scoring-api -> audit-events). Command:
   - kafka-console-consumer --topic audit-events --property print.key=true --from-beginning --max-messages=200 | jq 'select(.tenant_id=="$tenant")'
3. If mitigation is active and tenant impact is acceptable, coordinate with Customer Success to message the tenant and close the alert.
4. If mitigation is too aggressive or incorrectly applied: use the incident UI rollback button or run:
   - curl -XPOST "https://scoring-api.internal/v1/policies/rollback" -d '{"tenant_id":"$tenant","policy":"<policy_name>"}' -H "Authorization: Bearer $OPERATOR_TOKEN"
5. Open a post-incident ticket and tag with label tenant-safety and include the saved 1m/10m/1h aggregates.

SLA / Safety SLO mapping
------------------------
- Platform SLOs affected by tenant behavior: p95 latency < 250ms (critical routes), availability 99.95% monthly.
- Safety SLO obligations: TSS mitigations must not reduce a tenant's availability below 95% unless explicitly escalated to hard mitigation.

Testing and Rollout Plan
-----------------------
1. Simulation: run the TSS scoring service in a test cluster and replay synthetic tenant-traffic profiles using the tenant-sim harness. Evaluate false positive rate target < 1%.
2. Shadow mode: enable scoring and policy evaluation (no enforcement) for 4 weeks in prod; collect fidelity metrics and operator feedback.
3. Canary enforcement: select 5 low-risk tenants (opt-in) and enable full mitigation for 72 hours with manual observer oncall.
4. Phased increase: 10% -> 50% -> 100% of tenants, monitor Mitigation Efficacy and FP rate thresholds.

Postmortems and Retrospective Triggers
-------------------------------------
Create an automatic retrospective when any of the following occur:
- A mitigation rollback is performed more than twice in a single week.
- False positive rate >3% after enforcement.
- Any customer escalations >1 per month related to auto-mitigation.

Operational Metrics to Monitor
-----------------------------
- TSS FP rate (benign tenants receiving mitigation). Target: <1%.
- Mean time to mitigation (from TSS crossing threshold to policy applied). Target: <90s for automated actions.
- Mitigation efficacy: percent reduction in SLO burn within 5 minutes of action. Target: >60%.
- Eviction churn rate: number of tenant evictions per week. Target: <0.5% of tenants/week.

Security, Audit, and Compliance
------------------------------
- All scoring decisions and policy actions must be recorded to the audit-events sink for at least 180 days.
- Hard mitigations require two-person approval if tenant is tagged restricted-compute.
- Policy configuration changes must go through PR review and be signed by owners in the scoring-api CODEOWNERS file.

Appendix A: Example debugging checklist (quick)
--------------------------------------------
- Verify tenant attribution: request logs contain correct tenant_id and api_key.
- Inspect GPU traces: nvidia-smi, grpc histograms, and runtime p95 deviation.
- Check KV prefix cache stats: eviction_rate, top-prefix heatmap.
- Recompute TSS locally using 1h raw traces for postmortem.

Appendix B: Data retention and sample sizes
-----------------------------------------
- 1m resolution scoring values: retain 14 days.
- 10m aggregates: retain 60 days.
- 1h aggregates: retain 1 year.
- Audit-events (policy actions): retain 180 days.
