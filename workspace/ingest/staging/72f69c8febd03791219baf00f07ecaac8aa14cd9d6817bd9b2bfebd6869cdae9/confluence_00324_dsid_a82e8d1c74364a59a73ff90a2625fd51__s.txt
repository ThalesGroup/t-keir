Service Telemetry & Supply-chain Compatibility Matrix for Private Deploys

Overview

This document defines a combined telemetry contract and hardware/software compatibility matrix that field engineers, SREs, and customer integration teams use to validate private (VPC and on-prem) Redwood deployments. The goal is to unify observability acceptance criteria, supply-chain hardware compatibility, and operational guardrails so private deploys meet product SLAs and regulatory requirements while minimizing day-2 surprises.

Scope

- Applies to: Redwood Private control-plane + runtime, customer-managed VPC branches, and on-prem appliance installs.
- Includes: telemetry schemas, retention and sampling contracts; required agent/collector versions; supported NICs, GPUs, firmware baselines; upgrade/rollback safety gates; post-install verification steps.
- Excludes: application-level prompts and customer data policies (see compliance-evidence pages).

Why this matters

- Inconsistent telemetry and unexpected firmware on GPUs or NICs are root causes for 45% of private-deploy incident escalations in 2025.
- A single compatibility matrix reduces ambiguous requirements during procurement and shortens field lead time by ~30%.

Telemetry contract (service-level)

Summary requirements:
- Mandatory metrics (all must be emitted to the local collector within 60s of boot): runtime.request.latency_ms (p50/p95/p99), runtime.request.errors.count, runtime.kvcache.hits, runtime.kvcache.misses, gpu.utilization_pct, host.cpu_load_1m.
- Minimum span traces: request.received -> model.load -> token.stream -> response.sent. Span duration must include attributes: tenant_id, model_version, shard_id.
- Log levels: service logs must support structured JSON logs with keys: ts, level, svc, msg, trace_id, request_id.
- Sampling & retention: default trace sampling 5%; high-error routes sample 100% for up to 24 hours. Metric retention: 90 days at 1m resolution, 400 days at 1h resolution for customer-managed long-term retention packages.

Collector/agent versions and configuration

- Required collector: redwood-agent >= 2.4.0 (bundled with private-runtime image 2026.01+).
- Supported exporters: OTLP (gRPC), Prometheus remote_write (optionally to customer-prometheus).
- Example OTLP config snippet (YAML):

```yaml
receivers:
  otlp:
    protocols:
      grpc: {}
      http: {}
processors:
  batch: {}
exporters:
  otlp/remote:
    endpoint: "collector.redwood.local:4317"
service:
  pipelines:
    traces:
      receivers: [otlp]
      processors: [batch]
      exporters: [otlp/remote]
    metrics:
      receivers: [otlp]
      processors: [batch]
      exporters: [prometheus, otlp/remote]
```

This simplified table is the canonical acceptance matrix. Customers must provide inventory with exact SKUs and firmware versions. Any deviation must be flagged to Redwood Professional Services prior to cutover.

| Component | Supported SKU / family | Min firmware / driver | Notes / known issues |
|---|---|---:|---|
| GPU | NVIDIA A100 (PCIe) | GPU firmware 55.XX, NVIDIA driver 525.85+ | PCIe variants require IOMMU workarounds if host BIOS < 2022.6 |
| GPU | NVIDIA H100 SXM | GPU firmware 65.XX, NVIDIA driver 530.30+ | H100 requires UEFI secure boot off for current image (planner: 2026.2 runtime patch) |

| Disk | NVMe Samsung PM1733 | FW 3B2QCX0 | Ensure SMART TL margin set to 5% for endurance class C |
| BMC/UEFI | Supermicro X12 series | UEFI 4.1+, BMC 3.2+ | BMC must have remote syslog enabled for warranty telemetry capture |

Acceptance thresholds and tests

Field acceptance consists of the following checks (performed after base install and before tenant handover):
1) Inventory verification: checksum manifest comparing reported device-ids/firmware vs. inventory CSV.
2) Telemetry smoke: emit a full request trace across 1, 10, 100 token loads; verify p95 < 200ms for local L2 model variants and p95 < 400ms for pinned remote variants.
3) KV cache validation: synthetic workload generates 10k prefix requests, expected cache hit ratio >= 0.72.
4) Telemetry completeness: 100% of requests produce a trace_id and logs within 60s; metrics visible in Prometheus and retained for 1 minute at 10s scrape interval.
5) Stress burn-in: 4-hour soak at 60% of projected steady-state QPS with incremental GPU temperature and telemetry sampling checks.

Automated acceptance playbook (CLI)

Run the built-in acceptance script (operator privileges required):

```bash
# from operator host with SSH access to primary controller
./tools/acceptance/run-field-acceptance.sh \--inventory inventory.csv \--collector-endpoint 10.0.1.5:4317 \--soak-duration 14400

# output: acceptance-report-<date>.json
```

Acceptance report schema (flattened JSON fields in output file)
- report_id (string)
- cluster_id (string)
- operator (string)
- pass_fail (string: pass|fail)
- p95_latency_ms (string)
- kvcache_hit_ratio (string)
- missing_telemetry_keys (string, comma-separated)
- incompatible_hardware (string, comma-separated SKUs)
- remediation_action (string)

Day-2 operations: telemetry-first runbook

This runbook complements existing day-2 ops docs by focusing on telemetry-driven troubleshooting.

Alerting thresholds (recommended):
- runtime.request.errors.rate > 0.5% sustained for 5m -> P1 alert to oncall.
- gpu.utilization_pct > 98% for > 10m and queue-size growth -> action: scale-burst policy.
- telemetry.ingest.lag > 120s -> investigate network egress to collector.

Investigation steps (short):
1) Confirm agent health: `systemctl status redwood-agent` and `redwood-agentctl status`.
2) Check local metrics: `curl localhost:9100/metrics | grep runtime_request` for recent values.
3) Trace fetch: `otel-cli fetch --trace_id <id> --endpoint http://localhost:4318/v1/traces` to retrieve span chain.
4) If missing traces, check firewall rules (TCP 4317 and 4318) and MTU mismatch with NIC vendor drivers.

Upgrade & rollback safety gates for private deployments

Upgrade preflight checks (must pass before any coordinated upgrade):
- Inventory parity check (as above)
- Telemetry integrity: no missing mandatory keys in last 24 hours.
- Sufficient capacity: free GPU headroom >= 20% or validated burst policy.
- Upgrade window: customer-approved maintenance window and snapshot backup (if required by customer A/R policy).

Automated canary flow (recommended):
1) Canary subset: 5% of tenants routed to new runtime image and collector config.
2) 60-minute monitoring window: key metrics (p95 latency, error rate, kvcache hit ratio) compared to baseline using rolling 10m windows.
3) Automatic rollback triggers: p95 increases > 20% OR error rate increase > 0.3% sustained for 5 minutes OR consumer error types matching model-compatibility signature.

Rollback procedure (operator steps):
1) Trigger: Canary failed OR manual decision.
2) Execute: `k8s-rollback --deployment runtime --image <previous> --tenants all` (or use operator handoff for on-prem appliances).
3) Post-rollback verification: run telemetry smoke test and assert previous baselines restored.
4) Incident postmortem: attach acceptance-report and telemetry snapshots to the ticket.

Compliance & supply-chain notes

- Procurement: prefer vendors that provide signed firmware images and reproducible checksums. Record vendor-signed manifests in the deployment ticket.
- Evidence preservation: when a hardware incompatibility is detected during acceptance, capture a signed evidence blob (base64 of dmi + fw versions) and attach to the ticket for audit.

Appendix: troubleshooting matrix (common failure modes)

- Symptom: Missing traces only for large requests (> 10k tokens)
  - Likely cause: collector OOM or trace export batching misconfiguration
  - Action: increase collector memory to +2GB, lower batch export size to 200 events, re-run acceptance smoke.

- Symptom: High GPU temperatures during soak
  - Likely cause: incorrect thermal profile or chassis intake flow reversed
  - Action: confirm chassis airflow, apply OEM thermal firmware patch, re-run soak.
