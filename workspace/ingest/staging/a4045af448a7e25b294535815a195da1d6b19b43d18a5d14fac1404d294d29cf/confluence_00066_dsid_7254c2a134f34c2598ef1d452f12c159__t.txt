Tenant Airlock Commissioning and Operator Safety Playbook

Overview

Purpose: This playbook defines the commissioning pattern we call a "tenant airlock" — an isolated, auditable staging path used during initial tenant onboarding, major configuration changes (network/KMS), and sensitive model swaps. The airlock provides predictable safety gates for operators, reduces blast radius for misconfiguration, and produces artifacts required for compliance evidence. This document covers prerequisites, step-by-step commissioning procedures, automated validation checks, escalation and rollback steps, SLOs and audit artifacts, and recommended operator CLI snippets.

Intended audience: Field operators, SREs supporting private deployments, solutions engineers running customer handoffs, and compliance reviewers.

Scope and assumptions
- Applies to VPC-based private deployments and VPC-connected airgapped on-prem variants.
- Assumes the control plane and tenant data plane are installed and reachable via management jump host or operator bastion.
- Assumes operators have RBAC role "operator.airlock.commit" and access to tenant evidence bucket and KMS stamping keys.
- Not covering hardware provisioning steps (see field-installation guide).

Key goals
1) Minimize human blast radius during tenant commissioning.
2) Produce deterministic acceptance artifacts: smoke tests, telemetry samples, and signed evidence bundle.
3) Ensure immediate safe rollback path before any customer traffic flows into production.

Ownership and escalation
- Primary owner: Private Deployments Field Engineering (onboarding squad).
- Emergency escalation: oncall-private-deploy (pager duty) -> eng-platform oncall -> customer success lead.
- Compliance evidence owner: security-ops (verifies evidence bundle).

Airlock Architecture (conceptual)
- Airlock control plane: temporary namespace in customer VPC with restricted egress (HTTP/S to allowed endpoints only) and dedicated service account for operator actions.
- Staging runtime: reserved GPU pool with pinning to non-production models and quantization profiles to test performance under realistic load.
- Traffic gating: operator-approved route table that either points to the staging runtime (airlock) or to tenant production endpoints.
- Evidence store: encrypted object store (customer S3 or operator-managed evidence bucket) with KMS envelope encryption.

Pre-commission checklist (must pass before starting)
- Network: BGP/route validation completed and ACLs verified (CIDR whitelist for operator bastion).
- KMS: operator key present, policy allows encryption:Encrypt and Decrypt for evidence bucket.
- Quotas: reserved GPU capacity for staging assigned and tested with synthetic load.
- Telemetry: observability pipeline subscriptions created (sampling 1:10 for traces, 1:1 for errors).
- SME approvals: Solutions Engineer and Security reviewer signed off in ticketing system.

Commissioning procedure (operator steps)
1) Open onboarding ticket and attach pre-commission checklist. Record ticket ID in evidence bundle.
2) Create airlock namespace: run terraform module or operator CLI: 
   - terraform apply -var 'env=airlock' -target=module.airlock_namespace
3) Provision temporary service account and apply fine-grained RBAC: 
   - rbacctl create --role operator.airlock.commit --namespace tenant-airlock --expiry 72h --notes 'onboard-<ticket>'
4) Mount evidence bucket with KMS: 
   - operator-cli evidence mount --bucket s3://evidence-<tenant> --kms-key arn:aws:kms:...
5) Deploy staging runtime and default model variant: 
   - deployctl apply -f airlock/staging-runtime.yaml --wait 600s
6) Run automated validations (see next section). Do not proceed until all pass.
7) Manual performance verification: operator runs three controlled synthetic scenarios: 
   a) Low-latency conversational burst (95th percentile latency target <= 120ms)
   b) Batch-embedding throughput (tokens/sec target within 15% of benchmark)
   c) KV cache warmup and cold-start latency profile measured over 1 hour
8) Sign and upload evidence bundle: operator-cli evidence sign --ticket <id> --attach ./validation-report.json
9) If all validation gates pass, open ticket for production flip with proposed window and rollback conditions.

Automated validation checks (must be automated where possible)
- Network sanity: traceroute to control-plane endpoints, TLS cert validation, and egress firewall policy conformance.
- KMS and secret access: attempt envelope encrypt/decrypt roundtrip and verify rotation policy existence.
- Runtime health: all runtime pods at 1.0 readiness for 5 continuous minutes.
- Model correctness: 20 predefined prompt-set evaluations run; pass rate >= 98% for syntactic correctness checks and semantic match thresholds.
- Latency SLO smoke: 95th percentile response time <= target defined in tenant SLA matrix.
- Telemetry sampling: a minimum of 100 traces and 100 events ingested into observability backend.

Validation report contents (artifact)
- Ticket ID, operator name, timestamp
- List of checks run with pass/fail and deterministic logs/links to traces
- Synthetic workload artifacts: raw latency histograms, token counts, and CPU/GPU utilization samples
- Signed KMS envelope metadata and evidence bucket object IDs

Decision gates and criteria
- Gate A (Network & KMS): required. Any failure -> STOP and open incident labeled "airlock.network-kms-failure"
- Gate B (Runtime & Model): required. Minor failures in model match may proceed only with SE approval and a documented mitigation plan.
- Gate C (Performance & Telemetry): if latency or telemetry targets fail, operator must schedule an additional tuning iteration. Production flip is blocked until Gate C passes.

Rollback / safe-fail strategies
- Immediate rollback (fast path): if any catastrophic failure observed during commissioning or the first 10 minutes after production flip, execute: 
  1) operator-cli route set --tenant <id> --target staging (re-point traffic away from newly swapped variant)
  2) scale down new model pods: deployctl scale --name model-swap --replicas 0
  3) re-enable previous pinned model variant and confirm traffic flows correctly
- Evidence-first rollback: when compliance evidence required before rollback, capture a final evidence bundle before any destructive change.
- Graceful degrade: for partial performance regressions, enable rate-limiting or throttling policies to bound user impact while rolling back.

Upgrade and long-lived change coordination
- For scheduled upgrades (runtime, model, control plane) use airlock to validate each major change. Each upgrade must include: 
  - Upgrade runbook: planned steps, pre-checks, blackout windows, backout commands
  - Canary policy: start with 1% traffic directed to the upgraded runtime for 30 minutes observation, then 10% for 60 minutes, then 100% after final sign-off
  - Automated rollback trigger thresholds: error rate > 1.5x baseline OR 95th percentile latency increase > 30% -> automatic rollback
- State migration: when moving KV caches or model state, perform transactional snapshot, checksum verification, and a dry-run restore into airlock environment.

Operator safety checklists (quick reference)
- Before any change: verify RBAC and ephemeral credential expiry times
- Before flip: ensure at least two operators are available and at least one has production revert permissions
- After flip: remain on-call for 60 minutes and monitor defined dashboards (latency, errors, cpu_gpu, kv_hit_rate)

Runbook snippets and CLI commands
- Mount evidence: operator-cli evidence mount --bucket s3://evidence-tenantX --kms-key arn:aws:kms:region:acct:key/abcd
- Trigger validation suite: operator-cli validate --suite airlock-onboard --output ./validation-report.json
- Route flip to production: operator-cli route set --tenant tenantX --target production --window 2027-02-11T02:00Z/2027-02-11T03:00Z
- Emergency rollback: operator-cli emergency rollback --ticket <id> --reason "latency-regression" --confirm

SLOs and monitoring thresholds (recommended)
- Latency: 95th percentile <= tenant-SLA-95 (default 120ms for small conversational workloads)
- Error budget burn: automated alert when 1h burn-rate > 20% of hourly budget
- Telemetry fidelity: fewer than 0.5% missing traces across the sampling window
- Evidence retention: signed evidence bundles retained for minimum 180 days for regulated customers

Evidence and audit artifacts (what to store)
- validation-report.json (signed), signed KMS envelopes, a copy of deployed manifests with checksums, route-change audit log, operator action log (who/when/what), and observability links to recorded traces and dashboards.

Post-commission acceptance and handoff
1) Compile the evidence bundle and upload to evidence store with tags: tenant:<id>, ticket:<id>, type:commissioning, status:accepted
2) Notify customer success and provide handoff notes with SLA expectations, known limitations, and tuning suggestions
3) Schedule follow-up QBR with customer within 14 days to review performance and handle any model-quality concerns

Common failure modes and remediations
- KMS permission denied: verify IAM policies and check key policy for operator principal. Temporary mitigation: use operator-managed ephemeral key while key policy is updated.
- Trace ingestion gap: check observability sampler configuration and network egress rules to telemetry backend. If backlog grows, increase sampling temporarily to capture sufficient traces.
- GPU OOM during synthetic test: reduce batch size and restart staging runtime; record OOM logs and escalate to runtime-kernel team if recurrent.

Appendix A — Staging runtime manifest (example)
# YAML excerpt (operator should validate before apply)
# deploys a minimal staging runtime with pinned model variant
apiVersion: redwood/v1
kind: StagingRuntime
metadata:
  name: tenantX-airlock-runtime
spec:
  gpuPool: reserved-small
  modelPin: openmodel-compat-v2-quant
  kvCachePolicy: ephemeral
  observability:
    traces: sampleRate: 0.1
    logs: level: info

Appendix B — Evidence bundle file list (example)
- validation-report.json
- deployed-manifests.tar.gz (sha256)
- runtime-metrics.tar.gz
- kms-envelope.json
- route-audit.log

Appendix C — Troubleshooting checklist (operator quick commands)
- Check runtime pods: kubectl -n tenant-airlock get pods -o wide
- Confirm GPU utilization: nvidia-smi on runtime node or metrics query: sum(container_gpu_utilization) by (node)
- Recreate ephemeral service account: rbacctl rotate --name operator-airlock --namespace tenant-airlock
