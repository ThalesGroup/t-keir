Traffic Continuity Scorer and Notification Contract — Operator Handbook

Overview
========

Purpose: define the Traffic Continuity Scorer (TCS), the dashboard and alerting contract for continuity degradations, and the operator notification and triage runbook. The TCS is a single composite signal used by platform operators and downstream teams to prioritize incidents that threaten customer request continuity (e.g., token loss, model swap failures, long tail latency, partial response streams). This doc is the canonical contract for dashboards, alert rules, and runbook steps across regions.

Why we need it
---------------
- Multiple distinct symptoms (latency, 5xxs, stream truncation, model-swap misfires) historically generated noisy, disconnected alerts.
- Operators and SREs need a single, interpretable priority signal that balances severity and customer-perceived continuity.
- TCS enables consistent automation for short-circuit fallbacks and informs canary rollbacks.

Scope and boundaries
--------------------
- Applies to all hosted inference frontends and regional gateways that feed into the request routing plane.
- Not intended for batch jobs or offline ingestion pipelines.
- Each tenant, route, and region gets an independently computed TCS (scoped slices).

Design summary
--------------
1) Inputs (sampled per 1m):
   - request_success_rate (2xx/total)
   - token_deliveries_per_request (median and p90 of successfully emitted tokens)
   - long_tail_latency (p99 request duration for foreground requests)
   - model_swap_success_rate (percentage of model swap ops completed within 15s)
   - stream_close_aborts (count of client stream terminations classified as platform-initiated)

2) Normalization and weights (default):
   - request_success_rate -> 35% importance
   - token_deliveries_per_request -> 25% importance
   - long_tail_latency -> 20% importance
   - model_swap_success_rate -> 15% importance
   - stream_close_aborts -> 5% importance

3) Scoring function (interpretable 0–100):
   - Each input is mapped to a 0–100 subscore using monotonic transforms (higher = better).
   - Weighted sum gives final TCS (0 worst continuity — 100 perfect continuity).

Operational thresholds
----------------------
- Green: TCS >= 90 — normal
- Watch: 75 <= TCS < 90 — operator awareness, investigate if persistent 
- Degraded: 50 <= TCS < 75 — start mitigation (prefetch fallback, model variant swap)
- Critical: TCS < 50 — automatic escalation and region-level traffic shedding policies may be invoked

Dashboard contract
------------------
Every region/operator dashboard tile must include:
- Live TCS timeseries (1m resolution, 1h/6h/24h zoom)
- Breakdown bar chart of subscore contributions (requests, tokens, latency, swaps, streams)
- Tenant heatmap (top 50 tenants by query volume) annotated with current TCS slice and alerts
- Top 10 impacted routes and recent model-swap events

Suggested Grafana panels (panel queries are PromQL examples using our metric names):
- TCS (1m):
  sum by(region)(traffic_continuity_scorer{job="frontier"})
- Request success component (30s):
  100 * sum(successful_requests{job="frontier"}) / sum(total_requests{job="frontier"})
- Token delivery median (1m):
  histogram_quantile(0.5, sum(rate(tokens_emitted_bucket[1m])) by (le, region))

Alerting contract and example alert rules
---------------------------------------
Alerting must follow this pattern: a Watch alert (paged to oncall) is fired at Watch threshold; a Degraded alert triggers an Incident (Slack+PagerDuty); Critical triggers regional oncall escalation and automated protective actions. Attach the TCS slice with the alert.

Prometheus alert example (YAML-like pseudocode):

- alert: TCS_WATCH_Region_eu-west-1
  expr: traffic_continuity_scorer{region="eu-west-1"} < 75 and traffic_continuity_scorer{region="eu-west-1"} >= 50
  for: 5m
  labels:
    severity: warning
    runbook: /confluence/eng-platform/runbooks/regional-traffic-continuity-triage-runbook-2026
  annotations:
    summary: "TCS Watch in eu-west-1: {{ $value }}"

- alert: TCS_CRITICAL_Region_eu-west-1
  expr: traffic_continuity_scorer{region="eu-west-1"} < 50
  for: 2m
  labels:
    severity: critical
  annotations:
    summary: "TCS Critical in eu-west-1 — consider traffic shedding and automatic fallback"

Notification routing rules (contract):
- Watch -> Slack #platform-watch + email to platform-ops (no page)
- Degraded -> PagerDuty on-call for region (page), Slack incident channel created automatically
- Critical -> PagerDuty P1 flow (page + escalation), notify Product-Integrity and Customer Success if impacted tenants > 5

Runbook: operator triage checklist (ordered)
------------------------------------------------
1) Acknowledge alert and attach TCS slice and top-5 contributing subsignals.
2) Confirm scope (tenant-scoped? route-scoped? region-wide?). Use query: "traffic_continuity_scorer{route=~\"^api/.*\"}"
3) Check model-swap pipeline: exports/model-swap-events{region} for errors in last 15m. If >5 failed swaps, mark model_subsystem as suspect.
4) If long_tail_latency is primary contributor, examine recent GC / kernel/queueing events on affected nodes (node-level p99 duration dashboards).
5) If token_deliveries_per_request dropped: verify KV-prefix-cache hit rates and edge buffer backpressure metrics.
6) Apply mitigation in order of least-impactful first: increase warmset prefetch, switch to compatible lower-memory variant, enable prefix-kv-cache-read-only mode, apply tenant soft-throttle.
7) If automatic mitigation fails within 10 minutes and TCS < 50: execute region-level fallback (shift low-priority traffic to secondary region and enable model-variant fallback).
8) Post-incident: attach timeline, root-cause hypothesis and changes to the incident ticket and tag the TCS snapshot to the incident for future regressions.

Escalation and ownership
------------------------
- First responder: regional platform oncall (team: Platform-Operators).
- Secondary: Serving Runtime oncall if model-swap or kernel-level issues are implicated.
- Tertiary: Platform Engineering Pager if automated fallback fails to restore TCS in 20m.

Runbook templates and automation suggestions
------------------------------------------
- Use the incident commander CLI to capture the current TCS slice: `./inc-tools capture-tcs --region eu-west-1 --window 15m`
- Automate TCS gated runbooks as step functions with manual approvals for region-level fallbacks. The automation should expose a dry-run to estimate impact.

Retrospective and metricization guidance
---------------------------------------
- For each TCS-triggered incident, the owner must produce a short retrospective within 7 days including:
  1) TCS time-series snapshot (1h before, during, 2h after)
  2) Top-3 contributing subsignals and operator mitigations tried
  3) Regression test to prevent reoccurrence (add to preflight and synthetic checks)

- Suggested follow-ups: add a synthetic continuity test to the degradation lab that simulates token truncation and model-swap failures; track mean-time-to-recover (MTTR) from TCS_Degraded -> TCS_Green as a KPI.

Appendix: example SQL and PromQL snippets
----------------------------------------
- Tenant heatmap SQL (ClickHouse-like):
  SELECT tenant_id, avg(tcs) as avg_tcs, count(1) as qps
  FROM platform_metrics.traffic_continuity_scorer
  WHERE region = 'us-east-1' AND ts >= now() - interval 1 hour
  GROUP BY tenant_id
  ORDER BY avg_tcs ASC
  LIMIT 50;

- PromQL example: combined subscore breakdown:
  sum by (region) (
    0.35 * (100 * sum(successful_requests) / sum(total_requests))
    + 0.25 * (histogram_quantile(0.5, sum(rate(tokens_emitted_bucket[1m])) by (le)))
    + 0.2 * (100 - (100 * (increase(request_duration_seconds_bucket{le=\"0.5\"}[5m]) / increase(request_duration_seconds_count[5m]))))
  )
