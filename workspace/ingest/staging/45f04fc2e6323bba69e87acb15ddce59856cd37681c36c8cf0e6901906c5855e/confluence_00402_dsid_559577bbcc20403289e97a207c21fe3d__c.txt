Consumption Sandbox: Scenario Composer & Playback PRD

Overview:

This document describes the product requirements, high-level design, roadmap, pricing considerations, and release notes for the Consumption Sandbox: Scenario Composer & Playback ("Sandbox Composer"). The Sandbox Composer is a developer- and solutions-engineer-facing product that lets users define, simulate, and replay realistic inference workloads against Redwood Inference environments (hosted, dedicated, private) to estimate latency, cost, and fidelity outcomes prior to onboarding or large-scale migrations.

Goals and success metrics:
- Primary goal: reduce friction and uncertainty for teams migrating from hosted to dedicated/private or re-configuring fidelity/batching/quantization controls.
- Success metrics (12-week):
  1. 30% reduction in time-to-first-validated-simulation for new customers (measured from sign-up to completed simulation run).
  2. 20% increase in accurate cost projection signals (simulation estimate within ±15% of first-week actuals for customers that run the simulator during onboarding).
  3. Adoption: 40% of new Dedicated onboarding flows include a Sandbox Composer run during initial migration.

User personas:
- Developer (self-serve): wants a quick cost/latency preview for an integration.
- Platform/Infra engineer: composes multi-route scenarios including session affinity and warmup behavior.
- Solutions engineer / CSM: uses the composer to build a validated migration plan and confirm SLA expectations with customers.

Core product pillars (what we will build):
1) Scenario Composer UI + YAML DSL
   - A lightweight web UI (Console) for rapid scenario composition with: routes, sequence length distributions, concurrency, priority shaping, KV/cache warmup steps, and per-route fidelity presets.
   - A YAML-first DSL that captures scenario semantics for versioning and replay. Example:

   # example scenario: two-route conversational app\   routes:
     - name: chat_primary
       model: redwood-chat-3b-fused
       qps: 30
       seq_distribution: "p(256)=0.6,p(512)=0.3,p(1024)=0.1"
       warmup: {
         "type": "kv-prefill",
         "requests": 100
       }
     - name: reranker
       model: rerank-1.0
       qps: 5
       seq_distribution: "fixed(64)"

2) Playback Runner (cloud + private-friendly)
   - A scalable runner that replays composed scenarios against selected target environments. The runner supports: steady-state and burst traffic patterns, configurable inter-request timing jitter, and synthetic session affinity.
   - Runs can be instrumented with real telemetry collectors (latency histograms, P95/P99, token-level cost breakdowns, KV cache hit rate).

3) Cost & Fidelity Estimator
   - Produce per-run estimates including: per-token cost, estimated GPU-hours, projected invoices for first 7 days at projected load, and fidelity risk flags (where simulation indicates likely quality regression vs baseline).

4) Observability Integration
   - Out-of-the-box dashboards for scenario runs in Redwood Console: per-route latency distribution, batch sizes, inferred kernel choices, quantization mismatch warnings, and slowdown root-cause highlights.

Requirements (must-have):
- UI + YAML DSL for creating and saving scenarios.
- Replay runner with pluggable drivers for: hosted API (internal), dedicated stacks (internal network), and private deployments (customer VPC agent).
- Telemetry capture: trace_id propagation, per-request token counts, model variant used, kernel selection tag.
- Estimator accuracy target: simulation estimate within ±15% vs measured cost for simple conversational workloads and ±25% for multimodel pipelines.
- RBAC: read-only scenarios and run access for normal users; run-creation limited to owners or customers with specific entitlements.

Constraints and non-goals:
- Non-goal: exact parity with customer's production dataset fidelity; this is a synthetic workload runner intended for capacity, cost, and latency projections (not ML metric tuning).
- Non-goal v1: deep fidelity regression analysis based on full evaluation suites (we will provide high-level flags; deeper evals are in Eval Harness).

Design overview:
- Components:
  1. Composer Service (product): stores scenarios, validates DSL, exposes preview API.
  2. Runner Fleet: autoscaled workers (K8s job workers for hosted/dedicated), private-agent runtime for on-prem replay.
  3. Estimator Engine: hybrid offline estimator that uses performance profiles from the model catalog, token distribution sampling, and observed kernel costs.
  4. Telemetry Bridge: normalizes runtime telemetry into Console dashboards and attaches scenario metadata.

Deployment and integration notes:
- Hosted: Composer UI + Runner tasks run within Redwood's hosted account; runs priced as per consumption (see Pricing notes).
- Dedicated: Runner tasks can target Dedicated pools; telemetry must be forwarded to Redwood Console with tenant-id.
- Private: a lightweight Runner Agent bundle (binary + service manifest) will be shipped; agent authenticates to the Composer and uploads telemetry when permitted.

Acceptance criteria (MVP):
- Users can author and save scenarios in the Console and via YAML upload.
- Users can select a target environment and execute a run that completes end-to-end (runner, telemetry, estimator).
- Console shows run summary within 2 minutes of completion and includes cost and latency estimates.
- Estimator meets accuracy targets for at least 3 benchmarked customer patterns (conversational, retrieval-augmented, reranking pipeline).

API and CLI examples:
- Create scenario (curl):
  curl -X POST https://api.redwood.ai/v1/sandbox/scenarios -H 'Authorization: Bearer <TOKEN>' -d '@scenario.yaml'

- Launch run (CLI):
  rwin sandbox run --scenario-id=abc123 --target=dedicated-us-west-2 --duration=15m --concurrency=50

Telemetry and SLOs:
- Instrumentation must include: request_id, scenario_id, route_name, model_variant, tokens_in, tokens_out, kernel_id.
- UI SLOs: scenario save latency < 1s (p95), run start command acknowledged < 3s.
- Data retention: scenario definitions retained indefinitely; run telemetry retained 90 days by default with optional enterprise retention add-on.

Security and privacy:
- For private deployments, default mode is telemetry opt-in. Customers may choose to route collector data to their own telemetry backends; in that case Redwood's estimator will run in a dry-run mode (local-only sampling) and require manual upload to Console.
- No customer prompt or user data will be persisted in Redwood storage unless explicitly consented; default synthetic input generators are used in hosted/demo runs.

Pricing and packaging notes:
- Pricing model (v1): metered by scenario-run duration and concurrency footprint plus a small fixed scenario storage fee.
  - Scenario storage: $0.50 per active scenario / month for teams >10 scenarios.
  - Run compute credit: 0.01 credits per vCPU-minute equivalent, converted to GPU-equivalent using model profiles.
  - Billing options: consumption-billed for hosted customers; metered consumption report for Dedicated customers with optional credit-reservation bundles for frequent runs.
- Commercial playbook: include a free tier (3 scenarios + 2 runs / month), and a developer bundle add-on for startups with 100 free run-minutes during evaluation period.

Roadmap (quarters):
- Q2 2028 (alpha): internal SEs + pilot customers; YAML DSL and simple runner; basic estimator and Console integration.
- Q3 2028 (beta): private-agent; fidelity risk flags; telemetry dashboards; billing hooks.
- Q4 2028 (GA): enterprise retention, RBAC controls, scenario-sharing templates, pricing bundles.
- 2029+: advanced fidelity connectors to Eval Harness, exportable migration plans, adaptive scenario autotuning.

Operational playbook (runbook summary):
1) Validate scenario YAML with composer: composer-cli validate scenario.yaml
2) Start a run: composer-cli run --scenario <id> --target <env> --duration <t>
3) Monitor via Console: open /sandbox/runs/<run_id> for latency and cost breakdown.
4) If estimator diverges >30% from observed for production: open an SE ticket and capture run_id, telemetry snapshot, and kernel selection map.

Release notes (v1.0 - 2028-03-15):
- Initial public alpha releasing to internal SE org and 5 pilot customers.
- Features included: YAML DSL, Console scenario editor, hosted runner, basic estimator, Console telemetry dashboards, CLI tooling for run orchestration.
- Known limitations: private-agent requires manual install; estimator does not yet handle complex multimodel orchestration edge-cases; cost-to-invoice mapping may differ for customers with committed reserved capacity (we show gross compute estimates only).
