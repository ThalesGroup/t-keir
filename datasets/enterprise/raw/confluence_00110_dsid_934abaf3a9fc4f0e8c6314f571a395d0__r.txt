Response Fidelity Negotiation Protocol Spec

Overview

This design spec describes the Response Fidelity Negotiation Protocol (RFNP): a light-weight, backwards-compatible protocol for runtime negotiation of response fidelity between a Redwood client SDK (or edge proxy) and the Redwood serving plane. RFNP enables per-request fidelity preference signaling, server-side capability advertisement, deterministic fallback selection, and credit-impact estimation for pricing and billing.

Goals

- Provide a compact HTTP/JSON negotiation handshake that can be embedded in existing /generate and /chat endpoints with minimal latency overhead.
- Make fidelity selection deterministic and observable: decisions must be reproducible from inputs (client preference, tenant contract, server capability).
- Surface an economic estimate (token and compute credit delta) to the client before charging to enable preflight and cost-aware UX.
- Support staged rollouts and graceful degradation: server may downgrade fidelity when SLOs or capacity constraints require it.

Non-Goals

- This protocol does not replace long-lived model variant selection (catalog-level policy). RFNP is per-request negotiation only.
- Not intended to standardize every possible fidelity knob (e.g., kernel-level quantization). Those remain server-side controls surfaced as capability flags.

High-level contract

- Transport: HTTPS with standard Redwood auth headers. RFNP payload is embedded in the request body under the top-level field "fidelity_negotiation".
- Negotiation model: client sends a preference profile (tier, hard/soft constraints). Server responds with an agreed fidelity profile and an optional preflight estimate. If client marks a preference as "hard", the server must only accept or reject the request outright (400) if it cannot meet the hard requirement.

Example request snippet (JSON included in /generate body):

{
  "prompt": "Summarize the following...",
  "fidelity_negotiation": {
    "preference": "balanced",
    "constraints": {
      "max_latency_ms": 200,
      "min_response_quality_score": 0.82,
      "hard": ["max_latency_ms"]
    },
    "enable_preflight": true,
    "client_affinity": "edge-nyc-1"
  }
}

Example server response snippet (partial):

{
  "id": "resp_abc123",
  "fidelity_negotiation": {
    "agreed_profile": "balanced-v2",
    "capability_flags": ["kv_cache", "quant-8x2"],
    "estimated_credit_delta": 0.0042,
    "estimated_latency_p50_ms": 120,
    "status": "accepted"
  }
}

Fidelity Profiles and Capability Flags

- Profiles are short strings (immutable per release) that map to a deterministic server config (model variant, quantization, prompt templates, and runtime knobs). Example profiles: low-latency-v1, balanced-v2, high-fidelity-v1.
- Capability flags enumerate runtime features available to the request: kv_cache, local_prefetch, quant-8x2, batching-window-8ms, safety-scan.

Decision logic priority (server-side)

When a request arrives with fidelity_negotiation, the server evaluates in this priority order:
1) Tenant SLA/contract overrides (e.g., enterprise tenants pinned to dedicated profile).
2) Hard constraints from client (reject if unmet).
3) Current regional capacity and SLO headroom.
4) Server capability compatibility with requested preference.
5) Economy: prefer cheaper compatible profiles if client preference marked "cost_aware".

Negotiation flow (detailed)

1. Client constructs preference profile and optional constraints, sets enable_preflight true if it wants an estimate before continuing.
2. Client submits request to /generate with fidelity_negotiation in body.
3. Server computes candidate profiles (matching model, tenant mappings), filters by hard constraints and capability flags.
4. If enable_preflight is true, server responds synchronously with status: preflight and estimated_credit_delta and estimated latency percentiles. The server does not consume credits in preflight mode; request may be replayed to actually execute.
5. If preflight is false (default), server performs negotiation and either: accepts and executes with the chosen profile, or rejects (400) if hard constraints cannot be satisfied.
6. Execution path must include a negotiation trace id in logs and in response headers: X-RFNP-Trace: rfnp-<sha1>.

Preflight semantics and UX guidance

- Preflight is intended for client-side UI which surfaces an approximate cost and latency before the user action is billed. Estimated_credit_delta must be within ±20% for most workloads.
- If the client displays a preflight estimate, it must include a timestamp and the model/profile used to compute it (agreed_profile or candidate list).

API surface and fields (table-like text)

- fidelity_negotiation.preference (string): Suggested profile (informational).
- fidelity_negotiation.constraints.max_latency_ms (int): Soft/hard latency ceiling.
- fidelity_negotiation.constraints.min_response_quality_score (float 0..1): Minimum acceptable quality.
- fidelity_negotiation.constraints.hard (list[string]): Field names that are hard constraints.
- fidelity_negotiation.enable_preflight (bool): Requests an estimate only.
- fidelity_negotiation.client_affinity (string): Preferred edge/region id.
- Response: fidelity_negotiation.agreed_profile (string), capability_flags (list), estimated_credit_delta (float), estimated_latency_p50_ms (int), status (accepted|rejected|preflight).

Edge cases and compatibility

- Missing fidelity_negotiation: server uses tenant default mappings and proceeds as before.
- Unknown preference values: server maps unknown preferences to tenant default or balanced-v2 and includes warning in response.
- Conflicting hard constraints: server rejects with 400 and structured error: {"error_code":"RFNP_HARD_CONFLICT","details":"max_latency_ms cannot be met in region"}.

Rollout and migration plan

1. Feature flag behind runtime toggle: rfnp-enabled (default: false).
2. Canary rollout: enable rfnp-enabled for internal testing tenants and a subset of hosted tenants (5% traffic) for 2 weeks. Monitor negotiation acceptance rate, preflight accuracy, and median negotiation overhead.
3. Increase to 25% over next 2 weeks if error rate < 0.2% and preflight mean error < 20%.
4. Enable for all hosted traffic behind a second flag: rfnp-preflight-opt-in. After 4 weeks, flip the global flag if stability metrics are met.

Monitoring, SLOs and observability

- Latency overhead: negotiation median additional latency must be < 5ms p50 and < 15ms p95.
- Preflight accuracy SLO: 90% of preflight estimates must be within ±20% of actual credit delta.
- Acceptance rate: for balanced preference, server acceptance rate should be > 98% in normal capacity.
- Instruments to add: rfnp.acceptance_rate, rfnp.preflight_error_ratio, rfnp.negotiation_latency_ms_p50/p95, rfnp.hard_rejects_count.

Billing and metering integration

- If preflight is used, no charges apply. The subsequent execution must include negotiation trace id so billing correlates executed profile to preflight.
- estimated_credit_delta is advisory; billing is computed from executed profile and actual tokenization. Discrepancies should be surfaced via an itemized usage line with preflightId reference.

Security and safety considerations

- Never allow negotiated profile to sidestep tenant policy or safety scans. Capability flags are advisory only; tenant-level block lists must be enforced first.
- Preflight cannot be used to probe for model internals: limit preflight rate to 10/min per token_budget to mitigate probing attacks.

Backwards compatibility and SDK changes

- SDKs should add a thin wrapper that optionally populates fidelity_negotiation. Default behavior: do not enable preflight and pass an empty preference field to preserve existing routing.
- Console will add a developer toggle to preview preflight estimates in Dev Mode.

Example errors and recommended client handling

- RFNP_HARD_CONFLICT (400): retry not recommended; surface message to user and optionally offer lower-fidelity fallback.
- RFNP_CAPABILITY_MISMATCH (200 + warning): proceed with downgraded profile and include warning in response.
- RFNP_PREFLIGHT_STALE_ESTIMATE (200 + code): server estimates may be stale due to transient capacity; client can either proceed or request a second preflight.

Testing matrix

- Unit tests: negotiation matching logic, capability flag parsing, hard-constraint rejection.
- Integration tests: SDK -> hosted API with preflight on/off, ensure trace ids, validate billing correlation.
- Chaos tests: force capacity pressure to verify graceful degradation and fallback selection.

Next steps and open questions

- Should we permit multi-round negotiation (server proposes alternate profiles and client selects)? Tradeoff: extra RTT vs. more precise selection.
- Decide canonical list of capability flags to expose and their stability guarantees.
- Confirm maximum acceptable preflight rate for enterprise tenants and whether exemptions are required.
