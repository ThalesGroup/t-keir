docs-site-content-lifecycle-and-local-preview

Overview

Purpose: This page documents the content lifecycle, local preview workflow, and canonical fix process used by the Developer Experience team to keep SDK guides, API examples, quickstarts and docs-site content high-quality and production-ready. Use this as the single-source procedural reference for creating, reviewing, publishing, and maintaining developer-facing content.

Goals
- Reduce time from draft -> published to under 5 business days for small changes.
- Ensure all SDK and API example snippets are runnable and have CI coverage.
- Maintain a lightweight canonical-fix path for urgent support-driven fixes.
- Provide a reproducible local preview and linting workflow for contributors.

Scope
- Applies to: SDK guides, Quickstarts & templates, API examples, Docs-site operating procedures, and Canonical fixes for recurring support issues.
- Excludes: internal meeting notes, experimental research writeups (kept in Google Drive).

Ownership and Roles
- Author: creates the initial draft and is responsible for code sample correctness.
- Reviewer(s): at least one DX engineer and one product-owner reviewer for API/behavior changes.
- Docs Site Maintainer: owns CI checks, deploy pipeline, and rollback playbook. (Team: developer-experience/docs-site)
- Support Triage Lead: coordinates quick canonical fixes for critical customer-facing regressions.

Content Types and Metadata (frontmatter)
All docs in the docs-site repo must include a standardized frontmatter block. Key names and allowed values: 

- title: string
- description: short string (1–2 lines)
- sidebar_label: string
- sdk: one of [javascript, python, go, java, rest] or omitted
- language: one of [en-US, fr-FR, de-DE] (default en-US)
- product_area: one of [api, embeddings, streaming, console]
- api_examples: ["list of example ids"] (optional)
- last_updated_by: author name
- last_updated_at: YYYY-MM-DD
- canonical_fix_tag: freeform tag used for triage (optional)
- severity: one of [low, medium, high] (default low)

Example frontmatter (YAML-like):
---
title: Quickstart: Calls with the JavaScript SDK
description: Minimal example showing streaming + function calls
sdk: javascript
language: en-US
product_area: api
last_updated_by: Maya Chen
last_updated_at: 2025-02-10
---

Content Lifecycle (step-by-step)
1) Proposal / Intention (Owner creates a short proposal):
   - Create a short Confluence stub with the proposed scope, sample code language(s), and acceptance criteria. Add label `docs-proposal`.
2) Draft (Author produces full draft in the docs repo or as a Confluence draft):
   - Use the SDK quickstart template (see section "Templates & scaffolding").
   - Include runnable code blocks and tests where applicable.
3) Review (peer review + SME):
   - Request at least one DX and one Product/Model reviewer.
   - Run `yarn docs:lint` and `yarn docs:link-check` locally before requesting review.
4) CI & Staging (automated checks):
   - PR must pass: ESLint/remark-lint, link-checker, sample-code smoke tests, accessibility checks.
   - Docs Site Maintainer verifies staging preview and signs off.
5) Publish
   - Merge to main -> automatic deployment to https://docs.redwood.ai/staging.
   - After 24-hour smoke window, Docs Site Maintainer triggers production deploy.
6) Maintenance
   - Every document must have a `last_review` tag and be touched at least once per year.

Templates & Scaffolding
- Location: docs-repo/templates/quickstarts/ (monorepo path).
- Quickstart template includes: title, 1-paragraph intro, prerequisites, step-by-step commands, runnable code in 2 languages, test snippet, and troubleshooting section.

Minimal quickstart skeleton (example):

# Quickstart: Name
> Short one-liner about what this quickstart enables.

Prerequisites:
- Account with API key set in env var REDWOOD_API_KEY
- Node 18+ (or Python 3.10+)

Steps:
1) Install the SDK
   - JavaScript: `npm install @redwood/inference --save`
2) Run a simple call
   - JS snippet:

```js
import Redwood from '@redwood/inference';
const client = new Redwood({ apiKey: process.env.REDWOOD_API_KEY });
const res = await client.text.generate({ model: 'rw-open-7b', prompt: 'Write a short haiku about devx.' });
console.log(res.output_text);
```

3) Validate locally with `node example.js`

Local Preview & Developer Workflow
Requirements: Node 18+, yarn, Docker (for link-check container).

Typical flow:
- git checkout -b docs/<short-topic>
- yarn install (root)
- cd docs-site && yarn && yarn start:dev

Commands (docs-site repo using Docusaurus v2):
- yarn start:dev           # local server with live reload (http://localhost:3000)
- yarn build:staging       # build static site (staging bundle)
- yarn docs:lint           # runs remark + eslint for MDX and code blocks
- yarn docs:format         # run prettier on MDX and code samples
- yarn docs:smoke-test     # run sample snippets (via node/pytest harness)
- docker run --rm -v $(pwd):/src linkchecker/linkchecker:latest http://localhost:3000

Notes on running the preview:
- If you change an SDK API example, update the smoke-test fixture under tests/docs-fixtures.
- Use `yarn docs:smoke-test --file=path/to/snippet` to validate a single snippet quickly.

CI Integration
- PR Checks: `docs-lint`, `link-check`, `snippet-smoke-tests`, `accessibility-check`
- If a snippet test fails, CI posts a comment with the failing command and reproducer.
- Docs CI postings include a staging preview URL that expires after 7 days.

Canonical Fix Process (for priority customer issues)
When Support or an SRE flags a customer-facing regression tied to documentation or example code (e.g., broken auth pattern, model-compat mismatch, streaming cancellation behavior), follow the canonical fix runbook: 
1) Create an Issue in the docs repo with label `canonical-fix` and severity tag.
2) Assign to Support Triage Lead and add immediate owner.
3) Hotfix steps (author + maintainer):
   - Make minimal change that corrects customer impact (usually code snippet or short warning).
   - Run `yarn docs:smoke-test --fast` and `yarn docs:lint` locally.
   - Open PR with `canonical-fix` in title, request expedited review (24-hour SLA for high severity).
   - Once merged, Docs Site Maintainer triggers an expedited deploy to production and updates the issue.
4) Postmortem: If the problem was severe or repeated, create a short incident note and attach to the issue.

Common support-to-docs canonical examples
- Auth errors: missing or mis-ordered header examples (fix: show exact header order and example curl).
- Streaming cancellations: examples that omit `signal`/AbortController usage (fix: add minimal cancellation snippet).
- Embeddings mismatch: examples that use the wrong vector dims for a model (fix: add model-specific dims table).
- SDK version mismatches: quickstart referencing deprecated constructors (fix: update to current constructor and add deprecation note).

Top Support Issues & Canonical Fix Templates
- Template PR title: `[canonical-fix][high] Fix auth header example in quickstart - <short-desc>`
- PR body checklist:
  - [ ] Reproduced issue locally
  - [ ] Added/fixed code snippet and smoke test
  - [ ] Ran `yarn docs:lint` and `yarn docs:smoke-test`
  - [ ] Added link to support ticket or issue number

Sample CLI snippet showing correct curl auth (include exact spacing and header):

curl -s -X POST https://api.redwood.ai/v1/generate \ \
  -H "Authorization: Bearer $REDWOOD_API_KEY" \ \
  -H "Content-Type: application/json" \ \
  -d '{"model":"rw-open-7b","input":"Hello world"}'

Monitoring & Post-deploy Checks
- After any publish, the Docs Site Maintainer verifies:
  - Staging preview is accessible and smoke tests pass for 24 hours.
  - Production pages are reachable (HTTP 200) and no new 404s introduced.
  - Page-level analytics show expected traffic; anomalous spikes trigger investigation.

Rollback & Emergency Procedure
- If a production deploy introduces a regression:
  1) Docs Site Maintainer reverts the merge commit and triggers deploy.
  2) Notify #docs-channel and assigned reviewers.
  3) Open a postmortem if rollback is followed by an incident.

Maintenance Cadence
- Quarterly content sweeps by product area owners.
- Annual review for all quickstarts and SDK guides to ensure language parity across SDKs.

Appendix: Troubleshooting checklist for contributors
- Snippets failing smoke-test: confirm the local env var REDWOOD_API_KEY is valid and model name is correct.
- Link checker failing: run link-checker locally and fix absolute vs relative links. Prefer relative links for internal pages.
- Formatting diffs: run `yarn docs:format` before committing.
