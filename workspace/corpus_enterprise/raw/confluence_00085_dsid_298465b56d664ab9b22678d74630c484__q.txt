Quantized Serving: SLO–Cost Tradeoff Runbook

Summary
-------
This runbook describes the operational procedure, telemetry, and decision heuristics SREs and on-call owners should use when trading off SLOs for lower unit cost via quantized model serving. It focuses on production-facing inference (latency SLOs, error budgets, throughput) and ties the quantization decision to capacity planning, rollout, and incident review. The guidance applies to Redwood-hosted and Dedicated deployments; private deploys should adapt network/KMS specifics but follow the same decision logic.

Goals
- Provide clear, auditable steps for enabling, throttling, or rolling back quantized serving profiles (e.g., int8, int4, hybrid).
- Define required telemetry and alerts to ensure cost optimizations do not silently breach customer-facing SLOs.
- Offer a decision matrix mapping SLO tiers to allowed quantization, autoscaler targets, and emergency fallbacks.

Audience
- SRE on-call and capacity engineers
- Runtime engineers responsible for compiling/serving kernels
- Product/Platform managers approving cost experiments

Prerequisites and ownership
- Owner (primary): eng-sre/model-serving-capacity
- Secondary owners: eng-serving-runtime (kernel/quant), eng-platform (observability)
- Required telemetry: per-model and per-route histograms for latency (P50/P95/P99), per-token CPU/GPU time, request success rate, model_variant label (fp16/int8/int4), batch_size distribution, KV cache-hit ratio, and per-tenant error budget burn rate.

SLO and cost signals to monitor
1) SLOs (example):
   - Tier 1 (critical): P99 latency <= 250ms, availability >= 99.95%
   - Tier 2 (standard): P99 latency <= 500ms, availability >= 99.9%
   - Tier 3 (best-effort): P99 latency <= 1s, availability >= 99.0%
2) Cost signals: GPU-seconds per 1k tokens, average tokens-per-request, cost per inference (derived from reserved GPU hourly rate + amortized infra).
3) Quality signals: upstream regression flags, customer-reported hallucination/score regressions (from Redwood Optimize / evals).

Decision matrix (SLO -> allowed quantization and constraints)
| SLO Tier | Allowed quantization profiles | Max batch size | Cache policy | Fallback policy |
|---|---|---:|---|---|
| Tier 1 | fp16 only; quantized only in canaries with strict perf testing | 4 | aggressive KV preservation; do not evict on cold start | Route to reserved fp16 pool; circuit-break quantized traffic |
| Tier 2 | int8 (production); int4 in short canaries if quality passes | 8 | standard KV TTLs | Fallback to int8 or slower fp16 variant |
| Tier 3 | int4 / aggressive mixed quantization allowed | 16 | permissive eviction | Degrade to int8 or enqueue to best-effort queue |

Telemetry and dashboards (minimum)
- Dashboards per-model: latency P50/P95/P99 by model_variant label, batch_size heatmap, per-request token count distribution, cache-hit ratio timeseries.
- Error-budget burn panels: 1h/24h/7d burn rates, per-tenant contributors.
- Cost dashboard: GPU-seconds per 1k tokens, GPU-utilization per cluster, and forecasted monthly unit-cost delta when changing quantization.

Prometheus/Query examples
- P99 latency for model X (int8):
  sum(rate(latency_histogram_bucket{model="model-x", variant="int8", le="0.99"}[5m]))
- Token GPU walltime per 1k tokens (approx):
  sum(rate(gpu_walltime_seconds_total{model=~"model-.*"}[1m])) / (sum(rate(request_tokens_total[1m])) / 1000)

Alerting thresholds (examples)
- Alert: quantized-p99-exceed: triggers when P99 for a quantized variant exceeds permitted SLO by >20% for 5m.
- Alert: quantized-quality-regression: triggers when eval job on canary shows >2% degradation on critical prompt set.
- Alert: quantized-cost-anomaly: triggers when cost delta vs baseline >30% in 6h window.

Operational procedure: enabling a quantized profile (canary -> ramp -> audit)
1) Pre-checks (done by eng-serving-runtime + SRE):
   - Confirm quantization profile is uploaded and listed in model catalog (profile id, quant bits, kernel flags).
   - Ensure canary MLP has traffic shadowing enabled and telemetry ingestion for variant label.
   - Produce offline quality evaluation on the model's critical prompt sets. Quality pass required for production ramp.
2) Canary stage (0.5% traffic, 2h minimum):
   - Enable profile for a specific route with traffic weight 0.5%.
   - Verify P50/P95/P99 and quality metrics remain within SLO-band for Tier.
   - Check cost delta estimate on running traffic (projected GPU-seconds saved).
3) Gradual ramp (0.5% -> 5% -> 25% -> 50%):
   - At each step: 30m steady-state minimum, review P99 and error budget, run automated quality sampling (1000 senarios).
   - If an alert fires at any step, immediately step down to previous stable weight and open an incident review.
4) Full roll (>=75%):
   - Only after 24h of stable performance at >=50% and sign-off from product SLO owner.

Rollback and emergency mitigation
- If any of the following are observed: sustained P99 exceedance >20% over SLO for 10m, quality regression flagged by evals, or error-budget burn spikes, then perform the following: 
  1) Trigger traffic-weight decrease to 0% for the quantized variant (automated via rollout manager).
  2) If traffic cannot be shifted quickly (backend constraint), enable rate-limiter at gateway to reduce QPS for affected routes.
  3) If rollback causes capacity shortage (more GPU load than expected), escalate to capacity team to activate burst-reserved pool or notify customers per SLA.

Capacity planning heuristics when adopting quantized serving
- Baseline capacity model should include two working scenarios: 
  A) Reduced-cost steady-state (quantized enabled): calculate expected GPU-seconds reduction and adjust reserved capacity commitments conservatively by 60% of the estimated savings (leave 40% slack).
  B) Failure/rollback mode: assume full traffic routed back to fp16; maintain a capacity buffer equal to the differential GPU-seconds for peak 99th percentile traffic for 1h.
- Schedule a capacity rehearsal: simulate traffic returning to fp16 for 30 minutes during a low-traffic window monthly for the first 3 months after major rollouts.

Incident review guidance specific to quantized regressions
- Required evidence for a post-incident analysis: request ids (sampled), per-request variant and batch_size, GPU utilization and walltime for affected traces, KV-cache hit rates, evaluation prompt-run logs comparing normal vs quantized outputs.
- Triage checklist: 
  1) Did the incident begin after a quantization rollout or autoscaler change?
  2) Is the failure a latency tail, correctness regression, or degraded availability?
  3) Correlate the incident window with model_variant label, batch_size, and host kernel versions.
  4) Capture a rand-100 sample of requests spanning cold/hot sequences to replay in the perf-lab.

Automation and operational tooling recipes
- Minimal CLI examples (hypothetical)
  * Enable canary: redwood-rollout apply --model model-x --variant int8 --weight 0.005 --route chat.generate --note "canary int8"
  * Query P99: redwood-metrics query "p99(latency{model=\"model-x\",variant=\"int8\"})"
  * Force rollback: redwood-rollout set-weight --id <rollout-id> --weight 0.0 --urgent
- Observability instrumentation: ensure span/resource tags include model.variant, quant_profile_id, kernel_version, batch_size. Add lightweight sampling for full request payloads for the runbook's evidence collection (rotate retention policy to 7d for on-call review).

Testing and validation playbook
- Offline regression: run the canonical prompt set at n=10k examples comparing fp16 vs quantized variant. Acceptable thresholds are model-dependent but baseline: perplexity delta < 1.5% and critical-prompt accuracy delta < 1%.
- Perf profiling: run synthetic ramps with batch-size envelope from 1–max_batch and measure P99 and GPU-seconds. Feed results into the cost estimator to produce forecasted monthly savings.

Runbook examples and checklist (quick reference)
1) Before enabling: quality pass, telemetry flagged, notification to stakeholders.
2) Canary: 0.5% traffic, 2h minimum, monitoring on-call.
3) Ramp steps: 0.5% -> 5% -> 25% -> 50% -> 75% (sign-offs at 50% and 75%).
4) Post-roll: schedule capacity rehearsal within 72h.
5) If rollback: collect evidence bucket and open post-incident review within 48h.

Post-incident review template items
- Incident summary (what changed, when)
- Timeline of traffic weights and SLO breaches
- Root cause hypothesis (e.g., kernel mismatch for int8 GEMM on A100 driver X.Y)
- Remediation and long-term action items (e.g., require perf-bench signatures for new quant kernels)
- Cost impact analysis (savings vs. rollback cost)

Appendix B: Quick decision checklist for product managers
- Is the expected cost savings >10% for the tenant's forecasted usage?
- Can we accept a temporary quality delta at or below the pre-agreed threshold?
- Is there capacity slack to absorb a rollback to fp16 without violating SLOs?
