Tenant data redaction and privacy verification runbook

Summary:
This runbook defines the operational process for verifying tenant data privacy and performing content redaction for Redwood Dedicated and Private deployments. It is intended for customer success engineers (CSEs), on-call support (Tier 2/3), and SREs responsible for tenant onboarding or remediation after a data exposure event. The goal is to provide repeatable, auditable steps to detect, redact, verify redaction, and produce evidence for customers and internal compliance teams.

Scope and applicability:
- Applies to: Dedicated tenants, Private (VPC/on-prem) deployments, and customer-supplied S3/FTP data sources connected to Redwood ingestion pipelines.
- Does NOT replace: Legal escalation, incident response (see security incident runbook), or full data-erasure certification for decommissioning.
- When to use: suspected exposure of PII, customer request for emergency redaction, detection from telemetry indicating sensitive token leakage, or audit-triggered verification.

Pre-remediation checklist (perform before any destructive redaction):
1) Confirm scope: tenant_id, dataset(s), date ranges, ingestion paths.
2) Snapshot evidence: collect sample hits, query results, and save logs to secure bucket (retain per compliance).
3) Create a remediation ticket in Zendesk and link to internal incident channel.
4) Schedule a maintenance window if live customer traffic might be impacted.

Required information table (for ticket creation):
| Field | Expected value | Example |
|-------|----------------|---------|
| Tenant ID | Redwood tenant GUID | tenant-3f2a1c |
| Source type | ingestion / webhook / s3 / manual | s3 |
| Affected datasets | index name / table / bucket path | embeddings-prod/2026-07/* |
| Time range | ISO timestamps | 2026-07-30T00:00:00Z–2026-07-31T23:59:59Z |
| PII types suspected | email / ssn / card / key | email, aws_access_key |

Detection and triage steps (ordered):
1. Run targeted queries on the ingestion index using the tenant_id and time range. Example CLI:
   redwoodctl search --index embeddings-prod --tenant tenant-3f2a1c --query "contains_email:true" --from 2026-07-30 --to 2026-07-31
2. If matches found, capture a hashed sample (SHA256 of the content) and save to secure evidence bucket with access restricted to "tenant-safety" and "security-compliance" roles.
3. Cross-reference model-call traces and request payloads to identify whether the PII was used in embeddings generation, prompt storage, or persisted logs.
4. Classify exposure severity (low/medium/high) using the table below:
   - Low: single non-sensitive email, non-identifiable metadata.
   - Medium: multiple emails, names tied to identifiers, partial SSN.
   - High: full SSN, card numbers, keys, or any confirmed exfiltration to external endpoints.

Redaction strategy (choose one, document chosen option in ticket):
- In-place redaction (preferred when index supports field-level deletion): redact fields and reindex sanitized records.
- Backfill & reindex (preferred for embedding indexes): remove affected documents and trigger a reingest from source after sanitization.
- Token replacement (emergency mask): replace sensitive tokens with stable pseudonyms (e.g., <REDACTED_EMAIL_1>) when immediate availability must be maintained.

Redaction commands and examples:
- Field-level delete (Elasticsearch example):
  curl -X POST "https://es.prod/redwood-index/_delete_by_query" -H 'Content-Type: application/json' -d '{"query": {"bool": {"must": [{"term": {"tenant_id": "tenant-3f2a1c"}}, {"term": {"contains_email": true}}, {"range": {"@timestamp": {"gte": "2026-07-30","lte": "2026-07-31"}}}]}}}'

- Embeddings index removal + reingest pattern (S3 source):
  1) Mark objects in S3 with metadata tag redaction-pending=true using aws cli
  aws s3api put-object-tagging --bucket customer-bucket --key path/to/object --tagging 'TagSet=[{Key=redaction-pending,Value=true}]'
  2) Run redwoodctl reingest --source s3://customer-bucket/path --tenant tenant-3f2a1c --filter-tag redaction-pending=true

Verification and proof generation:
1) After redaction, rerun the original detection queries and save zero-match screenshots/CLI output into the ticket.
2) Produce an evidence bundle (zip) that includes: query outputs, redaction commands run (with timestamps), reingest job IDs, and access-control audit logs.
3) Create an audit note in the tenant record: who performed redaction, justification, and links to evidence.

Automated verification jobs (recommended):
- Nightly PII sweep for high-risk tenants (cron job): runs yara-like patterns against ingested text and flags matches.
- Weekly sample rehydrate and diff: rehydrate a 1% random sample of embeddings and check for PII via NER model.
- Alerts: create PagerDuty for >3 distinct PII matches in 24h from same tenant.

SLOs and thresholds:
- Triage SLA: acknowledge within 60 minutes for suspected PII exposures (business hours), 4 hours outside business hours.
- Containment SLA: implement initial redaction plan within 8 hours for medium, 4 hours for high.
- Verification SLA: provide evidence packet to customer within 48 hours for medium, 24 hours for high.

Customer communication templates (summary):
- Initial notification: brief description, mitigation steps in progress, expected time-to-update.
- Post-verification: summary of actions taken, evidence bundle link, recommended follow-ups, security contact.
(Templates stored in: /confluence/customer-success-and-support/templates/privacy-notifications)

Audit logging, retention, and compliance notes:
- Store redaction evidence in the encrypted evidence bucket (retention 365 days by default) and add a retention override only with Security approval.
- Record all redaction commands and job IDs in the tenant audit trail.
- For regulated customers (PCI/PHI), require Security & Legal sign-off before communicating externally.

Rollback and accidental-redaction recovery:
1) If accidental over-redaction occurs, restore from index snapshot created before redaction.
2) Steps: request SRE snapshot-restore, validate restored documents in a staging tenant, then reapply correct redaction script.
3) Document root cause and add a prevention checklist to the ticket.

Post-incident review (within 7 days):
- Participants: CSE owner, Security, SRE, Product (if needed).
- Deliverables: RCA, updated detection rules, change to onboarding checklists, communication lessons learned.
