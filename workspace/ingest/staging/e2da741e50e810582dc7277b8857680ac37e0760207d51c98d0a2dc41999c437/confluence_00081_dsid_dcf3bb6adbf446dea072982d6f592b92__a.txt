Authorization Audit Handoff and Retention Guideline

Overview

Purpose: This guideline defines how authorization and authentication telemetry is captured, correlated with audit logs, packaged for compliance evidence, and retained according to data‑residency constraints. It codifies the operational handoff from runtime services to the incident response and compliance teams and specifies SLOs, query patterns, packaging templates, and an exception workflow for retention/escrow scenarios.

Audience: Security engineers, SREs, compliance, legal, platform engineers, and oncall responders.

Scope

- Systems: Redwood API gateway (redwood-gw), authn/authz service (authz-v2), audit-streamer (auditq), evidence-orchestrator (evidence-orch).
- Events in scope: authn successes/failures, authorization decisions (allow/deny/fallback), token issuance/refresh, role changes, entitlement bindings, delegation events, service-to-service assertions.
- Not covered: application-level business events (handled by product teams) unless they carry authorization metadata.

Objectives

1. Ensure every authorization decision relevant to customer data access has: timestamp, actor, subject, resource, decision, reason, correlation_id, and residency tag.
2. Provide a standardized evidence package usable for audits and legal requests (schema + query + signed bundle).
3. Define maximums for evidence packaging and delivery under incident scenarios.
4. Minimize cross‑region transfer of retention copies unless explicitly approved.

Key Roles and Responsibilities

- AuthN/AuthZ Service Owner (authn-owner@redwood.internal): maintain decision schema, integration with auditq.
- Audit Platform (audit-platform@redwood.internal): ensure auditq retention lifecycle and immutability.
- Evidence Custodian (evidence-custodians@redwood.internal): packaging, signing, delivery to auditors/legal.
- Incident Commander (oncall rotation): trigger evidence packaging during incidents.
- Compliance Reviewer (compliance@redwood.internal): approves retention exceptions and cross-border transfers.

Event schema (summary)

Below is the canonical event contract that authz-v2 must emit to auditq. All fields are required unless marked optional. Services must version events using schema_version.

| Field | Type | Example | Notes |
|-------|------|---------|-------|
| schema_version | string | "authz.v2" | increment on incompatible changes |
| timestamp_utc | string | "2026-02-01T12:04:23Z" | RFC3339 |
| correlation_id | string | "req-7f8a3" | ties to request trace |
| actor_principal | string | "user:alice@example.com" | user or service id |
| actor_role | string | "platform-admin" | optional but recommended |
| subject_resource | string | "customer:acct-12345:dataset-logs" | resource identifier |
| action | string | "readTokens" | API action or permission name |
| decision | string | "allow|deny|fallback" | include denial reason if deny |
| reason | string | "policy:deny-cross-region" | human and machine readable |
| residency_tag | string | "eu-north-1" | region or residency boundary |
| token_id | string | "tok-9c3" | optional for token ops |
| changed_by | string | "service:role-manager-v1" | for role changes |

Retention mapping and residency constraints

- Default authz telemetry retention: 365 days in the originating residency.
- High‑sensitivity events (privileged role grants, cross‑region data access, export operations): 7 years with archival in customer residency when required.
- Short‑lived telemetry (sampling traces, debug-level allow logs): 30 days unless flagged by an incident.
- Export policy: copies for legal/audit requests may be packaged and exported to requestor region only after written approval by Compliance Reviewer.

Table: retention summary

| Event class | Retention (orig residency) | Archive copy | Export allowed | Notes |
|-------------|----------------------------|--------------|---------------|-------|
| Decision (all) | 365d | No | no (w/out approval) | default |
| Privileged bindings | 7y | Yes (cold) | Yes (approval) | includes recorded justification |
| Cross-region access | 7y | Yes | Conditional | flagged for follow-up |
| Token issuance | 365d | No | no | token_id present |
| Debug/sampled | 30d | No | no | sampling metadata present |

Packaging and evidence bundle specification

When an evidence request is raised (incident, legal, audit), evidence-orch builds a signed bundle. Bundle contents and convention:

- bundle.json (manifest) — JSON list of included queries, time windows, schema_version used, signature metadata.
- events.ndjson — line-delimited events matching schema_version with SHA256 checksums.
- query.log — sanitized queries used to extract events.
- access-log.tar.gz — redwood-gw request logs for the same window (if requested).
- signature.sig — PGP signature of bundle.json and SHA256 of events.ndjson.

SLOs for packaging/delivery

- Routine audit package: <= 72 hours from request to delivery.
- Incident emergency package (severity P0/P1): <= 4 hours (target) to provide initial bundle subset (last 24 hours).
- Legal holds: evidence must be preserved immediately and a manifest produced within 2 hours of hold creation.

Incident handoff procedure (stepwise)

1. Incident Commander raises evidence request in incident channel and tags evidence-orch. Include: window (UTC), business owner, reason, residency constraints.
2. AuthN/AuthZ owner confirms correlation_id list and identifies impacted services.
3. Audit Platform runs the canonical extraction queries (see section: query patterns) and streams to a holding bucket in the originating residency (immutable storage class).
4. Evidence Custodian composes a bundle, signs it using Redwood evidence key (KMS path: projects/redwood/keys/evidence-prod), and uploads to secure artifact store.
5. If export is required, Compliance Reviewer must approve via the exception flow (see below) and a cross‑region transfer job is kicked with logging and TTL.
6. Delivery: internal stakeholders receive a signed URL valid for 7 days. External auditors/legal receive packages via secure SFTP with two-step verification.

Query patterns and examples

Common extraction patterns (examples use the internal querycli against auditq):

- By correlation id:
  - querycli run --source auditq --filter "correlation_id='req-7f8a3'" --window "2026-02-01T12:00:00Z/2026-02-01T12:10:00Z" --out events.ndjson

- By principal across window:
  - querycli run --source auditq --filter "actor_principal='user:alice@example.com'" --window "2025-12-01T00:00:00Z/2026-02-15T00:00:00Z" --out alice-events.ndjson

- Privileged role changes:
  - querycli run --source auditq --filter "changed_by IS NOT NULL AND actor_role LIKE '%admin%'" --window "-30d" --out privileged-changes.ndjson

Packaging example (bash):

  mkdir evidence-req-12345 && mv *.ndjson evidence-req-12345/
  echo '{"request_id":"req-12345","schema_version":"authz.v2","window":"2026-02-01T12:00:00Z/2026-02-02T12:00:00Z"}' > evidence-req-12345/bundle.json
  tar czf evidence-req-12345.tar.gz evidence-req-12345 && gpg --sign --output evidence-req-12345.tar.gz.sig evidence-req-12345.tar.gz

SDLC integration and pre-release checks

- Any change to authz-v2 or auditq ingestion path must include:
  1) an ADR describing schema changes,
  2) automated contract tests that run in CI verifying new fields are emitted,
  3) a migration plan for stored events (if schema incompatible).

- CI gates:
  - contract-tests: must pass on every PR to authz-v2.
  - retention-policy-mock: changes to retention defaults must have a signed exception or be blocked.

Exception workflow (temporary retention change / cross-border export)

1. Requestor opens an exception in the governance tracker with justification, scope, duration, and export targets.
2. Security reviews technical feasibility and impact (24h); Compliance makes policy decision (48h).
3. If approved, Evidence Custodian prepares a restricted export job that logs transfer metadata and sets a TTL.

Risk considerations and mitigations

- Risk: Over-retaining low-value telemetry increases exposure.
  - Mitigation: automated retention sweeps and quarterly retention reviews by data-residency team.
- Risk: Unsanctioned cross-region evidence copy.
  - Mitigation: export jobs require two approvers (Security + Compliance) and audit-platform enforces approval tokens.
- Risk: Incomplete correlation between gateway logs and authz decisions.
  - Mitigation: mandate propagation of correlation_id in gateway (redwood-gw) and instrument client SDKs to include it.

Operational runbook snippets

- Validate bundle integrity after packaging:
  - sha256sum events.ndjson > events.sha256
  - gpg --verify signature.sig bundle.json

- Emergency evidence request template (incident commander):
  - Request ID: req-
  - Owner: team name + pager
  - Window: ISO interval
  - Residency constraints: yes/no + regions
  - Priority: P0|P1|P2

Audit and monitoring signals

- Metrics to monitor:
  - authz-event-drop-rate <= 0.1% (per region)
  - evidence-packaging-latency p95 <= 6h (routine), p95 <= 30m (emergency subset)
  - export-approval-latency <= 48h

- Alerts:
  - authz-event-drop-rate > 0.5% -> pager to authn-owner
  - packaging-latency (emergency) > 4h -> notify oncall + evidence-custodian

Appendix A — Sample minimal extraction queries

- Get all denies for resource pattern:
  - SELECT * FROM auditq WHERE decision='deny' AND subject_resource LIKE 'customer:acct-%:dataset-%' AND timestamp_utc BETWEEN '2026-01-01T00:00:00Z' AND '2026-02-01T00:00:00Z';

- Map token_id to principal for a specific window:
  - SELECT token_id, actor_principal, timestamp_utc FROM auditq WHERE token_id IS NOT NULL AND timestamp_utc BETWEEN '2026-02-10T00:00:00Z' AND '2026-02-12T00:00:00Z';
