Token Efficiency Regulator and Prefetch Runbook

Overview:

This runbook defines the Token Efficiency Regulator (TER) operational pattern and the Prefetch/Seeding subsystem used to stabilize per-token costs, reduce bursty KV-cache miss storms, and preserve tail latency SLOs for inference workloads. It combines IaC patterns, CI/CD rollout rules, and on-call runbook steps for incidents where token cost or tail latency exceed tolerances.

Intended audience:
- SREs on inference-oncall
- Infra engineers responsible for GPU pools and caching
- Runtime/serving engineers who implement batching and prefetch hooks
- FinOps engineers tracking token billing anomalies

Goals:
- Keep 99th-percentile token latency < 250ms for interactive routes (configurable).
- Bound per-token cost variance to +/- 10% week-over-week for major tenant classes.
- Prevent KV cache miss storms that cause >20% CPU/GPU overhead or increase egress.
- Provide deterministic fallback behaviors to maintain availability during capacity constraints.

Scope and non-goals:
- Scope: Redwood inference hosted and dedicated deployments; applies to Private deployments with minor config changes.
- Non-goals: This runbook does not specify model-architecture tuning (handled by model-onboarding team) or embedding batching heuristics (handled by embedding-svc docs).

Key concepts and glossary:
- Token Efficiency Regulator (TER): a control plane component that adjusts per-route token pacing, prefetch aggressiveness, and batch formation thresholds based on telemetry signals.
- Prefetch/Seeding subsystem: proactive KV-cache seeding for hot prefixes and model KV warmups for scheduled traffic (e.g., opening a session).
- Burst credit: short-lived allowance to temporarily raise batching or CPU limits for a tenant during peak.
- Cold-miss storm: high volume of requests hitting uncached KV prefixes within a short window.

SLOs and thresholds (operational knobs):
- Interactive routes (tier=interactive): p99 token latency <= 250ms; alert if p99 > 325ms for 5m.
- Batch routes (tier=batch): p95 latency <= 2s; alert if p95 > 3s for 10m.
- Token cost drift: alert when 24h rolling avg per-token cost > 15% change vs 7-day baseline.
- Cache miss rate: alert when aggregate prefix miss rate > 8% for 2m or when a single prefix accounts for >40% of misses.

Monitoring and dashboards:
- Dashboard tiles required: p50/p95/p99 token latency by route, per-route token-per-request, cache hit ratio, KV read ops/sec, GPU utilization, per-tenant token cost distribution.
- Alerts: create SLO-driven alerts in Prometheus/Alertmanager and route to inference-oncall. Example alert expr: (sum by(route) (increase(kv_cache_misses[2m])) / sum by(route) (increase(kv_cache_reads[2m]))) > 0.08

Preflight checks (run before a rollout that touches TER or prefetch behavior):
1) CI verification: run unit and integration tests for TER control logic and canary harness.
2) Canary workload: deploy to a single low-risk region with synthetic traffic matching the production token-distribution.
3) Load sweep: run a token-cost sensitivity sweep (0.1x, 0.5x, 1x, 2x) and validate that p99 latency and cache hit ratios remain within thresholds.
4) Telemetry sanity: ensure the new metrics (prefetch_backpressure, ter_decision_count) are emitted and consumed by dashboards.

Terraform / IaC pattern (example):
- The TER has two IaC artifacts: a feature-flagged config (Terraform) and a canary deployment (k8s manifest) with a traffic shadow.
- Config example (Terraform variables):

```
variable "prefetch_enabled" { type = bool default = true }
variable "prefetch_max_concurrency" { type = number default = 32 }
variable "prefetch_ttl_seconds" { type = number default = 300 }
```

- Recommended module layout:
  - modules/ter/config.tf (feature flags + constraints)
  - modules/ter/policy.yaml (policy map for tenant classes)
  - modules/ter/ci_canary_pipeline.tf (integrates with buildkite and promote workflow)

Traffic shaping and CI/CD rules:
- CI pipeline must include a safety gate job that runs a 30-minute synthetic session workload and asserts: p99 < threshold and cache hit ratio delta < 2%.
- Promotion to prod requires: two successful canary windows separated by at least 15 minutes, signoff from runtime or infra-sre reviewer, and a feature-flag toggle to allow rollback.

Runbook: Incident response flows
1) Symptom: sudden p99 token latency spike for interactive routes (>325ms)
   - Immediate check: use the latency dashboard to determine if spike is global or single-region.
   - If single-region and GPU utilization > 85%: run 'ter scale' (see commands) to increase hot-pool size.
   - If miss rate increased > 8%: inspect top 10 prefixes with highest misses. If a single tenant/prefix responsible, temporarily throttle that tenant via tenant-rate-limiter and open ticket to tenant-owner.

2) Symptom: per-token cost jump (>15% vs baseline)
   - Check query complexity and model version rollouts (release-notes). Verify no recent model-promotes.
   - If caused by increased KV reads: reduce prefetch aggressiveness (decrement prefetch_max_concurrency by 30%) and enable conservative burst-credit policy.
   - If unexplained, switch affected routes to a cheaper quantized model variant via smart-routing fallback.

3) Symptom: KV-cache cold-miss storm
   - Identify time window and compute cold prefixes: query 'kv_miss_top_prefixes' metric.
   - Kick prefetch seeding job for top prefixes: run prefetch-job CLI (see below) with immediate=true for top-20 prefixes.
   - If prefetch jobs fail due to API throttling, reduce batch size and stagger jobs by 30s.

Command references (CLI examples):
- Scale TER hot pool (region):
  - terctl scale --region us-west-2 --pool hot --delta 4
- Prefetch seeding job (one-off):
  - terctl prefetch --prefixes file://hot-prefixes.json --ttl 600 --concurrency 16 --immediate
- Inspect top miss prefixes:
  - promql: topk(10, sum by(prefix) (increase(kv_cache_misses[10m])))

Safe rollback checklist (if TER changes regress cost or latency):
1) Flip feature flag: terraform apply with prefetch_enabled=false (dry-run first).
2) Gradually scale down canary and rollback images to previous stable tag.
3) Re-run the CI synthetic test, validate telemetry.
4) Postmortem owner and timeline: runtime-team assigned within 24h.

Operational playbook for scheduled warmups (daily business hours):
- Schedule: 15m before the start of major tenant traffic windows (configurable per tenant).
- Job: prefetch-seed-top-100-prefixes --ttl 900 --stagger 5s --concurrency 8
- Verification: check KV read rates and hit ratio improvement within 3 minutes.

Cost accountability and FinOps signals:
- Each TER decision includes a cost-annotation tag (ter_decision_cost_estimate) used by billing pipelines.
- FinOps SLO: per-tenant variance dashboard and weekly token burn report. Any > 20% spike triggers a review.

Post-incident retrospective and changelog requirements:
- For any incident that triggers oncall paging, create a short incident summary in /confluence/eng-infra/runbooks/incidents with: timeline, root cause, mitigations, and three action items (owner + due date).
- Changelog: update modules/ter/policy.yaml and add release note with the exact terraform diff and the canary window timestamps.
