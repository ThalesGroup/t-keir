Per‑Tenant Fidelity Credit Framework

Summary:\n\nThis design document defines the Per‑Tenant Fidelity Credit Framework: a pricing and metering model that (a) lets customers allocate discrete credit budgets per tenant or route, (b) maps fidelity and service characteristics to credit multipliers, and (c) interoperates with Reserved/Dedicated contracts and Hosted usage billing. The goal is to enable predictable unit economics for customers and flexible monetization levers for Redwood while preserving per‑tenant SLO alignment.\n\nBackground and motivation:\n\n- Customers asked for deterministic cost controls when they run mixed workloads across routes with different fidelity needs (e.g., low‑latency chat vs. long‑form summarization).\n- Current per‑token pricing is precise but opaque when fidelity (sampling/top‑k, temperature, model variant, quantization) and routing policies change on requests.\n- The fidelity credit model abstracts those variables into a compact unit (credits) that is easier to allocate, forecast, and link to contractual commitments.\n\nObjectives:\n\n1. Provide a stable, predictable credit unit that represents a normalized compute/quality cost for inference operations.\n2. Allow tenants to reserve, allocate, and top up credits per route or application in the Console and via API.\n3. Keep per‑token transparency available for troubleshooting and billing reconciliation.\n4. Support Reserved (Dedicated) commitments, Hosted pay‑as‑you‑go, and Private billing integrations.\n\nKey definitions:\n\n- Credit: the smallest billing unit in this framework. One credit represents a baseline compute/quality unit defined by Named Baseline (see below).\n- Named Baseline: a canonical operation used to normalize costs (e.g., 1k tokens of short-chat generation on Redwood‑standard variant with standard sampling settings).\n- Fidelity Profile: named tier that adjusts credit multiplier (Low, Standard, High, Premium).\n- Route Budget: an allocation of credits assigned to a specific API route or tenant.\n\nFidelity tiers and multipliers (design proposal):\n\n- Low (batch/low‑latency trimmed): multiplier = 0.6x baseline\n- Standard (default): multiplier = 1.0x baseline\n- High (higher quality, larger context windows): multiplier = 1.8x baseline\n- Premium (safety checks, tool execution, long contexts, ensemble variants): multiplier = 3.5x baseline\n\nNote: multipliers are configurable per release window and are subject to quarterly economics reviews. They represent an abstraction of model compute, KV cache pressure, and runtime optimizations.\n\nCredit accounting and mapping rules: \n\n- Billing flow for a single request: 1) determine Named Baseline for the selected model+variant+request shape; 2) apply fidelity multiplier for the active Fidelity Profile; 3) compute credits_consumed = baseline_credits * multiplier; 4) report both credits_consumed and raw tokens/compute details to usage logs for reconciliation.\n- If runtime fallback to a lower‑fidelity compatible variant occurs, we bill at the fidelity actually executed and emit an event that triggered the fallback.\n- Reserved capacity customers may pre‑commit to credit bundles at discounted rates; these bundles are consumed before pay‑as‑you‑go credits.\n\nNamed Baselines (examples):\n\n- Chat‑short‑1k: 1 baseline credit = 1 credit for up to 1k tokens across request+response on Redwood‑standard small variant.\n- Summarize‑long‑4k: baseline = 4 credits for 4k combined tokens on Redwood‑high variant.\n- Embedding‑1k: baseline = 0.2 credits per 1k embedding units.\n\n(Engineering will maintain a canonical baseline table in runtime so mapping is deterministic; the Console displays the current baseline mapping.)\n\nPricing constructs and customer packaging:\n\n- Pay‑as‑you‑go: customers are charged per credit at the published per‑credit rate. The Console shows both credits consumed and equivalent per‑token breakdown for transparency.\n- Commitment bundles: 3, 12, 36‑month bundles sold as credit packs with volume discounts. Bundles can be tenant‑scoped or company‑wide.\n- Cross‑tenant transfer rules: credits are owned by contract; tenant admins may reassign credits subject to policy and audit trail.\n\nExamples (illustrative):\n\nScenario A — Interactive chat route (Standard):\n- Named Baseline: chat‑short‑1k = 1 credit baseline\n- Fidelity: Standard (1.0x)\n- Request uses 450 tokens -> credits_consumed = 1 * 1.0 = 1 credit\n- Console shows: 1 credit (equivalent tokens: 450), raw cost estimate $0.015 (for reconciliation)\n\nScenario B — Long‑form analysis (High):\n- Named Baseline: summarize‑long‑4k = 4 credits baseline\n- Fidelity: High (1.8x)\n- Typical request uses 3.2k tokens -> credits_consumed = 4 * 1.8 = 7.2 -> rounded to nearest 0.1 credit -> 7.2 credits\n\nBilling and invoicing implications:\n\n- Invoice items will list credit bundles consumed with effective per‑credit unit price and a reconciliation appendix mapping to token or GPU‑second estimates for audits.\n- For enterprises, an API to export raw per‑request token and fidelity metadata will be available for accounting reconciliation.\n\nConsole and API UX changes (high level):\n\n- Console: \"Credits\" panel under Billing, per‑route budget editor, warnings when route budget < 10% of daily burn rate.\n- API: endpoints for allocate_credits(tenant_id, route_id, credits), estimate_credits(model, tokens, fidelity_profile), and usage_stream with credits_consumed and raw token counts.\n\nImplementation details and runtime contract:\n\n- Runtime exposes a deterministic baseline mapping service that the serving layer queries when calculating credits for a request. The mapping service returns: baseline_name, baseline_value, and recommended fidelity multipliers.\n- All credit calculations happen at the edge routing layer to avoid post‑hoc reconciliation surprises. Events and metrics written to Kafka topic redwood.billing.credits with schema versioning.\n\nMigration plan for existing customers:\n\n1. Phase 0 (experimental, opt‑in): enable credit estimation in Console and API alongside existing per‑token billing (no enforcement).\n2. Phase 1 (coexistence): allow customers to purchase credit bundles but keep per‑token billing as primary; credits consumed are shown but not charged if not purchased.\n3. Phase 2 (default for new customers): new accounts default to credit‑aware billing.\n4. Phase 3 (migrate): for consenting enterprise customers, perform a migration analysis and optional swap where credits replace per‑token billing with negotiated bundle discounts.\n\nRollout milestones and ownering:\n\n- Product owner: Ananya Rao (Product Pricing Lead)\n- Engineering owner: Diego Morales (Billing & Runtime)\n- Finance owner: Priya Nambiar\n- Target milestones:\n  - M1 (2028‑06‑15): Baseline catalog and estimation API v1\n  - M2 (2028‑07‑30): Console budget editor and real‑time usage stream\n  - M3 (2028‑09‑01): Commitment bundle purchase flow and invoicing support\n  - M4 (2028‑10‑15): Enterprise migrations and audit export API\n\nSLOs, metrics, and reporting:\n\n- Accuracy SLO: >99.9% of credit calculations must match post‑process reconciliation within 0.5% per day (metric: credits_discrepancy_rate).\n- Latency SLO: baseline lookup and credit calc must add <2ms p50 at edge.\n- Product metrics: credit adoption rate, average credits per route, churn correlation with credit pricing.\n\nRisk assessment and mitigations:\n\n- Risk: Customers feel double‑billed if per‑token and credit numbers diverge.\n  - Mitigation: Ensure Console shows both numbers and include a reconciliation API; run customer education and an opt‑in migration.\n- Risk: Complexity in Reserved contract integration.\n  - Mitigation: Finance and Sales to own template contract language; provide contract mapping tooling for discounts and amortization.\n\nOpen questions for exec review:\n\n- Should fidelity multipliers be public in product docs or only surfaced to billed customers?\n- What ceiling discounts to allow for multi‑year Reserved bundles without undermining per‑unit economics?\n\nAppendices:\n\n- Implementation snippets (estimation API example):\n\n  POST /v1/credits/estimate\n  Body:\n  {\n    \"model\": \"redwood-high-2b\",\n    \"request_tokens\": 3200,\n    \"response_tokens\": 800,\n    \"fidelity_profile\": \"High\"\n  }\n\n  Response:\n  {\n    \"baseline\": \"summarize-long-4k\",\n    \"baseline_value\": \"4.0\",\n    \"multiplier\": \"1.8\",\n    \"credits_estimate\": \"7.2\",\n    \"token_equivalent\": \"4000\"\n  }\n\n- Recommended dashboards: per‑tenant credit burn, top‑10 routes by credits, daily credits discrepancy, credit bundle inventory.\n\nDecision log and next steps:\n\n- This document is a proposal;
