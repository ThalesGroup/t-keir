Integrated Control Taxonomy and Exemption Lifecycle

Overview

This playbook defines a unified control taxonomy across RBAC, audit logging, data residency & retention, secure SDLC gates, incident-response evidence collection, and the lifecycle for risk exceptions. The goal is to make control ownership, expected evidence, and exception handling consistent and auditable across Redwood Inference deployments (hosted, dedicated, and private).

Scope

- Applies to all services and teams that operate customer-facing inference workloads, control planes, and observability pipelines.
- Covers preventative controls (RBAC, gated releases), detective controls (audit streams, alerts), and compensating controls used when short-lived exceptions are granted.

Definitions

- Control: A specific security or compliance requirement (e.g., "Authorization decision logging").
- Evidence bundle: Packaged artifacts used to prove a control was operating (logs, screenshots, attestations, config snapshots).
- Exception: An approved, time-bound deviation from a control or requirement.

Principles

1. Single source of truth: Every control is mapped to an owner, control-id, expected evidence types, and a review cadence.
2. Least privilege baseline: Default system roles are narrowly scoped and require explicit justification for widening.
3. Time-bound exceptions: Exceptions must include mitigation, acceptance criteria, and an expiration date.
4. Auditability: Every exception and control change must produce an immutable record that can be assembled into an evidence bundle for auditors.

RBAC baseline and evidence requirements

- Baseline roles (applies to hosted, dedicated, private):
  - viewer: read-only access to dashboards and non-sensitive metrics. Evidence: role assignment records, last-change diff.
  - operator: runbooks, restart/scale, non-privileged routing changes. Evidence: assignment audit trail, JIT activation logs.
  - platform-admin: deploy builds, manage model artifacts, secret rotation. Evidence: multi-approver change record, credential issuance logs.

RBAC review cadence and automation

1. Monthly entitlement exports produced by IAM service and deposited to secure evidence bucket.
2. Automated drift detection: compare current role bindings to the baseline; generate anomalies.
3. Quarterly manual certification: team leads attest to required roles and approve or request removals.

Audit logging: schema, retention, and evidence packaging

- Minimum logged events (all services): authn events, authz decisions (allow/deny and policy reason), administrative changes (role create/delete/attach), model deployment/rollback, evidence-handling actions (export/create/delete), and alert acknowledgements.
- Event schema (example):
  {
    "timestamp": "2026-02-14T15:04:05Z",
    "service": "inference-gateway",
    "event_type": "authz_decision",
    "principal": "svc:platform-admin:srv-42",
    "action": "model.deploy",
    "resource": "model:v1.43",
    "decision": "DENY",
    "policy_id": "policy-deploy-3",
    "request_id": "req-6f7a2c"
  }

- Retention minimums: control C-AUD-002 requires raw immutable stream retention for 90 days in hot tier, 2 years in cold storage; aggregated event indices 12 months.
- Evidence packaging: when auditors request artifacts, assemble: schema contract, representative event samples (filtered by timeframe), retention config snapshot, and ingestion metrics. Include hash manifest signed by Observability owner.

| Data type | Default residency | Minimum retention | Purge action | Owner |

Secure SDLC gates (release checklist)

For a release to progress from staging -> canary -> prod the following controls must be true: 
- C-SDLC-005 checklist satisfied:
  1. Passing unit/integration tests and security SCA scan (zero critical vulnerabilities).
  2. Signed commit metadata and verifiable author identity.
  3. Feature flags in place for quick rollback and telemetry toggles.
  4. RBAC changes included as declarative policies in the release (no manual console grants).
  5. Evidence bundle (SCA report, pipeline signature, canary metrics snapshot) stored in evidence bucket.

Incident response (security-specific steps and evidence capture)

1. Triage: capture immutable copies of relevant audit partitions (timestamped, hashed).
2. Containment: if a privileged token is suspected, enact immediate token revocation and record revocation action in the audit log.
3. Forensic snapshot: record process lists, container images, model artifacts touched, and network flows.
4. Evidence packaging: assemble incident bundle with chain-of-custody manifest, hashes, observer notes, and access-control changes.
5. Legal/compliance engagement: trigger Data Residency review if data egress is suspected.

Exception (exemption) lifecycle: procedure

1. Request: team files an Exception Request using the central form (fields: control-id, justification, compensating controls, mitigation, expected expiration date, roll-forward plan).
2. Initial review by control owner within 3 business days.
3. If risk > medium, Security Risk Committee review required; if < medium, owner may approve with mitigation.
4. Approval artifacts: signed exception record, acceptance criteria, monitoring tasks, and expiration reminder entry.
5. Automated enforcement: where possible, exception approvals inject timebound feature flags and monitoring policies (e.g., increase audit sampling to 100% for the affected scope).

Approval matrix (simplified)

| Risk level | Approver(s) | Max duration |
|---|---|---:|
| Low | Control Owner | 30 days |
| Medium | Control Owner + Security Manager | 90 days |
| High | Security Risk Committee + Head of Product | 180 days (requires quarterly re-approval) |

Compensating controls examples (must be documented in request)

- Increase audit sampling and retention for the targeted resource.
- Isolate the resource into a temporary tenancy or constrained network ACL.
- Add automated regression/e2e checks to detect specific drift symptoms.

Evidence bundle template (minimum contents)

- control-id and exception id (if applicable)
- time-window covered by artifacts
- hashed archives: role-dump.zip (roles YAML), audit-sample.jsonl (filtered), retention-config.yaml, release-signature.txt
- attestation: named approvers and timestamps (SAML assertion or signed ticket)
- verification checklist and manifest with SHA256 hashes

Operationalizing and automation priorities

- Priority 1: automated entitlement exports and drift alerts (monthly -> daily).
- Priority 2: exception request API so approvals are machine-actionable and inject temporary mitigations.
- Priority 3: evidence bundling API to produce auditor-ready bundles on demand.

Metrics / KPIs to monitor program health

- Percentage of exceptions with compensating controls documented (target: 100%).
- Mean time to approve exception (target: <= 5 business days).
- Number of entitlement drifts detected per week (trend downward).
- Percentage of releases with complete SDLC evidence bundles (target: 100%).

Appendix B: Quick checklists

- Pre-approval checklist for exception reviewers:
  1. Verify mitigation is actionable and measurable.
  2. Ensure monitoring (alerts, dashboards) is enabled for the scope.
  3. Confirm expiration is set and automated reminder exists.
  4. Confirm evidence bucket path and manifest pattern.

- Post-incident evidence checklist for on-call:
  1. Preserve raw audit partitions (hash + store).
  2. Snapshot RBAC bindings and any policy diffs.
  3. Capture release pipeline logs and SCA artifacts.
  4. Tag evidence bundle with incident ID and legal hold flag if requested.
