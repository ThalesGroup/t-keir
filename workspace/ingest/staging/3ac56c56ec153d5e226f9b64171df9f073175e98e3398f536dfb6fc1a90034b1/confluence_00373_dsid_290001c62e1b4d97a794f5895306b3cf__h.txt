Hybrid Control-Plane Reference Architecture for Private Deployments

Overview

Purpose: This document describes a recommended reference architecture for private deployments that combine a lightweight, customer-hosted control plane (VPC or on-prem) with managed central services operated by Redwood Inference. The design balances security, low-latency local serving, and simplified day-2 operations for customers that require data residency and air-gapped options.

Scope: covers architecture patterns, on-prem packaging options, hardware profiles, day-2 operational runbook primitives, upgrade and rollback strategy, and a customer requirements checklist used during scoping. This is intended for solution engineers, SREs, and customer infrastructure teams.

High-level goals
- Provide deterministic latency for local traffic (SLO: 95th percentile < 75ms for in-VPC inference on 256-token requests).
- Maintain centralized observability and billing while ensuring customer controls over sensitive data.
- Allow safe, reversible upgrades with automated canary/rollback tooling.
- Support both Kubernetes-native and VM/systemd packaging with consistent operational primitives.

Reference architecture (hybrid control-plane)

Architectural components
1) Customer Control Plane (local) — runs in customer VPC or on-prem cluster
- redwood-local-control: API gateway and config agent (HTTPS, port 8443)
- redwood-edge-agent: inference worker manager and local KV cache
- model-store-proxy: optional pull-through cache for model artifacts (only for approved models)
- local telemetry relay: aggregates traces/metrics, forwards to central observability over TLS

2) Redwood Central Services (hosted) — managed by Redwood Inference
- onboarding API and licensing service
- model registry (metadata only; binary artifacts may be proxied)
- billing / quota system (token accounting)
- update delivery service (signed rollout artifacts)

3) Network & Security Patterns
- Private peering or AWS PrivateLink between customer VPC and Redwood control plane endpoints; fallback to mutual-TLS over public egress if peering not available.
- Mandatory mTLS for all control-plane traffic; customer controls root CA in restricted deployments.
- Minimal egress: telemetry, licensing heartbeat, and signed artifact retrieval; data plane (inference traffic) remains local unless explicitly routed.

Deployment topologies (pick one)
- Single-cluster VPC (recommended for cloud customers): Kubernetes cluster + LoadBalancer + Spawned GPU nodepool for inference.
- Multi-cluster edge (recommended for large retail/telecom): small clusters at edges serving local requests, federated to central control plane for policy/rollout.
- Air-gapped on-prem: initial artifact bundle delivered on USB or secure transfer; control plane operates fully locally with optional periodic signed manifest verification.

Packaging options
- Kubernetes Helm (primary): chart name rwd-inference-private, chart versioned with semver. Provides Helm values for: imageRepository, nodeSelector, tolerations, gpuClass, persistenceClass, and database backend.
- Containerd + systemd (edge or appliance): rwd-private-appliance.tar.gz contains systemd unit files, container images, and an installer script (./install.sh --accept-license).
- Bare-metal package: prebuilt Nix/Ansible role for managed installs in regulated facilities.

Hardware profiles (reference)
- Small (dev/test): 1x GPU T4, 8 vCPU, 32 GB RAM, 500 GB NVMe
- Medium (production): 2x A10/A100-40GB, 32 vCPU, 256 GB RAM, 2 TB NVMe
- Large (high throughput/low latency): 4x A100-80GB, 64 vCPU, 512 GB RAM, 4 TB NVMe

Storage and artifact strategy
- Models stored as immutable artifacts with hash-based names. Model download occurs to local persistent volumes in /var/lib/redwood/models.
- Recommended retention: keep last 3 model revisions on disk; older artifacts purged by policy.

SLOs and readiness
- Control plane API availability: 99.95% monthly (excluding maintenance windows)
- Local inference worker health probe: readiness within 5s; liveness should restart container if no forward progress for 30s
- Model load latency: 95th percentile < 20s for warm cache, < 120s for cold load from remote artifact store

Day-2 operations (runbook primitives)

Monitoring and alerts (baseline)
- Node GPU utilization: warn at 65%, critical at 85%
- Inference error rate (5xx): warn at 0.5%, critical at 2%
- Model load failures: immediate page to on-call if >3 failures in 10 minutes
- Telemetry heartbeat: alert if control-plane heartbeat missing for >10 minutes

Routine tasks
1) Scaling GPUs
- Kubernetes: update nodepool autoscaler config and label new GPU nodes with nodeSelector gpu=enabled. Verify pod eviction and re-scheduling with readiness probe.
- Non-K8s: add node, register with redwood-edge-agent via ./agentctl register --node-id <id>.

2) Certificate rotation (90-day cadence)
- Generate CSR using local CA or Redwood-managed CA depending on confidentiality.
- For zero-downtime rotation: deploy new cert to control-plane, wait for all agents to re-establish connections, then retire old cert.

3) Backup & restore
- Backup config DB daily (encrypted snapshot to S3-compatible endpoint).
- Test restore quarterly to a staging environment; document time-to-restore target (TTR) <= 2 hours for config DB.

Upgrade and rollback strategy

Principles
- Keep control plane and inference runtime decoupled: image compatibility matrix is required and enforced by the installer.
- All upgrade artifacts are signed by Redwood (verified by local agent).
- Provide canary and staged rollouts with automatic health gates.

Upgrade procedure (Kubernetes Helm example)
1) Prepare: ensure CI-generated release artifact is signed and in artifact registry.
2) Canary: deploy new control-plane chart to 5% of nodes or a dedicated canary namespace. Run regression evals against a smoke prompt set (automated).
3) Monitor: 30 minutes observation window with metrics: request latency, error rate, model load failures, and resource utilization.
4) Ramp: 25% -> 50% -> 100% in increments, with a minimum 15 minute observation window at each step.
5) Complete: mark release in local registry and notify Redwood central for telemetry aggregation.

Rollback procedure
1) If health gates fail during canary or ramp, initiate automated rollback: helm rollback <release> OR agentctl rollback --version <previous>.
2) If rollback fails or repeated issues occur, escalate to Redwood platform support and, if necessary, open a mitigation window (pause further rollouts globally).
3) Postmortem: collect control-plane logs, k8s events, agent heartbeats, and a core dump of the failed process where applicable. Run fail-mode simulation in staging.

Testing and QA requirements
- Mandatory: smoke evals, perf benchmark (p50/p95 latency vs baseline), and token-cost regression check.
- Optional but recommended: shadow traffic test for 24–72 hours before full cutover.

Operational ownership and escalation
- Customer infra owns cluster lifecycle, network peering, and encryption keys.
- Redwood Inference owns control-plane functional compatibility, signed artifacts, and central telemetry ingestion.
- Escalation path: on-call SRE -> Senior SRE -> Platform Eng -> Product Eng. Include contact matrix in customer onboarding doc.

Customer requirements checklist (pre-engagement)
1) Network connectivity: ability to create PrivateLink or allow outbound TLS to x.x.x.x:443 and telemetry.redwood.ai:443
2) KV and object storage: S3-compatible endpoint or permission to use Redwood-provided artifact mirror
3) Host OS and container runtime: Ubuntu 22.04, containerd 1.6+ (K8s), or supported RHEL/CentOS for air-gapped installs
4) GPU constraints: list of available GPU types and counts, NVMe scratch space per node
5) Compliance needs: required encryption at-rest algorithms, root CA controls, and required audit log retention window
6) Maintenance windows and allowed daily outage minutes for upgrades

Appendix: Example commands and snippets
- Helm install (canary namespace): helm upgrade --install rwd-control ./chart --namespace rwd-canary --set image.tag=2026.02-canary
- Agent register (systemd): sudo /opt/redwood/bin/agentctl register --server https://control.local:8443 --token-file /etc/redwood/token
- Backup config DB (example): pg_dump -Fc -h localhost -U rwd_config rwd_config > rwd_config_$(date +%F).dump
