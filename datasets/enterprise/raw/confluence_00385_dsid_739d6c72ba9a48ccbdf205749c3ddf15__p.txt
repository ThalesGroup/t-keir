Operator cheat sheet: private deployment field installations and first-24h runbook

Summary:
This operator cheat sheet is a compact, actionable runbook for field engineers and partner SREs performing private Redwood Inference deployments (VPC and on-prem). It focuses on the first 24 hours after install: preflight validations, connectivity and security checks, basic performance sanity, telemetry verification, common recovery steps, and escalation contacts. Use this as the quick reference during installs and handoff to day-2 teams; link to full deployment guides and reference architectures for detailed designs.

Scope:
- Applies to Redwood Private installations using the standard control-plane + data-plane package (airgapped and VPC gateway modes).
- Intended for operator-level activities: install verification, networking, KMS/K8s secrets validation, telemetry, and rapid rollback triggers.
- Not a substitute for full runbooks (see related pages); this document prioritizes checklist-style actions and measurable checks.

Before you arrive (preflight):
1) Confirm artifacts: signed container digests, installation manifest, license file, and customer acceptance test (CAT) bundle are present. Verify SHA256 for each artifact.
2) Confirm contact chain: primary customer admin, on-site engineer, network owner, and Redwood on-call.
3) Review expected topology: control-plane location (cloud or customer VPC), data-plane zone layout, and external ingress endpoints.

Quick reference: critical ports and endpoints (operator view)
- Control-plane API (HTTP): tcp 443 outbound to <control-plane-host> (or internal LB)
- Runtime-proxy (gRPC): tcp 9000 (pod-to-pod), tcp 15000 (external ingress for dedicated nodes)
- Metrics ingest: tcp 9080 (Prometheus pull) or 9200 (push gateway)
- KV-cache replication: tcp 6379/7000 (cluster ports) depending on configured store
- KMS/HSM control plane: tcp 443 to customer KMS endpoint (if remote)

Pre-install checklist (on-host):
- Kernel and container runtime:
  - Linux kernel >= 5.10; check with: uname -r
  - Docker/Containerd versions supported; check runtime: containerd --version or docker --version
- GPU nodes (if present):
  - NVIDIA driver version >= 525, nvidia-smi shows expected cards, CUDA libs accessible
  - Verify MIG partitioning (if used) and persistence daemon running
- Disk and storage:
  - Root partition >= 50GB free for install artifacts
  - PVs for model cache: ensure emptyDir vs localSSD allocations match the manifest
- Time sync: ntpq -p or timedatectl status (drift < 500ms)

Install verification (first 0–2 hours):
1) Pods/Services status: kubectl -n redwood get pods,svc -o wide
   - Expected: control-plane-0..2 Ready, runtime-proxy-* Running, node-agent DaemonSet Running
2) Image signature verification (sample):

   $ cosign verify --key cosign.pub redwood/runtime-proxy:2027.01.15
   $ sha256sum redwood-controlplane.tar.gz | grep <expected-sha>

3) Secrets/KMS: validate KMS policies and decrypt test token:

   $ kubectl -n redwood get secret redwood-kms-token -o yaml
   $ ./kms-decrypt-test --endpoint https://kms.example.com --token <token>

4) Network path checks: traceroutes and TLS handshake to control-plane and KMS endpoints.

Telemetry & observability (first 0–4 hours):
- Verify metrics are flowing to customer Prometheus/Redwood collector. Expected metrics and example queries: 
  - redwood_runtime_request_latencies_seconds_bucket (histogram)
  - redwood_runtime_concurrency_active_gauge
  - redwood_kvcache_hit_ratio (should be > 0.2 after warmup for typical workloads)
- Validate logs are being forwarded to configured sink (Elasticsearch/CloudWatch). Sample grep:

  $ kubectl -n redwood logs deployment/runtime-proxy | head -n 200 | grep -E "ERROR|WARN"

- Trace sampling: confirm that trace IDs from initial requests appear in the control-plane tracing UI or Jaeger instance.

Acceptance checks (first 6 hours):
1) Latency sanity: run the CAT (customer acceptance test) with the provided prompt set. Expect p50 <= declared SLA, p95 within 2x baseline for cold start.
2) Throughput: run a modest load (10–20 qps) for 10 minutes and verify no queue depth growth and no OOMs in the runtime pods.
3) Functional: run model-specific smoke tests - generation, streaming, embeddings, and function-calling probes.

SLOs and alert thresholds (operator quick list):
- Control-plane API 5xx rate: warn at 0.5% over 5m, critical at 2% over 5m
- Runtime request latency (p95): warn at SLA + 200ms, critical at SLA + 500ms
- Pod restarts: warn at 3 restarts in 15m for a single pod, critical at 10 restarts
- KV-cache miss spike: warn if miss ratio increases by > 50% vs baseline for 10m

Rapid recovery steps (first 30 minutes):
- If control-plane is unreachable:
  1) Confirm control-plane process on host (ps aux | grep redwood-control-plane).
  2) Check control-plane logs and rotate logs if I/O heavy.
  3) If restart required: kubectl -n redwood rollout restart deployment/control-plane --cascade=false (preserve nodes if running stateful workloads).
- If runtime pods OOM or crashloop:
  1) Inspect recent logs and memory usage: kubectl top pod <pod> and kubectl logs <pod> --previous
  2) If OOM due to model load, scale replica set temporarily to reduce per-node load: kubectl scale deployment/runtime-proxy --replicas=<n>
  3) If persistent, initiate model offload (see model offload playbook) or reduce max sequence length in runtime config and restart.
- If telemetry missing:
  1) Confirm metrics collector pod is Running. kubectl -n redwood get pod metrics-collector
  2) Validate network egress and LB rules to metrics sink; use tcpdump if necessary.

Rollback triggers and minimal rollback procedure:
- Triggers to consider rollback within first 6 hours:
  - High error rate: sustained 5xx > 2% for 15 minutes and root cause points to new control-plane binary or runtime image.
  - Severe performance regression: p95 > 2x baseline with no feasible configuration mitigation.
  - Data corruption indicators: KV checksum mismatches or model artifact integrity failures.

- Minimal rollback steps (fast path):
  1) Pin deployments to previous image tag recorded in release metadata (release-manifest.yaml).
  2) kubectl -n redwood set image deployment/control-plane control-plane=<previous_image_tag>
  3) kubectl -n redwood rollout status deployment/control-plane --timeout=10m
  4) Run CAT smoke tests (sanity latency + functional) and monitor SLOs for 15 minutes.
  5) If stable, document incident and continue controlled rollout.

Escalation matrix (who to call first):
- On-call private-deploy engineer (primary): +1-555-0101 — handles runtime failures and image rollouts
- Senior runtime engineer (secondary): +1-555-0107 — performance regressions and kernel/driver issues
- Security/Compliance contact: security-oncall@redwood.ai — for KMS/HSM or secret exposure concerns
- Customer success lead: customer-success@redwood.ai — for customer communications and SLA notifications

Handoff checklist to day-2 (after 24h):
- Provide condensed install log bundle (kubectl cluster-info dump, all redwood namespace logs, metrics snapshot)
- Record image digests and any configuration overrides in the release ticket
- Confirm these items are monitored by customer SRE: control-plane 5xx, runtime p95, KV-cache hit ratio, model-load error rate
- Schedule a 1-hour post-install review within 48 hours with customer and Redwood on-call to review telemetry and next steps

Appendix: useful commands and outputs
- Pod status with node allocation:

  $ kubectl -n redwood get pods -o wide

- Check GPU and driver: 

  $ nvidia-smi --query-gpu=name,index,memory.total --format=csv

- Verify Prometheus scrape targets (example):

  $ kubectl -n monitoring exec -it <prom-pod> -- curl -s localhost:9090/api/v1/targets | jq '.data.activeTargets[] | select(.labels.job=="redwood")'

- Example minimal rollback snippet (Bash):

  PREV_TAG=$(cat /opt/releases/previous_tag.txt)
  kubectl -n redwood set image deploy/control-plane control-plane=redwood/control-plane:${PREV_TAG}
  kubectl -n redwood rollout status deploy/control-plane --timeout=600s
