Zero-Trust Inference Mesh and Authorization Policy

Overview:

This document defines Redwood's zero-trust service mesh and authorization policy tailored for inference workloads. It covers authentication, per-request authorization, sidecar behavior, and operational constraints that preserve latency and throughput SLOs for model serving. The goal is to provide a repeatable, secure pattern that applies to hosted, dedicated, and private deployment modes while minimizing change to inference runtime paths.

Goals:
- Guarantee mutual authentication between edge and inference runtime with short-lived credentials.
- Enforce least-privilege per-request authorization for sensitive operations (model downloads, cache priming, admin endpoints).
- Limit auth-related latency impact on P95/P99 token generation and validation to within budget.
- Provide an auditable trail for data access tied to request metadata and tenant identifiers.

Scope:
- Applies to: edge-proxy -> gateway -> model-router -> runtime sidecar -> model process flow.
- Not in scope: developer local environments (see local-dev-auth.md), CI systems (see infra/cicd-authz).

Key constraints and rationale:
- Inference paths are latency sensitive: auth verification must not add more than 2ms median and 8ms P99 on top of baseline CPU-bound path for small requests (<=128 tokens). Where strict cryptographic checks add overhead, use a hybrid approach (local cache + async audit).
- Private deployments must support customer KMS-provisioned signing keys for identity issuance. Hosted and Dedicated deployments will use Redwood KMS and short-lived certificates.

Authentication model (workload identity):
1) Workloads obtain identities via a short-lived certificate issued by Redwood Identity Service (RIS) or customer KMS in Private mode. Certificates TTL default = 5 minutes.
2) Sidecars validate peer certificates using mTLS on all intra-cluster RPCs.
3) For cross-region/gateway calls, TLS with JWT delegation tokens is used (see JWT section).

Authorization model (per-request):
- Authorization decisions are made by the runtime sidecar using a local policy cache (sync'd from central Policy Store) and request attributes: tenant_id, model_id, route, cost_tier, and request_tag.
- Use a simple allow/deny policy language that supports attribute match, TTL, and rate-limited allow exceptions for emergency fallbacks.

Service and policy names (examples):
- redwood-identity-service (RIS) - issues short-lived certs and JWTs
- redwood-policy-store - canonical source of RBAC/ABAC policy for sidecars
- redwood-sidecar-authz - local enforcer embedded with runtime
- redwood-audit-collector - consumes signed request logs

Operational SLOs and thresholds:
- auth.cert_issue_latency.p95 <= 40ms
- sidecar.authz_check.p95 <= 5ms
- auth.failure_rate (production traffic) <= 0.01% per day
- audit.log_delivery_success >= 99.5% over 24h window
- sidecar.cpu_overhead median <= +6% vs. baseline; sidecar.mem_overhead <= +80MB per replica

Metrics to emit (suggested):
- auth.cert_issue_latency_p50/p95/p99
- sidecar.authz_check_latency_p50/p95/p99
- authz.decision.allowed_count, authz.decision.denied_count
- auth.token_replay_detected_count
- audit.log_enqueued_count, audit.log_delivery_latency_p95

Policy sync and cache semantics:
- Policy Store publishes delta snapshots every 30s; sidecars fetch full snapshot every 15m.
- Policy cache TTL default = 60s; stale-while-revalidate applies for 5s to reduce blocking on transient connectivity.
- If policy validation cannot be performed and request is critical (health-check, internal-mgmt), default to deny but trigger emergency fallback policy if configured by owner.

Example Authorization Rule (pseudocode):
- allow if tenant_id == request.token.tenant and model_id in tenant.allowed_models and request.route != admin_endpoint
- deny otherwise

YAML example: (Envoy JWT + simple RBAC mapping)
---
apiVersion: v1
kind: AuthorizationPolicy
metadata:
  name: allow-inference-calls
spec:
  selector:
    matchLabels:
      app: inference-sidecar
  action: ALLOW
  rules:
  - from:
    - source:
        requestPrincipals: ["spiffe://redwood/tenant/{{tenant_id}}/workload/*"]
    to:
    - operation:
        paths: ["/v1/generate", "/v1/embed"]
    when:
    - key: "model_id"
      values: ["model-*-public", "model-tenant-*"]
---
# JWT validation snippet (gateway)
jwt_validation: |
  {
    "issuer": "https://ris.redwood.internal/",
    "audiences": ["redwood-inference"],
    "jwks_uri": "https://ris.redwood.internal/.well-known/jwks.json"
  }

Performance and runtime considerations:
- Use local cache of JWT public keys and cert chains; rotate keys with grace_period = 30s.
- Offload heavy crypto to a shared crypto worker pool accessible by sidecars (gRPC interface). This avoids per-pod CPU spikes.
- For small requests, prefer symmetric MAC verification for internal delegation tokens to reduce cost; asymmetric signatures remain for cross-boundary calls.

Audit and signing requirements:
- Every inference request that touches models marked PII or regulated must record a signed audit entry containing: timestamp, tenant_id, model_id, request_hash, auth_decision, sidecar_id.
- Audit entries are batched and pushed to redwood-audit-collector; batch max interval = 5s, max size = 200 entries.
- In Private deployments, customers may opt-in for on-prem audit storage; sidecars must support local filesystem buffer + forwarder.

Rollout plan (gated):
1) Canary 1 (internal infra): deploy sidecar authz to 2% of traffic on non-critical models. Run for 48h.
   - Verification checks: authz.allowed_rate ~ expected, authz.denied_rate ~ 0, auth.latency overhead < 5ms P95.
2) Canary 2 (customer-facing read-only routes): increase to 10% for 72h.
   - Add synthetic traffic with edge-case JWTs (expired, malformed, tenant-mismatch).
3) Partial rollout: 50% of inference pods, 7 days. Monitor CPU and latency budgets.
4) Full rollout: all inference pods; enable audit batching.

Rollback criteria:
- sidecar.authz_check_latency_p95 increases > 8ms continually for 1h
- increased 5xx rate on runtime endpoints by > 0.2% absolute
- audit.log_delivery_success < 98% for 1h

Operational runbook (high level):
1) If sidecar authz failures spike: check policy-store connectivity, RIS health, cert TTLs.
2) For token replay: identify sidecar_id and revoke the token series via RIS; initiate tenant notification if necessary.
3) If audit backlog grows > 10k entries: temporarily drop non-regulated audit entries and prioritize PII/regulatory audits.

Permissions and ownership:
- Policy Store: eng-platform (primary), security (secondary)
- RIS (identity service): eng-infra (primary), security (secondary)
- Sidecar authz enforcer: eng-serving-runtime (primary), security (secondary)
- Audit collector and retention policy: security (primary), eng-sre (secondary)

Testing checklist before promotion:
- Unit tests for policy compile/parse and edge cases (missing attributes, wildcard matching).
- Integration tests: sidecar with a local Policy Store (simulate 30s delta + full snapshot).
- Load test: sidecar under synthetic mixed traffic at production QPS for 2h.
- Chaos: simulate policy-store partition and verify stale-while-revalidate behavior.
