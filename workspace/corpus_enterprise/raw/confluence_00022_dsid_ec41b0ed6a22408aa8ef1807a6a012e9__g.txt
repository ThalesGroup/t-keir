GPU Provisioning Rate Limits and IaC Throttling Policy

Summary
This page defines Redwood's standardized policy for rate limiting GPU provisioning operations and the corresponding IaC (Terraform) throttling patterns. The goal is to protect global capacity pools, avoid cross-account supply storms, reduce noisy-neighbor incidents, and ensure predictable oncall behaviour when provisioning pressure spikes.

Context and motivation
- We operate multi-account, multi-region GPU pools with a mix of on-demand, reserved and spot-backed capacity.
- Provisioning is a high-impact control plane activity: simultaneous requests can saturate cloud quotas, exhaust IP/EIP pools, and trigger eviction cascades across tenants.
- Prior incidents stemmed from unconstrained CI pipelines, self-serve onboarding flows, and bulk repo migrations that created large, parallel terraform apply operations.

Goals
1) Limit blast radius from mass-provisioning operations by enforcing global and per-tenant request caps.
2) Provide predictable throttling primitives in IaC modules so teams can safely self-serve.
3) Integrate throttling with CI/CD to gate large changes behind canary windows and operator approval.
4) Ensure transparent telemetry and runbook-able thresholds for oncall.

Policy overview (short)
- Global provisioning concurrency cap: 30 concurrent machine create operations per region across all accounts.
- Account-level concurrency cap: 8 concurrent machine create operations per account per region.
- CI/CD pipeline burst cap: 4 concurrent terraform apply jobs per repo in a single region (enforced by the shared CI runner queue).
- Daily provisioning budget per team (non-reserved): 120 nodes total (soft quota, alerts at 80% and hard block via CI gating at 100%).
- Spot fallback window: if >50% of queued requests fail due to capacity for 10 minutes, automatically route new requests to spot-backed warm pools with agreed fallbacks.

Technical design
1) Rate-limiter service: centralized lightweight service (gpu-provision-limiter) that exposes an API used by Terraform provisioner hooks, internal provisioning SDKs, and CI runners. Implements token-bucket per (region, account, team, repo).
2) Terraform module integration: modules call a provisioner hook that checks the limiter API and waits/queues before starting create operations. The module supports a "throttle_strategy" variable with values: "blocking", "queued", "fail-fast". Default: "queued".
3) CI/CD integration: shared Buildkite queue contains a rate-limiter step that consults gpu-provision-limiter and denies starting apply jobs when per-repo or per-account caps are hit.
4) Remote-state lock awareness: limiter integrates with remote-state lock TTLs to prevent deadlocks; locks are annotated with expected create counts.

Configuration matrix
| Scope | Metric | Default threshold | Enforcement action | Owner |
|-------|--------|------------------:|-------------------|-------|
| Global (per-region) | concurrent_creates | 30 | queue new requests (60s backoff) | infra-sre |
| Account (per-region) | concurrent_creates | 8 | queue or fail based on module setting | cloud-accounts team |
| Team (daily) | daily_create_count | 120 | alert @ 80%, CI gated at 100% | capacity-planning |
| CI Repo | concurrent_applies | 4 | block new jobs in Buildkite queue | eng-dx |
| Egress IP pool | ephemeral_ips_requested | 50 | block provisioning until IPs freed | network-ops |

Terraform module example (recommended pattern)
```hcl
module "gpu_node_pool" {
  source = "git::ssh://git@github.com/redwood-infra/terraform-modules.git//gpu-pool"

  region            = var.region
  desired_count     = var.desired_count
  throttle_strategy = "queued" # options: queued | blocking | fail-fast
  throttle_group    = "team-${var.owner_team}"
  tags = {
    Owner = var.owner_team
    Purpose = "inference-pool"
  }
}

# hook (executed as null_resource local-exec) will call internal limiter API before create.
```

Limiter API contract (example)
- POST /v1/allocations -> body: {"scope":"region:us-west-2","count":3,"meta":{"team":"vision"}}
- Response: {"status":"granted","token":"abc123","expires_at":"2025-02-20T12:34:00Z"} or {"status":"queued","eta_seconds":45}
- Clients must supply token when performing cloud create operations to allow accounting and idempotency.

CI/CD pipeline integration snippet (Buildkite step)
```yaml
steps:
  - label: ":terraform: apply"
    command: ./ci/terraform-apply-wrapper.sh
    parallelism: 1
    concurrency: 1
    agents: ["gpu-provisioner"]
```
Where terraform-apply-wrapper.sh calls limiter and aborts if the limiter returns "fail-fast".

Observability and metrics
Instrument these key metrics into Prometheus/Telemetry platform:
- gpu.provision.request.count{scope,team,region}
- gpu.provision.request.latency_seconds
- gpu.provision.concurrent_creates{region,account}
- gpu.provision.queue_depth{region,account}
- gpu.provision.daily_count{team}
- terraform.apply.blocked_by_throttle{repo}
Alerting rules (examples)
- P1: gpu.provision.queue_depth > 60 for 5m in a region -> page infra-sre and cloud-accounts.
- P2: terraform.apply.blocked_by_throttle spikes by >200% over baseline -> page eng-dx and capacity-planning.
- P3: daily_create_count for team > 120 and continues growing -> notify team-owner and capacity planner.

Runbook: typical oncall flow for a provisioning storm
1) Triage: check Prometheus dashboards (GPU Provisioning Overview) and limiter health endpoint /healthz.
2) If queue_depth > 60: open a slack #infra-incident channel, page infra-sre.
3) Check recent CI runs to identify a noisy pipeline (filter terraform.apply.blocked_by_throttle metric).
4) If noisy repo identified: temporarily increase its per-repo burst cap by +1 via limiter UI (requires cloud-accounts approver) and instruct the team to linearize their applies.
5) If cloud provider quota exhaustion is suspected: run quick checks: aws ec2 describe-instances quota and ENI usage; check ephemeral IP pool usage.
6) Fallback: enable spot-warm-pool routing (toggle in limiter) for new requests and communicate expected P99 latency increase.
7) Post-incident: require a retro and request a remediation plan from the owner (e.g., change module to use smaller batches or use instance reuse patterns).

Operational considerations and best practices
- Prefer desired_count adjustments (scale-up within a pool) over creating many independent node pools. This reduces per-create overhead and throttling pressure.
- When doing large migrations, break work into windows and request a temporary quota bump from capacity-planning at least 48h in advance.
- Use the module variable throttle_strategy to set fail-fast for automated tests and queued for production rollouts.
- Annotate terraform runs with `throttle_group` so accounting is available in the limiters.

Security and RBAC
- Limiter UI/API is protected via OAuth with short-lived tokens. Only cloud-accounts, capacity-planning, and infra-sre roles can adjust global caps.
- Per-repo burst increases require an approver from eng-dx or cloud-accounts. Approvals are recorded in audit logs.

Ownership and roadmap
- Owner: infra-sre (primary), cloud-accounts (secondary)
- Next roadmap items: automatic machine-type selection when capacity low, adaptive backoff algorithms using historical fill-rate, and terraform-provider plugin for native limiter checks.

Appendix B: Troubleshooting snippets
- Check limiter status: curl -sS https://limiter.redwood.internal/healthz
- Inspect current allocations: curl -sS -H "Authorization: Bearer $TOKEN" https://limiter.redwood.internal/v1/allocations?region=us-west-2
- Force-read cloud ENI counts: aws ec2 describe-network-interfaces --filters Name=availability-zone,Values=us-west-2a | jq '.NetworkInterfaces | length'
