SLO Corruption Detection and Artifact Quarantine Playbook

Summary:
This playbook defines detection, mitigation, and audit procedures for SLO corruption events: when telemetry or upstream artifacts make SLO measurements unreliable (false burn, sputtering error counts, or systematic metric inflation). It combines signal definitions, quarantine actions for suspect telemetry or tenants, capacity hedging steps to preserve customer-facing availability, and evidence requirements for incident review.

Goals:
- Minimize accidental error-budget consumption from bad signals or corrupted metrics.
- Protect customer-facing availability by hedging capacity and applying safe fallbacks.
- Provide a reproducible quarantine and validation path so SLO measurements can be repaired with full auditability.

Scope:
Applies to multi-tenant inference services hosted by Redwood Inference (hosted API and Dedicated). Excludes deep model-quality regressions driven by ML model output correctness (see regression-triage).

Definitions:
- SLO Corruption: Any change in telemetry pipeline, instrumentation bug, downstream aggregator failure, or ingestion spike that causes the computed SLO or error budget to diverge from user-facing reality by >5 percentage points for more than 10 minutes.
- Artifact: Any piece of telemetry or derived signal used to compute SLOs (latency histograms, error counters, synthetic-monitoring results, tenant attribution metadata).
- Quarantine: Temporary isolation of suspect artifacts/tenants from production SLO calculations and routing logic until validated.

Detection Signals (priority order):
1) Error-budget burn-rate anomaly: burn rate > 10x baseline for >5 minutes AND not explained by known deployment.
2) Synchronous spikes across unrelated services (indicates telemetry pipeline issue).
3) Histogram shape changes with identical percentiles across multiple tenants (indexing/aggregation bug).
4) Sudden loss of tenant attribution tags followed by a correlated jump in global 5xx rate.
5) Synthetic canary divergence: synthetic success rate drops but user-facing requests show no latency increase (possible sampling/tagging loss).

Minimum telemetry required to triage:
- Raw request logs (including tenant_id, route, request_id).
- Latency percentile buckets (p50/p90/p95/p99) by tenant and route for the last 60 minutes.
- Error counters with error codes and upstream dependency markers.
- Aggregation pipeline health metrics (topic lag, aggregator queue depth, error rates).
- Canary run logs and synthetic payload traces.

Automated rules and alerts (examples):
- Alert: slo-burn-rate-spike-high (firing when burn rate >= 10 for 5m). Pager severity: P1.
- Alert: metric-aggregation-lagging (topic lag > 10m or consumer lag > 2M messages). Pager severity: P2.
- Alert: tag-attrition-detection (percent missing tenant_id > 3% across 1m). Pager severity: P1.

Investigation checklist (first 10 minutes):
1) Confirm alert, record timeframe and current burn.
2) Check deployment calendar for recent rollouts (Console -> Rollouts).
3) Query raw logs for error signature and tenant distribution: 
   - rwictl logs query "service:inference AND timestamp:[now-15m TO now]" --fields tenant_id,error_code,request_id,latency_ms
4) Inspect aggregation pipeline health dashboards (topic lag, consumer errors).
5) Launch synthetic checks against sample routes and compare to canary history.
6) If telemetry pipeline shows tachyon spikes (high lag / consumer errors) or missing tenant tags, escalate to telemetry-oncall.

Quarantine decision matrix:
- Condition A: Aggregation/ingest failure detected (topic lag > 10m OR consumer crash) -> ACTION: Quarantine derived SLO inputs; mark affected SLOs as "measurement degraded" and stop counting error-budget until validated.
- Condition B: Tenant tag attrition (missing tenant_id > 3%) -> ACTION: Quarantine affected tenant(s) from global SLO rollups; route tenant traffic to a safe proxy routing layer if required.
- Condition C: Synthetic vs production divergence with intact pipeline -> ACTION: Investigate model/regression; do not quarantine telemetry but consider targeted rate-limits if errors are genuine.

How to quarantine artifacts (step-by-step):
1) Annotate the SLO dashboard with incident id (e.g., SLO-INC-2026-0218) and set SLO status = measurement_degraded.
2) Use rwictl to toggle the SLO calculator: 
   - rwictl slo disable-derived-inputs --slo inference_p99_latency --until 2026-02-18T18:30:00Z --reason "ingest-lag"
3) For tenant-level quarantine: add tenant to transient-exclude list: 
   - rwictl slo tenant-exclude add --tenant tenant-42 --slo inference_error_rate --incident SLO-INC-2026-0218
4) If quotas/quotas-based routing depend on the same corrupted inputs, set temporary quota overrides to avoid surprising tenant throttles: 
   - rwictl quota override --tenant tenant-42 --limit 80% --reason "SLO measurement quarantine"
5) Notify affected teams via the incident channel and Slack group #sre-slo-incidents. Include start timestamp and expected next validation.

Capacity hedging play (when quarantine is in effect):
- Goal: prevent genuine capacity exhaustion while artifact quarantine prevents normal SLO-driven throttles.
- Actions:
  1) Increase safety headroom by reserving 10–30% of serving pool capacity for critical tenants.
     - capacity-orchestrator reserve --pool core-inference --percent 20 --reason "SLO measurement degraded"
  2) Enable conservative autoscale policies (shorter cooldown, higher min replicas) for 30 minutes.
  3) Apply token-priority routing to protect high-SLA tenants; if unavailable, apply fairshare but cap burst windows.
  4) Implement temporary soft rate limits with clear client-facing messaging hooks (Console -> Status -> Maintenance).

Rollback / recovery verification steps:
1) Confirm aggregation pipeline health (consumer lag < 30s, error rate < 0.1%).
2) Re-enable derived inputs in canary mode for a narrow window (e.g., 5 minutes) and compare computed SLO against synthetic and raw-sampled truth.
   - rwictl slo enable-derived-inputs --slo inference_p99_latency --canary 300s
3) Run a differential audit: validate sample of 10k requests across tenants to ensure error counts align within 3%.
4) If differential audit passes, graduate the SLO back to production counting and remove tenant quarantines.
5) Document the precise cutover time and signal provenance in the incident ticket.

Incident review evidence checklist (minimum viable packet for postmortem):
- Incident summary (one-paragraph), scope, start/end times, and SLO(s) affected.
- Time-series of raw and derived SLO metrics with annotations for quarantine toggles.
- Aggregation pipeline metrics (topic lags, consumer restarts), logs, and error traces.
- Representative request traces (10–50 traces spanning affected tenants).
- rwictl command history and the operator ids who executed quarantine or overrides.
- Communications timeline (PagerDuty, Slack threads, status page updates).
- Decision log describing why quarantine was used vs. alternative mitigation.

Post-incident corrective actions (examples):
- Fix root cause in aggregation pipeline: consumer retry backoff or topic partitioning changes.
- Add schema-checking/assertions in ingestion to reject malformed messages earlier.
- Add a derived-metrics canary path that exercises the SLO calculator with synthetic inputs every 5 minutes.
- Increase telemetry retention/trace sampling during high-burn windows to allow faster forensics.

Operational tooling matrix (who to ping and toolset):
- Telemetry-oncall: access to ingestion dashboards, consumer group tooling (kafka-ops), and rwictl metrics-forwarder.
- Serving-oncall: capacity-orchestrator, pool-reserve API, and routing policies in Console.
- SLO-owner: has permission to disable/enable derived inputs and tenant excludes.

Permissions and ownerships (responsibilities):
- SLO owner (service/product team): final authority to quarantine tenants from SLO rollups.
- Telemetry team: owns ingestion and aggregation pipeline fixes and validation tests.
- SRE oncall: executes capacity hedging, temporary overrides, and incident documentation.

Runbook quick play (compact checklist for responders):
1) Acknowledge alert, capture incident id.
2) Triage: check deployment page, log signatures, and pipeline health.
3) If ingest badness observed -> Quarantine derived inputs and mark SLO measurement_degraded.
4) Reserve capacity 10–30% and apply conservative autoscale.
5) Notify SLO owner and affected product teams.
6) Run differential audit when pipeline shows healthy; re-enable canary; graduate when audit passes.

SLOs and thresholds table (reference):
- inference_p99_latency: corruption threshold = 5 percentage-point divergence, action = disable-derived-inputs.
- inference_error_rate: burn-rate anomaly threshold = 10x baseline for 5m, action = tenant-exclude if tenant attribution lost.
- synthetic_success_rate: divergence threshold = 2% absolute drop vs. rolling 1h baseline, action = immediate synthetic investigation.

Communication templates (status page / Slack / customer):
- Status page brief: "We are investigating degraded SLO measurement for inference_p99_latency affecting monitoring. No customer-request impact observed. Quarantine and capacity hedging in place. Next update in 30m."
- Slack message template: "[INC SLO-INC-2026-0218] Quarantined derived inputs for inference_p99_latency due to aggregator lag (topic x consumer lag=12m). Reserving 20% capacity. Telemetry team triaging. @telemetry-oncall"

Audit and compliance notes:
- All rwictl commands used during quarantine must be logged to the incident ticket with operator identity.
- Any tenant-level exclusions require approval from SLO-owner or SRE lead and must include retention of raw logs for 90 days.

Appendix A — Example queries and commands:
- Raw logs sample: rwictl logs query "service:inference AND timestamp:[now-60m TO now]" --filter "error_code:[500 TO 599]" --sample 1000
- Aggregation lag: telemetry-query "SELECT max(lag_ms) FROM consumer_lag WHERE topic='slo-events'"
- Reserve capacity: capacity-orchestrator reserve --pool core-inference --percent 20 --reason "SLO measurement degraded"
- SLO toggle: rwictl slo disable-derived-inputs --slo inference_p99_latency --until $(date -d '+30 minutes' -Iseconds) --reason "ingest lag"

Appendix B — Postmortem template fields (to paste into incident ticket):
1) Executive summary (1–2 sentences).
2) Timeline of key events and decisions.
3) Root cause and contributing factors.
4) Corrective actions and owners with due dates.
5) Validation plan and metric gates to close.
6) Lessons learned and follow-ups.
