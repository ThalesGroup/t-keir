Execution Degradation Simulator and Recovery Procedures

Summary
-------
This document describes the Execution Degradation Simulator (EDS) — a lab-grade harness and operational runbook for reproducing, characterizing, and automatically recovering from runtime degradation modes that affect execution coordination, kernel scheduling, KV cache warmup, and tail-latency amplification. The guide contains: architecture interactions, supported simulation scenarios, telemetry requirements, step-by-step recovery procedures, benchmark acceptance criteria, and post-test analysis templates.

Goals
-----
- Provide a deterministic, auditable way to inject realistic degradation into the serving runtime so teams can validate detection and recovery logic.
- Reduce time-to-detection for complex degradation classes (scheduler thrash, kernel saturation, KV cold miss storms).
- Validate automated mitigation policies (backpressure, model fallback, admission control) without impacting production.

Scope and intended use
---------------------
- Target: internal staging clusters and dedicated canary pools only. Never run EDS against production clusters unless authorized by SRE with a staged blast radius plan.
- Components in scope: Execution Coordinator, Scheduler, Kernel Handoff, KVCache layer, Dispatch layer, Telemetry collectors, and Autoscaler hooks.
- Not in scope: third-party accelerator firmware updates and hardware-level electrical faults.

High-level architecture interactions
-----------------------------------
- Execution Coordinator: central decision point for slot assignment and handoff. Simulations should exercise coordinator decisions (reject/accept), delayed handoff, and inconsistent state reconcilers.
- Scheduler: drives kernel admission and batch composition. Injected noise should include burst queueing, priority inversions, and synthetic long-running kernel reservations.
- Kernel Handoff: emulate slow kernel activation (warm-up latency), deliberate kernel failures, and fallback activation to software kernels.
- KVCache: simulate cold start storms, targeted shard eviction, and inconsistent session lookup latencies.

Prerequisites
-------------
1. Access to staging cluster with labeled nodes: eds-canary-*.
2. A snapshot of representative traffic (shadow replay corpus) stored at s3://redwood-eds/corpus/<name>.
3. EDS binary and manager CLI installed (see install section below).
4. Alerting subscribers and a post-test channel created (#eds-results).

Install (one-time)
------------------
# install EDS manager in your environment
kubectl -n eds-system apply -f https://internal-assets.redwood.com/eds/install/eds-manager-2027-02.yaml
edsctl auth login --token $EDS_TOKEN --cluster eds-canary-01

Simulation harness overview
--------------------------
- Components:
  - eds-controller: orchestration service that schedules scenario runs and controls blast radius.
  - eds-injector: surface for fault injections (latency, cpu-steal, kernel-delay, kv-evict).
  - eds-replayer: traffic replayer that feeds the runtime using recorded traces and synthetic load shapes.
  - eds-observer: aggregator that composes traces, kernel telemetries, and SLO metrics for the scenario timeline.

Supported fault injection primitives
----------------------------------
- latency-add(ms) — adds N ms latency to targeted RPCs (dispatch, coordinator, kv).
- cpu-steal(percent) — consumes CPU cycles on chosen process groups to emulate noisy neighbors.
- kernel-hold(ms) — delays kernel activation to simulate slow NVLink or kernel cold starts.
- kv-evict(pct,shard) — evict a percentage of keys from a KV shard to create cache coldness.
- batch-break(probability) — randomly split batches with given probability to simulate batching failure.

Standard test scenarios (examples)
--------------------------------
1) Coordinated KV Cold Storm
   - Objective: validate autoscaler + admission policy under KV cache miss amplification.
   - Steps: replay 3x peak traffic with kv-evict(80,shard-07) + latency-add(25) on KV RPCs for 10 minutes.
   - Pass criteria: median P50 latency < 300ms and P99 < 1.2s after mitigation policies engage; no dropped requests > 0.5% over 1 minute.

2) Priority Inversion and Kernel Starvation
   - Objective: ensure scheduler crediting and per-request SLOs remain enforced when a long-running kernel locks slots.
   - Steps: inject kernel-hold(4500) on selected kernel_id, replay mixed traffic ramp (50% short chat, 50% long completion) for 8 minutes.
   - Pass criteria: short requests P95 meets target (< 400ms) after preemption or cooperative handoff; scheduler logs show credit redistribution.

3) Handoff Oscillation (flapping model swap)
   - Objective: detect oscillatory fallback between model variants and verify hysteresis/backoff controls.
   - Steps: alternate model-variant health toggles with 30s cadence while sending steady traffic.
   - Pass criteria: no more than 2 model switch cycles per 5 minutes; fallback proportion < 10% of all requests.

Runbook: controlled execution and recovery (step-by-step)
-------------------------------------------------------
1. Prepare: notify #eds-results and owners; tag run in eds-controller (run-id generated).
2. Lock: ensure no other e2e/chaos jobs are running on the canary pool.
3. Snapshot: save current autoscaler config and coordinator routing table:
   kubectl -n runtime get configmap autoscaler-config -o yaml > /tmp/autoscaler-config.$RUNID.yaml
   kubectl -n runtime get configmap coordinator-state -o yaml > /tmp/coordinator-state.$RUNID.yaml
4. Start replay: edsctl run --run-id $RUNID --scenario kv-cold-storm --corpus s3://redwood-eds/corpus/weekday-peak
5. Monitor (first 5 minutes): watch streaming dashboard: Grafana -> /d/eds/eds-scenario?orgId=1&run=$RUNID. Key panels: P50/P95/P99, kernel-queue-len, coordinator-pending-ops, kv-miss-rate.
6. If P95 exceeds threshold (see thresholds table) for 2 consecutive minutes, proceed to automated mitigation; otherwise let the scenario run its full duration.

Automated mitigation sequence (triggered by watcher)
1) Step 0 (detect): eds-observer fires alert EDS-AUTO-MIT-01 when P95>threshold and kv-miss-rate > 5x baseline.
2) Step 1 (soft): temporarily tighten admission controller by 20% (admit-rate reduction). Command:
   edsctl mitigation apply --run-id $RUNID --policy admit-reduce-20pct
3) Step 2 (scale): request a fast scale up of dedicated slots:
   kubectl -n runtime annotate deployment serving-runtime autoscaler-request=\"fast-scale-$RUNID\" --overwrite
4) Step 3 (fallback): enable model-variant fallback (degraded quantized variant) for affected routes:
   edsctl variant set --route /chat --fallback-variant redwood-chat-q4f --ttl 900
5) Step 4 (observe): wait 90s and observe P95; if still > threshold, proceed to manual escalation to SRE.

Manual recovery checklist (if automated mitigation fails)
1. Pause scenario: edsctl run stop --run-id $RUNID
2. Revert admission changes: edsctl mitigation rollback --run-id $RUNID
3. If coordinator is unresponsive, restart coordinator replicas sequentially with zero-downtime replacement:
   kubectl -n runtime rollout restart statefulset coordinator --strategy=RollingUpdate
4. If kernel binary is suspect, pin a previous kernel version using the runtime-plugin manifest:
   kubectl -n runtime apply -f /manifests/kernel-plugin-pin-$KNOWN_GOOD.yaml
5. Post-recovery: collect full traces from eds-observer and run the postmortem checklist.

Telemetry and alert thresholds (reference)
----------------------------------------
| Metric                          | Warning threshold          | Critical threshold         | Recovery target |
|---------------------------------|---------------------------|---------------------------|-----------------|
| route.p95_latency_ms           | > 450ms for 2m            | > 900ms for 1m            | < 400ms         |
| kernel.queue_length            | > 120 (per device)        | > 200 (per device)        | < 80            |
| kv.miss_rate                   | > 3x baseline (2m)        | > 10x baseline (1m)       | baseline ±10%   |
| admission.rejected_rate        | > 2%                      | > 5%                      | < 1%            |
| error.rate                     | > 0.5%                    | > 2%                      | < 0.2%          |

Benchmarks and acceptance criteria (post-test)
----------------------------------------------
- Each scenario run must produce a benchmark artifact (JSON) with the following fields: run_id, scenario, corpus, p50,p95,p99, kernel_utilization_mean, kv_miss_rate, mitigation_steps_taken. The eds-controller automatically uploads these to s3://redwood-eds/results/<run_id>.
- Acceptance is defined per scenario; a two-stage pass is required:
  - Detection pass: alerts fire within 90s of the injected degradation.
  - Mitigation pass: P95 returns to recovery target within 5 minutes after automated mitigation.

Artifacts and analysis commands
------------------------------
- Fetch artifacts:
  aws s3 cp s3://redwood-eds/results/$RUNID/ /tmp/eds-results-$RUNID --recursive
- Summarize run (quick):
  jq '.metrics | {p50: .p50, p95: .p95, p99: .p99, kernel: .kernel_utilization_mean}' /tmp/eds-results-$RUNID/summary.json
- Generate timeline heatmap (local):
  edsctl analyze timeline --input /tmp/eds-results-$RUNID/traces.json --output /tmp/heatmap-$RUNID.html

Post-test reporting and checklist
--------------------------------
1. Upload run summary to Confluence under the test-results space and link to artifacts.
2. Create a short postmortem if either detection or mitigation pass fails. Include: root cause hypothesis, steps to reproduce, changes to telemetry or thresholds, and action items.
3. If kernel or scheduler adjustments were made, schedule a canary dry-run and sign-off with Runtime PM.

Ownership and escalation
------------------------
- Scenario owner: runtime-e2e (oncall: runtime-e2e-oncall@redwood.com)
- Telemetry owner: observability-infra
- Escalation: SRE -> Runtime leads -> CTO (only for cross-region incidents)

Safety and blast-radius controls
-------------------------------
- Automatic safeguards in eds-controller: max_nodes_affected default = 2; cooldown between mitigations = 60s; manual escalation required if rollback rate > 10%
- Always run with the --dry-run flag first to validate expected actions without changing cluster state.

Appendix: example alert rule (Prometheus format)
------------------------------------------------
- name: EDS-AUTO-MIT-01
  expr: |
    histogram_quantile(0.95, sum(rate(route_request_duration_bucket[1m])) by (le, route)) > bool 0
  for: 2m
  labels:
    severity: warning
  annotations:
    summary: "EDS scenario {{ $labels.route }} p95 high"
