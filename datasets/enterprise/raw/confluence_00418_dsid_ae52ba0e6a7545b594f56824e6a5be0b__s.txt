Session Resilience: Onboarding & Fallback Playbook

Overview

This playbook describes the recommended onboarding path, configuration checklist, SLO mapping, and operational runbook for session resilience and automatic fallback behavior for Redwood Inference customers and internal integrations. It is written for product managers, reliability engineers, and solutions engineers who are responsible for onboarding customers to high-availability conversational workloads and validating fallback guarantees.

Goals

- Provide a repeatable onboarding checklist to map customer SLAs to Redwood runtime policy and route configuration.
- Define fallback tiers, compatibility constraints, and fallback sequencing to minimize user-visible errors and cost spikes.
- Specify test cases, telemetry panels, and alert thresholds used to verify resilience before and after go-live.
- Assign ownership and rollback criteria for any canary or staged rollout that modifies fallback behavior.

When to use this playbook

Use this playbook when:
1. A customer with conversational workloads requests SLA-backed resilience or dedicated capacity.
2. An internal team needs to modify fallback ordering, add a new variant, or tune eviction/evacuation settings.
3. Running a canary rollout of fallback policy changes across regions or tenant tiers.

Key concepts and components

- Redwood Runtime (service name: redwood-runtime): token-serving engine that performs KV cache management and batching.
- Route Router (service name: route-router): policy engine that selects target model variants and fallback chains.
- Fallback Orchestrator (service name: fallback-orchestrator): coordinates in-flight session transfers and state hydration across variants.
- KV Cache Coordinator: shared prefix cache used to accelerate warm sessions; eviction policy matters for resilience.
- Variant Compatibility Matrix: a customer-visible matrix describing which models are compatible as fallbacks (format provided below).

SLO and tier mapping (recommended defaults)

| Customer SLA Tier | Target p99 Latency | Availability SLO | Fallback aggressiveness | Cost tolerance |
|---|---:|---:|---:|---:|
| Development / PoC | <= 500ms | 99% | Low (best-effort) | Low |
| Production (Standard) | <= 300ms | 99.9% | Medium (soft fallbacks) | Medium |
| Production (High) | <= 120ms | 99.95% | High (aggressive, multi-variant) | High |

Mapping notes: For High-tier customers we recommend reserved Dedicated capacity or pinned warm pools to reduce eviction-driven fallbacks.

Fallback sequencing and compatibility

Standard fallback chain (default policy):
1. Primary model variant (pinned to customer's tenant config)
2. Warm-variant (same architecture, lower precision quantization)
3. Regional-compatible variant (same coupling & tokenizer, possibly smaller context window)
4. Cost-tier fallback (smaller model with documented expected regressions)
5. Degraded response mode (short, deterministic response or transparent error)

Compatibility matrix example (deliverable to customer during onboarding):

| Primary Variant | Warm Variant | Regional Variant | Cost Fallback | Notes |
|---|---|---|---|---|
| rdx-7b-16k-fp16 | rdx-7b-16k-q4 | rdx-7b-8k-fp16 | rdx-3b-8k-q4 | Warm retains KV cache; regional requires tokenization check |

Configuration checklist for onboarding (must complete before entitlement)

1. Service-level checks
   - Confirm tenant placement: hosted | dedicated | private.
   - Confirm model variants to register and pin order in the fallback chain.
   - Validate quota and burst capacity options are configured for the customer.
2. Runtime and network checks
   - Verify KV cache footprint for the tenant (recommended: reserve 1–2 GB per 100k active sessions).
   - Ensure cross-region replication is enabled if regional fallbacks are used.
   - Validate TLS/KMS integration for private deployments.
3. Observability and alerts
   - Create dashboards: Session Health (active sessions, warm hits, fallback rate), Latency P99/P50, Eviction rate.
   - Create alerts: fallback_rate > 1% sustained for 5m (SEV3), p99 latency increase > 30% vs baseline for 10m (SEV2), warm-hit ratio < 60% for 15m (SEV2).
4. Contract and communications
   - Agree on documented degradations for tiered fallbacks and tie to billing credits.
   - Populate customer-facing compatibility matrix in the onboarding packet.

Operational validation tests (pre-go-live)

Perform the following tests in a staging environment that mirrors production traffic patterns:
- Warm-hit regression test: simulate warm workload and assert warm-hit ratio >= 80% within 30 minutes after ramp.
- Eviction stress test: ramp token churn to trigger eviction and assert fallback chain proceeds without session loss.
- Regional failover test: simulate region outage and validate fallback to regional-compatible variants with < 2% request failure.
- Fidelity check: run 500 sample prompts through each fallback variant and compute top-level quality delta (BLEU/ROUGE or domain-specific metric).

Test automation snippet (curl example)

curl -X POST https://api.redwood.example/v1/sessions/test-fallback -H 'Authorization: Bearer $TOKEN' -d '{"prompt": "Test fallback behavior: echo session id", "session_id": "staging-validate-01", "simulate": "eviction_spike"}'

Expected responses: 200 with fallback headers X-Model-Variant and X-Fallback-Reason when a fallback occurred.

Monitoring and dashboards

Minimum dashboard panels:
- Session Health: active sessions, sessions created/min, sessions evicted/min.
- Warm Cache: warm-hit %, average KV latency, eviction queue length.
- Fallback Metrics: fallback_count, fallback_rate, fallback_path_distribution.
- Latency & Errors: p50/p95/p99 latencies, 5xx rate, client timeouts.

Alert thresholds (recommended)

- fallback_rate > 0.5% for 10m -> Pager to SRE oncall (SEV3)
- p99 latency > SLO * 1.3 for 10m -> SEV2 escalation to runtime team
- eviction_queue_length > 1000 for 5m -> SEV2 to infra and runtime
- sudden increase in cost per token > 50% vs baseline for 1h -> billing & product notify

Canary and rollout guidance

When changing fallback policies or adding new fallback variants, follow this phased rollout: 
1. Internal canary: 0.5% of traffic routed to canary policy within non-customer-facing sandbox tenants for 24–48h.
2. Beta tenants: select 2–3 low-risk customers (with agreed rollback) for 48–72h.
3. Gradual ramp: 5% -> 25% -> 50% -> 100% over a minimum of 7 days, with automated abort on metric regressions.

Automated abort criteria (example):
- fallback_rate increases > 2x baseline and absolute > 1% for 10m.
- p99 latency regresses > 20% and absolute > SLO for 15m.
- end-to-end user error rate increases > 0.5% absolute for 30m.

Rollback procedure (owner: runtime oncall)

1. Pause rollout and remap affected routes to previous policy via route-router CLI: 
   route-router promote --route <route-id> --policy previous-policy --reason "rollback due to fallback regression"
2. Trigger eviction stabilization: increase warm-pool retention by 2x for affected tenants for 30 minutes.
3. Open incident bridge and notify customer success/customer contact.
4. Post-rollback validation: run smoke tests and confirm warm-hit ratio and latency back to baseline.

Appendix A: Recommended default knobs and values

| Knob | Default value | Rationale |
|---|---:|---|
| warm_pool_retention | 45m | Balances memory cost with warm-hit likelihood |
| kv_cache_size_per_tenant | 2GB per 100k sessions | Empirical baseline from production telemetry |
| fallback_evaluation_window | 5s | Time to wait for model to respond before trying next fallback |
| fallback_backoff | exponential, start 100ms | Prevent cascading bursts to fallback variants |
| session_transfer_timeout | 10s | Timeout for orchestrated state hydration between variants |
