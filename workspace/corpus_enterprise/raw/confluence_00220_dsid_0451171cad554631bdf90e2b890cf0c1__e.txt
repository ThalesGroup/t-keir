Edge Deployment: Consumption & Packaging Guidance

Overview

This document explains recommended consumption patterns, packaging options, and operational requirements for customers deploying Redwood inference at the edge (VPC-edge appliances, on-prem appliance, and lightweight cloud-edge regions). It is intended for product managers, solutions engineers, and the dedicated/private deployment teams who design packaging and pricing for edge use cases.

Goal and scope

- Goal: Provide prescriptive guidance that balances predictable economics, SLOs, and customer rollout friction for edge-style deployments.
- Scope: Applies to small-to-medium edge sites (single node to 4-node clusters) and distributed edge fleets with regional management. Does not replace Dedicated/Hosted economics guidance; it complements them.

Key design principles

1) Predictable unit metrics: prefer per-instance or per-site capacity metrics (concurrent sessions, reserved vGPU units) over purely per-token billing for edge customers.
2) SLO-aligned packaging: offer SKU variants tied to latency and availability SLOs (e.g., "Edge Standard" vs "Edge SLO+"), with explicit throttling and fallback behavior.
3) Operational simplicity: reduce on-site configuration needed; provide sane defaults for batching, KV caching, and quantization.
4) Graceful degradation: include automatic fallback to lower-cost/compatibility model variant and a controlled degradation policy to preserve uptime.

Recommended packaging primitives

- Site Reservation (monthly): commits to N reserved vGPU units (e.g., small=1, medium=2, large=4). Includes baseline throughput, priority routing, and access to remote control plane.
- Per-Request Add-on: optional metered overage for burst traffic (per-100ms inference unit).
- SLO Add-on: paid feature adding 99.9% availability SLA and 95th percentile per-request latency caps with penalty credits.
- Telemetry Retention Tiers: default 7d, premium 90d for diagnostics and audits.

Operational configuration defaults

- Kernel/Runtime: enable continuous batching with max_batch_size=64 for text-gen workloads and dynamic_batch_timeout_ms=5 for low-latency sites.
- KV Cache: enable local prefix/KV caching with eviction TTL=12h for conversational workloads.
- Quantization profile: recommend int8 dynamic quantization for Llama-family models; fallback to int8+KV-aware execution for long context workloads.
- Memory limits: set per-container token buffer ceiling at 512k tokens to avoid OOM during spike patterns.

YAML snippet (example config to seed customer appliance):

---
edge_site:
  reserved_vgpu: 2
  runtime_defaults:
    max_batch_size: 64
    dynamic_batch_timeout_ms: 5
    kv_cache_enabled: true
    kv_cache_ttl_hours: 12
    quant_profile: int8-dynamic
  telemetry:
    retention_days: 30
    sampling_rate: 0.2
  fallback_policy:
    - when: cpu_util &gt; 85%
      action: shift-to-compat-variant
    - when: network_latency &gt; 300ms
      action: circuit-breaker-throttle
---

Rollout checklist for new edge customers

1. Pre-sales sizing & spike analysis: collect 7-day traffic trace or synthetic peak tests.
2. Default package selection: map required QPS and latency to SKU; confirm telemetry needs.
3. On-site validation: install appliance, run smoke test suite (see CLI commands below), validate model variants and KV-caching.
4. Canary traffic: route 5–10% of production traffic for 24–72 hours to the site and monitor error budget usage.
5. Full cutover and monitoring: enable customer-facing DNS and begin normal routing; maintain enhanced analytical sampling for 72 hours.
6. Post-cutover review: run performance report and capture lessons in the customer folder.

Smoke test CLI examples

- Install verification: redwoodctl edge status --site SITE_ID
- Latency sanity: redwoodctl benchmark --site SITE_ID --model MODEL --duration 60s --qps 10
- KV caching check: redwoodctl inspect-kv --site SITE_ID --model MODEL

SLO definitions and monitoring signals

- Latency SLO (95th): measured as server-side response completion time from request receipt to final token emitted.
- Availability SLO: percent of successful RPCs over rolling 30-day window.
- Error budget policy: If error budget &lt; 25% over a 7-day window, trigger remediation runbook and consider temporary capacity boost.

Important thresholds (default)

- 95p latency target: Edge Small &lt;250ms, Edge Medium &lt;200ms, Edge High SLO &lt;120ms.
- CPU utilization watermark for scaling decisions: 70% (soft), 85% (hard).
- Network latency threshold for remote control plane failover: 300ms.

Billing and metering notes

- Primary metering: reserved vGPU units as the committed unit. This allows customers to predict monthly spend.
- Overage billing: measured in 100ms “inference units” for additional usage beyond reserved capacity.
- Cross-charge for telemetry storage and extended retention as separate line item.

Fallback and graceful degradation policy

- First-tier: model variant fallback (e.g., reduce context length or move to a sparsely-quantized variant) while preserving API contract.
- Second-tier: request shedding with informative 503 including Retry-After and diagnostics token.
- Third-tier: circuit-breaker engages, redirecting to remote-hosted instance (if allowed by customer policy).

Security and compliance considerations

- Default: encrypt all data-at-rest with customer KMS integrated to HSM when available.
- Network: site must provide egress rules allowing control-plane webhooks and telemetry uplinks. Optionally support fully air-gapped installs with offline license key exchange.
- Audit: generate deployment and model-change audit logs retained according to telemetry tier.
