Mixed-Precision Token Billing and Telemetry Playbook

Summary

This playbook defines the telemetry, tagging, measurement, and investigation process required to bill GPU inference usage at token granularity for mixed-precision and quantized execution paths. It is intended for infra engineers, billing/data platform, and SREs who operate the inference runtime and chargeback pipeline.

Goals

- Produce accurate token-level billing that reflects real execution cost differences between FP16/FP32/BF16 and INT8/4-bit quantized paths.
- Map runtime telemetry to billing dimensions without double-counting KV-cache reuse, cached prefixes, or streaming re-requests.
- Provide a reproducible investigation checklist for cost anomalies and reconciliations.
- Minimize instrumentation overhead and avoid exposing customer prompt text to billing systems (PII-sensitive).

Scope and non-goals

- Scope: hosted & dedicated deployments; applies to on-prem when telemetry bridge is enabled.
- Non-goals: prompt content collection, model-quality metrics, or per-token content inspection. This playbook is strictly about resource attribution and cost telemetry.

High-level approach

1) Emit a compact per-request telemetry envelope from the runtime that includes resource-attribution fields (not raw text). Telemetry must be signed and batched to avoid high cardinality.
2) Enrich telemetry in the ETL with model flavor, quantization profile, and effective execution kernel.
3) Convert tokens to a normalized token-charge unit using a kernel-cost table and per-region GPU cost factors.
4) Post-process to deduplicate cached tokens (prefix/kv hits) and to apply tenant-level discounts/credits.

Telemetry envelope (contract)

- Emit at request completion and for mid-stream checkpoint (for long streaming sessions). Envelope fields (compact):
  - request_id: opaque UUID
  - tenant_id: tenant-opaque-id
  - model_id: model name + pinned version (e.g., "llama-2-70b-v1")
  - kernel_id: runtime kernel identifier (e.g., "attn_v2_bf16_k8")
  - precision_path: one of [FP32, BF16, FP16, INT8, INT4]
  - input_tokens: integer (tokens in prompt sent to runtime)
  - output_tokens_emitted: integer (tokens emitted to user)
  - tokens_served_from_kv_cache: integer
  - continuous_batch_group: optional string (if request batched)
  - seq_len_distribution: short histogram string (buckets: <=32, 33-128, 129-512, 513+)
  - gpu_micros: integer (microseconds spent on GPU kernels attributable to request)
  - gpu_memory_bytes_peak: integer
  - region: cloud region code
  - instance_flavor: e.g., "p4d.24xlarge" or on-prem SKU
  - timestamp: ISO8601

Example (JSON emitted by runtime):

{"request_id":"f83c9a1e-...","tenant_id":"t-acme-42","model_id":"redwood-rlm-30b@v3","kernel_id":"attn_v2_bf16_k8","precision_path":"BF16","input_tokens":48,"output_tokens_emitted":96,"tokens_served_from_kv_cache":12,"gpu_micros":230000,"gpu_memory_bytes_peak":2147483648,"region":"us-west-2","instance_flavor":"g5dn.12xlarge","timestamp":"2025-10-05T17:12:09Z"}

Note: Runtime MUST NOT emit user prompt text or raw outputs in this envelope. Any enrichment requiring prompt length should only use token counts.

Kernel cost table and normalized token units

- Maintain a kernel cost table (canonical source: infra-config repo) that maps (kernel_id, instance_flavor, region) -> cost_per_micros and amortized overhead_per_request.
- Billing unit: normalized_token_cost = base_token_charge * precision_multiplier * kernel_efficiency_factor
  - base_token_charge is a global value per model family and region (configurable)
  - precision_multiplier examples: FP32=1.0, BF16=0.75, FP16=0.7, INT8=0.42, INT4=0.29 (numbers derived from profiling; updated quarterly)
  - kernel_efficiency_factor is derived from gpu_micros / output_tokens_emitted to capture kernel-level variance

Telemetry to billing pipeline mapping (ETL steps)

- Ingest raw envelopes into telemetry lake (Kafka -> minio).
- Enrich with model family tags and quantization profiles (from model-service metadata).
- Convert per-request fields into normalized_token_cost and token_count_for_billing = output_tokens_emitted - tokens_served_from_kv_cache.
- Aggregate per tenant per day/hour and write to billing ledger (append-only).

Deduplication & KV-cache handling

- Rule: Tokens served from KV cache do not incur full generation cost; they are charged at cache_retrieval_rate (configurable, default 10% of base token charge) unless the KV cache warmup was a paid generation by another tenant.
- If tokens were seeded by the same tenant earlier in the session, mark as internal cache hit -> charge at cache_retrieval_rate.
- If tokens were restored from a global warm-pool seeded by evaluation infra (non-customer), the ETL should flag this and drop charges (or route to evaluation billing codes) using warmpool_tag in telemetry.

Chargeback reconciliation rules

- Daily reconciliation: compare telemetry-derived spend vs. GPU utilization cost allocation. If delta > 3% absolute or > $2,500/day, trigger an automatic investigation ticket.
- Weekly sampling audit: pick 0.1% of requests, validate telemetry fields against raw runtime logs (only counts, never text).

Alerting thresholds (SRE + Finance)

- anomaly_spend_rate: 20% increase in normalized_token_cost per tenant vs. 7-day rolling baseline -> create high-priority alert.
- kernel_efficiency_regression: a kernel_id with median gpu_micros/output_token > baseline * 1.35 over 30 minutes -> pager to runtime-oncall.
- telemetry_backfill_lag: if ETL ingestion lag > 2 hours for > 10% partitions -> page data-platform.

Investigation runbook (step-by-step)

1) Triage ticket created automatically by reconciliation or manual alert.
2) Owner: infra-sre oncall. Attach tenant_id and the offending time window.
3) Query examples:
   - Prometheus: GPU kernel micros per request: sum(rate(runtime_gpu_micros_total{tenant_id=~"t-.*"}[5m])) by (kernel_id, tenant_id)
   - SQL (bigquery-like): SELECT tenant_id, SUM(gpu_micros) as gpu, SUM(output_tokens_emitted) as tokens, kernel_id FROM telemetry_enriched WHERE timestamp BETWEEN X AND Y GROUP BY tenant_id,kernel_id
4) Calculate normalized_token_cost_delta = current_cost_per_token / baseline_cost_per_token. If delta > 1.2, proceed.
5) Check for: model change (new model_id), kernel rollout, quantization override, instance flavor change (spot->on-demand). Cross-check with deploy history and rollout tags.
6) If kernel_efficiency_regression: roll back kernel rollout (see kernel rollback playbook) or engage runtime engineers.
7) If billing mis-attribution suspected: freeze ledger writes for the tenant for the time window and perform manual discounts/adjustments. Finance ops to approve crediting.

CI/CD & Terraform patterns for instrumentation rollout

- Instrumentation code lives in serving-runtime repo. Releases must follow canary promotion policy: 5% canary -> 25% -> 60% -> 100% with 12-hour observation windows.
- Terraform: add option to enable/disable enriched telemetry at tenant scope via terraform module parameter (module: tenant-gpu-config.enable_cost_telemetry).
- A sample Terraform snippet (HCL):

resource "redwood_tenant_config" "acme" {
  tenant_id = "t-acme-42"
  enable_cost_telemetry = true
  telemetry_retention_days = 30
}

Performance and privacy constraints

- Telemetry aggregation must be batched with max payload size 512KB and no more than 1 request/sec per inference process to the telemetry endpoint.
- All telemetry must be obfuscated at source: tenant IDs are hashed with a rotating salt when exported to datasets used by non-finance teams. Full tenant mapping is restricted to finance-data.

Operational play scenarios

- Scenario A: Sudden spike in per-token cost for a single tenant -> run Investigation runbook; if caused by accidental model pin to FP32, recommend a customer-facing configuration change and offer temporary credit.
- Scenario B: Kernel rollout caused fleet-wide 10% cost uplift -> immediate rollback and create postmortem with cost delta table.
- Scenario C: ETL lag causes underbilled tenants -> run backfill procedures (see "backfill-procedure" internal doc id) and communicate adjustments with finance ops.

Metrics dashboard (recommended widgets)

- Per-tenant normalized token cost (7d, 30d)
- Kernel efficiency heatmap (kernel_id x model_family) showing median gpu_micros/output_token
- KV-cache hit ratio by tenant and by model
- Daily delta: telemetry-derived spend vs. infra allocation cost

Quarterly governance

- Every quarter: update precision_multiplier table based on micro-benchmarking across representative model families.
- Finance and runtime lead to sign-off on multiplier changes; changes are annotated and backdated for historical comparability.

Appendices

A. Example ETL pseudo-SQL for deriving billing rows

INSERT INTO billing_ledger (tenant_id, day, normalized_tokens, amount_usd)
SELECT tenant_id, DATE(timestamp) as day, SUM((output_tokens_emitted - tokens_served_from_kv_cache) * precision_multiplier * kernel_efficiency) as normalized_tokens, SUM((output_tokens_emitted - tokens_served_from_kv_cache) * precision_multiplier * kernel_efficiency * base_rate) as amount_usd
FROM telemetry_enriched
WHERE timestamp BETWEEN @start AND @end
GROUP BY tenant_id, day;

B. Common troubleshooting checks (quick list)

- Did the tenant pin to a new full-precision model?
- Was a kernel rollout in the affected region?
- Did instance flavor change to an expensive SKU (spot->on-demand)?
- Are cache warmups being misattributed as paid generations?
- Is ETL normalizing tokens incorrectly (off-by-one in output token counts)?
