ADR — Request Credit Composition and Hedging Policy (2026)

Summary
-------
This ADR defines a single, composable "request credit" model used across Redwood's inference stack and a conservative hedging policy for short-tail latency degradation. The credit model converts heterogeneous cost signals (model size, token counts, fidelity multipliers, and priority tiers) into a uniform accounting unit used by routing, scheduling, and cost metrics. The hedging policy specifies when to issue duplicate (hedged) requests to alternative variants and the safety guards to prevent amplification and cost runaway.

Motivation and context
----------------------
Problem statements we solve:
- Inconsistent cost accounting across edge, router, and runtime causes opaque billing and makes capacity decisions brittle. Different services apply ad-hoc multipliers (quantization, batching, prefetch) and produce conflicting per-request cost estimates.
- Latency spikes in the fast-path (edge-proxy -> cost-scheduler -> runtime-orchestrator) can cause long tail p99 regressions. Simple naive hedging improves p99 but risks large additional GPU/throughput consumption if left unconstrained.
- Rollouts and autoscaling need a canonical signal to make conservative capacity decisions.

Goals
- Provide a single, well-documented credit composition formula that every service can compute deterministically.
- Use credits to drive routing (cheap vs premium), quota enforcement, and cost telemetry.
- Enable safe hedging for latency-sensitive requests while bounding cost and downstream amplification.

Non-goals
- This ADR does not change pricing or public billing APIs. It defines internal accounting only.
- It does not prescribe exact token pricing numbers for customers.

Decision (what we will adopt)
----------------------------
1) Request Credit Composition
   - Every inference request will advertise a credit vector and an aggregate credit scalar. Services MUST be able to compute the aggregate independently from the vector.
   - Composition formula (human-readable):
     credit = base_credit(model_variant) * fidelity_multiplier(model_flags) + per_token_credit * effective_input_tokens + kv_prefetch_credit

   - Components (definitions):
     - base_credit(model_variant): static per-variant baseline (e.g., gptx-13B: 10 credits).
     - fidelity_multiplier(model_flags): 0.5 for quantized-4bit, 1.0 for fp16, 1.6 for high-context/ensemble modes.
     - per_token_credit: normalized per-token cost unit; default 0.02 credits/token for short sequences. Adjusted dynamically by runtime-configd.
     - effective_input_tokens: input token count + prompt-expansion factor (for streaming/partial prompts).
     - kv_prefetch_credit: fixed cost for KV-prefetch operations when enabled (default 0.5 credits).

   - Priority modifier: incoming request priority (P0..P4) multiplies aggregate credit for scheduling fairness; e.g., P0*1.5, P1*1.2, P2*1.0, P3*0.8, P4*0.5. This is applied only to scheduling and quota—not to telemetry shown to customers.

   - Exported fields on request envelope (edge-proxy -> cost-scheduler -> runtime):
     - credit_scalar (float): computed aggregate credit as decimal string (e.g., "12.34").
     - credit_breakdown (string list): ["base:gptx-13B:10", "fidelity:fp16:1.0", "tokens:120:2.4", "kv:0.5"]

2) Hedging Policy (conservative, hierarchical)
   - Purpose: reduce p95/p99 tail latency for latency-critical routes with minimal cost amplification.
   - Eligibility: only requests with priority P0 or P1 and credit_scalar <= 50 are eligible. Large, long-running requests are excluded.
   - Safety caps (hard limits):
     - hedged_fraction_cap: at most 8% of eligible requests may be actively hedged system-wide over a rolling 10m window.
     - max_hedge_duplicates: 1 (i.e., at most one duplicate hedged request per original request).
     - per-variant hedging throttle: a given model_variant can accept at most 10 hedged requests per second per runtime shard.
   - Trigger conditions for issuing hedged request:
     1. If waiting_on_run_queue_ms > 35 ms, send hedged request to fallback_variant (prefer same-fidelity quantized variant or geographically closer shard).
     2. If first_token_stream_delay_ms > 75 ms for streaming routes, send hedged request.
   - Cancellation: the first successful response (non-500, non-429) returned must cancel remaining hedges. Runtimes SHOULD support best-effort cancellation but MUST avoid wasting work on model variants where cancellation cannot be honored.

Requirements (concrete metrics and SLO alignment)
------------------------------------------------
- SLOs to monitor as part of rollout:
  - Fast-path eligible p50/p95/p99 latency targets (for P0/P1): p50 < 35ms, p95 < 120ms, p99 < 300ms.
  - Hedging cost budget: hedged_requests_cost / total_cost <= 0.06 (6%) on rolling 1h.
  - Hedged failure amplification: additional error-rate attributable to hedges <= 0.5 percentage points.

- Observability: services MUST emit the following telemetry (as metrics and logs):
  - credit_scalar (histogram), credit_breakdown (sampled), hedged_request_count, hedged_duplicate_count, hedged_cancelled_count, hedged_cost_estimate, waiting_on_run_queue_ms, first_token_stream_delay_ms.
  - Events for hedging triggers with request-id, original_variant, fallback_variant, and reason_code.

Implementation details and configuration examples
----------------------------------------------
- Responsible services and owners:
  - edge-proxy: computes initial credit vector and credit_scalar at ingress. Owner: Edge Platform Team.
  - cost-scheduler: validates and enriches credits, enforces quotas. Owner: Cost & Billing Infra.
  - runtime-orchestrator: receives credit for scheduling and applies hedging logic on eligible requests. Owner: Runtime Performance Team.
  - telemetry-pipeline: consumes hedging and credit metrics, calculates hedged fraction and cost impact. Owner: Observability Team.

- Example credit table (human table representation):
   | component                | example value        | notes |
   |-------------------------|----------------------|-------|
   | base_credit(gptx-13B)   | 10                   | static per-variant |
   | fidelity_multiplier(fp16) | 1.0                | quantized-4bit = 0.5 |
   | per_token_credit        | 0.02                 | default, runtime-tunable |
   | tokens                  | 120                  | effective_input_tokens |
   | kv_prefetch_credit      | 0.5                  | when kv prefetch enabled |

- Example configuration snippet (YAML) for hedging guardrails:

  hedging_policy:
    eligible_priorities: [P0, P1]
    credit_threshold: 50.0
    wait_queue_ms_trigger: 35
    stream_delay_ms_trigger: 75
    hedged_fraction_cap: 0.08
    max_hedge_duplicates: 1
    per_variant_qps_cap: 10

Rollout plan
------------
1. Phase 0 — pilot (2 weeks): enable credit_scalar emission at edge-proxy and cost-scheduler for 5% of internal traffic (routes: internal-fastpath/*). No hedging enabled (read-only). Monitor credit distribution and outliers.
2. Phase 1 — guarded hedging (4 weeks): enable hedging for P0 routes for 2 internal customers and 1 synthetic traffic class. Apply hedging caps: hedged_fraction_cap = 0.03. Evaluate SLOs and hedging cost.
3. Phase 2 — extended (6 weeks): increase hedging to P1 and raise hedged_fraction_cap to 0.06 for synthetic + internal canary customers. Ramp incrementally to production only after passing safety checks.
4. Phase 3 — GA: open for all eligible internal routes and set initial per-tenant hedging budget.

Monitoring and automatic rollback criteria
----------------------------------------
- Automated rollback triggers (systems will disable hedging immediately if any of the following occur):
  - hedged_fraction > 12% sustained for 10m.
  - customer visible p99 latency increases by >20% compared to baseline for two consecutive 15m windows.
  - hedged_cost_estimate / total_cost > 12% sustained for 30m.
  - hedged-induced error amplification > 2 percentage points sustained for 15m.

Open questions and next steps
---------------------------
- How to expose credit breakdown to customers (if at all) for transparency while avoiding confusing billing signals? Recommend a separate public-mapping translation layer.
- Determine exact default per_token_credit values by experiment (A/B test across several model variants).
- Investigate whether tenant-level hedging budgets are necessary for large customers to avoid noisy-neighbor amplification.

Alternatives considered (short)
-----------------------------
1) No formal credit model: continue ad-hoc multipliers. Rejected for lack of observability and operational consistency.
2) Simple per-token-only credit: too coarse; hides model-variant fixed costs and fidelity differences.
3) Aggressive hedging without caps: improves p99 but risks uncontrolled cost spikes and GPU saturation. Rejected.
