Multi-signal prefetch governance and telemetry contract

Summary
This page defines the governance model, telemetry contract, and operational playbook for multi-signal prefetching in the runtime. It standardizes the signals we will accept, the scoring formula, the telemetry schema, dashboard/alert mappings, experimentation requirements, rollout safety gates, and post-rollout validation steps. This doc is meant to be the single source of truth for teams that build or operate prefetch/warmer logic (platform, runtime, operator tools).

Goals
- Reduce cold-start tail latency for interactive LLMs without increasing GPU token-cost by more than 8% at steady state.
- Make prefetch decisions auditable and debuggable with a stable telemetry contract.
- Provide a safe experiment and rollout pathway to tune prefetch behavior per-tenant and per-region.

Scope
Applies to: KV/prefix prefetcher, edge-warmers, region-local cohort prefetching, and operator-triggered warmup scripts. Does NOT cover proactive model weight loading (separate infra).

Definitions
- Signal: any input used to score a candidate for prefetch (history access, tenant SLA, synthetic ranking).
- PrefetchCandidate: a unique key (tenant_id, model_id, prefix_hash).
- PrefetchScore: single numeric score (0-100) computed using the telemetry signals and feature weights.

Approved Signals (canonical names and description)
1) recent_prefix_count_1h — count of requests matching the prefix in the last hour
2) tenant_priority_score — static tenant weight from billing/contract (0-1.0)
3) kv_cache_hit_rate_24h — recent hit-rate for same tenant/model
4) projected_token_savings — approximate tokens saved if cache-hit occurs
5) synthetic_sla_risk — risk signal from synthetic lab (0-1.0)
6) op_manual_inhibit — operator override (boolean)

Scoring formula (canonical)
- PrefetchScore = clamp(0,100, 20*normalize(recent_prefix_count_1h) + 30*tenant_priority_score + 25*normalize(kv_cache_hit_rate_24h) + 15*normalize(projected_token_savings) + 10*(1 - synthetic_sla_risk) - 50*op_manual_inhibit)
- Normalization functions MUST be the canonical helpers in infra-libs/prefetch (v2.1).

Telemetry contract (required fields)
All prefetch decisions MUST emit a structured event to telemetry with the following keys (JSON schema):
| field | type | description | example |
| tenant_id | string | canonical tenant id | t-01234 |
| model_id | string | model version id | llama-13b-vq-2026-11 |
| prefix_hash | string | sha1 of prefix | 3f2a... |
| decision_ts | iso8601 | timestamp of scoring | 2027-02-09T14:22:00Z |
| score | number | computed prefetch score (0-100) | 73.2 |
| signals | map<string,number> | raw normalized signals used in scoring | see example |
| decided_action | enum | {no-op, prefetch-queued, prefetch-executed, inhibit} | prefetch-queued |
| reason | string | human-readable rationale (optional) | high recent_prefix_count |
| operator_run_id | string | optional, if triggered by operator | run-20270201-42 |

Implementation notes
- Event emission must be idempotent for a given (tenant_id, model_id, prefix_hash, decision_ts). Use event deduplication key: <tenant_id>::<model_id>::<prefix_hash>::<minute-ts>.
- Signals must be calculated from the canonical time-windowers (1h,24h) and should not sample from offline backfills during normal scoring.

Dashboard and alert mappings
- Dashboards (must ship before rollout):
  - Prefetch Decisions Overview: timeseries of decisions/second, queued vs executed, mean score distribution (by model tier).
  - Cost Impact Viewer: token-cost delta attributable to prefetch (daily) with tenant breakdown.
  - Prefetch Reliability: event success rate, dedupe rate, and failure reasons.
- Alerts (initial thresholds):
  1) prefetch-error-rate > 1% sustained for 15m -> P3 alert to platform-ops.
  2) cost-delta > +12% across >24h -> P2 alert and rollback candidate.
  3) automated-prefetch-fallbacks > 0.5% -> investigate kernel/IO contention (P2).

Experimentation and rollout checklist (required for all changes to weights, new signals, or new prefetch actor)
1) Write experiment spec: hypothesis, target metric (tail P99 latency for interactive routes), safety metric (token-cost delta), cohorts, duration.
2) Synthetic validation: run the new scoring function in the synthetic lab for at least 48h across representative tenants and sequences.
3) Shadow run in production (no-op decisions logged) for 7 days; gather telemetry and cost projection.
4) Canary rollout to 5% of traffic in a non-critical region for 72h; monitor SLOs and cost.
5) Ramp to 25% if canary green for 72h; run retrospective.
6) Full ramp to 100% with automated rollback gates (see safety gates).

Safety gates (automated)
- If cost-delta > +10% sustained 2h => auto-disable prefetcher for the cohort and raise P1.
- If tail latency (P99) for interactive route degrades > 10% vs baseline for 30m => auto-disable and roll back weights.
- If prefetch-error-rate > 5% in 10m window => throttle queue drain and notify platform-ops.

Operator runbook (short)
1) Investigate: open Prefetch Decisions Overview for the region/tenant, filter by operator_run_id or prefix_hash.
2) If cost spike: throttle prefetch queue (CLI: infractl prefetch throttle --tenant t-... --percent 0) and open incident.
3) If latency spike: disable prefetch scoring (infractl prefetch set-mode --mode off) and route tenant to warmset fallback.
4) Postmortem: capture the score distribution, synthetic_sla_risk trend, and tenant_priority changes into the incident doc.

Ownership and SLAs
- Owner: platform-prefetch team (primary), eng-sre (oncall escalation).
- Oncall SLA: P1 response target 15 minutes, P2 2 hours.
- Telemetry retention: decision events retained at full fidelity for 90 days, aggregated rollups for 2 years.

Schema examples

{"recent_prefix_count_1h": 42, "tenant_priority_score": 0.8, "kv_cache_hit_rate_24h": 0.24, "projected_token_savings": 1200, "synthetic_sla_risk": 0.12, "op_manual_inhibit": 0}

FAQs and non-goals
- Q: Can teams add arbitrary signals? A: Not without a governance review. New signals must be registered, have owner, unit tests for normalizers, and pass synthetic lab validation.
- Non-goal: This doc does not specify runtime kernel selection or hardware affinity for executed prefetch tasks. Those remain in eng-serving-runtime docs.
