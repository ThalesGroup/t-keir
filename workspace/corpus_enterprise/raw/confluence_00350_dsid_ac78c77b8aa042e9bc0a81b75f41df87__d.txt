Dynamic Probe Priority Scoring and Synthesis Blueprint

Summary
-------
This blueprint defines a production-ready system for dynamically scoring and synthesizing evaluation probes ("probes") across the eval-harness. The goal is to prioritize limited human annotation and synthetic probe generation capacity toward probes that maximize signal for quality regressions, quantization fragility, latency-related failures, and customer-impacted slices.

Motivation
----------
- Probe budgets are constrained: annotation and compute cost mean we cannot exhaustively evaluate all slices continuously.
- Static prioritization leads to stale signals: workload drift, model updates, and quant changes shift the set of important probes.
- We need a unified, explainable scoring function that combines telemetry, model-change sensitivity, and business impact to 1) rank existing probes for evaluation and 2) seed new synthetic probes automatically where coverage gaps exist.

Scope
-----
This document covers:
- The priority scoring feature set and weight defaults.
- Algorithms for dynamic probe scoring.
- Synthetic-probe seeding heuristics and templates.
- Integration points: eval-harness scheduler, probe fabricator, and telemetry ingestion.
- Rollout plan, monitoring, and ownership.

Out of scope: human annotation UI and billing flows (see probe-curation-stewardship page).

Priority scoring design
----------------------
We represent each probe (existing or synthetic candidate) with a feature vector computed from telemetry and metadata. The final priority score is a weighted, normalized sum of feature contributions with a small stochastic exploration component (epsilon-greedy) to avoid blind spots.

Core features and default weights
(used to compute score = sum(weight_i * normalized(feature_i)))

| Feature name | Signal source | Purpose | Default weight |
|-------------|---------------|---------|----------------|
| Recent-Failure-Rate | eval telemetry (last 7d) | Prioritize probes with rising failure rates | 0.28 |
| Exposure | production shadow/sample rates | Ensure probe matches real traffic slices | 0.14 |
| Model-Change-Sensitivity | diff-of-eval-metrics pre/post model build | High sensitivity means likely regression | 0.20 |
| Quantization-Delta | replays across quant profiles | Detect probes that degrade under quant | 0.12 |
| Customer-Impact | tenant mapping / SLA score | Business-critical slices score higher | 0.10 |
| Latency-Tail-Exposure | p95/p99 per-slice | Latency sensitive prompts prioritized | 0.08 |
| Exploration-Bonus | random seed / novelty | Ensure coverage and avoid stagnation | 0.08 |

Normalization: each feature is normalized to [0,1] using clip-to-99.9th percentile and min=0 baselines computed over a sliding 30d window.

Telemetry ingestion and feature computation
------------------------------------------
- Inputs: eval results, production shadow traffic samples, per-tenant usage, quantized-replay outputs, model promotion diffs.
- Storage: feature aggregates stored in the eval-metrics-store as daily rollups (table: eval_probe_features).
- Freshness: features must be recomputed within 2 hours of new eval telemetry arrival for high-severity slices; otherwise stale flags are set.

Example SQL to compute Recent-Failure-Rate (simplified)
```
SELECT probe_id,
  SUM(CASE WHEN status = 'fail' THEN 1 ELSE 0 END) / COUNT(*) AS recent_failure_rate
FROM eval_results
WHERE occurred_at >= now() - interval '7 days'
GROUP BY probe_id;
```

Scoring pseudocode
------------------
```
features = fetch_features(probe_id)
score = 0
for name, weight in WEIGHTS.items():
  score += weight * normalize(features[name])
# add small randomized exploration
score = (1 - EPSILON) * score + EPSILON * random_uniform(0, 0.2)
return score
```

Dynamic weight tuning
- Default weights above are starting points. We run weekly bayesian optimization using historical detection throughput (true positives for real regressions found) as objective, constrained to maintain interpretability (max single-weight <= 0.4).
- All weight changes require a canary run and sign-off by the evaluation-steering panel.

Synthetic probe synthesis (seeding)
----------------------------------
When the scorer indicates coverage gaps (low exposure but high model-change-sensitivity or quantization-delta), the fabricator will generate candidate synthetic probes. There are two families of synthesis: template-driven and mutation-driven.

Template-driven synthesis
- Use curated prompt templates per product domain (customer-support, code-assist, summarization). Templates include placeholder slots with type constraints (numeric, name, code-snippet).
- Fill slots from a synthetic-lexicon derived from production anonymized tokens and prohibited-list filtering.
- Example template: "User asks to summarize the following transcript: [TRANSCRIPT_SNIPPET]" with TRANSCRIPT_SNIPPET length sampled from heavy-tail distribution to stress context window.

Mutation-driven synthesis
- Take high-value probes and apply controlled mutations: token-level paraphrase, meaning-preserving swap, adversarial perturbations (typos, punctuation changes), and context truncation/extension.
- Each mutation has an associated risk score; only mutations with acceptably low semantic drift are used for production seeding.

Synthesis quality controls
- Semantic similarity gate: new synthetic probe must score >= 0.65 cosine similarity in embedding space to an anchor family when mutation-driven, to avoid generating irrelevant tests.
- Privacy gate: all placeholder substitutions must pass PII detection; any candidate flagged is dropped and logged.
- Diversity cap: limit synthetic probes per fingerprint cluster to 3 per week to avoid overfitting.

Scheduler integration and lanes
----------------------------
We integrate scoring outputs into the eval-harness scheduler which supports lanes: real-eval (human-annotated), synthetic-eval, and stress-eval. Lanes have capacity budgets and SLOs.

- Allocation rule: allocate top-K scored probes to lanes according to a configurable split (default: 40% real, 40% synthetic, 20% stress).
- Backpressure: if annotation backlog > 48h, reduce real-eval allocation by 50% and move budget to synthetic-eval.
- Preemption: high-priority probes (score > 0.85) preempt lower-priority scheduled runs in the next 2-hour window.

Config example (JSON stored in config-store):
```
{
  "lane_split": {"real": 0.4, "synthetic": 0.4, "stress": 0.2},
  "annotation_backlog_threshold_hours": 48,
  "preemption_score_threshold": 0.85,
  "max_synth_per_cluster_per_week": 3
}
```

Monitoring, alerts, and SLOs
---------------------------
- Accuracy of regression catch: target 80% of production-impacting regressions detected by probes within first 24h of model promote (SLO). Measurement: retrospective mapping of incidents to earliest probe alert.
- Freshness: 95% of high-severity probe features recomputed < 2h after telemetry ingestion.
- False positive rate: keep manual triage FP rate < 30% for top-50 scored probes.

Key alerts
- Feature computation lag > 2h for > 5% of high severity probes -> page eng-eval-oncall.
- Spike in synthetic-probe rejection due to privacy gate -> notify security and evaluation-steering.
- Rapid weight drift during auto-tuning -> open ticket for manual review.

Operational runbook (quick steps)
-------------------------------
1. Incident: "probe storm" where too many probes spike score simultaneously.
   - Identify root cause: check model-change-diff, recent deploys, telemetry anomalies.
   - If model-induced, trigger a temporary freeze on synthetic seeding and escalate to model-owner.
2. Annotation backlog > 72h:
   - Increase synthetic-eval allocation and throttle non-critical probes (score < 0.35).
   - Notify annotation ops to scale reviewers.
3. Privacy gate failures:
   - Toggle synthesis off for affected templates, escalate to security to review lexicon and filters.

Rollout plan
------------
- Phase 0 (Lab): 2 weeks. Run scoring offline against historical evaluation data to calibrate weights and measure detection uplift.
- Phase 1 (Canary): 1 week. Enable scoring for 5% of eval-harness traffic; only surface suggestions (no auto-seed) to annotation queue.
- Phase 2 (Pilot): 3 weeks. Enable auto-seeding into synthetic lane for 10% capacity with manual triage for seeds.
- Phase 3 (GA): Gradual ramp to default lane_split over 4 weeks.

Ownership and governance
------------------------
- Primary owners: evaluation-platform (feature compute & scheduler) and probe-fabrication team (synthesis and template maintenance).
- Stakeholders: model-onboarding, applied-ml, security, customer-success.
- Governance: weekly evaluation-steering review of scoring metrics and any weight changes; quarterly privacy audit of synthetic lexicon.

Risk assessment
---------------
- Overfitting to synthetic probes: mitigate with diversity caps and embedding-similarity gating.
- Privacy leaks from lexicon: mitigate with PII detection and security audits.
- Annotation fatigue: mitigate with dynamic lane-splits and backlog-driven throttles.

Appendix B — Example mutation policy (short)
- Allowed mutations: paraphrase (preserve semantics), punctuation perturbation, token insertion of stop-phrases.
- Disallowed: replacement of entity types (e.g., identities) unless anonymized via lexicon.
