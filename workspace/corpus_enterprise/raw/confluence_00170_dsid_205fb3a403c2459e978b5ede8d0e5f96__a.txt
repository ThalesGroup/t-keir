Approval Timestamping and Evidence Chain for Delegated Access

Overview

Purpose: This runbook defines the architecture, operational procedures, and compliance packaging for approval timestamping and end-to-end evidence chains when access is delegated (temporary privileges, approved service delegation, or emergency access) across Redwood Inference services. The goal is to make every delegation auditable, tamper-evident, residency-aware, and queryable for regulatory audits and incident response.

Scope: Applies to all delegated access flows that grant elevated privileges for >5 minutes or that provide access to customer data, keys, or private deployment configuration. This includes: just-in-time (JIT) elevation, short-lived service tokens, delegation via ticketing systems, and emergency bypass workflows.

Key design goals
- Strong provenance: cryptographically verifiable timestamps and chaining between approval records and resulting credentials/actions.
- Auditability: every step is correlated across RBAC, audit logs, and evidence bundles with a stable correlation ID.
- Residency-aware packaging: evidence bundles preserve locality metadata for cross-border deployments and include residency policy tags.
- Operational resiliency: fallbacks when primary evidence capture fails (e.g., network partition, logging store outage).
- SDLC alignment: automated checks to ensure delegation logic is exercised in CI and gated in releases.

Definitions
- Delegation: granting temporary authority to a principal (human or service) to perform actions outside their default entitlement.
- Approval record: signed statement that documents who approved a delegation, scope, duration, and reason.
- Evidence bundle: a packaged artifact containing approval records, audit-log excerpts, credential issuance records, and residency metadata used for audits.
- Correlation ID (correlation_id): a UUID used to connect the approval, issuance, and audit trail for a single delegation incident.

Architecture and data flow (textual diagram)
1) User/Service requests delegation -> 2) Approval flow (UI/ticketing/JIT) -> 3) Approval service timestamps & signs approval (approval-service) -> 4) Credential issuer generates ephemeral credential -> 5) Audit-logging service captures the issuance event and links correlation_id -> 6) Evidence assembler compiles a signed bundle and stores it in evidence-store (geo-tagged).

Component responsibilities
- Approval-service: generate approval_id, attach approver identity, scope, duration, and create a signed approval object using KMS-backed signing keys. (Owner: Security Engineering)
- Credential-issuer: mint ephemeral tokens/credentials, include approval_id and correlation_id in credential metadata. (Owner: Identity Service)
- Audit-logging: ingest issuance events with correlation_id and context, forward to immutable-audit-store and stream to evidence-assembler. (Owner: Observability Platform)
- Evidence-assembler: assemble the evidence bundle (see packaging spec below), compute bundle hash, timestamp with approved signer, and store in evidence-store with residency tags. (Owner: Compliance Platform)

Concrete service names and endpoints
- approval-service: https://internal.approvals.redwood/api/v1/approve
- identity/issuer: https://internal.issuer.redwood/api/v1/issue
- audit-ingest: kafka-topic audits.high; http-ingest at https://internal.audit.redwood/api/v1/ingest
- evidence-store S3 buckets: evidence-us-west-2, evidence-eu-west-1 (encrypted, versioned)

Evidence bundle schema (flat key-value manifest)
- bundle_id: string (UUID)
- correlation_id: string (UUID)
- approval_id: string
- approver_principal: string (email/SERVICE_ACCOUNT)
- approval_signed_at: ISO8601 timestamp
- approval_signature_kid: string (KMS key id)
- issuance_record_id: string
- credential_id: string
- credential_ttl_seconds: integer (as string)
- audit_log_excerpt_ids: list of strings (comma-separated when stored in the manifest)
- residency_tag: one of [US, EU, APAC, MULTI]
- bundle_hash: sha256 hex string
- retention_policy: string (e.g., "evidence_standard_7yrs")
- stored_location: s3://bucket/path

Retention and residency mapping (table)
- Evidence type: Approvals for privileged access -> Retention: 7 years -> Residency: follows resource location (if customer-specific, match customer region)
- Evidence type: Emergency-bypass approvals -> Retention: 10 years -> Residency: store in multiple regions (primary + mirrored region)
- Evidence type: Routine JIT approvals -> Retention: 2 years -> Residency: single-region per policy

Operational SLOs and thresholds
- Approval record signed and emitted: P99 <= 2s
- Correlation ID present in audit ingest: P99 <= 10s after issuance
- Evidence bundle assembled and stored: P95 <= 300s (5 minutes)
- Evidence-store put_object success rate: >= 99.9% over 30d

Procedures: Delegation approval flow (step-by-step)
1) Requestor initiates delegation (UI/API) with requested scope, justification, and desired duration. Correlation ID is created client-side if possible; otherwise the approval-service issues it.
2) Approval-service validates request against policy engine (policy-service) and escalates if above thresholds (e.g., >24h or access to production keys).
3) Approver performs review; approval-service records approver identity, signs the approval payload using KMS sign key (key rotation required annually).
4) Approval-service emits approval_event to audit-ingest with correlation_id.
5) Credential-issuer listens for approval_event, issues ephemeral credential embedding approval_id + correlation_id, and emits issuance_event.
6) Audit-ingest links issuance_event to the approval_event by correlation_id.
7) Evidence-assembler subscribes to audit streams and, once all required pieces (approval, issuance, log excerpts) are available or after 5 minutes, assembles the bundle and writes to evidence-store.

Failure modes and fallback steps
- If audit-ingest is unavailable: approval-service persists signed approvals in a local queue and retries ingestion. Runbook: page oncall and trigger audit-ingest escalation (link: /confluence/eng-platform/runbooks/audit-ingest-outage).
- If evidence-assembler timed out: create provisional evidence bundle with a note "partial" and set follow-up job to reconcile within 24h. This provisional artifact must be retained and labeled.
- If approval signature key is unavailable: fallback to secondary KMS key; record key rotation/cross-signing proof in evidence bundle.

Evidence verification (for auditors and IR)
- Use the evidence verifier CLI: redwood-evidence verify --bundle s3://...
- Verification steps the CLI performs: 1) validate bundle_hash; 2) validate approval signature with provided KMS key id; 3) confirm presence of approval_id in audit logs (query via audit-search API); 4) confirm residency tags match customer deployment metadata.

Testing and SDLC gating
- Unit tests: policy-engine rules that gate approvals must have >= 90% rule coverage and explicit negative tests for cross-region delegations.
- Integration tests (pre-prod): simulate approval -> issuance -> audit -> evidence assemble pipeline using test KMS and ephemeral S3.
- Release gate: changes to approval-service or credential-issuer require a Security Review and inclusion in the compliance test harness (PR checklist item: "evidence-assembly test case added").

Incident response integration
- If a suspected misuse is reported, IR runbook should: 1) identify correlation_id(s) for the suspect window; 2) retrieve evidence bundles and audit logs; 3) validate approval signatures; 4) freeze evidence-store objects for legal hold (see retention policy).
- Legal hold: evidence bundles tied to an active investigation get an additional tag: legal_hold:true and are excluded from normal deletion TTL jobs. (Owner: Legal + Security)

Audit readiness checklist (pre-audit)
- All delegation evidence bundles for sample period are present and verifiable via redwood-evidence verify.
- All approval signer KMS keys used during sample period are listed with rotation events.
- Residency tags on bundles match customer region metadata for each sampled item.

Operational rollout plan
1) Pilot (2 weeks): instrument approval-service and credential-issuer in staging; verify end-to-end assembly for 100 simulated delegations.
2) Canary (4 weeks): enable in production for a subset of teams (internal infra and one customer integration).
3) Full rollout (2 months): enable globally with monitoring dashboards and alerting for evidence-assembly failures.

Monitoring and dashboards
- Dashboard tiles: evidence-assembly latency histogram, failed-bundles counter (24h), audit-ingest lag (P99), evidence-store put_object errors.
- Alerts: evidence-assembly failure rate > 0.25% sustained for 15m -> pager to Security Oncall.

Governance and review cadence
- Quarterly review of retention policies and residency mappings.
- Annual audit of approval key material and KMS access lists.
- Post-incident reviews to update failure fallbacks and retention exceptions.
