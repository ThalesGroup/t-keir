GPU tenant backpressure and queue-smoothing runbook

Summary

This runbook describes the design, detection, mitigation, and long-term fixes for tenant-level backpressure and request-queue smoothing in Redwood's GPU serving fleet. It covers the runtime components, SLO-oriented thresholds, automated mitigation policies, emergency manual steps for oncall, Terraform/Helm snippets for rate-limiter configuration, and guidance for post-incident follow-up.

Objectives

- Maintain per-tenant 99th-percentile request latency SLOs under mixed workloads.
- Prevent noisy tenants from causing cascading queuing and eviction events.
- Provide deterministic short-term mitigations and a path to corrective changes (rate limits, scheduling, capacity).
- Make runbook steps executable by oncall engineers with minimal blast radius.

Applicability and scope

- Applies to hosted and dedicated GPU pools managed by eng-infra.
- Focuses on inference serving paths (text generation, chat streaming, embeddings).
- Not a replacement for billing/fraud investigation - those runbooks are in customer-success.

Key concepts and components

- Frontline queue: per-host in-memory FIFO with configurable max-concurrency and max-queue-length.
- Tenant router: request router that tags requests with tenant_id and route metadata.
- Per-tenant rate limiter: token-bucket-based limiter with burst allowance and steady-rate target.
- Global admission controller: enforces cluster-wide soft caps and triggers fallback routing to warm-pools or cheaper model variants.
- Warm pool: pre-warmed containers/GPUs with shorter start latency used for smaller bursty requests.
- Eviction controller: removes low-priority tasks when memory or GPU RAM pressure is detected.

SLOs and thresholds (operational values)

- Service SLOs (runtime team): P50 < 40ms, P95 < 200ms, P99 < 600ms for short-generation requests (<512 tokens).
- Soft backpressure threshold: per-host queued requests > 200 or per-tenant concurrent requests > 120 => throttle advisory.
- Hard backpressure threshold: per-host queued requests > 500 or per-tenant concurrent > 300 => automatic throttling and priority demotion.
- Eviction trigger: GPU memory pressure > 92% for > 30s or OOMs > 3/min => start eviction policy.

Metrics to monitor (critical dashboards)

- gpu.request.latency.{p50,p95,p99} (tagged by tenant, model, region)
- gpu.queue.length.host and gpu.queue.length.tenant
- gpu.concurrent.requests.tenant
- gpu.mem.usage.percent.host and gpu.mem.usage.percent.pod
- gpu.eviction.count and gpu.preemption.count
- admission.throttle.actions and admission.throttle.rejections
- tokenbucket.fill.rate and tokenbucket.dropped.requests

Detection: triage checklist (first 10 minutes)

1. Confirm symptom: customer tickets or alerts showing elevated p95/p99 latency or queue backlog.
2. Look at cluster-level dashboard for sudden spikes in gpu.queue.length.host and gpu.mem.usage.percent.host.
3. Group by tenant_id: identify tenants with disproportionate request rate or sustained long-running sessions.
4. Check admission.throttle.rejections for which tenant was first rejected.
5. Correlate with recent deployments (ci-cd) or model rollouts: use /confluence/eng-infra/ci-cd-and-build to verify canary promotions in last 30m.
6. If noisy tenant(s) identified, verify request patterns (burst vs sustained) and model variant sizes (512 vs 4096 context).

Automated mitigations (behavior we expect to run)

- Step A (soft): per-tenant token-bucket reduces effective refill rate by 20% for tenants exceeding soft threshold for > 60s.
- Step B (fallback): route new requests to warm-pool or cheaper quantized model variant when hard threshold reached.
- Step C (preempt): demote low-priority background eval workloads and evict them from GPUs.

Manual rapid mitigations for oncall (ordered)

1. Announce: post on #oncall with cluster and region (e.g., us-west-2-gpu-pool-1) and attach key metrics screenshots.
2. Temporarily increase per-tenant rate-limiter denominator (reduce allowed concurrency) for the noisy tenant:

   CLI example (internal admin):
   rcli tenant update-rate --tenant-id tenant-123 --concurrency 80 --burst 120

3. If step 2 insufficient, enable forced fallback to warm-pool for that tenant:

   rcli routing set-fallback --tenant-id tenant-123 --fallback-target warm-pool-usw2 --duration 15m

4. If the cluster is memory pressured, mark non-critical nodes for cordon and drain of background workloads only:

   kubectl cordon worker-gpu-045 -n gpu-serving
   kubectl drain worker-gpu-045 --ignore-daemonsets --delete-local-data -n gpu-serving

5. As last resort, trigger capacity burst (if dedicated account permits) following the burst runbook: raise capacity request to 1.5x and notify capacity-oncall. See related page: /confluence/eng-infra/gpu-fleet-and-capacity/gpu-scaling-decision-framework-and-burst-policy

Short-term rollback (if mitigation causes regressions)

- Revert rate-limiter change with the audit id printed by rcli.
- Remove forced fallback and allow gradual roll-back over 10 minutes to avoid thundering herd.

Kubernetes/Helm/Terraform snippets (examples)

- Sample token-bucket Helm values (values.yaml fragment):

  tokenBucket:
    enabled: true
    defaultRefillRate: "100r/s"
    tenantOverrides:
      tenant-123:
        refillRate: "60r/s"
        burst: 120

- Terraform resource example (rate-limiter config):

  resource "redwood_rate_limiter_config" "tenant_123" {
    tenant_id = "tenant-123"
    refill_rate = 60
    burst = 120
    enforcement = "soft"
  }

- Admission controller config (K8s CRD pseudo):

  apiVersion: serving.redwood.ai/v1
  kind: AdmissionPolicy
  metadata:
    name: global-backpressure
  spec:
    queueLimitPerHost: 500
    tenantConcurrentLimit: 300
    fallbackTargets:
      - warm-pool
      - quantized-variant

Testing and pre-deployment checks

- Canary pattern: deploy rate-limiter changes to 5% of hosts behind a feature flag for 1 hour; monitor queue length and latency.
- Load test: run tenant-level simulated burst test (loadgen) that replicates 2x expected peak for 15 minutes against a staging cluster.
- CI checks: ensure terraform plan shows only rate-limiter changes for tenant configs and Helm charts include admission policy updates.

Post-incident analysis (PI) checklist

1. Collect traces (request IDs and tenant_id), CPU/GPU utilization, queue metrics for the incident window.
2. Identify root cause: noisy tenant, model size change, regression in admission controller, or capacity shortage.
3. Quantify impact: affected tenants, p99 delta, cost of burst capacity used.
4. Action items (prioritized):
   - Implement per-tenant adaptive refill that uses moving-average request rate.
   - Add preflight CI test to simulate model-context jumps (512->4096).
   - Update onboarding templates to set sensible tenant defaults (max concurrent, burst).
5. Schedule a retrospective with runtime, infra, and product leads; publish summary to /confluence/eng-infra/runbooks/postmortems (link incident id).

Operational tips and lessons learned

- Prefer progressive throttling over blunt rejects; gradual reductions avoid thundering herd.
- Warm-pools are effective for short bursts but must be sized carefully to avoid cost leak.
- Model size changes (context length) are a frequent root cause; include context-length in deployment metadata.
- Automate tenant whiteboard: maintain a small spreadsheet of tenants with known high-burst patterns and runbook contact points.
