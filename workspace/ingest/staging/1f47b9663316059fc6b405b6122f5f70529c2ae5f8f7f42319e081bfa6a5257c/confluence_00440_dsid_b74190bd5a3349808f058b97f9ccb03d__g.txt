GPU scaling decision framework and burst policy

Overview

This page defines the decision framework we use to scale GPU capacity, govern burst allocations for evaluation/benchmark workloads, and align provisioning with cost SLOs. It combines telemetry-driven thresholds, IaC gating, and a fast manual escalation path for urgent bursts. This framework applies to: Redwood-hosted GPU pools (prod and non-prod), Dedicated tenant pools, and ephemeral evaluation clusters used by the eval team.

Goals

- Keep production inference latency SLOs (p50/p95) while minimizing incremental cost.
- Allow controlled, observable bursts for model evaluation and nightly large-batch runs without impacting critical tenants.
- Make scaling decisions auditable and reproducible via IaC and CI/CD gates.
- Provide clear ownership for each decision step and automated fallback behaviors.

Scope

Applies to: GPU fleet allocation, autoscaler configurations, burst credit accounting, IaC modules that provision GPU pools, and CI/CD pipelines that publish GPU images. Not covered: low-level kernel tuning (see eng-serving-runtime), per-model micro-optimizations.

Key concepts and terms

- Base Capacity: steady-state GPU count allocated to a tenant or service to satisfy committed throughput.
- Burst Capacity: short-lived, pre-authorized ephemeral GPUs used for evals, training-style workloads, or predictable spikes.
- Burst Window: maximum wall-clock duration a burst allocation may remain active without manual renewal (default 4 hours).
- Burst Credit Bucket: per-team/account accounting of burst capacity in GPU-hours.
- Cost SLO: target monthly incremental spend threshold per team relative to committed cost baseline (e.g., +15%).

Decision framework (high level)

1) Observe: continuous telemetry collection

- Inputs: per-tenant p50/p95 latency, token throughput, GPU utilization (node-level and process-level), queue length, retry/backpressure rates, and spot-preemption events.
- Aggregation: 1m/5m/1h windows. Alert triggers populate the scaling decision workspace.

2) Analyze: rules and ML heuristic

- Primary rule: if p95 > latency_SLO AND GPU utilisation >= 78% on >30% of nodes in pool for 10m, recommend scale-out.

- Secondary rule: if queue_length > 2000 requests AND avg_processing_time increases by >20% in 5m, escalate to scale-out recommendation.

- Cost-safety override: do not auto-scale if this scale would breach Cost SLO for the billing cycle unless request has "critical" tag (see Tagging and priority below).

3) Recommend: autoscaler vs. manual action

- If recommendation is under 25% of current capacity and burst-credit bucket >= required, autoscaler executes a temporary burst allocation.
- If recommendation >= 25% and requires new IaC rollout (e.g., add new node-pool SKU), create a change-request in the autoscale queue and trigger the IaC pipeline.

4) Execute and monitor

- Change types:
  - Ephemeral burst (fast path): provisioned via runtime API (no IaC change). TTL default 4h. Monitored by the autoscaler supervisor.
  - Node-pool resize (stable): IaC PR created, peer-reviewed, promoted via cicd/gold image gating.
  - SKU change / topology: requires infra-owner approval and scheduled maintenance window.

Tagging and priority

- Traffic is tagged at the routing layer with priority categories: production-critical, production-best-effort, evaluation, nightly-batch. Only production-critical traffic can trigger cost SLO overrides.
- Tenants must request a Burst Credit Bucket from capacity-planning. Default burst-credit allocation: 48 GPU-hours/month for non-prod eval teams; custom for Dedicated customers per contract.

Burst accounting and billing

- Burst credit consumption is recorded in billing events as: {tenant, pool, start_ts, end_ts, gpu_type, node_count, gpu_hours}.
- After burst: cost reconciliation job runs and posts an invoice/alert if consumption exceeds the monthly credit. Overages are charged to the tenant cost center or pulled from a central research budget if pre-authorized.

IaC patterns and code samples

- All stable capacity changes must be represented in Terraform modules under modules/gpu-pools. The module must expose: min_size, max_size, instance_type, taints/tolerations, and preemption_policy.

Example module interface (HCL snippet)

```
module "gpu_pool_nightly" {
  source        = "git::ssh://git@repo.redwood.ai/infra/modules//gpu-pool?ref=v1.3.0"
  name          = "eval-nightly-pool"
  min_size      = 2
  max_size      = 20
  instance_type = "nvidia-a100-80gb"
  taints        = ["workload=nightly:NoSchedule"]
  preemption_policy = "spot-fallback"
}
```

- CI/CD gate: terraform plan must be produced and snapshot-approved by the cluster owner and cost owner. Changes that increase max_size by >50% require SRE lead approval.

Autoscaler configuration recommendations

- Use predictive autoscaler with the following default thresholds:
  - scale_out_threshold: 78% gpu_utilization sustained across 10m
  - scale_in_threshold: 28% gpu_utilization sustained across 20m
  - cooldown_period: 300s (scale out), 900s (scale in)
  - max_burst_fraction: 0.25 (fraction of pool allowed for ephemeral bursts)

Runbook: high-level playbook for burst-related incidents

1) Symptom
- Nightly evals consuming >max_burst_fraction leading to producer-facing latency degradation (p95 > SLO).

2) Immediate mitigations (0-10m)
- Toggle evaluation-routing to throttled mode: `rgctl route set-priority --route eval-nightly --priority low`
- If toggling is insufficient, mark non-critical pods with taint: `kubectl taint nodes <node> eval-burst=true:PreferNoSchedule`
- Notify oncall: `#infra-oncall` with incident key and runbook link.

3) Medium-term actions (10-60m)
- Trigger ephemeral burst: `infractl burst create --pool eval --gpus 8 --ttl 4h --tag "emergency"` if burst credits available.
- If burst credits are exhausted, open a fast-track IaC change: create PR using template `increase-pool-size.md` and tag SRE oncall.

4) Post-incident (within 48h)
- Run a capacity debrief: owner documents cause, timeline, and remediation. Update burst budgets as needed.
- If repeat, schedule a persistent pool resize via the IaC runway.

Operational controls and safety nets

- Preemption handling: node_pools with preemption_policy=spot-fallback must have at least 10% reserved on on-demand capacity for production-critical tiers.
- Fallback routing: if a node pool loses >30% of healthy nodes within 5m, primary router ramps down requests to best-effort variant and routes critical traffic to warm-pool on-demand nodes.
- Cancellation policy: autoscaler will cancel ephemeral bursts that fail health-probes for >2m and refund credits in case of platform error.

Observability and dashboards

- Dashboards required per pool: GPU utilization heatmap, per-tenant p95 latency, queue length, burst-credit usage, preemption events.
- Critical alerts:
  - p95 latency > SLO for 5m (sev2)
  - burst_credit_bucket <= 10% (notify tenant owner)
  - preemption_rate > 5% in 15m (investigate SKU/zone issues)

Ownership and escalation

- Capacity planning: capacity-planning@redwood.ai (owns burst credit allocations and monthly reconciliations).
- Runtime autoscaler: eng-infra-autoscaler (oncall rotation).
- IaC changes: infra-iac (code owner and PR reviewer).

Playbook for IaC promotion of stable capacity changes

1) Create terraform branch using `make ico-create-branch` with standardized naming: `gpu-pool/<team>-YYYYMMDD-<short-desc>`.
2) Run `make terraform-plan` in ephemeral CI and attach plan artifact to PR.
3) Cost owner (tag: @cost-owner) must approve increases > $5k/month.
4) Infra-iac runs canary deploy to a test region for 24h using `promote-canary` workflow.
\5) Post-promote: add release notes to `eng-infra/release-notes/gpu-capacity` and update dashboards.

Metrics to track success

- Monthly average p95 latency compliance for production-critical routes (target: >= 99.5% SLO compliance).
- Ratio of ephemeral burst usage to total GPU hours (target: < 12% for prod pools).
- Number of emergency IaC fast-tracks per quarter (target: <= 3).

Appendix: troubleshooting snippets

- Check burst credit usage: `billingctl burst-usage --tenant eval-team --month 2025-02`
- Force deallocate a stale burst: `infractl burst cancel --burst-id <id>`
- Query node preemption events: `kubectl get events --field-selector reason=Preempted -n gpu-system`
