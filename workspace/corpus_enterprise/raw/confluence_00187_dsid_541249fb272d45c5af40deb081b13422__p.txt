Heterogeneous GPU Scheduling and Thermal Mitigation for Private Deploys

Overview

This playbook describes Redwood Inference’s recommended operational model for private deployments that use heterogeneous GPU fleets (mixed generations, memory capacities, and power envelopes). It covers scheduling policies, thermal mitigation strategies, telemetry and alerting, firmware/driver upgrade and rollback procedures, and a customer readiness checklist.

Audience

- Operators and SREs running Redwood Private (VPC or on-prem)
- Field engineers installing hardware or performing upgrades
- Customer platform engineers responsible for tenant capacity and QoS

Scope and Objectives

- Support mixed GPU fleets with minimal latency impact to inference SLOs (p95 < 120ms for interactive routes unless otherwise specified)
- Prevent noisy-neighbor thermal cascades and single-host failures from affecting tenant availability
- Provide safe firmware/driver upgrade paths with evidence-preserving rollback
- Ensure telemetry covers thermal, power, scheduler decisions, and per-tenant evictions

Background and Motivation

Many private customers prefer to incrementally add hardware (e.g., RTX A5000 with A100) for cost, procurement, or availability reasons. The runtime must:

- Map models and workload profiles to compatible hardware classes
- Respect per-tenant quotas and fairness policies (prevent a large batch job from starving low-latency tenants)
- Detect and mitigate thermal conditions proactively (avoid sudden throttling or OOM)

Key Risks

- Thermal cascade: adjacent GPUs on the same blower-based chassis heat up and trigger throttling, causing increased latency and evictions.
- Improper scheduling: assigning latency-sensitive requests to under-provisioned GPUs during bursts.
- Upgrade rollback gaps: driver or firmware upgrades that change scheduling semantics causing silent correctness regressions.

Scheduling and Placement Policies

1. Hardware classes: label GPUs as classes at install-time (class:a100-40gb, class:rtx-a5000, class:low-memory). The scheduler only colocates cache-heavy models on GPUs with matching class labels.

2. Latency tiering: define three tiers for routes — interactive, low-latency-background, batch. Scheduling heuristics: 
- Interactive: prefer lowest-latency GPUs (A100-family); avoid hosts with thermal risk score > 0.5.
- Low-latency-background: allow broader placement but avoid nodes with concurrent batch reservations.
- Batch: best-effort; can be scheduled onto heterogeneous cards if peak capacity is available.

3. Affinity and anti-affinity: ensure small models with heavy KV caches are anti-affinitized with large-batch workloads to reduce KV eviction churn.

4. Graceful degradation: when thermal or power headroom falls below policy, move interactive traffic to fallback model families (quantized / distilled variants) using smart routing. Include a fast-fallback tag on model versions.

Thermal Mitigation Strategies

- Node Thermal Score: computed from short-window (1m) and long-window (15m) GPU temperature, fan speed, and power draw. Values: 0.0 (healthy) to 1.0 (critical). Thresholds: 
  - warning >= 0.6 
  - mitigation >= 0.75 (start moving load)
  - critical >= 0.9 (evict best-effort workloads, signal outage)

- Proactive throttling: if node thermal score >= 0.75, stop scheduling new interactive requests; allow ongoing requests to finish with a max timeout (30s) then preempt batch tasks.

- Thermal isolation lanes: reserve 1 host per 10 nodes as a cool standby (idle slot) to absorb overflow when a rack shows sustained thermal degradation.

- Fan and PDU integration: where available, integrate chassis telemetry to increase fan RPM via automation when thermal score is between 0.6–0.75. Avoid aggressive fan curves that trigger noisy neighbor complaints from adjacent racks.

Telemetry, Metrics and Alerting

Required telemetry streams (agent names and metrics):

- gpu.temperature.C (gauge) — per-GPU temperature in Celsius (1s granularity recommended)
- gpu.power.W (gauge) — instantaneous power draw
- gpu.utilization.pct (gauge) — SM utilization
- gpu.memory.used.MB and gpu.memory.total.MB (gauge)
- node.thermal_score (derived gauge) — 1m and 15m windows
- scheduler.evictions.count (counter) — per-node, per-tenant reasons (thermal, OOM, preemption)
- model.fallback.count (counter) — counts of automatic fallback events per route

Alerting thresholds (examples):
- P1: node.thermal_score > 0.9 for 30s — page oncall, auto-evict best-effort tenants, mark node unschedulable
- P2: node.thermal_score 0.75–0.9 for 2m — message SRE Slack channel, trigger autoscale from standby pool
- P3: gpu.temperature.C > 85C for 1m — create ticket for field ops; do not immediately evict unless accompanied by thermal_score > 0.9

Dashboards (recommended tiles):
- Rack thermal heatmap (per-node 1m average)
- Evictions timeline correlated with model.fallback.count
- Scheduler decisions: placement by hardware class over the last 24h

Firmware / Driver Upgrade and Rollback Procedure

Principles:
- Upgrade in phases: staging (lab), canary (2 nodes), small canary (10 nodes), broad rollout (20% increments).
- Preserve evidence: collect driver and firmware state, driver logs (dmesg, nvidia-smi logs) and full telemetry snapshot prior to each stage.
- Automated smoke tests: model correctness, latency tail (p99) for a representative prompt set, KV cache warm-up behavior.

Step-by-step upgrade flow:
1. Prepare artifact bundle: driver+firmware image, sha256 checksum, release notes.
2. Lab validation: run full perf and correctness suite on representative models.
3. Canary (2 nodes): schedule at non-peak; run smoke tests for 6 hours.
4. Small canary (10 nodes): expand to 10 nodes across 2 racks; run extended 24h tests.
5. Broad rollout: advance in 20% increments every 24h provided no regressions.
6. Post-rollout verification: run weekly regression checks for 2 weeks.

Rollback criteria and steps:
- Rollback triggers: p99 latency regressions > 20% versus baseline, new OOM patterns, increased model inference error rate, silent correctness changes.
- Rollback steps (automated where possible):
  a. Mark affected cohort unschedulable for new traffic.
  b. Drain non-interactive workloads.
  c. Reinstall previous driver/firmware image from artifact repository.
  d. Reboot node (if required by firmware) and validate telemetry returns to baseline.
  e. Preserve and archive pre- and post-upgrade telemetry and logs in the rollback ticket.

Day-2 Operations Runbook: Thermal Event (short protocol)

1. Detection: alert triggers for node.thermal_score > 0.75 for 2m.
2. Immediate action (automated): scheduler stops scheduling interactive traffic to node; best-effort jobs are queued or drained.
3. Operator steps (manual):
  a. Check dashboard: verify neighboring nodes for rack-wide thermal trends.
  b. If single node: SSH into host, run nvidia-smi, inspect fan RPM and system logs.
  c. If firmware provides chassis controls, increase fan RPM by predefined safe step (follow per-vendor SOP).
4. If thermal_score remains > 0.85 for 10m: engage field ops to inspect cooling and PDU (file a P1 if multiple hosts affected).
5. Recovery: return node to schedulable state only after 15m of thermal_score < 0.6 and passing the model smoke test.

Customer Requirements and Acceptance Checklist

- Facility: adequate CRAC capacity to maintain inlet air <= 30C at peak loads; signed facility cooling agreement.
- Network: redundant uplinks >= 25 Gbps; documented QoS for telemetry.
- Power: PDUs with remote power cycling and 20% headroom above sustained TDP.
- Inventory: GPU inventory sheet with serials and class labels uploaded to Redwood onboarding portal.
- Telemetry: agent deployed and able to send metrics at required cadence; firewall rules allowing egress to Redwood telemetry endpoint.
- Maintenance window policy: customer must provide 4h planned maintenance windows for major driver/firmware upgrades.

Operational Tips and Traps

- Avoid aggressive packing of mixed-generation GPUs in the same chassis when possible; distribute older cards across racks to reduce correlated wear and thermal load.
- Watch for small, frequent CVM (cold-VM) model startups; they increase KV cache churn and can amplify thermal load due to repeated model initializations.
- Use the model.fallback.count metric to tune the fallback threshold conservatively during initial rollouts.
