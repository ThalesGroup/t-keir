PRD: Session-Anchored Embeddings Cache and Metering

Summary
-------
This PRD defines a productized feature: a session-anchored embeddings cache with integrated metering and TTL tiers. The feature provides low-latency, cost-efficient vector retrieval for conversational and transactional workloads by keeping short-lived, session-scoped vectors hot while retaining an economical long-term tier for reuse and billing reconciliation. The goal is to reduce per-request embedding compute, improve tail latency for conversational flows, and introduce clear metering semantics for session-resident vectors.

Background and motivation
-------------------------
- Many customers run conversational agents that repeatedly re-query or augment a short-lived context (e.g., user session, chat thread). Generating embeddings repeatedly for the same context increases token and compute costs and increases latency.
- Existing incremental embeddings tiering work focuses on storage durability and long-term retention; there is a gap for short-lived, session-anchored caches that are both performance-optimized and correctly metered.
- Business asks: 1) reduce host inference spend for ephemeral high-QPS sessions, 2) offer predictable billing for cached embeddings (distinct from permanent storage), 3) instrument quality and eviction metrics for SRE/product monitoring.

Goals
-----
- Provide an in-platform session-anchored cache with three TTL tiers (session-hot: 0-30 minutes, session-warm: 30m-24h, persistent: >24h) configurable per-tenant.
- Expose a clear metering model: cached-hit credits for session-hot/warm usage and standard embedding credits for persistent or cache-miss generation.
- Keep additional tail latency for embed requests under 20ms P95 for session-hot cache on Dedicated and Hosted tiers.
- Provide SDK primitives and server-side hooks so customers can opt into session anchoring with a single flag (session_id + anchor=true).
- Emit telemetry to reconcile cache hits/misses with billing and to detect quality regressions due to TTL/quantization interactions.

Non-goals
---------
- This PRD does not introduce cross-tenant shared caching.
- Not handling GDPR data-deletion workflows beyond standard deletion APIs (deletion and retention policies handled by separate compliance playbooks).

User stories
------------
1) As a product engineer at a messaging startup, I want repeated assistant-context embeddings during a user conversation to be served from a session cache so the assistant responds faster and my bill decreases.
2) As a platform engineer at a regulated enterprise, I want to configure session TTLs and disable the persistent tier, preventing long-term retention of session vectors.
3) As a finance analyst, I want a daily report that attributes credits consumed to (a) hot cache hits, (b) cache warms (migrated to warm/persistent), (c) cache misses (fresh embedding generation).

Requirements (functional)
------------------------
- API changes:
  - New embedding API parameter: session_anchor: boolean (default false), session_id: string (optional), ttl_override: string (optional human duration).
  - Example request snippet:

```json
POST /v1/embeddings
{
  "model": "redwood-embed-2-sim",
  "input": "user message",
  "session_anchor": true,
  "session_id": "chat-12345"
}
```

- Cache behavior:
  - On session_anchor:true and a provided session_id, the runtime attempts to read the session-hot cache. If miss, compute embeddings and write to session-hot with default TTL 30m (configurable at tenant level).
  - Access frequency moves objects between tiers: >5 hits in 30m -> promote to session-warm (TTL 24h), explicit customer opt-in can promote to persistent (billed as persistent embeddings).
  - Eviction policy: LRU within session scope, configurable max bytes per-session (default 16MB).

- Billing model:
  - Cache hit in session-hot: minimal or zero embedding generation credits; bill a small per-hit metadata credit (to account for bandwidth/storage) as defined in the pricing matrix.
  - Promotion to persistent triggers an embedding-generation charge at prevailing rates plus storage crediting.
  - Cache miss: standard embedding generation credits.

- Admin controls:
  - Tenant-level toggles: enable_session_cache (bool), max_session_cache_bytes (int), session_hot_ttl, session_warm_ttl, allow_persistent_promotion (bool).
  - RBAC: only admin roles may change TTLs / persistent promotion setting.

- Observability and reconciliation:
  - Telemetry events: session_cache_read, session_cache_hit, session_cache_miss, session_cache_promote, session_cache_evict, session_cache_write. Each event must include tenant_id, session_id (hashed for PII), vector_id, tier, and latency_ms.
  - Daily billing reconciliation job must consume these events to attribute credits to customers.

Non-functional requirements
---------------------------
- Latency targets: P95 read latency for session-hot on hosted must be <= 20ms, P99 <= 50ms.
- Throughput: support 10k concurrent session caches per host in Dedicated targets with graceful degradation.
- Durability: session-hot/warm should be stored in-memory + replicated to local node persistent store for fast warm-up across container restarts; persistent tier uses existing embeddings store.
- Security: session_id must be accepted only over authenticated requests; if session_id is not present, behavior falls back to standard embedding generation.

Architecture and integration
---------------------------
- Components:
  - Session Cache Master (SCM): lightweight orchestrator per-host that coordinates TTLs, promotions, and eviction signals. Owned by eng-serving-runtime.
  - Local In-Memory Cache: per-runtime process LRU store for session-hot.
  - Warm Store: SSD-backed per-host store for session-warm tier.
  - Persistent Embeddings Store: existing global embeddings store for long-term retention.
  - Metering Bridge Service: receives telemetry events, aggregates, and forwards to billing pipeline and cost-analysis systems.

- Data flow:
  1. Request with session_anchor arrives at edge -> routed to preferred runtime.
  2. Runtime queries Local In-Memory Cache. If hit -> return vector and emit session_cache_hit.
  3. If miss -> compute embedding, write to Local Cache and Warm Store, emit session_cache_miss & session_cache_write.
  4. Promotion process runs asynchronously in SCM; on promotion to persistent, emit session_cache_promote and trigger billing event for generation+storage.

SLOs and monitoring
-------------------
- SLOs:
  - Session-hot read latency: 95th percentile <= 20ms (hosted), 99th <= 50ms.
  - Cache correctness: typed mismatch or corruption rate < 0.01% per 1M ops.
  - Billing-metering accuracy: discrepancy between aggregated telemetry-derived usage and billing pipeline < 0.5% over 7-day window.

- Key dashboards and alerts:
  - Session Cache Health: hit rate, average TTL remaining, eviction rate, memory pressure per-host.
  - Billing Reconciliation: daily variance, un-attributed credits, top tenants by promotions.
  - Regression detectors: sudden drop in hit-rate or spike in cache misses after rollout (auto alert and rollback path).

API and SDK changes (developer experience)
-----------------------------------------
- SDKs (Python/Node/Go) shall add a single optional parameter: session (object) with fields id and ttl_hint. Example (Python):

```py
client.embeddings.create(model="redwood-embed-2-sim", input="...", session={"id": "chat-12345", "ttl_hint": "15m"})
```

- UX guidance in docs: recommended pattern is to scope session_id to a conversation thread and to avoid using PII; SDK will automatically hash session_id for telemetry.

Telemetry and billing reconciliation
----------------------------------
- Event schema (flattened JSON per event):
  - event_type, timestamp, tenant_id, session_id_hash, vector_id, tier, latency_ms, host_id, model_name
- Reconciliation flow:
  1. Metering Bridge aggregates per-tenant daily counts for hits/misses/promotions.
  2. Aggregates fed into billing engine; promotions and misses are billed as embedding generation events.
  3. Daily report emailed to tenant admin and surfaced in Console under "Embedding Usage > Session Cache".

Security and compliance considerations
-------------------------------------
- Session identifiers are treated as potentially sensitive. We will store only hashed session_id in event logs.
- Tenants may opt-out of persistent promotions to meet retention regulations.
- Data deletion: explicit delete requests from tenant must remove all session-warm and session-hot records for that tenant; persistent tier deletion flows handled by existing embeddings retention APIs.

Rollout plan and migration path
------------------------------
1. Alpha: internal-only on staging, limited to internal tenants, no billing hooks enabled; telemetry only. (2 weeks)
2. Beta: opt-in for Hosted (small cohort) and Dedicated (selected customers) with billing hooks in dry-run mode (reconciliation only). (4 weeks)
3. GA: billing hooks enabled, SDK docs published, Console UI for session cache toggles. Gradual rollout with canary ratio 5% -> 25% -> 100% across tenancy segments. (4–6 weeks)
4. Post-GA: observe billing variance, iterate pricing if needed, add migration scripts for customers who want to port persistent vectors out. (Ongoing)

Migration considerations for existing customers
---------------------------------------------
- For tenants already using persistent embeddings for conversational workloads, recommend a migration plan: enable session cache opt-in, set conservative TTLs, monitor hit-rate for 2 weeks, then consider promotion policy.
- Provide a one-click Console toggle to opt-in with recommended defaults and a simulator that shows estimated cost impact (savings vs promotions).

Open questions (product / engineering)
------------------------------------
1. What is the exact per-hit metadata credit (business must set a pricing floor)? Suggested: 0.01x of standard embedding credit per hit for session-hot.
2. Promotion heuristics: should we use purely frequency-based criteria, or model access patterns and semantic stability?
3. Cross-region session affinity: how to handle when a session’s traffic shifts region mid-conversation? (fallback to recompute).
4. Measuring vector quality drift across caches with quantized warm store. Need an eval harness hook.
