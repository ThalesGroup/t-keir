Maintenance Symphony — Regional Evacuation, Cache Migration and Customer Signal Playbook

Summary

This playbook describes the coordinated operator, platform and comms steps for planned regional maintenance windows that require: controlled evacuation of in-memory/KV caches, graceful tenant traffic redistribution, and automated customer signal messages. It emphasizes minimizing user-visible latency spikes and token-cost regressions while preserving SLOs and providing clear communications to downstream teams and customers.

When to use this playbook

- Planned maintenance that affects an entire region (cloud AZ outage, datacenter patching, network fabric changes).
- Model-serving infra changes where cache shards or KV-coherent state must be drained/rebalanced.
- Any scenario where a warmup pattern is required to avoid cold-cache thundering and token-cost spikes.

Goals and success criteria

- No more than 5% increase in 95th-pct latency for customer-facing routes during migration window.
- Token-per-request cost increase limited to <=10% for affected tenants (measured at route granularity).
- All critical tenants (SLA tier 1) remain within contract SLOs or are explicitly migrated to dedicated capacity before work begins.

Roles & ownership

- Operator lead (primary): executes runbook steps and coordinates with oncall.
- Platform SRE: validation of traffic routing, capacity and metrics.
- Serving runtime owner: validates model-variant fallbacks and shard mappings.
- Customer Success / Solutions Engineer: prepares tenant comms and monitors customer signals.
- Engineering manager (escalation): available for decisions on abort/extend.

| Check | Command / Dashboard | Expected state | Owner |

Runbook — step-by-step procedure

1) Pre-announce & prepare (T-72h to T-12h)
   1.1 Create maintenance ticket and calendar block; tag impacted regions and tenant segments.
   1.2 For any tier-1 tenant without dedicated capacity, open SES with account owner and propose temporary route pinning.
   1.3 Run a dry run in the staging cluster that mirrors shard topology using the exact cache-drain script.

2) Final preflight (T-2h)
   2.1 Validate dashboards: runbook-preflight query set (attached below).
   2.2 Set global operator-mode flag: POST /api/operator-mode {"maintenance_window": true} (internal flag causes conservative autoscaler behavior).
   2.3 Snapshot routing table: curl -s http://router-admin/route-table > /tmp/route-table-$(date -I).json

3) Staged cache evacuation and tenant-friendly ramp (T0 -> +60m)
   3.1 Move non-critical tenants first. For each cache shard: 
       - Issue a graceful drain: POST /cache/shard/{id}/drain?mode=staggered&grace_period=60s
       - Wait for KV-reads fallback rate to remain < 0.5% before proceeding.
       - Commands (example):
         - kubectl exec -n runtime cache-operator -- /usr/local/bin/cache-drain --shard-id=shard-42 --stagger=10s
         - redis-cli -h cache-shard-42 INFO | grep 'used_memory_human'
   3.2 For tenant warmup in target region, trigger controlled synthetic warmup requests: 
       - curl -X POST https://synthetic-service/api/warmup -d '{"routing_key": "region-west-2", "paths": ["/v1/generate?model=redwood-medium"]}'
       - Use low qps (0.5-2qps per shard) and monitor token-rate meters.

4) Traffic steering & fallback validation (T+30m -> T+90m)
   4.1 Update routing policy for drifting tenants gradually (10% increments) using the routing DController: 
       - PATCH /routing/tenants/{tenant_id} {"weights": {"a": 90, "b": 10}}
   4.2 Watch for evidence of model-variant misalignment: look for "fallback_rate" > 1% or LM-quality regression alert. If detected, revert that tenant's routing to previous config and escalate to serving-runtime owner.

5) Final drain and verification (T+90m -> complete)
   5.1 Once shard drains reach 0 active writes and < 1% read-fallback, complete the shard removal: POST /cache/shard/{id}/finalize
   5.2 Validate end-to-end SLA dashboards and run the regression check: compare pre-maintenance baseline to current for samples of 1000 requests per tenant tier.

Abort criteria (immediate stop and roll back)

- Observed >= 10% absolute increase in 99th-pct latency for tier-1 routes sustained for 5m.
- Token-per-request cost > 25% increase for any SLA-bound tenant for 10m.
- > 2% of requests returning model-fallback errors or schema mismatches.

Rollback steps (if abort triggered)

1) Immediately set routing back to snapshot: POST /router/import-snapshot -d @/tmp/route-table-<timestamp>.json
2) Cancel any ongoing cache-finalize operations and re-introduce shard replicas: POST /cache/shard/{id}/un-drain
3) Notify customers with an incident notice and open incident channel (#ops-maintenance).

Dashboards, queries and alerts (examples)

- Canary latency panel: PromQL: histogram_quantile(0.95, sum(rate(request_duration_seconds_bucket{job="canary"}[5m])) by (le))
- Token rate and cost: sum(rate(tokens_generated_total{region="us-west-2"}[5m])) by (tenant) / sum(rate(requests_total{region="us-west-2"}[5m])) by (tenant)
- Cache-fallback alert (Firing if >1% over 10m): avg_over_time(cache_read_fallback_rate[10m]) > 0.01
- Routing drift anomaly: increase in 95th-pct error-rate on newly routed nodes: increase(errors_total[5m]) / increase(requests_total[5m]) > 0.005

Customer communications templates

- Short status banner (for in-console notice):
  "Planned maintenance in region US-WEST-2 starting 2026-02-15 02:00 UTC. You may see short-lived latency increases; we expect < 5% impact. Contact support@redwood.com for questions."

- Email (template):
  Subject: Scheduled Platform Maintenance — US-WEST-2 — Feb 15 2026
  Body: Hi <customer-name>,
  We will run a planned maintenance window affecting inference routing in US-WEST-2. We are taking steps to prevent user-visible regressions (staged cache warmup and staggered tenant moves). If your workload requires higher assurance, let us know and we will provision temporary dedicated routing during the window.

Monitoring & validation checklist (post-step)

- Confirm 95th/99th latency per-tenant <= 1.2x baseline.
- Confirm fallback_rate < 0.5% for all tenant classes.
- Confirm token-cost delta <= +10% measured over 15m windows.
- Finalize telemetry snapshot: POST /telemetry/snapshot?label=maintenance-2026-02-15

Post-operation retrospective template (to complete within 3 business days)

- Incident summary: what changed, timeline of actions.
- Metrics snapshot: pre/post comparisons (latency, token-cost, fallback_rate, error-rate).
- What went well: list 3 items.
- What surprised us: list 3 items.
- Action items: owner, due date, priority (P0/P1/P2).

Playbook tuning notes (lessons learned guidance)

- If warmup QPS > 2qps per shard causes token-cost spikes, add rate caps and extend warmup to 90m.
- For multi-tenant shards with heavy skew, schedule eviction by tenant affinity instead of shard-level.
- Record a synthetic regression harness that mirrors tenant prompts for fast quality checks.
