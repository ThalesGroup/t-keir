Preflight acceptance checklist for private GPU deployments (on‑prem / VPC)

Summary
-------
This page is the canonical preflight acceptance checklist for Redwood Private GPU deployments (customer VPC or on‑prem installations). It is intended for SRE, Private Deployments, and Customer Engineering during handover to customer operations. The checklist covers hardware and capacity validation, network and egress patterns, Terraform/IaC gating, CI/CD smoke tests, runtime validation, security controls, and operational runbook readiness. Use this checklist to validate a deployment before the customer goes live or before we handoff day‑2 operations.

Scope
-----
- Applies to Redwood Private deploys that include GPU inference nodes, the Redwood control plane connector, and optional on‑prem artifact registries.
- Not a replacement for customer regulatory audits; use as an engineering acceptance gate.

Quick acceptance criteria (pass/fail)
-------------------------------
- All infra resources created by the deployment IaC converge without errors.
- GPU fleet nodes attach to the control plane and report healthy KV cache metrics for >15 minutes.
- Networking tests (TLS egress, PrivateLink / VPC peering, and NAT path) pass.
- Baseline perf smoke test: 95th percentile token latency <= declared SLA for the model tested.
- Security: audit logging enabled, KMS integration validated, and secrets rotation experiment passed.

Preflight checklist sections
---------------------------
1) Hardware & firmware verification (owner: infra‑ops)
   - Inventory: verify serial, model, and firmware for each GPU host. Acceptable GPUs: A10G, A100‑40GB, or equivalent as agreed with customer. Record device IDs.
   - Firmware/BIOS: platform firmware within supported revision range (example: BIOS >= 2024.06.1).
   - Drivers: CUDA >= 12.2, NVIDIA driver >= 537.x. Ensure driver modules load at boot.
   - NCCL and cuDNN: versions pinned in the image manifest.
   - Health probes: SMART pass for NVMe, ECC error rate < 1e‑6 over last 24h.

2) Networking & egress (owner: cloud‑networking)
   - Subnet allocation: tenant subnets match IaC vars (see Appendix). No overlapping CIDRs with control plane.
   - DNS: internal DNS entries for control plane connectors resolvable from each host.
   - Egress path: verify NAT or proxy rules allow outbound TLS 443 to the control plane endpoints. Use curl/openssl tests outlined below.
   - MTU: confirm MTU >= 9000 if configured for RDMA/GPUDirect; otherwise validate MTU 1500 path.
   - Firewall rules: ports allowed: 443 (control plane), 22 (maintenance, bastion restricted), 123 (NTP) — see table.
   - Latency and bandwidth: run iperf3 to the egress gateway; target >= 500 Mbps sustained per host for model pulls during startup.

   Example CLI checks:
   - DNS resolution: dig +short controlplane.redwood.example.internal || fail
   - TLS handshake test: openssl s_client -connect controlplane.redwood.example.internal:443 -servername controlplane.redwood.example.internal 

3) Terraform / IaC acceptance (owner: infra‑iac)
   - Plan validation: terraform plan must show no diffs after apply in acceptance environment.
   - Policy checks: run OPA/Conftest where policies must pass (no public s3 buckets, IAM least‑privilege checks).
   - Remote state: state backend healthy and locked during apply. Test cross‑account lock/unlock.
   - Module pinning: all modules referenced by version tags; no local path overrides in final PR.
   - Integration smoke script: run ./ci/acceptance/run_iac_smoke.sh — expect exit code 0.

4) CI/CD and image promotion (owner: infra‑ci)
   - Image provenance: image manifests signed and digest matches manifest in IaC variables. Verify with cosign: cosign verify --key k8s/key.pub registry/repo:tag.
   - Canary deploy: promote to a 1‑node canary pool; validate startup logs and health endpoints for 30 minutes.
   - Rollback test: exercise the automated rollback by triggering a failing healthcheck and confirming the orchestrator demotes the canary and restores previous image.

5) Runtime & serving smoke tests (owner: serving‑runtime)
   - Control plane registration: nodes must register and report "READY" state in the fleet console within 5 minutes.
   - KV cache warmup: seed and read back a KV object; validate cache hit ratio > 50% for a warmup synthetic.
   - Baseline model test: run generate endpoint against the deployed small model (e.g., opt‑1.3b quantized) with these checks:
       * correctness: outputs not truncated or garbled for a 200 token prompt.
       * latency: P95 token latency <= 120ms (adjust based on declared customer SLA).
       * throughput: sustain 10 RPS for 5 minutes without errors.
   - Streaming & chunking: validate streaming responses are delivered in <= 200ms chunks for first token.

6) Observability & telemetry (owner: eng‑platform)
   - Metrics: host_exporter, nvml_exporter, and runtime exporter enabled. Confirm required metrics exist:
       * gpu_utilization, gpu_temperature_celsius, host_cpu_steal_pct, token_latency_p95, inference_errors_total
   - Traces: distributed tracing headers propagate through control plane; sample traces are visible in Jaeger/OTEL backend.
   - Logs: centralized logging configured (stack: Loki or ELK). Verify a 15‑minute log retention pipeline for critical logs.
   - Alerts: default alerting rules present for node_down (5m), gpu_overtemp (1m), token_latency_p99_exceed (10m).

7) Security & compliance (owner: security)
   - Secrets: verify KMS integration (AWS KMS / customer HSM) and that secrets in transit are encrypted.
   - RBAC: admin, operator, readonly roles mapped to customer groups. Validate one user in each role for testing.
   - Audit logging: API calls and node registration events forwarded to audit log sink and retained per SLO.
   - Pen test quick check: run the container CVE scanner and confirm no critical CVEs in the runtime image.

8) Operational readiness & runbooks (owner: private‑deployments)
   - Runbook completeness: runbooks exist and are linked in the customer runbook index: node‑drain, kernel‑panic, network‑partition, kv‑cache‑evict.
   - Escalation path: defined oncall list, pager duty rotations, and primary/secondary oncall prepopulated.
   - Playbook drill: run a short table‑top for a node failure with the customer and record gaps.

Acceptance matrix (required checks)
--------------------------------
| Area                | Check (pass criteria)                                     | Responsibility       |
|---------------------|-----------------------------------------------------------|----------------------|
| Hardware            | Firmware and driver match manifest; SMART OK              | infra‑ops            |
| Network             | DNS, TLS, MTU, and egress path verified                   | cloud‑networking     |
| IaC                 | terraform plan/apply converges; OPA policies pass         | infra‑iac            |
| CI/CD               | Image signed; canary and rollback behavior validated      | infra‑ci             |
| Runtime             | Nodes READY; P95 latency within SLA for baseline model    | serving‑runtime      |
| Observability       | Metrics, logs, traces present; alerts firing in test      | eng‑platform         |
| Security            | KMS, RBAC, audit logging validated                        | security             |
| Ops readiness       | Runbooks exist; oncall assigned; drill completed          | private‑deployments  |

Operational rollout procedure (numbered)
-------------------------------------
1. Kickoff validation meeting: confirm owners and signoff checklist sections.
2. IaC apply in preflight namespace (tagged: customer‑acpt). Confirm remote state stable.
3. Promote image to canary pool (1 node). Monitor for 30 minutes.
4. Run runtime smoke tests and collect telemetry for 15 minutes.
5. If canary passes, promote to 10% of nodes. Run 1 hour soak tests.
6. If soak passes, promote remainder in rolling batches while monitoring replication of latency and error signals.
7. Post‑promotion: run full suite of security checks and handoff meeting for day‑2 ops.

Rollback decision criteria (examples)
-----------------------------------
- Latency regression: sustained P95 increase > 25% vs baseline for 15 minutes.
- Error spike: inference_errors_total increase > 50% absolute or >5x rate for 5 minutes.
- Node crash loop: >3 restarts in 10 minutes for the same node.

Post acceptance tasks
--------------------
- Tag the IaC commit with "customer‑acpt‑YYYYMMDD" and close the deployment runbook.
- Export a final telemetry packet (metrics + 1h of logs) and attach to the customer artifact archive.
- Schedule a 1‑week follow‑up QBR with product and customer engineering.
