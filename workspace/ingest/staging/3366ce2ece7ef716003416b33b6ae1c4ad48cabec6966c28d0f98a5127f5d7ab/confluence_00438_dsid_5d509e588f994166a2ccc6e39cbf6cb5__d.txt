Dedicated Cluster Hotfix Rollout Notes (Runtime Updates)

h2. Purpose
Dedicated customers run on isolated clusters with customer-specific SLOs and maintenance expectations. This page describes how to roll out an emergency runtime hotfix to Dedicated clusters safely and with required customer coordination.

h2. Key differences vs Hosted
* Customers may have pinned model versions and strict latency SLOs.
* Maintenance windows may be contractually required.
* Failover between clusters may not exist; assume restarts can cause brief interruptions.

h2. Required inputs
Before scheduling a Dedicated hotfix rollout, gather:
* Customer name + cluster ID
* Current runtime image tag
* Target runtime image tag
* Impact statement (expected restart behavior)
* Rollback image tag
* Whether the issue is customer-specific or global

h2. Required approvals
* IC or SRE on-call approval for emergency change
* Dedicated service owner approval
* Customer Success escalation manager sign-off on customer messaging

h2. Customer communication requirements
For Sev-1: follow /oncall-and-incident-response/incident-process/sev1-communication-requirements. Additionally for Dedicated hotfixes:
* If we will restart runtime pods: send a short note that brief interruptions may occur
* Provide a time window (even if approximate)
* Provide rollback criteria in plain language (e.g., 'if errors increase after deployment, we will revert within 15 minutes')

h2. Rollout plan
1. Canary on one Dedicated cluster first (prefer: internal dogfood dedicated or lowest-traffic customer, with CSEM approval).
2. Validate for 30 minutes: success rate, p95 latency, GPU OOM, restart frequency, customer-specific health checks.
3. Schedule remaining impacted clusters; do not roll more than 3 clusters in parallel unless IC approves.

h2. Execution steps (per cluster)
1. Confirm customer comms sent (or waived by IC for active outage).
2. Update helm values: runtime_image_tag = <new-tag>
3. Apply via ArgoCD app: dedicated-<cluster-id>-runtime
4. Watch rollout status and ensure no CrashLoopBackOff.
5. Run customer smoke checks: chat route, embeddings route, streaming completion.

h2. Rollback
If rollback triggers are met:
1. Revert runtime_image_tag to previous tag
2. Restart runtime deployment if needed
3. Notify customer immediately (CSEM)

h2. Post-rollout
* Record cluster-by-cluster outcome in the incident timeline
* Ensure the hotfix is promoted into regular release
