Anticipatory Degradation Lab: Curriculum and Dashboard Templates

Summary

This page defines a repeatable, instructor-led curriculum and a set of dashboard + alert templates to run "anticipatory degradation" labs for Redwood's platform operators and platform engineers. The labs simulate slowdowns, token surges, cache thrash, and region-level partial outages so teams can practice detection, mitigation, and graceful degradation.

Goals

- Teach operators to detect early signals of SLO drift using dashboards and enriched traces.
- Validate alert thresholds and escalation flows before production incidents.
- Exercise fallback policies (model swap, region failover, reduced-batch mode) with minimal customer impact.
- Improve postmortem fidelity by codifying measurement and regression checks.

Audience and prerequisites

- Audience: platform-operators, oncall-eng, runtime-engineering, SREs, and solutions engineers.
- Prereqs: access to staging tenant, synthetic traffic harness (load-generator), Grafana + Prometheus test instance, ability to run controlled traffic through routing policies, and a disposable GPU pool in a sandbox region.

Instructor notes

- Keep experiments constrained to the staging environment and pre-approved tenants.
- Each lab run must have a designated "control" observer who does not touch remediation steps; their role is to adjudicate timing and to measure detection latency.
- Expected run length: 60–120 minutes depending on scenario complexity.

Scenario Catalog (short)

| id | name | injected signal | expected SLO impact | median run | primary owner |
|----|------|-----------------|---------------------|------------|---------------|
| S1 | KV cache thrash | sudden drop in KV cache hit rate (simulate re-shard) | p95 latency up, token cost up | 45m | runtime-engineering |
| S2 | Token surge (burst) | 5x request rate to single model variant | queue depth increase, tail latency | 60m | eng-platform |
| S3 | GPU interference | background noisy process on one GPU node | increased variance in latency, dropped async batches | 30–45m | gpu-fleet |
| S4 | Model worker OOMs | controlled process kills for a subset of workers | service errors, failovers to fallback model | 45m | serving-runtime |
| S5 | Region partial outage | network partition to approx 20% of API nodes | increased cross-region routing, cost spike | 90m | infra |

Detailed Scenario Example: S1 - KV Cache Thrash

Purpose: Validate detection when prefix/KV cache coherence breaks and evaluate fallback to cold-cache warmup policy.

Preflight checklist:
1) Ensure staging metric collection is enabled for token-level telemetry and KV cache metrics (kv_cache_hit_rate, kv_cache_evictions, kv_prefix_miss_count).
2) Provision 2 synthetic tenants: one control, one experiment.
3) Confirm canary routing policy points to an alternate model variant for fallback.
4) Schedule the run and notify oncall (Slack #platform-gameday).

Execution steps:
1) Baseline collection: run synthetic traffic for 10m and capture p50/p95/p99 latency, token/sec, and kv_cache_hit_rate.
2) Trigger: run a script to delete cache shards for experiment tenant (sample command):
   kubectl -n sandbox exec deploy/cache-controller -- ./scripts/delete-shards --tenant=exp-01 --shards=3
3) Observe dashboards for: kv_cache_evictions > 100/min, kv_cache_hit_rate drop > 20% absolute, p95 latency increase > 30%.
4) If p95 > SLO threshold for > 3 minutes, initiate fallback: set routing policy to reduced-batch and model-variant B. CLI example:
   redwood ctl route set --tenant exp-01 --policy reduced-batch --variant model-B
5) Continue observation until metrics return to within 10% of baseline.
6) Run postmortem checklist and collect traces for the 30m window surrounding the trigger.

Observation metrics (canonical)

- latency_p50_request_ms, latency_p95_request_ms, latency_p99_request_ms
- token_rate_per_tenant (tokens/sec)
- request_rate_per_model_variant (req/s)
- kv_cache_hit_rate, kv_cache_evictions, kv_prefix_miss_count
- queue_depth_by_shard, worker_error_rate, worker_restart_count
- gpu_utilization_percent (per instance), bg_process_load

Dashboard template library (summary and example queries)

Each template is a collection of small panels (3–7) that should be combined into a single Grafana dashboard. Use panel IDs in the runbook for quick reference. Recommended tags: team=platform, lab=scenario-id, env=staging.

Template A: Degradation Early-Detection (panels)
- Panel 1: SLO burn rate (line)
  Query: sum(rate(errors_total[5m])) / sum(rate(requests_total[5m])) * 100
  Thresholds: warning 0.5%, critical 1.5%
- Panel 2: p95 latency (line)
  Query: histogram_quantile(0.95, sum(rate(request_duration_bucket[1m])) by (le, service))
  Thresholds: warning = 0.8 * SLO_ms, critical = SLO_ms
- Panel 3: kv_cache_hit_rate (single stat)
  Query: avg(kv_cache_hit_rate{tenant=~"exp-.*"}) by (tenant)
  Thresholds: warning drop > 10pt, critical drop > 20pt
- Panel 4: queue_depth_by_shard (bar)
  Query: sum(queue_depth) by (shard)
- Panel 5: token_rate_heatmap (heatmap)
- Panel 6: backend_error_rate_by_code (table)

Template B: Operator Triage View (short)
- Overview: top 5 p95 latency contributors (by route and model)
- Dependency graph snapshot (static image updated every minute)
- Recent deploys and model-version rollouts (events panel)

Alert rule examples

- Simple Prometheus alert for sustained p95 breach (YAML style):

alert: SustainedP95Breach
expr: histogram_quantile(0.95, sum(rate(request_duration_bucket{env="staging"}[2m])) by (le, route)) > 1.0 * scalar(SLO_MS_BY_ROUTE{route="/v1/generate"})
for: 5m
labels:
  severity: page
annotations:
  summary: "p95 latency > SLO for /v1/generate in staging"

- Cost-aware alert for token surge:

alert: TokenBurstDetected
expr: increase(token_count_total{tenant=~"exp-.*"}[5m]) > 50000
for: 3m
labels:
  severity: ticket
annotations:
  summary: "Sudden token volume increase for experimental tenant"

Alert playbook (on-page quick actions)

When page triggered:
1) Confirm alert validity by checking token_rate_per_tenant and request_rate_per_model_variant.
2) Identify the top five routes and the top model variants serving the spike.
3) If token surge exceeds auto-burst threshold, apply tenant soft-throttle:
   redwood ctl throttle set --tenant exp-01 --limit 0.6
4) If fallback is needed, trigger model swap or region failover per runbook.
5) Document actions in the incident timeline and tag the run with lab scenario id.

Runbook snippets (copyable)

- Capture a trace window around the event (example):
  curl -H "Authorization: Bearer $ADMIN_TOKEN" \
    "https://traces.internal.redwood/api/v1/query?start=$(date -d \"-10 minutes\" +%s)&end=$(date +%s)&trace_filter=tenant:exp-01"

- Apply reduced-batch routing:
  redwood ctl route set --tenant exp-01 --policy reduced-batch --reason "lab:kv-thrash"

- Redeploy cache-controller with forced warmup:
  kubectl -n sandbox rollout restart deploy/cache-controller --timeout=5m

Cleanup and post-lab actions

- Revert any routing policies and throttles applied during the lab.
- Rebuild the cache from snapshots where relevant:
  kubectl -n sandbox exec deploy/cache-controller -- ./scripts/warmup-from-snapshot --tenant=exp-01
- Tag the run artifacts and dashboards with labels: lab=scenario-id, run=YYYYMMDD-HHMM, facilitator=name.

Postmortem checklist (template)

- Timeline with timestamps (detection, remediation start, remediation complete)
- Detection latency: time from injection to alert firing and time from alert to operator acknowledgement
- Actions taken and who performed them
- SLO impact: delta p95/p99 and token-cost delta during window
- Lessons learned and next steps (three concrete follow-ups)

Measurement of success & continuous improvement

- Aim to reduce mean detection latency by 25% quarter-over-quarter for the lab scenarios.
- Maintain a runbook coverage metric: 100% of scenarios must have an owner and a dashboard within 2 weeks of addition.
- Track run friction on a simple score (0–5) where operators rate whether the dashboards and alerts made triage straightforward.

Cadence and governance

- Labs run monthly by platform team with rotating facilitator and a different tenant each run.
- Quarterly cross-functional review (runtime + infra + sres + solutions) of dashboards and alert thresholds.
- Change control: any alert threshold changes discovered during a lab must be submitted as a small PR to the alert rules repo and reviewed by at least one SRE.

Appendix: useful queries and quick references

- Top p95 contributors by route (PromQL):
  topk(5, histogram_quantile(0.95, sum(rate(request_duration_bucket{env="staging"}[2m])) by (le, route)) )

- KV cache hit rate (per-tenant):
  avg_over_time(kv_cache_hit_rate{env="staging", tenant=~"exp-.*"}[5m])

- Queue depth alert example (PromQL):
  sum(queue_depth{env="staging"}) by (shard) > 100
