Gameday 2024: Chaos Injection Case Study — Prefix Cache Starvation

Summary
-------
This case study documents the Nov 2024 gameday in us-west-2 where a planned chaos injection (simulated node OOM + high churn) exposed a latent failure mode that caused prefix-cache starvation and tenant-priority inversion. The incident produced a 95th percentile generation latency SLO breach (target 120ms, observed spike to ~420ms for 28 minutes) for a tranche of production customers.

Context and goals
-----------------
- Exercise regional degradations and validate automated fallback policies, cache coherence, and operator runbooks.
- Validate SRE/operator response time and remedial actions for resource-starvation scenarios on the serving runtime.
- Evaluate observability coverage: can we detect cache-quality regressions early and attribute to tenant slices?

Planned experiment
------------------
1) Inject simulated OOM on 3/12 nodes in the us-west-2 GPU pool (controlled, orchestrated via chaos harness).
2) Induce synthetic tenant traffic burst skewed to long-sequence requests for a set of low-priority tenants.
3) Enable a short-lived configuration toggle (test) to reduce global prefix-cache capacity by 40% to simulate metadata pressure.
4) Observe routing, latency, eviction rates, and cost attributions.

Timeline (high level)
---------------------
- 2024-11-12 09:00 UTC — Gameday kickoff; baseline dashboards validated.
- 09:15 UTC — Node OOM injections start; cluster autoscaler triggers but with 3–4 min delay.
- 09:22 UTC — Synthetic tenant burst begins (long context, frequent new prefixes).
- 09:27 UTC — Cache capacity toggle flipped (40% reduction).
- 09:30 UTC — Platform synthetic SLI probe alerts: "prefix_cache_hit_rate_usw2 < 0.6 for 10m" fires.
- 09:40–09:58 UTC — 95p latency breach for tiered tenants; increased cost token usage observed.

- 10:05 UTC — Latency returns to within SLO for most tenants; follow-up cleanup completed by 11:00 UTC.

Impact summary
--------------
- Customer-facing: 28 minutes of elevated latency for ~7% of production requests routed to us-west-2. Surface errors were low (error rate stayed <0.5%), impact primarily latency.
- Economic: transient increase in per-token cost from repeated re-generation and backend retries, estimated additional cost ~$1.8k for the window.
- Operational: identified ambiguous alerting coverage and a missing fast path to bump priority weights for critical tenants during cache degeneration.

Observations and signals
------------------------
- Telemetry: rapid increase in prefix_cache_eviction_rate_usw2 and per-tenant eviction skew. Prometheus query we used:
  - prefix_cache_hit_rate = sum by (tenant) (cache_hits_total{region="us-west-2"}) / sum by (tenant) (cache_requests_total{region="us-west-2"})
  - eviction_rate = increase(cache_evictions_total{region="us-west-2"}[5m])
- Tracing: KV cache miss traces showed repeated long-tail lookups hitting remote blobstore (200–400ms additional latency per miss).
- Router behavior: Smart routing attempted cross-region failover but constrained by regional deployment pins for dedicated tenants, leading to uneven load distribution.
- Tenant priority inversion: the eviction policy used a global LRU with tenant-weighted tokens, but under metadata pressure the implementation favored recency over configured tenant weight, causing high-priority tenants to lose cached prefixes.

Root cause analysis
-------------------
Primary causes (ordered):
1) Cache eviction algorithm gap: an implementation detail in the weighted-LRU fast path ignored per-tenant weight during accelerated eviction windows. This was triggered by reduced cache capacity combined with high churn.
2) Insufficient TTL isolation: shared prefix cache for variable-length contexts allowed long-context synthetic workloads to occupy the same cache region as short-context, high-throughput tenants.
3) Alerting gaps: existing alert "prefix_cache_hit_rate" was aggregated across the region and did not include per-tenant or per-slice triggers; by the time the regional alert fired, high-priority tenants were already degraded.
4) Runbook friction: the operator runbook required manual escalation to change tenant weights (config change propagated via the control plane), a path that took ~7 minutes to execute and validate.

Mitigations and follow-ups (short/medium/long-term)
---------------------------------------------------
Short-term (emergency during gameday) — completed:
- Emergency bypass: toggled per-tenant cache isolation flag for two high-priority tenants to allocate dedicated prefix-sets (runtime config via control plane):
  - curl -X POST https://control-plane.internal/api/v1/runtime-config 
    -d '{"region":"us-west-2","tenant":"TENANT-CRITICAL-1","prefix_cache.isolated":true}' 
- Temporarily increased tenant weight for critical tenants to 3x via the control plane to prevent eviction.
- Rebalanced synthetic traffic to limit new-prefix churn while cluster recovered.

Medium-term (2–6 weeks) — in progress / scheduled:
- Implement correctness fix for weighted-LRU fast path to respect tenant weights even during accelerated eviction. (owner: eng-serving-runtime/kernel_team; due: 2025-03-01)
- Add per-tenant prefix-cache SLI rollups and dashboards, with alert rules:
  - Alert: PrefixCacheDegradationPerTenant
    - Trigger when: prefix_cache_hit_rate{tenant="$TENANT"} < 0.7 for 5m
    - Pager: oncall-platform
- Add TTL bucketing in the cache allocator so long-context prefixes cannot evict short-context hot prefixes. (owner: eng-serving-runtime/cache_team; due: 2025-02-15)
- Automate a rapid operator action: a new CLI helper and Control Plane API to set temporary tenant priority weights with a 1-click Console button and rollback. (owner: eng-platform/tools; due: 2025-02-28)

Long-term (quarterly roadmap) — planned:
- Regional redundancy improvements: reduce failover friction for dedicated tenants by allowing controlled cross-region evictions or warm-standby routing when local cache degraded. (product + eng; Q2 2025)
- E2E canary that exercises cache eviction paths under simulated prefix churn monthly.
- Cost-sensitive heuristics to detect repeated regeneration loops and auto-throttle offending clients.

Runbook snippet: immediate operator steps for prefix-cache degradation
--------------------------------------------------------------------
1) Confirm alert and scope: check dashboard "Prefix Cache Health — REGION" and run:
   - promql: topk(20, (sum by (tenant) (cache_hits_total{region="us-west-2"}) / sum by (tenant) (cache_requests_total{region="us-west-2"})))
2) If high-priority tenant hit-rate < 0.7: set isolation flag for tenant via control plane (example above).
3) If overall eviction_rate > 200/min: reduce incoming new-prefix churn by applying soft-rate-limiting on synthetic/integration tenants:
   - curl -X POST https://control-plane.internal/api/v1/traffic-controls -d '{"region":"us-west-2","selector":"tags:integration","qps":10}'
4) To temporarily bump tenant weight:
   - rtictl set-weight --region=us-west-2 --tenant=TENANT-CRITICAL-1 --weight=3 --expires=10m
5) Monitor: cache_hit_rate, eviction_rate, downstream 95p latency, and token_cost_rate.
6) When stable for 15 minutes, roll back control-plane temporary flags and open follow-up ticket.

Lessons learned and recommendations
----------------------------------
- Surface per-tenant cache SLIs by default for multi-tenant components; region-level aggregates hide targeted degradations.
- Implement isolation primitives earlier in the caching stack (TTL buckets, reserved slots for critical tenants).
- Reduce operator friction: add validated fast paths for emergency weight changes; document rollback safeguards.
- Include synthetic churn scenarios in routine canaries; ensure canaries exercise eviction and rehydration cycles.
- Improve alert signal fidelity to reduce mean time to detect and mean time to mitigate.
