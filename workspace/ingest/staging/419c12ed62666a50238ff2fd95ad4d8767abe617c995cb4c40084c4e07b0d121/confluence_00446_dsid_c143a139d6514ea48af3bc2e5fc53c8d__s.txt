SLO Composition for Multi‑Tenant Model Serving

Purpose

This page defines Redwood's standard approach for composing, allocating, and monitoring Service Level Objectives (SLOs) across multi-tenant model-serving surfaces (hosted API, Dedicated pools, and Private runtime sidecars). The goal is predictable customer experience, fair resource isolation, and measurable unit economics that feed billing and capacity planning.

Scope

- Applies to: text generation, chat streaming, embeddings and reranking endpoints that are served from a shared runtime (multi-tenant GPU pools and multi-variant model deployments).
- Excludes: one-off batch-only offline workloads and single-tenant appliance deployments with explicit per-customer SLA contracts.

Key principles

1) Tenant-first SLOs: SLOs are expressed from the consumer's perspective (e.g., 95th percentile request latency for a customer route), not only internal pod metrics.
2) Composability: Service-level SLOs are built from per-route, per-variant, and infra SLO primitives using explicit weighting and error budgets.
3) Isolation and fairness: Composition must support throttling and fallback policies that avoid noisy-neighbor effects.
4) Cost-awareness: SLO formulas must account for cost amplification (model size, quantization, batch size) so capacity planning and billing reflect true unit economics.

Definitions and primitives

- route: the API surface configured by a customer (e.g., /v1/generate with model=redwood-alpha).
- variant: an individual model binary/configuration (fp16, q4_0, q8_0) served behind a route.
- infra_slo: cluster-level SLOs (e.g., GPU prewarm availability, queue latency).
- tenant_slo: per-tenant observable (latency_p95_ms, error_rate_5m, token_throughput_rps).

SLO composition model (formula)

We define a deterministic composition function that aggregates variant-level observations into route-level SLOs and then into service-level commitments. The canonical form: 

route_slo = sum_i(weight_i * variant_slo_i) + infra_risk_margin

Where: 
- weight_i is the traffic-weight fraction for variant i over a sliding window (default 1-minute).
- variant_slo_i is the measured objective (e.g., p95 latency) for that variant.
- infra_risk_margin is a fixed offset derived from infra_slo violations (see infra interaction).

Example: p95 latency composition

If variant A (weight 0.7) has p95=120ms and variant B (weight 0.3) has p95=260ms, route_p95 = 0.7*120 + 0.3*260 = 162ms.

Per-tenant SLO tiers

We standardize on three tenant tiers for hosted and dedicated customers. Private deployments may map these to contract terms.

| Tier | Commitments (example) | Error budget 
|------|-----------------------|----------------|
| Standard | p95 <= 250ms, available 99.9% (monthly), error_rate < 0.5% | 0.1% monthly 
| Premium  | p95 <= 150ms, available 99.95% (monthly), error_rate < 0.2% | 0.05% monthly 
| Latency-Optimized | p95 <= 80ms, available 99.99% (monthly), error_rate < 0.1% | 0.01% monthly

Note: These are customer-facing commitments. Internally we map them to route and variant objectives with explicit headroom and safety margins.

Infra interaction and risk margins

Infra SLOs (GPU prewarm time, queueing time, streaming packet loss) feed a risk score R in [0,1] every minute. We add an infra_risk_margin_ms = baseline_margin_ms * R to composed latency SLOs. Baseline_margin_ms = 40ms by default for shared pools, 10ms for Dedicated.

Monitoring and queries

Instrumentation must expose the following time series per (tenant, route, variant):
- redwood.requests.latency_ms.p95
- redwood.requests.errors.count (HTTP 5xx, model-runtime-failure)
- redwood.tokens.generated.total
- redwood.queue.wait_ms.p50/p95

Example PromQL for tenant p95 latency (1m lookback):

  histogram_quantile(0.95, sum by (tenant, le) (rate(redwood_requests_latency_bucket[1m])))

Alerting thresholds (recommended)

- Alert: tenant_p95_exceeded
  - Condition: tenant_p95 > committed_p95 for 3 consecutive 1m windows
  - Severity: P2 for Standard, P1 for Premium / Latency-Optimized
  - Runbook: see runbook id: eng-sre/runbooks/tenant-slo-breach

- Alert: infra_risk_degraded
  - Condition: infra_risk_score > 0.6 for 5m
  - Severity: P1

Operational behaviors on SLO pressure

1) Reactive traffic shaping (automated): when a tenant exceeds error budget and infra risk > 0.5, system applies soft-throttles (rate limit 10% reductions, per-tenant) and moves lower-priority traffic to fallback variants.
2) Canary-aware rollbacks: deployment changes that increase variant tail latency by > 15% must be automatically rolled back (see ADR: canary-mesh-guidelines).
3) Billing impact: sustained tier violations >72h triggers account review and cost-corrective actions (credits, prioritized capacity purchase offers).

SLO spec (YAML example)

  kind: SLO
  tenant: example-corp
  route: /v1/generate
  metric: latency_p95_ms
  objective: 150
  window: 30d
  weights: 
    variants:
      - name: redwood-alpha-fp16
        weight: 0.8
      - name: redwood-alpha-q4_0
        weight: 0.2

CLI integration

To apply a tenant SLO (engineers):

  # redwoodctl is the internal control-plane CLI
  redwoodctl slo apply -f tenant-slos/example-corp-slo.yaml --env=prod

Rollout and validation checklist (owners must complete before going GA)

1) Define per-variant telemetry exports (owner: runtime-team).
2) Configure composition weights and initial infra_margin (owner: eng-sre).
3) Smoke tests: synthetic traffic that exercises 99th percentile flows for 24h (owner: perf-team).
4) Observability validation: dashboards, alerts, and sampled traces available for tenant (owner: eng-platform).
5) Assume-failure drills: simulate node preemption and verify fallback routing (owner: eng-serving-runtime).

Ownership and governance

- Runtime: implementation of variant-level metrics and weight reporting — eng-serving-runtime team.
- SLO system & alerts: eng-sre.
- Billing & cost mapping: finance-legal + product (billing-data-pipeline).
- Policy & tier definitions: product team (final approval).

Appendix: Examples and edge cases

1) Cold-start amplification: for routes with >25% cold starts in a 5m window apply an extra cold_start_penalty_ms of 200ms to the composed SLO and escalate to eng-sre.
2) Skewed variant traffic: If any variant weight < 0.05 but variance in p95 > 3x other variants, ignore that variant's p95 and use cluster-median instead (to avoid noisy short-lived canaries impacting route commitments).
3) Private deployments: customers may opt-in to "contractual isolation" where infra_risk_margin is negotiated and removed from public commitments; documentation lives in eng-private-deployments/day-2-ops.
