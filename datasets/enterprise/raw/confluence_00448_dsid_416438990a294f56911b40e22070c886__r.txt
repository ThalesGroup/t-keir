Runtime experiment signal catalog and hypothesis matrix

Purpose
-------
This document centralizes the signal definitions, collection guidance, and hypothesis matrix for runtime experiments across Redwood's serving stack. It is intended for engineers running controlled performance experiments, A/B rollouts, profiling campaigns, and benchmark suites. The goal is to reduce ambiguity about which telemetry to use for which kind of experiment and to standardize evaluation heuristics and rollback criteria.

Scope
-----
Applies to hosted, dedicated, and private runtime variants. Focused on: request path telemetry, kernel scheduling metrics, KV cache signals, batching utilization, and cost-attribution signals used by Redwood Optimize and runtime autoscalers. Not a replacement for incident runbooks; where an experiment reveals an incident, follow the incident playbooks in oncall_and_incident_response.

Quick summary (one-line)
----------------------
Use this catalog to: (1) select 3–5 core signals for hypothesis acceptance, (2) set primary/secondary thresholds, (3) follow the step-by-step experiment run, and (4) export the result to the benchmark suite for regression tracking.

Signal catalog and rationale
---------------------------
Each signal below includes: name, cardinality (per-request / per-slot / host-level), sampling guidance, expected distribution shape, primary/secondary use, and recommended alert thresholds for experiments.

1) request.latency_ms.{p50,p95,p99} (per-route, per-model)
- Cardinality: per-request aggregated by route/model/region.
- Sampling: full for release-level A/B; 10% for long-running smoke experiments.
- Distribution: heavy right tail; expect multiple modes if mixed sequence lengths.
- Use: Primary for latency SLO experiments.
- Experiment thresholds: delta(p95) <= +10% relative for canary acceptance; delta(p99) <= +20% triggers manual triage.

2) kernel.queue_depth_avg (per-device, per-kernel-type)
- Cardinality: device,kernel-type (attention, ff, matmul).
- Sampling: continuous at 1s resolution.
- Distribution: near-zero for elastic workloads; spikes indicate contention.
- Use: Secondary signal to explain latency regressions.
- Thresholds: sustained > 50% of peak slot count for >30s => consider reducing concurrency or increasing slots.

3) kvcache.hit_rate (session-id, per-model)
- Cardinality: session-level aggregated to route/model.
- Sampling: computed on write-window (1m).
- Distribution: dependent on prompt reuse; typical baseline for chat products is 0.35–0.85.
- Use: Primary when testing prefix caching or warmup strategies.
- Thresholds: drop > 15 percentage points relative -> expect token cost increase; auto-fallthrough if paired with latency increase.

4) batch_utilization_pct (executor-pod, per-1m)
- Cardinality: executor-pod.
- Sampling: 10s rolling window.
- Distribution: multi-modal depending on client batching.
- Use: Primary for cost-efficiency experiments; correlate with tokens/sec.
- Thresholds: sustained < 20% while throughput stable suggests misconfiguration (e.g., slice size mismatch).

5) kernel.exec_time_ms.{mean,95th} (per-kernel-type, per-device)
- Cardinality: kernel-type, device.
- Use: Diagnosing scheduling vs kernel inefficiency.
- Thresholds: > +25% mean vs baseline => flag for kernel rollout hold.

6) memory.gpu.free_mb and memory.gpu.fragmentation_pct (node-level)
- Use: Safety signals for private/on-prem experiments; fragmentation > 60% + free_mb < reserve -> OOM risk.

7) cost.per_token_usd (route, model_variant)
- Use: Primary for Optimize-driven experiments.
- Calculation: (infra_cost + reserved_amortization) / tokens_generated.

Instrumentation and collection guidance
-------------------------------------
- Services and names: rdx-runtime-dispatcher (ingest), rdx-kernel-agent (device-facing), rdx-kvcache (session store), rdx-metrics-aggregator, rdx-benchmark-runner. Tag metrics with: service, cluster, region, model, model_variant, route, experiment_id, canary_group.
- Metric format: Prometheus-style timeseries with labels above; export to metrics pipeline with 10s scrape where possible and 1s for kernel-level counters.
- Logs: include structured JSON request events with fields: request_id, route, model, seq_len_in, seq_len_out, kernel_hints, start_ts, end_ts. Example: 

```json
{
  "request_id": "r-7f3a2c",
  "route": "chat-default",
  "model": "open-vicuna-13b-quant-v2",
  "seq_len_in": 64,
  "seq_len_out": 128,
  "kernel_hints": "sharded-attn",
  "start_ts": "2027-02-10T15:12:03.123Z",
  "end_ts": "2027-02-10T15:12:03.379Z"
}
```

Benchmark config and expected artifacts
--------------------------------------
When converting an experiment to a benchmark, include a config file. Minimal example (YAML):

```yaml
benchmark_name: kvcache-warmup-vs-none
model: rdx-llama-30b-q4
routes: [chat-default]
workload_profile: production-sampled-2027-01
duration: 30m
concurrency: 64
metrics: [request.latency_ms.p95, kvcache.hit_rate, batch_utilization_pct, cost.per_token_usd]
export_to: perf-db://benchmarks/kvcache-warmup-vs-none-2027-02-10
```

Expected artifacts:
- raw telemetry (prometheus histograms + traces)
- per-request logs (parquet)
- experiment summary (markdown) with stat tests (see below)

Hypothesis matrix and statistical evaluation rules
--------------------------------------------------
Use the following convention for experiment outcomes: Primary signals (1–2) must meet acceptance thresholds; secondary signals should exhibit no regression beyond soft thresholds.

- Hypothesis example: "Enabling async kvcache prefetch will reduce p95 latency by >= 8% without increasing cost per token by > 5%."
- Primary signals: request.latency_ms.p95 (delta <= -8%) and kvcache.hit_rate (delta >= +6 percentage points).
- Secondary signals: cost.per_token_usd (delta <= +5%), kernel.queue_depth_avg (no sustained >75% saturation).

Statistical rules:
1) Use bootstrap resampling over per-request latencies; report 95% confidence intervals for deltas.
2) Accept only if delta and CI both exceed the acceptance threshold in the favorable direction.
3) For cost signals where variance is high, cap sample variance by stratifying on seq_len buckets: [0-64, 65-256, 257+].

Experiment runbook (step-by-step)
--------------------------------
1) Define experiment_id and register in the experiments board (team-wiki experiments index).
2) Select the core signals (max 5). Mark primaries.
3) Create benchmark config and a dedicated metrics dashboard with experiment_id filter.
4) Run warmup: 10 minutes at 25% target load to populate caches.
5) Execute canary: 5–10% traffic for 30 minutes.
6) Collect telemetry and run stats pipeline: 
   - Command: rdx-benchmark-runner analyze --experiment-id EXP123 --save-summary ./summary.md
7) Evaluate acceptance per hypothesis matrix.
8) If accepted, escalate to rollout plan (see rollout checklist). If rejected, capture triage notes and create a follow-up profiling ticket.

Rollout checklist and safety gates
----------------------------------
- Gate 1 (canary acceptance): primary signals meet thresholds; no kernel exec_time regression > 25%.
- Gate 2 (stability hold): run 2h at 50% traffic with continuous monitoring; no alerts fired.
- Gate 3 (full rollout): ramp to 100% over 3 steps (50%, 75%, 100%) with 10–20 minute hold per step.

Rollback criteria (automated and manual)
---------------------------------------
Automated rollback (preferred): any of:
- request.latency_ms.p99 increases > 40% for > 2 minutes.
- kernel.queue_depth_avg sustained > 80% for > 60s and accompanied by increase in request errors.
- memory.gpu.fragmentation_pct leads to OOM events.

Manual rollback: triggered by oncall if triage finds systemic regression in model quality (see eval signals) or client-facing error rates > 0.5% over 10m.

Tracing and attribution guidance
-------------------------------
- Ensure each request carries experiment_id, route, and model_variant. Span composition should include: dispatcher -> scheduler -> kernel-agent -> kvcache.
- For expensive experiments, enable 100% traces for canaries for 5–10 minutes to capture tail behaviors.

Examples: short triage checklist for a regression
------------------------------------------------
1) Confirm metric delta with raw per-request data (avoid dashboard smoothing artifacts).
2) Check kernel.exec_time_ms by kernel-type to see if new kernel hints caused regressions.
3) Inspect kvcache.hit_rate and warmup windows; check prefetch logs.
4) Run microbench: single-request microbench with the failing profile using rdx-runtime-local-runner.
5) If kernel-level, annotate a kernel snapshot and assign to kernel-team for kernel rollout revert.

Appendix A — canonical metrics queries
--------------------------------------
PromQL examples (simplified):
- p95 latency: histogram_quantile(0.95, sum(rate(request_latency_seconds_bucket{route="chat-default",experiment_id=~"EXP.*"}[1m])) by (le))
- kvcache hit rate: sum(rate(kvcache_hits_total{model=~".*"}[1m])) / sum(rate(kvcache_requests_total{model=~".*"}[1m]))

Appendix B — experiment result template (markdown)
--------------------------------------------------
- experiment_id: EXP123
- hypothesis: text
- primary_signals: list with baselines and deltas
- secondary_signals: list
- raw_artifacts: link to perf-db
- statistical_summary: link
- verdict: accept | reject | inconclusive
- triage_notes: free text
