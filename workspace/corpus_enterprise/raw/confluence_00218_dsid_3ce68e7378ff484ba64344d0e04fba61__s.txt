Service Fidelity Spotlight — End-to-end Benchmark & Kernel Impact Mapping Protocol

Overview

This page defines a repeatable, cross-team protocol for spotlighting service-level fidelity changes (quality vs. cost/latency) and mapping those changes to kernel scheduling and runtime subsystems. Use this protocol when onboarding a new model variant, validating a quantization rollout, or investigating regressions in production SLOs. The goal: produce a minimal, reproducible benchmark and instrumentation bundle that ties observable customer impact to kernel-level signals and actionable runbook steps.

Scope

- Applies to: runtime-dispatcher, kernel-scheduler, kvcache-store, gpu-dispatcher, request-multiplexer, and model-variant-adapter.
- Not covered: client-side SDK behavior, non-inference storage tiers, or billing pipelines (except where cost-per-token is measured).

Success Criteria

- A reproducible benchmark (input corpus + harness) that reproduces the customer-visible regression within ±5% on p95 latency and token-efficiency.
- Mapped kernel signals (GPU occupancy, kernel-duration histogram, warp-stall rate, memory-copy latency) correlated with at least one service-level metric.
- A short remediation runbook with owner and rollback clause that can be executed within a 2-hour operational window.

Quick summary of metrics to capture (minimum):

| Metric | Level | Target window | Notes |
|---|---:|---:|---|
| p95 request latency (inference path) | service | 60s | end-to-end, excluding client network |
| p99 tail latency | service | 60s | critical for SLO signoff |
| tokens/sec per-GPU | infra | 60s | aggregated by gpu-dispatcher |
| kernel duration (histogram) | kernel | 10s | per-kernel id, percentile buckets |
| GPU occupancy | kernel | 10s | % of active warps/SMs |
| KV cache hit ratio | service | 60s | per-session prefix reuse |
| end-to-end quality delta | application | corpus-run | BLEU/ROUGE/LL-judge score per prompt set |

Bench harness and corpus

1) Choose a narrow corpus that represents the failing surface: typically 200–1000 prompts drawn from production replay (anonymized) or curated prompt set.
2) Define a deterministic run profile: request concurrency, sequence length distribution, and per-request stop tokens.
3) Use the benchmark harness located at infra/bench/harness (team artifact) with the following example invocation: 

# Example CLI (internal lab machine with GPU access)
# runs 500 prompt-replays with concurrency=16 against a local runtime build
./bench/harness \
  --target http://localhost:8080/v1/generate \
  --corpus ./corpora/fidelity-spotlight/replica-2026.jsonl \
  --concurrency 16 \
  --seqlen-dist ./seqlen/prod-trimmed.yaml \
  --collect-kernel-traces /tmp/kernels.trace \
  --tag "fidelity-spotlight-$(date +%Y%m%d)"

Instrumentation checklist (kernel -> service mapping)

- Enable per-kernel tracing: kernel-scheduler must be started with KERNEL_TRACE=1 and trace export to a path with timestamps in nanoseconds.
- Correlate each request id with kernel trace id via the request-provenance header. Ensure request-provenance is present in the harness.
- Capture GPU metrics (SM utilisation, memory bandwidth, PCIe latency) using gpu-exporter at 5s resolution for the run.
- Collect runtime-level traces (request timeline) with trace level=INFO and the following fields: request_id, model_variant, sequence_length, kvcache_hit, chosen_kernel_hint, gpu_node.

Causal kernel-impact mapping procedure (numbered step playbook)

1. Baseline run: execute the bench harness against the previously certified model variant and collect all signals. Label artifact as baseline-<tag>.
2. Test run: execute the harness against the candidate model/quantization/kernel-change. Label artifact as candidate-<tag>.
3. Compute deltas for service metrics (p95/p99, tokens/sec, error-rate, quality delta). If deltas are <= threshold (p95 delta < 7%, quality delta within guardrail), proceed to step 7.
4. If regression observed, run kernel-signal diffing: align kernel traces by request_provenance and compute per-kernel-duration deltas and stall-rates.
5. Identify top-3 kernel IDs with largest duration increase and check associated inputs (sequence length, batch size, kvcache-hit). If top kernels map to attention or fused-matmul kernels, flag possible memory layout or schedule regressions.
6. Cross-check scheduling signals: examine scheduler decisions for these requests — preemption events, slice boundaries, and co-scheduled kernel sets. If scheduler consistently inserts extra preemption/slice boundaries for candidate, add scheduling hypothesis to incident doc.
7. Re-run targeted microbenchmarks for suspect kernels (single-kernel isolations) with 5–10% input perturbations to confirm sensitivity. Document command used and raw kernel profiles.
8. Produce remediation plan: configuration tweak (kernel-flag or scheduler param), model pin, or rollback. Include risk assessment and estimated cost impact.

Profiling playbook excerpts (how to capture good traces)

- Prefer stratified-capture: sample 1 in N requests for full kernel trace but collect light-weight metrics for all (tokens/sec, kv-hit). N depends on cost budget; default N=5.
- For tail investigations, use targeted 100% tracing on a small cohort of requests that hit the fault surface.
- Always correlate traces with the benchmark tag and git SHA of runtime to enable fast bisects.

Benchmark analysis checklist (deliverable items)

- Repro artifacts: corpus, harness args, kernel traces, gpu-exporter TSV, runtime log bundle, and model SHA.
- A concise findings table (1–2 pages) answering: What regressed? Which kernels changed? Which scheduler behavior changed? What is the recommended remediation?
- Estimated rollback cost and performance delta if remediation is applied.

Release notes & labelling template (short)

When a kernel or scheduler change is promoted to canary or prod, include the following in the release note: 

- Change ID: release/kernel-<X> or release/scheduler-<Y>
- Short description: what the change modifies
- Risk summary: p95 impact observed in lab runs (absolute and percent), top kernels affected
- Canary checklist: yes/no (list of required traces and metrics)
- Rollout gates: automatic rollback threshold (p99 increase > 15% or BLEU drop > 2 points)

Known-issues cataloging format (how to add an entry)

When you discover a novel kernel or scheduling-related issue, create an entry in the known-issues catalog with these flattened fields (one-line examples):

- id: KERNEL-2026-0123
- title: unexpected memcpy on model swap causing p99 spikes
- symptom: intermittent p99 spikes when model-variant-adapter performs hot-swap after session affinity change
- kernel_evidence: kernel COPY_00 duration increased by 10x for affected requests
- workarounds: reduce per-node max-connections to avoid hot-swap batching; disable aggressive prefetcher
- owner: Evan Ross

Runbook snippet (emergency mitigation for kernel regressions)

1. Triage: confirm alerts (p99 spike and tokens/sec drop) and fetch latest bench harness run tag.
2. Validate: run a short 5–10 minute harness with request-provenance set to 'triage-<incident>' against a replica canary pool.
3. If kernel duration anomaly reproduced, scale down candidate pool and route traffic to baseline variant (mechanism: runtime-routing annotate route/variant with fallback=true).
4. If routing not available, execute rapid rollback to previous runtime image via k8s rollout undo for runtime-dispatcher.
5. Collect post-mitigation traces and attach to incident ticket.
