Proactive Capacity Sentinel & Incident Evidence Capture Playbook

Summary
-------
This playbook defines the Proactive Capacity Sentinel (PCS): a small, deterministic control loop that pre-emptively earmarks capacity or throttles low-priority tenants when leading SLO signals indicate an elevated probability of tail-latency or throughput saturation. It also defines the incident evidence-capture template tied to any PCS action so that post-incident reviews have consistent, machine-readable artifacts.

Scope
-----
- Services: model-serving* (all inference frontends), routing/ingress, cache layers (KV prefix cache), and autoscaler controllers.
- Signals: SLO burn rate, 99.9th latency spikes, queue depth, model hot-pool hit rate, and GPU memory pressure.
- Audience: oncall SRE, runtime engineers, capacity planners, and incident reviewers.

Goals
-----
- Detect stress before hard SLO breaches and apply repeatable mitigation actions within the SLO guardrail.
- Capture consistent incident evidence (telemetry snapshot, allocation decisions, request samples) for deterministic post-incident analysis.
- Ensure mitigations are reversible and measurable (pre/post metrics).

Owner & Escalation
------------------
- Primary owner: SRE-Serving (rotation lead).
- Pager: SRE (page policy: P1-P2 per existing oncall roster).
- Escalate to Runtime Reliability if mitigation requires model-hotpatch or rollback.

SLO mapping and priority tiers
-----------------------------
Map PCS actions to SLO classes and tenant priority. Use the following priority tiers when deciding mitigation severity:
1) Critical tenants (enterprise SLA) — minimal preemption; prefer burst capacity reservation.
2) Standard tenants (paid) — allow soft degradation (token-priority throttles).
3) Best-effort (free/experimental) — eligible for immediate soft-eviction and cache eviction.

Signals & thresholds (reference table)
--------------------------------------
Use this table as the canonical signal-to-action mapping. These thresholds are tuned for a 100-GPU serving cluster typical of a shard. Adjust per-cluster using the cluster tuning sheet.

Signal | Window | Threshold | Action (PCS) | Escalation
------ | ------ | --------- | ------------ | ----------
SLO burn rate (end-to-end) | 5m | > 3x expected | Stage 1: increase reserved burst / enable prewarm hot-pool | If persists 10m escalate
99.9 latency (inference) | 1m | > SLO by 20% | Stage 1: enable request shaping for tier 3; reduce batch sizes for new requests | Escalate to runtime after 5m
Queue depth (router) | 30s | > 75% of queue limit | Stage 2: enable backpressure (reject with 429 for low-priority token classes) | Immediate page if critical tenants impacted
GPU memory pressure | 1m | > 85% | Stage 2: soft-evict best-effort models, reassign weights to different GPU pools | Page runtime reliability
Model hot-pool hit rate | 5m | < 60% | Stage 1: prewarm missing models on a small hot-pool; increase cache TTLs for frequently-used prefixes | Monitor for additional regressions

Runbook: Proactive mitigation steps
-----------------------------------
1) Detect: Observe PCS alert firing in AlertManager and Slack #sre-ops.
2) Triage: Confirm the signal via the SLO dashboard (last 15m) and the cluster metrics (GPU/memory/queue).
3) Decide: Apply the least-disruptive action that would reduce the leading signal per the table above. Decision factors:
   - Which tenant classes are affected?
   - Is this localized to a cluster or global?
   - Do we have burst capacity available?
4) Execute: Follow one of the standardized mitigations (examples below). Record the action using the PCS Evidence Recorder (CLI).
5) Observe: Wait 60–180s for measurable change. If signal improves, move to monitor and schedule a post-incident evidence handoff. If not, escalate and apply Stage 2 mitigations.
6) Recover: Roll back non-persistent mitigations (e.g., throttles) once metrics are stable for two consecutive windows.
7) Post-incident: Run the evidence extraction and submit to the incident review board (IRB).

Standardized mitigations (examples)
----------------------------------
- Reserve burst capacity (Preferred for tier 1): apply API call to capacity-orchestrator to allocate N GPUs for 5–15 minutes.
- Hot-pool prewarm: call runtime-prewarm --model <id> --pool small.
- Token-priority shaping: update token-priority policy to reduce qps for token classes low-priority by 30%.
- Soft-eviction: move best-effort model allocations off overloaded GPUs (graceful drain).
- Batch-size reduction: for affected model route, reduce max_batch_size from 64 to 32 via model-routing-config.

CLI / API snippets (examples)
----------------------------
- Reserve burst GPUs (capacity-orchestrator):
  rcli capacity reserve --cluster shard-east-1 --gpus 4 --ttl 10m --reason "PCS preemptive reserve"

- Prewarm model hotpool (runtime):
  rcli runtime prewarm --model-id redwood-llama-13b-q4 --pool small --instances 4

- Apply token shaping (policy):
  curl -X POST https://ops-api.internal/policies/token-shape -H 'Authorization: Bearer $OPS_TOKEN' -d '{"policy":"tier3:0.7"}'

Alert rule examples (Prometheus-style YAML)
-----------------------------------------
# Simplified rule: SLO burn-rate heavy
- alert: PCSSloBurnRateHigh
  expr: (sum(rate(end_to_end_slo_burn[5m])) / sum(rate(expected_slo_burn[5m]))) > 3
  for: 1m
  labels:
    severity: warning
  annotations:
    runbook: "confluence://eng-sre/reliability-initiatives/proactive-capacity-sentinel-and-evidence-capture-playbook-2026"

Incident evidence capture (required fields)
------------------------------------------
Every PCS action MUST be accompanied by a completed evidence record. The PCS Evidence Recorder auto-populates most fields; the oncall must verify and add commentary where needed. Required fields (machine-readable):
- incident_id (generated by PCS recorder)
- timestamp
- cluster_id
- signal_type and value
- action_taken (enum: reserve_burst, prewarm, token_shape, soft_evict, reduce_batch)
- action_owner (SRE oncall)
- affected_tenants (list of tenant ids)
- pre_snapshot_metrics_location (s3 path /metrics-snapshots/<incident_id>/before.json)
- post_snapshot_metrics_location (s3 path /metrics-snapshots/<incident_id>/after.json)
- sample_requests_path (s3 path /request-samples/<incident_id>.ndjson)
- notes (free text)

Evidence capture checklist (manual)
----------------------------------
1) Run: pcs-recorder capture --incident-id $ID --cluster $CLUSTER --action reserve_burst
2) Upload request samples: pcs-recorder samples collect --duration 30s --out s3://...
3) Snapshot GPU allocations: rcli capacity snapshot --cluster $CLUSTER --out s3://...
4) Add rationale and expected rollback plan to notes.

Post-incident actions and IRB handoff
------------------------------------
- Within 24 hours: SRE oncall attaches the evidence record to the incident ticket and marks the incident for IRB review if the action changed allocation or impacted tier 1 tenants.
- Within 72 hours: Capacity planner runs a stress-profile simulation using the pre/post snapshots and submits a remediation proposal (scale, partitioning, or config change).
- Within 7 days: Implement low-risk config fixes (cache TTL tuning, token policy default change).

Measurement and KPIs
--------------------
Track these KPIs to evaluate PCS effectiveness:
- Mean time from PCS alert to mitigation deployment (goal &lt; 120s).
- Fraction of PCS actions that prevented a formal SLO breach (goal &gt; 80%).
- Number of IRB escalations triggered by PCS actions (trend down).

Safety & rollback guidance
-------------------------
- All PCS actions must be reversible with a documented rollback command. Example: rcli capacity release --reservation-id <id>.
- For any action that moves tenant allocations, maintain a custody log in the evidence record.
- For model hotpatches or permanent model config changes, follow the dedicated runtime hotpatch runbook (link in Related Pages).

Notes
-----
This playbook is intentionally conservative with tenant disruption for tier 1 customers. The PCS is a pragmatic, operational bridge between SLO monitoring and capacity actions—we expect tuning and incremental automation. If you are implementing automation hooks to the PCS, coordinate with the runtime team to ensure safe rate limits and circuit-breakers are enforced.
