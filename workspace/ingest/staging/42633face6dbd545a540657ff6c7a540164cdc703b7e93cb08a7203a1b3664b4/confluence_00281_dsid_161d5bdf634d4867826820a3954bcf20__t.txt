Tenant Liveness SLA and Data Consistency Attestation

This document defines the SLOs, acceptance tests, attestation checklist, and operator playbook for tenant liveness and cross-node data consistency in Private (VPC/on-prem) deployments. It captures the contract Redwood requires customers to verify during onboarding and that operators must monitor and remediate during steady state and upgrades.
Overview
This page establishes a combined liveness (availability/latency) and data-consistency attestation that must be validated for every private deployment (VPC or on-prem). The goal is to give customers and field operators a single, reproducible acceptance and day-2 verification workflow that covers: network readiness, control-plane heartbeats, KV/replicated cache consistency, model artifact consistency, and safe rollback triggers.

Scope
- Applies to: Private Deployments (VPC, on-prem, air-gapped) provisioned by Redwood.
- Components covered: tenant-proxy, runtime-pool (GPU nodes), KV-cache (replicated), control-plane gateway, model-artifact store, telemetry pipeline.

SLOs and Acceptance Criteria
1) Tenant Liveness SLOs (per-tenant):
   - Availability: 99.95% over a rolling 30-day window for the tenant API route(s).
   - P95 latency: <= 120ms for control-plane token validation and <= 300ms for inference cold-starts (first request to a model variant).
   - Error budget: max 0.05% 5xx responses for production customer routes per week.

2) Data Consistency & KV-cache Contract:
   - Replication Lag: median replication lag < 50ms, 99th percentile < 500ms across nodes under nominal load.
   - Read-after-write: immediate read-after-write must succeed for prefix writes used by in-flight sessions 99.9% of the time.
   - KV Eviction Safety: eviction should not lead to observable incorrect outputs for pinned-session workloads.

3) Model Artifact Consistency:
   - Checksum Agreement: model-image and weights checksums must match across all runtime nodes before routing.
   - Rollout Window: canary rollout to 5% of traffic for at least 15 minutes with no correctness regressions before increasing.

Operator Attestation Checklist (pre-acceptance and periodic)
Network: BGP/peering validated, TTL and MTU tested end-to-end.
Control plane: heartbeat=OK on all managed control-plane gateways; certificates valid and not expiring within 30 days.
KV cluster: replication status=healthy; replication-lag median <50ms observed during 10-minute soak.
Artifacts: model-image checksums consistent on all candidate nodes; image signing verified.
Telemetry: metric ingest pipeline latency < 10s; alerting rules loaded and tested.
Backup & snapshot: last snapshot age < 24h; restore test documented.
Operator sandbox: rollback and safe-degrader runbook tested in shadow traffic for the tenant.
Acceptance tests: all acceptance_tests in this doc pass (see section).
| Component | Minimum Requirement | Recommended | Test Command / Query |
|---|---:|---|---|
| Control-plane proxies | 3 per-region HA, TLS 1.2+, 1Gbit NIC | 5 per-region | curl -sS https://cp.example/health |
| KV cluster | 3 replicas, journaled persistence | 5 replicas with local SSD log | redis-cli -h kv-0 PING && redis-cli -h kv-0 INFO replication |
| Model store | Signed image storage; >= 200GB free | 500GB with caching node | sha256sum /models/model-v1.tar.gz |
| Telemetry | Ingest < 10s, retention 90d | 30d hot + cold storage | prometheus query: max_over_time(scrape_latency[5m]) |
Smoke: curl tenant-route /health returns 200 and JSON {"status":"ok"}
Cold start latency: send 50 cold model requests and assert P95 <= 300ms
KV read-after-write: write key K; immediately read key K from another node; assert equality for 99.9% of attempts in 10k trials
Model checksum gate: deploy model image to all nodes; verify sha256 on every node matches control-plane manifest
Canary correctness: run canary set of 100 prompt/response pairs and verify no regression in acceptance prompts
High-level operator playbook
1) Preflight (operator): run network tests, validate NTP/time sync, validate KMS access.
2) Acceptance (customer/field): execute acceptance_tests consecutively; record screenshots/metrics into the evidence bundle.
3) Monitor: enable SLO dashboards and set alert thresholds (see Alerts).
4) If replication lag>500ms for >1 minute: reduce incoming traffic for affected tenant(s), open an incident with 'kv-replication-lag' tag, and scale replication followers by +1.
5) If model checksum mismatch detected during a rollout: pause rollout immediately, revert to previous signed artifact, and trigger artifact re-sync across nodes.
6) If P95 latency > SLA for 10m: activate safe-degrader -> fall back to lower-latency model variant or route to dedicated capacity; notify customer success.
7) Rollback procedure: follow the rollback checklist in this doc (Rollback Steps).
Step 1: Switch traffic to the last-known-good model tag via control-plane (use canary route feature).
Step 2: If switching fails, place the tenant in maintenance mode (control-plane flag) to prevent new requests.
Step 3: Ensure KV cache warmup is disabled for the draining nodes; perform cache flush only if safe-degrader indicates data corruption.
Step 4: Re-deploy previous artifact with signed image; verify checksums across 100% of nodes before returning traffic.
Step 5: Run acceptance_tests smoke subset and validate telemetry for 30 minutes before full resumption.
Recommended alerts (examples)
- kv_replication_lag_p99 > 500ms for 1m -> Severity P2
- tenant_api_5xx_rate > 0.5% for 5m -> Severity P1
- model_checksum_mismatch detected on any runtime node -> Severity P1
- telemetry_ingest_lag > 30s -> Severity P2
- control_plane_heartbeat_missing for >45s -> Severity P1

Alerting notes: Integrate with PagerDuty by service. For P1, notify oncall immediately and send customer success pro-forma email template (stored in related_pages).
Useful queries (Prometheus-like)
- KV replication lag (ms): histogram_quantile(0.99, sum(rate(kv_replication_lag_bucket[5m])) by (le))
- Tenant 5xx rate: sum(rate(tenant_http_responses_total{code=~"5.."}[5m])) / sum(rate(tenant_http_responses_total[5m]))
- P95 control-plane latency: histogram_quantile(0.95, sum(rate(cp_request_duration_seconds_bucket[5m])) by (le))

Example: run a 10m query and capture result into evidence bundle before acceptance signoff.
Evidence bundle requirements
Operators and customers must attach the following prior to 'go-live' signoff:
- Acceptance test logs (raw)
- Screenshots of SLO dashboards (30m window)
- KV replication status dump (redis INFO replication or equivalent)
- Model image checksum manifest and per-node sha256 output
- Telemetry ingest latency trace (30m)

Signoff matrix
- Technical owner (operator): name + email + signed timestamp
- Customer technical contact: name + email + signed timestamp
- Security reviewer: name + email + signed timestamp
- Program manager: name + email + signed timestamp

Signoff implies the customer and Redwood agree the acceptance_tests passed and the deployment satisfies the SLO thresholds for initial production traffic.
Design rationale
- Combine liveness and consistency in one attestation because customer incidents frequently touch both areas simultaneously (e.g., long replication lag + request spikes).
- Keep the acceptance checklist automatable: each item should be runnable in CI/CD or by a deployment agent.
- Where immediate read-after-write cannot be 100% guaranteed, we require probabilistic thresholds and observable metrics so that operators have deterministic rollback triggers.

FAQ
Q: What if the customer cannot provide signed image storage?
A: We require vehicle for artifact attestation; if customer cannot support signed images, Redwood will provide a signed stub and additional runtime verification hooks; this is a restricted exception and requires Security approval.

Q: Can the read-after-write threshold be relaxed?
A: Only by exception; any relaxation requires changes in the operator runbook to add compensating checks and increases in allowed error budgets.
