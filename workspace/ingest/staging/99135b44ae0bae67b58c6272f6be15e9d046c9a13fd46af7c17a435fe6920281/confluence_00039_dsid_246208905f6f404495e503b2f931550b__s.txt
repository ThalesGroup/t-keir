Streaming Fidelity Handshake and Progressive Degradation Protocol

Summary

This document defines the Streaming Fidelity Handshake and Progressive Degradation Protocol (SF-Handshake). SF-Handshake is an API-level contract between clients, edge proxies, and the streaming runtime that enables: negotiation of output fidelity and cost/latency tradeoffs, progressive degradation when capacity or latency constraints are hit, and traceable fallbacks with deterministic observability hooks.

Motivation

As Redwood serves a spectrum of applications (interactive chat, embedders, high-volume summaries), we need a common, lightweight mechanism for clients to express fidelity preferences and for the runtime to respond with deterministic degradation steps rather than opaque failures. Existing streaming contracts either assume fixed fidelity or rely on ad-hoc headers. SF-Handshake standardizes the capabilities, signals, and telemetry so downstream systems (billing, routing, caching) can make consistent decisions.

Scope

- Applies to: hosted API streaming endpoints (edge-proxy -> stream-gateway -> runtime).
- Not in scope: non-streaming batch RPCs, internal-only debug hooks (these remain separate).
- Backwards compatibility: servers must accept requests without SF-Handshake fields and use safe defaults.

- Document owner: eng/runtime-platform

Protocol overview

High-level flow:
1) Client sends an initial negotiation envelope as the first message or as request headers.
2) Edge validates the envelope, applies client-tier policies (quota, tenant SLOs), and forwards a server decision object.
3) Runtime executes generation respecting the decision and emits streaming tokens with fidelity annotations.
4) If the runtime must degrade, it emits a deterministic degradation event and updates the decision path; clients can optionally request a retry or accept degraded output.

Core concepts

- Fidelity Vector: A small typed set of dimensions describing desired result quality and cost: {accuracy, verbosity, creativity, safety_strictness, latency_priority}. Each dimension is an integer 0..100.
- Decision Envelope: Server-side response containing: selected fidelity vector, reason_code, allowed_cost_multiplier, degradation_plan (if applicable), observable_keys.
- Degradation Plan: Ordered instructions the runtime may apply in sequence (e.g., reduce creativity -> truncate output -> switch to cached summary).
- Observable Keys: Set of short opaque strings used to link tokens/events to telemetry traces and billing entries.

Negotiation surface (HTTP + streaming)

- Endpoint: POST /v1/stream/generate (existing streaming endpoint). SF-Handshake may be provided either as headers or as a JSON negotiation preamble.
- Headers (optional, lightweight):
  - X-RW-Fidelity: base64url(JSON) — compact fidelity vector when using headers.
  - X-RW-Client-Tier: free | standard | enterprise
  - X-RW-Negotiate-Mode: prefer | require | best-effort

- JSON preamble (recommended for full expressivity). Example: 

Preamble JSON example:
{
  "handshake_version": "1.0",
  "fidelity_vector": {"accuracy": 80, "verbosity": 60, "creativity": 40, "safety_strictness": 90, "latency_priority": 70},
  "budget_usd": 0.02,
  "client_tier": "standard",
  "request_id": "cli-1234-ctx-7890",
  "negotiate_mode": "prefer"
}

Server Decision object (example returned synchronously or as the first streamed control event):
{
  "decision_version": "1.0",
  "selected_fidelity": {"accuracy": 75, "verbosity": 55, "creativity": 35, "safety_strictness": 90, "latency_priority": 80},
  "allowed_cost_multiplier": 1.2,
  "reason_code": "latency_slo_adjustment",
  "degradation_plan": ["prune_long_form_summaries","early_token_exit","quantize_hidden_states"],
  "observable_keys": ["ok_47f3","path_99b1"]
}

Client behavior and expectations

- Conservative clients: set negotiate_mode=require. If the server cannot honor the request, the request should fail with 422 /error {"reason":"UNABLE_TO_SATISFY_FIDELITY"}.
- Opportunistic clients: set negotiate_mode=prefer or best-effort. They should accept decision objects with lower fidelity.
- Clients should always correlate server observable_keys to local telemetry and include request_id in logs.

Server behavior and enforcement rules

- Edge-proxy must validate handshake_version and apply tenant policy (quota, minimum fidelity floor for enterprise tier).
- If negotiate_mode=require and constraints cannot be met, reject early with detailed reason_code and allow clients to retry with altered fidelity/budget.
- When allowed_cost_multiplier > 1.0, billing signals must be emitted to the cost pipeline; stream-gateway must annotate tokens with the chosen multiplier.

Degradation semantic primitives (order matters)

1) Soft downgrades (non-destructive): reduce creativity, shorten verbosity, increase repetition penalty.
2) Structural downgrades: switch to a lighter head model (same family), reduce sequence rematerialization.
3) Performance tradeoffs: enable aggressive KV-cache eviction policies or turn on quantized kernels.
4) Fallbacks (last resort): return cached or synthetic summary, mark response as degraded=true, attach degradation_plan_trace.

Concrete headers and token annotations (stream payload)

- Control event structure (first stream event):
  - type: "decision"
  - payload: <Decision object JSON above>

- Token annotation envelope (attached to token frames):
  - token_text: "..."
  - fidelity_annotation: "f:75,v:55,c:35,l:80,s:90"
  - trace_key: "ok_47f3"

Observability and SLOs

Minimum telemetry required for each SF-Handshake request (emitted as structured events):
- handshake.received (tags: request_id, client_tier, hashing of fidelity_vector)
- decision.emitted (tags: decision_version, reason_code, allowed_cost_multiplier)
- degradation.event (tags: plan_step, runtime_node, latency_ms)
- token.emitted (tags: trace_key, fidelity_annotation)

SLOs (service-level guidance):
- handshake latency (time to first decision event): p95 <= 30ms for edge-proxy local decisions; p99 <= 120ms globally.
- faithful-degradation response time (time between decision to degrade and first degraded token): p95 <= 40ms.
- correctness alerting: if more than 2% of standard-tier requests receive a degradation_plan with step "fallback_cached" for 12h window, create an incident.

Billing and cost signals

- If allowed_cost_multiplier != 1.0, stream must emit cost.multiplier events to the billing pipeline.
- Offline aggregator will compute unit-cost adjustments; design of the billing pipeline is outside this doc but streams must contain observable_keys for correlation.

Testing, rollout, and compatibility

- Feature gate: SF-Handshake is gated via feature-flag edge.synthetic.sf_handshake. Default off for free-tier.
- Canary plan: enable for 5% of traffic with negotiate_mode=prefer, collect metrics for handshake.latency, degradation.rate, billing.adjustments.
- Backwards compatibility: if client sends no handshake, runtime must behave as if fidelity_vector={accuracy:70,verbosity:60,creativity:50,safety_strictness:80,latency_priority:50}.

Operational runbook (high-level)

1) Detect spike in degradation.event rate (dashboard alert).
2) Validate whether increased degradation correlates with capacity events, policy changes, or a new model rollout.
3) If caused by model rollout, trigger automatic rollback to previous variant and alert product/ML.
4) If caused by tenant quota misconfiguration, apply tenant-specific temporary uplift and notify billing.

Security and privacy considerations

- Fidelity Vector values are not PII but may correlate with business-critical usage. Mark handshake events as internal.
- Observable_keys must be short opaque tokens; do not encode tenant or user IDs directly.

Compatibility matrix and decision rationale

- Rationale: We prefer an explicit JSON preamble to allow extensibility; header form remains for low-bandwidth clients.
- Compatibility: Servers will maintain a mapping layer to translate legacy headers into the fidelity_vector shape for at least 12 months.

Open questions and follow-ups

- Should we define a canonical set of degradation_plan steps and identifiers across runtime teams? (Action: convene engineering standards working group Q1 2026).
- How granular should cost multipliers be (per-token vs per-request)? Current recommendation: per-request multiplier with downstream prorated attribution.
