SDK local-cache, stub servers, and graceful-degradation playbook

Overview

This playbook describes recommended patterns for local SDK caching, lightweight stub servers, and graceful degradation when the Redwood runtime or network is unavailable. It covers: developer-local workflows, SDK configuration recipes, canonical API examples, telemetry expectations, and a short incident / support playbook for common failures. The goal is to make offline development reliable, make error modes deterministic for QA, and reduce support churn from transient runtime outages.

When to use this playbook

- Building local prototyping sandboxes where calling hosted inference is slow or costly.
- Enabling reliable CI for prompt-driven tests without hitting production endpoints.
- Implementing client-side fallbacks for consumer apps that must remain partially functional during runtime incidents.

Motivation and constraints

- Developer velocity: enable fast local iteration without paying tokens or waiting on remote cold-starts.
- Determinism for tests: replayable responses and deterministic stubs improve eval reliability.
- Safety: cached responses should be labeled and quality-monitored to avoid leaking stale outputs in production.

Service names and components referenced

- redwood-sdk: the official client library (node/py/go)
- runtime-proxy: the local dev proxy used to route requests to stubs or the real API
- dev-sandbox: internal template repo for running the local stack (docker-compose/k8s manifests)
- telemetry-orch: ingestion pipeline for SDK telemetry including cache-hit metrics and stub usage

High-level patterns

1) Local-Cache-as-Primary (for dev)
- SDK consults a local cache first (LRU/TTL-based).
- If cache miss, SDK records the request to a local "capture log" and then either: (a) forward to runtime in debug mode, or (b) return a synthetic placeholder.
- Use for: rapid iteration, offline demos.

2) Stub-Server with Replay Mode (for CI)
- A small HTTP stub implements the Redwood API surface required by the app.
- Stub seeded with golden responses (JSON) and a deterministic matching algorithm (exact prompt key + normalized params).
- Use for: CI acceptance tests, performance smoke tests without production cost.

3) Graceful-degradation policy (for production clients)
- Control via SDK config: on_failure = [retry, use_cache, degrade_to_default] with per-endpoint policy.
- Fallback tiers: local-cache -> lightweight-model-variant -> default-static-message.
- Use for: user-facing features that must never block user flows.

Configuration reference (SDK examples)

NodeJS sample (redwood-sdk config snippet)

```js
const Redwood = require('@redwood/sdk');
const client = new Redwood({
  apiKey: process.env.REDWOOD_API_KEY,
  dev: {
    localCache: { path: './.redwood/cache.json', ttlSeconds: 3600 },
    stubServer: { url: 'http://localhost:19527' },
    gracefulDegrade: {
      defaultAction: 'use_cache',
      retry: { attempts: 2, backoffMs: 200 },
    }
  }
});

await client.generate({ model: 'rw-medium-v1', prompt: 'Summarize the doc' });
```

Python sample (redwood_sdk config)

```py
from redwood_sdk import Redwood
client = Redwood(api_key=os.getenv('REDWOOD_API_KEY'), dev={
    'local_cache': {'path': '.redwood/cache.json', 'ttl_seconds': 600},
    'stub_server': {'url': 'http://localhost:19527'},
    'graceful_degrade': {'default_action': 'use_cache', 'retry': {'attempts': 1, 'backoff_ms': 300}}
})
response = client.chat.create(model='rw-medium-v1', messages=[{'role':'user','content':'Hello'}])
```

Canonical stub-server behavior

- API: Accepts the same REST endpoints as hosted API (POST /v1/generate, /v1/chat, /v1/embeddings).
- Response matching: normalizes inputs (strip timestamps, normalize whitespace, canonicalize numeric seeds) then performs exact or prefix matching.
- Fallthrough: if no match, stub returns HTTP 404 with a clear body showing the captured request id and a CLI hint to seed the data.

Seeding stubs for CI

1) Capture mode: run the app against production or dev runtime with SDK dev.capture = true to record request/response pairs to ./test-fixtures/seed.json.
2) Review and redact sensitive fields (PII, private data) using the seed-redact utility: `dev-sandbox/bin/seed-redact ./test-fixtures/seed.json`
3) Commit fixtures to repo and use the stub image that mounts fixtures at /app/fixtures.json.

Example captured entry (fixture)

```json
{
  "id": "fixture-20260111-001",
  "endpoint": "/v1/chat",
  "request": {"messages": [{"role":"user","content":"Explain event sourcing"}], "max_tokens": 200},
  "response": {"choices": [{"message": {"role":"assistant","content":"Event sourcing stores state changes as a sequence of events..."}}], "meta": {"model":"rw-medium-v1","latency_ms":123}}
}
```

Operational guidance and SLOs

- dev-sandbox templates: owner eng-developer-experience team (team wiki link in references).
- Cache TTL recommendation: 600s for interactive dev, 3600s for offline demos.
- Production-only: SDK must never return cached model outputs to end-users unless the app explicitly allows it and audit-flagging is enabled. Default: cache-only-for-local.
- Telemetry metrics to emit: sdk.cache.hit, sdk.cache.miss, sdk.stub.request, sdk.stub.miss, sdk.degrade.invocations.
- Alerting thresholds (telemetry-orch): raise when sdk.degrade.invocations > 5% of requests over 10m or stub.miss > 1% of CI runs.

Runbook: common support issues and canonical fixes

1) Symptom: local cache never hits
- Check: correct cache file path and permissions; ensure request normalization key matches (strip session IDs).
- Fix: run `node tools/debug-cache-key.js --sample` to inspect key extraction. Regenerate cache with `REDWOOD_DEV_CAPTURE=1 node ./scripts/capture.js`.

2) Symptom: stub server returns 404 on CI
- Check: fixtures bundle was mounted and the fixture keys match the normalized request. Verify CI uses the correct stub image tag.
- Fix: re-seed fixtures from a reproducible run, run `./dev-sandbox/bin/seed-validate /app/fixtures.json`.

3) Symptom: app shows stale cached outputs in production
- Check: ensure SDK is not running in dev mode (REDWOOD_ENV must be 'prod'), verify cache policy.
- Fix: rotate cache storage, invalidate entries with `redwood-cli cache invalidate --all` and ensure telemetry flagged the incident.

Testing guidance

- Unit tests: mock the SDK transport layer and verify fallback order (retry -> cache -> stub -> default).
- Integration tests: run against stubbed dev-sandbox using `make ci-stub` to ensure deterministic runs.
- Golden regression: include a small set of prompt-based golden responses in PRs; run `tools/compare-golden --update` for intentional updates.

Docs site and snippet hygiene

- Snippets: always use `<!--redwood-snippet:example-id-->` in docs to enable automated snippet validation. The docs-site will run the snippet through the local stub server in the preview pipeline.
- Canonical fixes: when a snippet fails due to API drift, update the fixture then triage under `devx/snippet-failures` with a tag `snippet-fix`.

Telemetry and privacy notes

- Captured fixtures must be reviewed and redacted before committing: remove PII, customer IDs, and long personal text. Use `dev-sandbox/bin/seed-redact` which applies a standard redaction policy.
- Telemetry events that include sampled prompt hashes (sha256) are acceptable for diagnostics, but never store raw prompt text in centralized logs by default.

Rollout and ownership

- Owner: eng-developer-experience (primary), eng-sre (secondary for telemetry/alerting).
- Rollout steps: 1) publish dev-sandbox templates and sample app; 2) add snippet validation to docs-site preview; 3) enable telemetry metrics for cache/stub usage; 4) run team-wide training and update runbooks.

FAQ

Q: Can cached outputs be used in user-facing production flows?
A: No — not by default. The SDK config explicitly separates dev cache from production cache and requires an explicit opt-in flag plus audit-trace to allow any cached outputs to be surfaced to users.

Q: How do we keep fixtures small and maintainable?
A: Seed minimal representative responses, prefer short completions, and compress fixtures with `tools/fixture-compress` in CI.
