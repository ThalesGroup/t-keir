cross-cluster-failover-execution-and-verification-playbook-2025

Summary:
This playbook documents a tested, low-friction procedure for executing an orchestrated cross-cluster failover for Redwood Inference’s production inference stack, and for verifying service health, SLO impact, and capacity stability after failover. It is intended for use by on-call SREs and incident commanders during partial or full cluster outages affecting inference-router, request-broker, model-runtime, or KV-cache layers.

Scope:
- Applies to cross-cluster failover between active clusters (us-west-2 primary -> us-east-1 secondary) and to on-prem -> cloud emergency evacuation.
- Covers pre-failover checks, execution steps, verification queries, rollback criteria, and post-incident evidence collection.
- Does NOT replace application-level canary rollout procedures or model-configuration rollbacks.

Primary goals:
- Maintain critical SLOs (latency and availability) within error budget constraints while preserving data isolation guarantees for Dedicated tenants.
- Minimize tail-latency impact during topology changes.
- Produce clear evidence for incident review and capacity planning.

Ownership:
- Incident commander: SRE on call for model-serving-systems
- Execution lead: Cluster platform engineer (runtime team)
- Verification lead: Observability engineer (eng-platform)
- Communications: Customer Success for affected tenants if >5% of traffic is affected

Pre-failover checklist (must be green before initiating failover):
1) Confirm incident classification and triage decision to failover (Incident commander).
2) Error budget snapshot: query error_budget_service("inference-api") and verify current consumption < 90%. If >90%, start emergency cadence.
3) Capacity readiness: ensure secondary cluster has at least 1.5x baseline capacity for the expected drained RPS. Use capacity matrix below.
4) Model compatibility: run model-compatibility-check.sh against the secondary cluster image set.
5) KV-cache warming plan: confirm cache pre-warm scripts are validated for top-100 prefixes.
6) Routing policy: confirm new routing rule exists in traffic-router (policy id: failover-policy-v1).
7) Communication: notify #oncall, #infra-ops, and Customer Success with expected timeline and rollback window.

Execution procedure (step-by-step):
1) Stage maintenance window and mark affected services: POST /api/v1/incidents/{id}/status with status=failover_in_progress
2) Activate traffic guard rails: set traffic-router threshold to 75% RPS for gradual shift:
   - CLI: traffic-router set-policy --id failover-policy-v1 --gradual-shift 75 --duration 00:10:00
3) Pre-warm model runtimes and caches on the target cluster in parallel:
   - ssh ops@secondary-cluster "./scripts/prewarm-models --models-file top_models.txt --parallelism 8"
   - Run kv prewarm: kubectl --context=secondary apply -f prewarm-job.yaml
4) Shift 10% traffic for 3 minutes and run verification checks (see below). If green, shift to 50% for 5 minutes, then to 100%.
5) Monitor autoscaler behavior; if scaling does not keep avg CPU or GPU util in expected band (GPU util target 60-70%), pause shift and invoke emergency scale (see tooling section).

Verification and validation (automated + manual checks):
- Health checks to run after each traffic step (script: failover-verify.sh):
  1) API correctness: curl -sS -X POST https://secondary.example.com/v1/generate -d '{"prompt":"health-check"}' | jq -e '.id'
  2) Latency profile: query observability API: 
     GET /telemetry/query?metric=p95_latency&service=inference-api&window=5m&cluster=secondary (expected p95 <= 200ms initially)
  3) Error rate: GET /telemetry/query?metric=error_rate&service=inference-api&window=5m (target <= 1.0% during transition)
  4) KV hit rate: GET /telemetry/query?metric=kv_cache_hit_rate&service=kv-cache (expect >= 60% after pre-warm)
  5) Token cost delta: compare per-token cost for top tenants; alert if > +40% relative to baseline.
- Manual verification: sample 5 tenant requests end-to-end; validate deterministic fields and model artifacts are intact.

Rollback criteria (immediate rollback if any of the following):
- P95 exceeds 500ms for 5 consecutive minutes and is not improving after restart of hot paths.
- Error rate > 5.0% sustained for 3 minutes.
- Autoscaler fails to add capacity and GPU queue depth > 1000 for 2 minutes.
- Any Dedicated tenant reports an isolation or data residency violation.
Rollback steps:
1) Pause traffic-router gradual shift and revert policy: traffic-router set-policy --id failover-policy-v1 --revert true
2) Drain secondary cluster of newly routed traffic gracefully: kubectl scale --replicas=0 deployment/traffic-shim -n inference --context=secondary
3) Re-run verification on primary and resume traffic to primary following the same staged approach.

SLO and error budget considerations during failover:
- Primary SLOs: availability 99.95% monthly, p95 latency <= 150ms, request error rate < 0.5%.
- During declared failover (incident classification "failover"), error budget windows are extended by incident-duration for the purpose of downstream automation, but product teams must be notified when >25% incremental error budget is consumed.
- Escalation thresholds:
  - >25% of monthly error budget consumed -> notify platform PM and SRE manager.
  - >50% -> schedule emergency review and capacity injection.
  - >90% -> mandatory rollback and restore to last known healthy topology.

Capacity planning and quick knobs:
- Fast capacity injection: runbook-run capacity-inject --cluster secondary --gpu-n 8 --node-type p4d.24xlarge (allowed during declared failover only)
- Pre-warm concurrency targets per GPU: recommended model-concurrency 8 for 32k-context models, 16 for 4k-context smaller models.
- Capacity matrix (baseline):
| Component       | Primary provisioned | Secondary minimum required | Notes |
|-----------------|---------------------:|---------------------------:|-------|
| inference-api   | 3000 RPS            | 4500 RPS (1.5x)            | elastic autoscale enabled |
| model-runtime   | 512 vGPU units      | 768 vGPU units             | ensure image parity |
| kv-cache        | 2M keys             | 2M keys (warmed)           | pre-warm top prefixes |
| request-broker  | 800 concurrent      | 1200 concurrent            | shard affinity on failover |

Operational tooling and automation notes:
- Primary scripts: scripts/failover-orchestrator.py (invokes traffic-router, pre-warm jobs, verification harness).
- Observability queries (examples):
  - p95 latency: POST https://observability.internal/api/query -d '{"query":"p95(inference_api_latency{cluster=\"secondary\"}[5m])"}'
  - error rate: POST https://observability.internal/api/query -d '{"query":"rate(inference_api_errors[5m]) / rate(inference_api_requests[5m])"}'
- Emergency scale CLI (requires approver token): 
  export APPROVER_TOKEN=xxxx
  capacity-inject --cluster secondary --gpu-n 8 --approver $APPROVER_TOKEN
- Canary verifier: /opt/redwood/bin/canary-checker --tenant-file sample-tenants.csv --endpoint https://secondary.example.com --timeout 10s

Incident review and evidence collection (post-failover):
- Required artifacts for post-incident review:
  1) failover orchestration logs (s3://redwood-ops/failover-logs/{incident-id}/orchestrator.log)
  2) Telemetry snapshots (p95, p99, error rate, kv hit rate) for both clusters for window [-30m, +120m] around failover.
  3) Traffic-router audit trail showing step percentages and timestamps.
  4) Autoscaler events and node provisioning timeline.
  5) Sample request traces (at least 10 end-to-end traces across affected tenants).
- Postmortem template items: timeline, decision rationale, root cause hypotheses, mitigation actions, SLO impact calculation, follow-up owners with deadlines.

Runbook DR drills and cadence:
- Scheduled full failover drill: quarterly, run by platform team; record run duration, verification time, and SLO impact.
- Mini drills (warm-only): monthly, focus on pre-warm and cache hit recovery.
- After any drill or real event: update runbook if total failover time or SLO impact deviates > 20% from expected.

Appendix: quick command cheat sheet
- Start failover (dry-run): ./scripts/failover-orchestrator.py --incident-id INC-12345 --mode dry-run --target-cluster secondary
- Execute staged shift: traffic-router set-policy --id failover-policy-v1 --gradual-shift 75 --duration 00:10:00
- Verify API health: curl -sS -X POST https://secondary.example.com/v1/generate -d '{"prompt":"health-check"}' | jq
- Pull telemetry snapshot: observctl snapshot --service inference-api --window "-30m:+120m" --output s3://redwood-ops/failover-archives/INC-12345
