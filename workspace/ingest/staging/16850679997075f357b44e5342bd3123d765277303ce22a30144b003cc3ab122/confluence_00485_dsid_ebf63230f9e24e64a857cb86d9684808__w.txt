Workload Priming and Quantization Sensitivity Manifest

Purpose:
This document defines a standardized manifest and operational workflow for measuring a workload's sensitivity to quantization and context priming interactions. The goal is to provide a reproducible, slice-driven way to capture failure modes introduced by weight/activation compression and by prompt/context priming that affect token-level quality and KV-cache behavior.

Scope and intended audience:
- Applies to model onboarding, quant-profile generation, and pre-production rollout for Hosted, Dedicated, and Private deployments.
- Primary readers: model ops, serving runtime engineers, applied ML evaluators, and SRE oncall.

High-level summary:
1) Define per-workload "priming vectors" that represent realistic context shapes (short, medium, long, multi-turn).
2) Attach stress profiles that vary sequence-length distributions, repetition rates, and token entropy.
3) Run a quant-sensitivity matrix across model variants (FP16, INT8/4 hybrid, QLoRA-adapted) with KV-cache on/off.
4) Aggregate slice-level degradation metrics and create a manifest artifact that inputs into rollout gates and fallback policies.

Key definitions:
- Priming vector: a representative context + instruction template used for shadow replay. Includes sample prompts, few-shot examples, and optional system messages.
- Stress profile: a probabilistic generator defining sequence lengths, token entropy, and turn-taking behavior.
- Sensitivity delta: the relative change in quality metric (e.g., BLEU/ROUGE/Embedding-similarity/LLM-quality-score) between baseline and quantized run.

Manifest schema (human-readable):
- workload_id: short key (team-workload)
- priming_vectors: list of named vectors (short/medium/long/multi-turn)
- stress_profiles: list of named profiles with distribution parameters
- model_variants: ordered list of checkpoint ids + quant tag
- kv_cache_modes: [on, off, partial]
- slices_of_interest: list of tags (e.g., legal-templates, code-edit, multi-turn-churn)
- failure_thresholds: mapping of metric -> absolute or delta limit
- recommended_fallback: model variant id or policy
- telemetry_keys: required telemetry fields to collect

Example manifest (YAML-like snippet):
workload_id: payments-invoice-processor
priming_vectors:
  - name: short-system
    description: one-line system, single user query
  - name: long-multi
    description: system + 3-shot examples + 2 prior turns
stress_profiles:
  - name: tail-heavy
    seq_len_p50: 64
    seq_len_p95: 2048
  - name: repetition-heavy
    repeat_token_prob: 0.08
model_variants:
  - id: rwd-gpt-3b-fp16
  - id: rwd-gpt-3b-q4_0
kv_cache_modes: [on, off]
slices_of_interest: ["invoice-parsing", "table-extraction", "debit-credit-ambiguity"]
failure_thresholds:
  quality_delta: 0.06  # relative drop allowed
  embedding_cosine_drop: 0.02
  latency_p95_increase: 0.20
recommended_fallback: rwd-gpt-3b-fp16
telemetry_keys: ["slice_id", "priming_vector", "model_variant", "kv_cache_mode", "latency_ms", "tokens_generated", "quality_score"]

Operational workflow (step-by-step):
1) Create manifest: owning team defines workload_id, selects priming vectors and slices. (Owner: ML product / workload lead)
2) Baseline run: run full synthetic suite on FP16 baseline; store baseline artifact and telemetry. (Owner: Evaluator)
3) Quant sweep: run model variants under each stress profile with kv_cache modes toggled. Use parallelized eval harness. (Owner: Evaluator + Runtime testing)
4) Analyze deltas: compute sensitivity deltas per-slice and per-priming-vector. Generate a ranked list of problematic slices. (Owner: Applied ML)
5) Triaging playbook: if any slice exceeds failure_thresholds, create a regression ticket with the manifest attached and mark rollout gate = fail. (Owner: Oncall/Evaluator)
6) Mitigation paths: a) refine quant profile (per-layer, activation clipping), b) adjust priming (trim examples), c) enable alternative fallback at routing layer. (Owner: Model Ops + Runtime)
7) Re-run affected slices after mitigation and close ticket when all slices pass.

Analysis and metrics (what to collect):
- Token-level deltas: per-token perplexity increase and per-token edit distance to baseline when applicable.
- Cohort quality: human-rated quality delta on a sampled subset (N=200 per problematic slice).
- Embedding stability: cosine similarity and nearest-neighbor drift vs baseline.
- Latency and tail behaviour: p50/p90/p95 and GPU memory pressure.
- KV-cache refill ratio: percentage of requests that benefit from cached KV hits vs misses.

SLOs and rollout gates (recommended):
- Overall quality_delta (weighted by slice traffic share) <= 0.04 for production promotion.
- No single slice may exceed quality_delta 0.08 without an explicit mitigations plan.
- Latency_p95 increase <= 15% relative to baseline.
- Embedding_cosine_drop <= 0.03 for retrieval-heavy workloads.

Triage rubric (prioritization):
1) User-visible correctness regressions on high-traffic slices (severity P0).
2) Multi-turn coherence regressions causing stateful failure (P1).
3) Embedding drift impacting downstream retrieval (P2).
4) Latency regressions affecting SLA but not correctness (P2).

Runbook snippets and commands:
- Launch sweep (example CLI):
  rwd-eval run --manifest payments-invoice-processor.yaml --variants rwd-gpt-3b-q4_0,rwd-gpt-3b-fp16 --profiles tail-heavy --kv-modes on,off --out s3://redwood-eval/results/payments-2026-02-10

- Quick analysis (jq + python):
  aws s3 cp s3://redwood-eval/results/payments-2026-02-10/summary.json - | jq .slices | python scripts/compute_sensitivity.py --baseline baseline.json --out report.csv

Mitigation cookbook (patterns observed):
- Per-layer activation rescaling: slight improvements for repetition-heavy stress profiles at cost of small latency bump.
- KV-cache-aware prompts: moving long examples into context cacheable prefixes improved long-multi priming vector performance by ~30% of delta.
- Hybrid fallback routing: route particular slices to FP16 variant if sensitivity delta > threshold.

Ownership and escalation:
- Workload owner: the product or feature team that owns workload_id (responsible for priming vectors).
- Evaluator owner: team that runs the manifest sweeps and produces artifacts.
- Runtime owner: serving runtime contact responsible for fallback and quant-profile application.
- Escalation path: oncall -> Evaluator lead -> Runtime eng -> Head of Serving. Include manifest and failing slice ids in the incident ticket.

Storage and artifactization:
- Artifacts (outputs, logs, metrics) must be stored under a standardized S3 path: s3://redwood-eval/{workload_id}/{date}/{run_id}/
- Manifests and analysis reports should be checked into the gated dataset registry and referenced by SHA.

Appendix B: Common failure signatures and suggested probes:
- Signature: high embedding drift but token-level match preserved. Probe: increase embedding sample size, run retrieval downstream check.
- Signature: multi-turn hallucination increase only when kv_cache on. Probe: run isolated long-multi vectors with kv_cache toggled and inspect KV hit-map.
