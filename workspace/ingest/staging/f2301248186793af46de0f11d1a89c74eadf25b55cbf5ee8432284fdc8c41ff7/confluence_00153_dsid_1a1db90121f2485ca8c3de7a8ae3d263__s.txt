SLO Heatmap Entropy and Traffic Reshuffle Playbook

Overview

This playbook explains how Redwood Inference generates SLO heatmaps, computes an entropy-based prioritization score, and executes a traffic reshuffle to protect high-impact SLOs during capacity pressure or degradation events. It is intended for SRE, eng-platform, and runtime owners responsible for service-level guarantees and operational resilience.

Goals

- Provide an automated, explainable mechanism to prioritize traffic to instances/variants that preserve critical SLOs.
- Reduce customer-visible latency/regression by steering lower-priority requests to degraded/cheaper variants while preserving higher-priority traffic.
- Create observable, reversible traffic reshuffles with clear rollback criteria.

Scope and applicability

- Applies to production inference endpoints and internal control-plane services wired into the runtime routing mesh.
- Not intended for offline batch workloads.
- Works with Redwood’s multi-variant model serving (e.g., fp32/quantized/ distilled variants) and regional routing policies.

Key definitions

- SLO heatmap: A time-windowed matrix of SLO attainment across dimensions (route, model-variant, region, customer-tier).
- Entropy score: A scalar derived from the heatmap distribution that quantifies dispersion of failures across dimensions. High entropy indicates widespread degradation; low entropy indicates concentrated degradation.
- Traffic reshuffle: Policy-driven rerouting that shifts fractional traffic among variants/regions to maximize preserved SLO attainment.

Heatmap construction (data sources)

1. Dimensions: route_id, model_variant, region, customer_tier, latency_class (p95/p99 buckets), window (5m).
2. Signals: success_rate (>= configured threshold), p95_latency_ms, token_cost, error_rate, kv-cache_hit_rate.
3. Aggregation: per-dimension sliding window (default 5m with 1m step) producing: 
   - heatmap_cell = {requests, good_requests, total_latency_ms_sum, cost_sum}.
4. Export: heatmap is exported every 1m to the telemetry index with TTL = 30d.

Entropy metric and prioritization formula

- For each SLO class (e.g., Latency SLO for interactive endpoints), compute distribution p_i = failures_i / total_failures across the chosen dimension (example: model_variant).
- Entropy H = - sum_i p_i * log2(p_i) (treat p_i=0 as 0).
- Prioritization score for a cell combines:
  - criticality_weight (derived from customer_tier and route importance),
  - cell_failure_rate (failures / requests),
  - inverse_entropy_boost = (1 / (1 + H)) to prefer concentrated failure repair.

CombinedScore = criticality_weight * cell_failure_rate * inverse_entropy_boost

Interpretation: higher CombinedScore => candidate for traffic-preserving action (either move high-priority traffic away from this cell or move low-priority traffic into it depending on policy).

Policy taxonomy

1. ProtectHighPriority: move customer_tier=enterprise and route=payment-checkout to low-latency variants/regions first.
2. CostDegrade: route best-effort trials to quantized/cheap variants under sustained load.
3. RegionalIsolation: when a region shows low entropy (failures concentrated in region), failover cross-region before variant-level reshuffle.

Runbook: automated reshuffle flow (high level)

1. Detection
   - Alert fires when route-level p99 latency > SLO threshold for 3 consecutive windows (default 3*5m).
   - Heatmap shows cell_failure_rate > 3x baseline for a cell contributing >= 10% of route failures.
2. Scoring and decision
   - Compute CombinedScore for affected cells.
   - If the top N cells (configurable by route) account for >= 60% of failures and entropy H < H_threshold (default 1.2), mark as concentrated failure.
3. Action selection (automated policy engine)
   - If ProtectHighPriority: attach a temporary priority route to affected enterprise tokens redirecting to preserved-variant (fractional 100% enterprise traffic).
   - Otherwise apply graduated reshuffle: reduce traffic fraction to hit cell by delta = min(0.25, observed_failure_fraction).
   - Apply traffic changes via control-plane patch API in two waves: immediate partial steering (10%) then ramp after 60s when probes confirm.
4. Validation
   - Post-action check: 2 consecutive windows with p99 latency improvement >= 15% for protected traffic or total error reductions for route >= 20%.
5. Rollback/Manual intervention
   - If metrics worsen or new cells degrade (entropy increases > +0.5), revert changes and trigger escalation.

Operational configuration (table)

| key | default | purpose |
|-----|---------|---------|
| detection.window | 5m | sliding window for heatmap aggregation |
| detection.threshold_multiplier | 3.0 | multiplier of baseline failure rate to trigger cell alert |
| entropy.h_threshold | 1.2 | below this value treat failures as concentrated |
| reshuffle.max_fraction_delta | 0.25 | max per-step traffic fraction change |
| reshuffle.ramp_delay_s | 60 | time between partial and full ramp steps |
| validation.windows_required | 2 | consecutive windows for post-action validation |
| preserve.customer_tiers | [enterprise, paid] | tiers treated as high criticality |

Ownership and escalation

- Primary owner: eng-sre (team: runtime-slo-ops).
- Secondary owner: eng-platform (team: routing-and-mesh).
- On-call: runtime-slo-ops rotation. Page slack channel: #slo-ops.
- Escalation matrix: first 10m -> on-call, 30m -> runtime lead, 2h -> eng manager and product.

Monitoring and alerting (rules)

- Alert A1: Route p99 exceedance (severity P1) when > SLO*1.1 for 3 windows. Notify #oncall, create incident.
- Alert A2: Heatmap concentration (P2) when top cell contributes >= 40% of route failures. Annotate with cell id, entropy, CombinedScore.
- Synthetic probes: per-variant probes at 10s cadence; missing probe data for 3 probes triggers degraded telemetry fallback.

Safe rollout practices and preflight checks

1. Canary validation: always run traffic reshuffle on 1–2 non-production shadow accounts to validate pathing and observability.
2. Safety gates: reshuffle control-plane API requires dual approval if intended fraction delta > 0.15 for production routes.
3. Simulation: before global reshuffle, run simulator with historical heatmap (90th percentile worst-case window) to ensure > 95% probability of SLO preservation for protected tiers.

Manual playbook (when automation disabled)

1. Identify affected route and top failing cells using heatmap UI or telemetry query.
2. Evaluate entropy H; if H < 1.2 follow concentrated-failure path; else follow dispersed-failure path.
3. For concentrated-failure path: perform targeted route override for customer_tier=enterprise to preserved_variant with a 10% partial ramp.
4. Validate with live queries and tracing; if green, continue ramp to required fraction.

Example CLI snippets

# compute CombinedScore for route "checkout" (pseudo)
redwood-slo-tool heatmap fetch --route checkout --window 5m | redwood-slo-tool score --entropy-threshold 1.2 --output json

# apply traffic patch (partial ramp)
redwood-control patch-traffic --route checkout --from variant:q123 --to variant:q456 --fraction 0.10 --reason "reshuffle: protect enterprise" --author a.patel

Testing and retrospective requirements

- Any automated reshuffle that ran on production must have a post-incident note in the incident tracker within 24h with: inputs (heatmap snapshot), decision rationale, validation windows, and a playback of the traffic-change timeline.
- Quarterly simulation exercises to validate entropy thresholds and weighting parameters against synthetic failure modes.

Audit and compliance

- All traffic patches are auditable: control-plane writes event with user, timestamp, before/after fractions, and heatmap snapshot id. Retention = 1y.

FAQ and rationale highlights

Q: Why entropy instead of raw failure counts?
A: Entropy helps detect whether failures are concentrated (safe to surgically reroute) or widespread (requires capacity/proactive remediation). It reduces oscillation and wrong corrective actions.

Q: Won't reshuffles cause customer impact?
A: The policies prioritize protecting high-criticality tiers and use gradual ramps with validation windows. Every production reshuffle requires post-run documentation.
