Ensemble evaluation orchestration and weighting guidelines

Overview
=======

Purpose
-------
This document specifies a standard for orchestrating ensemble-style evaluations in Redwood's eval harness. It covers how to configure multi-metric evaluation jobs, how to compute a single acceptance score from heterogeneous metrics, recommended weighting strategies, and the operational rules used for model acceptance, canary rollouts, and automated rollback triggers. The goal is consistent, explainable production decisions across different product use-cases (chat, summarization, reranking, embeddings).

Background and motivation
-------------------------
Teams frequently need to combine multiple eval signals (e.g., BLEU/ROUGE-like n-gram overlap, semantic similarity, safety pass rate, latency percentiles) into a single decision for model promotion or rollback. Without a standard approach:
- teams create ad-hoc weights that are hard to justify
- comparisons across workloads are inconsistent
- drift or slice regressions are missed when only aggregate metrics are considered

Scope
-----
This guide applies to:
- All evaluation jobs run through eval-harness-runner and eval-orch services.
- Post-training checks that feed Redwood Optimize and model-onboarding pipelines.
- Production acceptance gates tied to rollout automation in the deployment orchestration layer.

Terminology
-----------
- eval job: a single run that produces a set of metrics for a model version on a prompt set.
- slice: an orthogonal data subset (e.g., low-resource queries, long-contexts, legal-phrasing).
- metric vector: the set of scalar metrics produced by one eval job.
- ensemble score: a normalized, weighted aggregation of metrics used for acceptance decisions.

High-level orchestration
-----------------------
1) Eval job submission: developers submit an eval job YAML to eval-orch. Jobs declare model id, dataset id, slices, metrics, and desired aggregations.
2) Parallel runners: eval-harness-runner scales horizontally to execute slices in parallel. Per-slice results are written to metric-store with a unique job id.
3) Post-processing: a standardized post-processing step normalizes raw metrics, computes slice-level z-scores or bounded transforms, and produces the ensemble score.
4) Decision hooks: the ensemble score is compared against the configured acceptance matrix (thresholds and weights). If the score passes, the model progresses to canary rollout; otherwise it triggers triage.

Orchestration diagram (text)
---------------------------
- user -> eval-orch -> queue (kafka) -> runner pool -> metric-store (timeseries + artifacts) -> postproc -> decision-service -> deployment-orch

Weighting and aggregation strategies
----------------------------------
We provide three canonical strategies. Choose the simplest that satisfies your product requirements; prefer reproducibility over complexity.

1) Equal-weight normalized aggregation (default)
- Use when metrics are commensurate after normalization (e.g., all are percentages or bounded scores).
- Steps: compute per-metric min/max clipped to historical percentiles (5th/95th), rescale to [0,1], average.
- Pros: simple, transparent.
- Cons: can under- or over-emphasize rare but critical metrics.

2) Priority-weighted aggregation
- Use when one metric is safety-critical (e.g., toxicity, hallucination rate).
- Steps: assign integer priority weights (example: safety=5, accuracy=3, latency=1), normalize weights to sum to 1, compute weighted sum of normalized metrics.
- Documentation: every priority weight must have an author and justification recorded in the eval job metadata.

3) Dynamic frequency-weighted aggregation (recommended for customer-facing embeddings/reranking)
- Use when production slice frequencies differ significantly from training/test distributions.
- Steps: estimate slice frequencies from production telemetry (last 30 days), compute per-slice weight proportional to frequency, and combine slice-level metric aggregates into a global metric before normalization.
- Important: frequency estimates are clipped to [0.01, 0.5] per slice to avoid domination by a single slice.

Normalization and transforms
---------------------------
We standardize on the following transforms before aggregation:
- bounded metrics in [0,1] (no transform)
- unbounded error metrics (e.g., MSE): apply inverse transform 1/(1+log(1+value)) then rescale to [0,1]
- latency percentiles: map P50/P95 to score = 1 - min(latency / latency_slo, 1) (SLOs stored in product-config)
- safety/failure rates: use 1 - rate so higher is better
- For metrics with heavy tails, use winsorization at 99th percentile prior to normalization

Scoring formula (canonical)
--------------------------
Given normalized metrics m_i in [0,1] and weights w_i that sum to 1:
ensemble_score = sum_i w_i * m_i

When combining slices, compute slice_score_j first (per-slice aggregation across metrics), then global_score = sum_j slice_weight_j * slice_score_j where slice_weight_j is chosen per weighting strategy.

Config examples
--------------
Example eval job YAML (submit to eval-orch):

---
job_name: "chat-v2-ensemble-eval"
model_id: "m-redwood-chat-v2-2026-03"
dataset_id: "chat-production-sim-2026-01"
metrics: ["semantic-similarity", "toxicity_rate", "response_length_variance", "p95_latency_ms"]
slices: ["all", "long_context_>2048", "low_english_proficiency"]
weighting_strategy: "dynamic-frequency"
weights: {} # optional for dynamic; required for priority-weighted
postproc:
  normalization: "percentile-clip-5-95"
  latency_slo_ms: 150
notify_on_fail: ["ml-evals@redwoodeval.internal"]
---

Example postproc snippet (pseudo-YAML) for priority-weighted:

weights:
  semantic-similarity: 0.4
  toxicity_rate: 0.4
  p95_latency_ms: 0.2
normalization: "1/(1+log(1+value))"

Acceptance matrix and thresholds
--------------------------------
Acceptance matrices must be checked into model-onboarding metadata and include:
- minimum safety pass rate by slice (e.g., safety >= 0.995 on all slices),
- global ensemble_score threshold (default 0.82),
- latency SLO tolerances (P95 <= configured SLO),
- allowed per-metric regressions from baseline (e.g., no more than 2% drop in semantic-similarity).

Default baseline policy (applies if team does not provide custom matrix):
- safety pass rate >= 0.998 on all slices
- ensemble_score >= 0.80
- no metric regressions > 3% compared to production baseline
- canary rollout limited to 5% traffic for 48 hours with monitoring hooks

Canary and rollback rules
------------------------
Canary rollout: on pass, deployment-orch will deploy model to canary cluster at 5% traffic. During canary the following automated checks run every 15 minutes:
- Production sampler run: compare online metrics with eval predictions for a random sample of requests (1 per 1000 requests or at least 1000 samples/day).
- Alert conditions: ensemble_score drop > 0.05 vs baseline OR safety failure spike > 0.01 absolute OR P95 latency increase > 25% -> trigger rollback.

Automated rollback sequence (executed by deployment-orch):
1) Pause canary traffic.
2) Demote model from canary and switch traffic to previous stable model.
3) Create incident and assign to on-call owner of model-service (see runbooks).
4) Persist failing eval artifacts and logs under job id for triage.

Regression triage flow
---------------------
1) Triage owner reviews per-slice deltas and pulls failing examples (eval-harness provides direct links).
2) If failure is dataset-related (label drift), tag dataset and schedule augmentation.
3) If failure is model-related (systematic hallucination/safety), open ModelRegression ticket with: baseline artifacts, counterexamples, per-slice metrics, and suggested mitigation (prompt tuning, quantization rollback, smaller context window).
4) For performance regressions, check runtime config (quantization profile, batching settings) and revert to last-known-good profile if needed.

Operational considerations and do's/don'ts
----------------------------------------
Do:
- Record weight justifications in job metadata.
- Use production frequency data for dynamic weighting when available.
- Always include safety metrics as separate slices (do not absorb safety into a single aggregate without explicit weight).
- Keep acceptance matrices in model-onboarding for auditability.
Don't:
- Hard-code weights in deployment scripts without provenance.
- Use raw latency numbers directly without mapping to SLO-based scores.
- Rely solely on aggregate scores; always require per-slice checks for safety and critical business slices.

Metrics and observability
------------------------
- metric-store: stores per-job, per-slice metrics with job_id and model_id tags.
- dashboards: ensemble-over-time, per-slice-breakdown, canary-sampler-comparison.
- alerts: configured in deployment-orch and routed to ml-evals and eng-sre channels.

Appendix: example of normalized score calculations
------------------------------------------------
Given metrics: semantic_sim=0.78 (higher better), toxicity_rate=0.002 (lower better), p95_latency_ms=120 (SLO=150)
Transform toxicity: 1 - toxicity_rate = 0.998
Transform latency: 1 - min(120/150, 1) = 0.2
Assume weights [0.5, 0.3, 0.2] -> ensemble_score = 0.5*0.78 + 0.3*0.998 + 0.2*0.2 = 0.39 + 0.2994 + 0.04 = 0.7294
