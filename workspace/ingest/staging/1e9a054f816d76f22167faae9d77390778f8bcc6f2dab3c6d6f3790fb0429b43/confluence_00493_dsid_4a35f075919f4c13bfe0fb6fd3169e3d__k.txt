Kernel State Redistribution and Roll-Forward SOP

Overview
======
This runbook documents the standard operating procedure (SOP) for redistributing kernel-managed execution state across GPUs and performing a roll-forward recovery when a traditional rollback (reinstating an older model or kernel bundle) is unsafe or unavailable. The focus is on minimizing customer-visible latency and preserving KV-cache / session-consistency while satisfying SLO guardrails.

Scope and when to use this SOP
-----------------------------
- Applies to sharded and single-GPU kernel topologies that maintain volatile execution state (KV caches, per-request scratch, compiled kernel state).
- Intended for incidents where:
  - a kernel variant becomes unresponsive or corrupt mid-epoch and a rollback would cause unacceptable latency/regression, or
  - partial state loss affects a subset of shards but continuing execution with reconstructed state is preferable to global fallback.
- Not for: full-node hardware failures with persistent disk loss (see node-replacement playbook).

Ownership and escalation
------------------------
- Primary owner: Serving Runtime Oncall (team: eng-serving-runtime).
- Secondary: Kernel/ Scheduling Squad.
- Pager escalation: if the runbook cannot bring request-service back within 5 minutes, escalate to SRE lead and declare P1.

Success criteria
----------------
- Target: 99% of in-flight sessions either complete without user-visible error or are gracefully migrated to a compatible fallback within SLA.
- Safety gates: token-consistency checks pass, KV cache rehydration success rate >= 95% for affected sessions, no silent divergence of session outputs after roll-forward.

Prerequisites and fast checks (0-2 minutes)
-------------------------------------------
1) Confirm incident classification: kernel corruption vs performance regression.
2) Check SLO dashboards: tail latency 95/99 quantiles, error-rate spike.
3) Run quick telemetry queries:
   - kernel_process_health{kernel=\"X\"} over last 2m
   - kv_rehydration_failures{shard=~\"affected.*\"}
4) If hardware-level alerts present (ECC, nvlink down), consult hardware runbooks — do not proceed with roll-forward.

High-level steps
----------------
1) Quiesce new admissions to the affected kernel cohort (2 channels):
   - Set admission controller tag: \"redistribute-only\" for experimental routes.
   - For high-severity incidents, flip canary routing rule to divert new traffic to fallback pool.
2) Mark kernel shards for snapshot extraction.
3) Extract consistent snapshots with lightweight freeze and copy protocol (see snippet).
4) Verify snapshot integrity and generate redistribution plan.
5) Perform state redistribution (shard relocalization) in parallel with live rehydration probes.
6) Monitor session consistency checks and release admissions once thresholds met.
7) Post-incident audit and write-up.

Detailed procedure (play-by-play)
--------------------------------
1) Quiesce and force admissions policy (operator, 0-1 min)
   - Run: 
     ```bash
     # route new traffic away from kernel-X cohort
     rctl set route --cohort kernel-x --policy divert --target-pool fallback-pool
     rctl tag cohort kernel-x set redistribute-only=true
     ```
   - Expected result: new requests are diverted or annotated so redistribution does not need to handle them.

2) Snapshot extraction (operator + kernel-scheduler, 1-3 min)
   - Goal: capture consistent KV cache and minimal execution metadata without halting in-flight generation.
   - Implementation pattern (incremental freeze):
     - Apply per-shard soft-lock: sets `frozen=true` for snapshot epoch.
     - Drain micro-batches for 200-500ms to allow deterministic cache flush windows.
     - Emit snapshot artifact to object-store: `s3://runtime-snapshots/<incident-id>/shard-<n>.tar.gz`
   - Example command (controller):
     ```yaml
     # snapshot job manifest (pseudo-yaml)
     job: snapshot-extract
     cohort: kernel-x
     epoch: 2026-03-01T12:34:00Z
     shards: [0..7]
     mode: incremental
     ````

3) Validate snapshots (kernel-scheduler, 1-2 min)
   - Run integrity checks: size sanity, checksum (sha256), schema validation.
   - Telemetry queries to confirm snapshot completeness: `snapshot_manifest_complete{incident=\"<id>\"}`
   - If any snapshot fails validation, mark shard for targeted re-extraction.

4) Redistribution planning (scheduler + operator, 1-3 min)
   - Build plan: mapping from source shards -> target GPUs. Consider affinity, NUMA, memory headroom, and thermal state.
   - Example planning table (human-readable):
     | source_shard | target_node | target_gpu | mem_headroom | reason |
     |--------------|-------------|------------|--------------|--------|
     | 0            | node-a      | gpu0       | 18GB         | underloaded
     | 1            | node-b      | gpu1       | 12GB         | hot-swap

5) Roll-forward redistribution (parallelized, 2-8 min)
   - Steps per target shard (automated operator actions):
     a) Allocate ephemeral slot on target GPU with `prewarm=true` to compile kernels and reserve KV memory.
     b) Stream snapshot artifact into slot and perform in-situ rehydration.
     c) Run deterministic probe (seeded micro-batch) to validate cache coherence.
     d) Promote slot to live routing (gradual weight ramp).
   - Example CLI (pseudo):
     ```bash
     runtimectl allocate-slot --node node-b --gpu 1 --slot-prewarm --labels redistributed
     runtimectl stream-snapshot --src s3://runtime-snapshots/<id>/shard-1.tar.gz --dest slot://node-b/gpu1/slotA
     runtimectl probe-slot --slot slotA --probe-seed sha256:abc123 --timeout 10s
     runtimectl ramp-route-weight --slot slotA --from 0 --to 100 --duration 30s
     ```

6) Consistency and divergence checks (continuous during roll-forward)
   - Checkpoints to observe:
     - per-session hash equality for deterministic probes: `session_output_hash{session=~\"migrated.*\"}`
     - KV miss ratio for migrated sessions should be <= 3% after 60s of promotion.
     - Token-level latency regression: tail p99 for migrated cohort must not increase more than 25% relative to baseline.
   - Abort criteria: any deterministic probe mismatch, KV rehydration failure > 5% for > 2m, or sustained p99 > 2x baseline.

7) Cutover and release (finalize, 1-2 min)
   - Once targets pass probes and metrics are within thresholds:
     - Promote routing weight to 100%.
     - Remove `redistribute-only` tags and re-enable normal admission.
     - Emit event: `incident.<id>.rollforward.complete` to the incident channel.

8) Post-incident and cleanup (10-30 min)
   - Deallocate ephemeral prewarm slots.
   - Archive snapshots with retention policy: keep hot snapshots 7 days, cold snapshots 90 days.
   - Create incident audit: attach snapshot manifests, metric timelines, and decisions.

Emergency roll-forward (when snapshots incomplete)
--------------------------------------------------
- If snapshot extraction fails for a shard but continuing service is required, we may perform a partial in-memory reconstruction:
  1) Identify compatible donor shard (same model variant, recent epoch).
  2) Copy best-effort subset of KV entries: high-frequency keys first (top-10k by recency).
  3) Mark reconstructed shard as "best-effort" with stricter monitoring flags.
  4) Notify product and CS if reconstructed sessions are customer-visible.
- Safety note: this step increases risk of subtle output divergence. Use only under explicit P1 authorization.

Telemetry and dashboards to monitor during procedure
--------------------------------------------------
- Essential metrics: `kv_rehydration_success_rate`, `probe_output_match_rate`, `cohort_p99_latency`, `admission_diversion_rate`, `slot_compile_errors`.
- Suggested dashboard panels (table):
  | panel | description | alert threshold | owner |
  |-------|-------------|-----------------|-------|
  | KV Rehydrate | % success per shard | <95% -> warn | Kernel Squad |
  | Deterministic Probe | match rate | <99% -> alert | Scheduler |
  | Tail Latency | p99 cohort | >1.25x baseline -> warn | SRE |

Safety concerns and fallbacks
---------------------------
- Rolling forward can mask deeper data-corruption bugs. If divergence persists post-rollforward, perform a conservative rollback to last verified kernel variant and notify security/product for deeper investigation.
- Maintain legal/compliance trace of snapshot artifacts—treat as sensitive if they contain customer prompt-derived identifiers. Follow security-and-compliance retention policy.

Runbook decision matrix (quick reference)
----------------------------------------
- If kernel unresponsive but memory intact -> attempt roll-forward.
- If nvlink/PCIe errors or ECC -> stop and engage hardware replacement.
- If snapshot integrity fails across >50% shards -> fallback to global model variant rollback.

Postmortem checklist
--------------------
- Collect: snapshot manifests, controller logs, probe outputs, compile errors.
- Quantify customer impact: sessions affected, requests timed out, cost of emergency slots.
- Action items: schedule root-cause analysis, follow-up kernel tests, and a small-run chaos test to validate the snapshot/recovery path.
