Tenant traffic shaping and KV consistency playbook

Overview

This playbook documents operational patterns, configuration examples, and an actionable runbook for combining tenant-level traffic shaping with the Redwood runtime's KV cache coherence guarantees. It is intended for field operators, SREs supporting private deployments (VPC or on-prem), and solution engineers implementing multi-tenant isolation policies.

Goals

- Provide deterministic per-tenant latency SLOs during bursty load by shaping ingress at the service-lattice boundary.
- Ensure KV/prefix cache consistency and safe eviction when traffic shaping reduces capacity for a tenant.
- Define upgrade and rollback steps for cache policy or traffic-shaper changes with minimal risk to tenant correctness.
- Offer concrete alert thresholds, dashboards, and troubleshooting steps for common failure modes.

Scope and assumptions

- Applies to private deployments (VPC-controlled or on-prem) running the Redwood inference runtime version 3.4+.
- Tenants may be dedicated (reserved GPUs) or multiplexed on shared pools. This playbook covers both modes but calls out differences where relevant.
- Assumes tenants are identified by tenant-id headers at the ingress edge and that the control plane has an authoritative mapping for tenant configs.

Architecture summary (text diagram)

Ingress (LB / Envoy) -> Tenant Shaper -> Service Lattice -> Router -> Inference Runtime (per-tenant routes) -> KV Cache (local + distributed) -> Model worker

Key concepts

- Tenant Shaper: Layer at ingress that enforces request rate, concurrency, and burst tokens per tenant. Can be implemented with Envoy rate-limit filter + Redis token bucket or with cloud-managed traffic shaping.
- KV Cache Coherence Window: The period during which runtime nodes schedule background coordination to ensure prefix KV caches remain consistent following eviction or migration. Default: 30s in 3.4.
- Eviction-safe-mode: A runtime flag that delays hard eviction of cached entries for a tenant while in-flight requests are drained. Recommended to coordinate with traffic shaping changes.

Configuration reference

1) Example tenant shaper (Envoy + Redis token bucket)

YAML snippet (Envoy filter config conceptual):

shaper_config:
  redis_service: redis-infra.private.svc.cluster.local:6379
  token_bucket:
    capacity: 2000  # tokens
    refill_rate: 100  # tokens/second
  rules:
    - tenant_id: "tenant-42"
      max_concurrency: 40
      max_rps: 800
      burst_tokens: 1200

2) Runtime KV policy (runtime-config.yaml)

kv_cache:
  coherence_window_seconds: 30
  eviction_safe_mode: true
  tenant_priority_buckets:
    - name: premium
      min_reserve_tokens: 500
    - name: standard
      min_reserve_tokens: 100

Operational SLOs and thresholds

- Per-tenant p95 latency: <= 200ms (generation path) under normal load.
- Per-tenant error rate: < 0.5% over 5m sliding window.
- Cache-coherence latency (time from model mismatch detection to revalidation): <= 60s.
- Guardrail: If 5-minute sustained dropped requests > 1% for a tenant, initiate mitigation runbook.

Monitoring and alerts

Critical alerts (page P1):
- TENANT_LATENCY_SLO_BREACH: p95 > 250ms for > 3m (notify oncall).
- TENANT_DROPPED_REQUEST_SPIKE: dropped requests > 1% sustained over 5m.
- KV_INCONSISTENCY_RATE: detected model output divergence after cache eviction > 0.1% across sample set.

Warning alerts (P3):
- SHAPER_REJECT_RATE: rejected requests > 0.5% over 5m.
- TOKEN_BUCKET_EMPTY: token bucket under 10% for a tenant for > 2m.

Dashboards (recommended panels)

- Per-tenant RPS, concurrency, rejected requests, token-bucket level.
- KV cache hit ratio and revalidation events per tenant.
- Recent model variant fallbacks and rollbacks.

Change procedure: adjusting tenant shaping or KV policy

1) Plan and test in staging
  - Create a staging tenant that mirrors production traffic shape.
  - Run synthetic workload at 1.25x expected burst for 30 minutes.
  - Validate cache coherence window and eviction behavior using the KV test harness (see test commands below).

2) Canary rollout (production)
  - Apply shaper change for 1% of tenants (tagged canary group) for 30 minutes.
  - Observe: rejected request rate, p95 latency, KV revalidation events.
  - If metrics stable, increase to 10% for 60 minutes; then 50% for 2 hours; then full.

3) Full rollout
  - Schedule a maintenance window for non-disruptive policy changes that touch min_reserve_tokens.
  - Coordinate with Customer Success for customers in the high-risk list.

Rollback criteria

- Immediate rollback if any of the following are triggered within 30 minutes of a change:
  - TENANT_LATENCY_SLO_BREACH fires for canary tenants.
  - TENANT_DROPPED_REQUEST_SPIKE > 1% sustained.
  - KV_INCONSISTENCY_RATE > 0.2%.

Runbook: immediate mitigation for a tenant experiencing increased drops after a shaping change

1) Triage (first 5 minutes)
  - Confirm alert details in PagerDuty and open incident in status tool.
  - Identify tenant-id and the last successful config change (config history service).
  - Check ingress shaper metrics: token bucket level, rejected requests, token refill rate.
  - Check runtime KV metrics: hit ratio, in-flight revalidations, coherence events.

2) Fast rollback (minutes 5–15)
  - If the shaper change is the latest config, revert to previous shaper policy for the tenant using the config API:
    curl -X POST https://controlplane.private/api/v1/tenant-config/revert -d '{"tenant_id":"tenant-42","target_revision":"-1"}' -H "Authorization: Bearer $CP_TOKEN"
  - Enable eviction_safe_mode=true in runtime for affected hosts (if not already enabled):
    ./runtime-cli set kv_cache.eviction_safe_mode true --hosts "host[1-4]" --auth-token $RT_TOKEN

3) Drain and redistribute (minutes 15–60)
  - If the tenant remains noisy, route new traffic for that tenant to an isolated pool (if available) or temporarily increase reserved tokens for the tenant:
    curl -X PATCH https://controlplane.private/api/v1/tenant-config -d '{"tenant_id":"tenant-42","traffic_shaper":{"burst_tokens":2000,"max_rps":1200}}' -H "Authorization: Bearer $CP_TOKEN"
  - Trigger KV revalidation:
    ./kv-tool revalidate --tenant tenant-42 --sample-size 500 --concurrency 10

4) Post-mortem and stabilisation (hours 1–24)
  - Collect request traces and sample inputs/outputs for 1 hour pre/post change.
  - If divergence observed, escalate to Applied ML for model/regression analysis.
  - Re-run the canary sequence with tighter telemetry sampling.

Troubleshooting checklist (common causes)

- Rejection due to token exhaustion: inspect redis latency and token refills. If Redis latency > 50ms, consider switching to local token-bucket caching for short windows.
- Cache churn due to low coherence window: increase coherence_window_seconds and monitor revalidation events.
- Misrouted headers: confirm tenant-id is present and normalized at the LB. Missing tenant-id causes requests to land on default/no-tenant bucket and will be rate-limited aggressively.
- Backpressure amplification: when shaper rejects, clients may retry immediately; enforce backoff headers and client-rate-limit recommendations in SDK.

Testing and verification commands

- Synthetic burst test (k6):
  k6 run --vus 200 --duration 5m scripts/tenant-burst.js --env TENANT=tenant-42 --out json=burst.json

- KV cache validation (sample):
  ./kv-tool sample-compare --tenant tenant-42 --samples 1000 --verbose

- Health check endpoint to confirm tenant is served and not degraded:
  curl -sS -H "X-Tenant-ID: tenant-42" https://runtime.private/healthz | jq

Backwards compatibility and upgrade notes

- Runtime versions before 3.4 do not support eviction_safe_mode and have a shorter coherence window. For upgrades from older runtime versions:
  - Schedule a dual-run policy where new version hosts are warmed with identical shaper configs for 48 hours before shifting traffic.
  - Run the KV revalidation harness after cutover and monitor divergence metrics for 24 hours.

Operational playbook for long term capacity incidents

1) If multiple tenants are experiencing sustained throttling due to cluster pressure:
  - Activate cluster-wide burst policy: temporarily increase global token refill_rate by 10% for 30 minutes.
  - Trigger autoscale for dedicated pools where possible.
  - If autoscale and token bumps are insufficient, activate pre-defined fallbacks: route lower-priority tenants to a cheaper model-variant with an explicit QoS header.

2) Communication checklist to customers:
  - Immediately notify impacted tenants via the customer status channel and include: what happened, mitigations in-flight, expected time to stabilize.
  - For high-risk customers, open a direct support bridge and share temporary traffic and KV state snapshots.
