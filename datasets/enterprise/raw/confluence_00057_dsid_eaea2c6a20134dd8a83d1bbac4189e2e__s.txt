SafeMode Degrader and Fallback Orchestration Playbook

SUMMARY

This document describes the SafeMode Degrader (SMD) — an operator-facing and automated orchestration subsystem used in Redwood private deployments to gracefully degrade service capabilities under capacity, thermal, or upstream network stress. It defines the decision trees, policy primitives, SLO thresholds, observability signals, deployment & testing steps, and rollback guidance for on-prem and VPC installations.

Use case and scope

- Primary goal: keep customer-facing APIs available and predictable by trading off non-essential or expensive work (large-model variants, long-context requests, non-critical caching) when infrastructure signals indicate imminent SLO violations.
- Scope: tenant-level and node-level degradation for Private (VPC/on-prem) control planes and runtime nodes. Not intended for hosted API mode.
- Audience: field operators, SREs, account engineers, and partner integration engineers.

Key concepts

1) Safemode Degrader (SMD)
- Lightweight policy engine that executes ranked degradation actions (degraders) when configured triggers fire.
- Runs as part of the operator agent on each control-plane node and as a central orchestrator in customer-managed control planes.

2) Degrader (action) examples
- reject-large-requests: drop or 429 requests exceeding configured token length per tenant.
- downgrade-model-variant: route new requests to quantized or smaller model family.
- kv-prefetch-disable: disable aggressive prefix/KV prefetch to reduce memory pressure.
- batch-size-limit: cap continuous-batching window to preserve latency.
- soft-throttle-embeddings: reduce embedding concurrency.
- cost-airgap: suspend non-essential billing-intensive background jobs.

3) Policy primitives
- trigger: metric + comparator + duration (e.g., node_gpu_util > 92% for 30s).
- priority: integer ranking of degraders; lower = higher precedence.
- scope: tenant | node | control-plane | region.
- duration: intended degrade duration and max_auto_rollback window (e.g., 5m, 30m, 2h).
- cooldown: minimum time after an auto-rollback before re-applying same policy.

SLOs and thresholds (recommended defaults)

- Availability SLO (API): 99.95% per tenant per 30d (target for Dedicated/Private).
- P50 latency (token response): <40ms local GPU workloads.
- P95 latency: <150ms; escalate to SMD if approaching 200ms sustained over 60s.
- GPU util: soft-trigger at 85% sustained 120s (candidate for preemptive degradation). Hard trigger at 95% sustained 30s (immediate action).
- KV cache evictions: >12 evictions/s per node sustained 60s = trigger.
- Swap/IO wait time: >20ms per second sustained 30s = trigger for throttling background tasks.

Observability signals and dashboards

- Required metrics (per node, per tenant): gpu_util, gpu_memory_free_mb, kv_evictions_per_sec, request_rate_rps, avg_tokens_per_request, p95_latency_ms, error_rate_5m, cold_start_count_1h.
- Derived signals: tenant_pressure = weighted(gpu_util, kv_evictions, request_rate).
- Alerts (suggested):
  - SMD:policy_fired (severity: warning) when any policy enters active state.
  - SMD:degrader_escalation (severity: critical) when primary degraders cannot restore SLOs and fallback to more impactful actions.
  - tenant:safemode_active (severity: info) with list of active degraders per-tenant.

Dashboard layout (recommended):
- Top row: cluster GPU utilization heatmap, node-level active policies, rolling error rate.
- Middle: tenant pressure scatter, per-tenant active degraders, latency P95.
- Bottom: recent auto-rollbacks, manual overrides, and operator notes.

Operator procedures

1) Pre-install checklist (field handoff)
- Confirm SMD version matches runtime compatibility matrix.
- Verify telemetry: required metrics exported and sampled at 10s resolution.
- Ensure RBAC: operators with "smd.operator" role and read-only auditors.
- Confirm emergency escape hatch: operator can force global-safemode-off with 2-person approval.

2) Deployment steps (central orchestrator + agent)
- (A) Stage: deploy SMD central controller in a tenant-isolated namespace.
- (B) Validate: run `redwoodctl smd validate --telemetry-endpoints` to confirm metrics ingestion.
- (C) Promote: enable dry-run mode for 24h to record policy triggers without enforcement.
- (D) Enable enforcement: flip `enforce: true` with staggered rollout to 10% of control-plane nodes for 15m, then 50% for 30m, then 100% if no regressions.

3) Runbook: responding to an SLO incident with SMD firing
1. Triage: identify affected tenant(s) using dashboard.
2. Check active degraders: `smdctl active --tenant <id>` (lists actions, priority, since).
3. Evaluate metrics: confirm the trigger condition and scope (node vs tenant).
4. If degraders restored latencies: monitor for 15m then mark incident resolved.
5. If not restored: escalate to next-priority degrader (see escalation table below) or perform manual intervention (model swap to smallest) and notify customer success.
6. Document operator action in incident log and add tags for post-incident review.

Escalation matrix (example)

- Stage 0 (preemptive): limit-batch-window -> reduces throughput, low customer impact.
- Stage 1 (non-disruptive): soft-throttle-embeddings, kv-prefetch-disable -> impacts throughput/accuracy slightly.
- Stage 2 (moderate): downgrade-model-variant -> lower token quality/latency improvements.
- Stage 3 (high-impact): reject-large-requests, global-rate-limit -> more customer-visible but preserves core availability.

Configuration examples

- Sample policy YAML (flat fields only):

  policies:
    - id: node_gpu_pressure_preemptive
      scope: node
      trigger:
        metric: gpu_util
        comparator: GT
        threshold: 85
        duration: 120s
      actions:
        - name: limit-batch-window
          priority: 10
          duration: 15m
          cooldown: 5m
    - id: tenant_severe_capacity
      scope: tenant
      trigger:
        metric: p95_latency_ms
        comparator: GT
        threshold: 200
        duration: 60s
      actions:
        - name: downgrade-model-variant
          priority: 30
          duration: 30m
          rollback_on: p95_latency_ms_LT_150
        - name: reject-large-requests
          priority: 40
          duration: 10m

- CLI sample: `redwoodctl smd apply policies.yaml --namespace redwood-smd --mode enforce`

Testing and validation

- Unit tests: policy evaluation functions, comparator math, cooldown logic.
- Integration: simulate node pressure using synthetic GPU-util generator and confirm action ordering.
- Chaos test: run controlled chaos where 2/3 nodes in a zone hit 98% GPU util for 90s and assert availability remains >99.5.
- Acceptance: run a 24h dry-run during a low-traffic window and review recorded actions before enabling enforcement.

Operator scripts and utilities

- smdctl (examples)
  - `smdctl list-policies` -> prints effective policy per-scope.
  - `smdctl simulate --policy-id tenant_severe_capacity --simulate-duration 120s` -> local dry-run trigger.
  - `smdctl active --tenant <id>` -> list active degraders for tenant.
  - `smdctl override --tenant <id> --degrader reject-large-requests --action disable --reason "Customer in maintenance window"`

Permissions and safety controls

- Two-person approval is required for: disabling all degraders in a customer environment, globally turning off enforcement, or forcing a stage-3 degrader.
- Audit logs: every automatic change and manual override must write an immutable audit event to the telemetry lake (retention 2y for enterprise customers).

Rollback and post-incident work

- Auto-rollback: configured by policy via `rollback_on` expression. Example: rollback when p95_latency_ms < 150 for 10m.
- Manual rollback: `smdctl rollback --policy-id <id> --reason "post-fix validation"` with a 2-person signoff annotation.
- Post-incident: run a root-cause analysis template that records root cause, which degraders triggered, why, and proposed config changes. Attach sample telemetry: time-series charts, raw logs (redact PII), and request traces.

Customer communication templates

- Notice for scheduled safemode trial: short email template with date/time, expected impact, and how to opt-out by requesting a maintenance window.
- Incident FAQ snippet: brief explanation of degraded features, expected customer-visible differences, and estimated restoration steps.

Compatibility and integration notes

- Runtime compatibility: SMD v2.1+ required for quantized-model routing. See compatibility matrix in referenced page.
- Private control-plane note: when running fully air-gapped, ensure time synchronization (NTP) across nodes; policy windows rely on consistent clocks.

Appendix A — Example operator checklist (quick)

1. Confirm telemetry ingestion and sampling rates.
2. Switch SMD to dry-run for 24h and collect triggers.
3. Review triggers and update priorities where actions are too aggressive.
4. Enable enforcement to 10% nodes for 15m, verify no SLO regressions.
5. Ramp enforcement as noted in deployment steps.
