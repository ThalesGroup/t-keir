LLM Sandbox Integration Workshop — Starter Kit

Overview
--------
This page is a hands-on workshop starter kit intended to accelerate engineering teams' first integration of a Redwood Inference SDK into a local sandboxed application. The kit bundles a reproducible dev environment, short lab exercises, example integration templates (Node.js + Python), and a canonical fixes table for the top support patterns we see during onboarding.

Goals
-----
- Reduce time-to-first-successful-call for devs integrating generation, chat, and embeddings.
- Teach safe failure modes and graceful degradation patterns that preserve UX while lowering token cost.
- Provide reproducible artifacts for ramp sessions and internal workshops.

Audience
--------
- Software engineers building product features with LLMs (front-end, backend, or full-stack).
- Solutions engineers running customer POC workshops.
- Developer experience engineers creating SDK examples and templates.

Prerequisites
-------------
1. Redwood developer account with a test API key (use a dedicated sandbox key for workshops).
2. Docker and Docker Compose installed locally (>= 20.10).
3. Node 18+ or Python 3.10+.
4. Git and a terminal emulator.

What you get in this starter kit
-------------------------------
- reproducible/docker-compose.yaml: local sandbox proxy (rate-limiter + cache layer).
- examples/node-app/ and examples/python-app/: small sample apps demonstrating generation + embeddings + streaming.
- templates/observability-mapping.yaml: recommended telemetry event names and fields.
- canonical-fixes.md: curated failure symptoms and deterministic fixes (short triage paths).

Workshop format (45–90 minutes)
------------------------------
1. 10 min: Overview + architecture diagram (local proxy, SDK, test harness).
2. 25–45 min: Hands-on labs (modules below).
3. 10–20 min: Failure injection & triage exercise using the included harness.
4. 10 min: Wrap-up, next steps, and where to open support tickets.

Architecture (text diagram)
-------------------------
Developer machine -> Local sandbox proxy (Docker) -> Redwood hosted API
- Local proxy responsibilities: local caching of prefixes, deterministic failure injection, simulated rate limits, token-cost meter.

Hands-on modules
----------------
Module A — Basic call and response (10 min)
- Objective: Make a simple generation call and render the stream.
- Node snippet (src/examples/node-app/index.js):

```js
import Redwood from '@redwood/inference';
const client = new Redwood({ apiKey: process.env.REDWOOD_API_KEY, baseUrl: 'http://localhost:8080' });
const resp = await client.generate({ model: 'redwood-1-small', prompt: 'Write a one-paragraph summary of Redwood Inference' });
console.log(resp.text);
```

Module B — Embeddings sync and local similarity (15 min)
- Objective: Index a small dataset with embeddings and perform a nearest-neighbor lookup locally (useful for RAG tests).
- Python snippet (src/examples/python-app/embeddings_example.py):

```py
from redwood import Client
cli = Client(api_key=os.getenv('REDWOOD_API_KEY'), base_url='http://localhost:8080')
vec = cli.embeddings.create(input='What is Redwood Inference?')
# store vec in local in-memory index for the workshop
```

Module C — Streaming resume + idempotency (10–15 min)
- Objective: Demonstrate how to resume partially received streams and ensure idempotent generation for retries.
- Pattern: attach a client-generated request_id, persist last_event_offset on client, and call /resume with request_id + offset.

Module D — Failure injection and graceful degrade (15 min)
- Objective: Practice safe fallbacks: cached responses, short-template fallback, and reduced-token stub when Redwood API is unreachable.
- Included proxy supports two failure modes: (a) random 5xx at 1–10% and (b) simulated rate-limit bursts.
- Client pattern checklist:
  - If error is transient (5xx), backoff + retry with exponential jitter up to 3 tries.
  - On 429, switch to lower-cost model variant and queue request for background refresh.
  - On unreachable: serve cached content or sanitized default with an event logged to telemetry.

Observability and telemetry mapping (short)
-----------------------------------------
We provide a recommended mapping file (templates/observability-mapping.yaml) with the following important events and fields:
- event: inference.request.sent -> fields: request_id, model, prompt_tokens, timestamp, route
- event: inference.response.streaming_chunk -> fields: request_id, chunk_index, bytes
- event: inference.error -> fields: request_id, code, message, retries, upstream_latency_ms

SLOs for workshop/demo context
------------------------------
- Cached responses: p95 < 50 ms.
- Local proxy round-trip to Redwood hosted API: p95 < 250 ms.
- Generation end-to-end for non-cached, small prompts (<= 128 tokens): p95 < 800 ms.

Sample local proxy docker-compose (excerpt)
------------------------------------------
```yaml
version: '3.8'
services:
  proxy:
    image: redwood/dev-sandbox-proxy:2026-02
    ports:
      - 8080:8080
    environment:
      - REDWOOD_ENDPOINT=https://api.redwood.ai
      - FAILURE_INJECTION_RATE=0.02
      - CACHE_TTL_SECONDS=300
```

Canonical fixes (common support patterns and deterministic actions)
-------------------------------------------------------------------
| Symptom | Likely cause | Immediate fix | Owner | Notes |
|---|---|---|---|---|
| 429 on warmup | Burst of parallel calls, no batch shaping | Apply client-side rate limiting (token bucket) and use model variant with higher concurrency | Customer eng / Dev | Use fallback queue and background refresh for warmed items |
| Partial stream + aborted on resume | Missing request_id or offset state | Ensure client stores request_id and last_offset; use /resume endpoint | DX team | See Module C code pattern |
| High token costs during early testing | Long, unbounded prompts and repeated retries | Insert prompt length guard, enable short-template fallback on retries | Product/Dev | Add cost-meter to telemetry events |

(If you prefer a plaintext canonical-fixes.md, use the included file in the repo.)

Triage playbook (3-step)
------------------------
1. Reproduce locally against the sandbox proxy (set FAILURE_INJECTION_RATE=0.0).
2. Collect diagnostics: request_id, SDK version, proxy logs, telemetry event ids.
3. If the issue persists against hosted API with same inputs, escalate to eng-serving-runtime and include bundle: request payload, full server-side logs, and pcap if network suspected.

Ownership and escalation
------------------------
- Owner for the starter kit artifacts: Developer Experience (internal alias: devx-team).
- First-line support: Customer Success for customer workshops; DevX for internal ramp sessions.
- Escalation path: devx-team -> eng-serving-runtime -> eng-infra.

Release checklist for workshop templates
--------------------------------------
1. Bump proxy image tag and run integration smoke tests.
2. Validate examples against the most recent SDK minor (Node 1.x, Python 0.9.x).
3. Confirm observability mapping aligns with current telemetry contract.
4. Tag the Git repo and publish a docs-site entry pointing to this page.
