Authorization Telemetry and Retention Playbook

Overview

Purpose: This playbook defines how Redwood collects, stores, and packages authorization and access telemetry (RBAC grants, role changes, token issuance/revocation, and enforcement events) to satisfy operational audits, incident response, and cross-border retention requirements. It prescribes retention tiers, collection topology, evidence packaging formats, and responsibilities for secure SDLC checkpoints that affect auth surfaces.

Scope: Applies to: Redwood cloud control plane, Dedicated control plane endpoints, Private/VPC control plane connectors, identity providers (IdPs) integrations, and runtime enforcement components (agentd, auth-proxy). Excluded: ephemeral developer-only test systems with no customer data.

Owners and escalation
- Primary owner: Security Platform (security)
- Secondary owners: Eng-Infra (cloud accounts), Eng-Serving-Runtime (runtime enforcement), Legal (compliance evidence requests)
- On-call escalation: PagerDuty security-oncall -> eng-infra -> legal-compliance escalation (see contacts table below)

Retention tiers and retention matrix
| Data type | Retention tier | Minimum retention | Encryption-at-rest | Region-specific handling | Example use cases |
|---|---:|---:|---:|---:|---:|
| AuthZ grants (role create/update/delete) | retention-primary | 7 years | AES-256-CMK | Retain in region of record; copy to legal-region on request | Regulatory audit, privileged access review |
| Token issuance/revocation events | retention-transient | 90 days | AES-256 | Keep 90 days; retain PII redaction rules | Incident recon, anomaly detection |
| Enforcement denies (401/403) with policy eval | retention-audit | 3 years | AES-256-CMK | Customer-specific options per contract | Security investigations, policy tuning |
| Admin console ACL snapshots | retention-snapshot | 2 years | AES-256 | Archived to cold storage after 180 days | Periodic attestation, audits |

Collection topology and sources
- Primary collectors: auth-collector-service (Kinesis stream), agentd sidecars (gRPC stream to collector), IdP webhooks (SAML/OIDC events)
- Ingress pipeline: source -> Kinesis -> processor (k8s) -> hotstore (Elasticsearch/ClickHouse) -> coldstore (S3 encrypted buckets)
- Telemetry attributes to capture: timestamp, principal_id, principal_type, action, resource, resource_type, policy_id, decision (allow/deny), decision_chain (list), request_id, request_context, region, correlation_id, retention_class

SLOs and monitoring
- Collection success rate: 99.9% (5m rolling) for control plane auth events
- Pipeline delivery latency: 95th percentile < 8s to hotstore for non-batched events
- Evidence package readiness for legal request: GET /evidence/:request_id must return initial manifest within 4 hours for standard requests, 24 hours for complex multi-region requests

Secure SDLC touchpoints
1. Pre-merge checks (CI): changes to auth-related code must include unit tests for decision logic, static analysis (policy linter), and pipeline integration tests that validate telemetry emission.
2. Staging: enable telemetry sampling at 100% on staging for 72 hours when releasing auth changes; collect snapshots and evaluate policy drift.
3. Release gating: release requires signed approval from security approver group if change touches policy evaluation or token lifecycle code.

Evidence packaging and manifest format
- Evidence package is a compressed archive with an index manifest (JSON). Minimal manifest fields: package_id, requester, time_range, sources, checksums, redaction_stamp, chain_of_custody_id.
- Example manifest (CLI-ready):
```json
{
  "package_id": "pkg-20270115-az1",
  "requester": "Legal / Audit",
  "time_range": "2026-12-01T00:00:00Z/2026-12-31T23:59:59Z",
  "sources": ["kinesis-auth-01","clickhouse-auth-audit"],
  "files": ["authz-events-20261201-20261231.ndjson.gz"],
  "checksums": {"authz-events-20261201-20261231.ndjson.gz": "sha256:..."},
  "redaction_stamp": "pii-masked-v1",
  "chain_of_custody_id": "coc-20270115-42"
}
```

Packaging commands (operator)
1. Create manifest and request extraction token:
```bash
export REQUEST_ID=$(uuidgen)
redwood-evidence create-manifest --package-id "$REQUEST_ID" --start "2026-12-01" --end "2026-12-31" --owner security@example.com
```
2. Run extractor (reads retention class):
```bash
redwood-evidence extract --manifest /tmp/$REQUEST_ID.json --output /tmp/$REQUEST_ID.tar.gz --regions us-west-2,eu-west-1
```
3. Verify checksums and upload to legal vault:
```bash
shasum -a 256 /tmp/$REQUEST_ID.tar.gz | tee /tmp/$REQUEST_ID.sha256
s3cmd put /tmp/$REQUEST_ID.tar.gz s3://redwood-legal-vault/requests/$REQUEST_ID --server-side-encryption=AES256
```

Chain-of-custody and audit trail
- Each extraction run generates a chain_of_custody_id which maps to: initiating_user, approval_ticket, extractor_version, host_fingerprint, sha256(file) and time. This record is inserted into the evidence-db (immutable ledger partition).
- Audit trail retention: chain_of_custody records retained for same duration as primary evidence for compliance traceability.

Incident response interplay
- If security incident references auth telemetry: IR lead files an evidence collection request using the incident template. Priority: P0 (active compromise) requests trigger expedited collection with the pipeline running in write-through mode and a full cold-store copy.
- Steps for IR lead:
  1) Open incident ticket and tag evidence-needed
  2) Call redwood-evidence create-manifest with time range and scope
  3) Approve expedited policy if P0 (security-oncall + eng-infra)
  4) Pull package and transfer to secure forensic host (HSM-wrapped key)

Risk and exceptions handling
- Risk type: Long-running retention exception (e.g., retaining tokens > 7y). Exception process: submit exception request -> include compensating controls (encryption to separate KMS, approval from Legal + CISO, associated SOD controls) -> store exception in exception register with expiration and review cadence.
- Exception template fields: exception_id, owner, justification, compensating_controls, approval_signatures, expiry_date, evidence_location.

Operational runbook: Quick play (extraction for auditors)
1. Verify requestor identity and scope (Legal or Compliance only)
2. Confirm retention class and region constraints
3. Generate manifest and run extractor in read-only mode
4. Upload package to legal vault and notify requester
5. Record chain_of_custody and close request ticket

Queries and useful examples
- Find all role changes for a principal (ClickHouse sample):
```sql
SELECT event_time, principal_id, action, resource, details
FROM authz_events
WHERE event_type = 'role_change' AND principal_id = 'user:alice@redwood.com'
ORDER BY event_time DESC
```
- Search denies with policy id and correlation id:
```sql
SELECT * FROM authz_events
WHERE decision = 'deny' AND policy_id = 'policy-privileged-access' AND correlation_id = 'ctx-1234'
```

Security controls and redaction
- PII redaction: before packaging, run redaction pipeline: remove headers: ip_address, client_fingerprint; mask user_display_name; transform email -> hash(email) unless legal-approved plaintext required.
- Encryption: evidence packages must be encrypted with a KMS CMK owned by Legal when moved to long-term vault. Transfer keys use envelope encryption and HSM for private key custody.

Metrics to report to compliance quarterly
- Number of evidence requests processed, median time-to-manifest, 95th percentile extraction latency, number of exceptions active, number of expedited P0 requests.
