SDK handoff and support runloop templates

Overview

This document provides a compact, battle-tested set of templates and an operational runloop to improve handoffs between SDK authors, developer experience (DevX) support, and customer-facing support teams. The goal is to shorten time-to-resolution for SDK regressions, telemetry mismatches, and runtime integration bugs while preserving reproducibility and postmortem quality.

Scope

- Applies to all Redwood first-party SDKs (JS, Python, Go, Java) and officially supported third-party adapters.
- Targets: integration regressions, mismatched telemetry, streaming edge-cases, and canonical patches (not product feature requests).

When to use this runloop

1. Customer or QA reports an SDK-related outage, degraded latency, or incorrect API surface behavior.
2. Observability detects repeated error cohorts tied to client SDK versions (>= 3 errors/minute sustained for 5 minutes).
3. Developer working on an SDK change cannot reproduce production behavior locally.

Quick summary of the runloop (3-phase)

1) Triage (15–30m): support identifies severity, captures minimal repro, flags telemetry cohort, and assigns an owner.
2) Repro & Fix (1–72h): SDK engineer reproduces, implements fix or mitigation, publishes a canary patch.
3) Rollout & Verify (1–7d): staged release, telemetry validation, customer communication, and retrospective.

Minimal Repro Template (copy into support ticket)

Purpose: capture the smallest amount of information that lets an SDK engineer reproduce the issue. Fill and paste into a ticket.

1) Short description (1 sentence):
   - e.g. "JS SDK v2.3.1: streaming response drops after 12s when using chunked uploads"
2) Severity: P0|P1|P2
3) Affected SDK(s) and exact version(s):
   - JS: redwood-js-sdk@2.3.1
4) Steps to reproduce (minimal):
   - Step 1: npm install redwood-js-sdk@2.3.1
   - Step 2: node repro.js (attach repro.js below)
5) Observed behavior (logs, status codes, stack traces):
   - Paste 10–20 lines of logs, include correlation ids (request_id) if available
6) Expected behavior: one sentence
7) Sample request payload (redact PII): attach as file or inline JSON
8) Telemetry cohort id or sample query output: attach link to dashboard or saved query
9) Customer contact (if external): email and preferred contact window

SDK Bug Issue Template (engineering backlog)

Title: [SDK][library][severity] Short summary
Assignee: SDK owner
Priority: P0|P1|P2

Description: include Minimal Repro Template output.

Acceptance criteria:
- Repro script demonstrates failure in CI and locally.
- Unit / integration test added that fails pre-fix and passes post-fix.
- Patch includes changelog entry and migration notes if API surface changed.
- Telemetry event published on fix then validated in canary traffic.

Testing matrix (example):

Telemetry Event Schema (recommended minimal fields)

We require a short, consistent telemetry schema for SDK errors to aid rapid grouping in detection queries. The following JSON illustrates the recommended event payload that SDK clients should emit for captured errors (SDKs should map to host telemetry pipeline).\nExample body (send as JSON to telemetry pipeline):
{
  "event_type": "sdk.error",
  "sdk_name": "redwood-js-sdk",
  "sdk_version": "2.3.1",
  "error_code": "STREAM_ABORTED",
  "error_message": "socket hang up after 12s",
  "request_id": "req_abcdef12345",
  "timestamp": "2027-01-12T21:09:05Z",
  "context": {"sequence_length": 1024, "model": "rw-v3-medium", "route": "/v1/generate"},
  "customer_id": "acct_9876"
}

Notes: the top-level "context" may be a free-form map, but the fields in the example are strongly recommended. Ensure PII is redacted prior to emitting.

Saved queries (examples)

- High error rate: count(sdk.error) by sdk_version where event_time > now() - 5m group by sdk_version having count > 3
- Streaming aborts: filter error_code = 'STREAM_ABORTED' and count > 1 in 10m

Support Handoff Checklist (one page)

1) Verify customer-reported reproduction using Minimal Repro Template. If not reproducible, capture network traces / HAR and escalate to engineering with "needs-more-info" label.
2) If reproducible: create SDK Bug Issue and attach repro and telemetry links.
3) Add temporary mitigation: feature flag, server-side throttle, or client default change. Give mitigation a TTL and document in ticket.
4) Assign SDK owner and set a fix ETA.
5) Notify Customer Success and the original reporter with clear next steps and expected ETA.

Canonical Fix TL;DR format (for KB)

- Title: 1 line summary of root cause and affected versions
- Symptoms: bullet list
- Root cause: 2–3 sentences
- Fix: patch version and brief description of change
- Workarounds: immediate action customers can take if they cannot upgrade
- How we validated: telemetry queries + test matrix results

Example canonical fix (short):
- Title: JS SDK 2.3.x streaming hangs due to missing keep-alive in chunked requests
- Symptoms: streaming payloads drop after ~12s, request_id shows ECONNRESET
- Root cause: Node HTTP agent default socketTimeout closed idle connection before next chunk
- Fix: set agent.keepAlive = true in low-level transport, add integration test for chunked streaming
- Workaround: set SDK option {streamingKeepAlive: true} until upgrade
- Validation: canary traffic (5% of production) for 48h, error rate back to baseline

Operational playbook: step-by-step run (example P0)

1) Alert triggers: high error cohort or on-call support page.
2) Triage owner confirms reproducibility within 15 minutes using Minimal Repro Template.
3) If not reproducible, collect HAR, debug logs, and escalate to "investigate-io" channel.
4) If reproducible, open SDK Bug Issue and start a short-lived bugfix branch with scope-limited change.
5) Publish canary package (npm/pypi) with tag `canary-support-<ticket>` and run automated canary job that mirrors customer traffic for 4 hours.
6) If canary passes, cut patch release, publish changelog, and schedule an orchestrated rollout (see Rollout checklist).

Rollout checklist

- Prepare release notes and KB canonical fix entry.
- Coordinate with Customer Success for targeted customer notifications.
- Release strategy: 10% -> 25% -> 50% -> 100% over 48–72 hours with telemetry validation at each step.
- If regression detected at any stage, revert to previous version and announce rollback.

Ownership and escalation

- Primary owner: SDK owner listed in SDK CODEOWNERS.
- Secondary owner: DevX on-call for SDKs.
- Escalation: if a customer-impacting regression cannot be mitigated within 8 hours, escalate to Director of Developer Experience and include incident bridge.

Postmortem & retrospective guidance

- Required for P0s: full postmortem within 72 hours. Include timeline, root cause, remediation, and follow-ups with owners and due dates.
- Run a retro with Support + SDK Engineers + QA to identify tooling or test gaps; add action items to the sprint backlog.
