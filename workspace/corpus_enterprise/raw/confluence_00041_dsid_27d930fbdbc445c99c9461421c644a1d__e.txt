Evidence Assembly Matrix for Regulatory Audits

Summary
-------
This page defines the Evidence Assembly Matrix (EAM): a concise, repeatable format for collecting, validating, and packaging technical evidence for regulatory audits (SOC 2, GDPR, HIPAA, PCI-DSS) and customer compliance requests. The EAM prioritizes reproducibility, minimal manual steps, and verifiable provenance for each artifact.

Scope and audience
------------------
- Scope: Redwood Inference platform components that generate or control security-relevant artifacts: API control plane, serving runtime, infra provisioning, audit pipelines, RBAC systems, and private deployment connectors.
- Audience: Security Engineers, Compliance Engineers, SREs, Incident Response, Legal/Security review, and Customer Trust teams.

Why we use an Evidence Assembly Matrix
-------------------------------------
- Single canonical source mapping regulations to artifacts and concrete collection steps.
- Reduces ad-hoc evidence requests during audits.
- Provides verifiable provenance and chain-of-custody metadata for each item.
- Enables automation where possible and clearly documents manual steps where automation is not feasible.

How to read the matrix
----------------------
Each row in the EAM corresponds to a single piece of evidence. Columns are: Regulation, Evidence ID, Artifact Type, Source Service, Collection Method, Retention Window, Custodian, Verification Procedure, Storage Location, Proof-of-Presence artefacts (hashes/logs). Example matrix rows are below. Use the "Evidence Collection CLI" (see section) to automate fetching when supported.

Evidence collection procedures
-------------------------------
1) Identify audit scope and required regulations. Confirm with Legal/Compliance what evidence IDs are required.
2) Retrieve EAM rows relevant to the scope. Filter by Regulation and Source Service.
3) For each Evidence ID:
   a) Attempt automated retrieval using Evidence Collection CLI.
   b) If automation is unavailable, follow the explicit manual steps recorded in the EAM row. Document the operator and timestamp.
   c) Compute and record cryptographic hash (SHA-256) of each artifact.
   d) Generate a manifest entry containing: Evidence ID, artifact filename, sha256, collected_by, collected_at (UTC), collection_method.
   e) Upload the artifact and manifest to the ephemeral evidence bucket for audit assembly.

Evidence Collection CLI (examples)
----------------------------------
- Purpose: standardize automated retrieval for supported sources (IAM, audit pipeline, config DB exports, console logs).
- Location: git@redwood:infra/compliance/evidence-cli.git
- Quick example:
  # export RBAC snapshot for a given date
  ./evidence-cli iam-export --date 2026-02-15 --output /tmp/eam-iam-20260215.json

  # pull audit logs for a 1-hour window (UTC)
  ./evidence-cli logs-dump --service api-gateway --start 2026-02-14T10:00:00Z --end 2026-02-14T11:00:00Z --out /tmp/gateway-logs-1000-1100.jsonl

Manual collection guidance
-------------------------
- Always use a separate workstation with MFA and compliance-approved device posture.
- For UI exports: capture a video (screen recording) of the export operation if the service does not provide an automated export; attach the recording to the manifest.
- Do not sanitize logs unless explicitly instructed by Legal; instead, request a filtered export with the Compliance Engineer present.

Manifest format (plain text)
---------------------------
- Example manifest line (one-per-artifact) – store in UTF-8 text: 
  EvidenceID: EAM-API-01 | Filename: iam-snapshot-2026-02-15.json | SHA256: <sha256sum> | CollectedBy: a.patel | CollectedAt: 2026-02-15T18:05:12Z | Method: automation | Location: s3://redwood-compliance/tmp/eam-20260215/iam-snapshot-2026-02-15.json

Verification and signing
------------------------
1) After artifacts are uploaded, run the verify-manifest tool: ./evidence-cli verify-manifest --manifest /path/to/manifest.txt
2) Verify-manifest performs: sha256 validation, schema sanity checks, and cross-checks expected artifact counts for the audit scope.
3) The Security Custodian signs the manifest with a GPG key and stores the signed manifest alongside artifacts. Example: gpg --sign --armor --output manifest.txt.asc manifest.txt

Chain-of-custody and immutable storage
-------------------------------------
- All artifacts intended for long-term retention must be copied into the immutable evidence bucket: s3://redwood-evidence-immutable/<regulation>/<year>/
- Immutable bucket has MFA-delete enabled and lifecycle rules to transition to cold storage after 180 days.
- Each copy operation must be recorded in the chain-of-custody log (COC), which is an append-only audit stream (Kafka topic: coc-evidence-events). The Evidence CLI automatically emits COC events on successful uploads.

Retention and purge controls
----------------------------
- Default retention per regulation: SOC2=3 years, PCI-DSS=6 years, HIPAA=6 years, GDPR=7 years for residency-related artifacts. See the EAM retention column for exceptions.
- Purge requests must follow the Data Retention Exception process: file a request in the Risk and Exceptions portal with explicit business justification and legal approval. Purge actions are recorded and require a two-person approval from Security + Legal.

Audit-ready packaging checklist
------------------------------
Before handing artifacts to auditors or legal, confirm:
- [ ] Manifest present and signed
- [ ] sha256 hashes verified
- [ ] Chain-of-custody entries present for each upload
- [ ] Access control on the package limited to the audit team and Security Custodian
- [ ] Any redaction or PII handling steps documented and approved by Legal

Escalation and SLAs
-------------------
- Evidence retrieval SLA for external audits: 72 business hours for standard requests, 24 business hours for executive-critical escalations (requires Legal approval).
- If evidence collection cannot meet SLA due to technical gaps, notify Compliance@redwood.com with a remediation plan within 8 business hours.
- Owner escalation chain: Security Custodian -> Head of Security (Lena Ortiz) -> Chief Security Officer (Rahul Sharma).

Periodic maintenance and audits of the EAM
-----------------------------------------
- The EAM CSV and automation scripts are reviewed quarterly by Security and Compliance.
- Run an internal mini-audit every six months: select a random subset of 10 Evidence IDs and validate collection, verification, and archival end-to-end. Failures must be remediated within 30 days with a postmortem.
