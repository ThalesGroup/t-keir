Extensible tool-call versioning and safeguard playbook

Summary

This playbook defines Redwood's standard approach for introducing, evolving, and deprecating tool-call (function/tool) APIs and their schemas across hosted, dedicated, and private deployments. It focuses on three goals: preserving customer runtime stability, enabling safe evolution of tool signatures and behavior, and minimizing costly rollbacks when incompatibilities surface.

Context and motivation

- Tool-calls are first-class in our generation/chat API surfaces. They allow model outputs to invoke structured functionality downstream (e.g., search, database queries, external tool execution).
- Tool schemas change frequently during product iteration (new params, removed fields, semantics). Without explicit guardrails, changes can cause production failures, user-visible regressions, or silent correctness issues.
- Private and on-prem deployments require extra caution: runtime-sidecar adaptors and compatibility filters must support graceful pivoting when the control plane pushes schema or behavior changes.

Scope

This playbook applies to:
- REST/streaming generation endpoints that expose tool-calling (hosted and self-hosted).
- Client SDKs that serialize and deserialize tool-call payloads.
- Runtime sidecars/adaptors used in Private deployments.
- Rollout automation and canary policies in the Redwood Console.

Key principles

1) Always additive-first. New optional fields and tools are preferred over changing existing field semantics.
2) Capability negotiation. Clients and runtimes must advertise supported tool schema versions and feature flags.
3) Fail-safe behavior. If a runtime cannot safely execute a tool-call due to schema mismatch, it must fall back to a safe no-op path and emit a clear diagnostic event.
4) Observability and guardrails. Every tool invocation must produce structured telemetry for lineage, validation failures, and user impact scoring.

Roles and ownership

- API Product: decides recommended schema expansion windows and backwards-compatibility constraints.
- Runtime (serving-runtime) team: implements adaptor shims, capability headers, and runtime fallbacks.
- DX/SDKs: provide client-side helpers for capability negotiation and migration warnings.
- Customer Success & Private-deployments: manage communication and upgrade coordination for private customers.

Compatibility model and headers

- All tool-call requests must include a Tool-Version header and a Capability-List claim in the request context. Example headers:

  Tool-Version: tool/search@v1.4.0
  X-Redwood-Capabilities: tool-call=stable,structured-params=v1.4,early-return=true

- The server responds with a negotiated Tool-Version and a Compatibility-Outcome field when the toolbox adapts or downgrades:

  HTTP/1.1 200 OK
  Negotiated-Tool-Version: tool/search@v1.3.0
  Tool-Compatibility-Outcome: downgraded (missing param: bounding_box)

Negotiation rules (ordered):
1. Exact match: if the runtime supports declared version, use it.
2. Minor-compatible downgrade: if runtime supports a lower minor version with identical semantics for required fields, downgrade and record outcome.
3. Safe fallback: if required fields are missing in runtime, return a capability rejection and route to safe fallback path.

Schema evolution lifecycle

- CHANGE TYPE: ADD OPTIONAL FIELD
  - Acceptable: immediate rollout.
  - Action: no tolerance window required. Clients should be resilient to unknown fields.

- CHANGE TYPE: PROMOTE OPTIONAL -> REQUIRED
  - Acceptable: after 90-day deprecation window and client-usage audit.
  - Action: publish migration guide, add server-side soft-reject flag for 30 days (return 422 with migration_hint).

- CHANGE TYPE: REMOVE FIELD or CHANGE SEMANTICS
  - Acceptable: never without clear migration plan.
  - Action: create a staged deprecation ADR, run automated compatibility tests (see Tests & gating), and schedule a phased rollout with canary and customer opt-in.

Runtime adaptors and shims (Private deployments)

- Sidecar behaviour: Private runtimes must ship a sidecar that can perform schema translation for common safe changes (rename, default-injection, minor-version mapping). The sidecar MUST NOT attempt to guess semantics for removed fields — it should reject with a clear diagnostic.
- Shipping a shim: sidecar shim must include a mapping table in YAML, signed artifact, and a checksum. Example shim snippet: 

  mappings:
    - from: tool/search@v1.4.0
      to: tool/search@v1.3.0
      transforms:
        - rename: { from: 'bbox', to: 'bounding_box' }
        - inject_default: { field: 'timeout_ms', value: 1500 }

- Security: shims that alter payloads must be validated by runtime-signing (HSM/KMS) and logged in audit trail.

Testing and gating

- Unit tests: schema-parsers in SDKs and runtime must have >95% coverage for boundary and optional-field behavior.
- Integration test matrix (automated):
  - Client vX + Server vY + Sidecar shim present/absent (matrix permutations).
  - Use our synthetic harness to exercise 10K tool-call permutations and flag any unexpected rejects or silent drops.
- Canary policy: 1% traffic for 72 hours, then 5% for 48 hours, with automatic rollback on these signals:
  - Tool invocation error rate > 0.1% (absolute) above baseline.
  - User-impact score increase > 0.5 (see Observability section).
  - Latency p95 increase > 25% for tool routes.

Operational playbook: rollout and rollback steps

1) Pre-release
   - Publish migration guide and release notes.
   - Add compatibility tests to CI (matrix above).
   - Signal private-deployment customers and schedule maintenance windows if shim installation is required.

2) Canary rollout
   - Enable new tool version for 1% of traffic using runtime routing rules.
   - Monitor the three automatic rollback signals and set alerts.

3) Ramp
   - After 72h with no trigger, ramp to 5% for 48h, then 20% for 24h, then full rollout if green.
   - During ramp, disable automatic pruning of unknown fields in SDKs (so clients surface schema issues).

4) Post-rollout
   - If pushing a version that promotes fields to required, start 90-day deprecation calendar and add server soft-reject.

Failure modes and mitigations

- Silent-accept (runtime ignores unknown required semantics): Requires immediate incident. Mitigation: identify affected routes, force negotiation failure to block malformed invocations, and revert routing.
- Shim-mismatch (sidecar applied an incorrect rename): Treat as data-corruption incident. Mitigation: revert shim, re-run migration test harness, and provide remediation script to affected customers.
- Client that cannot be upgraded: use per-tenant feature flags to continue serving an older behavior for up to 12 months and log a technical debt ticket for product follow-up.

Observability and telemetry requirements

Every tool-call must emit the following structured fields:
- tool.id (string)
- tool.version.requested (string)
- tool.version.negotiated (string)
- tool.compatibility.outcome (enum: exact|downgraded|rejected|shim-transformed)
- tool.validation.fail_reasons (list)
- user-impact-score (float 0..1) — derived from downstream error mappings

Retention and alerting: events are retained at high fidelity for 45 days for hosted customers and 90 days for enterprise customers. Alerts: create alert when tool.compatibility.outcome == rejected AND invocation-rate > 1/min for 5m.

Examples and snippets

- Example client negotiation (curl):

  curl -X POST https://api.redwood.ai/v1/chat/generate \
    -H 'Authorization: Bearer $TOKEN' \
    -H 'Tool-Version: tool/search@v1.4.0' \
    -H 'X-Redwood-Capabilities: tool-call=stable,structured-params=v1.4' \
    -d '{"messages": [{"role":"user","content":"Find restaurants near me"}], "tools": [{"id":"tool/search","params":{"q":"restaurants"}}] }'

- Example negotiation response: 

  {
    "id": "resp_123",
    "tool": {
      "id": "tool/search",
      "version": "v1.3.0",
      "compatibility": "downgraded",
      "notes": "bounding_box param not supported, defaulted to full-radius"
    }
  }

Tests and automation hooks (CI)

- Add a compatibility job that runs on every schema change PR. The job performs:
  - Schema linting (reject breaking changes without ADR).
  - Matrix-runpermutations using our ephemeral runtime testbed.
  - Generates a compatibility report artifact stored with PR.

- PR gating rule: any PR that modifies a tool schema must include a compatibility_report artifact and a migration.md file.
