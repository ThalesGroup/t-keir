Private Deploy Playbook — VPC & On‑Prem Packaging

Summary:
This playbook describes Redwood Inference's recommended process for delivering private deployments that run inside customer VPCs or on-prem clusters. It covers network reference architecture, packaging and installer options, day-2 operational procedures, and deterministic upgrade + rollback steps. Use this document during pre-sales scoping, delivery planning, and handover to SRE/Customer Success.

Goals:
- Provide a repeatable, audit-friendly delivery path for VPC and on‑prem deployments.
- Reduce downtime and customer risk by standardizing upgrade and rollback flows.
- Clarify customer minimal requirements and sizing expectations.

1) Quick architecture overview
- Supported deployment modes in this playbook:
  - VPC-hosted: customer-managed cloud VPC with private subnets, NAT, and optional Transit Gateway.
  - On‑prem k8s: customer-managed Kubernetes (>=1.24), with node pools for GPU and CPU and private registry access.
  - Hybrid (edge+cloud): control plane in Redwood Private with data plane inside customer network.

2) Customer prerequisites checklist (must be validated before kickoff)
- Network & connectivity:
  - BGP/VPN or AWS Transit Gateway/VPN: IP connectivity between Redwood control plane and customer VPC.
  - CIDR ranges: allow list for control-plane IPs (see Appendix A).
  - DNS: internal DNS for service discovery or split-horizon DNS configured.
- Identity & secrets:
  - KMS/HSM request approved and keys provisioned for at-rest encryption.
  - Service account (cloud) or dedicated namespace (k8s) with least privilege.
- Compute & storage:
  - GPU types required (e.g., A10G, H100) and minimum counts.
  - Block storage performance: 6000 IOPS baseline for model shards.
- Security & compliance:
  - Audit log sink (S3/GCS/SMB) and retention policy; TLS mTLS between services required.

3) Reference network topology (VPC)
- Minimum design (three-tier):
  - Public subnet: NAT gateway, bastion (optional).
  - Private compute subnet: inference nodes, autoscaling groups, EKS worker nodes.
  - Data subnet: persistent model stores and cache nodes (prefer separate AZ placement).
- Routing and SLOs:
  - Cross-AZ latency target: <= 5ms for KV cache lookups within region.
  - Egress policing: limit burst bandwidth for model downloads during rollout to avoid bucket storms.

4) Packaging and installer options
- Option A — K8s Helm bundle (recommended for cloud & on-prem k8s):
  - Releases baked as chart: redwood-runtime, redwood-proxy, redwood-operator.
  - Bundle verifies cluster prerequisites during helm pre-checks.
  - Example install:
    - helm repo add redwood https://packages.redwood.ai/charts
    - helm install redwood-base redwood/redwood-runtime -n redwood --create-namespace --set image.tag=2026.01.0
  - Supports values.yaml overrides for GPU nodeSelector, tolerations, and registry credentials.
- Option B — System packages + systemd (for air-gapped or non-k8s):
  - RPM/DEB installer with a declarative config at /etc/redwood/config.yaml
  - Systemd unit: redwood-runtime.service (restarts on failure, journald collection).
- Air-gap pattern:
  - Provide tarball of images and a signed manifest. Customer loads images into private registry and runs installer with --airgap flag.

5) Day‑2 operations (SRE checklist)
- Observability:
  - Ensure Prometheus scrape targets: redwood-metrics:9090, proxy:9100.
  - Logging: forward /var/log/redwood and container stdout to customer ELK/Datadog.
- Capacity management:
  - Autoscaling policy: target 70% GPU utilization; scale up policy 5–10 nodes at a time, cooldown 300s.
  - Warm pool: keep 10% reserved nodes for burst.
- Common runbook items (fast paths):
  1. Model cache saturation — clear LRU caches: curl -X POST https://redwood.local/admin/cache/evict
  2. High latency tail — verify CPU steal, inspect dmesg for OOM or GPU driver faults.
  3. Disk pressure — run offload: /usr/local/bin/redwood-offload --models older-than 30d

6) Upgrade procedure (standard k8s Helm path)
- Preconditions:
  - CI pipeline green for new tag; integration tests passed against staging.
  - Backup: snapshot model store and PVs, export Prometheus metrics for 48h window.
- Step-by-step:
  1. Announce maintenance window and enable read-only mode via API: POST /admin/maintenance {"mode":"drain"}.
  2. Increase replica counts of stateful services to maintain in-flight sessions (see scaling table below).
  3. Run helm upgrade with --atomic and --wait: helm upgrade redwood-base redwood/redwood-runtime -f production-values.yaml --timeout 20m
  4. Monitor SLOs for 30m. If errors exceed threshold (see rollback triggers below), initiate rollback.
- Rollback triggers:
  - 5xx rate > 2% for 10 minutes
  - Median latency increase > 100ms sustained for 15 minutes
  - Outage of >1 AZ in region

7) Rollback procedure (fast rollback)
- Fast rollback path (if helm used): helm rollback redwood-base <previous_revision> --wait --timeout 15m
- Manual rollback steps (if stateful changes applied):
  1. Revert configmap and secrets to previous version: kubectl apply -f previous-config.yaml
  2. Scale down new pods and scale up old replicas progressively (max surge = 20%).
  3. Validate session continuity: run smoke tests (smoke/run-smoke.sh) against /health endpoints.

8) Sizing & configuration reference (example table)
- Minimal production single-region (8k rps inference mix)
  - GPU nodes: 4 x A10G (16 vCPU, 64GB RAM)
  - CPU nodes: 3 x m5.xlarge for proxy & workers
  - Persisted storage: 5TB multi-AZ block store, 6k IOPS
- High‑availability production (50k rps)
  - GPU nodes: 16 x H100 (high-throughput)
  - CPU nodes: 12 x c6i.4xlarge
  - Cache layer: 3 x redis-cluster (m5.2xlarge)

9) Customer requirements library (pooled checklist for contracts)
- Contract-level items to capture in Statement of Work:
  - Network topology and IP allow-list
  - Dataset residency constraints and retention policies
  - Supported hardware list and replacement SLAs for failing GPUs
  - Backup frequency, restore RTO and RPO targets
  - Audit and log retention (minimum 1 year)

10) Troubleshooting appendix (common failure modes)
- GPU driver mismatch:
  - Symptom: CUDA initialization errors in redwood-runtime logs.
  - Fix: validate driver version and reinstall NVIDIA driver package matching runtime kernel.
- Model load hot-loop:
  - Symptom: repeated model load/unload and high S3 egress.
  - Fix: pin model versions, enable aggressive prefix cache, and throttle model download concurrency via config.download.max-concurrency=3
