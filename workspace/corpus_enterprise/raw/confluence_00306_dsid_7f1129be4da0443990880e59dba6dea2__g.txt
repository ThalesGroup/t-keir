GPU topology resilience checklist and canary protocol

Summary
-------
This page defines a cross-cutting resilience checklist and a lightweight canary protocol for topology and capacity changes to GPU pools (heterogeneous and homogeneous), networking, and Terraform/IaC promotions. The goal is to reduce blast radius from infra changes that affect inference latency, allocation failures, or egress/networking reliability. This is a living team‑wiki reference intended for infra engineers performing topology/placement changes, image promotions, and CI/CD pipelines that touch GPU runtime components.

Scope
-----
- Changes to GPU pool topology (adding/removing zones, changing instance types, hetero-packing rules)
- Terraform module promotions that alter placement, subnets, or host networking
- CI/CD image promotions for GPU runtime containers and kernel modules
- Network egress/path changes that affect routing between inference tiers and model store

Goals and success criteria
-------------------------
- No more than 1% increase in 95th/99th percentile token latency for affected routes during canary window.
- Allocation success rate >= 99.5% for customer traffic to existing pools; new pool target >= 99% after canary.
- No silent data-plane divergence (cache/kv inconsistency) after topology transitions.

High-level approach
-------------------
1. Preflight: automated checks (Terraform plan, CI image smoke, network path validation).
2. Canary: route a small, observable fraction of traffic to the changed topology.
3. Monitor: automated guardrails (alerts, Canary SLOs, error budgets).
4. Promote or rollback: decision window with clear thresholds and owners.
5. Post‑mortem & config capture: record plan, metrics, and artifacts.

Preflight checklist (quick table)
--------------------------------
| Check | Tool/Command | Acceptable threshold | Owner |
|---|---|---:|---|
| Terraform plan diff size | terraform plan -out=plan.tfplan | < 15 resource changes (manual review otherwise) | infra‑iac |
| New AMI / image signature | cosign verify | verified | ci-cd |
| Kernel/driver compatibility smoke | canary-smoke.sh (local runner) | passes full smoke (exit 0) | runtime |
| Network ACL / route overlap | net-checker --compare | no overlapping CIDRs in target account | cloud-net |
| Capacity forecast | capacity-forecast --window=6h | delta < 10% of baseline reqs | capacity-planning |

(Examples) cli snippets:  
- terraform plan -out=plan.tfplan && terraform show -json plan.tfplan | jq '.resource_changes | length'
- ./ci/canaries/canary-smoke.sh --image gcr.io/redwood/runtime:2025-02-canary

Canary protocol (step-by-step)
------------------------------
1) Preparation (T-60 to T-15 minutes)
   - Owner: the engineer who authored the change.
   - Verify all preflight checks pass. Attach plan and image digest to the change ticket.
   - Communicate: post a short note to #infra‑deploys with expected start, potential impact, and rollback windows.

2) Canary deploy (T=0)
   - Create canary pool with explicit tags: redwood:canary=true, topology: <name>.
   - Terraform: apply with -target to avoid wide changes: terraform apply -target=module.gpu_pool.canary
   - CI/CD: promote runtime image to a canary channel (do not overwrite stable tag).

3) Probe and probe routing (T=+0 to +30m)
   - Probe traffic: looped synthetic requests with representative prompt lengths and batch sizes. Use canary-prober from infra repo.
   - Traffic routing: incremental traffic shift using routing policy (example internal CLI):
       redwood route set-weight --route inference-prod --variant canary --weight 0.02
   - Observability: enable detailed tracing for canary token ids (trace_sampling=100%) for first 15 minutes.

4) Monitoring and guardrails (continuous during window)
   - Primary metrics to watch (Prometheus/Grafana / Redwood Console):
       - allocation_success_rate{pool=canary} (target >= 99%)
       - token_p99_latency_ms{route=inference-prod,variant=canary} (target <= baseline_p99 * 1.01)
       - OOM or driver_restarts{node_type=gpu} (should be 0)
       - model_cache_miss_rate (must not increase > 2%)
   - Prometheus alert examples (evaluate in your own Alertmanager rules):
       - alert: CanaryAllocationDrop
         expr: (1 - sum(rate(allocation_success_total{pool="canary"}[5m])) / sum(rate(allocation_request_total{pool="canary"}[5m]))) > 0.005
       - alert: CanaryLatencySpike
         expr: histogram_quantile(0.99, sum(rate(token_response_latency_seconds_bucket{variant="canary"}[5m])) by (le)) > baseline_p99_seconds * 1.01

5) Decision window (T=+30m to +90m)
   - If all metrics are within thresholds for 30 continuous minutes, increase weight to 10% and re-evaluate for another 30 minutes.
   - For heterogeneous hardware changes, extend evaluation to 3x longer (min 90m) because memory/packing interactions may appear over time.

6) Promote or rollback (T=+90m or when criteria met)
   - Promote: merge Terraform change from canary-target to full apply, remove canary tag, update image stable channel, and update runbook notes.
   - Rollback: shift weight to 0 immediately, taint problematic nodes, run terraform destroy on canary resources, and open incident if allocation failures > 0.5%.

Terraform / IaC promotion guidance
---------------------------------
- Use isolated module targets for canaries: keep canary module path separate from main module (module.gpu_pool.canary).
- Always check plans for implicit resource replacements (lifecycle changes). If plan indicates replacement of >10% of pool, escalate for manual review.
- Add a short plan summary to the change ticket with resource counts and provider-level diffs.

Example terraform snippet (canary pool)
--------------------------------------
module "gpu_pool_canary" {
  source = "git::ssh://git@repo/redwood-iac.git//modules/gpu-pool?ref=stable"
  name   = "inference-gpu-canary-${var.env}"
  min_nodes = 2
  max_nodes = 6
  node_type = "a10g"
  tags = { "redwood:canary" = "true" }
}

CI/CD specifics (image and kernel)
----------------------------------
- Build artifacts must be signed and promoted through CI channels: canary -> staging -> stable. Use signed digests (sha256) in Terraform/Service config; never rely on mutable tags.
- Buildkite snippet for canary promotion (example):
  - label: ":docker: publish canary image"
    command: |
      docker build -t gcr.io/redwood/runtime:${BUILDKITE_COMMIT} .
      cosign sign --key ${COSIGN_KEY} gcr.io/redwood/runtime:${BUILDKITE_COMMIT}
      gcloud container images add-tag gcr.io/redwood/runtime:${BUILDKITE_COMMIT} gcr.io/redwood/runtime:canary --quiet

Networking considerations
------------------------
- Ensure egress NAT pools are provisioned in canary region and that SNAT CIDRs align with kernel bypass rules.
- Validate cross-account VPC routes using net-checker and confirm no blackhole routes in the next 48h by running a traceroute sweep against a known model-store endpoint.
- If BGP/eBPF changes are in scope, schedule a rolling canary across a single AZ first.

Runbook: emergency rollback (quick steps)
----------------------------------------
1. Set route weight to 0: redwood route set-weight --route inference-prod --variant canary --weight 0
2. Mark canary nodes unschedulable and drain: kubectl cordon && kubectl drain --ignore-daemonsets
3. terraform destroy -target=module.gpu_pool.canary -auto-approve
4. Revert any image promotions: retag stable to previous digest and restart deployment.
5. Notify stakeholders (#infra‑deploys, oncall) and open a postmortem ticket.

Post-promotion capture
----------------------
- Save terraform state snapshot and attach to change ticket.
- Export three-minute and thirty-minute aggregates for primary metrics and attach graphs.
- Record the build digest, kernel/drivers, and node AMI/firmware.

Notes and caveats
-----------------
- Heterogeneous pools require longer observation periods due to packing/eviction nonlinearities. Expect to extend canary windows for significant instance-type changes.
- This protocol is intentionally conservative for production inference routes; for lower‑priority eval or staging workloads a shortened window with higher traffic percentage is acceptable.

If you are about to run a change that touches more than 20% of total serving capacity, escalate to a blue/green migration plan and coordinate with oncall SRE for a scheduled maintenance window.
